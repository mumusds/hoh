# 产品定义｜HoH

版本：设计基线 HOH-BASELINE-1.1（revision 5，CR-001/002/003/004）；实现状态：M0 完成，产品功能未实现。本文记录已采纳的产品决定，不把设计描述成现成功能。

## 目标与价值

让用户在熟悉的 Coding Agent TUI 中，与可配置的工程团队协作，从明确的产品规格持续推进到有证据的软件交付。核心价值是规范、持续进展、可恢复、独立验证与看得懂的工程过程，而非堆叠 Agent 数量。输入可以是一句话，但复杂产品必须先收敛规格；明确的小修复采用 Lite 流程。

目标用户为个人开发者与小型工程团队，已有 Codex、Claude Code、Pi 使用习惯，愿意在独立 Linux VM 运行较高自主性的开发任务。第一版按单机、单使用者、多项目设计；同一项目只有一个拥有写租约的活动开发分支。

## 成功定义

可持续完成“理解→规格→任务→实现→独立测试/审查→修复→验收”；所有结论可追溯到原始执行证据。TUI 的 Ask、指令与工程进度连续，不要求用户学习 Workflow DSL。关闭 UI 不中断已接受的任务。故障恢复不重复破坏代码，不篡改失败历史。

产品指标：已验收需求变化、需求遗漏率、回归捕获率、错误验收率、每有效增量的模型/执行开销、恢复正确率、用户干预次数。分别测量模型、调度、测试耗时，不能用“总 token 数增加”证明能力进步。所有具体数值门槛见 PRD 与验收文档，它们是拟定工程目标，不是已经测出的成绩。

## 范围

v1 完整范围包括三个原生 Agent 适配器、可配置角色、双层编排、规格与模板/Skill、四层 Prompt、三插件集成、CLI/TUI/Web、事件与需求追踪、恢复、独立验收、部署与使用文档。先完成某里程碑不等于可以删掉其余范围。

非目标：训练模型；取代三个底座的工具/编辑/压缩实现；多机分布式执行；多人审批平台；插件商店；移动端；默认多写者；扫描和修改主机隐私设置；在 VM 内再建复杂权限沙箱。项目质量和版本完整性仍是核心要求。

## 产品心智模型

“我向团队提出目标，Commander 负责整体决策，CTO/Developer 构建设计和代码，QA/Reviewer 验证；HoH 把全过程可靠地运行并展示出来。”职位不等于进程，模型能力不应写死为品牌定律。默认绑定体现用户偏好，实际能力以安装探测和任务实测为准。

## 自主性的现实边界

模型认证、网络、服务额度和外部部署权限来自用户环境；HoH 不能创造它们。预算与需求不足时给出 BLOCKED/INCOMPLETE，而非自称完成。自动安装工具仅使用明确配置的来源，记录版本；用户可自己选择模型，不假定某未核验模型永远存在。
