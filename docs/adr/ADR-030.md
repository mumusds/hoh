# ADR-030 · 能力匹配与缺员：fallback 选择、缺员的阻塞与恢复、兼容套件闸门

状态：提议（2026-11-13；M2-T15；第一版，待设计审查）

## 背景

## 决定

1. **模块与在 tick 中的位置。**
   - 纯函数在新模块 `hoh_core::staffing`（crates/hoh-core/src/staffing.rs：事实、判决、选择、绑定的判定）；store 侧在新文件 crates/hoh-core/src/persistence/staffing.rs（读输入，一个判定写一个事务）；host 侧 `host::agents::staff` 取代 `bind`（agents.rs:466-505）。
   - 它在 tick 里就在 `bind` 的位置（crates/hoh-app/src/host/runner.rs:557-570）：checkpoint 之后，首个输入投递、对账、pace 与调度轮之前。所以 ADR-020 决定 5 的“fallback 选择放在调度前能力检查之前”成立：同一 tick 里 staffing 先写绑定，pace 与调度轮读它。
   - 没有注册表的 host（脚本化执行器）不运行 staffing，与今天不运行 `bind` 相同；决定 7 的 pace 规则不依赖注册表。
   - `runner_waiting` 的 `unbound` 换成 `staffing: Vec<Staffed>`：每个未结束 Run 的每个绑定，带 agent、model、role_epoch、state、blocked_reason、missing、会话的 (agent_version, capabilities_json)、live、`order`（决定 3）、所需能力与排除记录（决定 6）；已移除的职位照旧排除（team.rs:1078-1081）；配置修改待生效（`team::pending`，team.rs:467-489）的职位也排除，那是 checkpoint 的事（ADR-022 决定 8）。runner.rs:544 与 :578 随之改读它（:578 改为“本 tick 没有 staffing 的写入”）。

2. **Agent 的事实（Q3）。** `staffing::Fact`（每个 Agent 名一个，host 从注册表得出，交给纯函数；表里没有即未查看）：
   - `NotInstalled(d)`：`ProbeError::NotFound`。
   - `Unsupported(d)`：`ProbeError::Unsupported`，以及 `session_capabilities` 失败（M2T07R-260 的第二种情形）。
   - `ProbeFailed(d)`：`TimedOut`、`NotStarted`、`Failed`、`Io`、身份戳读不出——暂时的。
   - `LoginMissing(d)`：登录状态命令明说未登录（ADR-024 决定 7），或 turn 发现的缺认证（下文）。
   - `Usable{version, session: Value, granted: BTreeSet<String>, compat: Compat}`，`Compat` 为 `Verified`、`Pending(why)`、`Failed(why)`（决定 9）；`granted` 用 `decision::granted_capabilities`，与 `load_binding` 同一函数。

   注册表的改动（agents.rs）：`Seen.outcome` 存 `Result<Ready, Probe{class, detail}>`，class 取自 `ProbeError` 的变体（:38-41、:199-214）；暂时类不按身份戳缓存，至少每 30 s（`AUTH_EVERY`）重新探测；`Ready` 带探测的 `AgentEntry` 与 `Stamp`，并缓存 `session_capabilities(agent, 项目根)`（每次实际查看算一次）；想要查看的 Agent（team.rs:1017-1041 的 `agents`）加上每个绑定所在 revision 中该职位的 fallback 列表，所以候选也被查看；`Registry::facts(names)` 给出 `BTreeMap<String, Fact>`；`Observation`（crates/hoh-core/src/decision.rs:164-169）加 `verified: bool`（该 Agent 为 `Compat::Verified`），供决定 7、11。

   **turn 发现的缺认证是 Agent 的事实**：`Registry::turn_auth_failed(agent, attempt_id)` 记在内存里，使该 Agent 为 `LoginMissing("turn <attempt> failed BLOCKED_AUTH")`，作用于绑到它的每个职位。只在三种恢复事实之一出现时清除：之后的登录查看先说“未登录”、再说“已登录”（看得见的转变）；该 Agent 的身份戳变了；host 重启（内存清空，至多再失败一次，决定 13）。只说“已登录”的查看不清除它：状态命令可能一直这么说，而按时间重试违反 REQ-020 行为 7。runner.rs 中把结局交给 store 的各处（`runner_finished`：:862、:892、:928、:960、:998、:1222）改经一个 `finished()`：结局为 Auth 类时先调 `turn_auth_failed`，再交给 store。

3. **判决与选择（Q1、Q4，AC-020-01）。** `staffing::verdict(agent, required, facts, excluded) -> Verdict`，按次序取第一个成立的：
   1. 未查看 → `not_looked_at`；`NotInstalled` → `not_installed`；`Unsupported` → `unsupported`；`ProbeFailed` → `probe_failed`；
   2. `LoginMissing` → `BLOCKED_AUTH`；`Compat::Failed` → `COMPAT_UNVERIFIED`；
   3. 在 `excluded` 中且记录的版本等于事实的 version（决定 6）→ 记录的 `MODEL_UNAVAILABLE` 或 `BLOCKED_CAPABILITY`；
   4. `required ⊄ granted` → `CAPABILITY_UNSUPPORTED:<缺的能力名，排序，逗号连接>`；
   5. `Compat::Pending` → `compat_pending`；否则 `usable`。

   - 判决的**行**是 `<agent>:<code>`：`pi:not_installed`、`X:CAPABILITY_UNSUPPORTED:resume`、`claude:BLOCKED_AUTH`；细节只在证据对象里（决定 5）。
   - 原因码只用 `$defs.BlockedReason` 已有的：not_looked_at、not_installed、unsupported、probe_failed → AGENT_UNAVAILABLE；BLOCKED_AUTH；COMPAT_UNVERIFIED、compat_pending → COMPAT_UNVERIFIED；MODEL_UNAVAILABLE；BLOCKED_CAPABILITY、CAPABILITY_UNSUPPORTED（ErrorCode，已在 ReasonCode 中）→ BLOCKED_CAPABILITY。小写的 `not_installed` 等是细节文字，不是原因码。
   - **永久**（REQ-020 决定 3：评估 fallback）：not_installed、unsupported、BLOCKED_AUTH、COMPAT_UNVERIFIED、MODEL_UNAVAILABLE、BLOCKED_CAPABILITY、CAPABILITY_UNSUPPORTED。**等待**（不评估 fallback）：not_looked_at、probe_failed、compat_pending。
   - `staffing::select(order: &[String], required, facts, excluded) -> Selection{chosen, waiting_on, evaluated}`：按 `order` 逐个求判决并记入 `evaluated`；`usable` → chosen，停；等待类 → waiting_on，停；永久类 → 下一个；走完则两者皆空。
   - `order` = 绑定所在 revision 中该职位的 `[agent] ++ fallback`（配置保证不重复、不含自身）；revision 没有记录时为 `[绑定的 agent]`（没有 fallback）；绑定的 Agent 不在其中时（手写的行）放在最前。不在 `order` 中的 Agent 从不被求值（REQ-020 行为 3，AC-020-01 的 codex）。
   - 输入是 Agent 名字符串与 `BTreeMap`/`BTreeSet`，没有 HashMap、时钟或随机数，所以 AC-020-01 的“X”这样的名字也能进入；`Selection` 序列化为 `{"chosen", "waiting_on", "evaluated": [行…]}`，同一输入逐字节相同。

4. **绑定的判定（Q1、Q2、Q5、Q6、Q8）。** `staffing::judge(&Staffed, facts) -> Judgment`；live 与 checkpoint 同义（该 Run 该职位有 PREPARED/STARTING/RUNNING 的 Attempt，team.rs:556-568，含监督 Attempt）。记 c = 绑定的 Agent，v = verdict(c)：

   | v | 绑定 | 判定 |
   |---|---|---|
   | usable | 无会话 | `Grant`：授予会话（`bind_session`），BLOCKED 的同时回 ACTIVE |
   | usable | 会话新鲜：`agent_version`、`capabilities_json` 等于事实的 version、session | BLOCKED → `Unblock`；ACTIVE → 无 |
   | usable | 会话陈旧（升级、能力变化） | `Rebind`：同一 Agent 与模型，epoch+1，新会话（Q6） |
   | not_looked_at、compat_pending | 任何 | 无（有会话的照常派发，由决定 9 的闸门逐个 Attempt 拒绝） |
   | probe_failed | 任何 | `Block(AGENT_UNAVAILABLE, ["<c>:probe_failed"])`，不评估 fallback |
   | 永久 | 任何 | s = select(order)：s.chosen = a → `Switch(a)`；s.waiting_on 且绑定 ACTIVE 无会话 → 无；否则 `Block(v 的原因, missing = s.evaluated 的行)` |

   - **粘滞（Q2）**：c 可用时不求选择，所以换到 fallback 之后不因首选恢复而换回；c 自己永久不可用时从 `order` 头部重选（首选已恢复即回到它）；修改了该职位的新 revision 由 checkpoint 照 ADR-022 决定 8 生效，未修改的职位随 revision 推进、留在 fallback。
   - **模型（Q8）**：`Switch(a)` 时 a 等于配置的首选则取配置的 model，否则为 NULL（Agent 的原生默认；Attempt 记 resolved_model）；`Rebind` 保留绑定的 model。
   - “s.waiting_on 且 ACTIVE 无会话 → 无”只为启动时的次序：首选已查看而候选尚未查看时，不先写一次失效再换绑；这样的绑定本来就不派发。

5. **判定的写入（REQ-020 行为 2、4，REQ-019 行为 1、2）。** `Store::staff(StaffChange)` → persistence/staffing.rs 的一个 IMMEDIATE 事务：以 (run, role, role_epoch, agent) 为条件（与 `bind_session` 相同，不再匹配即无操作并返回 false），并在事务内重新判 live。
   - **证据**：Block 与 Switch 之前，host 把每个被求值候选的 `{agent, line, probe:{class, detail, cli_version, launcher_path, implementation_sha256, help_sha256, schema_sha256, capabilities, observation:{host_epoch, n}}}` 组成数组，规范化为 JSON，经 `objects::put`（crates/hoh-core/src/objects.rs:73）存为对象；事务以 `runner::register` 登记 artifact 行，事件带 `probe_artifact_id` 与 `probe_sha256`（AC-020-02 的“引用 probe 证据”）。对象写不进时本 tick 不写这一判定，下一 tick 重来：没有证据就不换绑、不阻塞（这期间闸门照样拒绝不可用的 Agent，K3）。
   - **staffing 事件的 id**：同一 (run, role, epoch) 的为 `child_id(run, "staffing/<role>/<epoch>/<n>")`，n 为该前缀已有事件数加 1（`events.event_id` 唯一索引上的范围计数，不按条目扫 JSON，ADR-025 决定 5 的规则）；按 seq 最近的一条是这个 epoch 的 staffing 状态。
   - **种类**：`team.binding_blocked{run_id, role, role_epoch, agent, reason, missing, evaluated, probe_artifact_id, cause: "staffing"|"turn", attempt_id?}`（角色失效：ADR-025 决定 1 唤醒 Commander；只在进入 BLOCKED 或 (reason, missing) 改变时写）；`team.binding_unblocked`；`team.binding_change_pending{cause: "fallback"|"rebind", to}`；`team.binding_change_withdrawn`。只有 `team.binding_blocked` 唤醒；其余与替换事件、套件事件都只进下一次唤醒的摘要。
   - `Block`：`state='BLOCKED', blocked_reason, missing_json`（会话保留）与 `team.binding_blocked`。`Unblock`：`state='ACTIVE', blocked_reason=NULL, missing_json='[]'` 与 `team.binding_unblocked`。`Grant`：`bind_session`（team.rs:1094-1151），其 WHERE 由“BLOCKED 且 AGENT_UNAVAILABLE”改为“BLOCKED 且原因属于缺员集合 V”（决定 7）。
   - **`Switch(a)` 且无在途**，一个事务（REQ-019 行为 2）：
     - 绑定不是同一原因的 BLOCKED 时先写 `team.binding_blocked`（失效事件）；
     - `UPDATE role_bindings SET agent=a, model, role_epoch=role_epoch+1, session_id=NULL, state='ACTIVE', blocked_reason=NULL, missing_json='[]', bound_at`，**`config_revision` 不变**：`changes()`（team.rs:398-414）比较的仍是两份配置，fallback 不会被读成配置修改；
     - `team.binding_applied{…, cause: "fallback"}`（id `team/<role>/<epoch>`，与 checkpoint 同一格式，epoch 唯一）；替换事件 `team.binding_fallback{run_id, role, from, to, evaluated, chosen, probe_artifact_id}`（id `child_id(run, "fallback/<role>/<新 epoch>")`）；
     - `handover::prepare` 的交接包、`handoff.prepared` 与 session.start 通知（ADR-024 决定 1、2，与 team.rs:656-724 同一调用）。新 epoch 的会话由之后的 `Grant` 给出，首个输入付清之前不派发（ADR-024 决定 4）。
   - **`Switch(a)` 且有在途**：写 `Block`（若尚未）与 `team.binding_change_pending{cause: "fallback", to: a}`（REQ-019 行为 1 的“先持久化为待交接请求”）；在途 Attempt 照旧用旧绑定与 epoch；之后无在途的 tick 重新判定（可能换到别的候选；c 已恢复则 `Unblock` 并写 `change_withdrawn`）。
   - **`Rebind`**：无在途时同 `Switch` 的生效事务，agent 不变、`cause: "rebind"`，没有失效与替换事件；有在途时只写 `team.binding_change_pending{cause: "rebind"}`，`decide::load_binding`（crates/hoh-core/src/persistence/decide.rs:818-825）把“本 epoch 最近的 staffing 事件是 cause 为 rebind 的 change_pending”算作待生效——该职位不再派发，等在途结束（ADR-022 决定 8 的“有在途就等待”）；会话又变新鲜时写 `change_withdrawn` 解除。
   - 团队视图（team.rs:1207-1228）加 `missing`（missing_json），`pending` 加 `cause`（"config"、"fallback"、"rebind"）；`Page` 的 items 是自由对象，受锁 openapi 不改。

6. **turn 发现的失败（Q3，AC-020-05，REQ-020 行为 7）。**
   - `FailureClass`（crates/hoh-core/src/retry.rs:18-30）加 `Model`、`Unavailable`、`Compat`；`after_failure`（:87-95）分别给出 `Blocked(MODEL_UNAVAILABLE)`、`Blocked(AGENT_UNAVAILABLE)`、`Blocked(COMPAT_UNVERIFIED)`；`to_json`/`from_json`（:36-67）加 "model"、"unavailable"、"compat"，旧记录照旧可读。
   - `class_of`（product.rs:207-214）把 MODEL_UNAVAILABLE 归 `Model`；`prepare` 中“绑定未指名 Agent”与 `Some(Err)`（:459-470）归 `Unavailable`；`turn()` 的拒绝（:547）仍是 `Capability`；`None`（未查看，:471-477）仍是瞬时类。
   - `fail_task`（persistence/retry.rs:65-216）在 Task BLOCKED 的同一事务里，对 Auth、Capability、Model 类：以 (run, Task 的 role, Attempt 的 role_epoch, Attempt 的 agent) 为条件把绑定置 BLOCKED（原因同 Task，missing `["<agent>:<CODE>"]`），写 `team.binding_blocked{cause: "turn", attempt_id}`。所以同一 tick 的 pace 不会在 staffing 看到注册表的事实之前把该 Task 放回 READY。Capability、Model 另写排除记录 `team.binding_excluded{run_id, role, config_revision, agent, agent_version, reason, attempt_id}`（id `child_id(attempt_id, "excluded")`，agent_version 取 Attempt 所在会话的）。监督 Attempt 不走这条（:79-94，ADR-025 有自己的类别表）。
   - staffing 读 (run, role, 绑定的 config_revision) 下、agent_version 等于该 Agent 当前事实的 version 的排除记录作为 `excluded`（按 (run_id, kind) 读该 Run 的这一种事件，条数以“职位 × Agent × 版本”为界）。每次切换都要先有一次失败的 turn，一个 revision、一个版本之内至多切换 |order| 次，不会来回；新 revision 或 Agent 升级使它们失效。
   - 429/503 与其他瞬时类不变（ADR-020 决定 2）：WAITING_EXTERNAL、持久 `next_retry_at`，staffing 不因它们改变任何绑定（AC-020-05 的 503）。产品适配器仍不解析 Retry-After（M2T07R-256，见“移交”）。

7. **缺员职位的 Task：标记与恢复（Q5，AC-020-03，CR-018，ADR-028:308）。** 缺员集合 V = {AGENT_UNAVAILABLE, BLOCKED_AUTH, BLOCKED_CAPABILITY, MODEL_UNAVAILABLE, COMPAT_UNVERIFIED}。pace（persistence/retry.rs:562-596，R2 所在处）每次：
   - **先恢复**：每个 BLOCKED 且 `blocked_reason ∈ V` 的 Task，若其职位此刻可派发——`load_binding` 的 `active`（ACTIVE、有会话、无待生效、首个输入已交付）、所需能力 ⊆ 会话能力，且原因为 COMPAT_UNVERIFIED 时 `Context.observations` 中绑定 Agent 的 `verified` 为真（没有 observations 时视为真）——同一事务 `UPDATE tasks SET blocked_reason = NULL, next_retry_at = NULL`，再 CAS BLOCKED→READY（ADR-011:42：先清 blocker），写 `task.unblocked{task_id, reason, role, role_epoch}`（id `child_id(task, "unblocked/<revision>")`）。
   - 恢复不动的：NEED_DECISION（M2-T13）；`attempt_count`；附在 Task 上的失败项，下一个 Attempt 的返工上下文照常列出（ADR-028 决定 11 第 2a 步）。这就是 CR-018 的“绑定恢复后回到可派发”：登录转变、能力回来后的 Rebind、套件 PASS 使绑定 active，验证 Task 与开发 Task 一样回 READY。
   - **再标记**：到期的 Task（:510-515），其职位的绑定 BLOCKED 且原因 ∈ V → Task BLOCKED（绑定的原因），`next_retry_at` NULL，不建 Attempt，`attempt_count` 不变，写 `task.blocked{task_id, reason, missing, cause: "vacancy"}`（沿用 R2 的 id）；绑定 active 而能力不足 → BLOCKED_CAPABILITY（R2 原样）。
   - **停滞判定**（:597-611）不变：被标记的 Task 不再算能推进，只有别的 Task 也都推进不了时 Run 才 BLOCKED，原因按 `blockers::ordered`（ADR-020 决定 5、ADR-028 决定 10 的 -202）；别的职位有可派发的 Task 时 Run 照常推进（AC-020-03 的 T3）。commander 的 Task 不在 pace 内（:477），由 ADR-025 处理；BLOCKED 的 Run 上验证派发照旧（ADR-028 决定 10）。
   - host 把 `observations` 也交给 pace（runner.rs:672 的 `at()`）。

8. **冻结时的缺员规则（Q13，ADR-028 决定 3 的行 :161）。** “Run 缺 qa 或 reviewer 的绑定”只指没有绑定行（crates/hoh-core/src/persistence/completion.rs:567-577 不变）：内置职位不能被移除（config.rs:437），所以产品里只有手写夹具会出现。绑定 BLOCKED（任何原因）的验证职位不阻止冻结：候选照常冻结、开轮次、写交接，验证 Task 由决定 7 标记并等待；候选停在 VERIFYING，没有该方的报告就没有汇合（ADR-029 决定 11），所以不会 ACCEPTED（REQ-020 失败模式 1、行为 6）。completion.rs:573 的说明文字改为引用本决定。

9. **兼容闸门（Q10、Q12，AC-027-04，REQ-027 行为 4）。**
   - **一个谓词**：`hoh_agents::compat::verdict(manifest: Option<&CompatManifest>, agent, entry: &AgentEntry) -> Compat`：清单缺失、无该 Agent 的项、或实现/help/schema 三个哈希任一不等 → `Pending`；三者相等且 suite PASS → `Verified`；相等且 FAIL → `Failed`；相等且 NOT_RUN → `Pending`（即受锁 schema 标题的规则）。doctor 的 `assess::protocol`（assess.rs:24-55）改为调用它，再按 transport 给出 compatible/degraded，结论与说明文字不变；remedy（:156）改为“host 在没有写租约时自动运行兼容套件；运行中的写任务结束后即登记该版本”。
   - **闸门**：`ProductExecutor::prepare`（product.rs:457-478）在取得 `Ready` 之后、准备其他任何东西之前依次核对：(a) 重读启动器与实现的身份戳（`stamp()`，agents.rs:287-302，只读元数据），与 `Ready` 的不同 → 拒绝 COMPAT_UNVERIFIED（“files changed since the last look”），这使替换之后、注册表重新查看之前的派发也被拒；(b) `verdict(注册表持有的清单, agent, &ready.entry) != Verified` → 拒绝 COMPAT_UNVERIFIED；(c) 注册表此刻对该 Agent 为 `LoginMissing` → 拒绝 BLOCKED_AUTH（Auth 类，staffing 之后才出现的竞争）。
   - 拒绝都在 spawn 之前：Attempt FAILED（failure_reason 为该码）、`attempt.start_refused`，没有子进程（ADR-026 决定 9 的拒绝路径）。`Compat` 类使 Task BLOCKED(COMPAT_UNVERIFIED)，不退避，`attempt_count` 加 1（确有一个 Attempt）。运行中的 Attempt 不受影响：进程映像在启动时已固定。
   - **会话只给已验证的版本**：决定 4 的 `Grant` 与 `Rebind` 只在 `Verified` 时发生（`usable` 蕴含它）。所以新 host 或新安装在套件 PASS 之前不派发（绑定没有会话）；已有会话的绑定遇到版本变化，由闸门逐个 Attempt 拒绝——即 TEST-027-04 的“首个新 attempt 被拒”。
   - **待验证不触发 fallback**：`Pending` 在写租约空闲时由套件解决，是 REQ-020 决定 3 意义上的暂时状况；套件 FAIL（`Failed`）才是永久的，按决定 4 评估 fallback 或 BLOCKED(COMPAT_UNVERIFIED)。被拒的 Task 由决定 7 在 `verified` 为真且绑定可派发时放回 READY；版本或能力变了的绑定先由 `Rebind` 换新会话。

10. **兼容套件（Q9、Q10、Q11，REQ-027 行为 3、决定 2）。**
    - **用例**：`interface`（该版本查看成功：help/schema 含适配器所驱动的接口，缺的版本在查看时已是 `Unsupported`、走不到套件；能力按探测记），与六个回放用例 `success`、`failure`、`cancel`、`compaction`、`tool`、`unknown_fields`。七个都 PASS 即 PASS，否则 FAIL。
    - **嵌入的合成 fixture**：crates/hoh-agents/src/compat/fixtures/<agent>/<case>.jsonl 与 `expected.json`（终态、失败码、`adapter.unknown_event` 数），由 `include_bytes!` 编进产品；每个适配器加 `replay(bytes, version) -> Replayed{state, failure, unknown_events}`，走它的 turn 同一段帧读取与记录处理，不起进程。`fixture_set_sha256` = 嵌入集合按 (相对路径, sha256) 排序后的摘要（与 probe.rs:2540 的树摘要同一算法）。录制的真实 fixture（tests/fixtures/protocol）只留在测试里，不随产品分发（其 README 的“Provenance limits”）；一个单元测试扫描嵌入 fixture，不得含录制机器的路径与凭据形态。
    - **何时运行**：host 的注册表任务（runner.rs:474-487 的 `registry_watch`，改为也持有 store）在每次 `refresh` 之后，对每个想要查看、查看成功且 `verdict` 为 `Pending` 的 Agent：
      - 项目有写租约（`leases` 中该项目 kind 为 writer 的行，新的读接口 `Store::writer_lease(project)`；尚未回收的过期行也算持有，偏保守）→ 不运行，写 `compat.suite_deferred{agent, cli_version, implementation_sha256, lease_attempt_id, reason: "write_lease_held", detail: "维护窗口：写租约释放后自动运行兼容套件"}`，每个 (agent, 实现哈希, 租约 Attempt) 一条（id 由三者确定，已有即不写）——即 AC-027-04 的“写租约活跃时套件请求被拒绝”与 REQ-027 失败模式 5 的“提示维护窗口，不中途替换正在使用的版本”；
      - 否则在阻塞线程运行套件（同时至多一个）；结束时重读身份戳，与开始时不同即丢弃结果（下一轮再跑）；相同则写清单，并写 `compat.suite_completed{agent, status, implementation_sha256, fixture_set_sha256}`。同一哈希的 `Failed` 不重跑，哈希变了才重跑。
    - **清单只由 host 写，放在注册表里**：host 启动时以项目根调用 `Registry::open_manifest(root)` 读 `.hoh/compat-manifest.json`（缺失为空；读不了或不合 schema 视为空，并写一条 `compat.manifest_unreadable` 诊断），并删除上次崩溃留下的同目录临时文件。写入时替换该 Agent 的一项（其余保留），`generated_at` 取当时，按受锁 schema 校验，写到同目录临时文件、fsync、rename、fsync 目录，成功后才换掉内存中的那份；校验或写入失败不改内存、写诊断，至多每 30 s 重试。闸门、staffing 的 `Fact` 与套件都在注册表的锁内读内存中的那份；doctor 读文件（ADR-015 决定 2 的位置不变）。
    - **不加请求入口**：REQ-003 只许 attach/web/doctor 与固定选项，openapi 的命令种类封闭，二者受锁；AC 只要求“租约活跃时请求被拒”，host 自己的请求满足它。
    - **测试接缝**：hoh-app 公开产品写者 `compat::write_entry(project, entry)`；测试在 host 启动前用假 Agent 的探测以它写 PASS 项。不写时，套件在首次查看后自动运行（探测已有，回放与二进制无关），既有测试因而不依赖它。

11. **Commander（Q14，ADR-025 决定 5）。** staffing 对 commander 绑定与其他职位相同：首选不可用而有可用 fallback 时换绑（epoch+1，交接包即 Commander 的首个输入，ADR-024 决定 4）。ADR-025 决定 5 的不可用原因按绑定此刻的 Agent 判：`binding_blocked` 只在没有可用候选、或换绑在等在途监督 turn 结束时成立；`agent_unavailable`、`login_missing` 换绑后按新 Agent 的观察判（“新 Agent 还没有被观察过，就不因注册表而不可用”）。所以 COMMANDER_UNAVAILABLE 只在连 fallback 都不可用时持续，另外至多持续到在途监督 turn 结束。监督的分配在 commander 的 Agent `verified` 为假时延后，原因 `COMPAT_UNVERIFIED`，与 NO_SESSION 一样计入 `inactive` 的 `DEFER_LIMIT`（crates/hoh-core/src/persistence/wakes.rs:1717、:1795），不让闸门的拒绝把唤醒的失败数推到上限。

12. **能力表（Q7）。** 保留 ADR-022 决定 10 的子集（structured_events；commander、reviewer 另要 resume）。REQ-020 决定 1 的“developer/qa 需要经 probe 实测的命令执行能力”没有 AC 依赖（AC-020-01 自带所需集合）；`probe::CAPABILITIES`（probe.rs:25-35）与受锁 REQ-027 行为 2 的能力表都没有这一项，加入要改适配器探测并经 CR 改 REQ-027 行为 2。记为缺口（docs/22 余项与 PROGRESS），本任务不做。

13. **崩溃点、并发与余项。**
    - staffing 的每个写入是一个事务：提交前崩溃整笔回滚，重启后按同样的输入重判（事件 id 由 run、role、epoch 与计数决定，epoch 只加一次）；提交后、`Grant` 前崩溃，重启后照常授予（会话 id 由 run、role、epoch 派生，`INSERT OR IGNORE`，ADR-024 决定 8）。
    - staffing 读的是 tick 开始时注册表的快照；它与闸门之间的变化由闸门兜底（决定 9 的 (a)–(c)），与 pace 之间的变化由结算时的绑定阻塞兜底（决定 6）。
    - 套件与写租约：开始运行之后才取得写租约的写者不使用被测的 Agent（它未验证，闸门拒绝），所以检查与运行之间的竞争无害；套件开始与结束时的身份戳相同才写清单（K6）。
    - **余项（接受，有界）**：(a) 状态命令一直说“已登录”而令牌已失效时，turn 鉴权失败的事实在本 host 生命周期内不清除，恢复靠重新登录后重启 host（每次重启至多再失败一次；上一个生命周期的结算不喂给注册表），docs/12 写明。(b) 闸门核对身份戳到 exec 之间文件被替换（微秒级窗口），这次 turn 以未验证的版本运行；下一次查看即重新探测。(c) 回放用例只证明本构建的适配器处理六类帧，新版本的帧级兼容只由 `interface` 与 adapter-live 的实跑证明（REQ-027 决定 2 的 live smoke 单独记录），所以产品里的 FAIL 实际只来自构建缺陷。(d) 每次版本变化，已有会话的职位上每个到期 Task 各消耗一个被拒的 Attempt（`attempt_count` 加 1），之后等待，不重试。

## 不变量

- **K1** `select` 是全函数：同一 (order, required, facts, excluded) 得到逐字节相同的 `Selection`；chosen 若有，是 `order` 中第一个 usable 且之前的候选全为永久类；`evaluated` 是 `order` 的前缀；不在 `order` 中的 Agent 不出现。
- **K2** 绑定只在其职位没有在途 Attempt 时换 Agent 或 epoch；每次换绑在一个事务里写绑定、`team.binding_applied`、交接包与 session.start（REQ-019 行为 2），fallback 另有失效（若尚未）与替换事件；staffing 从不改 `config_revision`。
- **K3** 一个 Agent 的事实不是 usable 时，没有新的 turn 以它的进程启动：不授予会话、绑定 BLOCKED，或闸门在 spawn 之前拒绝；运行中的 Attempt 不受影响。
- **K4** 缺员职位的到期 Task 不产生 Attempt、`attempt_count` 不变、`next_retry_at` 为空；只在职位可派发时由 pace 放回 READY；NEED_DECISION 不经此解除；Run 只在没有别的 Task 能推进时 BLOCKED。
- **K5** 暂时状况（429/503、未查看、探测失败、兼容待验证）从不触发 fallback；每次切换之前都有一个新的永久事实，一个 revision 与版本内的切换次数 ≤ |order|。
- **K6** 清单只由 host 写、原子替换、合受锁 schema；PASS 项的三个哈希出自套件开始与结束时同一身份戳下的探测。闸门、staffing 与 doctor 对“是否已验证”用同一个 `compat::verdict`。

## 未采用

- **在 checkpoint 里选 fallback**（配置路径）：fallback 会改变 `config_revision` 或被 `changes()` 读成配置修改，与 ADR-022 决定 8 v3 冲突；staffing 只改 Agent 与 epoch。
- **首选恢复即换回**：每次换绑都是 epoch+1、交接与一次 Commander 唤醒，来回切换没有收益（Q2）。
- **兼容待验证即阻塞绑定或触发 fallback**：TEST-027-04 要求“首个新 attempt 被拒”，绑定级阻塞使这个 Attempt 根本不存在；待验证在维护窗口自行解决。
- **按版本录制的 fixture、缺失即 FAIL**：任何真实升级都会阻塞到有人录制；随产品分发录制品会泄露操作者数据。
- **加一个运行套件的 CLI 或 API**：REQ-003 与 openapi 受锁，需 CR；host 自动运行已满足 AC。
- **原地更新 `sessions.capabilities_json`**：改写已结束 Attempt 所用会话的记录；epoch+1 的新会话保留历史（Q6）。
- **按时间重试 turn 发现的缺认证**：REQ-020 行为 7 不许重试永久错误；改为只在看得见的恢复事实时清除。
- **新的原因码（如 NOT_INSTALLED）**：CR-003；用已有码加细节行。
- **探测超时触发 fallback**：REQ-020 决定 3。
- **只靠注册表、结算时不阻塞绑定**：同一 tick 的 pace 会在 staffing 看到注册表的事实之前把 BLOCKED_AUTH 的 Task 放回 READY，多一次失败的 Attempt。

## 与倾向不同之处

1. **兼容待验证不触发 fallback，也不阻塞已有会话的绑定**（倾向 Q1 把 compat unverified 列为触发）：TEST-027-04 要一个被拒的 Attempt，REQ-020 决定 3 把会自行解决的状况归为等待；只有套件 FAIL 是永久的。新会话仍只授予已验证的版本。
2. **turn 发现的缺认证另在结算事务里阻塞绑定**（倾向只说进入注册表）：否则同一 tick 的 pace 会先放回 Task；注册表事实的清除条件写成看得见的转变、新文件或重启，因为状态命令可能一直说“已登录”。
3. **能力、模型的 turn 失败另有持久的排除记录**（倾向说是绑定的事实）：换 epoch 后绑定上的事实会丢，没有记录就可能在候选间来回；记录按 revision 与版本失效。
4. **粘滞到“修改了该职位的 revision”**，而不是任何新 revision：ADR-022 决定 8 v3 让未修改的职位随 revision 原样推进。
5. **COMMANDER_UNAVAILABLE 另可持续到在途监督 turn 结束**（倾向说只在没有可用 Agent 时）：ADR-025 决定 5 按绑定此刻的 Agent 判，而换绑必须等在途结束（REQ-019 决定 3）。
