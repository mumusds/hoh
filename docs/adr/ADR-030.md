# ADR-030 · 能力匹配与缺员：fallback 选择、缺员的阻塞与恢复、兼容套件闸门

状态：提议（2026-11-14；M2-T15；第四版，设计审查第 3 轮之后，待第 4 轮）

## 背景

M2-T15 的验收是 REQ-020 的 AC-020-01..05 与 AC-027-04（contracts/development-tasks.json:681）；done_when 另有 CR-018 的条款：绑定恢复后，BLOCKED_AUTH/BLOCKED_CAPABILITY 的验证 Task 回到可派发（docs/cr/CR-018-verification-hand-overs.md:30；ADR-028 出口表 :308、移交 :347）。检查归属：TEST-020-01、-05 属 `unit`（`cargo test --lib --bins`，测试在 `src/**/tests.rs`），TEST-020-02..04 与 TEST-027-04 属 `integration`（`--test '*'`；scripts/product/cargo-tests.sh:9-10）。预研清单 `.hoh-dev/evidence/m2t15-prep/inventory.md`；下文行号按 main 1d9c34d 复核。

现状：

- **选择**：配置有 `Role.fallback`（crates/hoh-core/src/config.rs:131，解析 :782-803，拒绝以自身为 fallback :846-852），没有代码读它。职位所需能力是 `host::agents::required`（crates/hoh-app/src/host/agents.rs:307-313；ADR-022 决定 10：都要 structured_events，commander、reviewer 另要 resume）；REQ-020 决定 1 的“developer/qa 需要经 probe 实测的命令执行能力”没有实现。
- **注册表**：`Registry::look`（agents.rs:185-242）把 `ProbeError` 压成字符串（:199-200、:214），并按文件身份缓存失败——探测超时一次，同一文件就永不再探测；`Ready`（:24-31）丢掉了探测的 `AgentEntry`（三个哈希）与身份戳。登录每 30 s 看一次（:112-133，ADR-024 决定 7），只用于拒绝团队修改（crates/hoh-core/src/persistence/team.rs:636-656）。每次实际查看给该 Agent 的计数 n 加一（agents.rs:244-248），(host_epoch, n) 是观察的身份（ADR-025 决定 5）。
- **绑定器**：`bind`（agents.rs:469-505）只看等会话与 AGENT_UNAVAILABLE 的绑定（team.rs:1044-1090），给未登录的 Agent 照样授予会话；任何失败都写 AGENT_UNAVAILABLE（`block_binding`，team.rs:1156-1204，事件 id 每个 epoch 只有一个）；已有会话的绑定不再被查看。`bind_session`（team.rs:1094-1151）写 `team.session_bound{…, agent_version}`（id `child_id(session_id, "bound")`），不记会话是在哪个实现身份下授予的。
- **失败**：`class_of`（crates/hoh-app/src/host/product.rs:208-214）把 MODEL_UNAVAILABLE 并入 Capability；`prepare`（:457-478）对“绑定后 Agent 消失”以 AGENT_UNAVAILABLE、Capability 类拒绝，Task 成 BLOCKED_CAPABILITY（M2T07R-260）；`fail_task`（crates/hoh-core/src/persistence/retry.rs:65-216）对 Auth/Capability 直接 BLOCKED，不动绑定；监督 Attempt 在 :79-94 提前返回，只写 `supervisor.turn_failed`，其类别只由 wakes.rs:1244-1255 认 auth、capability、decision。
- **pace**：R2（retry.rs:562-596）在 `if state != RunState::WaitingExternal`（:562）之内，只对 ACTIVE 的绑定判能力；BLOCKED 绑定的 READY Task 仍算到期（:510-515），Run 因此永不停滞；没有写者把 BLOCKED_AUTH/BLOCKED_CAPABILITY 的 Task 放回 READY（只有 closing.rs:400-415 在取消时清除）。tick 里 pace（runner.rs:672）在 supervise 取注册表观察（:678-688）之前。
- **租约**：一个项目每个槽一行，永久保留以维持 epoch（crates/hoh-core/src/persistence/leases.rs:1-9）；持有的谓词是 `effective`（:69-71：未过期，或持有者 Attempt 未结束）；结束即在同一事务把租约的 `expires_at` 置为结束时刻（`release_held_by`，:177-187，由 attempts.rs:487 调用），行不删。写者槽只经 `free_slot`（:75-96）与 `grant`（:109-146）取得（调用处 decide.rs:568、:674，rounds.rs:104、:180）。
- **兼容**：清单类型在 crates/hoh-agents/src/compat.rs:1-86，探测给出 suite NOT_RUN 的条目（crates/hoh-agents/src/probe.rs:343-380），`fixture_root` 为空时 `fixture_set_sha256` 是空集的哈希（:2540-2555）；探测只核对方法与信封，`params` 一律放开（`params_open`，:829-841；ADR-015 决定 2：参数结构“由兼容套件验证”）；doctor 读 `.hoh/compat-manifest.json`（crates/hoh-app/src/doctor.rs:36-60），以 `assess::protocol`（crates/hoh-app/src/doctor/assess.rs:24-55）判 unknown；产品没有清单的写者、套件与闸门，也不随产品带 fixture。
- **启动闸门**：`hoh __gate`（crates/hoh-app/src/gate.rs:19-46）读到 `go` 后按路径 `exec` 启动器；runner 在 `prepare` 之后还要装箱、spawn、加入 cgroup、读 Git 起点、提交 RUNNING（runner.rs:942-1026）才开闸。启动器到实现的解析：codex 的 npm 包装 `bin/codex.js` 在运行时自己解析并 `process.execve` 原生二进制；pi 的 sh 启动器在运行时读 `install/current-version` 再 `exec` 该版本的 `node_modules/.bin/pi`（一个 node 脚本）；claude 的启动器是指向版本化原生二进制的链接（probe.rs:2400-2538 为探测建模了这三种布局）。

约束：requirements.json、acceptance-scenarios.json、protocol.schema.json（`$defs.BlockedReason` 已有 AGENT_UNAVAILABLE、BLOCKED_AUTH、BLOCKED_CAPABILITY、MODEL_UNAVAILABLE、COMPAT_UNVERIFIED；ReasonCode 写明“New codes need a CR”）、openapi.json（命令种类封闭）、001_initial.sql（`role_bindings.agent` 只许三个 Agent，没有“首选 Agent”列；`leases.kind` 只许 writer、supervisor、reader-N，`leases.attempt_id` 引用 attempts）、compat-manifest.schema.json 与 CONTRACT.md 都受锁。

- **需要的 CR**：只有 CR-021（REQ-027 行为 2 的能力列表加 `command_execution`，决定 12；行为 3 的“manifest 记录所用 fixture 集 hash”写明为本构建的套件集摘要，决定 10，M2T15D-250；属 CR-003 D1 的细化，草案见“移交”）。其余不改受锁文件，不加原因码、命令、API 路径、列或租约种类；新的事件种类与 docs/12、docs/13、docs/22 不在锁内。第三、四版的改动也都在锁外：`suite.fixture_set_sha256` 在受锁 schema 里只限定为 64 位 hex（决定 10 的套件集摘要写进它），闸门的参数、go 行与记录文件、`team.session_bound` 的载荷、新的事件种类都不在锁内。第一版“不需要 CR”的总括结论撤回。
- **所有者已决定（本会话）**：决定 9 的 R1、R2（2026-11-13）接受为文档化的余项，并在协议让 HoH 先说话处于首个输入之前再核对 (dev, ino, ctime)，变了即取消、不发输入；R3（2026-11-14）接受为文档化的余项，并在 turn 进行中定期再核对，变了即取消该 turn（决定 9“余项”）。闸门的表述是“除 R1、R2、R3 之外，新 Attempt 不使用未验证的版本”，批准人：所有者（R1、R2：2026-11-13；R3：2026-11-14）。没有待所有者决定的事项。

## 决定

1. **模块、在 tick 中的位置与快照。**
   - 纯函数在新模块 `hoh_core::staffing`（crates/hoh-core/src/staffing.rs：事实、判决、选择、绑定的判定、新鲜度）；store 侧在新文件 crates/hoh-core/src/persistence/staffing.rs（读输入，一个判定写一个事务）；host 侧 `host::agents::staff` 取代 `bind`（agents.rs:469-505）。
   - 它在 tick 里就在 `bind` 的位置（crates/hoh-app/src/host/runner.rs:558-571）：checkpoint 之后，首个输入投递、对账、pace 与调度轮之前。所以 ADR-020 决定 5 的“fallback 选择放在调度前能力检查之前”成立：同一 tick 里 staffing 先写绑定，pace 与调度轮读它。
   - **一个快照（-51）**：staffing 之前 host 取一次 `Registry::snapshot(host_epoch) -> Arc<staffing::Snapshot>`（每个想要查看的 Agent 的 `Fact` 与 `Observation`，决定 2），在注册表的锁内一次读出。同一份快照交给 staffing、本 tick 每次 pace（`Context.staffing`，runner.rs:623 的 `at()`）、supervise 与分配（`Context.observations` 由快照给出，取代 runner.rs:678-688 的另一次读取）。套件在两次读取之间写下的 PASS 因此只在下一个 tick 的快照里出现，staffing 与 pace 对“是否已验证”不会不一致。
   - **prepare 的一份事实（-100）**：prepare 不用 tick 的快照（派发与 prepare 之间文件或登录可能已变），也不分几次读注册表：它取 `Registry::fact(agent) -> Fact`——注册表此刻该 Agent 的事实，与 `snapshot` 的每一项同一构造函数、在注册表的锁内读出——prepare 的全部核对（含实际 assignment 的会话对它是否新鲜）与闸门的 `expect` 都只用这一份（决定 9）。第二版“prepare 读此刻的状态只会更严”不成立：调度依据的是快照时的会话能力（rounds.rs:373-383），而 prepare 当时没有把会话与当前事实关联起来。
   - 没有注册表的 host（脚本化执行器）不运行 staffing，与今天不运行 `bind` 相同；它的 `Context.staffing` 与 `Context.observations` 为 `None`，决定 7、11 对 `None` 与“有快照而缺该 Agent”分别规定。
   - `runner_waiting` 的 `unbound` 换成 `staffing: Vec<Staffed>`：每个未结束 Run 的每个绑定，带 agent、model、role_epoch、state、blocked_reason、missing、会话的 (agent_version, capabilities_json) 与授予时的身份（`team.session_bound` 的 `identity`，决定 4）、live、`order`（决定 3）、所需能力与排除记录（决定 6）；已移除的职位照旧排除（team.rs:1078-1081）；配置修改待生效（`team::pending`，team.rs:467-489）的职位也排除，那是 checkpoint 的事（ADR-022 决定 8）。runner.rs:544 与 :578 随之改读它（:578 改为“本 tick 没有 staffing 的写入”）。

2. **Agent 的事实（Q3）。** `staffing::Fact`（每个 Agent 名一个，来自快照；快照里没有即未查看）：
   - `NotInstalled(d)`：`ProbeError::NotFound`。
   - `Unsupported(d)`：`ProbeError::Unsupported`，以及 `session_capabilities` 失败（M2T07R-260 的第二种情形）。
   - `ProbeFailed(d)`：`TimedOut`、`NotStarted`、`Failed`、`Io`、身份戳读不出——暂时的。
   - `LoginMissing(d)`：登录状态命令明说未登录（ADR-024 决定 7），或 turn 发现的缺认证（下文）。
   - `Usable{version, identity: AgentIdentity, stamp: Stamp, generation, session: Value, granted: BTreeSet<String>, compat: Compat}`：`generation` 为得出它的查看的 (host_epoch, n)；`Compat` 为 `Verified`、`Pending(why)`、`Failed(why)`、`Undecided(why)`（决定 9）；`granted` 用 `decision::granted_capabilities`，与 `load_binding` 同一函数；`stamp` 为得出它的查看所读的身份戳 `Stamp{launcher: FileStamp, implementation: FileStamp}`，`FileStamp{dev, ino, ctime_sec, ctime_nsec}`（跟随链接的 `stat`），不属于身份，只供 prepare、闸门与再核对比较“还是不是那个文件”（-201）。

   **一个身份类型（-104）**：`hoh_core::staffing::AgentIdentity{launcher_path, launcher_sha256, implementation_path, implementation_sha256}`（serde、`Eq`、`Ord`），由探测条目同名的四个字段构成（`AgentEntry::identity()`，crates/hoh-agents/src/compat.rs:52-58 的字段）。事实的 `identity`、`team.session_bound.identity`（决定 4）、闸门的 `Expect`（决定 9）、排除记录（决定 6）、`compat::verdict` 的“相符”（决定 9）与 `Ran` 都是这一类型，比较总是四个字段整体相等；任何一处缺字段或解析不了即“没有身份”。所以版本行与两个哈希都相同、只有实现路径或启动器路径不同的，也是另一个身份。

   注册表的改动（agents.rs）：`Seen.outcome` 存 `Result<Ready, Probe{class, detail}>`，class 取自 `ProbeError` 的变体（:38-41、:199-214）；暂时类不按身份戳缓存，至少每 30 s（`AUTH_EVERY`）重新探测；`Ready` 带探测的 `AgentEntry`、`Stamp` 与 `generation`（身份戳每个文件另加 ctime：今天 agents.rs:287-302 只有 (dev, ino, size, mtime)；只改元数据的 chmod、xattr 因此也换身份戳、重新探测，-201），并缓存 `session_capabilities(agent, 项目根)`（每次实际查看算一次）；想要查看的 Agent（team.rs:1017-1041 的 `agents`）加上每个绑定所在 revision 中该职位的 fallback 列表，所以候选也被查看；`Registry::snapshot`；`Observation`（crates/hoh-core/src/decision.rs:164-169）加 `verified: bool`（该 Agent 为 `Compat::Verified`），供决定 7、11。

   **turn 发现的缺认证是有身份、有代次的事实（-07）**：每个 Attempt 在 prepare 时取得 `Ran{agent, identity, generation}`（prepare 所用事实 F 的身份——按决定 9 (d) 它等于会话的身份——与注册表此刻对该 Agent 的 (host_epoch, n)），随 runner 的在途条目保存；它只供注册表锁存缺认证，排除记录不靠它（决定 6，-103）。runner.rs 中把结局交给 store 的各处（`runner_finished`：:862、:892、:928、:960、:998、:1222，监督 Attempt 也经这些）改经一个 `finished()`：结局为 Auth 类时先调 `Registry::turn_auth_failed(ran, attempt_id)`，再交给 store。注册表为每个 Agent 记“最近恢复事实的代次” `recovered_at`：看到与前一次不同的身份的查看，或登录查看先说“未登录”、再说“已登录”的那一次（看得见的转变）。`turn_auth_failed` 只在两条同时成立时锁存：`ran.identity` 等于该 Agent 当前 `Ready` 的身份，且 `ran.generation ≥ recovered_at`（这个 turn 是在最近一次恢复之后启动的）；否则是旧身份或恢复之前的结果，记一条诊断，不改事实。锁存的 `LoginMissing("turn <attempt> failed BLOCKED_AUTH")` 作用于绑到该 Agent 的每个职位，只在之后的恢复事实（代次更新的身份变化或看得见的转变）或 host 重启时清除；只说“已登录”的查看不清除它：状态命令可能一直这么说，而按时间重试违反 REQ-020 行为 7。

3. **判决与选择（Q1、Q4，AC-020-01）。** `staffing::verdict(agent, required, facts, excluded) -> Verdict`，按次序取第一个成立的：
   1. 未查看 → `not_looked_at`；`NotInstalled` → `not_installed`；`Unsupported` → `unsupported`；`ProbeFailed` → `probe_failed`；
   2. `LoginMissing` → `BLOCKED_AUTH`；`Compat::Failed`、`Compat::Undecided` → `COMPAT_UNVERIFIED`；
   3. 在 `excluded` 中且记录的 (agent_version, identity) 等于事实的 (version, identity)（决定 6）→ 记录的 `MODEL_UNAVAILABLE` 或 `BLOCKED_CAPABILITY`；
   4. `required ⊄ granted` → `CAPABILITY_UNSUPPORTED:<缺的能力名，排序，逗号连接>`；
   5. `Compat::Pending` → `compat_pending`；否则 `usable`。

   - 判决的**行**是 `<agent>:<code>`：`pi:not_installed`、`X:CAPABILITY_UNSUPPORTED:resume`、`claude:BLOCKED_AUTH`；细节只在证据对象里（决定 5）。
   - 原因码只用 `$defs.BlockedReason` 已有的：not_looked_at、not_installed、unsupported、probe_failed → AGENT_UNAVAILABLE；BLOCKED_AUTH；COMPAT_UNVERIFIED、compat_pending → COMPAT_UNVERIFIED；MODEL_UNAVAILABLE；BLOCKED_CAPABILITY、CAPABILITY_UNSUPPORTED（ErrorCode，已在 ReasonCode 中）→ BLOCKED_CAPABILITY。小写的 `not_installed` 等是细节文字，不是原因码。
   - **永久**（REQ-020 决定 3：评估 fallback）：not_installed、unsupported、BLOCKED_AUTH、COMPAT_UNVERIFIED、MODEL_UNAVAILABLE、BLOCKED_CAPABILITY、CAPABILITY_UNSUPPORTED。**等待**（不评估 fallback）：not_looked_at、probe_failed、compat_pending。`Undecided` 归永久：同一身份重跑得到同一结果（决定 10），等待它不会自行解决。
   - `staffing::select(order: &[String], required, facts, excluded) -> Selection{chosen, waiting_on, evaluated}`：按 `order` 逐个求判决并记入 `evaluated`；`usable` → chosen，停；等待类 → waiting_on，停；永久类 → 下一个；走完则两者皆空。
   - `order` = 绑定所在 revision 中该职位的 `[agent] ++ fallback`（配置保证不重复、不含自身）；revision 没有记录时为 `[绑定的 agent]`（没有 fallback）；绑定的 Agent 不在其中时（手写的行）放在最前。不在 `order` 中的 Agent 从不被求值（REQ-020 行为 3，AC-020-01 的 codex）。
   - 输入是 Agent 名字符串与 `BTreeMap`/`BTreeSet`，没有 HashMap、时钟或随机数，所以 AC-020-01 的“X”这样的名字也能进入；`Selection` 序列化为 `{"chosen", "waiting_on", "evaluated": [行…]}`，同一输入逐字节相同。

4. **绑定的判定（Q1、Q2、Q5、Q6、Q8）。** `staffing::judge(&Staffed, facts) -> Judgment`；live 与 checkpoint 同义（该 Run 该职位有 PREPARED/STARTING/RUNNING 的 Attempt，team.rs:556-568，含监督 Attempt）。记 c = 绑定的 Agent，v = verdict(c)。

   **会话新鲜**（`staffing::fresh(session, fact)`，-51、-104）：会话的 `agent_version` 等于事实的 version、`capabilities_json` 等于事实的 session，且会话授予时的身份与事实的 identity 是同一个 `AgentIdentity`（四个字段整体相等）。授予时的身份记在 `team.session_bound` 的新字段 `identity`（完整的 `AgentIdentity`；`bind_session` 写，team.rs:1135-1146；按事件 id `child_id(session_id, "bound")` 一次唯一索引查到）。版本行相同而实现不同（TEST-027-04 的 A、B 都说 `codex-cli 0.166.0`）不新鲜；版本与两个哈希都相同、只有实现路径（或启动器路径）不同的也不新鲜。第三版之前授予、事件里没有 `identity` 或缺字段的会话算陈旧：升级 HoH 之后每个这样的绑定在无在途时 Rebind 一次。staffing 的判定、pace 的可派发谓词（决定 7）与 prepare 的 (d)（决定 9）用的是这同一个函数。

   | v | 绑定 | 判定 |
   |---|---|---|
   | usable | 无会话 | `Grant`：授予会话（`bind_session`，写入身份），BLOCKED 的同时回 ACTIVE |
   | usable | 会话新鲜 | BLOCKED → `Unblock`；ACTIVE → 无 |
   | usable | 会话陈旧（升级、能力变化、实现身份变化） | `Rebind`：同一 Agent 与模型，epoch+1，新会话（Q6） |
   | not_looked_at、compat_pending | 任何 | 无（有会话的照常派发，由决定 9 的闸门逐个 Attempt 拒绝） |
   | probe_failed | 任何 | `Block(AGENT_UNAVAILABLE, ["<c>:probe_failed"])`，不评估 fallback |
   | 永久 | 任何 | s = select(order)：s.chosen = a → `Switch(a)`；s.waiting_on 且绑定 ACTIVE 无会话 → 无；否则 `Block(v 的原因, missing = s.evaluated 的行)` |

   - **粘滞（Q2）**：c 可用时不求选择，所以换到 fallback 之后不因首选恢复而换回；c 自己永久不可用时从 `order` 头部重选（首选已恢复即回到它）；修改了该职位的新 revision 由 checkpoint 照 ADR-022 决定 8 生效，未修改的职位随 revision 推进、留在 fallback。
   - **模型（Q8）**：`Switch(a)` 时 a 等于配置的首选则取配置的 model，否则为 NULL（Agent 的原生默认；Attempt 记 resolved_model）；`Rebind` 保留绑定的 model。
   - “s.waiting_on 且 ACTIVE 无会话 → 无”只为启动时的次序：首选已查看而候选尚未查看时，不先写一次失效再换绑；这样的绑定本来就不派发。

5. **判定的写入（REQ-020 行为 2、4，REQ-019 行为 1、2）。** `Store::staff(StaffChange)` → persistence/staffing.rs 的一个 IMMEDIATE 事务：以 (run, role, role_epoch, agent) 为条件（与 `bind_session` 相同，不再匹配即无操作并返回 false），并在事务内重新判 live。
   - **证据**：Block 与 Switch 之前，host 把每个被求值候选的 `{agent, line, probe:{class, detail, cli_version, launcher_path, implementation_sha256, help_sha256, schema_sha256, capabilities, compat, observation:{host_epoch, n}}}` 组成数组，规范化为 JSON，经 `objects::put`（crates/hoh-core/src/objects.rs:73）存为对象；事务以 `runner::register` 登记 artifact 行，事件带 `probe_artifact_id` 与 `probe_sha256`（AC-020-02 的“引用 probe 证据”）。对象写不进时本 tick 不写这一判定，下一 tick 重来：没有证据就不换绑、不阻塞（这期间闸门照样拒绝不可用的 Agent，K3）。
   - **staffing 事件的 id（-202）**：同一 (run, role, epoch) 的为 `ids::member(ids::series(run, "staffing/<role>/<epoch>"), n)`，n 为该族已有事件数加 1（`ids::count`：`events.event_id` 唯一索引上的范围计数，不按条目扫 JSON，ADR-025 决定 5 的规则）；按 seq 最近的一条是这个 epoch 的 staffing 状态。不用 `child_id(run, "…/<n>")`：它按整个后缀缩短长的 parent（ids.rs:28-34），`child_id(p, s + n)` 不一定以 `child_id(p, s)` 开头（160 字符的 id 即如此），前缀计数会漏数、重复编号。
     - `ids::series(parent, family) -> String`（族的前缀 stem）：`<parent>/<family>` 不超过 `MAX_ID − 21` 时原样，否则与 `child_id` 同一缩短（截断加 FNV-1a 标记，ids.rs:10-23）到恰为 `MAX_ID − 21`；`ids::member(stem, n)` 为 `<stem>/<n>`（n ≥ 1，十进制、无前导零，至多 20 位），所以成员不超过 160 字符、总以 `<stem>/` 开头；`ids::count(tx, stem)` 数 `event_id` 在 `[<stem>/, <stem>0)` 之内（`0` 是 `/` 的下一个字节）且余下部分全为数字的行，另一族以 `<stem>/1/…` 开头的成员不被计入。
   - **种类**：`team.binding_blocked{run_id, role, role_epoch, agent, reason, missing, evaluated, probe_artifact_id, cause: "staffing"|"turn", attempt_id?}`（角色失效：ADR-025 决定 1 唤醒 Commander；只在进入 BLOCKED 或 (reason, missing) 改变时写）；`team.binding_unblocked`；`team.binding_change_pending{cause: "fallback"|"rebind", to}`；`team.binding_change_withdrawn`。只有 `team.binding_blocked` 唤醒；其余与替换事件、套件事件都只进下一次唤醒的摘要。
   - **不重复（-55）**：本 epoch 最近的 staffing 事件已是同一 (cause, to) 的 `change_pending` 时不再写；它之后有 `change_withdrawn`、`binding_applied` 或另一 (cause, to) 时才写新的一条。所以有在途的若干 tick 只写一条。
   - `Block`：`state='BLOCKED', blocked_reason, missing_json`（会话保留）与 `team.binding_blocked`。`Unblock`：`state='ACTIVE', blocked_reason=NULL, missing_json='[]'` 与 `team.binding_unblocked`。`Grant`：`bind_session`（team.rs:1094-1151），其 WHERE 由“BLOCKED 且 AGENT_UNAVAILABLE”改为“BLOCKED 且原因属于缺员集合 V”（决定 7），`team.session_bound` 加完整的 `identity`（-104）。
   - **`Switch(a)` 且无在途**，一个事务（REQ-019 行为 2）：
     - 绑定不是同一原因的 BLOCKED 时先写 `team.binding_blocked`（失效事件）；
     - `UPDATE role_bindings SET agent=a, model, role_epoch=role_epoch+1, session_id=NULL, state='ACTIVE', blocked_reason=NULL, missing_json='[]', bound_at`，**`config_revision` 不变**：`changes()`（team.rs:398-414）比较的仍是两份配置，fallback 不会被读成配置修改；
     - `team.binding_applied{…, cause: "fallback"}`（id `team/<role>/<epoch>`，与 checkpoint 同一格式，epoch 唯一）；替换事件 `team.binding_fallback{run_id, role, from, to, evaluated, chosen, probe_artifact_id}`（id `child_id(run, "fallback/<role>/<新 epoch>")`）；
     - `handover::prepare` 的交接包、`handoff.prepared` 与 session.start 通知（ADR-024 决定 1、2，与 team.rs:656-724 同一调用）。新 epoch 的会话由之后的 `Grant` 给出，首个输入付清之前不派发（ADR-024 决定 4）。
   - **`Switch(a)` 且有在途**：写 `Block`（若尚未）与 `team.binding_change_pending{cause: "fallback", to: a}`（REQ-019 行为 1 的“先持久化为待交接请求”）；在途 Attempt 照旧用旧绑定与 epoch；之后无在途的 tick 重新判定（可能换到别的候选；c 已恢复则 `Unblock` 并写 `change_withdrawn`）。
   - **`Rebind`**：无在途时同 `Switch` 的生效事务，agent 不变、`cause: "rebind"`，没有失效与替换事件；有在途时只写 `team.binding_change_pending{cause: "rebind"}`，`decide::load_binding`（crates/hoh-core/src/persistence/decide.rs:792-833）把“本 epoch 最近的 staffing 事件是 cause 为 rebind 的 change_pending”算作待生效——该职位不再派发，等在途结束（ADR-022 决定 8 的“有在途就等待”）；会话又变新鲜时写 `change_withdrawn` 解除。
   - 团队视图（team.rs:1207-1228）加 `missing`（missing_json），`pending` 加 `cause`（"config"、"fallback"、"rebind"）；`Page` 的 items 是自由对象，受锁 openapi 不改。

6. **turn 发现的失败（Q3，AC-020-05，REQ-020 行为 7）。**
   - `FailureClass`（crates/hoh-core/src/retry.rs:18-30）加 `Model`、`Unavailable`、`Compat`；`after_failure`（:86-97）分别给出 `Blocked(MODEL_UNAVAILABLE)`、`Blocked(AGENT_UNAVAILABLE)`、`Blocked(COMPAT_UNVERIFIED)`；`to_json`/`from_json`（:36-63）加 "model"、"unavailable"、"compat"，旧记录照旧可读。
   - `class_of`（product.rs:208-214）把 MODEL_UNAVAILABLE 归 `Model`、COMPAT_UNVERIFIED 归 `Compat`（这个码只来自 prepare 的拒绝、闸门钥匙相符的 `refused` 记录与两个再核对，决定 9，K9；从不来自底座的退出码或输出）；其中闸门或再核对只发现身份戳不符、而重新解析与哈希得到的身份不变时，类别为瞬时类（`Facts.stamp_only`，-201）；`prepare` 中“绑定未指名 Agent”与 `Some(Err)`（:459-470）归 `Unavailable`；`turn()` 的拒绝（:547）仍是 `Capability`；`None`（未查看，:471-477）仍是瞬时类。
   - `fail_task`（persistence/retry.rs:65-216）在 Task 结算的同一事务里，对 Auth、Capability、Model 类——**监督 Attempt 也一样（-05）**——以 (run, Task 的 role, Attempt 的 role_epoch, Attempt 的 agent) 为条件把绑定置 BLOCKED（原因同该类，missing `["<agent>:<CODE>"]`），写 `team.binding_blocked{cause: "turn", attempt_id}`。所以同一 tick 的 pace 不会在 staffing 看到注册表的事实之前把该 Task 放回 READY。Capability、Model 另写排除记录 `team.binding_excluded{run_id, role, config_revision, agent, agent_version, identity, reason, attempt_id}`（id `child_id(attempt_id, "excluded")`，唯一索引使重复的写入成为无操作）。监督分支（:79-94）照旧把监督 Task 置 CANCELLED、写 `supervisor.turn_failed`，绑定的阻塞与排除在同一事务里追加；其余监督规则见决定 11。
   - **排除记录的身份来自会话（-103）**：`fail_task` 在同一事务里按 Attempt 的 `session_id` 读 `sessions.agent_version` 与该会话的 `team.session_bound.identity`（按事件 id `child_id(session_id, "bound")` 一次唯一索引查到），不读 runner 的内存。所以两条结算路径得到同一个输入：runner 的结算（`runner_finished`，经 `finished()`）；崩溃恢复——runner 在 effect 进入 OBSERVED 时已把类别持久化（runner.rs:1082-1090 的 `observed_detail`），新 host 的对账以持久的 `work_class` 直接调 `fail_task`（reconcile.rs:443-462），不经过 `finished()`。
     - **等价性**：会话的身份在授予时写下，之后不变；prepare 只在会话对它所用的那份事实 F 新鲜时启动（决定 9 (d)），闸门只 exec 身份等于 F 的实现（决定 9 的执行时核对），所以该会话里每个 turn 实际运行的就是会话的身份——R1、R2 之内的偏差不改变 HoH 核对过的那个身份，排除记录记的正是它。启动之前的拒绝（`turn()` 的 Capability，product.rs:545-547）没有进程，它的会话同样已过 (d)。

   - 结算时阻塞绑定不看注册表，迟到的旧身份失败也会阻塞它（-07）：这是暂时的，下一个 tick 的 staffing 按快照判 c：旧身份的失败没有进入事实，c 为 usable → `Unblock`（会话新鲜）或 `Rebind`（会话属于旧身份）→ 决定 7 恢复 Task。旧身份的排除记录按身份不适用于新身份。
   - staffing 读 (run, role, 绑定的 config_revision) 下、(agent_version, identity) 等于该 Agent 当前事实的排除记录作为 `excluded`（按 (run_id, kind) 读该 Run 的这一种事件，条数以“职位 × Agent × 身份”为界）。每次切换都要先有一次失败的 turn，一个 revision、一个身份之内至多切换 |order| 次，不会来回；新 revision 或 Agent 换了身份使它们失效。
   - 429/503 与其他瞬时类不变（ADR-020 决定 2）：WAITING_EXTERNAL、持久 `next_retry_at`，staffing 不因它们改变任何绑定（AC-020-05 的 503）。产品适配器仍不解析 Retry-After（M2T07R-256，见“移交”）。

7. **缺员职位的 Task：标记与恢复（Q5，AC-020-03，CR-018，ADR-028:308）。** 缺员集合 V = {AGENT_UNAVAILABLE, BLOCKED_AUTH, BLOCKED_CAPABILITY, MODEL_UNAVAILABLE, COMPAT_UNVERIFIED}。
   - **位置（-54）**：pace 中 R2 所在的整块（retry.rs:562-596）移出 `if state != RunState::WaitingExternal`（:562），放在预算停止之外的分支开头、在途与停滞判定（:597-611）之前。pace 只对 RUNNING、VERIFYING、WAITING_EXTERNAL、BLOCKED 的 Run 往下走（:469-471），所以这四种状态都执行恢复与标记。WAITING_EXTERNAL 的 Run 里某个验证 Task 恢复为 READY 时，它是到期的，同一次 pace 后面的唤醒把 Run 带回工作状态（ADR-020 决定 4）。
   - **可派发谓词** `dispatchable(task.role)`：`load_binding` 的 `active`（ACTIVE、有会话、无待生效、首个输入已交付）；所需能力 ⊆ 会话能力；并且
     - 有快照（`Context.staffing` 为 `Some`）时：快照中绑定 Agent 的事实是 `Usable` 且 `Compat::Verified`，绑定的会话按决定 4 对它新鲜。快照里没有该 Agent 即不成立（缺观察即未验证，-51）。这样被放回 READY 的 Task 派发时能通过 prepare 与闸门，除非它们看到快照之后的变化；
     - 没有快照（没有注册表的 host）时：原因为 COMPAT_UNVERIFIED 不成立（这种 host 没有闸门，不产生这个原因），其余原因只看前两项。
   - **先恢复**：每个 BLOCKED 且 `blocked_reason ∈ V` 的 Task，若 `dispatchable`，同一事务 `UPDATE tasks SET blocked_reason = NULL, next_retry_at = NULL`，再 CAS BLOCKED→READY（ADR-011:42：先清 blocker），写 `task.unblocked{task_id, reason, role, role_epoch}`（id `child_id(task, "unblocked/<revision>")`）。
   - 恢复不动的：NEED_DECISION（M2-T13）；`attempt_count`；附在 Task 上的失败项，下一个 Attempt 的返工上下文照常列出（ADR-028 决定 11 第 2a 步）。这就是 CR-018 的“绑定恢复后回到可派发”：登录转变、能力回来后的 Rebind、套件 PASS 后的 Rebind 使绑定 active 且新鲜，验证 Task 与开发 Task 一样回 READY。
   - **再标记**：到期的 Task（:510-515），其职位的绑定 BLOCKED 且原因 ∈ V → Task BLOCKED（绑定的原因），`next_retry_at` NULL，不建 Attempt，`attempt_count` 不变，写 `task.blocked{task_id, reason, missing, cause: "vacancy"}`（沿用 R2 的 id）；绑定 active 而能力不足 → BLOCKED_CAPABILITY（R2 原样）。绑定 ACTIVE 而事实为 compat_pending 的 Task 不在此标记：它被派发并由闸门拒绝一次（TEST-027-04 的“首个新 attempt 被拒”），之后按上一条等待。
   - **停滞判定**（:611）不变：被标记的 Task 不再算能推进，只有别的 Task 也都推进不了时 Run 才 BLOCKED，原因按 `blockers::ordered`（ADR-020 决定 5、ADR-028 决定 10 的 -202）；别的职位有可派发的 Task 时 Run 照常推进（AC-020-03 的 T3）。commander 的 Task 不在 pace 内（:477），由 ADR-025 处理；BLOCKED 的 Run 上验证派发照旧（ADR-028 决定 10）。

8. **冻结时的缺员规则（Q13，ADR-028 决定 3 的行 :161）。** “Run 缺 qa 或 reviewer 的绑定”只指没有绑定行（crates/hoh-core/src/persistence/completion.rs:567-577 不变）：内置职位不能被移除（config.rs:437），所以产品里只有手写夹具会出现。绑定 BLOCKED（任何原因）的验证职位不阻止冻结：候选照常冻结、开轮次、写交接，验证 Task 由决定 7 标记并等待；候选停在 VERIFYING，没有该方的报告就没有汇合（ADR-029 决定 11），所以不会 ACCEPTED（REQ-020 失败模式 1、行为 6）。completion.rs:573 的说明文字改为引用本决定。

9. **兼容闸门（Q10、Q12，AC-027-04，REQ-027 行为 4）。**
   - **一个谓词**：`hoh_agents::compat::verdict(manifest: Option<&CompatManifest>, agent, entry: &AgentEntry) -> Compat`。“相符”指清单的该 Agent 项与探测条目的身份（`AgentIdentity` 的四个字段，-104）、`help_sha256`、`schema_sha256`、`cli_version` 都相等，且 `suite.fixture_set_sha256` 等于本构建的套件集摘要 `compat::SUITE_SET_SHA256`（-52、-102，决定 10）。比受锁 schema 标题的三个哈希多比较的几项只会使更多版本未验证，不放宽任何规则。
     - 清单缺失、无该 Agent 的项、或不相符 → `Pending`；
     - 相符且 PASS → `Verified`；相符且 FAIL → `Failed`；
     - 相符、NOT_RUN 且 `suite.run_at` 非空（本 host 的套件跑过而判不了，决定 10）→ `Undecided`；
     - 相符、NOT_RUN 且 `run_at` 为空（只探测、未跑套件，AC-027-01 的条目）→ `Pending`。

     doctor 的 `assess::protocol`（assess.rs:24-55）改为调用它，`Verified` 再按 transport 给出 compatible/degraded，其余都是 unknown（结论取值与 ADR-015 决定 2 一致），说明文字写出原因（FAIL 的用例名、判不了的部分、身份或哈希不符、套件集不是本构建的）；remedy（:156）改为“host 在没有写租约时自动运行兼容套件；运行中的写任务结束后即登记该版本”。
   - **prepare 的核对（-100）**：`ProductExecutor::prepare`（product.rs:457-478）以 `Registry::fact(agent)` 取一份事实 F（决定 1；今天的 `registry.seen`，agents.rs:279-284，改为返回它），在准备其他任何东西之前依次核对，全部只用 F：
     - (a) 重读启动器与实现的身份戳（`stamp()`，agents.rs:287-302，只读元数据），与 F 的不同 → 拒绝 COMPAT_UNVERIFIED（“files changed since the last look”）；

     - (c) F 为 `LoginMissing` → 拒绝 BLOCKED_AUTH（Auth 类，staffing 之后才出现的竞争）；
     - (d) **会话新鲜**：`Assignment`（team.rs:793-827）加 `session_capabilities`（`sessions.capabilities_json`，team.rs:844-860 的查询已经连接 `sessions s`）与 `session_identity`（该会话 `team.session_bound` 的 `identity`，一次唯一索引查找）；`agent_version` 已有。`staffing::fresh(会话, F)`（决定 4 的同一函数）不成立 → 拒绝 COMPAT_UNVERIFIED，细节为“session <S> was granted for <版本/身份/能力>, the agent is now <…>; it waits for its rebind”。
     - 拒绝都在 spawn 之前：Attempt FAILED（failure_reason 为该码）、`attempt.start_refused`，没有子进程（ADR-026 决定 9 的拒绝路径，runner.rs:942-962）。`Compat` 类使 Task BLOCKED(COMPAT_UNVERIFIED)，不退避，`attempt_count` 加 1（确有一个 Attempt）。之后下一个 tick 的快照里 staffing 看到同一事实：会话陈旧 → `Rebind`（无在途时；有在途时 `change_pending`）→ `Grant` → 首个输入交付 → 决定 7 恢复。
     - (d) 封住的次序（M2T15D-100）：快照里 B 为 Pending，staffing 保留 A 的会话（决定 4 的表：compat_pending 无动作）；套件随后发布 B 的 PASS；同一 tick 的调度按 A 的会话能力授予一个从未 BLOCKED 的 READY Task；prepare 的 (a)–(c) 都过（文件、清单、登录都是 B 的），(d) 因会话的身份是 A 而拒绝——没有 (d) 时 B 会以 A 的会话与 epoch 启动。

   - **执行时的身份（-03）**：prepare 之后 runner 还要装箱、spawn 闸门、加入 cgroup、读 Git 起点、提交 RUNNING 才开闸（runner.rs:942-1026），这期间的替换由闸门自己在 exec 之前核对：
     - `GateCommand`（crates/hoh-agents/src/adapter.rs:28-32）加 `expect: Option<Expect{agent, identity: AgentIdentity, stamp: Stamp, plan}>`（都取自 prepare 的事实 F）与 `status: Option<GateStatus{path, key}>`（下一条）；闸门的 argv 为 `hoh __gate --expect <agent> <launcher_path> <launcher_sha256> <implementation_path> <implementation_sha256> --stamp <启动器的 dev:ino:ctime_sec:ctime_nsec> <实现的同样四项> --plan <fd|path> --status <path> -- <program> <args…>`，钥匙不在其中。`--expect`、`--stamp` 与 `--status` 只一同接受，缺一即以 64 退出（用法错误，gate.rs:21 今天的码）、不 exec，所以产品的拒绝总有记录；三者都不给是今天的无核对闸门（只用于直接驱动闸门的既有测试）。
     - 读到 `go` 之后（gate.rs:28-40）、exec 之前，闸门：以与探测相同的 `probe::resolve_implementation(agent, launcher)`（probe.rs:2400-2412）重新解析，要求得到同一实现路径（pi 的 `current-version` 已翻转、codex 的平台包换了、claude 的链接改指，都在这里不符）；以 `O_RDONLY|O_CLOEXEC` 打开启动器与实现，经这两个文件描述符计算 sha256（与 `file_sha256` 同算法），与 `expect` 比较；实现的描述符在哈希前后各 `fstat` 一次，两次的 (dev, ino, ctime) 不等即按“读的时候被改写”不符；两个描述符的 `fstat` 另须等于 `expect.stamp` 的对应项（item `stamp`）——prepare 的 (a) 核对了路径上的文件仍是 F 的那个，这里核对闸门打开、哈希并将执行的正是它，所以内存中的 `Expect.stamp` 就是被执行文件的身份戳，两个再核对只与它比较（-201）。任一不符或读不出 → 写 `refused` 记录（下一条；只有 `stamp` 一项不符时记录带 `stamp_only: true`），不 exec，向 stderr 写一行给人看的 `hoh gate: COMPAT_UNVERIFIED: <哪一项>`，以 65 退出。底座的进程没有运行（运行过的只是 HoH 自己的闸门）。
     - **闸门的结果通道（-101、-201）**：退出码与帧数不能证明来源——exec 之后仍是同一个 pid（gate.rs:40），已执行的底座也可能在首帧之前以任何码（包括 65）退出、在 stderr 写任何文字。所以分类只依据闸门自己写下、带底座拿不到的钥匙的记录：
       - **位置与钥匙**：`GateStatus.path` 为该 Attempt 日志目录（`Turn.logs`，适配器在 spawn 之前创建：claude.rs:478、codex.rs:663、pi.rs:558）下的 `gate.jsonl`；`key` 为 `ProductExecutor::start`（product.rs:592）每个 Attempt 以 `rustix::rand::getrandom`（hoh-app 已启用 rustix 的 `rand`，crates/hoh-app/Cargo.toml:27）取的 32 字节，小写 hex，只在 HoH 的内存里（不写进库、事件、日志或任何文件）。
       - **钥匙只经 go 行**：有 `status` 时适配器开闸写的是 `go <key>` 加换行（今天写 `go\n` 处：claude.rs:512、codex.rs:701、:732、pi.rs:603；之后的提示词照旧在同一次写入里）；闸门逐字节读到换行为止（gate.rs:28-37，`MAX_LINE` 由 16 改为 80），有 `--status` 时只认 `go ` 加 64 位小写 hex，否则以 64 退出、不 exec；没有 `--status` 时只认 `go`（今天的行为）。读完这一行钥匙就从管道里取走了，底座继承的 stdin 只剩其后的字节；写进 stdin 的字节今天不被记录，go 行也不记录。
       - **闸门写**（gate.rs，读到 go 行之后）：以 `O_WRONLY|O_CREAT|O_APPEND|O_CLOEXEC|O_NOFOLLOW`、0600 打开 path，每个决定写一行 JSON、关闭，再 exec 或退出：核对不符 → `{"outcome": "refused", "key", "code": "COMPAT_UNVERIFIED", "item", "stamp_only", "expected", "seen"}`，以 65 退出——带钥匙的只有这一种，写下它的闸门随即退出，这个 Attempt 没有底座运行，钥匙此后公开也无从利用；核对通过 → `{"outcome": "verified", "plan": "E1"|"E2", "implementation": {"path", "dev", "ino", "ctime_sec", "ctime_nsec"}}`（不带钥匙或由它导出的任何值，只供人与证据读），再 exec；exec 失败 → 追加 `{"outcome": "exec_failed", "errno"}`，以 127 退出（gate.rs:41-47 今天的行为）。记录写不进（目录不可写、磁盘满）→ 不 exec，以 65 退出：没有记录，适配器按下文当作底座自己的失败（瞬时类，有退避与封顶），下一个 Attempt 的 prepare 或闸门照样拒绝——只会更保守。
       - **底座拿不到钥匙**：钥匙不在闸门与底座的 argv、环境与继承的描述符里，也不在日志目录、工作区或库里；go 行在 exec 之前已从管道读走；exec 换掉了闸门的进程映像。已验证的底座即使读遍它够得着的文件（含 `gate.jsonl` 的 `verified` 行）、复制任何一行追加进去，也写不出钥匙相符的 `refused`。边界：底座与 HoH 是同一用户，能 ptrace HoH 进程的程序可以读它的内存（Yama `ptrace_scope` ≥ 1 时底座作为后代不能 ptrace HoH；本机为 1），这样的程序同样能改写 `.hoh/` 的库——HoH 不防护有意攻击自己的同用户进程；通道保证的是，HoH 交给底座或放在它够得着之处的任何东西都不能让它（有意或无意）产生 HoH 接受的拒绝记录。工作区禁止 unsafe（Cargo.toml:13 `unsafe_code = "forbid"`），所以钥匙走现有的 stdin 管道，不用固定号码的专用描述符（见“未采用”）。

       - **E1，实现是 ELF**（claude 链接指向的版本化二进制；直接安装的 codex；codex npm 包装解析出的 vendored 原生二进制）：闸门以 `execveat(实现的描述符, "", argv, envp, AT_EMPTY_PATH)` 执行刚算过哈希的那个 inode，argv[0] 为实现路径（codex.js 自己就这样 `process.execve(binaryPath, [binaryPath, …])`）。路径之后被 rename、删除重建、链接改指或装入新版本都不影响主进程的这次执行；`/proc/self/exe` 仍指向真实路径。经 `/proc/self/exe` 派生的辅助进程（codex 的 `--codex-run-as-process-setup`、claude 的 seccomp 辅助）执行的是同一个 inode；按路径派生的辅助进程执行的是那时路径上的文件——第二版“至多是一次失败”只在路径于底座取得自身路径之前被替换时成立（取得的是“…(deleted)”），之后的替换使它们运行新文件，见 R3（-152）。codex npm 包装另加它为 npm 安装设置的两个环境变量（`CODEX_MANAGED_PACKAGE_ROOT=<包根>`、`CODEX_MANAGED_BY_NPM=1`；只影响升级提示，HoH 不用）。

        2. **帧接纳（只 codex App Server）**：该类别嵌入的服务端帧中适配器据以判断的三种通知（`codex::APP_SERVER_NOTIFICATIONS`：turn/completed、item/started、item/completed，codex.rs:149）以被测 `ServerNotification.json` 校验，不放开 `params`。“否”说明被测版本已不会发出适配器所读的形状；“是”不证明它会发出（见第 3 类）。
        3. **回放**：该类别的嵌入 fixture 经适配器的 `replay(bytes, version) -> Replayed{state, failure, unknown_events}` 与 `expected.json` 一致（本构建的适配器处理这六类帧，REQ-027 行为 3）。

        任一项“否”→ 该用例 FAIL；没有“否”而有“判不了”（校验器给 `Unknown`、预算或截止时间用完、导出缺所需的响应 schema）→ 该用例 NOT_RUN；全“是”→ PASS。
      - `live`：恒为 NOT_RUN。被测新版本在一次真实 turn 里发出的响应帧（以及 claude 经 stdin 的提示词、pi 的 RPC 命令这些没有 schema 的载荷）离线判不了（下文第 3 类），REQ-027 决定 2 把 live smoke 交给 adapter-live 检查单独记录（tests/check-plan.json:63 的 `adapter-live`，其 `live-sessions.json`）；清单以这个用例写明它不在 PASS 的依据之内，产品从不运行它（会产生费用）。
      - **套件状态**：`probe` 与六个类别都 PASS → PASS；任一 FAIL → FAIL；否则 NOT_RUN（判不了），三种都写 `run_at` 与 `cases`。`verdict` 把相符的 NOT_RUN 且 `run_at` 非空读成 `Undecided`（决定 9）：同一身份不重跑（结果相同），哈希变了才重跑——与 FAIL 相同；这样“证据不足”永远不是 PASS（REQ-027 失败模式 1、2）。
    - **同一构建函数**：codex App Server 的请求今天在驱动里就地拼出（app_server.rs:476-505 等处）；改为纯函数 `codex::app_server::requests::{initialize, thread_start, thread_resume, turn_start, turn_interrupt, turn_steer}`，驱动与套件都调用它们。单元测试回放录制的 `app-server-turn`，断言驱动写进 stdin 的帧与这些函数对同一启动的输出逐个相等，所以套件核对的就是驱动发出的。
    - **嵌入的合成 fixture**：crates/hoh-agents/src/compat/fixtures/<agent>/<case>.jsonl 与 `expected.json`（终态、失败码、`adapter.unknown_event` 数），由 `include_bytes!` 编进产品，连同各类别的启动变体表。codex 的 `tool` 用例含一个 `params.item.type` 为 `"commandExecution"` 的 `item/started` 帧，决定 12 的能力测量用它。
    - **套件集摘要（-52、-102）**：PASS 是“本构建的请求在被测二进制上符合”的证据，所以缓存它的键必须绑定本构建怎样构建、核对与回放这些请求，不只是 fixture 文件。`compat::SUITE_SET_SHA256` 写进 `suite.fixture_set_sha256`（受锁 schema 只限定它是 64 位 hex），是下列成员按 (名字, sha256) 排序后的摘要（与 probe.rs:2577-2614 的树摘要同一算法）：
      1. `fixtures/…`：嵌入的 fixture、`expected.json` 与启动变体表（第二版的嵌入集）；
      2. `requests/<agent>/<case>/<variant>`：本构建的请求构建函数（`codex::app_server::requests::*`、`codex::exec_args`、`codex::headless_answer`、`claude::argv`、`pi::args`）对变体表中每个启动变体实际给出的消息或 argv 的规范 JSON，输入是固定的占位值（cwd `/hoh-suite`、固定的提示词、model 与会话 id），首次使用时算一次（`OnceLock`）——请求怎样构建一变，这些字节就变，不靠人记得改常量；
      3. `definition`：新的 crates/hoh-agents/build.rs 在编译时对 `crates/hoh-agents/src/**`（构建函数、套件、三值校验器 probe.rs、各适配器的 `replay`、嵌入 fixture）、该 crate 的 Cargo.toml 与工作区 Cargo.lock 计算树摘要，经 `cargo:rustc-env` 编进 `compat::DEFINITION_SHA256`（`cargo:rerun-if-changed` 指向这三者），并以 `compat::DEFINITION_FILES` 公开所列的文件名；改了怎样校验或回放（不只是怎样构建）也换键。
      所以一个 HoH 构建只接受由它自己的套件定义得出的 PASS：上一构建的 PASS 即使 Agent 的全部比较字段都不变也不相符（`Pending`），在写租约空闲时重跑。测试二进制与 `hoh` 二进制由同一源码构建，摘要相同，doctor 子进程与 host 的判定一致——所以不用可执行文件自身的哈希（二者不同）。代价：HoH 每升级一次，每个 Agent 重跑一次套件（离线，秒级），期间新 turn 等待（决定 9）。
    - codex 的嵌入帧须被录制的 0.166.0 `ServerNotification.json` 接纳（单元测试），否则帧接纳在真实版本上会误判 FAIL。录制的真实 fixture（tests/fixtures/protocol）只留在测试里，不随产品分发（其 README 的“Provenance limits”）；一个单元测试扫描嵌入 fixture，不得含录制机器的路径与凭据形态。
    - **探测读取的扩展**：`probe::conform(agent, env, plan) -> (AgentEntry, Conformance)` 走与 `probe` 相同的命令、截止时间与停止（ProbeEnv.cancel）；codex 的 schema 读取（`read_schema`，probe.rs:1599-1721）在放开 `params` 与丢弃解析值之前，先对 `plan` 的消息做不放开的校验，并只为无头答复另解析所需的响应文件（计入同样的值个数与文件上限）。
    - **何时运行与互斥（-01、-04）**。host 的注册表任务（runner.rs:474-487 的 `registry_watch`，改为也持有 store）在每次 `refresh` 之后，对每个想要查看、查看成功且 `verdict` 为 `Pending` 的 Agent，一次一个：
      - **准入**（`Store::begin_suite(project, agent, identity, now)`，一个 IMMEDIATE 事务）：读项目写者槽的行，以 leases.rs:69-71 的 `effective`（未过期，或持有者 Attempt 未结束）判断是否持有——**不看行是否存在**：结算已在同一事务把租约过期（attempts.rs:483-488、leases.rs:177-187），行与 epoch 永久保留（leases.rs:1-9，leases/tests.rs:169-181）。**至多一个打开（-151）**：准入先以 `leases::suite_open(tx)` 看本 epoch 是否已有打开的套件——有而属于另一个 (agent, 实现哈希) → 什么都不写（不延后、不打开），返回 `Busy(suite_id)`，注册表任务在那个套件结束之后的查看里再试；“一次一个”因此由持久状态保证，不只靠任务的循环。否则：持有 → 写 `compat.suite_deferred{agent, cli_version, implementation_sha256, lease_attempt_id, lease_epoch, reason: "write_lease_held", detail: "维护窗口：写租约释放后自动运行兼容套件"}`（每个 (agent, 实现哈希, 租约 Attempt, 租约 epoch) 一条，id 由四者确定，已有即不写），不运行——即 AC-027-04 的“写租约活跃时套件请求被拒绝”与 REQ-027 失败模式 5。不论持有与否，本 epoch 还没有为这个 (agent, 实现哈希) 打开的套件时，先写打开标记 `compat.suite_opened{suite_id, agent, implementation_sha256, host_epoch}`；未持有时再写 `compat.suite_started{suite_id}`，提交后在阻塞线程运行套件。过期而持有者未结束的行算持有（与 `free_slot`、`grant` 相同，REQ-037 行为 7）。
      - **套件打开时不授予写者槽**：`leases::suite_open(tx, project_id) -> Option<suite_id>` 读 `projects.host_epoch` 为 E，比较 `ids::count(ids::series(project, "compat-suite-opened/<E>"))` 与 `…-ended/<E>` 一族的计数（决定 5 的编号，-202；suite_id 为前一族的 `member(stem, n)`，n 为其计数加 1，结束事件是后一族同一个 n 的成员；同时至多一个打开）。`free_slot(writer=true)`（leases.rs:75）在它打开时返回 `None`，`grant(kind="writer")`（:109）返回 `LeaseUnavailable("the writer slot waits for compat suite <id>")`。这是写者槽仅有的两个入口，所以调度轮（rounds.rs:104、:180）与决策派发（decide.rs:568、:674）都等套件结束；读者槽与监督槽不受影响（REQ-027 只要求无写租约）。准入与授予都在 IMMEDIATE 事务里，二者按 SQLite 的写锁串行：先授予的使准入看到持有者而延后，先准入的使授予看到套件打开而等待。
      - **等待中的套件不被饿死**：打开标记在第一次延后时就写下，所以从那时起写者槽不再授予新的持有者；当前持有者结束（释放）之后，下一次注册表查看（至多一个 `TICK`）即准入。写者因此至多多等“当前写任务的剩余时间加一次套件”，而别的 Agent 接连的写任务不能无限推迟套件。该身份不再需要时（不再想要查看，或已不是当前身份）host 写 `compat.suite_ended{status: "withdrawn"}` 关闭它。
      - **发布**（`Store::publish_suite(suite_id, entry)`，一个 IMMEDIATE 事务，在 store 的写线程里）：核对该 suite 已开始、仍打开且 `projects.host_epoch` 未变；构造新清单（以注册表内存中的清单为底，替换该 Agent 的一项、其余保留、`generated_at` 取当时、按受锁 schema 校验——清单只由发布写，发布要求自己的套件仍打开，而同时至多一个打开，所以这份底就是当前清单），写同目录临时文件、fsync、rename 到 `.hoh/compat-manifest.json`、fsync 目录；写 `compat.suite_ended{suite_id, status}` 与 `compat.suite_completed{agent, status, implementation_sha256, fixture_set_sha256, cases}`；提交；成功后才换掉注册表内存中的清单。替换因此发生在“打开”的区间里，任何写者授予都不能与之并发提交。核对不过（已被关闭）→ 不替换、不写清单；校验或写入失败 → 不替换，写 `compat.suite_ended{status: "unpublished", error}`，至多每 30 s 重试。rename 之后提交失败时清单已更新而 suite 仍打开：写者槽保持关闭（只会更保守），host 每个 tick 以 `Store::end_suite` 重试关闭它。
      - **有界、停止与崩溃**：套件的命令用它自己的 `ProbeStop`（同时登记在注册表，host 停止时一并停止），运行时长以探测的时限为界（每条命令 20 s，schema 读取窗口另加 2.5 s，ADR-015 决定 2）；开始运行超过 `SUITE_LIMIT = 5 min` 时 host 停止它并写 `compat.suite_ended{status: "timed_out"}`，之后迟到的结果在发布的核对处被丢弃。host 停止时运行中的套件被停止，能写时写 `compat.suite_ended{status: "abandoned"}`。崩溃或停止没写成的，由 host epoch 关闭：`suite_open` 只数当前 epoch，新 host 启动在项目锁下把 epoch 加一（commands.rs:442-448）；项目锁由写线程持有，直到所有 store 句柄（包括套件线程持有的）都丢弃才释放（ADR-016），所以 epoch 变了即旧 host 的套件线程与发布都已不在。旧 host 留下的探测子进程（`--version`、`--help`、schema 生成）不写项目，也不写清单。
      - 结束时另重读身份戳，与开始时不同即不发布（写 `ended{status: "discarded"}`，下一轮再跑）；同一身份的 `Failed` 与 `Undecided` 不重跑，身份或套件集（本构建）变了才重跑。
    - **清单只由 host 写，放在注册表里**：host 启动时以项目根调用 `Registry::open_manifest(root)` 读 `.hoh/compat-manifest.json`（缺失为空；读不了或不合 schema 视为空，并写一条 `compat.manifest_unreadable` 诊断），并删除上次崩溃留下的同目录临时文件。闸门、staffing 的 `Fact` 与套件都在注册表的锁内读内存中的那份；doctor 读文件（ADR-015 决定 2 的位置不变）。
    - **不加请求入口**：REQ-003 只许 attach/web/doctor 与固定选项，openapi 的命令种类封闭，二者受锁；AC 只要求“租约活跃时请求被拒”，host 自己的请求满足它。
    - **测试接缝**：hoh-app 公开 `compat::register(project, agent, path)`：以产品同一套件对 PATH 上的二进制运行并经同一发布路径写清单（不伪造 PASS）；测试在 host 启动前用它登记。不登记时套件在首次查看后自动运行，既有测试的假 CLI 回答的是录制的 help 与 schema，套件对它们 PASS（正对照）。

11. **Commander（Q14，ADR-025 决定 5）。**
    - staffing 对 commander 绑定与其他职位相同：首选不可用而有可用 fallback 时换绑（epoch+1，交接包即 Commander 的首个输入，ADR-024 决定 4）。
    - **监督 turn 的永久失败进入 staffing（-05）**：决定 6 的结算对监督 Attempt 一样阻塞 commander 绑定并写排除记录，所以“探测正常、配置的模型实际不可用”的 Commander 在第一次 Model 失败后绑定 BLOCKED(MODEL_UNAVAILABLE)，staffing 按 fallback 换绑，而不是在原 Agent 上退避到封顶；Capability 同理。Auth 另经 `finished()` 进入注册表（决定 2）。
    - **监督的类别表**（wakes.rs:1244-1255；ADR-025 决定 5 的不可用原因表）：`auth` → `auth`、`capability` → `capability`、`decision` → `context`（不变），新加 `model` → `model`（对象、事实与恢复与 `capability` 相同：当前 epoch 的 turn 以该类失败且其后没有 SETTLED；恢复事实是该 epoch 此后有 turn SETTLED，或换 epoch）；`unavailable` 不保持原因（注册表的 `agent_unavailable` 观察已判它）；`compat` 不保持原因（见下条）。恢复按 epoch 与身份：换绑使旧 epoch 的类别不再计入；绑定的 BLOCKED 由 staffing 按事实解除（排除记录按版本与身份、缺认证按身份与代次）。
    - ADR-025 决定 5 的不可用原因按绑定此刻的 Agent 判：`binding_blocked` 只在没有可用候选、或换绑在等在途监督 turn 结束时成立；`agent_unavailable`、`login_missing` 换绑后按新 Agent 的观察判（“新 Agent 还没有被观察过，就不因注册表而不可用”）。所以 COMMANDER_UNAVAILABLE 只在连 fallback 都不可用时持续，另外至多持续到在途监督 turn 结束。
    - **未验证时延后，不计时（-53、-51）**：分配（wakes.rs:760 起）对 active 的 commander 绑定，`Context.observations` 为 `Some` 而其中没有绑定 Agent、或其 `verified` 为假时，不分配，写一次 `supervisor.deferred{reason: "COMPAT_UNVERIFIED"}`（`defer_once`，同一原因与 epoch 自上次分配以来只写一次）。它与 `CHANGE_PENDING` 一样等的是会自行解决的状况（写租约释放后的套件），不进入 `inactive_too_long`（wakes.rs:1789-1822 只认 NO_SESSION、FIRST_INPUT_UNDELIVERED），所以长写任务期间换了 CLI 不会把 Commander 判为不可用。`observations` 为 `None`（没有注册表的 host，没有闸门）不延后。分配之后、exec 之前身份才变的竞争由闸门拒绝，记为该唤醒的一次失败；每次这样的失败都需要一次新的身份变化。

        - 不当成工具名的：`--allowedTools` 的 `"Bash(git *)` 这类权限规则不在 `--tools` 的文字里，且它的词剥不掉不成对的引号与 `(git`；`BashOutput` 不等于 `Bash`；示例改成空格分隔的 `"Bash Edit"` 时第一段是 `"Bash`，结果 false——失败关闭：claude 不被选为 developer/qa，判决行写明 `claude:CAPABILITY_UNSUPPORTED:command_execution`，重录 help 时正对照测试会指出。
        - `--restricted`（help.txt:195-208，“removes the built-in tools that run commands or code (Bash, …)”）不作依据：它描述 HoH 不用的模式；依据只取一处，所以去掉示例里的 `Bash` 结果就是 false。HoH 不传 `--tools`、`--disallowedTools`、`--restricted`，所以默认集合适用。
      - **pi**：`pi::builtin_tools(help) -> Option<BTreeMap<String, String>>`：找到去掉首尾空白后恰为 `Built-in Tool Names:` 的行，取其后的行直到空行或第一个不缩进的行；每行在第一个 ` - ` 处分为名字与说明，两者都去掉首尾空白再用（录制品以空格把名字列补齐：`bash       - Execute bash commands`，不去掉就得到带尾随空白、不等于 `bash` 的名字，M2T15D-200）。有名字恰为 `bash` 的一行、且其说明不含 `off by default` → true；有该段而没有 `bash`，或 `bash` 的说明含 `off by default` → false；没有该段 → None。正对照：录制的 1.5.0 help（help.txt:187-195：`bash       - Execute bash commands`；grep、find、ls 的说明带 `(read-only, off by default)`）。HoH 不传 `--no-tools`、`--no-builtin-tools`、`--tools`、`--exclude-tools`。
    - **会话能力**：各适配器的 `session_capabilities`（claude.rs:150、codex.rs:592、pi.rs:518）把 `command_execution` 计入它实现的集合（claude、codex 在 YOLO 时，pi 恒为），与探测的取值相与写进 `sessions.capabilities_json`（REQ-027 行为 2）；套件的请求符合性同时核对这些启动选项对被测版本有效。
    - **离线证明不了的**：一次真实 turn 里命令确实能跑（操作系统策略、沙箱、被测版本的行为）只有 live turn 能显示，由 adapter-live 检查记录（REQ-027 决定 2）；离线的 `command_execution` 指“被测二进制声明了运行命令的内置工具，并在 HoH 的启动选项下可用”。
    - 加入这个能力键要改受锁 REQ-027 行为 2 的列表：CR-021（“移交”中的草案），属 CR-003 D1 第 1 条（REQ-020 决定 1 要求的能力在 REQ-027 行为 2 的列表里缺失，是规格之间的不一致）；不是延期。

13. **崩溃点、并发与余项。**
    - staffing 的每个写入是一个事务：提交前崩溃整笔回滚，重启后按同样的输入重判（事件 id 由 run、role、epoch 与计数决定，epoch 只加一次）；提交后、`Grant` 前崩溃，重启后照常授予（会话 id 由 run、role、epoch 派生，`INSERT OR IGNORE`，ADR-024 决定 8）。
    - staffing、pace、supervise 与分配读同一份快照（决定 1）；快照与 prepare、闸门之间的变化由 prepare 以一份当前事实做的 (a)–(d)（含会话新鲜）与闸门的执行时核对兜底（决定 9）；与结算之间的变化由结算时的绑定阻塞兜底（决定 6）；结算与崩溃恢复从同一份持久输入（会话的身份、OBSERVED 时的类别）写出排除记录（决定 6）。
    - 套件与写者槽的互斥见决定 10（K7）。
    - **余项（接受，有界）**：(a) 状态命令一直说“已登录”而令牌已失效时，同一身份的 turn 鉴权失败在本 host 生命周期内不清除，恢复靠重新登录后重启 host（每次重启至多再失败一次；上一个生命周期的结算不喂给注册表），docs/12 写明。(b) 每次身份变化，已有会话的职位上每个到期 Task 至多消耗一个被拒的 Attempt（`attempt_count` 加 1，prepare 的 (b) 或 (d)），之后按决定 7 等待已验证且新鲜的会话，不再派发。(c) 跨 HoH 升级被对账的 Capability/Model 失败，若其会话没有身份，不写排除记录，该绑定至多多一次失败的 turn（决定 6）。(d) 每次 HoH 升级，每个 Agent 在写租约空闲时重跑一次套件，期间新 turn 等待（决定 10）。
    - **所有者接受的**：决定 9 的 R1、R2（2026-11-13），附首个输入之前的再核对（pi 的 RPC、codex App Server）；R3（2026-11-14），附 turn 中的再核对。
    - **再核对的界限**：只有身份戳不符而身份不变的拒绝与取消按瞬时类，受 ADR-020 的重试封顶约束；身份变了的每次变化每个在途 turn 与到期 Task 至多各被拒或取消一次（(b)）。
    - **离线判不了、单独记录的**：新版本在真实 turn 中的响应帧，以及 claude 的 stdin 提示词与 pi 的 RPC 命令（没有 schema 导出）；清单以 `live` 用例 NOT_RUN 写明，由 adapter-live 检查记录（REQ-027 决定 2、3）。套件的 PASS 只依据被测二进制可离线核对的事实（决定 10），不声称覆盖它们。

## 不变量

- **K1** `select` 是全函数：同一 (order, required, facts, excluded) 得到逐字节相同的 `Selection`；chosen 若有，是 `order` 中第一个 usable 且之前的候选全为永久类；`evaluated` 是 `order` 的前缀；不在 `order` 中的 Agent 不出现。
- **K2** 绑定只在其职位没有在途 Attempt 时换 Agent 或 epoch；每次换绑在一个事务里写绑定、`team.binding_applied`、交接包与 session.start（REQ-019 行为 2），fallback 另有失效（若尚未）与替换事件；staffing 从不改 `config_revision`；有在途时每个 (epoch, cause, to) 至多一条 `change_pending`。
- **K3** 一个 Agent 的事实不是 usable 时，没有新的 turn 以它的进程启动：不授予会话、绑定 BLOCKED，或 prepare/闸门在执行底座之前拒绝。新 turn 只在它的会话对 prepare 所用的那份事实新鲜（版本、能力与完整身份相等）、该事实已验证时启动，闸门执行的是它刚以描述符核对过、身份等于同一事实、身份戳等于 `Expect.stamp` 的文件；有先行答复的 transport（pi 的 RPC、codex App Server）在首个工作输入之前、每个带 `expect` 的 turn 在进行中每 200 ms 把启动器与实现路径的 (dev, ino, ctime) 与 `Expect.stamp` 比较，变了即不发输入或结束该 turn。例外：R1、R2（所有者 2026-11-13 接受）与 R3（所有者 2026-11-14 接受），各自由上述再核对收窄。
- **K4** 缺员职位的到期 Task 不产生 Attempt、`attempt_count` 不变、`next_retry_at` 为空；只在 `dispatchable`（有快照时：已验证、会话新鲜）时由 pace 放回 READY，WAITING_EXTERNAL 的 Run 也一样；NEED_DECISION 不经此解除；Run 只在没有别的 Task 能推进时 BLOCKED。
- **K5** 暂时状况（429/503、未查看、探测失败、兼容待验证）从不触发 fallback；每次切换之前都有一个新的永久事实，一个 revision 与身份内的切换次数 ≤ |order|。
- **K6** 清单只由 host 写、原子替换、合受锁 schema；PASS 项的身份与哈希出自套件开始与结束时同一身份戳下的探测，PASS 依赖被测二进制的请求符合性（与 codex 的帧接纳），`fixture_set_sha256` 是本构建的套件集（嵌入 fixture、请求构建函数的实际输出、hoh-agents 的定义摘要），所以只有本构建的套件得出的 PASS 被接受；判不了从不写成 PASS。闸门、staffing 与 doctor 对“是否已验证”用同一个 `compat::verdict`。
- **K7** 在当前 host epoch 里，同时至多一个打开的套件；套件运行（`compat.suite_started` 之后、`compat.suite_ended` 之前）与写者槽被有效持有不同时成立：准入要求写者槽不被 `effective` 持有，套件打开（`compat.suite_opened` 多于 `compat.suite_ended`，从第一次延后起）时写者槽不授予新的持有者，二者在 IMMEDIATE 事务里串行；清单的替换在核对仍打开的同一事务里发生，以当时唯一的清单为底。
- **K8** 迟到的旧结果不覆盖新的恢复事实：turn 的缺认证只在其身份是当前身份、其代次不早于最近恢复事实时进入事实；排除记录只对同一版本与同一 `AgentIdentity` 适用，其身份取自 Attempt 的会话，所以 runner 的结算与崩溃恢复写出同一条记录（同一 id，至多一次）。
- **K9** COMPAT_UNVERIFIED 的结局只来自 HoH 自己的判断：prepare 的拒绝、闸门写下的钥匙相符的 `refused` 记录、两个再核对（比较内存中的 `Expect.stamp`）；钥匙只经 go 行交给闸门，底座拿不到，所以底座的退出码、帧数、输出与它写的任何文件从不产生它，已执行的底座自己的失败按它自己的类别（多为瞬时类）结算。其中只有身份戳不符而身份不变的按瞬时类结算。

## 未采用

- **在 checkpoint 里选 fallback**（配置路径）：fallback 会改变 `config_revision` 或被 `changes()` 读成配置修改，与 ADR-022 决定 8 v3 冲突；staffing 只改 Agent 与 epoch。
- **首选恢复即换回**：每次换绑都是 epoch+1、交接与一次 Commander 唤醒，来回切换没有收益（Q2）。
- **兼容待验证即阻塞绑定或触发 fallback**：TEST-027-04 要求“首个新 attempt 被拒”，绑定级阻塞使这个 Attempt 根本不存在；待验证在维护窗口自行解决。
- **只回放本构建的 fixture 即写 PASS**（第一版）：与被测二进制无关，任何探测成功的版本都 PASS（M2T15D-02、-50）。
- **按版本录制的 fixture、缺失即 FAIL**：任何真实升级都会阻塞到有人录制；随产品分发录制品会泄露操作者数据。
- **判不了按 Pending 重跑，或按 PASS**：前者对同一身份永远得到同一结果、反复运行；后者放宽闸门。
- **在套件里做 live smoke**：产生费用，REQ-027 决定 2 选了离线必需、live 单独记录。
- **套件以写者租约占位**：`leases.attempt_id` 引用 attempts，要伪造 Task 与 Attempt；**新的租约种类 `maintenance`**：`leases.kind` 的 CHECK 受锁，需改 001_initial.sql 的 CR。事件标记在锁内即可，且能挡住超时之后迟到的发布。
- **只在进程内加互斥锁**：挡不住超时之后迟到的发布，停止与崩溃之后也无从核对；事件标记加 host epoch 两者都覆盖。
- **把实现复制进 memfd、封存后执行**（可关闭 R1）：`/proc/self/exe` 变成 `memfd:`，codex 以自身路径派生的辅助进程与 arg0 分派失效，`vm.memfd_noexec` 也可能禁止；脚本实现仍需按路径读。
- **照旧执行包装、事后看 `/proc/<pid>/exe`**：旧版 Node 上 codex.js 以子进程启动原生二进制，pid 不同；脚本实现的 exe 是解释器，看不到脚本。
- **加一个运行套件的 CLI 或 API**：REQ-003 与 openapi 受锁，需 CR；host 自动运行已满足 AC。
- **原地更新 `sessions.capabilities_json` 或把身份塞进它**：改写已结束 Attempt 所用会话的记录，且该列只放能力；epoch+1 的新会话保留历史，身份记在 `team.session_bound`（Q6）。
- **按时间重试 turn 发现的缺认证**：REQ-020 行为 7 不许重试永久错误；改为只在看得见的恢复事实时清除。
- **新的原因码（如 NOT_INSTALLED）**：CR-003；用已有码加细节行。
- **探测超时触发 fallback**：REQ-020 决定 3。
- **只靠注册表、结算时不阻塞绑定**：同一 tick 的 pace 会在 staffing 看到注册表的事实之前把 BLOCKED_AUTH 的 Task 放回 READY，多一次失败的 Attempt。
- **把命令执行能力记为缺口延后**（第一版决定 12）：REQ-020 决定 1 是受锁义务，免除它要所有者批准（M2T15D-06）。
- **以“65 退出且没有帧”认定闸门拒绝**（第二版）：exec 之后是同一个 pid，已执行的底座也可能这样退出；误判为 Compat 会让决定 7 立即恢复 Task 并反复派发同一个失败的程序，绕过退避与封顶（M2T15D-101）。
- **专用的描述符或管道报告“已 exec”**（CLOEXEC 管道读到 EOF 即已 exec，std 的 spawn 就这样报告 exec 失败）：要在子进程里把管道放到固定的描述符号上，std 没有安全的 API，`pre_exec` 是 unsafe，而工作区 `unsafe_code = "forbid"`（Cargo.toml:13）；钥匙走开闸已有的 stdin 管道，不需要 unsafe。
- **记录里写明 nonce，适配器取 nonce 相符的最后一行**（第三版）：`verified` 行把 nonce 明文留在底座可读写的文件里，已验证的底座可读出它、追加同 nonce 的 `refused`，把自己的失败变成 COMPAT_UNVERIFIED，绕过退避与封顶（M2T15D-201）。
- **对记录做 HMAC**：也能防伪，但再核对仍要读底座可写的文件（被删除即无从比较）；改为只让拒绝带钥匙、再核对比较内存中的身份戳，更简单，也不需要新的依赖。
- **再核对只看身份（发现变化后重新哈希，相同即继续）**：换走再换回之后路径上的内容与哈希都和核对时相同，而解释器读到的可能是另一份；所有者的规则是 (dev, ino, ctime) 变了即取消。只把这种情形的类别降为瞬时类，界限由重试封顶给出。
- **以 HoH 可执行文件自身的哈希作套件键**：测试二进制与 `hoh` 二进制不同，doctor 子进程与进程内的 host 会对同一清单给出不同结论；源码与锁文件的摘要对同一源码的所有构建相同。
- **只用手工递增的套件版本常量**：改了请求构建函数而忘了递增，就会接受旧 PASS——正是 M2T15D-102；构建函数的实际输出与源码摘要不靠记忆。
- **允许多个打开的套件，发布在事务内重读清单**（M2T15D-151 的另一个选项）：也是失败关闭，但探针并行、写者槽关闭得更久；一次一个更简单，也让发布的底清楚。
- **prepare 改用 tick 的快照**：派发与 prepare 之间文件或登录的变化要等下一个 tick 才看到；现在 prepare 读一份当前事实，并用它核对会话（-100），既不旧也不混用两次读取。
- **排除记录的身份另存一条 `attempt.ran` 事件**（M2T15D-103 的另一个方向）：多一个来源就要证明它与会话的身份一致；由 (d) 与闸门，二者本来相等，直接读不可变的会话身份即可。

## 与倾向不同之处

1. **兼容待验证不触发 fallback，也不阻塞已有会话的绑定**（倾向 Q1 把 compat unverified 列为触发）：TEST-027-04 要一个被拒的 Attempt，REQ-020 决定 3 把会自行解决的状况归为等待；只有套件 FAIL 与判不了是永久的。新会话仍只授予已验证的版本。
2. **turn 发现的缺认证另在结算事务里阻塞绑定**（倾向只说进入注册表）：否则同一 tick 的 pace 会先放回 Task；注册表事实的锁存与清除按身份与代次，清除条件写成看得见的转变、新身份或重启，因为状态命令可能一直说“已登录”。
3. **能力、模型的 turn 失败另有持久的排除记录**（倾向说是绑定的事实）：换 epoch 后绑定上的事实会丢，没有记录就可能在候选间来回；记录按 revision、版本与身份（`AgentIdentity`）失效。
4. **粘滞到“修改了该职位的 revision”**，而不是任何新 revision：ADR-022 决定 8 v3 让未修改的职位随 revision 原样推进。
5. **COMMANDER_UNAVAILABLE 另可持续到在途监督 turn 结束**（倾向说只在没有可用 Agent 时）：ADR-025 决定 5 按绑定此刻的 Agent 判，而换绑必须等在途结束（REQ-019 决定 3）。
6. **闸门执行已解析的实现而不是包装**（倾向未提）：包装在运行时重新解析，闸门的核对会被它绕开；包装仍在身份里。
