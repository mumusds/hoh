# ADR-028 · 候选验证的派发、并行 barrier 与运行目录

状态：第一版草案（设计审查前；M2-T16）

## 背景

M2-T16 的验收是 AC-021-05、AC-035-03、AC-035-05、AC-036-03、AC-037-02、AC-037-03、AC-037-04、AC-053-03、AC-054-03、AC-039-03（都属 `integration`）。done_when 另要求：Commander 不可用时 candidate_ready 仍派发 QA/Review；FAILED/UNKNOWN 永不投影为 PASS；AC-039-03 经产品的 QA 派发、同一收集函数与装箱器生成并由 FakeAgent 捕获（CR-016）；为 QA、Reviewer 与返工的 Developer 加代码类上下文来源（ADR-026 决定 12）；写 `handoffs` 表（ADR-026 决定 6）。

起点（预研 `.hoh-dev/evidence/m2t16-prep/inventory.md`、`notes.md`，按 main 8b88397 复核）：

- `Store::accept_task_result`（persistence/results.rs）已能在一个事务里把 Developer 的 COMPLETED TaskResult 变成 Task RUNNING→IMPLEMENTED→VERIFYING、候选 FROZEN→VERIFYING、`candidate_ready` 事件与 qa、reviewer 两条 kind=handoff 的 outbox 行（ADR-018 决定 5、6）。产品里没有任何调用者：Developer 的 Attempt 成功只把 Task 置 IMPLEMENTED（persistence/runner.rs 的结算）。
- 产品里没有 Developer、QA、Reviewer 的结构化输出通道：只有 Commander 的文件桥（ADR-025 决定 8，`messages.jsonl`）。
- 冻结驱动 `verify::freeze` 与检查驱动 `verify::check`（ADR-027）只是库，host 不调用；host 启动不对账候选。独立 Review 对 m2t10-008 的 V01-IR-001（critical）指的就是这一缺口。
- outbox 的投递机制（`claim_outbox`、`consume`、`Dispatcher`/`Consumer`，ADR-018 决定 4）没有接入 host，没有 qa/reviewer 消费者。
- 没有 barrier、运行目录、Attempt 级的 tree 核对、Issue 写者、`handoffs` 写者、代码类上下文条目、`iteration.completed` 产生方、wait-for 视图。
- 规格行（`specs`）没有文件路径，产品里也还没有规格导入（M3-T02）；冻结要求 spec 与 test plan 是候选的跟踪文件（ADR-027 决定 4）。
- CONTRACT 第 3 条：`hoh` 的子命令只保留 attach、web、doctor。docs/06：没有独立工具接口时用规范化结构化输出或文件提交桥，不假设所有 Agent 有相同的自定义工具。

## 决定

1. **角色输出桥（扩展 ADR-025 决定 8）。** 每个 Developer、QA、Reviewer 的 Attempt 和 Commander 的回合一样，在自己的 Attempt 目录下有桥文件 `messages.jsonl`。Prompt 的任务上下文写明它的路径；执行器在 Attempt 结束时按同样的上限（`BRIDGE_LINES`、`BRIDGE_BYTES`）读取非空行，放进 `Observed.messages`。行的种类：`TaskResult`（protocol.schema.json，`role` 须是本 Attempt 的角色，run/task/attempt/role_epoch 须是本 Attempt 的），以及 kind 为 `query` 或 `steer` 的 HCP `Message`（只有验证角色的会被处理，见决定 9）。一行不合 schema 或身份不符即记 `bridge.rejected{attempt_id, line, reason}`，不影响其他行。同一 Attempt 有多条 TaskResult 时取最后一条。结算事务把桥内容（行与 sha256）记进 `attempt.outputs` 事件，供重放与审计。

2. **Developer 完成即冻结（ADR-027 决定 4、5 的移交，REQ-052 行为 1、2，REQ-053 行为 1）。** 写者 Attempt 的执行结束且成功、桥里最后一条 TaskResult 的 status 为 COMPLETED 时，runner 在结算之前、写租约仍在的时候：
   - 生成或复用 `.hoh/environment.json`（决定 3），用 `verify::freeze` 冻结写者工作区：spec 取 `contracts/requirements.json`，test plan 取 `tests/check-plan.json`（项目布局约定；规格事实源的位置由 M3-T02 接手，见移交）。冻结拒绝（脏工作区、链接、spec 摘要与 Run 的 spec 不符等）时不冻结，记 `candidate.freeze_refused{attempt_id, reasons}`，这次 Attempt 按协议修复处理（决定 11）。
   - 冻结得到候选 C 后，用 Runtime 构造的 TaskResult 调 `Store::accept_task_result`：status、summary、evidence、issues、next_action 取自 Agent 的 TaskResult，candidate_id 取 C；Agent 自己给出的 candidate_id 非空且不等于 C 时拒绝（CANDIDATE_MISMATCH 的 `task_result.rejected`），按协议修复处理。`Frozen::Existing` 按状态处理（ADR-027 决定 5）：同 Run 同内容且为 FROZEN 时照常；为 STALE、INVALID、REJECTED 时不复活，记 `candidate.freeze_refused{reason: "content already judged; commit anew"}`，按协议修复处理；另一 Run 的同内容同样拒绝。
   - 接受的事务即 ADR-018 决定 5 的那个（Task 到 VERIFYING、候选到 VERIFYING、candidate_ready、两条交接），另加决定 4 的 `handoffs` 行。之后的结算看到 Task 已不是 RUNNING，不再置 IMPLEMENTED；写租约随结算释放（REQ-019 行为 6 的工作区记录照旧）。
   - status 不是 COMPLETED 或没有 TaskResult 时，结算照旧（成功的 Attempt 置 IMPLEMENTED，交给 Commander），另记 `task_result.missing` 或 `task_result.unsupported{status}`，便于监督摘要看到。

3. **环境描述（ADR-027 决定 4 的移交）。** `.hoh/environment.json` 由 host 生成：`{schema_version, hoh_version, os{sysname, machine}, tools{git, cargo?}}` 之类只与环境有关、不含时间与随机值的字段，键排序、紧凑、以换行结尾；内容与已有文件相同即不重写。这样 host 重启不改变它的摘要，检查不因失败模式 3 被拒。字段集合写进 docs/22。

4. **`handoffs` 表与交接包对象（ADR-026 决定 6）。** `accept_task_result` 的事务为每条验证交接写一行 `handoffs(handoff_id = 消息 id, run_id, from_role = "runtime", to_role, role_epoch, package_artifact_id, state = PREPARED)`；交接包（ContextHandoff 的规范 JSON）先写成对象并登记 artifacts 行。状态：消费者创建验证 Task 时 → DELIVERED；验证 Attempt 以它启动（Prompt 已发出）时 → ACCEPTED；在派发前候选已 STALE/INVALID 或接收角色的 epoch 已变 → REJECTED（带原因事件）。Commander 交接包（ADR-024）也写这张表：交接事务写 PREPARED，首个输入送达时 DELIVERED（同一套状态，from_role 为旧持有者的角色）。

5. **验证交接的消费（ADR-018 决定 4、5 的移交）。** host 的循环在每个 tick 的调度轮之前运行 HCP 投递，只为 qa、reviewer 的 kind=handoff 行注册产品消费者（其他种类与角色不领取，保持 PENDING，steer/query 的产品路由移交 M3-T04，见移交）。消费者在一个事务里：
   - 核对交接仍然有效：候选仍是 Run 的当前候选且为 VERIFYING，接收角色的 epoch 等于消息的 role_epoch；不成立即回执为 rejected（REJECTED 的 `handoffs`），不创建 Task。
   - 创建一个验证 Task：`task_id = child_id(候选, "verify/<角色>")`（幂等），role 为 qa 或 reviewer，writer=0，spec_id 为 Run 的 spec，layer 0（与修复同层，先于普通增量），状态直接 READY，`task_requirements` 复制 Developer Task 的；事件 `verification.dispatched{candidate_id, task_id, role, handoff_id}`。不移动 Developer Task 的 revision（两条交接带同一个 expected_revision，ADR-018 决定 6）。
   - 写回执与 `handoffs` 的 DELIVERED。
   KeyReuse 计为一次拒绝、不重试到死信（M2T17R-254）；投递上限取 `delivery.max_delivery_attempts`。新持有者首个输入之前不投递给它（M2T17R-153）：验证交接只创建 Task，不投递到会话，所以对它是空条件；写进测试。

6. **Runtime 规则类派发（ADR-025 决定 3 的移交，AC-035-05、AC-021-05）。** 验证 Task 的派发是 Runtime 规则类：调度轮对 BLOCKED 的 Run 除已排的重试外也派发验证 Task；派发通知带 `origin: "verification"`，runner 对 BLOCKED 与 WAITING_EXTERNAL 的 Run 放行。消费者本身不看 Run 的状态（暂停、取消除外：PAUSE_REQUESTED/PAUSED/CANCEL_REQUESTED/CANCELLED 的 Run 不创建验证 Task，交接保持 PENDING，恢复后再消费）。所以 Commander 不可用（Run BLOCKED，COMMANDER_UNAVAILABLE）时，candidate_ready 照样产生两条交接、两个验证 Task 与派发。

7. **运行目录（REQ-037 行为 3、5）。** 每个验证 Attempt 在 `.hoh/runs/<attempt_id>/` 有自己的检出：`git clone --shared --no-checkout --quiet <项目根> <目录>`，再 `git -C <目录> checkout --quiet --detach <候选 commit>`，核对 HEAD 与 tree 等于候选（不等即拒绝启动，Attempt 以非瞬时失败结束）。`--shared` 不复制对象，不写项目仓库的索引、引用或对象。Agent 的工作目录是它。执行器在 spawn 之前、启动门打开之前取它的工作区哈希（ADR-021 g：HEAD、tree、`diff --binary` 的哈希、未跟踪内容的哈希）作为 `pre_tree`，记进 RUNNING 的提交。运行目录在该 Attempt 的验证证据都已入库、Attempt 终结之后删除；host 启动时删除没有活 Attempt 的运行目录。

8. **检查请求桥（REQ-053 行为 3，ADR-027 原则二）。** 验证 Agent 运行检查计划条目的“run_check 类绑定工具”是一个文件提交桥，不是 `hoh` 的子命令：
   - 执行器在 Attempt 目录写一个 POSIX sh 小脚本 `run-check`，路径经环境变量 `HOH_RUN_CHECK` 与 Prompt 的任务上下文给出。`run-check <check_id>` 原子地写 `checks/<n>.request.json{check_id}`，然后等待 `checks/<n>.response.json`（上限为计划超时加宽限），打印结论与记录路径，以检查的退出码结束（请求被拒为 2）。
   - host 为每个运行中的验证 Attempt 轮询它的 `checks/`，按序号逐个处理：只接受冻结计划里的 check_id；以该 Attempt 为生产者、运行目录为检出、`.hoh/` 为状态根调用 `verify::check::run`（ADR-027 决定 1、6、8：前后核对、记录、证据、恢复协议都在其中）；写回应（outcome、原因、record 路径、exit_code）。同一 Attempt 的请求串行；每个 Attempt 至多 `MAX_CHECK_REQUESTS`（初值 32）个。
   - Attempt 被取消或结束时，进行中的检查按 ADR-027 决定 6 收尾（记录照写、退出码 130），之后不再处理它的请求。
   - 证据的 outcome 来自检查，不来自 Agent 的自述；Agent 的报告由 M2-T18 入 independent_reports。

9. **Attempt 级的运行后核对（REQ-037 行为 5，AC-037-03，ADR-027 移交）。** 验证 Attempt 结束（任何结束路径：成功、失败、取消、reconcile 结算）时，在它的结算之前取运行目录的工作区哈希 `post_tree`，并核对 HEAD 与 tree 仍是候选。写 `verification.tree_checked{attempt_id, candidate_id, pre_tree, post_tree, equal}`。不相等或读不了时，经 `Store::record_evidence` 写一条 INVALID 证据，执行记录按本决定的形态：check_id 为该角色的 `independent-qa` 或 `independent-review`，command 为 `["hoh", "verification-attempt", <attempt_id>]`（不声称运行了计划命令），exit_code 0、`source_unchanged=false`，stdout/stderr 为空文件，artifacts 为空，前后 tree 进 `evidence.recorded`；记录写在 `.hoh/evidence/<候选>/<check>/<record>/`，走 ADR-027 决定 8 的恢复协议（记录目录与锁、先写待入库事实、再写记录与提交）。原则一对它给出 COMMAND_MISMATCH 与 SOURCE_CHANGED 的否决，所以候选在同一事务置 INVALID，traceability 的文件扫描同样否决；M2-T16 从不直接改候选状态。同一事务写 `integrity_violation`（ADR-027 决定 7）。

10. **barrier（REQ-037 行为 4，AC-037-02、AC-054-03）。** 一个候选的 barrier 由它的两个验证 Task 组成，从 candidate_ready 打开，到两者都**结束验证**时关闭：Task 为 IMPLEMENTED（Attempt 成功结算）、BLOCKED 或 CANCELLED，且没有待派发的重试（失败的验证 Attempt 按 ADR-020 的重试策略重排，重排期间 barrier 不关）。关闭由 runner 在使第二个验证 Task 结束的那个结算事务里完成（或由 reconcile、取消在同样的位置完成），写：
    - `verification.barrier_closed{candidate_id, qa{task_id, attempt_id, state}, reviewer{...}, evidence:[{evidence_id, check_id, outcome}]}`，事件 seq 必然大于两个 Attempt 的终态事件；
    - `iteration.completed{iteration, candidate_id, verdict}` 与一行 `iterations(run_id, number)`（决定 12）；
    - 候选的迁移：有任一证据为 FAIL 或 INVALID、或任一验证 Task 为 BLOCKED/CANCELLED 时 VERIFYING→REJECTED（`AND state = 'VERIFYING'`，不覆盖 INVALID 或 STALE）；否则保持 VERIFYING，等 M2-T18 的汇合函数在同一关闭点判定 ACCEPTED 或 REJECTED（AC-054-05 归 M2-T18）。M2-T16 从不写 ACCEPTED，所以 FAILED/UNKNOWN 不会投影为 PASS。
    - Developer Task 的迁移：候选 REJECTED 时按决定 11 的返工计数 VERIFYING→READY（ADR-011 §3 的“验证失败待修复”）或 BLOCKED；返工的派发是决策类（调度轮在 RUNNING/VERIFYING 的 Run 里派发）；候选仍为 VERIFYING 时 Developer Task 不动。
    QA 与 Review 互不等待：一方失败不取消另一方（REQ-054 行为 7）。

11. **协议纠正与返工的计数（ADR-020 决定 10、ADR-022 决定 6 的移交：两者的调用方都是 M2-T16）。** 都经已有的 `Store::request_repair`：
    - 协议纠正：Developer 的冻结被拒、TaskResult 缺失、不合 schema 或被拒。请求 `Repair::Protocol{attempt_id}`，键为这条纠正链的首个 Attempt（链上的后继 Attempt 在 `task.protocol_correction{root, attempt_id, reasons}` 事件里带着它），上限 `max_protocol_repairs`。准许时这次 Attempt 照常结算，Task 回 READY（纠正的再派发是决策类，与返工相同，不扩大 ADR-025 决定 3 的 Runtime 规则类清单），下一个 Attempt 复用同一会话，Prompt 的任务上下文带上拒绝原因；超限时 `request_repair` 已把 Task 置 BLOCKED（NEED_DECISION）并写 need_decision。
    - 返工（决定 10 的 REJECTED）：请求 `Repair::Local{fingerprint}`，fingerprint 为被拒候选的失败集合的摘要（FAIL/INVALID 证据的 check_id 与 OPEN Issue 的 fingerprint，排序后 sha256），上限 `max_local_repairs`；同样的失败反复出现才累积。准许时 Developer Task VERIFYING→READY、`attempt_count` 清零（重试预算按迭代计），事件 `task.rework{candidate_id, fingerprint, count}`；超限时 Task BLOCKED（NEED_DECISION）。

12. **迭代计数（ADR-020 的移交）。** 迭代 = 一个候选的验证 barrier 关闭。每次关闭插入 `iterations(iteration_id, run_id, number = 已有数 + 1)`，并按 ADR-020 的用量规则累加 `iterations` 用量；`max_iterations` 的判定照旧由 ADR-020 的预算检查读取。`iteration.completed` 是 balanced 监督的轮次边界唤醒（ADR-025 决定 2）的产生方。

13. **barrier 期间的改写请求（REQ-037 行为 6、失败模式 5，AC-037-04，REQ-053 行为 5）。** 验证 Attempt 桥里 recipient_role 为 developer 的 `query`/`steer`，在它的候选 barrier 未关闭时一律拒绝：同一结算事务写 `request.rejected{message, reason_code: ILLEGAL_TRANSITION, detail: "the candidate under verification is not changed; an Issue for the next candidate"}` 与一行 `issues(candidate_id = 该候选, fingerprint = sha256(规范化 payload 文本), severity = payload.severity 或 medium, state = OPEN, description)` 及 `issue.opened` 事件；不入 outbox、不形成等待。wait-for 视图（`Reader::wait_for`）由未结束的角色间请求（PENDING/DELIVERING 的 query/steer outbox 行，发送方→接收方）构成，所以被拒的请求不产生边。修复在 barrier 关闭后经返工进行（决定 10），返工的派发事件必然晚于 barrier_closed；返工产生的 C2 冻结时 STALE 旧候选（ADR-027 决定 5），C2 的 acceptance_results 在它自己的 QA/Review 之前为 0 行。

14. **验证 Prompt 与代码类来源（REQ-053 行为 2，AC-053-03，AC-039-03，ADR-026 决定 3、10、12）。** 验证 Attempt 的 Prompt 由执行器用交接包（决定 4 的对象）经 `Reader::verification_context` 与同一装箱器生成，不另写路径：
    - 证据上下文里 Developer 的自测报告：TaskResult.evidence 中每个 ArtifactRef，按普通文件、非阻塞读取并核对 sha256，UTF-8 文本取前 8 KiB（截断处标明），条目标为 `diagnostic`（“开发者自测（diagnostic，仅作诊断，不作验收依据）”），relevance 最低，排在全部 AC 正文之后（AC 是强制项，按装箱顺序先于证据层）。Developer Attempt 自己的原始日志与会话记录（`attempt.artifacts` 里登记为 raw log 的对象）从不读入正文，即使出现在 TaskResult.evidence 里也只按引用列出。
    - 代码类来源：候选相对其基准改动的文件（`git diff --name-only <基准> <候选 commit>`，基准为同一 Run 被它取代的候选的 commit；没有时为 Developer Task 首个写者 Attempt 启动时记录的 HEAD，见下），按路径排序，每个文件读候选 commit 中的内容（`git show <commit>:<path>`，非 UTF-8 或超过 64 KiB 的只列路径），至多 50 个文件，条目类别 Code，交给装箱器按 45% 的份额取舍。返工的 Developer 用同一来源（它的候选为被拒的那个）。
    - 写者 Attempt 在 RUNNING 的提交里记 `attempt.workspace_start{head}`，供上一条的基准。

15. **host 启动（ADR-027 决定 8 的移交）。** host 启动时、在第一个 tick 之前，对每个有记录目录的候选调用 `check::reconcile`；一个候选的错误记 `candidate.reconcile_failed{candidate_id, error}` 并挡住该候选（它的验证 Task 不派发），不使 host 启动失败。没有活 Attempt 的运行目录与检查请求删除。

16. **验证报告的保存（AC-054-03）。** 验证 Attempt 结束时，执行器从最后一条助手消息里取 ```hoh-report 代码块（与 `tools/agent_task.py --report-out` 相同的提取规则），由 Runtime 补上 session_id、candidate_id、spec_sha256、raw_session{path, sha256}（该 Attempt 的原始日志对象）、native_attempt{path, sha256}，写成对象并登记，事件 `verification.report{attempt_id, role, status, report{path, sha256}}`。它进 `independent_reports`、Issue 登记与投影由 M2-T18 完成。
