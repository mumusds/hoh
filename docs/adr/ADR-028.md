# ADR-028 · 候选验证的派发、并行 barrier 与运行目录

状态：第六版（设计审查第 5 轮之后；M2-T16）

## 背景

M2-T16 的验收是 AC-021-05、AC-035-03、AC-035-05、AC-036-03、AC-037-02、AC-037-03、AC-037-04、AC-053-03、AC-054-03、AC-039-03（都属 `integration`）。done_when 另要求：Commander 不可用时 candidate_ready 仍派发 QA/Review；FAILED/UNKNOWN 永不投影为 PASS；AC-039-03 经产品的 QA 派发、同一收集函数与装箱器生成并由 FakeAgent 捕获（CR-016）；为 QA、Reviewer 与返工的 Developer 加代码类上下文来源（ADR-026 决定 12）；写 `handoffs` 表（ADR-026 决定 6）。

起点（预研 `.hoh-dev/evidence/m2t16-prep/inventory.md`、`notes.md`，按 main 8b88397 复核）：

- `Store::accept_task_result`（persistence/results.rs）已能在一个事务里把 Developer 的 COMPLETED TaskResult 变成 Task RUNNING→IMPLEMENTED→VERIFYING、候选 FROZEN→VERIFYING、`candidate_ready` 事件与 qa、reviewer 两条 kind=handoff 的 outbox 行（ADR-018 决定 5、6）。产品里没有调用者：Developer 的 Attempt 成功只把 Task 置 IMPLEMENTED。
- 产品里没有 Developer、QA、Reviewer 的结构化输出通道，只有 Commander 的文件桥（ADR-025 决定 8，Attempt 结束后读取）。
- `verify::freeze` 与 `verify::check`（ADR-027）只是库，host 不调用；host 启动不对账候选（独立 Review 对 m2t10-008 的 V01-IR-001）。
- outbox 的投递（ADR-018 决定 4）没有接入 host，没有 qa/reviewer 消费者。
- 没有 barrier、运行目录、Attempt 级 tree 核对、Issue 写者、`handoffs` 写者、代码类上下文条目、`iteration.completed` 产生方与 wait-for 视图。
- Commander 的验收门禁（decision.rs 的 `Evidence::gate`，persistence/decide.rs 的 `load_evidence`）接受状态为 VERIFYING 或 ACCEPTED、验收行全为 PASS 的候选，不看 barrier 与验证结论。
- `specs` 没有文件路径，产品里也还没有规格导入（M3-T02）；冻结要求 spec 与 test plan 是候选的跟踪文件（ADR-027 决定 4）。
- CONTRACT 第 3 条：`hoh` 的子命令只保留 attach、web、doctor。docs/06：没有独立工具接口时用规范化结构化输出或文件提交桥，不假设所有 Agent 有相同的自定义工具。

## 第二版的更正（设计审查第 1 轮：Codex M2T16D-01..11 FAIL，Claude M2T16D-50..68 FAIL）

- 验收入口（-01 critical、-50）：只“不写 ACCEPTED”挡不住 Commander 现有的接受与完成提议。门禁改为只认 ACCEPTED 的候选（决定 12）。
- Developer 完成（-03、-11、-55、-66）：冻结、接受与结算合成一个提交，正常结束与 reconcile 共用；输出的处置改为一张表（决定 3、4）。
- barrier（-06、-07、-08、-51、-52、-56、-57）：barrier 由持久的验证义务构成，只由每个 tick 的幂等清扫关闭；修复义务、未完成与待汇合三种结论分开；INVALID 与 Issue 也走返工，STALE 的候选让它的 Developer Task 重新冻结；验证 Task 不受 Commander 迁移（决定 9、10、11）。
- 修复计数（-09、-53）：裁决函数接受调用方的事务、按动作身份幂等，指纹限定到 Developer Task 与失败的 (AC, 测试)（决定 11）。
- 运行中的请求（-05、-58、-64）：验证 Agent 的请求经运行中轮询的请求桥，即时拒绝并开 Issue（决定 7、13）。
- 检查进程（-04）：在 Attempt 的进程追踪之内运行，Attempt 的结束证明覆盖它们（决定 7）。
- 运行目录（-02、-61）：放到项目树之外，恢复冻结的环境文件，完整前核对；验证 Attempt 不续接原生会话（决定 6）。
- Prompt（-10、-59）：强制的身份头；自测报告只取已登记的对象（决定 2、14）。
- 报告（-60）：产品的 native_attempt 对象与 raw_session 的来源、无效时的协议纠正（决定 15）。
- 移交（-54）：CR-018 改 M2-T18、M3-T02、M3-T04 的 done_when；逐条列出承接与改派（移交节）。
- 测试（-62、-67）：补正对照与 done_when 各项的测试（测试计划）。
- 其余（-63、-65、-68）：验证 Task 的 id 与消息 id 分开；Issue 的 severity、指纹与 id；守卫清单加新路径。

## 第三版的更正（设计审查第 2 轮：Codex M2T16D-100..105 FAIL，Claude M2T16D-150..163 FAIL）

两类问题第二次出现，所以本版先改模型、再改条文（docs/19 的同类两次规则）：

- **barrier 的存活（第 1 轮 -08、-57，第 2 轮 -101、-103、-105、-151、-152、-153）。** 第二版的“义务 + 交接消费 + 单次关闭”有太多不归一的出口：交接被拒、死信、关闭后又挂接、合法的非 COMPLETED 结果、验证 Task 的终态。更正为**验证轮次**（决定 9）：一轮属于一个候选，含一组源开发 Task，在冻结的完成提交里与它的两个验证 Task 一起原子地建立（不再经投递循环）；每轮各自关闭一次；被取代的候选上未完成的源 Task 在取代它的提交里转入新候选的轮次，不再重跑 Developer；验证 Task 的输出不完整时在同一轮内纠正；轮次关闭时验证 Task 进入终态。不变量与每个状态的出口写成一节（不变量）。
- **结论的语义（第 1 轮 -06、-52、-56，第 2 轮 -100、-150、-154、-155）。** 第二版自己写了一套“哪些证据算失败”。更正为复用 ADR-027 原则一的结论：只有有结论的失败触发返工；无结论（超时、中断、未开始、缺插件、不完整）与覆盖缺口在同一候选上重新验证；Issue 只认本任务开出的改写请求与 critical/high；返工按失败项逐项计数（决定 11、12）。
- 其余：源 Task 与当前轮次的关联 CAS（-102）；门禁测试先满足旧门禁的全部其他条件（-104，已在 S1 实现）；C2 验收行的解释与断言（-156）；TaskResult.evidence 只丢弃不合规的项（-157）；测试计划的补充（-158）；移交的归属（-159、-160、-163）；只有 steer 或改写意图的 query 开 Issue（-161）；合成记录的命令标记（-162）。

## 第四版的更正（设计审查第 3 轮：Codex M2T16D-200..204 FAIL，Claude M2T16D-250..260 FAIL）

第三版的轮次模型站住了，两类问题在它的边界上第三次出现，本版把它们各收成一条原则：

- **存活：以源 Task 为中心的出口（-202、-252、-253、-254、-256）。** 轮次关闭时，按“候选此刻是否仍为 VERIFYING”与本轮的分类，对每个以本轮为当前轮次的源 Task 给出唯一的去向；候选已不是 VERIFYING（被兄弟轮次判 REJECTED、被取代、被否决、规格变化置 STALE）时，源 Task 回 READY 重新冻结、不计修复；这样的候选上的验证 Task 不再重试或纠正，改为 CANCELLED。pace 只把真正能推进的执行计为在途（决定 10、11）。
- **失败的含义：唯一的三分类（-201、-251）。** 轮次与 M2-T18 的汇合用同一个分类：有结论的失败→返工；无结论或 UNKNOWN→同一候选上重新验证；可通过→等候选的全部轮次关闭后汇合。UNKNOWN 永远不触发返工（决定 11，CR-018）。
- **候选级的栅栏（-200）。** 汇合只在候选的全部轮次都已关闭且都可通过时进行；ACCEPTED 的候选上不再开新轮次（决定 3）。
- **全范围验证（-203、-250）。** 轮次的范围只是源 Task 的 AC；对最终候选的全范围验证属于发布门禁（docs/06 的 Release Gate，REQ-056，M5-T02），经 CR-018 移交；在此之前多 Task Run 的 Run→COMPLETED 由门禁保持 fail-closed（不是放宽）。
- **交接的 epoch（-204）。** 派发验证 Task 的事务核对它的交接消息的 role_epoch，过期的按 REQ-022 行为 8 拒绝（DEAD_LETTER，原因 STALE_ROLE_EPOCH）并以当前 epoch 重发（决定 9）。
- 其余：投递循环永不领取验证交接（-255）；Runtime 在汇合 ACCEPTED 时接受源 Task（-257）；验证 Task 不写 task_requirements（-258）；done_when 与 REQ-036 失败模式 5 的追溯（-259）；重新验证用自己的修复种类（-260）。

## 第五版的更正（设计审查第 4 轮：Codex M2T16D-300..304 FAIL，Claude M2T16D-350..363 FAIL）

两类问题第四次出现，原因在机制而不在条文：第四版的出口在轮次关闭的那一刻按事件触发，关闭之后才发生的变化（兄弟轮次判 REJECTED、候选失效、验证 Task 先 BLOCKED 后候选失效）落空；分类按若干特例列举，汇合时遇到没列到的输入就无路可走。本版换掉这两个机制：

- **按状态的对账（-300、-301、-351、-352）。** 验证的推进只由一个幂等函数完成，每个 tick 与 host 启动时运行，只读此刻的状态、不依赖事件的先后：取消失效候选上一切未完成的验证 Task（含 BLOCKED 的），关闭已了结的轮次，再为每个 VERIFYING 的源 Task 按（当前轮次是否关闭、它的结论、候选此刻的状态、兄弟 Task 是否还在产出后继）给出唯一的去向（决定 11）。
- **全函数的分类（-303、-350、-354）。** 分类按范围内每个 AC 的验收历史（与 M2-T18 的投影同一规则）、本轮证据的检查级状态、Issue 与两方报告的状态，输出 failed、flaky、inconclusive、passable 四类之一，覆盖全部输入；M2-T18 的汇合就是“passable 即 ACCEPTED，否则按同一类别处置”（决定 11，CR-018）。报告状态在 M2-T16 已取得（决定 15），所以 UNKNOWN 现在就归 inconclusive，可测。
- 其余：规格变化后旧 Task 的迁移归 M3-T02 并写明（-302）；发布验证是独立的义务、不开轮次（-304）；没有 AC 的写任务的出口（-353）；Commander 的契约写明被验证候选的 Issue 由 Runtime 返工（-355）；测试计划的修正（-356、-357）；运行目录的路径入记录（-358）；最后一条 TaskResult 形态的行决定结果（-359）；M2-T18 移交的接口细节（-360）；会话独立被拒的出口（-361）；迭代只在有结论时计数、验证者合法的非 COMPLETED 结果计入重新验证（-362）；请求目录位置的余项（-363）。

## 第六版的更正（设计审查第 5 轮：Codex M2T16D-400..404 FAIL，Claude M2T16D-450..463 FAIL）

第五版的两个机制站住了，本轮的发现都在它们的输入与归属上：

- **分类的输入（-401、-402、-451、-452）。** 分类的输入写成 AC-054-05 的四个维度（QA、Review、确定性检查、AC 覆盖）加上 AC 的历史与 Issue；passable 是正向条件，其余一律 inconclusive（fail-closed）；没有观察（NOT_RUN、空观察的 INVALID(INSUFFICIENT)、UNKNOWN、BLOCKED、STALE 行或没有行）只算未定，不算失败；汇合只看每条重新验证链的当前轮次，被重验取代的旧报告只作历史。
- **Issue 与失败的归属（-403、-450、-453）。** 改写请求的 Issue 归属于开出它的轮次的源 Task，直到被该 Task 的一次返工消费为止，作为它之后每个轮次的分类输入，不随候选被取代而丢失；AC 级的失败项只归属范围含该 AC 的源 Task；报告 FAIL 也是一个可计数的失败项。
- **出口（-400、-454）。** 验证 Attempt 以 UNKNOWN_EFFECT 结束时重新验证（验证只追加证据，没有外部效果，重放安全）；出口表补上“开发 Task 因验证而 BLOCKED”一行，栅栏把它算进候选。
- **AC-037-04 的字面（-455）。** 验证轮次产出的证据的验收行在轮次关闭的事务里写入（否决照常即时生效），所以候选的验收行在它的 QA 与 Review 都完成之前为 0 行。
- 其余：输出的登记与 OBSERVED 解耦（-404）、截断的桥（-456 的余项）、决定 2 与实现一致（-457）、REQ-037 决定 1 在 Commander 一侧的显式延期（-458）、AC-042-04 的“QA FAIL”（-459）、会话独立的核对范围（-460）、CR 的措辞（-461、-463）、代码来源的基准（-462）。

## 决定

1. **范围与解释。**
   - AC-037-02 的“两份 evidence”指两个验证 Attempt 各自经检查请求桥（决定 7）运行计划检查而写入的证据行：QA 一行 FAIL、Review 一行 PASS，各自的 attempt_id 是自己的 Attempt。验证 Agent 的结论报告不进 evidence：产品的 Reviewer 没有运行计划里 independent-review 的命令，把报告记成该检查的执行记录会被原则一规则 4 否决（ADR-027）；报告进 `independent_reports` 归 M2-T18。
   - AC-037-04 与 REQ-037 失败模式 4 的“C2 的 acceptance_results 在其 QA/Review 完成前为 0 行”按字面满足（-156、-455）：**验证轮次的验证 Attempt 产出的证据，它的验收行不在证据的事务里写，而在轮次关闭的事务里**，按 ADR-027 决定 9 的同一结论函数由 `evidence.recorded` 的载荷投影写入（ADR-027 决定 9 加注记）；证据行、`evidence.recorded`、否决（候选置 INVALID）与 `integrity_violation` 照常即时入库。不属于任何轮次的生产者（M2-T10 的测试夹具）照旧在证据的事务里写验收行，所以 AC-052-0x 不变。测试断言：C2 的 QA 已写证据而 Review 仍在运行时 C2 的验收行为 0；关闭后的每一行的证据都属于 C2、生产者是 C2 的验证 Attempt；C2 在汇合之前不是 ACCEPTED。

2. **身份头与角色输出桥（扩展 ADR-025 决定 8，-10）。** Developer、QA、Reviewer 的 Prompt 在任务上下文开头有强制的身份头：当前 run_id、本 Task 的 task_id、attempt_id、role、role_epoch；验证角色另有被测候选的 6 项身份与**源开发任务**的 task_id（明确标为“被验证的任务”，不是本 Task）；桥文件路径与请求助手（决定 7）。它是强制项，不可裁剪（ADR-026 决定 4）。每个这样的 Attempt 在 `.hoh/attempts/<attempt_id>/messages.jsonl` 有桥文件；执行器在 Attempt 结束时按 `BRIDGE_LINES`、`BRIDGE_BYTES` 读取非空行，放进 `Observed.messages`，每条结束路径（成功、失败、取消、reconcile）都读取。行的种类：
   - `TaskResult`（protocol.schema.json；run/task/attempt/role/role_epoch 须等于身份头）：**最后一条 TaskResult 形态的行**（含 `status` 的对象）决定结果，它无效时结果即无效（走协议纠正），不退回更早的有效行（-359）；它的 evidence 中不合决定 14 规定的项只被丢弃（各记一条 `bridge.rejected`），不使整条结果无效（-157）；
   - 验证角色在 Attempt 结束前没有经请求桥送出的 `query`/`steer` Message，在结算之前按决定 13 处理。
   不合 schema 或身份不符的行记 `bridge.rejected{attempt_id, line_sha256, reason}`，不影响其他行。桥的行（原文，至多 `BRIDGE_LINES` 行、`BRIDGE_BYTES` 字节）由一个幂等的登记（事件 id `child_id(attempt, "outputs")`）记成 `attempt.outputs{attempt_id, success, truncated, lines}`：它与工作效果的确认分开，正常结束（OBSERVED）、UNKNOWN_EFFECT 的结束与 reconcile（读仍在 Attempt 目录里的桥文件）都走同一个登记，已登记即不再写（-404、-457）。读取超过上限时 `truncated` 为真，结果按无效处理（最后的 TaskResult 可能被截掉，-456）。测试用读取产品 Prompt、只凭其中的身份头写出结果的假 CLI 证明闭环。

3. **Developer 输出的处置表（-11、-55）。** 写者 Attempt 的进程组已证明结束（与 `Observed.workspace` 同一时点，-66）之后，按下表处置，全部在决定 4 的一个提交里：

   | 桥里的结果 | Attempt | Task | 计数与唤醒 |
   |---|---|---|---|
   | COMPLETED，冻结成功且接受 | SETTLED | RUNNING→VERIFYING | — |
   | 缺失、不合 schema、身份不符、candidate_id 非空且不等于冻结结果、冻结被拒、同 Run 同内容的候选为 STALE/INVALID/REJECTED/ACCEPTED（ACCEPTED 的候选上不开新轮次，-200） | SETTLED | RUNNING→READY（纠正的再派发是决策类） | `Repair::Protocol`；超限则 Task BLOCKED（NEED_DECISION）并写 need_decision |
   | COMPLETED，冻结得到同 Run 同内容、状态为 VERIFYING 的候选 | SETTLED | RUNNING→VERIFYING | 在该候选上为本 Task 开一个新的轮次（决定 9；与该候选已有的轮次无关，不论它们是否已关闭） |
   | FAILED 或 BLOCKED | SETTLED | RUNNING→BLOCKED（NEED_DECISION） | need_decision，带 Agent 的 summary 与 issues |
   | INCOMPLETE | SETTLED | RUNNING→BLOCKED（NEED_DECISION） | need_decision（续跑由 Commander 决定） |
   | COMPLETED，但该 Task 在 Run 的 spec 下没有 AC（轮次范围为空，REQ-053 行为 8） | SETTLED（写租约释放） | RUNNING→BLOCKED（NEED_DECISION） | need_decision，原因“任务没有可验证的 AC”；不冻结、不开轮次（-353） |

   Attempt 自身失败（进程失败、超时、鉴权）照旧走 ADR-020 的重试，不读桥里的结果。

4. **Developer 完成的单一提交与恢复（ADR-027 决定 4、5 的移交，REQ-052 行为 1、2，-03）。**
   - 冻结分成文件侧与库侧：`verify::freeze::prepare` 在写租约仍持有时做守卫、算清单、写对象（幂等：同一工作区重复调用得到同一清单与对象）；库侧的候选行插入、更早候选置 STALE、`candidate.frozen` 进入完成提交。
   - **完成提交**（一个 IMMEDIATE 事务，新增 `Store::complete_writer_attempt`）：按决定 3 的那一行写候选行（更早候选置 STALE）、接受（ADR-018 决定 5 的事件与两条交接消息）、新轮次与它的两个验证 Task 和 `handoffs` 行（决定 9），被取代候选上未完成的源 Task 转入新轮次（决定 9），Task 迁移、修复裁决（决定 12 的事务内函数）、need_decision，以及 Attempt 的结算（SETTLED、写租约随 REQ-019 行为 6 的工作区记录释放）。提交之前崩溃，什么都没写，写租约仍在。
   - **恢复**：成功结束、尚未完成提交的写者 Attempt（工作效果为 OBSERVED 成功、Attempt 仍 RUNNING），由 host 的 reconcile 先证明进程已结束，再读它的桥文件（仍在 Attempt 目录里）、重新 `prepare`、走同一个完成提交；不再走通用的成功结算（那会置 IMPLEMENTED 并释放租约）。完成提交按 Attempt 幂等：Attempt 已 SETTLED 即为无操作。
   - spec 取 `contracts/requirements.json`，test plan 取 `tests/check-plan.json`（项目布局约定，规格事实源的位置归 M3-T02，见 CR-018）；environment 为 `.hoh/environment.json`（决定 5）。
   - 写者 Attempt 在 RUNNING 的提交里记 `attempt.workspace_start{head}`（决定 14 的基准）。

5. **环境描述（ADR-027 决定 4 的移交）。** `.hoh/environment.json` 由 host 生成：`{schema_version, hoh_version, os{sysname, machine}, tools{git}}`，只含与环境有关、不含时间与随机值的字段，键排序、紧凑、以换行结尾；内容与已有文件相同即不重写，所以 host 重启不改变它的摘要。字段集合写进 docs/22。

6. **运行目录（REQ-037 行为 3、5，-02、-61）。** 每个验证 Attempt 的检出在项目树之外：`$XDG_STATE_HOME/hoh/runs/<project_id>/<attempt_id>/`（未设时 `~/.local/state/hoh/…`，与 Commander 的工作目录同根，ADR-025 决定 3），所以 Agent 向上找不到写者工作区；状态根仍是项目的 `.hoh/`。准备步骤（执行器在 spawn 之前、启动门打开之前）：
   - `git clone --shared --no-checkout --quiet <项目根> <目录>`，`git -C <目录> checkout --quiet --detach <候选 commit>`；`--shared` 不复制对象，不写项目仓库的索引、引用或对象；
   - 在检出里建 `.hoh/`（`.gitignore` 为 `*`），把候选冻结的环境对象的字节写到清单里 environment 的路径（它是 `.hoh/` 下的被忽略文件时；跟踪文件已在检出里）；
   - 对检出做完整的候选前核对（ADR-027 决定 6 的清单身份、HEAD、tree、干净、spec/environment/test plan 摘要），不符即拒绝启动（Attempt 以非瞬时失败结束，记原因）；
   - 取工作区哈希（ADR-021 g）作 `pre_tree`，与运行目录的路径一起记进 RUNNING 的提交（`verification.attempt_started{attempt_id, run_dir, pre_tree}`，-358）。
   验证 Attempt 不续接原生会话（每次是新的原生会话，HoH 的 session 行仍是该角色绑定的）：运行目录每次不同，Claude 的 `--resume` 按目录找会话，续接会失败；验证也不应带着上一个候选的记忆。运行目录在该 Attempt 结算之后删除；host 启动时删除没有活 Attempt 的运行目录。余项：被测仓库自带的 AGENTS.md/CLAUDE.md 会被 Agent 读到，与写者工作区相同，角色契约优先（写进 docs/22）。

7. **请求桥：检查与消息（REQ-053 行为 3、5，ADR-027 原则二，CONTRACT 第 3 条，-04、-05、-58）。** 验证 Agent 运行检查计划条目的“run_check 类绑定工具”与它给其他角色的请求，经同一个运行中的文件提交桥，不是 `hoh` 的子命令：
   - 执行器在 Attempt 目录写两个 POSIX sh 小脚本，路径经环境变量 `HOH_RUN_CHECK`、`HOH_ASK` 与身份头给出。`run-check <check_id>` 原子地写 `requests/<n>.json{kind: "check", check_id}`；`ask <message.json>` 写 `{kind: "message", message}`；两者都等待 `requests/<n>.response.json`（检查的上限为计划超时加宽限，消息为 60 s），打印结论；`run-check` 以检查的退出码结束，被拒为 2。
   - host 对每个运行中的验证 Attempt 轮询 `requests/`，按序号逐个处理，同一 Attempt 串行，至多 `MAX_REQUESTS`（初值 64）个。
   - `check`：只接受冻结计划里的 check_id；以该 Attempt 为生产者、运行目录为检出、`.hoh/` 为状态根调用 `verify::check::run`。检查命令经与 Attempt 主进程相同的启动门启动：委派 cgroup 下先进入该 Attempt 的 cgroup，`/proc` 退化模式下带该 Attempt 的标记环境（ADR-021 决定 8d），所以 Attempt 的取消、结束与 reconcile 的“进程已结束”证明覆盖它们（host 被 SIGKILL 后，reconcile 先终止并证明它们结束，再由 `check::reconcile` 补记已写出待入库事实的记录）。驱动拒绝（前核对不符）时写 `verification.check_refused{attempt_id, check_id, reasons}`（ADR-027 决定 6 的“供 M2-T16 记录”）并回应 Agent；不写证据（Attempt 级的核对另行判定，决定 8）。回应带 outcome、原因、记录路径、exit_code。
   - `message`：按决定 13 即时处理，回应 rejected 或 deferred。
   - Attempt 的进程结束后，执行器先等它进行中的检查收尾（记录与证据已提交），再做决定 8 的核对与结算；之后不再处理它的请求。
   - 证据的 outcome 来自检查，不来自 Agent 的自述。

8. **Attempt 级的运行后核对（REQ-037 行为 5，AC-037-03，ADR-027 移交）。** 验证 Attempt 的每条结束路径（成功、失败、取消、reconcile）在结算之前取运行目录的工作区哈希 `post_tree`，并核对 HEAD 与 tree 仍是候选，写 `verification.tree_checked{attempt_id, candidate_id, pre_tree, post_tree, equal, status}`（`status` 为运行目录 `git status --porcelain` 的前 4 KiB，供观察）。不相等或读不了时，经 `Store::record_evidence` 写一条 INVALID 证据，执行记录的形态：check_id 为该角色的 `independent-qa` 或 `independent-review`，command 为 `["hoh-runtime:verification-attempt", <attempt_id>]`（不可执行的标记，不对应任何执行，也不是 `hoh` 的子命令，-162），exit_code 为约定值 1（不声称成功）、`source_unchanged=false`，stdout/stderr 为空文件，artifacts 为空，前后 tree 进 `evidence.recorded`；记录写在 `.hoh/evidence/<候选>/<check>/<record>/`，走 ADR-027 决定 8 的恢复协议。原则一对它给出 COMMAND_MISMATCH 与 SOURCE_CHANGED 的否决，候选在同一事务置 INVALID（M2-T16 从不直接改候选状态），traceability 的文件扫描同样否决；同一事务写 `integrity_violation`（ADR-027 决定 7，监督器同一 tick 唤醒 Commander）。

9. **验证轮次（ADR-018 决定 5、6，ADR-026 决定 6，REQ-022 行为 8，REQ-053 行为 1、6，REQ-054 行为 2，-08、-57、-63、-101、-102、-105、-151、-204、-250、-255、-258）。**
   - 一个**轮次**是 (候选 C, 源开发 Task 的集合, 序号 g)，由 `verification.round_opened{round_id, candidate_id, number, source_task_ids, acceptance_ids, tasks{qa, reviewer}, handoffs}` 事件记录（round_id = `child_id(C, "round/<g>")`）。它只在完成提交（决定 4）或重新验证（决定 11）的事务里建立，同一事务写：
     - 两条交接消息（ADR-018 决定 5、6；message id 为 `child_id(round_id, "verify/<角色>")`）；
     - 两个验证 Task（`task_id = child_id(round_id, "task/<角色>")`，与消息 id 分开，-63），role 为 qa 或 reviewer，writer=0，spec_id 为 Run 的 spec，layer 0，状态 READY；不写 `task_requirements`（范围来自交接包的 acceptance_ids，验证 Task 的终态不计入任何需求，-258）；它们是 Runtime 的（决定 10）。
   - **本轮的范围**：源 Task 的 acceptance_ids 的并集，不自动扩展（-250）。对最终候选的全范围验证属于发布门禁（docs/06 的 Release Gate、docs/07 §6，REQ-056，M5-T02，CR-018）；在此之前，多 Task Run 的当前候选不会覆盖全部 required_release 需求，Run→COMPLETED 的门禁照样拒绝（fail-closed）。
   - **不经投递循环**：投递循环的领取排除 `payload.handoff_kind = "verification"` 的交接（outbox 的领取函数加这一条，测试：注册了 qa/reviewer 消费者时领取跳过它们，-255）。派发验证 Task 的调度轮事务核对它的当前交接消息：role_epoch 不等于该角色此刻的绑定时，按 REQ-022 行为 8 拒绝旧消息（DEAD_LETTER，`outbox.dead_letter{reason: "STALE_ROLE_EPOCH"}`，不改变其他状态），并在同一事务以当前 epoch 重发一条（id `child_id(旧 id, "e<epoch>")`，交接包除 role_epoch 外相同），派发用新消息（-204）。验证 Attempt 以它启动（Prompt 已发出）的 RUNNING 提交里该消息置 ACKED，并写一行 `handoffs(handoff_id = 消息 id, from_role = "runtime", to_role, role_epoch, package_artifact_id = 执行器写下的交接包对象, state = DELIVERED)`；轮次关闭时结果为 COMPLETED 的一方 → ACCEPTED；轮次以 superseded 关闭时未启动一方的消息置 DEAD_LETTER（`reason: "superseded"`），已建的 `handoffs` 行 → REJECTED。
   - **源 Task 的当前轮次**：每个 VERIFYING 的源 Task 恰有一个当前轮次（含它的、最新的 round_opened）。Runtime 对源 Task 的每次迁移都核对“该轮次是它的当前轮次”，不是就不迁移它（-102）。
   - **取代**：完成提交冻结的新候选 C2 时，同一事务把当前轮次所在候选不是 ACCEPTED（即被本事务置 STALE 的，或已是 REJECTED、INVALID 的）、仍为 VERIFYING 的源 Task 并入 C2 的新轮次（与本次完成的 Task 一起，一对交接，AC-053-04 的“各 1 条”）。源 Task 不重跑 Developer（-151）。它们原来的轮次照常关闭，但不再迁移它们（当前轮次已变）。
   - 同 Run 同内容、状态为 VERIFYING 的候选（决定 3）在它上面开新一轮，只含本次完成的 Task（-101）；它与兄弟轮次的关系由候选级的栅栏决定（决定 11）。
   - Commander 交接包（ADR-024）也写 `handoffs`：交接事务写 PREPARED，首个输入送达时 DELIVERED、首个输入付清（该会话首个回合完成）时 ACCEPTED、被取代的通知（ADR-024 决定 4）时 REJECTED（from_role 为旧持有者的角色，-259）。

10. **验证 Task 是 Runtime 的（ADR-025 决定 3 的移交，REQ-036 失败模式 5，AC-035-05、AC-021-05，-57、-153、-202、-253、-259）。**
    - 派发是 Runtime 规则类：调度轮对 BLOCKED 的 Run 除已排的重试外也派发验证 Task；派发通知带 `origin: "verification"`，runner 对 BLOCKED 与 WAITING_EXTERNAL 的 Run 放行；暂停与取消照常停止它。所以 Commander 不可用（Run BLOCKED，COMMANDER_UNAVAILABLE）时，candidate_ready 照样产生两条交接、两个验证 Task 与它们的派发。
    - 派发的事务另核对会话独立：验证 Attempt 将用的会话等于任一源开发 Attempt、Run 的 Commander 或同一轮另一验证方的会话时拒绝（SESSION_NOT_INDEPENDENT，REQ-036 失败模式 5、行为 7，REQ-054 行为 1，-460），同一事务把该验证 Task 置 BLOCKED（NEED_DECISION）并写 `integrity_violation`（-361）；按构造不会发生（会话按职位分开，验证 Attempt 每次新起原生会话），所以测试以伪造的同会话绑定证明拒绝与出口。
    - Commander 对验证 Task 的迁移提议与派发一律 ILLEGAL_TRANSITION（decision.rs 的 TaskView 加 `runtime_owned`，由 round_opened 事件判定）；它们不进依赖图。
    - **候选已不是 VERIFYING 或 Run 正在取消时**：由决定 11 的对账把该轮次一切未了结的验证 Task 置 CANCELLED（`task.cancelled{reason: "superseded"}`）：READY、BLOCKED（同时清除它的 blocked_reason 与重试时间，所以它不再给 Run 阻塞原因，-301、-352）、以及运行中 Attempt 结束后本应回 READY 的；LEASED/RUNNING 的等它的 Attempt 结束。准备步骤（决定 6）拒绝非 VERIFYING 的候选（-253）。
    - 终态：轮次关闭时，IMPLEMENTED 的验证 Task IMPLEMENTED→VERIFYING→ACCEPTED（“验证工作已完成”；它没有 task_requirements，不计入任何需求）；其余为 CANCELLED。
    - **在途（pace）**：在途只算真正能推进的执行——LEASED/RUNNING 的 Task、可派发的 READY Task、到期或等待中的重试。VERIFYING 的源 Task 与 IMPLEMENTED 的验证 Task 自身都不算在途；BLOCKED 的验证 Task 照常给出 Run 级的阻塞原因。所以一方验证 BLOCKED_AUTH、另一方已完成时，Run 停滞并进入 BLOCKED（BLOCKED_AUTH）（-202）。唯一的例外是 M2-T16 内的过渡：候选的全部轮次都可通过、在等 M2-T18 的汇合时，它的源 Task 计为在途（“等汇合”）；M2-T18 的汇合在关闭清扫的同一事务里完成，这个例外随之消失。

11. **验证的对账：关闭、分类与源 Task 的去向（REQ-037 行为 4，REQ-053 行为 4、8，REQ-054 行为 7、失败模式 4，REQ-053 决定 1，ADR-027 原则一，-06、-07、-100、-103、-150、-152、-154、-200、-201、-251、-252、-254、-256、-300、-301、-303、-350、-351、-352、-354、-362）。**
    - **验证 Task 的输出**（决定 15）：结果为 COMPLETED 的 Attempt 照常结算，Task 到 IMPLEMENTED；结果缺失或无效按 `Repair::Protocol` 在同一轮内重来；合法的 FAILED、BLOCKED、INCOMPLETE，以及 Attempt 以 UNKNOWN_EFFECT 结束（验证只追加证据、没有外部效果，重放安全；不同于写者的 UNKNOWN_EFFECT，-400），按 `Repair::Reverify`（与重新验证同一条链，-362）在同一轮内重来（Task 回 READY，新的原生会话，Prompt 带原因）；超限时 Task BLOCKED（NEED_DECISION）；Attempt 自身失败照旧走 ADR-020 的重试；候选已不是 VERIFYING 时由下面的对账改为 CANCELLED。一个验证 Task 只在 IMPLEMENTED（结果 COMPLETED）或 CANCELLED 时**了结**。
    - **对账** `Store::reconcile_verification(run)`：每个 tick（调度轮之前）与 host 启动时运行，一个事务，只读此刻的状态，幂等；依次：
      1. 候选不是 VERIFYING（或 Run 正在取消）的轮次：未了结的验证 Task 按决定 10 置 CANCELLED。
      2. 两个验证 Task 都已了结、还没有 `verification.round_closed` 的轮次：关闭（事件 id `child_id(round_id, "closed")`，seq 必然大于两个 Attempt 的终态事件），写下分类与结论；结论为 repair、reverify、flaky 时按下表迁移**以本轮为当前轮次**的源 Task。
      3. 每个 VERIFYING 的源 Task，按它的当前轮次与候选此刻的状态取唯一的去向（下表），不论这些状态以什么次序到达。
      4. 候选级栅栏：候选为 VERIFYING，当前轮次在它上面的每个开发 Task（VERIFYING 或因验证而 BLOCKED）的当前轮次都已关闭且为 passable 时，写 `verification.candidate_ready_for_join{candidate_id, rounds}`（事件 id 随轮数，幂等）；M2-T18 的汇合在同一事务里完成（CR-018）。
    - **分类**（唯一的分类函数 `verification::classify`，纯函数，全函数；M2-T18 的汇合复用它，-401、-402、-451、-452）。输入是 AC-054-05 的四个维度加两项：
      - **QA**、**Review**：该方在**当前轮次**的报告状态（PASS、FAIL、UNKNOWN；没有有效报告为 NOT_RUN）。重新验证链上被取代的轮次的报告只作历史，不进输入。
      - **确定性检查**：本轮验证 Attempt 产出的证据的检查级状态（ADR-027 原则一）：全部有效且 PASS；有一项 FAIL（原因不在无结论集合 {TIMED_OUT, NOT_STARTED, INTERRUPTED, INCOMPLETE, PLUGINS_MISSING} 内）；空列表或只有无结论。
      - **AC 覆盖**：范围内每个 AC 在本候选上的投影，覆盖 `acceptance_results.status` 的全集：只有 PASS 与合规 DEGRADED 为满足；有 FAIL（与 PASS 并存亦然）为失败；有 FLAKY 行，或 UNKNOWN/BLOCKED 之后有 PASS，为 FLAKY；其余（没有行、只有 NOT_RUN、UNKNOWN、BLOCKED、STALE，或空观察的 INVALID(INSUFFICIENT)）为未定。被否决证据的 INVALID 行只随候选 INVALID 出现，由出口表的 superseded 行处理，不进分类。
      - **Issue**：归属于本轮源 Task、尚未被返工消费的改写请求 Issue（决定 13），与候选上 severity 为 critical/high 的 OPEN Issue（low/medium 不算，REQ-054 决定 3）。
      输出按优先级取第一类：`failed`（任一方 FAIL；确定性检查有 FAIL；任一 AC 失败；有上述 Issue）；`flaky`（任一 AC 为 FLAKY 且不属于 failed）；`passable`（两方 PASS、确定性检查全部有效 PASS、每个 AC 满足——正向条件）；其余一律 `inconclusive`（任一方 UNKNOWN 或 NOT_RUN、检查为空或只有无结论、任一 AC 未定）。所以 AC-054-05 的 96 种组合只有 (PASS, PASS, 全部 PASS, 全覆盖) 为 passable，测试计划写明四个维度到输入的映射。
    - **验收行的写入**（-455）：关闭的事务先把本轮证据的验收行按 ADR-027 决定 9 投影写入，再求分类，所以分类读到的历史含本轮。
    - **结论与去向**（只迁移以该轮为当前轮次的源 Task；表在对账的第 2、3 步各按此刻的状态求值）：

      | 当前轮次 | 候选此刻 | 去向 |
      |---|---|---|
      | 未关闭 | 任意 | 等待（轮次的验证 Task 决定是否在途或阻塞） |
      | 已关闭，`failed`（结论 repair） | VERIFYING | 候选 VERIFYING→REJECTED（`AND state = 'VERIFYING'`）；有失败项归属于它的源 Task 按决定 12 返工（READY，layer 0）或 BLOCKED；没有归属项的源 Task 按下面“候选 REJECTED”一行等待兄弟的后继（-453） |
      | 已关闭，`inconclusive`（结论 reverify） | VERIFYING | 同一候选上开下一轮（同样的源 Task 与范围），`Repair::Reverify` 计数，超限 BLOCKED（NEED_DECISION） |
      | 已关闭，`flaky` | VERIFYING | 源 Task BLOCKED（NEED_DECISION）与 need_decision：REQ-055 的 flaky 处置或新的候选由决策给出 |
      | 已关闭，`passable` | VERIFYING | 等候选级栅栏与汇合（M2-T16 内停在这里） |
      | 已关闭，任意 | ACCEPTED | M2-T18 的汇合在同一事务已接受它（CR-018） |
      | 已关闭，任意 | REJECTED、INVALID、STALE（兄弟轮次的失败、否决、取代或规格变化） | 若兄弟源 Task（当前或最近一轮在这个候选上的其他开发 Task）还在产出后继（READY、LEASED、RUNNING 或 BLOCKED），等待它的下一次冻结把本 Task 并入新轮次（决定 9 的取代）；否则回 READY 重新冻结（`task.superseded{round_id, candidate_state}`，不计修复；Prompt 写明“候选因其他原因不再有效，内容未变时需新的提交，可为空提交”，候选为 INVALID 时另写“因验证完整性被否决”，-256）；Run 已取消时不动 |
      | 未关闭或已关闭 | Run 正在取消 | 不动（随 Run 结束） |
      | 开发 Task 因验证而 BLOCKED（flaky、超过 REVERIFY_LIMIT 或 max_local_repairs） | 任意 | 等待决策（M2-T13 的答复路径，CR-018）；解除后回 READY：候选仍 VERIFYING 且该轮为 flaky 时 Prompt 要求新的提交（同内容再冻结不能使 FLAKY 满足，REQ-053 决定 1，决定 3 的同内容 VERIFYING 候选上若有 flaky 轮次即走纠正）；候选已不是 VERIFYING 时同“候选 REJECTED…”一行；它的当前轮次仍算在候选上，所以候选级栅栏不会越过它（-454） |

    - **迭代**（-362）：只在有结论的候选级结果上计一次——结论 repair 的关闭，或候选级的汇合点——写 `iteration.completed{iteration, candidate_id, verdict}` 与一行 `iterations(run_id, number = 已有数 + 1)`，按 ADR-020 的用量规则累加 `iterations` 用量；superseded、reverify 与 flaky 不计。它是 balanced 监督的轮次边界唤醒的产生方（ADR-025 决定 2）。
    - 关闭的事务把了结的验证 Task 置终态（决定 10）。QA 与 Review 互不等待：一方失败不取消另一方。

## 不变量与每个状态的出口（第五版）

- **I1** 每个 VERIFYING 的开发 Task 恰有一个当前轮次；只有建立轮次的事务（完成提交、取代、重新验证）改变它。
- **I2** 每个轮次恰好关闭一次（固定事件 id）；源 Task 的去向是（当前轮次、候选此刻的状态、兄弟 Task 此刻的状态）的函数，每个 tick 由对账求值，所以与事件到达的先后无关。
- **I3** 每个验证 Task 属于一个轮次，终态为 ACCEPTED（了结并关闭）或 CANCELLED（候选不再 VERIFYING 或 Run 取消）；失效候选上的验证 Task 不再给 Run 阻塞原因。
- **I4** 候选的 ACCEPTED 只由候选级栅栏之后的汇合写（M2-T18）；门禁只认它；ACCEPTED 的候选上不开验证轮次（发布门禁的全范围验证是另一种义务，M5-T02，见移交）。
- **I5** 分类只有一个全函数（`verification::classify`），对账与汇合共用；UNKNOWN、BLOCKED 与无结论永远不触发返工；汇合 ACCEPTED 当且仅当分类为 passable。

出口：

| 状态 | 出口 |
|---|---|
| 开发 Task RUNNING，Attempt 成功结束 | 完成提交（决定 3、4），或崩溃后由 reconcile 走同一提交 |
| 开发 Task VERIFYING | 对账按决定 11 的表；每一行都有去向 |
| 开发 Task 因验证而 BLOCKED | 决策解除（M2-T13）后按决定 11 表的该行回 READY；期间候选级栅栏不越过它 |
| 验证 Attempt 以 UNKNOWN_EFFECT 结束 | 同一轮内重新验证（`Repair::Reverify`），超限 BLOCKED |
| 验证 Task READY/LEASED/RUNNING | 派发（Runtime 规则类）与结算；候选不再 VERIFYING 时 CANCELLED |
| 验证 Task，结果非 COMPLETED | 同一轮内纠正或重新验证，超限 BLOCKED；候选不再 VERIFYING 时 CANCELLED |
| 验证 Task BLOCKED，候选 VERIFYING | 阻塞解除（鉴权或能力由 pace 与绑定恢复，M2-T15；NEED_DECISION 由 M2-T13 的答复路径；CR-018）后再派发；期间 Run 按它的原因进入 BLOCKED |
| 验证 Task BLOCKED，候选不再 VERIFYING | 对账置 CANCELLED，阻塞原因随之消失 |
| 验证 Task IMPLEMENTED | 轮次关闭时 ACCEPTED |
| 候选 VERIFYING | 轮次的 repair→REJECTED；被取代→STALE；否决→INVALID；汇合→ACCEPTED/REJECTED |
| 候选因规格变化 STALE（M3-T02） | 轮次以 superseded 关闭，验证 Task 取消；旧规格下的开发 Task 的迁移或替代（含需求映射）由 M3-T02 规定（-302，CR-018） |
