# ADR-028 · 候选验证的派发、并行 barrier 与运行目录

状态：第二版（设计审查第 1 轮之后；M2-T16）

## 背景

M2-T16 的验收是 AC-021-05、AC-035-03、AC-035-05、AC-036-03、AC-037-02、AC-037-03、AC-037-04、AC-053-03、AC-054-03、AC-039-03（都属 `integration`）。done_when 另要求：Commander 不可用时 candidate_ready 仍派发 QA/Review；FAILED/UNKNOWN 永不投影为 PASS；AC-039-03 经产品的 QA 派发、同一收集函数与装箱器生成并由 FakeAgent 捕获（CR-016）；为 QA、Reviewer 与返工的 Developer 加代码类上下文来源（ADR-026 决定 12）；写 `handoffs` 表（ADR-026 决定 6）。

起点（预研 `.hoh-dev/evidence/m2t16-prep/inventory.md`、`notes.md`，按 main 8b88397 复核）：

- `Store::accept_task_result`（persistence/results.rs）已能在一个事务里把 Developer 的 COMPLETED TaskResult 变成 Task RUNNING→IMPLEMENTED→VERIFYING、候选 FROZEN→VERIFYING、`candidate_ready` 事件与 qa、reviewer 两条 kind=handoff 的 outbox 行（ADR-018 决定 5、6）。产品里没有调用者：Developer 的 Attempt 成功只把 Task 置 IMPLEMENTED。
- 产品里没有 Developer、QA、Reviewer 的结构化输出通道，只有 Commander 的文件桥（ADR-025 决定 8，Attempt 结束后读取）。
- `verify::freeze` 与 `verify::check`（ADR-027）只是库，host 不调用；host 启动不对账候选（独立 Review 对 m2t10-008 的 V01-IR-001）。
- outbox 的投递（ADR-018 决定 4）没有接入 host，没有 qa/reviewer 消费者。
- 没有 barrier、运行目录、Attempt 级 tree 核对、Issue 写者、`handoffs` 写者、代码类上下文条目、`iteration.completed` 产生方与 wait-for 视图。
- Commander 的验收门禁（decision.rs 的 `Evidence::gate`，persistence/decide.rs 的 `load_evidence`）接受状态为 VERIFYING 或 ACCEPTED、验收行全为 PASS 的候选，不看 barrier 与验证结论。
- `specs` 没有文件路径，产品里也还没有规格导入（M3-T02）；冻结要求 spec 与 test plan 是候选的跟踪文件（ADR-027 决定 4）。
- CONTRACT 第 3 条：`hoh` 的子命令只保留 attach、web、doctor。docs/06：没有独立工具接口时用规范化结构化输出或文件提交桥，不假设所有 Agent 有相同的自定义工具。

- 修复计数（-09、-53）：裁决函数接受调用方的事务、按动作身份幂等，指纹限定到 Developer Task 与失败的 (AC, 测试)（决定 11）。
- 运行中的请求（-05、-58、-64）：验证 Agent 的请求经运行中轮询的请求桥，即时拒绝并开 Issue（决定 7、13）。

- 移交（-54）：CR-018 改 M2-T18、M3-T02、M3-T04 的 done_when；逐条列出承接与改派（移交节）。

## 决定

1. **范围与解释。** AC-037-02 的“两份 evidence”指两个验证 Attempt 各自经检查请求桥（决定 7）运行计划检查而写入的证据行：QA 一行 FAIL、Review 一行 PASS，各自的 attempt_id 是自己的 Attempt。验证 Agent 的结论报告不进 evidence：产品的 Reviewer 没有运行计划里 independent-review 的命令，把报告记成该检查的执行记录会被原则一规则 4 否决（ADR-027）；报告进 `independent_reports` 归 M2-T18。

2. **身份头与角色输出桥（扩展 ADR-025 决定 8，-10）。** Developer、QA、Reviewer 的 Prompt 在任务上下文开头有强制的身份头：当前 run_id、本 Task 的 task_id、attempt_id、role、role_epoch；验证角色另有被测候选的 6 项身份与**源开发任务**的 task_id（明确标为“被验证的任务”，不是本 Task）；桥文件路径与请求助手（决定 7）。它是强制项，不可裁剪（ADR-026 决定 4）。每个这样的 Attempt 在 `.hoh/attempts/<attempt_id>/messages.jsonl` 有桥文件；执行器在 Attempt 结束时按 `BRIDGE_LINES`、`BRIDGE_BYTES` 读取非空行，放进 `Observed.messages`，每条结束路径（成功、失败、取消、reconcile）都读取。行的种类：
   - `TaskResult`（protocol.schema.json；run/task/attempt/role/role_epoch 须等于身份头），同一 Attempt 多条时取最后一条；
   - 验证角色在 Attempt 结束前没有经请求桥送出的 `query`/`steer` Message，按决定 13 处理。
   不合 schema 或身份不符的行记 `bridge.rejected{attempt_id, line_sha256, reason}`，不影响其他行；结算事务把全部行（文本的 sha256 与对象引用）记进 `attempt.outputs`。测试用读取产品 Prompt、只凭其中的身份头写出结果的假 CLI 证明闭环。

3. **Developer 输出的处置表（-11、-55）。** 写者 Attempt 的进程组已证明结束（与 `Observed.workspace` 同一时点，-66）之后，按下表处置，全部在决定 4 的一个提交里：

   | 桥里的结果 | Attempt | Task | 计数与唤醒 |
   |---|---|---|---|
   | COMPLETED，冻结成功且接受 | SETTLED | RUNNING→VERIFYING | — |
   | 缺失、不合 schema、身份不符、candidate_id 非空且不等于冻结结果、冻结被拒、同 Run 同内容的候选为 STALE/INVALID/REJECTED/ACCEPTED | SETTLED | RUNNING→READY（纠正的再派发是决策类） | `Repair::Protocol`；超限则 Task BLOCKED（NEED_DECISION）并写 need_decision |
   | COMPLETED，冻结得到同 Run 同内容、状态为 FROZEN 或 VERIFYING 的候选 | SETTLED | RUNNING→VERIFYING | 接到该候选上：为本 Task 另开一对验证义务（决定 9） |
   | FAILED 或 BLOCKED | SETTLED | RUNNING→BLOCKED（NEED_DECISION） | need_decision，带 Agent 的 summary 与 issues |
   | INCOMPLETE | SETTLED | RUNNING→BLOCKED（NEED_DECISION） | need_decision（续跑由 Commander 决定） |

   Attempt 自身失败（进程失败、超时、鉴权）照旧走 ADR-020 的重试，不读桥里的结果。

4. **Developer 完成的单一提交与恢复（ADR-027 决定 4、5 的移交，REQ-052 行为 1、2，-03）。**
   - 冻结分成文件侧与库侧：`verify::freeze::prepare` 在写租约仍持有时做守卫、算清单、写对象（幂等：同一工作区重复调用得到同一清单与对象）；库侧的候选行插入、更早候选置 STALE、`candidate.frozen` 进入完成提交。
   - **完成提交**（一个 IMMEDIATE 事务，新增 `Store::complete_writer_attempt`）：按决定 3 的那一行写候选行、接受（ADR-018 决定 5 的全部写入与决定 8 的 `handoffs` 行）、Task 迁移、修复裁决（决定 11 的事务内函数）、need_decision，以及 Attempt 的结算（SETTLED、写租约随 REQ-019 行为 6 的工作区记录释放）。提交之前崩溃，什么都没写，写租约仍在。
   - **恢复**：成功结束、尚未完成提交的写者 Attempt（工作效果为 OBSERVED 成功、Attempt 仍 RUNNING），由 host 的 reconcile 先证明进程已结束，再读它的桥文件（仍在 Attempt 目录里）、重新 `prepare`、走同一个完成提交；不再走通用的成功结算（那会置 IMPLEMENTED 并释放租约）。完成提交按 Attempt 幂等：Attempt 已 SETTLED 即为无操作。
   - spec 取 `contracts/requirements.json`，test plan 取 `tests/check-plan.json`（项目布局约定，规格事实源的位置归 M3-T02，见 CR-018）；environment 为 `.hoh/environment.json`（决定 5）。
   - 写者 Attempt 在 RUNNING 的提交里记 `attempt.workspace_start{head}`（决定 14 的基准）。

5. **环境描述（ADR-027 决定 4 的移交）。** `.hoh/environment.json` 由 host 生成：`{schema_version, hoh_version, os{sysname, machine}, tools{git}}`，只含与环境有关、不含时间与随机值的字段，键排序、紧凑、以换行结尾；内容与已有文件相同即不重写，所以 host 重启不改变它的摘要。字段集合写进 docs/22。

6. **运行目录（REQ-037 行为 3、5，-02、-61）。** 每个验证 Attempt 的检出在项目树之外：`$XDG_STATE_HOME/hoh/runs/<project_id>/<attempt_id>/`（未设时 `~/.local/state/hoh/…`，与 Commander 的工作目录同根，ADR-025 决定 3），所以 Agent 向上找不到写者工作区；状态根仍是项目的 `.hoh/`。准备步骤（执行器在 spawn 之前、启动门打开之前）：
   - `git clone --shared --no-checkout --quiet <项目根> <目录>`，`git -C <目录> checkout --quiet --detach <候选 commit>`；`--shared` 不复制对象，不写项目仓库的索引、引用或对象；
   - 在检出里建 `.hoh/`（`.gitignore` 为 `*`），把候选冻结的环境对象的字节写到清单里 environment 的路径（它是 `.hoh/` 下的被忽略文件时；跟踪文件已在检出里）；
   - 对检出做完整的候选前核对（ADR-027 决定 6 的清单身份、HEAD、tree、干净、spec/environment/test plan 摘要），不符即拒绝启动（Attempt 以非瞬时失败结束，记原因）；
   - 取工作区哈希（ADR-021 g）作 `pre_tree`，记进 RUNNING 的提交。
   验证 Attempt 不续接原生会话（每次是新的原生会话，HoH 的 session 行仍是该角色绑定的）：运行目录每次不同，Claude 的 `--resume` 按目录找会话，续接会失败；验证也不应带着上一个候选的记忆。运行目录在该 Attempt 结算之后删除；host 启动时删除没有活 Attempt 的运行目录。余项：被测仓库自带的 AGENTS.md/CLAUDE.md 会被 Agent 读到，与写者工作区相同，角色契约优先（写进 docs/22）。

7. **请求桥：检查与消息（REQ-053 行为 3、5，ADR-027 原则二，CONTRACT 第 3 条，-04、-05、-58）。** 验证 Agent 运行检查计划条目的“run_check 类绑定工具”与它给其他角色的请求，经同一个运行中的文件提交桥，不是 `hoh` 的子命令：
   - 执行器在 Attempt 目录写两个 POSIX sh 小脚本，路径经环境变量 `HOH_RUN_CHECK`、`HOH_ASK` 与身份头给出。`run-check <check_id>` 原子地写 `requests/<n>.json{kind: "check", check_id}`；`ask <message.json>` 写 `{kind: "message", message}`；两者都等待 `requests/<n>.response.json`（检查的上限为计划超时加宽限，消息为 60 s），打印结论；`run-check` 以检查的退出码结束，被拒为 2。
   - host 对每个运行中的验证 Attempt 轮询 `requests/`，按序号逐个处理，同一 Attempt 串行，至多 `MAX_REQUESTS`（初值 64）个。
   - `check`：只接受冻结计划里的 check_id；以该 Attempt 为生产者、运行目录为检出、`.hoh/` 为状态根调用 `verify::check::run`。检查命令经与 Attempt 主进程相同的启动门启动：委派 cgroup 下先进入该 Attempt 的 cgroup，`/proc` 退化模式下带该 Attempt 的标记环境（ADR-021 决定 8d），所以 Attempt 的取消、结束与 reconcile 的“进程已结束”证明覆盖它们（host 被 SIGKILL 后，reconcile 先终止并证明它们结束，再由 `check::reconcile` 补记已写出待入库事实的记录）。驱动拒绝（前核对不符）时写 `verification.check_refused{attempt_id, check_id, reasons}`（ADR-027 决定 6 的“供 M2-T16 记录”）并回应 Agent；不写证据（Attempt 级的核对另行判定，决定 8）。回应带 outcome、原因、记录路径、exit_code。
   - `message`：按决定 13 即时处理，回应 rejected 或 deferred。
   - Attempt 的进程结束后，执行器先等它进行中的检查收尾（记录与证据已提交），再做决定 8 的核对与结算；之后不再处理它的请求。
   - 证据的 outcome 来自检查，不来自 Agent 的自述。

8. **Attempt 级的运行后核对（REQ-037 行为 5，AC-037-03，ADR-027 移交）。** 验证 Attempt 的每条结束路径（成功、失败、取消、reconcile）在结算之前取运行目录的工作区哈希 `post_tree`，并核对 HEAD 与 tree 仍是候选，写 `verification.tree_checked{attempt_id, candidate_id, pre_tree, post_tree, equal, status}`（`status` 为运行目录 `git status --porcelain` 的前 4 KiB，供观察）。不相等或读不了时，经 `Store::record_evidence` 写一条 INVALID 证据，执行记录的形态：check_id 为该角色的 `independent-qa` 或 `independent-review`，command 为 `["hoh", "verification-attempt", <attempt_id>]`（不声称运行了计划命令），exit_code 0、`source_unchanged=false`，stdout/stderr 为空文件，artifacts 为空，前后 tree 进 `evidence.recorded`；记录写在 `.hoh/evidence/<候选>/<check>/<record>/`，走 ADR-027 决定 8 的恢复协议。原则一对它给出 COMMAND_MISMATCH 与 SOURCE_CHANGED 的否决，候选在同一事务置 INVALID（M2-T16 从不直接改候选状态），traceability 的文件扫描同样否决；同一事务写 `integrity_violation`（ADR-027 决定 7，监督器同一 tick 唤醒 Commander）。

9. **验证义务与交接（ADR-018 决定 4、5，ADR-026 决定 6，REQ-022 决定 2，-08、-57、-63）。**
   - 一个候选的验证义务是 (候选, 源开发 Task, 角色) 三元组，持久地记在 `handoffs` 行上：接受的提交为每个角色写一条交接消息与一行 `handoffs(handoff_id = 消息 id, from_role = "runtime", to_role, role_epoch, package_artifact_id, state = PREPARED)`；交接包（ContextHandoff 的规范 JSON）写成对象并登记 artifacts 行。消息 id 为 `child_id(候选, "verify/<源 Task>/<角色>")`（同一候选可有多个源 Task，决定 3），与 ADR-018 决定 6 的写法相比加了源 Task（注记）。
   - host 的循环在每个 tick 的调度轮之前运行 HCP 投递，只为 qa、reviewer 的 kind=handoff 行注册产品消费者；其他种类与角色不领取（ADR-018 决定 4 的“已注册消费者”）。消费者在一个事务里：候选已 STALE 或 INVALID、或 Run 已取消 → 回执 rejected，`handoffs` → REJECTED（原因事件），义务以 NOT_RUN 结束；接收角色的 epoch 已变 → 回执 rejected，同一事务以当前 epoch 重发一条新消息（id 加 `/e<epoch>`）与新的 `handoffs` 行，义务不变；否则创建验证 Task（`task_id = child_id(候选, "verify-task/<源 Task>/<角色>")`，role 为 qa 或 reviewer，writer=0，spec_id 为 Run 的 spec，layer 0，状态 READY，`task_requirements` 复制源 Task 的），写 `verification.dispatched{candidate_id, task_id, source_task_id, role, handoff_id}`、回执与 `handoffs` 的 DELIVERED。暂停的 Run 照样创建 Task（暂停只停派发）。KeyReuse 计为一次拒绝、不重试到死信（M2T17R-254）；投递上限取 `delivery.max_delivery_attempts`。验证交接不投递到会话，所以“新持有者首个输入之前不投递”（M2T17R-153）对它是空条件，测试固定这一点。
   - 验证 Attempt 以它的交接启动（Prompt 已发出）时 `handoffs` → ACCEPTED。
   - Commander 交接包（ADR-024）也写这张表：交接事务写 PREPARED，首个输入送达时 DELIVERED（from_role 为旧持有者的角色）。
   - 验证 Task 是 Runtime 的：Commander 对它的迁移提议与派发一律 ILLEGAL_TRANSITION（decision.rs 的 TaskView 加 `runtime_owned`）；它不进依赖图。

10. **Runtime 规则类派发（ADR-025 决定 3 的移交，AC-035-05、AC-021-05）。** 验证 Task 的派发是 Runtime 规则类：调度轮对 BLOCKED 的 Run 除已排的重试外也派发验证 Task；派发通知带 `origin: "verification"`，runner 对 BLOCKED 与 WAITING_EXTERNAL 的 Run 放行。所以 Commander 不可用（Run BLOCKED，COMMANDER_UNAVAILABLE）时，candidate_ready 照样产生两条交接、两个验证 Task 与它们的派发。

11. **barrier 与结论（REQ-037 行为 4，REQ-054 行为 7，-06、-07、-09、-51、-52、-53、-56、-57）。**
    - 一个候选的 barrier 从它的第一条验证义务起打开；一条义务**已了结**，当它的验证 Task 已结束（Task IMPLEMENTED，即 Attempt 成功结算；或 CANCELLED），或它以 NOT_RUN 结束（决定 9）。BLOCKED 的验证 Task（鉴权、能力、重试用尽）不算了结：阻塞解除后它会再派发，barrier 等它。
    - **关闭只有一处**：每个 tick（与 host 启动时）运行的幂等清扫 `Store::close_barriers`，对每个有验证义务、义务全部了结、还没有 `verification.barrier_closed` 的候选，在一个事务里关闭（事件 id `child_id(候选, "barrier")`），所以关闭事件的 seq 必然大于两个 Attempt 的终态事件。
    - **结论**（写进 `verification.barrier_closed{candidate_id, verdict, obligations:[{source_task_id, role, task_id, attempt_id, task_state, result_status}], evidence:[{evidence_id, attempt_id, check_id, outcome}], issues:[…]}`）：
      - `repair`（有修复义务）：该候选有任一 FAIL 或 INVALID 证据、候选为 INVALID、或有 `candidate_id` 为它的 OPEN Issue。候选 VERIFYING→REJECTED（`AND state = 'VERIFYING'`，不覆盖 INVALID）；每个源开发 Task（仍为 VERIFYING 的）按决定 12 的返工裁决到 READY（返工，layer 置 0，ADR-017 的关键修复层）或 BLOCKED。
      - `incomplete`：没有修复义务，但有义务以 NOT_RUN 或 CANCELLED 了结，或验证 TaskResult 不是 COMPLETED。候选保持 VERIFYING、不返工，写 need_decision（唤醒 Commander）；不是 PASS，也不是失败（REQ-054 行为 7）。
      - `pending_join`：义务全部完成、验证 TaskResult 都是 COMPLETED、没有修复义务。候选保持 VERIFYING，由 M2-T18 的汇合函数在这一关闭点判定 ACCEPTED 或 REJECTED（AC-054-05）。M2-T16 从不写 ACCEPTED。
    - 同一事务写 `iteration.completed{iteration, candidate_id, verdict}` 与一行 `iterations(run_id, number = 已有数 + 1)`，按 ADR-020 的用量规则累加 `iterations` 用量；它是 balanced 监督的轮次边界唤醒的产生方（ADR-025 决定 2）。
    - **STALE**：候选在 barrier 期间被另一个写任务的候选取代（ADR-027 决定 5，AC-054-02 的前提）时，冻结新候选的完成提交把旧候选的源开发 Task（仍为 VERIFYING 的）置 READY（`task.superseded{candidate_id}`，不计修复）：它再次运行时，工作已在新的提交里，冻结得到当前内容，按决定 3 接到当前候选上或另行冻结。旧候选的 barrier 仍按上面关闭，结论之外不再迁移任何 Task。
    - QA 与 Review 互不等待：一方失败不取消另一方。

12. **修复与纠正的裁决、验收门禁（ADR-020 决定 10、ADR-022 决定 6 的移交，ADR-011 §3 的更正，-01、-09、-50、-53）。**
    - 抽出 `retry::repair_in(tx, request, action_id)`：在调用方的事务里裁决、按 `action_id` 幂等（已有该 action 的计数事件即返回当时的裁决，不再计数）；`Store::request_repair` 改为调用它。返工的 action_id 为 `child_id(候选, "rework/<源 Task>")`，协议纠正的为被纠正的 Attempt id。
    - 返工请求 `Repair::Local{fingerprint}`，fingerprint = sha256(源 Task id ‖ 排序后的失败项)，失败项为该候选的 FAIL/INVALID acceptance_results 行的 (AC id, 测试名)、没有验收行的 FAIL/INVALID 证据的 (check_id, 原因)，以及 OPEN Issue 的指纹（与候选无关，见决定 13），所以只有同一 Task 的同一失败反复出现才累积；上限 `max_local_repairs`。准许时源 Task VERIFYING→READY、`attempt_count` 清零（重试预算按迭代计），`task.rework{candidate_id, fingerprint, count}`；超限时 Task BLOCKED（NEED_DECISION）与 need_decision。
    - 协议纠正请求 `Repair::Protocol{attempt_id}`，键为这条纠正链的首个 Attempt（后继 Attempt 的 `task.protocol_correction{root, attempt_id, reasons}` 带着它），上限 `max_protocol_repairs`；下一个 Attempt 的 Prompt 任务上下文带上拒绝原因。验证角色的纠正见决定 15。
    - **验收门禁**：Task VERIFYING→ACCEPTED、Run→COMPLETED 与 accepted_requirements 要求候选的状态为 ACCEPTED（只由 M2-T18 的汇合函数写），不再接受 VERIFYING 的候选（persistence/decide.rs 的 `load_evidence` 与 decision.rs 的门禁一起改）。M2-T18 接入之前这些提议一律 EVIDENCE_GATE_UNMET：fail-closed，没有任何路径能在 barrier 之前或在 FAIL/UNKNOWN 上接受。依赖旧门禁的已有测试改为在夹具里把候选置 ACCEPTED（收紧，不是放宽）；ADR-011 §3 加更正注记。

13. **barrier 期间的改写请求与其他消息（REQ-037 行为 6、失败模式 5，AC-037-04，REQ-053 行为 5，-05、-58、-64、-65）。**
    - 验证 Agent 经请求桥或桥文件送出的、recipient_role 为 developer 的 `query`/`steer`，在它的候选 barrier 未关闭时一律拒绝：一个事务写 `request.rejected{attempt_id, message_id, reason_code: ILLEGAL_TRANSITION, detail: "the candidate under verification is not changed; an Issue for the next candidate"}`、一行 `issues(issue_id = child_id(Attempt, "request/<message_id>"), candidate_id = 该候选, fingerprint, severity, state = OPEN, description)` 与 `issue.opened`；回应 Agent rejected。不入 outbox、不形成等待。severity 取 payload.severity，不是四个合法值之一时为 medium；fingerprint 按 REQ-054 决定 2 的与候选无关形式：sha256(severity ‖ 规范化的请求正文)。
    - 其他接收者（commander、cto 等）或 Developer 自己的 query/steer：写 `request.deferred{attempt_id, message_id, recipient_role}` 并回应 deferred（角色间路由归 M3-T04，见 CR-018），不静默忽略。
    - wait-for 视图 `Reader::wait_for(run)`：由未结束的角色间请求（PENDING/DELIVERING 的 query/steer outbox 行）构成的有向边，发送方→接收方；被拒与 deferred 的请求不入 outbox，所以不产生边。测试以预置的一条 qa→developer 的 PENDING query 行作正对照（看得到边）。
    - 修复经决定 11 的 `repair` 结论与决定 12 的返工进行，返工的派发事件必然晚于 barrier_closed；返工产生的 C2 冻结时 STALE C1（ADR-027 决定 5），C2 的 acceptance_results 在它自己的验证之前为 0 行。返工 Developer 的证据上下文列出被拒候选的 OPEN Issue 与 FAIL/INVALID 证据的引用（决定 14）。

14. **Prompt 的来源（REQ-053 行为 2，AC-053-03，AC-039-03，ADR-026 决定 3、10、12，-59、-62）。**
    - 验证 Attempt 的 Prompt 由执行器用交接包对象经 `Reader::verification_context` 与同一装箱器生成，不另写路径；身份头见决定 2。
    - **开发者自测**：Developer 把自测记录写在 `.hoh/self-tests/<自己的 attempt_id>/` 下（被忽略），TaskResult.evidence 只接受指向这里的项目相对路径（拒绝绝对路径、`..`、链接）。完成提交前，执行器按普通文件、非阻塞读取并核对 sha256，存为对象并以 `self_test` 种类登记进 `attempt.artifacts`；不符的项只记引用。收集函数只从这些已登记的对象取正文：UTF-8 文本取前 8 KiB（截断处标明），条目标为 `diagnostic`（“开发者自测（diagnostic，仅作诊断，不作验收依据）”），relevance 最低；TaskResult 的 summary 条目同样标 diagnostic。AC 正文是强制项，按装箱顺序先于证据层。原始日志与会话记录（`attempt.artifacts` 里的 raw log 种类）从不读入正文，只按引用列出。
    - **代码类来源**：候选相对其基准改动的文件（`git diff --name-only <基准> <候选 commit>`；基准为同一 Run 中被它取代的候选的 commit，没有时为源开发 Task 首个写者 Attempt 的 `attempt.workspace_start.head`），按路径排序，每个文件读候选 commit 中的内容（`git show`，非 UTF-8 或超过 64 KiB 的只列路径），至多 50 个文件，条目类别 Code，交给装箱器按 45% 的份额取舍。返工的 Developer 用同一来源（候选为被拒的那个），另加被拒候选的 OPEN Issue 与 FAIL/INVALID 证据的引用（证据类，命名的收集函数 `Reader::rework_context`）。
    - 三份角色契约（developer.md、qa.md、reviewer.md）随之更新（产品内容，中文）：冻结由 Runtime 在 COMPLETED 后完成、自测记录的位置、桥文件、`run-check` 与 `ask`、报告块。

15. **验证 Attempt 的结论与报告（AC-054-03，ADR-022 决定 6 的移交，-56、-60）。** 验证 Attempt 的进程结束后：
    - 桥里的 TaskResult 决定它的 `result_status`（COMPLETED、FAILED、BLOCKED、INCOMPLETE，缺失或无效为 `missing`），记进结算事务与 barrier 的义务载荷。
    - 从最后一条助手消息里取 ```hoh-report 代码块（与 `tools/agent_task.py --report-out` 相同的提取规则）。Runtime 生成产品的 native_attempt 对象（contracts/native-attempt.schema.json：record_type、role、status、session_ids 含该 Attempt 的原生会话 id、candidate_id、stdout_sha256 等于原始会话对象的 sha256）与 raw_session（该 Attempt 原始会话日志的对象），把报告补上 session_id（原生会话 id）、candidate_id、spec_sha256、raw_session{path, sha256}、native_attempt{path, sha256}，写成对象并登记，事件 `verification.report{attempt_id, role, status, report{path, sha256}}`。
    - TaskResult 或报告缺失、不合 schema 时：`verification.output_invalid{reasons}`，按决定 12 的协议纠正（准许时验证 Task 回 READY，下一个 Attempt 是新的原生会话，Prompt 带原因；超限时 Task BLOCKED）。
    - 报告进 `independent_reports`、独立性校验、Issue 登记与投影归 M2-T18。

16. **host 启动（ADR-027 决定 8 的移交，-57）。** host 启动时、第一个 tick 之前：对每个有记录目录的候选调用 `check::reconcile`；一个候选的错误写 `candidate.reconcile_failed{candidate_id, error}` 与 `integrity_violation`（唤醒 Commander），挡住该候选（它的验证 Task 不派发），并在之后每个 tick 重试，不使 host 启动失败。没有活 Attempt 的运行目录与请求删除；然后运行一次 barrier 清扫。

17. **守卫清单（ADR-027 决定 3，-68）。** 冻结与核对的守卫加上新的 HoH 写入路径：`.hoh/environment.json`、`.hoh/self-tests/`、`.hoh/attempts/<id>/requests/`、`.hoh/attempts/<id>/run-check`、`.hoh/attempts/<id>/ask`（运行目录在项目树之外，不在守卫内）。
