# ADR-033 · Markdown 规格事实源、索引与批准事务

日期：2026-11-21。状态：采用。关联：REQ-034、REQ-033；CR-018、CR-019、CR-026。

本决定落实 M3-T02 准备清单 §8–10 与 CTO 的 Q1–Q10 决定。M3-T01 的
`8d9ae599` 已补齐 Rust 原因码。S1–S6 已实现；S6 的顺序矩阵与进程证据见第 5 节。自测是诊断，不是验收；独立验收由 M3-T05 执行。

## 1. 事实源与语法（Q1）

事实源是用户项目 `docs/spec/` 的直接子文件 `*.md`，不是数据库、生成页或 HoH
自身的 contracts。文件名区分大小写，按项目相对路径排序。拒绝非 UTF-8、重复路径、
链接与不规则文件。每份文件遵循以下产生式；`NL` 可为 LF 或 CRLF，源摘要始终取
原始字节。空行可以出现在任意完整行之间；结构行不得缩进。所有文本值非空、单行。

```text
document    = users scope non_goals decisions questions requirements
users       = "# 用户" NL prose*
scope       = "# 范围" NL prose*
non_goals   = "# 非目标" NL prose*
decisions   = "# 决策" NL ("无" NL | decision*)
decision    = "- " text NL "source: " source_kind "=" identifier NL
source_kind = "question_id" | "input_id" | "event_id"
questions   = "# 开放问题" NL ("无" NL | question*)
question    = "- Q-" req_id " " text NL "阻塞：" ("是" | "否") NL
requirements = "# 需求" NL requirement*
requirement = "## REQ-" req_id " " text NL class? acceptance*
class       = "class: " ("required" | "degradable") NL
acceptance  = "### AC-" req_id "-" ordinal NL
              "given: " text NL "when: " text NL
              "then: " text NL "check: " identifier NL
req_id      = alnum (alnum | "_")*
ordinal     = digit digit
identifier  = (alnum | "_" | "-" | "." | ":" | "/")+
```

`alnum` 与 `digit` 是 ASCII 字符。文件末行可以不带换行。`prose` 是不以 `#`
起始的非空文本行；结构标题只允许产生式中的六种一级标题及 REQ/AC 标题，顺序固定、
每种一级标题恰一次。`无` 不能与同节的条目并存。class 只在 REQ 标题之后、首个 AC
之前出现一次，缺省 `required`。AC 的需求部分须与所在 REQ 相同；REQ、AC 与开放问题（`Q-<id>`）的 id 在
全部文件中唯一。开放问题的 id 与阻塞标记、决策的来源由解析器连同位置一并给出，不进
index.json（文件摘要已覆盖它们；ADR-035 决定 1，M3-T06 S5 修订本产生式）。AC 四个字段顺序固定、各一次，不接受未知字段，也不猜补缺失内容。
解析只校验决策来源的语法；来源真实性由提议与批准事务在写入前校验，归 M3-T06（ADR-035 决定 2：缺来源即
422 `SPEC_INVALID`，`details.unsourced` 列出条目，不写任何东西）；批准者身份归 M3-T04，readiness 归 M3-T06。
因此可解析的空节、无 AC 的需求可以生成索引，不等于可派发。

索引校验失败返回 `IndexError{path,line,error}`，line 为从 1 起的源文件行号；缺少字段时指向
下一个结构行或文件末尾。host 映射为 422 `SPEC_INVALID` 并记录
`spec.index_failed{path,line,error,spec_revision}`。无半份索引或新修订落库。

Git 枚举或文件系统读取失败与内容校验失败分开（CR-036，M3B-07）：host 以
`SpecReadError::Unavailable` 交给命令事务，映射为 503 `SPEC_SOURCE_UNAVAILABLE`、
`retryable=true`。响应沿用 DB_BUSY 的 Error 结构，不加 `Retry-After`；失败回滚，
不接受命令、不写 `spec.index_failed`，恢复访问后可原样重试。非法语法、链接、
非规则文件等实际校验失败仍为不可重试的 422。CLI 对 503 沿用退出码 69 和既有
重试，TUI 显示返回的原因码与消息。

## 2. 规范字节、生成与冻结（Q7、Q9）

`docs/spec/index.json` 的根对象只有 `generated`、`files`、`requirements`、
`scenarios`。`generated` 为字符串 `生成，勿改`；`files` 是
`{path,sha256}` 数组，路径按字典序，摘要为每个 Markdown 原始字节的 SHA-256。
requirements 按 id 排序，使用已有需求对象的字段形状：`id`、`title`、
`release_class`、`release_targets`、`acceptance`；不虚构语法未提供的项目元数据。
`release_targets` 恒为 `["project"]`。acceptance 按 id 排序，字段为
`id,given,when,then,test_id`；`test_id` 将 AC 前缀换为 TEST。
scenarios 按 id 排序，每项为 `{id,requirement_id,acceptance_id,check_id}`，
`check_id` 来自 check 行。

所有对象的键递归按字典序，UTF-8（不将中文转为 ASCII 转义）、LF、两空格缩进，
末尾恰一个换行。规格摘要就是这些字节的 SHA-256。源文件的空白变化也会改变 files
摘要进而改变规格摘要。索引不含时间、机器路径或数据库 id，输入顺序不影响输出。

纯生成函数返回规范字节及字节差异；调用者负责文件和事件。显式生成覆盖不等于重建
字节的索引；只有已有索引的摘要既不属于本项目任一已批准修订，也不属于本项目任一
`spec.proposed` 事件绑定的 CR 摘要时，才记录
`spec.generated_drift{path,spec_revision}`。旧修订或已提议的生成索引落后于 Markdown
不算人工漂移；缺失索引是创建，不记漂移。已拒绝或应用的 CR 的生成摘要仍可核对来源。
解析失败保留已有文件。批准只核对，不在冲突时覆盖文件。没有新 CLI。

冻结在现有干净工作区检查之后，只取 Git 已跟踪的 `docs/spec/*.md` 直接子文件，
从本次捕获的 HEAD commit 读取原始字节，以相同函数重建索引；忽略文件和未跟踪
文件不作为生成输入，未忽略的未跟踪文件仍由干净检查拒绝。与提交的 index.json
逐字节不等则 `SPEC_INVALID`，不产生候选。同一提交的结果不依赖忽略文件是否存在。既有检查仍拒绝隐藏改动的
Git 标志、链接与子模块，冻结末尾仍核对 Git 身份和干净状态。
产品 `inputs().spec` 改为 index.json。Q7 测试以非 root 运行：忽略的
`contracts/requirements.json` 权限为 000，冻结仍成功，inputs 列表无此路径。
该文件必须被忽略，否则既有冻结规则会把它作为源码或未提交文件处理。
不引入 open 拦截或 strace。删除 CR-019 的 `read_as_data` 旧路径条目；保留
`files` 的同名扫描条目。HoH 自身的 tools 仍读取自己的 contracts。

## 3. 批准与提议的事务（Q2、Q3）

host 读取工作区 Markdown、索引及其 Git 跟踪身份，纯核心重新生成；持久化模块在
现有命令幂等与 expected_revision 边界内提交。成功命令的重放返回同一结果，不新增
修订或事件。`specs` 只存已批准修订，没有草稿行。

批准的命令摘要必须等于重建摘要，且已跟踪的索引字节必须等于规范字节。失败返回
409 `SPEC_CONFLICT`；details 的 `expected` 是命令摘要，`actual` 是重建摘要；
索引不一致时额外带 `tracked`（缺失或未跟踪为 null）。冲突不写库、不改文件，
包括不登记已接受命令或漂移事件。

首次批准在同一事务插入 revision=1 的 specs、requirements、acceptance_criteria，
AC 的 check_id 取 scenarios；设置命令所在 Run 的 spec_id（原为空或更旧），写
`spec.changed{cause:approved,from:null,spec_revision:1}`。不插 CR，不置 STALE。
APPROVE_ONLY 与 APPROVE_AND_BUILD 共用批准写路径，后者的模式/起草调度由 M3-T04
接入。REJECT 不创建修订；后续修订的 REJECT 按命令中的提议摘要定位 CR，只把对应
CR 置 REJECTED。REJECT 不要求工作区摘要或已跟踪索引与提议一致，因此文件已改回或
索引已取消跟踪后仍可拒绝（M3B-06）；身份、Run revision、CR base 等其余校验不变，
提议和两种批准仍执行原有的摘要与跟踪校验。

S3 提供正常提议与第二修订所需的 CR 存储接缝：提议以当前最高已批准修订为 base，
绑定新摘要、写 PROPOSED，不变更已批准规格或 Run.spec_id；命令仍按通用协议递增
Run.revision。为避免用空数组冒充影响分析，S3 的成功提议调用下节的纯闭包函数写入
真实 impact_json；STALE、验收投影及 AC-033-01 的独立验收仍留给 S4。
当重建摘要等于当前已批准摘要时，提议入口只修复生成文件，不创建 CR、不产生新修订、
不使候选或验收失效；事务记录 `spec.regenerated` 命令回执，人工漂移事件另按上一节
条件记录。重放同一命令可补齐文件发布，不重复记录事件。即使旧实现已存入同摘要 CR，
批准也以 409 `SPEC_CONFLICT` 拒绝结果摘要等于 base 的 CR；REJECT 仍可拒绝该 CR。
批准按提议绑定的摘要定位 CR，
base 过期则 409 且 CR 保持 PROPOSED；成功写 revision+1、派生行、CR APPLIED 与
result_spec_id、`spec.changed{cause:changed,from,to,cr_id,spec_revision}`。
同项目非终态且 spec_id 为 base 或更旧的 Run 在事务内采用新修订；终态 Run 保留
历史。半写入失败回滚整个事务。解析失败只写诊断事件，不写 CR 或新修订，调度仍用
上一已批准修订；修好后重新提议、批准。

提议事务提交后，host 原子写入生成索引。写文件失败返回可重试的 503，明确告知
提议已经入库；重启后重放同一命令可补齐文件，不重复插入 CR 或漂移事件。
发布前再次核对 Markdown 与原索引快照；期间有外部编辑则拒绝覆盖。索引已为规范
字节时无需重写。批准路径始终只核对文件。

## 4. 闭包、失效与任务（Q4、Q5、Q6、Q8；S4–S5）

影响闭包只沿显式映射：增删改 REQ → 新旧 AC → TEST → task_requirements
关联任务；不按文件猜测。`impact_json` 为恰好四个字段
`{"requirements":[],"acceptance":[],"tests":[],"tasks":[]}`，每个数组排序、去重。
闭包的独立验收属于 S4 的 AC-033-01。

任何新修订使受影响 Run 上 FROZEN、VERIFYING、ACCEPTED 候选变为 STALE。
`candidate.stale{candidate_id,reason:spec_changed}` 只由 persistence/recovery.rs 写入，
使用既有 judgment id；若已有 evidence_unrecoverable 判定则保留它，状态更新和
后续取消请求仍执行。批准与采用的 cause 不触发失效。

当前验收范围为 Run 当前修订的全部 AC，不依赖 task_requirements，也不因任务被取消
而从分母删除 AC（Q4 取代旧的按任务计数规则）。Run 投影 acceptance 增加
spec_revision；最新候选摘要不属于当前修订时，当前 AC 均为 NOT_RUN、无观察行，
accepted 与 passing 为 0，全部 AC 为分母。

验收 API 保持受锁 ApiPage 的顶层形状（items、next_cursor、watermark），当前修订
尚无候选时，将其全部未观察 AC 作为 items 中的 NOT_RUN 项，candidate_id 与
candidate_state 均为 null，按 AC id 排序置于历史之前。历史优先使用
acceptance_results 的 spec_id，尚无观察时按候选摘要查找修订；没有匹配的旧导入
数据保持当前修订的空投影。旧修订项一律标 STALE，数据库观察行不改写。分页游标
的第三段增加修订次序；当前无候选项使用保留的 (i64::MAX, 0) 位置，避免漏项或
虚构候选身份。items 与 Run 投影均在各自同一读事务下计算。
本段取代 ADR-029 决定 5 里按 task_requirements 取验收范围、以及 items 的
`candidate_id` 必为字符串的写法（2026-11-24，M3B-54；ADR-029 该条下有同日注记）。
尚无观察的候选按冻结当时的规格修订绑定摘要，不因之后有修订恢复同一字节而改标为当前。
没有新候选时 Commander 的当前候选为空，申请 COMPLETED 被既有
EVIDENCE_GATE_UNMET 拒绝。显式引用同一 Run 的旧修订 STALE 候选时，完成申请仍被
既有门禁拒绝，持久化层将这项拒绝说明为 EVIDENCE_GATE_UNMET，详情列出候选、
STALE、当前规格修订及该修订 required 需求的 AC。门禁函数与接受谓词不变；不是
旧修订 STALE 候选的候选不匹配仍为 CANDIDATE_MISMATCH。TEST-033-03 按各 AC 的
check_id 写夹具证据，在同一真实候选上先证明批准前门禁放行（仅在完成写入点注入
回滚，保留 Run 供后续批准），再断言批准后的具体拒绝与全部新修订 AC。

S4 在批准事务中为 FROZEN、VERIFYING、ACCEPTED 设置 STALE（不覆盖 INVALID、
REJECTED），与新修订、Run 采用、失效事件原子提交。已有判定不重复写，失败整体
回滚。S4 的夹具只有持久状态，不运行验证进程；独立报告翻转与 Attempt 取消仍属 S6。

S5 在批准事务内迁移每个被移动 Run 的全部非终态任务，不以 CR 影响闭包、写者
标记或 READY/PENDING/BLOCKED 等状态筛选（M3B-51，所有者本次修复指令；取代
准备清单“未迁移任务保持不可派发”的限制）。所有关联 REQ 仍在时，tasks.spec_id
与全部 task_requirements 一起迁到新修订，写 task.migrated；没有需求映射的任务也
随 Run 迁移。通常保留状态、blocked_reason、next_retry_at 与 attempt_count，仅增加
任务 revision 以阻挡旧的派发决策。终态 Run、ACCEPTED/CANCELLED 任务保留历史。

只有当前开放问题为 work / spec_mismatch、且没有有效修复拒绝的 BLOCKED 写任务
同时被放行：BLOCKED→READY，清除 blocked_reason 与 next_retry_at。其他问题、
修复拒绝和只读任务的阻塞不被解除，但其规格映射仍迁移。无需用户回答，也不伪造
question.answered；已放行任务的问题按状态自然关闭。若 Run 被 pace 阻塞，既有
pace 在迁移任务可推进后释放自己的声明并恢复 Run。

任一关联 REQ 被删除时取消整个非终态任务，保留旧映射作历史，写 task.cancelled，
清除 blocked_reason 与 next_retry_at，保留 attempt_count，并写下述 Q5 开放替代
记录；不静默缩小任务范围。VERIFYING 源任务也在批准时迁移：候选失效之后，既有
reconcile_verification 把它送回 READY 时，它已指向新修订，可重新派发和冻结；
因需求删除而取消任务时，同一批准事务也给该任务全部 PREPARED/STARTING/RUNNING
Attempt 设置 cancel_requested（M3B-100，所有者后续修复指令）。host 复用 S6 的单
Attempt 取消，证明进程已结束并记录写者工作区后才释放租约；不等待自然完成走
runner_error。已结束 Attempt 与未取消任务的 Attempt 不受影响。全部任务改动、
取消请求、失效与批准仍在同一事务内。
既有 Route::Continue 保留，但不是本 AC 的放行路径。

批准事务写一条开放记录，列出取消任务 from 与被删 requirement_id。仅该 Run 批准后
**第一次计划导入**新建的任务可参与替代；双方按 created_seq 一一配对，写
task.replaced{from,to} 并消费开放记录。新任务多余部分普通处理；没有新任务时原任务
保持 CANCELLED、不写 task.replaced，也不留给第二次导入补配。这是因受锁
PlanProposal 无 replaces 字段而采用的推断规则；增加字段须另行 CR。

开放记录采用 spec.task_replacements_opened，含 spec_revision、spec_id 与 cancelled
数组（每项 from、deleted_requirement_ids、created_seq）。消费记录采用
spec.task_replacements_consumed，以开放记录 id 派生唯一 id；计划导入只读取本 Run
该种类的记录，再按唯一 id 查消费状态。多个批准尚无计划导入时，第一次成功导入
统一按 created_seq 配对，每个新任务最多接一个旧任务；所有开放记录同时消费，
未配对部分仍取消。计划、task.replaced 与消费事件同事务提交，失败回滚全部内容。
记录是持久事件，重启无需内存队列。锁定的 PlanProposal 至少要求一个新任务，因此
空或非法计划不是成功导入，不消费开放记录；没有计划时不产生替代事件。

## 5. Attempt 取消与恢复（Q10；S6）

批准事务对失效候选的验证 Attempt，以及上一节因需求删除而取消的任务的未结束
Attempt 设置 cancel_requested，独立报告标 STALE，
不改变 Run 状态、不关闭轮次。host tick 与启动对账运行既有单 Attempt 取消阶梯，
包括 cgroup 中的 run-check；严禁为规格变化调用 Canceller::step(run_id)。重启后
同一持久旗标继续生效。只有进程结束证据齐全、两个验证任务了结之后，
reconcile_verification 才以 superseded 恰好关轮一次。迟到报告不进入验收。
S6 需要进程生命周期与并发两份互补审查。

host 的取消工作者按 Run 去重，但逐轮重新读取取消范围：仅显式 Run 取消才进入
`Canceller::step(run_id)`；规格变化只调用从既有阶梯抽出的 `step_attempt`，只取走
这些 Attempt 的 inflight 工作。这样规格批准与稍后的用户 CancelRun 也只有一个取消
所有者。STARTING 先关闭并等待启动门；PREPARED 由同一结束事务取消，领取事务也
检查 cancel_requested，避免批准与派发交错时继续启动。启动对账继续使用既有进程
身份与 cgroup 终止证明，PREPARED 的取消不再 Redeliver。
M3B-150 的真实派发测试还复现了 STARTING 的提交窗口：批准置取消旗标之后，
`runner_running` 原先仍会提交 RUNNING 与 effect.started。现在该提交在同一事务中
核对 Attempt 仍为 STARTING、没有 cancel_requested 且 Task 不是 CANCELLED，
否则返回未启动；host 丢弃未打开的 Gate。领取前的 PREPARED 则由 runner_received
拒绝真实 dispatch notice，不创建进程。STARTING 测试允许门控辅助进程已经存在，
断言门未打开、Agent 未执行、辅助进程已回收。

**取消恢复的完整映射（M3B-200）。** 恢复的纯判定仍描述进程与效果，持久化的
apply 在自己的事务中重读 `attempt.cancel_requested OR task.state = CANCELLED`，
不依赖扫描时的旧值。取消成立时，Redeliver、Ended（包括原本是 Cancelled/Ready）、
Complete、Completed、UnknownEffect 全部结算 Attempt 为 CANCELLED，且不改 Task、
不增加重试次数、不安排重试。Unreaped 仍保留 Attempt 与租约，直到有结束证明。
效果的迁移与 UNKNOWN 诊断保留；正常终结仍经既有路径释放租约并记录写者工作区。
这同时覆盖取消已经提交、以及扫描后才提交的情况，避免已取消任务复活或非法迁移
使整个启动恢复事务回滚。没有取消的恢复行为不变。
取消旗标轮询使用持久化 Reader 的只读查询，不新增 Reconcile 写者请求，保持既有调度
tick 的事务序列；完整回归中的 held-staffing 测试覆盖这一边界。

批准可能在 reconcile_verification 与 schedule_round 之间提交。调度事务自身再次
读取验证任务所属候选的状态：候选为 STALE 时，该任务不参与选择，即使任务
仍为 READY 且已迁到新修订（M3B-101）。后续对账仍负责取消任务与恰好一次关轮。
测试先证明 QA 与 Reviewer 在批准前均可派发，再按“对账、批准、调度”的顺序断言
没有新 Attempt；不靠下一轮对账提前取消任务来掩盖此窗口。
此处仅处理失效候选。同修订共享候选被兄弟轮次判为 REJECTED 时，保留既有的轮次
历史与分类语义；既有 a_siblings_rows_published_after_a_round_opened_are_not_its_history
测试覆盖该边界。将所有非 VERIFYING 状态一并排除会破坏这一回归，故未采用。
