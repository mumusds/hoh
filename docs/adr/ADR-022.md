## 决定

### 配置

1. **配置文件**
   - 项目配置在 `<project>/.hoh/config.toml`，叠在内置默认之上；没有用户级全局层。文件不存在时就是内置默认。
   - 内置默认与 `config/hoh.example.toml` 逐键相等（AC-018-01）。
   - 相对的 `prompt` 路径以项目根为基准。
2. **解析与校验**：用 `toml` 1.x 带位置解析，由 `hoh_core::config` 统一校验，文件与 ConfigureTeam 走同一套规则。
   - **未知键**：REQ-018 决定 6 键表之外的键，在任何层级都拒绝，并给出键路径和行列。
   - **取值范围**：
     - `config_version` 必须是 `"1.0"`；
     - `execution.writer_slots` 必须为 1（REQ-037）；
     - `scheduler.*` 的范围同 SchedulerSettings；
     - `web.host` 只能是回环地址；
     - 枚举值：`default_mode`、`document_profile`（REQ-029）、`execution.profile`（只有 `yolo-vm`）、`supervision.policy`、`ui.view`；`ui.statusline` 暂只有 `standard`，M4 扩充。
   - **职位**：
     - Agent 只能是 codex、claude 或 pi，fallback 是互不相同的 Agent，且不含该职位自己的 Agent（M2T07R-60）；
     - `model` 为空表示用底座的默认模型；
     - `reviewer.independent_session` 不能为 false（CONTRACT 7）；
     - 自定义职位名为小写字母开头，最多 64 个字符，只含小写字母、数字和 `_`，必须有 Agent，并给出 prompt 覆盖文件或 `builtin:<内置职位>`（REQ-018 决定 5）。
   - 任何拒绝都不改用默认值，也不忽略出错的键。

### 团队 revision 与 ConfigureTeam

3. **团队 revision 按项目编号**
   - revision 0 就是内置默认，由第一个团队事务补写，不产生事件。
   - 接受 ConfigureTeam 时，在接受事务内写入 r+1 并直接标为 APPLIED，它就是项目当前的配置。`expected_revision` 与最新的 APPLIED revision 比较（与 SQL 注释一致）。并发请求中输掉的一方在同一事务中读到 current_revision=r+1（AC-019-04）。
   - 被拒绝的命令什么都不写，所以 PENDING 与 REJECTED 两个状态不用。
   - `config_json` 为 `{team, scheduler, source}`，其中 `source` 记录来源：命令，或文件及其 sha256。
4. **ConfigureTeam**
   - `bindings` 是对团队映射的合并补丁（RFC 7396）：`<role>: null` 删除职位，`<role>.<key>: null` 让该键回到默认值。合并后的整个团队再按决定 2 校验。
   - `run_id` 可以为 null，或是已存在的 Run；`scheduler` 仍按 CR-007（已有 Run 返回 409 RUN_CONFIG_FROZEN）。
   - 接受后返回 202，revision 为 r+1，写一条 run_id 为 null 的 `team.configured` 事件。幂等规则照旧：同 key 同 payload 重放原响应，同 key 不同 payload 返回 409 KEY_REUSE。
5. **错误**
   - kind 为 ConfigureTeam 时，payload 本身或其内部的 schema 校验失败（如 `apply_at=now`、缺 `apply_at`、payload 不是对象）与语义校验失败，都返回 400 INVALID_TEAM_CONFIG，键路径放在 `details.key_path`，message 取自同一个违例。payload 内部的违例，键路径是它在 payload 中的路径；payload 本身的违例，键路径是缺少的成员名（如 `apply_at`），其他情形为 `payload`（M2T07R-100、-151）。信封层面的违例（缺 idempotency_key 等）仍是 400 BAD_REQUEST（M2T07R-58）。
   - 过期的 `expected_revision` 返回 409 STALE_REVISION。
   - 这些错误体都带 `current_revision`，取团队 revision。
   - 判定顺序：解码 → 幂等 → 过期 → 合并与校验。带 scheduler 且指向已有 Run 的命令，也在幂等检查之后才以 409 RUN_CONFIG_FROZEN 拒绝（M2T07R-05）。KEY_REUSE 的 `current_revision` 同样取团队 revision（M2T07R-04）。
6. **文件归一为 ConfigureTeam**（REQ-018 行为 4）
   - host 启动时和每次 StartRun 时读一次文件。与最近一个来自文件的 revision 不同（按 sha256），就以内部 ConfigureTeam 走同一条存储路径：run_id 为 null，以当前 revision 为期望值，`command_id` 为 `config-file/<sha256>/<基准 revision>`，内容是文件给出的整个团队与调度参数（替换，不是合并补丁），来源记为文件及其 sha256。
   - 没有文件时以内置默认为准，来源记为 builtin：文件被删除后，下一次读取写出内置团队的 revision。只比较“最近一个来自文件或内置默认的 revision”，所以文件没变时，之后经 API 做的修改保持有效。
   - 两个读取同时写同一份文件时，命令 id 相同，后到的是重放；期间团队被别处改过（STALE_REVISION）就以新的基准重试，最多三次。
   - StartRun 在查幂等键之前读文件：文件变无效后，重发一个已接受的 StartRun 也会被拒绝，而不是重放（实现上的取舍）。
   - 文件无效时（解析失败、版本不符、坏键）：
     - StartRun 返回 400 INVALID_TEAM_CONFIG，details 带 `path`、`key_path`、`line`、`column`；
     - 写 `config.invalid` 事件，同一份文件内容只写一次（事件 id 含内容的 sha256）；
     - 上一个 revision 保持不变，host 继续服务（REQ-018 失败模式 5）。
   - 非团队键分两类：
     - 进程级的键（读者槽位、取消宽限、写队列容量、端口）在 host 启动时读取，修改后要重启 host 才生效。`execution.writer_slots`、`execution.reserve_supervisor_slot`、`delivery.max_delivery_attempts` 与 `web.host` 已校验，但还没有接线：writer 槽位与监督槽位仍是 REQ-037 的初值 1 与 true（M2-T08 接入），投递上限仍是 delivery 的初值 5（M2-T08 接入；更正，ADR-025 决定 9：`execution.reserve_supervisor_slot` 已由 M2-T08 的分配读取，host 把它放进 runner 的 Context；`delivery.max_delivery_attempts` 要等投递循环才有消费者，归 M2-T16；`writer_slots` 已校验为 1），host 只绑定回环地址（ADR-016），`web.host` 留给 M6 的 Web GUI（M2T07R-256）；
     - `project.default_mode` 由 TUI 读取（ADR-014 把它交给本任务，M2T07R-355）：顶栏的 mode 取项目配置文件中的值，文件无效或没有时为内置默认 AUTO。TUI 提交 StartRun 时使用它，随 M2-T13 接入。
     - 其余已校验、已载入但还没有产品代码读取的键，与接入它们的任务（M2T07R-355）：
       - `supervision.policy`：M2-T08（REQ-021 的 Commander 监督）；
       - `budget.max_local_repairs`：M2-T16 的 QA 返工循环（ADR-020 决定 10 的调用方）；
       - `budget.max_protocol_repairs`：同样随 M2-T16 接入。ADR-020 决定 10 写的“协议纠正随 M2-T07 接入”在此更正：本任务的执行器只把适配器的事实映射为结果，不读取 Agent 的报告，也就无从纠正其格式；读取 QA/Review 报告的是 M2-T16；
       - `project.document_profile`：M3-T03（REQ-029）；
       - `ui.view`、`ui.statusline`、`ui.mouse`：M4-T02 与 M4-T03。
       - `execution.profile` 只接受 `yolo-vm`，没有别的取值可读，产品代码不读它（M2T07R-455）。
     - `budget.*` 与调度参数在 StartRun 时读取（预算取自这次读到的文件，没有文件时为内置默认）。
     - host 启动时文件无效：进程级的键用内置默认，原因写入 `config.invalid` 事件，并写到拉起它的客户端的 stderr（这时 host 还没有把 stderr 移到 host.log，M2T07R-256）；团队仍是上一个 revision。
     - 文件的 revision 写不进去（存储失败，或三次尝试中团队都被别处改动）时，StartRun 不在旧团队上继续：存储失败按命令的存储错误回答，三次都被改动回 409 STALE_REVISION（可重试），都不建 Run（M2T07R-204）。三次都被改动这一支由 host 的测试钩子覆盖：钩子在读取团队 revision 与提交文件的 revision 之间改动团队（M2T07R-351、-454）。

### Run 内的绑定

7. **StartRun**
   - 在接受事务内，按当前 revision 为每个职位写 `role_bindings`：role_epoch=1，config_revision=r，ACTIVE。
   - 把调度参数写入 Run 的快照（CR-007 S2）。
   - 写入预算行（iterations、wall_seconds；设了 `max_usd` 时写 usd，price_known=0）和 `runs.deadline_at`（ADR-020 决定 7）。
8. **checkpoint**（第 2 版，第一轮审查 M2T07R-01、-02、-03、-50..52、-54 后的设计修正；第 3 版只改被拒的修改，第二轮审查 M2T07R-150）
   - 定义：某个 Run 的某个职位此刻没有 PREPARED、STARTING 或 RUNNING 的 Attempt，就处在它的 checkpoint（REQ-019 决定 3）。写租约属于 Attempt，所以这也覆盖了写者的安全点。
   - **修改只看配置**：一个职位是否被修改，只比较两份配置：绑定所在 revision 中的这个职位，和项目当前 revision 中的这个职位，包括它在两边是否存在；比较的内容是 agent、model、fallback、prompt、independent_session。绑定的可用性状态（BLOCKED_AUTH、注册表给的 AGENT_UNAVAILABLE 等）从不当作配置读取。第 1 版用状态推断修改与删除，把可用性阻塞误当成修改（M2T07R-01、-51）。
   - **未修改的职位**：不论有没有在途 Attempt，都直接推进到新 revision，epoch、状态、阻塞原因与会话都不变（M2T07R-03）。
   - **被修改的职位**：
     - 先看调用方传入的注册表结果（在 writer 之外探测，见决定 10）。新 Agent 不可用时，这次修改**被拒**：旧绑定、旧 epoch 与会话保留，并且照常派发，职位不空缺（REQ-019 决定 2、失败模式 3，M2T07R-52、-150）。第 2 版让被拒的职位仍算待生效、不派发，职位实际空缺。
     - 新 Agent 可用（或 host 没有注册表）时：
       - 有在途 Attempt 就等待。在此期间 rounds 与 decide 都不派发它，以免旧绑定再租出一个 Attempt；运行中的 Attempt 沿用旧绑定（AC-018-02）。
       - 没有在途 Attempt 就生效：更新绑定，role_epoch+1，config_revision=r+1，会话置空，写 `team.binding_applied`（带 from、to、config_revision）。
     - 被拒的修改在之后每个 checkpoint 都重新判定，不被放弃：Agent 一旦可用，职位重新待生效（不再派发），等在途 Attempt 结束后生效。判定的每次转向写一条事件，同一判定持续多少个 tick 都只写一条：转为被拒写 `team.binding_refused`（带原因与保留的绑定），被拒后转为可用写 `team.binding_pending`。职位是否待生效，取 (Run, 职位, revision) 最近一条判定事件，没有判定事件时为待生效。
     - 项目再改出新的 revision 时，从头判定：新 revision 若撤回了修改，职位直接推进；若仍指向不可用的 Agent，仍被拒。
     - projection 中，被拒的修改在 `pending.refused` 给出原因（AGENT_UNAVAILABLE），其余为 null。
   - **删除**：被删除的职位不删行。该行置为 BLOCKED（AGENT_UNAVAILABLE，`$defs.BlockedReason` 没有别的码），epoch+1，写 `team.binding_applied`（to 为 null）。删除由配置识别（绑定 revision 中有这个职位、当前 revision 中没有），不由阻塞原因识别。projection 的成员带 `removed: true`，以免与可用性阻塞混淆。同名职位再加回来时，旧 epoch 的持有者仍被隔离。
   - **尚未绑定会话的绑定**（StartRun 刚写的，或刚换绑的）：rounds 与 decide 不派发它的任务，pace 也不把这些任务判为能力缺失。它们照常等待，由绑定器（决定 9）写入会话与探测到的能力（M2T07R-50）。
   - **哪些 Run 做 checkpoint**：runner 每个 tick 先用读连接找出所有非终态、且 `runs.config_revision` 低于项目当前 revision 的 Run，不论它处于 RUNNING、PAUSED、BLOCKED 还是 CREATED。在 pace 与 rounds 之前，每个 Run 交给 writer 一个事务（M2T07R-02、-54）。所有职位都到达新 revision 后，再推进 `runs.config_revision`。
   - M2-T17 在同一事务中补交接包。
9. **会话**
   - 每个 (run, role, epoch) 一个 HoH 会话，id 由三者确定性派生。绑定时写入 `sessions`，带探测得到的 Agent 版本与能力，并设到 `role_bindings.session_id`。
   - `lease_task` 把绑定的会话、config_revision 和 role_epoch 写进 Attempt。
   - 会话的能力有 resume 时，按 `sessions.native_id` 续接原生会话；没有时，下一个 turn 新开一个原生会话（M2T07R-257）。这条对 Claude 与 Codex 才有区别。Pi 能用就一定有 resume：它的接口要求 `--session-id`（`pi::interface_missing`），探测因此总给出 resume。所以 Pi 的会话按 ADR-013 决定 1，每轮传同样的 `--session-dir` 与 `--session-id`，续接时核对会话文件（M2T07R-354）。修订（ADR-024 决定 4，M2-T17 第 5 至 8 轮，M2T17R-450、-500、-600、-700、-754）：上一句“按 `sessions.native_id` 续接”不再成立。现行规则：会话的能力有 resume 时，只续接该会话最近一条 `session.native` 事件给出的原生会话 id：这种事件只由结为 SETTLED 的 turn 在其结算事务里写出，读取时还须引用该会话一个已 SETTLED 的 Attempt；最近一个 SETTLED 的 turn 若没有写这条事件（Pi 的 `handled`、reconcile 判为完成），就续接更早一条（第 1 轮修正，M2T17FR-54）；该会话没有这样的事件时，每个 turn 新开原生会话（Pi 用同一个派生的 id 新起）。失败、取消、结果未知的 turn 不写这条事件，也不覆盖它；`sessions.native_id` 只是记录，不决定续接。理由：原生会话 id 早于任何输入就会出现（Pi 的 get_state、Codex 的 thread/start），第 6 轮之前失败的结算也会记下它，而 Pi 1.5.0 只在会话有了消息之后才写会话文件：续接一个从未落盘的会话会在启动前被拒（SESSION_NOT_FOUND，瞬时类），该职位就永远跑不了 turn。Pi 不续接时仍用同一派生 id，找到文件就接着用（M2T17R-501）。
   - 职位不同，会话 id 一定不同，reviewer、qa 和自定义职位都不会共用会话。进程退出不改变团队，也不改变会话（AC-018-03）。
10. **Agent 注册表与能力**
    - host 内只有一个注册表。它在 writer 之外（spawn_blocking）按 host 的 PATH 惰性探测各 Agent，并按启动器与实现文件的 (dev, ino, size, mtime) 缓存，文件变了就重新探测。
    - 职位需要的能力取 REQ-020 决定 1 中已有名字的部分：每个职位都要 structured_events，commander 与 reviewer 另要 resume；自定义职位继承它所引用的内置职位，没有引用时只要 structured_events。
    - Agent 不可用时，该职位为 BLOCKED（AGENT_UNAVAILABLE，带 missing）。绑定器每个 tick 都重新查看它阻塞的绑定（AGENT_UNAVAILABLE 且不是被删除的职位），Agent 可用时写入会话并恢复为 ACTIVE（M2T07R-155）。
    - 注册表有自己的任务：每个 tick 的间隔里，它查看 runner 需要的 Agent，按启动器与实现文件的身份缓存，没变就不重新探测。需要的 Agent 是项目当前团队的，加上未结束 Run 中每个绑定的（第三轮审查的设计修正，M2T07R-250：只看团队与等待会话的绑定时，被拒修改所保留的旧 Agent、重启前已绑定的 Agent 都不会被查看）。探测可能要几秒（例如 Codex 生成 schema），所以 tick 从不等探测：tick 只读注册表最近一次看到的结果，交给 checkpoint 与绑定器。这样被拒的修改在 Agent 可用后的下一个 tick 就重新判定（决定 8 第 3 版）。
    - 交给 checkpoint 的是三类：查看过且可用的、查看过且不可用的（带原因，被拒事件的 `detail` 即此原因，M2T07R-260），两类都不在的就是“未知”。未知按 checkpoint 自己读到的团队判断，所以 runner 读团队之后才到的修改也不会被当作可用（M2T07R-255）。指向未知 Agent 的修改等待，不写判定事件，职位暂不派发；绑定器也等它被查看后再给会话或阻塞。
    - 已有会话的绑定照常派发。执行器的 `deliver` 等到注册表查看过该 Agent 才确认（最多 60 s，没确认就由 runner 再交一次），所以 host 重启后、首次探测完成之前派发的 Attempt 不会因“未查看”而失败（M2T07R-250）。
    - host 停止时的探测命令（第 6 版，第八轮审查的设计修正，M2T07R-700、-750；这一类连续第三次，前几版见下）。原则：停止从不等任何探测线程；每条命令由停止方杀掉，停止方取不到某把锁时由持锁的探测线程杀掉；探测线程没有得到调度时留下的命令，在余项中逐条写明。
      - **共享的锁只有三处**，停止方都只“尝试”：停止句柄的命令表锁（启动方登记时持有），以及每个槽的锁（启动方放入子进程时持有，回收方取出子进程并发 SIGKILL 时持有）。停止方先置停止标志，再在一个共同期限（`STOP_WAIT`，200 ms，自停止开始算）之前每毫秒 try_lock 一次；到期仍被占着的锁就跳过，期限过后仍会取下空闲的锁。持锁只有几步，只有没被调度的线程才会占这么久。所以 `stop` 至多用 `STOP_WAIT` 加上它发出的信号就返回，与探测线程停在哪里无关（M2T07R-700：之前停止方阻塞地取槽锁，回收方的 kill 被 strace 延迟 8 s，停止就等了 7.7 s，而 runner 的 5 s 上限从停止返回后才开始计时）。
      - **登记先于启动，spawn 在锁外**。启动前，在命令表锁内查看停止标志（已停止就不启动），并登记一个空槽；spawn 在锁外，所以停止从不等 spawn，exec 卡住也不会拖住停止。
      - **放入与查看在同一次持有槽锁内**（`Started::new`，这一交接只有这一处）。spawn 返回后，启动方取一次槽锁，放入子进程，查看停止标志，已停止就向其进程组与领头进程发 SIGKILL，然后才放开锁。停止方在尝试任何锁之前就已置好标志，所以：停止方看到空槽，启动方随后在锁内必然看到标志并杀掉命令；停止方在启动方放开锁之后取到它，就看到子进程并发 SIGKILL（领头未回收，号仍是它的；`stop` 只发信号，不取出子进程）；停止方到期限仍取不到这把槽锁时，启动方的查看若在置标志之后，它在锁内杀掉命令，若在置标志之前（查看之后、放锁之前停住），命令留给探测在 capture 中的下一轮查看，即余项 (b)（M2T07R-800、-850）。正确性靠的是“一次持锁”加上“停止方先置标志、后试槽锁”（M2T07R-752：并不依赖锁内先放入、后查看的次序；在取槽锁之前就读停止标志才是错的）。
      - **回收**照旧由启动方完成：它在槽锁内取出子进程并无条件发 SIGKILL，再回收，所以停止方不会向已回收的号发信号，停止方取不到这把锁时命令也已由回收方杀掉。启动方在 capture 的循环里每轮（至多 10 ms）查看停止，看到就结束并回收命令，返回 STOPPING；离开进程组、仍占着输出管道的后代不会让它等到时限。
      - runner 停止时先调 `Registry::stop`（至多 `STOP_WAIT` 加信号），再等注册表任务结束，最多 5 s；`__host` 退出时另给阻塞线程 2 s。读取 Codex schema 的调用方在停止后最多再等工作线程一个清理宽限（2 s 加 0.5 s），让它删除临时目录，过了时限照旧报告目录可能留在何处。
      - **余项**（第 6 版，完整）：停止本身总是有界。一条探测命令只在下面的情形中活过停止，都需要某个探测线程在停止时没有得到调度（进程在 D 状态、被 ptrace 停住、长时间饥饿）：(a) 从 spawn 开始到启动方在槽锁内查看停止之前，pid 只有启动方知道（spawn 一直不返回也属此类，例如 exec 卡在无响应的文件系统上）；(b) 共同期限到时，启动方或回收方仍持着该槽锁，停止方跳过了它（后面的槽只剩期限的余下部分，不必独自被持满 200 ms）：回收方放锁前已杀掉命令；在置标志之后查看的启动方在锁内杀掉它；在置标志之前已查看的启动方不再查看，命令由该探测在 capture 的下一轮查看时杀掉；(c) 共同期限到时，另一个启动方仍持着命令表锁，停止方跳过了整张表、一条也没杀，表中各命令由各自的探测线程在 capture 的下一轮查看时杀掉（这里没被调度的是持表锁的启动方，命令活过停止则还需要各自的探测线程也没被调度）。线程再运行时会杀掉命令；host 先退出（停止后 5 s 加 2 s）时，这条命令（`--version`、`--help` 或生成 schema）会在 host 之后运行完，不受探测时限约束。M2-T14 让 host 在 systemd unit 中运行（KillMode=control-group）之后，host 退出时 systemd 会连同 host 的 cgroup 一起杀掉这些命令。
      - **验证方法**（这一类的修正方法）：列出停止方与探测线程共享的每一把锁，以及探测线程每一个可能停住的点，各设一个测试停顿，让停止发生在那里：停止在 `STOP_WAIT` 加余量之内返回，命令在线程再运行之后（或之前）已死。停顿点：登记时持命令表锁（`registering`）、spawn 中（`spawning`）、spawn 返回后放入之前（`spawned`）、放入时持槽锁（`putting`）、放开槽锁的那一刻（`placed`，由守卫的 Drop 在解锁后触发，所以提前放锁的写法会在查看之前停住，测试为红，M2T07R-751）、`start` 返回之后（`started`）、回收时持槽锁（`ending`）、放入时已查看而尚未放锁（`looked`：停止有界返回，命令由 capture 的下一轮查看杀掉，探测以 STOPPING 结束，M2T07R-800、-850）。持锁线程被放开之后，测试让它在下一个停顿点（`placed`）再停一次，在那里查看命令已死，所以断言的是持锁线程自己的 SIGKILL，而不是探测随后的查看（M2T07R-851）。另有测试让启动方持命令表锁几步，查看停止方在期限内取到锁后杀掉另一条已登记的命令；让一个启动方卡在 spawn 中，查看停止方仍能杀掉已登记的命令；让三个启动方都持着槽锁，查看停止只等一个共同期限（M2T07R-852）；让停止方试过一个启动方的空槽之后由它线程上的测试钩子停住（`slot-tried`，停止方尚未结束），再放开该启动方，查看它放入时看到了停止方最先置的标志；次序由两处停顿固定，不靠计时（M2T07R-950、-1001）。测试观察进程的约定（第十二轮的设计修正，这一类连续第三次：M2T07R-900、-1000、-1050、-1051）：列举 /proc 只用来证明进程存在，列举本身失败（打开时或遍历中）报错，单个读不了的条目跳过，名字按字节比较；按名字找命令时在有限时间内反复查看，直到看到为止；进程是否已结束只按它自己的进程号判定，已不在、号已归别的进程或为僵尸才算结束，任何读取失败都不算结束。同一模块的探测测试都按此观察，包括 `ended()` 与 M1-T07 测试中“没有条目留下”的检查（原来用 `Path::exists`，读取失败也会当作已消失）；测试失败时报出探测的返回值与本进程的所有子进程，罕见的失败可以据此区分。变异集 `m2t07-r8-fix-mutations` 到 `m2t07-r11-fix-mutations` 覆盖阻塞取锁、只试一次、每把锁各算期限、先取表再置标志（取不到表锁时）、试完各槽之后才置标志、放入后不查看或不杀、提前放锁与 capture 不查看。
      - 前几版：第 3 版只设一个标志，由运行命令的线程自己结束命令，`codex_schema` 不等工作线程就返回，工作线程被延迟时 host 先退出，schema 命令成了孤儿（M2T07R-300，审查用 ptrace 复现）。第 4 版让停止方自己杀掉已登记的命令，但把 spawn 放在停止句柄的锁内，exec 卡住时停止没有上限（M2T07R-450，审查用 strace 延迟 execve 复现）。第 5 版最初把“放入”与“查看”分开，停止方扫过空槽之后，启动方放入子进程、到它在 capture 中查看之前，命令一直活着（M2T07R-500，审查用两个测试钩子固定这一交错复现）；其修复仍把两步分在两次取锁中（M2T07R-600，审查用 ptrace 在两次取锁之间停住启动方 8 s 复现），第七轮改为一次持锁，并在启动方每个可能停住的点设测试停顿。第 5 版的停止方阻塞地取各把锁，持锁线程被延迟时停止跟着等（M2T07R-700、-750，审查用 strace 延迟回收方的 kill、用测试停顿停住持锁的启动方复现），第 6 版改为只尝试、有期限。这一类问题最早在 S6 自测中出现：探测放在 tick 内时，刚由 detach 启动的 host 在首次探测期间收到 SIGTERM，迟迟不退出（M2T07R-202）。
    - **测试观察进程的约定，第 2 版**（CI 可靠性分支的设计修正，2026-11-10；第 1 轮审查 CIR-001 至 -005、-050 至 -057 之后修订；第 2 轮审查 CIR-100 至 -103 之后再修订“进程是否已结束”“fork 出的副本”“只杀同一个进程”三条：-100、-101 与第 1 轮的 CIR-002 同类，是第二次，按 docs/19 先改定义再实现；第 3 轮的 CIR-200 是同一类的第三次：第 2 轮的定义（pidfd 可读）在非主线程 exec 时仍有瞬态，于是换了做法而不是再加一层判断，见下一条）。第 1 版（上一条末尾）只写给探测测试，这一类问题仍在别处再现：M2T07R-1150（`group_members` 把列不出的 /proc 当作空组，测试拿它当清理完成的证据）、-1151（`process_ended` 把任何读取失败当作已结束）、-1203（只把 Z 当作已结束，正在被回收的 X 读成还活着），以及 2026-11-10 CI 中的五次偶发失败：`setsid` 之前就读子进程的组；锁的描述符被别的测试线程 fork 出的子进程继承，drop 之后锁没有立即释放；用墙钟预算取消 future；claude 的 SIGINT 替身在取消 3 秒后信号记录仍为空（只观察到这一症状；原因未证实，推测是 bash 在处理 trap 的间隙丢了 INT，这里不当作已知原因）。第 2 版适用于仓库中观察进程、锁与取消的测试，并给出共用的实现：
      - **进程是否已结束**按观察者与进程的关系分三种情形判定（第 4 轮把原来的两种写清为三种，CIR-352），答案都来自内核而不是 stat 的状态字母（X 与 Z 只说明所读的那个 task：组长调用 `pthread_exit` 后其他线程还在跑时组长显示 Z，CIR-002；非主线程 exec 时内核的 `de_thread` 让它接替组长的号码与启动时间，同一次读取可能读到正在释放的旧组长，CIR-100）。（1）**本进程自己的、尚未回收的子进程**：用父进程自己的视图 `identity::child_ended(pid)`（`waitid(P_PID, WEXITED | WNOHANG | WNOWAIT)`，不回收它；只有退出、被信号杀死或 core dump 算结束：本进程跟踪的子进程的 ptrace 停止（`CLD_TRAPPED`）不算，CIR-300）。内核在 tasklist 锁下、且只在整个线程组都已退出后才把子进程的退出报告给父进程，所以线程 exec 的瞬态不会被读成结束；已回收或不是本进程的子进程时得到 ECHILD，是错误而不是“已结束”。（2）**由同一进程中别的代码回收的子进程**（被测代码的监督者、进程内的 host）：要看它是否已被回收，用在它尚未回收时打开的 pidfd（`identity::reaped_held`：fdinfo 不再显示进程号），不再看号码（CIR-201）；要看它是否已结束或还活着，用（3）的 `identity::ended` 加启动时间，受（3）的 exec 限制。（3）**不是本进程子进程的进程**，以及（2）中要看结束与否的：`identity::ended(pid, start)`：`pidfd_open` 得到“没有这个进程”就是已结束；给了 `start` 时在拿到 pidfd 之后读启动时间，不是记下的那个就说明原进程已结束（先核对身份，再看状态，CIR-101）；最后看 pidfd 是否可读（内核的 `pidfd_poll`）。这对只在主线程 exec（或从不 exec）的进程是准确的；非主线程 exec 时，Linux 不加锁的 `pidfd_poll` 仍可能读到旧组长而显得已结束（CIR-200：本机约 3.5 亿次查看中 9 次，审查者 500 万次中 3 次，`.hoh-dev/evidence/ci-reliability-r3-kernel/`），没有哪个非特权的查看能关上这个窗口。所以用（3）观察的对象必须只在主线程 exec 或从不 exec：仓库里用它观察的都是 sh、sleep、不带线程 exec 的 python 替身和 hoh 自己，一律满足。自己尚未回收的子进程一律用（1）（recovery 的信号记录替身、identity 的线程 exec 测试与 zombie 前提、process_substrate、claude_live 与 install 测试中的 zombie 前提，CIR-350）；探测测试的辅助函数、product.rs 的探测命令与 tui_pty 的 agent 是别的代码回收的子进程，用（3）。读启动时间以外的任何失败都是错误，从不当作结束。**进程是否已被回收**（连 zombie 也不是）由 `identity::reaped(pid)` 判定：`/proc/<pid>` 不在才算，其他读取失败是错误；不再用 `Path::exists` 的否定。
      - **组是否已空**只由内核的查找（`identity::group_empty`，`kill(-pgid, 0)` 为 ESRCH，zombie 也算在组里）判定；/proc 的扫描（`identity::group_left`）只用于诊断与失败消息，它失败就报错，从不当作空组；但扫描能证明存在：等一个组变空时，扫描找到一个尚未结束的成员就立即判为留下，不再等它自己结束，只有成员都已结束（等待回收的 zombie）或正在退出（有待处理的 SIGKILL，或 stat 标志中已有 `PF_EXITING`）时才继续等（CIR-153、-255）。`process::group_members` 这样把失败当作空的扫描不再使用。

        - CIR-601（第 7 轮）：“SIGTERM 立即发出”曾按文件的修改时间判断，替身写完证据之后的停顿会被算进去；改为写者自己的 `term` 记录。
        - CIR-802（第 9 轮）：组长在 SIGTERM 时请测试的 spawner 造出写者、然后等 SIGKILL 的那个场景（control.rs 的 `a_cancel_ends_a_writer_made_at_the_sigterm_with_only_the_attempts_marker`）断言写者的 `term` 记录减去它的 `established` 记录小于 2 s，但 `established` 写在解除阻塞 SIGTERM 之前，替身在两步之间停 3 s，正确的产品也会失败。改为在解除阻塞的前一刻另记 `unblocking <毫秒>`，量 `term` 减 `unblocking`：两端都在写者，中间只有解除阻塞与产品的信号（已挂起的 SIGTERM 在解除时立即送达）。对照：替身在 `established` 之后停 3 s 再解除阻塞，必须通过；产品把新找到的进程的 SIGTERM 推迟 3 s 的变异，必须失败。
        - product.rs `a_cancelled_run_stops_its_agent_by_its_native_cancel_then_sigterm_after_the_configured_grace`（M2-T13 分支的负载循环，60 次中 3 次）：它按替身收到两个信号的时刻量宽限，失败时为 872 至 894 ms；而 host 自己的记录（`cancel.native_cancel` 与 `cancel.sigterm` 的 `at_ms`）相隔 1002 至 1003 ms，替身在 host 记下原生中断之后 110 ms 才收到 INT。改为量这两条产品记录，界限照旧（900 ms 至 8 s）；替身只断言先 INT、后 TERM。对照：替身收到 INT 后先停 0.5 s 再记录，必须通过（原定的 3 s 做不到：原生宽限 1 s 加 TERM 宽限 1 s，替身在 2 s 处就被 SIGKILL 结束，来不及记录）；产品不等宽限就发 SIGTERM 的变异，必须失败。
        - 修订（2026-11-17，F 第 1 轮审查 CIRF-01）：所用的产品记录必须在该步骤发生时取得（发送返回之后），而不是在决定发送时；取消梯级原先在 `send()` 之前取时，慢的原生中断会吃掉宽限、慢的 SIGTERM 会被记早，这两种错都量不出来。已改为发送之后取时（ADR-021 决定 8c 的说明）；对照两个方向都有：原生中断慢过宽限，SIGTERM 仍在它之后整整一个宽限才发；SIGTERM 慢 9 s，记录与断言都看到它。
      - **依赖锁被释放的测试**显式解锁（`flock(LOCK_UN)`，对共享同一打开文件描述的任何副本都生效），或在自己的进程中持锁；不靠 drop：别的测试线程此刻 fork 出的子进程在 exec 之前持有描述符的副本，锁不会立即释放。测试保留一个 `try_clone` 的副本代替那样的子进程，使这一窗口每次都被走到。
      - **在 host 的异步线程上等待的钩子**：runner 的各个点由 tick 或 runner 在运行时的 worker 上同步调用；这样的钩子若要等 host 的其他任务做成某事（例如 registry 自己的循环看到 agent 已不在），在 `tokio::task::block_in_place` 中等，而不是直接阻塞这个 worker。直接阻塞时，若这个 worker 刚放下驱动运行时计时器的 driver、其余 worker 都停在条件变量上，就没有线程推进计时器：钩子等的事，以及测试自己基于计时器的等待，都要到钩子自己的界限才发生（product.rs 的 `a_turn_whose_agent_went_after_staffing_is_refused_before_it_starts`：负载下 517 次中 1 次，60 s 后失败；只给运行时一个 worker 时两个这样的测试每次都失败，改用 `block_in_place` 后都通过；证据见 `.hoh-dev/evidence/cirel2/staffing/`）。在 spawn_blocking 的线程上调用的钩子（`completing`、`reconciling`、`suite_ran`）不阻塞 worker，不受此限；只停固定时长、不等任何条件的钩子也不受此限。
      - **测试只在已知到达的点上取消 future**（由被测代码或替身发出信号），不用超时取消；超时只把挂起变成失败，每个等待都有这样的外层界限（CIR-005；原来的两处后续项 CIR-502 已关闭，见下文“适用范围与例外”）。等一个记录（例如替身记下收到的信号）时，在有限时间内反复查看直到出现，而不是 sleep 固定时长后读一次；界限取原测试所断言的时限（CIR-053）。
      - **适用范围与例外**。第 1 轮审查之后对全部测试做了一次清查（/proc 的列举与读取、`Path::exists` 的否定、按命令行的缺席证明、信号记录替身、显式解锁、取消点），第 2 轮之后补上第 1 轮漏掉的类别（进程结束的判定方式、“还活着”的断言、按裸号码发出的信号、trap 写法的信号记录替身、按命令行的所有扫描），第 3 轮之后再补（以状态字母判断的“还活着”、固定时长之后的缺席断言、只改变行为的 trap 替身是否断言了行为发生），结果记在 reports/reviews/M2.md 的“CI reliability”一节。原来的后续项 CIR-502（`until` 的同步 `query` 与 gate.rs 的 `wait_with_output` 等待子进程时没有自己的界限，挂住的子进程要靠套件自己的界限结束）已关闭：这两处与 src/gate/tests.rs 的同一种等待都改为 `output_within`，到界限时杀掉并回收自己的子进程，同时读完两个管道（`40949a9`）。已知的例外只有一处：`a_claim_whose_dispatcher_stopped_waiting_costs_no_delivery` 在 150 ms 后取消一个等写锁的 tick，产品代码没有“正在等锁”的事件可等；锁现在在取消之后才放开，所以慢的运行不会先让 tick 通过而误报失败，但 150 ms 内若 tick 还没把认领交给写线程，这一次运行就没有测到“等锁时被取消”的情形：产品若在这里有缺陷，这样的一次运行会漏掉它（不会误报失败）；普通的运行在 150 ms 内早已到达那里。清理代码（`Drop`、`kill_strays`）只做尽力的清理，不断言任何东西，可以把列不出的 /proc 当作没有可清理的。
    - 被停止中断的探测不是关于 Agent 的结论（M2T07R-352）：结果不写入注册表，该 Agent 保持上一次看到的结论，从未查看过的仍是未查看。否则 host 停止的那一刻，等待首次查看的派发可能把“停止”当作 Agent 不可用，Task 被持久阻塞为 BLOCKED_CAPABILITY。
    - 注册表的探测看得到安装、版本、能力与启动所需的事实，看不到认证：不跑一个 turn 就无法知道是否缺认证。缺认证由 turn 发现（Attempt 以 BLOCKED_AUTH 结束）。由此恢复绑定、在交接前按认证拒绝（REQ-019 失败模式 3 的“缺认证”）以及 fallback（REQ-020 行为 2、4），分别留给 M2-T17 与 M2-T15。
    - 绑定之后 Agent 才消失时，`start` 以 AGENT_UNAVAILABLE（能力类）拒绝，Task 成为 BLOCKED_CAPABILITY；会话能力无法得出（session_capabilities 失败）时，绑定器把绑定阻塞为 AGENT_UNAVAILABLE。精确的缺员码（REQ-020 行为 6）与这两种情形的分类留给 M2-T15（M2T07R-260）。
    - 兼容套件闸门（COMPAT_UNVERIFIED）留给 M2-T15。
11. **Prompt**
    - Prompt 由两部分组成：职位契约（内置的 `resources/prompts/<role>.md`，编译进二进制；或覆盖文件），加上任务头（Run 目标、任务 id 与标题、职位）。没有 prompt 的职位用自己的内置契约，`builtin:<role>` 用该内置职位的契约（`hoh_core::config::contract`）。
    - Prompt 记录随 Attempt 的结束提交写入（不在 STARTING 写，执行器不写 store）：一条 `prompt_revisions`（layer 为 builtin 或 project，含路径与 content_sha256，id 为 `<layer>/<role>/<sha256>/<路径>`：内容相同的两个文件是两个来源（M2T07R-205）），并设置 `attempts.prompt_revision`；`attempts.prompt_sha256` 是实际发出内容的 sha256（AC-018-05）。host 在 turn 结束前崩溃时，这个 Attempt 没有 Prompt 记录。
    - 覆盖文件在配置时就要校验：项目内的相对路径（不含 `..`），指向可读的普通文件；路径上的符号链接全部解析之后，文件仍须在解析后的项目根之内（文件加载与 ConfigureTeam 都查，不合格时按键路径拒绝，M2T07R-53、-101）。STARTING 时用同一个函数解析，再读取。STARTING 时文件丢失或读不了，Attempt 以 FAILED（PROMPT_UNAVAILABLE）结束，不退回内置契约。

### 产品执行器

12. **执行器端口**
    - 执行器不写 store。产品执行器的 `deliver` 在注册表查看过该 Agent 后确认（决定 10）；`start` 用注册表最近一次查看的结果准备 turn：读职位契约、拼任务头、按绑定的 model 与原生会话（续接）组装命令，经启动门 spawn。
    - `start` 拒绝时返回 `Refusal{reason, class, detail}`：reason 写入 `failure_reason`（产品的为原因码：PROMPT_UNAVAILABLE、AGENT_UNAVAILABLE、BLOCKED_CAPABILITY 等），class 决定重试，detail 记入 `attempt.start_refused` 事件。测试执行器的文字拒绝按瞬时类处理，与以前相同。
    - `Outcome` 带上事实：原生会话、resolved_model、usage、raw_log_path、诊断事件、失败码（作为 `failure_reason`）、类别、`group_gone`。这些都写在 runner 自己的结束提交中，写队列满也不会丢掉判定所需的事实；原生会话只在 Attempt 结为 SETTLED 时写（`session.native` 事件，决定 9 的修订）。
    - **适配器的终态完整保留**（第三轮审查的设计修正，M2T07R-200）：第一版把终态压成 success 布尔值，UNKNOWN_EFFECT（turn 开始了一个效果却没有报告结果就结束）被记成 FAILED 并按瞬时类重试，未知的外部效果会被重放。现在 `Outcome.unknown_effect` 与 `Ending.unknown_effect` 带上它：runner 不把工作效果记为 OBSERVED/COMMITTED（它保持 STARTED），仍先要求进程组清空与终结证明，然后把 Attempt 结束为 UNKNOWN_EFFECT。Task 原地不动，不安排重试，租约释放，并写一条 `runner.diagnostic`（code UNKNOWN_EFFECT，列出 STARTED 的 effect_key）。这与 ADR-019 决定 5 的 reconcile 处置一致；host 在其间崩溃，下次 reconcile 也得到同一结论。
    - **一条规则**（第五轮审查的设计修正，M2T07R-451，与 -301 同类第二次）：结束 Attempt 的每条路径（runner 的结束、取消的一轮、reconcile）对效果用同一条规则：结束时仍为 STARTED、没有观察到结果的效果，在结束 Attempt 的同一事务里记为 UNKNOWN；Attempt 的状态是取消优先（CANCELLED），其次有这样的效果就是 UNKNOWN_EFFECT，Task 不动，不计数，不重试。runner 的结束不再只看执行器报告的 `unknown_effect`，库中仍有 STARTED 效果也按未知处理（runner 观察到工作结束时，先把工作效果记为 OBSERVED 再 COMMITTED，所以正常结束不会留下 STARTED）。runner 与取消的一轮共用同一个函数把 STARTED 改为 UNKNOWN。诊断：runner 写 `runner.diagnostic`，取消的一轮写 `cancel.diagnostic`，reconcile 写 `reconcile.diagnostic`，都列出这些 effect_key（M2T07R-552）。条件：reconcile 与 settle 在记为 UNKNOWN 之前会问配置的观察者（Observer）；runner 的结束与取消的一轮不问。产品在 M2 用的是什么也确认不了的 NoObserver，两者结果相同；接入真正的观察者（例如 M6-T03 的 forge 查询）时，这两条路径也要先问它，记为该任务的后续项（M2T07R-552）。第 2 版只在取消时改效果，没有取消的未知效果由 runner 结束时留在 STARTED、由 reconcile 结束时记为 UNKNOWN（AC-041-05 要求 UNKNOWN），结局取决于崩溃发生在哪一刻。
    - **取消优先**（ADR-021 决定 8e，第四轮审查 M2T07R-301）：Attempt 带 `cancel_requested` 时，runner 的结束与 reconcile 的处置得出同一结果：Attempt 为 CANCELLED，其未观察到的 STARTED 效果记为 UNKNOWN，Task 不动（由取消的最终事务处理），不计数，不重试；有效果记为 UNKNOWN 时，照样写一条诊断（runner 写 `runner.diagnostic`，reconcile 写 `reconcile.diagnostic`），列出这些 effect_key。之前 runner 的结束把 Attempt 记为 CANCELLED，却把效果留在 STARTED；reconcile 的取消优先只覆盖 FAILED 与 SETTLED，漏了 UNKNOWN_EFFECT。两条路径的结果因此取决于崩溃发生在哪一刻。
    - 一个事件只有一个写出者：降级的 `adapter.degraded` 由适配器写入 recorded，执行器不再补一条（M2T07R-201：同一 key 两次，结束提交违反唯一约束而回滚）。
    - 原始日志在 `.hoh/attempts/<attempt id>/`，Pi 的会话目录在 `.hoh/sessions/<session id>/`（id 中的 `%` 与 `/` 转义）。新 Pi 会话的 `--session-id` 是 HoH 会话 id 的 sha256 摘要，排成 UUID 形状，同一会话每次都相同；之后的 turn 用记录下来的原生 id 续接（只有结为 SETTLED 的 turn 才以 `session.native` 事件记下它，见决定 9 的修订，M2T17R-500、-600）。
    - 原生取消：`Executor::cancel` 通知正在运行的 turn（Claude、Codex exec 发 SIGINT，App Server 发 turn/interrupt，Pi 发 abort）；适配器自己的升级宽限取 execution 的 cancel_native_grace_seconds 与 cancel_term_grace_seconds。
13. **启动门**
    - Agent 进程不经 shell 启动（REQ-024/025 行为 1），改为由隐藏入口 `hoh __gate <program> <args…>` 先行启动：它从 stdin 逐字节读到 LF；读到 `go` 时以 `exec` 换成目标程序，pid、进程组、环境（含 `HOH_ATTEMPT_ID`）与 cgroup 都不变；EOF 或读到其他内容则以 0 退出。
    - exec 之前，信号处置与屏蔽恢复为默认（M2T07R-203：std 的 exec 不会恢复被忽略的信号，也不清屏蔽集；而 shell 的后台任务与 nohup 会让 host 继承被忽略的 SIGINT/SIGHUP，Agent 就听不到原生取消）。工作区禁止 unsafe，所以做法是：对 1..31 中 signal-hook 允许的每个信号设一个处理器（exec 会把有处理器的信号恢复为默认，被忽略的则不会），再用 nix 的 `pthread_sigmask` 清空屏蔽集（nix 0.31.3，MIT）。SIGKILL、SIGSTOP 没有别的处置；SIGILL、SIGFPE、SIGSEGV 不能经 signal-hook 设处理器，保持继承（启动 host 的进程不会忽略它们）。
    - runner 收养的是阻塞在 read 中的 `__gate` 的 pid，然后记身份与 tracking，再开门，与 ADR-021 决定 8d 的顺序相同。
    - 产品用 `current_exe()` 作为门程序，测试传入 `CARGO_BIN_EXE_hoh`。
14. **适配器的 runner 模式**
    - 三个适配器各增加一种模式，分三步：准备（argv、日志、检查）→ 经调用方给的门命令 spawn → 在执行器拥有的任务中驱动（等到开门才写协议字节）。
    - 这种模式下适配器不迁移 Attempt 状态，只交回事实（决定 12）。
    - 现有的 `run()` 留给 `doctor --live` 与适配器测试使用，行为不变。
    - host 的取消阶梯为准：`Executor::cancel` 只发原生取消（Claude 发 SIGINT，Codex app-server 用 turn/interrupt、exec 发 SIGINT，Pi 发 abort）。适配器只在自己的判定（帧过大、协议失败）上升级信号。
    - runner 模式下 turn 不设 deadline。
    - Claude 的 Launch 增加 `--model`：help 有这个参数才用，没有则 BLOCKED_CAPABILITY。
    - runner 的事实中不带 `cost_usd`，Claude 自报的估算放进 usage 的 `reported_cost_usd`（ADR-020，M2T07R-256）。
15. **Codex 的传输方式**
    - 每个 Attempt 在启动前按注册表定下传输方式。
    - app-server 在 initialize 时返回方法不存在或握手超时，这个 Attempt 以 FAILED 结束（CAPABILITY_UNSUPPORTED，瞬时类），记录 `adapter.degraded` 事件，执行器把这个实现（启动器路径与版本）标为 exec，下一个 Attempt 走 exec（REQ-024 失败模式 4：降级为 exec 并记录原因）。版本变了（升级）就重新尝试 app-server。
    - exec 也不可用时为 BLOCKED_CAPABILITY。
    - 不在同一个 Attempt 内另起第二个进程，以免绕开启动门与终结证明。
16. **失败类别映射**（ADR-020 决定 1）：
    - BLOCKED_AUTH → Auth；
    - BLOCKED_CAPABILITY、MODEL_UNAVAILABLE → Capability；
    - TRANSIENT_EXTERNAL → Transient；适配器目前不解析 Retry-After，按不带等待的瞬时类重试（M2T07R-256，记入后续项：在 M2-T11 之前补上）；
    - 其余 → Transient（不带等待）。
    - **设计修正（提供方重置，2026-11-16，M2T07R-256 复审）。** 复审第 1、2 轮在同四类问题上各连续两次发现缺陷（RA-01/-100 归属，RA-02/-101 监督的重试，RA-03/-102 恢复，RA-04/-103 证据的清除），不再逐条修补，改以下四条规则为准，代码按它们改：
      1. **归属。** 只有确认失败的限额适用于这个 turn 时才用它的重置；归属不明（缺 `normalModelSlug`、稀疏或不全的快照、不止一个候选）就没有重置，按 full jitter。codex 的快照按 limitId 跨多次 `account/rateLimits/updated` 合并（稀疏更新留空或给 null 的字段不清除旧值）。账户级的证明：limitId 为 `codex`（录制中账户自己的配额就是这个 id：codex/0.166.0/app-server-turn 的真实账户、`_provider-faults` 中由 `x-codex-primary-*` 头得到的快照）且从未报过 `normalModelSlug`；模型级的证明：合并后的 `normalModelSlug` 等于 thread 的模型（thread/start 或 thread/resume 的答复）。别的模型的配额无关。用满（usedPercent ≥ 100）的配额里只要有一个归属不明，或适用的不止一个，就没有重置；唯一适用的那个，取它用满窗口的最晚 `resetsAt`，有一个用满窗口没有可用时刻也没有。Claude：类型字段 `usage_limit_reached` 的 `rate_limit_info` 是该次拒绝自己的记录，归属已定；退路 `rate_limit_event` 只在本 turn 主线程失败、且下文第 4 条未清除时用。
      2. **重试预算。** 等配额重置与别的瞬时失败用同一个持久预算，对每个职位都一样：首次失败之后至多重试 `MAX_RETRIES`（8）次（REQ-042 行为 3），按库中记录计数，重启不清。普通 Task 照旧（第 9 次失败 → BLOCKED 与 need_decision）。监督路径（ADR-025 决定 3、5）：唤醒在当前 epoch 下的失败数（含半开试探 `supervisor.probe` 的失败）达到 `MAX_RETRIES` 时 Commander 不可用（`failures_capped`，Run BLOCKED），这一点不变；改变的是半开试探只在该唤醒还剩重试时分配：失败数为 `MAX_RETRIES` 时还可试探一次（第 9 个 turn），失败数超过 `MAX_RETRIES` 的唤醒在这个 epoch 里不再分配，试探也不分配，Run 保持 BLOCKED，等决策：换 Commander 的 epoch（ConfigureTeam、交接）。ADR-025 其余的试探规则（冷却、选最老的封顶唤醒、成功后立即可再试、Auth/Capability 的恢复事实）不变；Auth/Capability 的试探也计入同一个唤醒的失败数，所以同样有界。
      3. **恢复。** OBSERVED 记下的绝对 `retry_at` 是每条恢复路径上唯一的依据：OBSERVED 未 COMMITTED、已 COMMITTED、恢复时重置已过去，都不以“恢复时刻加一段时长”重建。恢复按所用的失败时刻把 `retry_at` 重新换成等待（`with_reset`），所以 Task 与监督唤醒都在 `retry_at` 到期；恢复时它已过去，则等待为零、立即到期（这次等待已经过完，不再 jitter，也不再等一遍）。生命周期与预算用的保守结束时刻（未 COMMITTED 时取恢复时刻）与重试排期分开。
      4. **证据的范围。** 重置的证据只由能证明同一限额已解除的成功清除：同一线程（主线程与子 Agent 以 `parent_tool_use_id` 区分）且同一限额或模型。Claude 的 rejected `rate_limit_event`：`rateLimitType` 为账户级（`five_hour`、`seven_day`、`overage`、`seven_day_overage_included`）时，主线程任何一条成功的 assistant 消息都清除它；为模型级（如 `seven_day_opus`）或未知时，只有模型与记下该证据时主线程模型相同的主线程成功才清除。子 Agent 的成功从不清除主线程的证据。
17. **host**
    - `HostConfig::new` 仍不带 runner，供现有测试使用。新增 `HostConfig::product(project, config, gate, path)`，`__host` 使用它：带产品执行器（门程序为 `current_exe()`）、按 host 的 PATH 查找 Agent 的注册表，以及进程级配置（端口、写队列容量、读者槽位、取消宽限）。尚未接线的键见决定 6。
    - 取消宽限接到 host 的每一级（M2T07R-254）：CancelRun 的阶梯（`HostConfig.cancel`，原生 → SIGTERM → SIGKILL）、租约到期收尾在原生取消之后的等待（`ReconcileSettings.native_grace`），以及适配器自己的升级。初值仍为 REQ-043 决定 1 的 10/5 s。收尾只在确实发了原生取消（执行器手里还有这个 Attempt 的 turn）时等 native_grace；没有发时，照旧等 SIGTERM 的宽限（M2T07R-353）。“发了”取自执行器的回答：`Executor::cancel` 返回它是否通知了一个仍持有的 turn，收尾的等待与 `native_cancel` 一步的 `sent` 都用它；执行器已不持有这次 turn（例如 executor_lost 的两条路径）时为 false（M2T07R-453）。CancelRun 的原生一步同样用这个回答：只有回答为 true 才记为已发送（`cancel.native_cancel`），阶梯的时刻照旧推进（ADR-021 决定 8c，M2T07R-501）。
    - host 停止时，产品的 Agent 进程不保证继续运行：它们的管道随 host 关闭，适配器读不到输出，Agent 可能因 EOF 或 SIGPIPE 结束，也可能继续运行。两种情况都由下次启动的 reconcile 按 ADR-019 与 ADR-021 决定 8d 处置：先证明进程组与 cgroup 已空，才结束 Attempt（STARTED 且没有观察到结果时为 UNKNOWN_EFFECT）。这里不用 PR_SET_PDEATHSIG（M2T07R-59）。
18. **可观察性**
    - `GET /v1/runs/{id}` 的 projection 增加 `team`（按 commander、cto、developer、qa、researcher、reviewer 排序，自定义职位按字母序排在后面，每项含 agent、model、role_epoch、config_revision、session_id、state、pending）和 `team_revision`。
    - 新增 `GET /v1/runs/{id}/team`，按 openapi 的 limit（1..500，默认 100）与 cursor 分页，cursor 是上一页最后一个职位，非法参数与 list_runs 一样回 404（M2T07R-06、-57）。
    - 帧过大的诊断仍用 `adapter.diagnostic` 事件，另写入 `<raw_log_path>/diagnostics.jsonl`；事件带 `reader_max_buffered`（读取器最多缓冲的字节数，AC-027-03 的测试探针）。

## 决定 19：不活动看门狗（2026-11-16，REQ-042 行为 8）

REQ-042 行为 8 要求 wall deadline 与 inactivity watchdog 分别计时、无输出而工具进程仍在运行不判为死机（docs/13“进程与终结”同）。此前只有 hoh-agents process.rs:17 的注释，没有实现，也没有 AC 覆盖（M2-T11 预研发现的范围缺口）。放在本 ADR：它管 runner 驱动一次 Attempt 的进程（决定 12–17）——看门狗读的原始日志（决定 12）、runner 模式下 turn 不设 deadline（决定 14）都在这里；ADR-019 管崩溃之后的 reconcile 与 effect ledger，不管在跑的 Attempt；ADR-021 决定 8d 的进程追踪与决定 7 的暂停、取消只被读，不改。

1. **位置**：runner 的 `attempt()` 在开门之后等待结束的循环里，每个 Attempt 一个看门狗，只在这个 host 运行它时存在。不改 hoh-agents 与适配器：那里的源码进兼容套件集摘要，改动会让已记录的 PASS 全部待验证（ADR-030 决定 10）。
2. **两个时钟分开**：runner 模式下 turn 不设 deadline（决定 14），wall 的后备是 Run 的 `deadline_at`、`max_duration_hours`（REQ-042 行为 6，由 pace 处理）与 hoh-agents `run()` 的 deadline（doctor --live、适配器测试）。看门狗用自己的单调时钟，不读不改它们，不碰租约（租约照旧每 30 s 续）。
3. **度量**：自该 Attempt 最后一次输出以来的时间。输出 = 执行器为这个 turn 保存的原始 stdout、stderr 副本的总字节数增长：hoh-agents 的进程子层在数据到达时不经缓冲写入它们（process.rs 的 Tee 与 stderr drain），适配器的帧与事件都来自其中。执行器端口加 `Executor::output_bytes(work)`（缺省 None）；产品执行器对 `.hoh/attempts/<id>/` 中的 `*stdout.jsonl` 与 `*stderr.log` 求和（ADR-031 决定 11 的 stderr 转发按同一命名找文件）。读不到为“判不了”，按有输出处理，不报。比较的是两次观察之间的大小，按单调时钟，不用会随墙钟跳的 mtime。
4. **工具进程**：该 Attempt 中 leader（已记录的 pid 与 start time）之外仍在运行的进程：/proc 中 leader 的后代（父链），以及环境里带 `HOH_ATTEMPT_ID=<marker>` 的进程（决定 8d 的同一标记，覆盖离开进程组、cgroup 或被重新收养的工具）；僵尸不算。只读：不 pin、不发信号。有不能读的进程而没有找到工具时为“判不了”，按有工具处理。cgroup 模式也走 /proc：cgroup 外的标记进程反正要扫，一条路径更简单。
5. **判定**：最后活动 = 最近一次看到输出增长、最近一次看到工具进程，两者取晚。`now − 最后活动 ≥ N` 即不活动：N 之内既没有输出，每次看也没有工具进程。工具结束之后的静默从它最后一次被看到时起算，所以“刚跑完 9 分钟测试”不会马上报。**N = 15 分钟，每 15 s 看一次**。理由：产品的 claude 不带 partial messages（agents.rs 的 Launch 为 `partial: false`），一条助手消息是一帧，长思考加长回答可以几分钟没有输出（32k token 的输出按约 50 token/s 约 11 分钟）；codex app-server 与 pi 流式输出增量。15 分钟高于健康 turn 不跑工具时的最长静默，误报的代价只是一条事件。N 与间隔是 host 的常量（`HostConfig::watchdog`，测试缩短），**不是配置键**：不新增 REQ-018 的配置项；要让用户调整时另写 CR。
6. **动作**：从不终止、不发信号，不改 Attempt、Task、Run 的状态，不计失败，不触发重试。每个不活动段写一条 `attempt.inactive{attempt_id, episode, since_ms, quiet_ms, tool_running: false}`（since_ms：自最后一次输出的毫秒；quiet_ms：N），同一段内不再写；之后第一次看到输出增长时写 `attempt.inactive_cleared{attempt_id, episode, inactive_ms}`（inactive_ms：从 inactive 到看到输出），这一段结束，再静默 N 才有下一段（episode + 1）。Attempt 的结束（进程结束、取消、host 停止）也结束这一段，不另写 cleared——最后的输出与 turn 的结束落在两次观察之间时也是如此——所以一段的终点是它的 cleared 或它的 Attempt 的结束。事件 id 为 `child_id(attempt, "watchdog/<episode>/inactive")` 与 `…/cleared`。段中出现工具进程不结束这一段（CLI 运行工具之前会先输出工具调用）。写入意图为缺省的 Progress：处于 G 的 Run 没有未结束的 Attempt（G 只在安静时进入，ADR-031 更正 D），竞态下得到 Held 时这个 Attempt 不再记录；其他写入失败写 host 的 stderr，段不打开，下一次再写。
7. **不唤醒 Commander，不喂停滞探测器**：REQ-021 行为 1 的唤醒集合受锁，`attempt.inactive` 不在其中，也不在 `supervise::KINDS`；它是行为 2 那一类遥测（心跳、工具输出）。集合中的 no_progress 由 M3-T04 产生，而静默不等于没有进展（长测试、长思考）。ADR-031 更正 C 的停滞谓词 (a) 要求没有未结束的 Attempt：在跑的 Attempt 即使不活动也不是停滞，把它算作停滞就是判死，与行为 8 相违。留给 M3-T04：no_progress 的定义若要用到 Attempt 的静默，可以读这些事件，在锁定的集合之内，不需要 CR。本决定不改任何受锁文本。
8. **用户看得到**：事件经 GetEvents、`hoh attach` 与 `-p` 的跟随可见（stream-json 原样输出；text 模式与 TUI 显示 `#seq attempt.inactive`）。Run 的 projection 不加字段：openapi 受锁，事件已足够；要状态字段时另写 CR。
9. **重启**：状态只在内存。host 停止或被 kill -9 之后，新的 host 不接管上一个 host 的 Attempt（决定 17：启动 reconcile 证明进程已空之后结束它们），所以没有要恢复的看门狗：没有清除的段随它的 Attempt 结束而结束，新的 host 不补写 cleared，也不为它开新段。每个新 Attempt 从开门起重新计时。
10. **代价**：每 15 s 一次，在阻塞线程上：列出 Attempt 目录、stat 其中几个文件；只在两次观察之间没有输出时扫一次 /proc（每个进程读 stat，找不到后代时再读 environ），段打开期间与输出流动时都不扫。没有忙轮询；每段至多两条事件。
11. **暂停、等待与取消**：PAUSE_REQUESTED 时在跑的 Attempt 不收信号（ADR-021 决定 7），看门狗照常；PAUSED 时没有在跑的 Attempt。WAITING_EXTERNAL 是 Run 级的，看门狗按 Attempt 计、不看 Run 的状态，等待重试的 Task 没有在跑的 Attempt。取消先移除并中止 runner 的 attempt 任务（control.rs 的 `cancel`），看门狗随之停止，不在取消的宽限里记录；其他结束这个任务的路径也一样。验证者的 Attempt 同样看守：它的检查请求由它的 helper 进程等待，算工具进程。
12. **已知局限**：Agent 常驻的子进程（例如以 stdio 运行的 MCP server）算工具进程，这样的 turn 不会被报为不活动——宁可漏报，不误判死机（行为 8）。看门狗也分不出 Agent 在网络上等待与卡住：两者都是“没有输出、没有工具”，所以它只记事实。

测试（先红后绿）：计时器的单元测试（输出、工具、判不了、每段一次、清除后的新段）；/proc 的工具判定用测试自己的进程树（后代、标记、僵尸、不能读）；产品测试用假 claude：有子进程“工具”时静默超过 N 不写事件，工具结束后静默 N 写一条，再输出则清除，Attempt 不因此结束；重启测试：一段打开时 host 停止，新的 host 结束该 Attempt，不补写也不重复。

修正（2026-11-17，审查第 1 轮 WD-01、WD-52，生命周期）：一次观察（阻塞线程上的采样，以及之后的记录）是该 Attempt 的一个在途操作，和它的结束、它的请求一起轮询，从不在 `select!` 分支体里把它们挡住。Attempt 结束时，未完成的观察随之丢弃，不再提交任何东西。记录经 `Store::runner_watched` 在一个事务里写入，只在 Attempt 仍为 RUNNING、本身没有 cancel_requested、所属 Run 不在 CANCEL_REQUESTED 或 CANCELLED 时写；否则什么也不写，看门狗不再看这个 Attempt。所以已入队的记录也不会落在 Attempt 结束之后，或取消开始之后（第 11 条）。

修正（2026-11-17，审查第 1 轮 WD-02、WD-03，第 4 条的三态）：判断工具进程时，进程的任一线程在运行，这个进程就在运行。`stat` 为 Z 只说明主线程结束了，其余线程可能还在跑工具，所以要读 `/proc/<pid>/task` 中各线程的状态；读不到时为判不了。标记先读进程的 environ，读不到或主线程已结束时读各线程的；都读不到时，只有能证明它与这个 Attempt 无关才不算：它在 leader 之前启动（这个 Attempt 的进程都是 leader 的后代），或它的真实用户不是 host 的用户（set-user-id 的工具保留真实用户）。否则为判不了，按有工具处理。例如同一用户、设了 PR_SET_DUMPABLE=0 的进程是判不了，不是没有。在 leader 之前启动的进程一律不看，扫描也因此便宜。
