# ADR-022 · 团队配置、角色绑定、role_epoch 与产品执行器

状态：采纳（M2-T07，随任务分步补全）

## 背景

M2-T07 的验收是 REQ-018 的全部 AC（AC-018-01..05）和 AC-027-03。done_when 另有两项要求（CR-008）：

- 执行循环经角色绑定，以产品执行器运行三个适配器，适配器进程经启动门启动（ADR-019 决定 8）；
- TEST-027-03 在 host 内重测。

本任务开始时（main d5ae06a）的情况：

- **配置与团队**：没有配置加载器；产品代码不写 `role_bindings`、`team_revisions`、`budgets`，也不在首个 turn 之前写 `sessions`，测试都用 SQL 预置。
- **ConfigureTeam**：只有 `scheduler` 一项有实现，其余一律返回 422。
- **host**：`HostConfig::new` 没有 runner，`__host` 用的就是它。
- **适配器**：三个适配器自己迁移 Attempt 状态，并且不经启动门直接 spawn。
- **runner 的端口**：`Work`、`Executor`、`Outcome` 不带 Agent、模型、会话或 Prompt。

设计草稿的事实核对和 19 个问题的取舍，留在开发证据 `.hoh-dev/evidence/m2t07-prep/` 中。

## 决定

### 配置

1. **配置文件**
   - 项目配置在 `<project>/.hoh/config.toml`，叠在内置默认之上；没有用户级全局层。文件不存在时就是内置默认。
   - 内置默认与 `config/hoh.example.toml` 逐键相等（AC-018-01）。
   - 相对的 `prompt` 路径以项目根为基准。
2. **解析与校验**：用 `toml` 1.x 带位置解析，由 `hoh_core::config` 统一校验，文件与 ConfigureTeam 走同一套规则。
   - **未知键**：REQ-018 决定 6 键表之外的键，在任何层级都拒绝，并给出键路径和行列。
   - **取值范围**：
     - `config_version` 必须是 `"1.0"`；
     - `execution.writer_slots` 必须为 1（REQ-037）；
     - `scheduler.*` 的范围同 SchedulerSettings；
     - `web.host` 只能是回环地址；
     - 枚举值：`default_mode`、`document_profile`（REQ-029）、`execution.profile`（只有 `yolo-vm`）、`supervision.policy`、`ui.view`；`ui.statusline` 暂只有 `standard`，M4 扩充。
   - **职位**：
     - Agent 只能是 codex、claude 或 pi，fallback 是互不相同的 Agent，且不含该职位自己的 Agent（M2T07R-60）；
     - `model` 为空表示用底座的默认模型；
     - `reviewer.independent_session` 不能为 false（CONTRACT 7）；
     - 自定义职位名为小写字母开头，最多 64 个字符，只含小写字母、数字和 `_`，必须有 Agent，并给出 prompt 覆盖文件或 `builtin:<内置职位>`（REQ-018 决定 5）。
   - 任何拒绝都不改用默认值，也不忽略出错的键。

### 团队 revision 与 ConfigureTeam

3. **团队 revision 按项目编号**
   - revision 0 就是内置默认，由第一个团队事务补写，不产生事件。
   - 接受 ConfigureTeam 时，在接受事务内写入 r+1 并直接标为 APPLIED，它就是项目当前的配置。`expected_revision` 与最新的 APPLIED revision 比较（与 SQL 注释一致）。并发请求中输掉的一方在同一事务中读到 current_revision=r+1（AC-019-04）。
   - 被拒绝的命令什么都不写，所以 PENDING 与 REJECTED 两个状态不用。
   - `config_json` 为 `{team, scheduler, source}`，其中 `source` 记录来源：命令，或文件及其 sha256。
4. **ConfigureTeam**
   - `bindings` 是对团队映射的合并补丁（RFC 7396）：`<role>: null` 删除职位，`<role>.<key>: null` 让该键回到默认值。合并后的整个团队再按决定 2 校验。
   - `run_id` 可以为 null，或是已存在的 Run；`scheduler` 仍按 CR-007（已有 Run 返回 409 RUN_CONFIG_FROZEN）。
   - 接受后返回 202，revision 为 r+1，写一条 run_id 为 null 的 `team.configured` 事件。幂等规则照旧：同 key 同 payload 重放原响应，同 key 不同 payload 返回 409 KEY_REUSE。
5. **错误**
   - kind 为 ConfigureTeam 时，payload 本身或其内部的 schema 校验失败（如 `apply_at=now`、缺 `apply_at`、payload 不是对象）与语义校验失败，都返回 400 INVALID_TEAM_CONFIG，键路径放在 `details.key_path`，message 取自同一个违例。payload 内部的违例，键路径是它在 payload 中的路径；payload 本身的违例，键路径是缺少的成员名（如 `apply_at`），其他情形为 `payload`（M2T07R-100、-151）。信封层面的违例（缺 idempotency_key 等）仍是 400 BAD_REQUEST（M2T07R-58）。
   - 过期的 `expected_revision` 返回 409 STALE_REVISION。
   - 这些错误体都带 `current_revision`，取团队 revision。
   - 判定顺序：解码 → 幂等 → 过期 → 合并与校验。带 scheduler 且指向已有 Run 的命令，也在幂等检查之后才以 409 RUN_CONFIG_FROZEN 拒绝（M2T07R-05）。KEY_REUSE 的 `current_revision` 同样取团队 revision（M2T07R-04）。
6. **文件归一为 ConfigureTeam**（REQ-018 行为 4）
   - host 启动时和每次 StartRun 时读一次文件。与最近一个来自文件的 revision 不同（按 sha256），就以内部 ConfigureTeam 走同一条存储路径：run_id 为 null，以当前 revision 为期望值，`command_id` 为 `config-file/<sha256>/<基准 revision>`，内容是文件给出的整个团队与调度参数（替换，不是合并补丁），来源记为文件及其 sha256。
   - 没有文件时以内置默认为准，来源记为 builtin：文件被删除后，下一次读取写出内置团队的 revision。只比较“最近一个来自文件或内置默认的 revision”，所以文件没变时，之后经 API 做的修改保持有效。
   - 两个读取同时写同一份文件时，命令 id 相同，后到的是重放；期间团队被别处改过（STALE_REVISION）就以新的基准重试，最多三次。
   - StartRun 在查幂等键之前读文件：文件变无效后，重发一个已接受的 StartRun 也会被拒绝，而不是重放（实现上的取舍）。
   - 文件无效时（解析失败、版本不符、坏键）：
     - StartRun 返回 400 INVALID_TEAM_CONFIG，details 带 `path`、`key_path`、`line`、`column`；
     - 写 `config.invalid` 事件，同一份文件内容只写一次（事件 id 含内容的 sha256）；
     - 上一个 revision 保持不变，host 继续服务（REQ-018 失败模式 5）。
   - 非团队键分两类：
     - 进程级的键（读者槽位、取消宽限、写队列容量、端口）在 host 启动时读取，修改后要重启 host 才生效。`execution.writer_slots`、`execution.reserve_supervisor_slot`、`delivery.max_delivery_attempts` 与 `web.host` 已校验，但还没有接线：writer 槽位与监督槽位仍是 REQ-037 的初值 1 与 true（M2-T08 接入），投递上限仍是 delivery 的初值 5（M2-T08 接入），host 只绑定回环地址（ADR-016），`web.host` 留给 M6 的 Web GUI（M2T07R-256）；
     - `project.default_mode` 由 TUI 读取（ADR-014 把它交给本任务，M2T07R-355）：顶栏的 mode 取项目配置文件中的值，文件无效或没有时为内置默认 AUTO。TUI 提交 StartRun 时使用它，随 M2-T13 接入。
     - 其余已校验、已载入但还没有产品代码读取的键，与接入它们的任务（M2T07R-355）：
       - `supervision.policy`：M2-T08（REQ-021 的 Commander 监督）；
       - `budget.max_local_repairs`：M2-T16 的 QA 返工循环（ADR-020 决定 10 的调用方）；
       - `budget.max_protocol_repairs`：同样随 M2-T16 接入。ADR-020 决定 10 写的“协议纠正随 M2-T07 接入”在此更正：本任务的执行器只把适配器的事实映射为结果，不读取 Agent 的报告，也就无从纠正其格式；读取 QA/Review 报告的是 M2-T16；
       - `project.document_profile`：M3-T03（REQ-029）；
       - `ui.view`、`ui.statusline`、`ui.mouse`：M4-T02 与 M4-T03。
     - `budget.*` 与调度参数在 StartRun 时读取（预算取自这次读到的文件，没有文件时为内置默认）。
     - host 启动时文件无效：进程级的键用内置默认，原因写入 `config.invalid` 事件，并写到拉起它的客户端的 stderr（这时 host 还没有把 stderr 移到 host.log，M2T07R-256）；团队仍是上一个 revision。
     - 文件的 revision 写不进去（存储失败，或三次尝试中团队都被别处改动）时，StartRun 不在旧团队上继续：存储失败按命令的存储错误回答，三次都被改动回 409 STALE_REVISION（可重试），都不建 Run（M2T07R-204）。

### Run 内的绑定

7. **StartRun**
   - 在接受事务内，按当前 revision 为每个职位写 `role_bindings`：role_epoch=1，config_revision=r，ACTIVE。
   - 把调度参数写入 Run 的快照（CR-007 S2）。
   - 写入预算行（iterations、wall_seconds；设了 `max_usd` 时写 usd，price_known=0）和 `runs.deadline_at`（ADR-020 决定 7）。
8. **checkpoint**（第 2 版，第一轮审查 M2T07R-01、-02、-03、-50..52、-54 后的设计修正；第 3 版只改被拒的修改，第二轮审查 M2T07R-150）
   - 定义：某个 Run 的某个职位此刻没有 PREPARED、STARTING 或 RUNNING 的 Attempt，就处在它的 checkpoint（REQ-019 决定 3）。写租约属于 Attempt，所以这也覆盖了写者的安全点。
   - **修改只看配置**：一个职位是否被修改，只比较两份配置：绑定所在 revision 中的这个职位，和项目当前 revision 中的这个职位，包括它在两边是否存在；比较的内容是 agent、model、fallback、prompt、independent_session。绑定的可用性状态（BLOCKED_AUTH、注册表给的 AGENT_UNAVAILABLE 等）从不当作配置读取。第 1 版用状态推断修改与删除，把可用性阻塞误当成修改（M2T07R-01、-51）。
   - **未修改的职位**：不论有没有在途 Attempt，都直接推进到新 revision，epoch、状态、阻塞原因与会话都不变（M2T07R-03）。
   - **被修改的职位**：
     - 先看调用方传入的注册表结果（在 writer 之外探测，见决定 10）。新 Agent 不可用时，这次修改**被拒**：旧绑定、旧 epoch 与会话保留，并且照常派发，职位不空缺（REQ-019 决定 2、失败模式 3，M2T07R-52、-150）。第 2 版让被拒的职位仍算待生效、不派发，职位实际空缺。
     - 新 Agent 可用（或 host 没有注册表）时：
       - 有在途 Attempt 就等待。在此期间 rounds 与 decide 都不派发它，以免旧绑定再租出一个 Attempt；运行中的 Attempt 沿用旧绑定（AC-018-02）。
       - 没有在途 Attempt 就生效：更新绑定，role_epoch+1，config_revision=r+1，会话置空，写 `team.binding_applied`（带 from、to、config_revision）。
     - 被拒的修改在之后每个 checkpoint 都重新判定，不被放弃：Agent 一旦可用，职位重新待生效（不再派发），等在途 Attempt 结束后生效。判定的每次转向写一条事件，同一判定持续多少个 tick 都只写一条：转为被拒写 `team.binding_refused`（带原因与保留的绑定），被拒后转为可用写 `team.binding_pending`。职位是否待生效，取 (Run, 职位, revision) 最近一条判定事件，没有判定事件时为待生效。
     - 项目再改出新的 revision 时，从头判定：新 revision 若撤回了修改，职位直接推进；若仍指向不可用的 Agent，仍被拒。
     - projection 中，被拒的修改在 `pending.refused` 给出原因（AGENT_UNAVAILABLE），其余为 null。
   - **删除**：被删除的职位不删行。该行置为 BLOCKED（AGENT_UNAVAILABLE，`$defs.BlockedReason` 没有别的码），epoch+1，写 `team.binding_applied`（to 为 null）。删除由配置识别（绑定 revision 中有这个职位、当前 revision 中没有），不由阻塞原因识别。projection 的成员带 `removed: true`，以免与可用性阻塞混淆。同名职位再加回来时，旧 epoch 的持有者仍被隔离。
   - **尚未绑定会话的绑定**（StartRun 刚写的，或刚换绑的）：rounds 与 decide 不派发它的任务，pace 也不把这些任务判为能力缺失。它们照常等待，由绑定器（决定 9）写入会话与探测到的能力（M2T07R-50）。
   - **哪些 Run 做 checkpoint**：runner 每个 tick 先用读连接找出所有非终态、且 `runs.config_revision` 低于项目当前 revision 的 Run，不论它处于 RUNNING、PAUSED、BLOCKED 还是 CREATED。在 pace 与 rounds 之前，每个 Run 交给 writer 一个事务（M2T07R-02、-54）。所有职位都到达新 revision 后，再推进 `runs.config_revision`。
   - M2-T17 在同一事务中补交接包。
9. **会话**
   - 每个 (run, role, epoch) 一个 HoH 会话，id 由三者确定性派生。绑定时写入 `sessions`，带探测得到的 Agent 版本与能力，并设到 `role_bindings.session_id`。
   - `lease_task` 把绑定的会话、config_revision 和 role_epoch 写进 Attempt。
   - 会话的能力有 resume 时，按 `sessions.native_id` 续接原生会话；没有时，下一个 turn 新开一个原生会话（M2T07R-257）。这条对 Claude 与 Codex 才有区别。Pi 能用就一定有 resume：它的接口要求 `--session-id`（`pi::interface_missing`），探测因此总给出 resume。所以 Pi 的会话按 ADR-013 决定 1，每轮传同样的 `--session-dir` 与 `--session-id`，续接时核对会话文件（M2T07R-354）。
   - 职位不同，会话 id 一定不同，reviewer、qa 和自定义职位都不会共用会话。进程退出不改变团队，也不改变会话（AC-018-03）。
10. **Agent 注册表与能力**
    - host 内只有一个注册表。它在 writer 之外（spawn_blocking）按 host 的 PATH 惰性探测各 Agent，并按启动器与实现文件的 (dev, ino, size, mtime) 缓存，文件变了就重新探测。
    - 职位需要的能力取 REQ-020 决定 1 中已有名字的部分：每个职位都要 structured_events，commander 与 reviewer 另要 resume；自定义职位继承它所引用的内置职位，没有引用时只要 structured_events。
    - Agent 不可用时，该职位为 BLOCKED（AGENT_UNAVAILABLE，带 missing）。绑定器每个 tick 都重新查看它阻塞的绑定（AGENT_UNAVAILABLE 且不是被删除的职位），Agent 可用时写入会话并恢复为 ACTIVE（M2T07R-155）。
    - 注册表有自己的任务：每个 tick 的间隔里，它查看 runner 需要的 Agent，按启动器与实现文件的身份缓存，没变就不重新探测。需要的 Agent 是项目当前团队的，加上未结束 Run 中每个绑定的（第三轮审查的设计修正，M2T07R-250：只看团队与等待会话的绑定时，被拒修改所保留的旧 Agent、重启前已绑定的 Agent 都不会被查看）。探测可能要几秒（例如 Codex 生成 schema），所以 tick 从不等探测：tick 只读注册表最近一次看到的结果，交给 checkpoint 与绑定器。这样被拒的修改在 Agent 可用后的下一个 tick 就重新判定（决定 8 第 3 版）。
    - 交给 checkpoint 的是三类：查看过且可用的、查看过且不可用的（带原因，被拒事件的 `detail` 即此原因，M2T07R-260），两类都不在的就是“未知”。未知按 checkpoint 自己读到的团队判断，所以 runner 读团队之后才到的修改也不会被当作可用（M2T07R-255）。指向未知 Agent 的修改等待，不写判定事件，职位暂不派发；绑定器也等它被查看后再给会话或阻塞。
    - 已有会话的绑定照常派发。执行器的 `deliver` 等到注册表查看过该 Agent 才确认（最多 60 s，没确认就由 runner 再交一次），所以 host 重启后、首次探测完成之前派发的 Attempt 不会因“未查看”而失败（M2T07R-250）。
    - host 停止时，探测命令不比 host 活得久（第四轮审查的设计修正，M2T07R-300，与 -202 同类第二次）。
      - **由停止的一方结束命令，不靠启动它的线程何时得到调度**。每条探测命令启动时登记到注册表的停止句柄（`ProbeStop`，经 `ProbeEnv.cancel` 传给探测）。“是否已停止”的判断、spawn 与登记在同一把锁内完成，所以停止之后不会再有命令启动。
      - `ProbeStop::stop` 返回之前，对每条已登记、领头进程尚未回收的命令，向其进程组和领头进程发 SIGKILL：领头未回收，这个号仍是它的。
      - 回收照旧由启动命令的线程完成。它结束一条命令时，先从登记中取走再发信号，所以停止的一方不会向已回收的号发信号。
      - runner 停止时先调 `Registry::stop`，上述 SIGKILL 在其中同步完成；然后等注册表任务结束，最多 5 s。读取 Codex schema 的工作线程被延迟时，命令也已被杀。读取 schema 的调用方在停止后，最多再等工作线程一个清理宽限（2 s 加 0.5 s），让它删除临时目录；过了这个时限，照旧报告目录可能留在何处。`__host` 退出时另给阻塞线程 2 s 的上限。
      - 第 3 版只设一个标志，由运行命令的线程自己结束命令。`codex_schema` 收到停止后不等工作线程就返回；工作线程被延迟时（审查用 ptrace 复现），host 先退出，schema 命令成了孤儿（PPid 1）。
      - 这一类问题最早在 S6 自测中出现：探测放在 tick 内时，刚由 detach 启动的 host 在首次探测期间收到 SIGTERM，迟迟不退出（M2T07R-202）。
    - 被停止中断的探测不是关于 Agent 的结论（M2T07R-352）：结果不写入注册表，该 Agent 保持上一次看到的结论，从未查看过的仍是未查看。否则 host 停止的那一刻，等待首次查看的派发可能把“停止”当作 Agent 不可用，Task 被持久阻塞为 BLOCKED_CAPABILITY。
    - 注册表的探测看得到安装、版本、能力与启动所需的事实，看不到认证：不跑一个 turn 就无法知道是否缺认证。缺认证由 turn 发现（Attempt 以 BLOCKED_AUTH 结束）。由此恢复绑定、在交接前按认证拒绝（REQ-019 失败模式 3 的“缺认证”）以及 fallback（REQ-020 行为 2、4），分别留给 M2-T17 与 M2-T15。
    - 绑定之后 Agent 才消失时，`start` 以 AGENT_UNAVAILABLE（能力类）拒绝，Task 成为 BLOCKED_CAPABILITY；会话能力无法得出（session_capabilities 失败）时，绑定器把绑定阻塞为 AGENT_UNAVAILABLE。精确的缺员码（REQ-020 行为 6）与这两种情形的分类留给 M2-T15（M2T07R-260）。
    - 兼容套件闸门（COMPAT_UNVERIFIED）留给 M2-T15。
11. **Prompt**
    - Prompt 由两部分组成：职位契约（内置的 `resources/prompts/<role>.md`，编译进二进制；或覆盖文件），加上任务头（Run 目标、任务 id 与标题、职位）。没有 prompt 的职位用自己的内置契约，`builtin:<role>` 用该内置职位的契约（`hoh_core::config::contract`）。
    - Prompt 记录随 Attempt 的结束提交写入（不在 STARTING 写，执行器不写 store）：一条 `prompt_revisions`（layer 为 builtin 或 project，含路径与 content_sha256，id 为 `<layer>/<role>/<sha256>/<路径>`：内容相同的两个文件是两个来源（M2T07R-205）），并设置 `attempts.prompt_revision`；`attempts.prompt_sha256` 是实际发出内容的 sha256（AC-018-05）。host 在 turn 结束前崩溃时，这个 Attempt 没有 Prompt 记录。
    - 覆盖文件在配置时就要校验：项目内的相对路径（不含 `..`），指向可读的普通文件；路径上的符号链接全部解析之后，文件仍须在解析后的项目根之内（文件加载与 ConfigureTeam 都查，不合格时按键路径拒绝，M2T07R-53、-101）。STARTING 时用同一个函数解析，再读取。STARTING 时文件丢失或读不了，Attempt 以 FAILED（PROMPT_UNAVAILABLE）结束，不退回内置契约。

### 产品执行器

12. **执行器端口**
    - 执行器不写 store。产品执行器的 `deliver` 在注册表查看过该 Agent 后确认（决定 10）；`start` 用注册表最近一次查看的结果准备 turn：读职位契约、拼任务头、按绑定的 model 与原生会话（续接）组装命令，经启动门 spawn。
    - `start` 拒绝时返回 `Refusal{reason, class, detail}`：reason 写入 `failure_reason`（产品的为原因码：PROMPT_UNAVAILABLE、AGENT_UNAVAILABLE、BLOCKED_CAPABILITY 等），class 决定重试，detail 记入 `attempt.start_refused` 事件。测试执行器的文字拒绝按瞬时类处理，与以前相同。
    - `Outcome` 带上事实：原生会话、resolved_model、usage、raw_log_path、诊断事件、失败码（作为 `failure_reason`）、类别、`group_gone`。这些都写在 runner 自己的结束提交中，写队列满也不会丢掉判定所需的事实。
    - **适配器的终态完整保留**（第三轮审查的设计修正，M2T07R-200）：第一版把终态压成 success 布尔值，UNKNOWN_EFFECT（turn 开始了一个效果却没有报告结果就结束）被记成 FAILED 并按瞬时类重试，未知的外部效果会被重放。现在 `Outcome.unknown_effect` 与 `Ending.unknown_effect` 带上它：runner 不把工作效果记为 OBSERVED/COMMITTED（它保持 STARTED），仍先要求进程组清空与终结证明，然后把 Attempt 结束为 UNKNOWN_EFFECT。Task 原地不动，不安排重试，租约释放，并写一条 `runner.diagnostic`（code UNKNOWN_EFFECT，列出 STARTED 的 effect_key）。这与 ADR-019 决定 5 的 reconcile 处置一致；host 在其间崩溃，下次 reconcile 也得到同一结论。
    - **取消优先**（ADR-021 决定 8e，第四轮审查 M2T07R-301）：Attempt 带 `cancel_requested` 时，runner 的结束与 reconcile 的处置得出同一结果：Attempt 为 CANCELLED，其未观察到的 STARTED 效果记为 UNKNOWN，Task 不动（由取消的最终事务处理），不计数，不重试；有效果记为 UNKNOWN 时，照样写一条诊断（runner 写 `runner.diagnostic`，reconcile 写 `reconcile.diagnostic`），列出这些 effect_key。之前 runner 的结束把 Attempt 记为 CANCELLED，却把效果留在 STARTED；reconcile 的取消优先只覆盖 FAILED 与 SETTLED，漏了 UNKNOWN_EFFECT。两条路径的结果因此取决于崩溃发生在哪一刻。
    - 一个事件只有一个写出者：降级的 `adapter.degraded` 由适配器写入 recorded，执行器不再补一条（M2T07R-201：同一 key 两次，结束提交违反唯一约束而回滚）。
    - 原始日志在 `.hoh/attempts/<attempt id>/`，Pi 的会话目录在 `.hoh/sessions/<session id>/`（id 中的 `%` 与 `/` 转义）。新 Pi 会话的 `--session-id` 是 HoH 会话 id 的 sha256 摘要，排成 UUID 形状，同一会话每次都相同；之后的 turn 用记录下来的原生 id 续接。
    - 原生取消：`Executor::cancel` 通知正在运行的 turn（Claude、Codex exec 发 SIGINT，App Server 发 turn/interrupt，Pi 发 abort）；适配器自己的升级宽限取 execution 的 cancel_native_grace_seconds 与 cancel_term_grace_seconds。
13. **启动门**
    - Agent 进程不经 shell 启动（REQ-024/025 行为 1），改为由隐藏入口 `hoh __gate <program> <args…>` 先行启动：它从 stdin 逐字节读到 LF；读到 `go` 时以 `exec` 换成目标程序，pid、进程组、环境（含 `HOH_ATTEMPT_ID`）与 cgroup 都不变；EOF 或读到其他内容则以 0 退出。
    - exec 之前，信号处置与屏蔽恢复为默认（M2T07R-203：std 的 exec 不会恢复被忽略的信号，也不清屏蔽集；而 shell 的后台任务与 nohup 会让 host 继承被忽略的 SIGINT/SIGHUP，Agent 就听不到原生取消）。工作区禁止 unsafe，所以做法是：对 1..31 中 signal-hook 允许的每个信号设一个处理器（exec 会把有处理器的信号恢复为默认，被忽略的则不会），再用 nix 的 `pthread_sigmask` 清空屏蔽集（nix 0.31.3，MIT）。SIGKILL、SIGSTOP 没有别的处置；SIGILL、SIGFPE、SIGSEGV 不能经 signal-hook 设处理器，保持继承（启动 host 的进程不会忽略它们）。
    - runner 收养的是阻塞在 read 中的 `__gate` 的 pid，然后记身份与 tracking，再开门，与 ADR-021 决定 8d 的顺序相同。
    - 产品用 `current_exe()` 作为门程序，测试传入 `CARGO_BIN_EXE_hoh`。
14. **适配器的 runner 模式**
    - 三个适配器各增加一种模式，分三步：准备（argv、日志、检查）→ 经调用方给的门命令 spawn → 在执行器拥有的任务中驱动（等到开门才写协议字节）。
    - 这种模式下适配器不迁移 Attempt 状态，只交回事实（决定 12）。
    - 现有的 `run()` 留给 `doctor --live` 与适配器测试使用，行为不变。
    - host 的取消阶梯为准：`Executor::cancel` 只发原生取消（Claude 发 SIGINT，Codex app-server 用 turn/interrupt、exec 发 SIGINT，Pi 发 abort）。适配器只在自己的判定（帧过大、协议失败）上升级信号。
    - runner 模式下 turn 不设 deadline。
    - Claude 的 Launch 增加 `--model`：help 有这个参数才用，没有则 BLOCKED_CAPABILITY。
    - runner 的事实中不带 `cost_usd`，Claude 自报的估算放进 usage 的 `reported_cost_usd`（ADR-020，M2T07R-256）。
15. **Codex 的传输方式**
    - 每个 Attempt 在启动前按注册表定下传输方式。
    - app-server 在 initialize 时返回方法不存在或握手超时，这个 Attempt 以 FAILED 结束（CAPABILITY_UNSUPPORTED，瞬时类），记录 `adapter.degraded` 事件，执行器把这个实现（启动器路径与版本）标为 exec，下一个 Attempt 走 exec（REQ-024 失败模式 4：降级为 exec 并记录原因）。版本变了（升级）就重新尝试 app-server。
    - exec 也不可用时为 BLOCKED_CAPABILITY。
    - 不在同一个 Attempt 内另起第二个进程，以免绕开启动门与终结证明。
16. **失败类别映射**（ADR-020 决定 1）：
    - BLOCKED_AUTH → Auth；
    - BLOCKED_CAPABILITY、MODEL_UNAVAILABLE → Capability；
    - TRANSIENT_EXTERNAL → Transient；适配器目前不解析 Retry-After，按不带等待的瞬时类重试（M2T07R-256，记入后续项：在 M2-T11 之前补上）；
    - 其余 → Transient（不带等待）。
17. **host**
    - `HostConfig::new` 仍不带 runner，供现有测试使用。新增 `HostConfig::product(project, config, gate, path)`，`__host` 使用它：带产品执行器（门程序为 `current_exe()`）、按 host 的 PATH 查找 Agent 的注册表，以及进程级配置（端口、写队列容量、读者槽位、取消宽限）。尚未接线的键见决定 6。
    - 取消宽限接到 host 的每一级（M2T07R-254）：CancelRun 的阶梯（`HostConfig.cancel`，原生 → SIGTERM → SIGKILL）、租约到期收尾在原生取消之后的等待（`ReconcileSettings.native_grace`），以及适配器自己的升级。初值仍为 REQ-043 决定 1 的 10/5 s。收尾只在确实发了原生取消（执行器手里还有这个 Attempt 的 turn）时等 native_grace；没有发时，照旧等 SIGTERM 的宽限（M2T07R-353）。
    - host 停止时，产品的 Agent 进程不保证继续运行：它们的管道随 host 关闭，适配器读不到输出，Agent 可能因 EOF 或 SIGPIPE 结束，也可能继续运行。两种情况都由下次启动的 reconcile 按 ADR-019 与 ADR-021 决定 8d 处置：先证明进程组与 cgroup 已空，才结束 Attempt（STARTED 且没有观察到结果时为 UNKNOWN_EFFECT）。这里不用 PR_SET_PDEATHSIG（M2T07R-59）。
18. **可观察性**
    - `GET /v1/runs/{id}` 的 projection 增加 `team`（按 commander、cto、developer、qa、researcher、reviewer 排序，自定义职位按字母序排在后面，每项含 agent、model、role_epoch、config_revision、session_id、state、pending）和 `team_revision`。
    - 新增 `GET /v1/runs/{id}/team`，按 openapi 的 limit（1..500，默认 100）与 cursor 分页，cursor 是上一页最后一个职位，非法参数与 list_runs 一样回 404（M2T07R-06、-57）。
    - 帧过大的诊断仍用 `adapter.diagnostic` 事件，另写入 `<raw_log_path>/diagnostics.jsonl`；事件带 `reader_max_buffered`（读取器最多缓冲的字节数，AC-027-03 的测试探针）。
