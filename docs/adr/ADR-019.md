# ADR-019 · 启动 reconcile、effect ledger、租约 fencing 与 kill -9 恢复矩阵

状态：采纳（M2-T05，随任务分步补全）

## 背景

M2-T05 要求 host 在 kill -9 后按固定顺序 reconcile（REQ-041），一次迁移中的 state、event、outbox 要么全在、要么全无（REQ-036 AC-036-02），旧 host_epoch 与过期租约的写入被拒（AC-041-02），PID 复用不得误杀（AC-041-03），外部效果走 effect ledger（AC-041-05），并且 recovery 检查要能落地。事实与缺口见 `.hoh-dev/evidence/m2t05-prep/analysis.md`。

## 决定

1. **写入的故障点**（REQ-036，CR-006 F2/F4）。
   - writer 的每个请求带一个上下文 `Ctx`，内容是请求名（"Decide"、"Commit"……）、故障钩子和 host 栅栏（决定 2）。它取代了原来的 `after_events` 闭包。
   - 每个写事务都从 `writer::begin` 开始。唯一的例外是 `begin_host`，它本身就是推进 epoch 的那一步。
   - `FaultHooks::at(job, point)` 依次报告五个点：
     - `Begun`：事务已开始，栅栏已核对；
     - `StateWritten`：状态 CAS 之后；
     - `EventsWritten`：事件之后；
     - `OutboxWritten`：发件箱之后；
     - `Committed`：提交之后、回复之前。
   - 这五个点对应 AC-036-02 的"BEGIN后、state UPDATE后、event INSERT后、outbox INSERT后、COMMIT后ACK前"。
   - 产品实现 `NoFaults` 什么也不做。制造故障的实现（例如进程自发 SIGKILL）只在测试目标里。钩子扫描（`only_the_no_op_fault_hooks_are_in_product_code`）不需要改，因为新方法是已有 trait 的默认方法。
2. **host_epoch 栅栏**（REQ-041 失败模式 4，M2T12R-183）。
   - writer 在 `begin_host` 成功后记下这次 host 的 (project_id, host_epoch)。
   - 此后每个写事务都在 `begin` 中、持有写锁的前提下核对项目的当前 epoch，不一致就以 IntegrityViolation 失败。失败信息注明"0 rows changed"，事务回滚，状态不变。
   - 核对在写锁下进行，所以新 host 不可能在核对与提交之间推进 epoch。
   - 没有开始过 host 的 store（例如测试或 scratch）不受栅栏约束。
   - 核对用 SELECT，不用自赋值 UPDATE：后者会让每个空闲的领取事务也写一页 WAL。
3. **Run 开始运行的通知**（AC-036-02 的迁移）。
   - 决策把 Run 迁入 RUNNING 时，在同一事务中写一条运行时通知 `{"notice":"runtime","kind":"run.started"}`。这条通知发给 `runtime`，指向该决策的 `decision.applied` 事件。
   - 它是这次迁移的持久记录与唤醒：执行循环每个 tick 都为所有工作中的 Run 运行调度轮，派发不依赖这条通知；执行循环取到它时 ACK（M2T05R-57）。
   - 所以"READY→RUNNING 会派发 T1"的含义是：这条迁移的一个事务恰好写入状态、1 个事件和 1 行 outbox；Run 一旦为 RUNNING，执行循环的调度轮就派发 T1（决定 8）。
   - 调度轮仍各自写 `schedule.round` 事件（ADR-017 决定 6 不变）。
   - 这条通知不是 HCP 消息，HCP 投递循环不领取它（ADR-018 决定 4）。
4. **进程身份**（REQ-041 b3，`hoh_agents::identity`）。
   - attempts 进入 RUNNING 时记下 pid、`boot_id`（/proc/sys/kernel/random/boot_id）和 `process_start_id`（/proc/<pid>/stat 第 22 字段，即开机以来的时钟滴答）。三个适配器的四处 STARTING→RUNNING 都改用 `identity::running(pid)` 填这些事实。`AttemptRow` 可以读出它们。
   - 只有 pid、boot 与启动时间都相符，才算"是这个 Attempt 的进程"。查找时先打开 pidfd，再重读启动时间。所以核对和之后的每个信号指向同一个进程，PID 复用也改变不了这一点。
   - 不相符时给出依据，不发任何信号：`no_pid`、`boot_id_differs`、`no_process`、`start_time_differs`。
   - 停止流程：
     1. 向它的进程组发 SIGTERM；
     2. 宽限期过后，向进程组发 SIGKILL，并经 pidfd 向组长发 SIGKILL；
     3. 再等组长退出、进程组清空。孤儿进程由新的父进程回收。
     - 只有组长仍存活（pidfd 不可读）或组内还有成员时，才向进程组发信号：进程组 id 在还有成员时不会被复用。
5. **启动 reconcile 的处置**（REQ-041 b1–b2，`hoh_core::reconcile::dispose`，纯函数）。
   - **时机**：`begin_host` 之后、绑定任何监听之前执行，所以完成前不接受写命令。事件顺序是 `reconcile.started` → 每个未完成 Attempt 一条 `reconcile.attempt` → `reconcile.completed`（计数）。
   - **单个 Attempt**：每个 Attempt 的处置写在一个事务里，包括效果迁移、Attempt 迁移（结束时释放租约）、Task CAS 和事件。`reconcile.attempt` 记录处置、找到的进程（依据或停止步骤）、记录的身份和效果迁移。
   - **处置**：
     - 进程停了却没回收干净 → `Unreaped`：什么都不迁移，租约继续占用，因此不会授予新的写租约，并写一条 `reconcile.diagnostic`（PROCESS_NOT_REAPED）。（失败模式 5）
     - STARTED 效果：查到了 → COMMITTED，并记下 external_ref；查不到或无法查询 → UNKNOWN。OBSERVED → COMMITTED。
     - 有效果为 UNKNOWN → Attempt 置为 UNKNOWN_EFFECT。Task 原地不动，不自动新增 Attempt，并写一条 `reconcile.diagnostic`（UNKNOWN_EFFECT），列出这些 effect_key。（失败模式 1）
     - Attempt 自己的工作效果（`work_key(attempt)`）已 COMMITTED（或 OBSERVED 后提交）时，按 OBSERVED 记录的结果处置：只有 RUNNING 且成功才为 SETTLED（Task 若是 RUNNING，则改为 IMPLEMENTED）；记录的失败为 Ended(FAILED, READY)；没有记录结果则为 UNKNOWN_EFFECT（见决定 8 的设计修正）。
     - PREPARED 且没有已开始的效果 → `Redeliver`：保持原状，它的派发会重投（"确认未发送才重投"）。
     - 其余情况（工作未确认完成，开始过的效果都已查到，或者一个也没开始）→ `Ended`：STARTING 改为 CANCELLED，RUNNING 改为 FAILED，Task 回到 READY，等待新的 Attempt。副作用的 key 对每个逻辑效果稳定，新 Attempt 会按 marker 找到旧 Attempt 已做的部分。
   - **修订 ADR-017 决定 4**：UNKNOWN_EFFECT 也算持有者已结束，进入该状态时释放租约。前提是只有确认进程已不在之后才会进入 UNKNOWN_EFFECT：找到的进程已停止并回收干净，或记录的身份已不存在。无法确认的情况一律为 Unreaped，见决定 8 的设计修正。未知的是效果，不是仍在运行的写者。原来的规则下，一个 UNKNOWN_EFFECT 会永远挡住所有写任务。
   - 每次 host 启动都写 reconcile 事件，未完成数为 0 时也写，作为每个 host_epoch 的恢复留痕。host 测试里统计"这条命令恰好写了一个事件"的断言，因此把 `reconcile.%` 事件排除在外。
6. **effect ledger**（REQ-041 b6）。
   - 状态依 SQL：PREPARED→STARTED→OBSERVED→COMMITTED，或进入 UNKNOWN。迁移用 CAS，条件是原状态与 attempt_id。
   - 键：
     - Attempt 自己的工作用 `<attempt>/work`，每个 Attempt 一个。执行循环在 agent 执行前写 STARTED（预写），见决定 8。
     - 副作用（例如 PR）的键对每个逻辑效果稳定，它也是远端查找用的 run marker。
   - reconcile 不会重做任何效果，只经端口 `hoh_core::reconcile::Observer` 按 marker 查询。产品实现 `NoObserver` 一律答"无法查询"，结果是 UNKNOWN（失败即关闭）。测试中的 FakeRemote 实现同一端口，记录每次查询。这个端口只读，没有任何创建手段，所以"创建调用数为 0"是结构上的保证，测试断言恰好两次查询（M2T05R-56）。
   - host 的 `ReconcileSettings` 带停止的宽限时间（默认各 5 s）和 observer。

7. **租约续约与过期链**（REQ-041 b4，AC-041-02）。
   - **时钟**：执行循环的时钟是端口 `HostConfig::clock`。产品用系统时钟，测试传入假时钟（CR-006 F2"换时钟"）。
   - **续约**：每 30 s 为在途 Attempt 续约一次，到期时间设为 now + 120 s。只续仍未过期的租约，过期的租约只能按下面的过期链处置，不能复活。
   - **过期链**：每个 tick 先查过期链，再运行调度轮。持有者尚未结束而租约已过期时，过期本身不能证明旧进程已死，依次执行：
     1. 先中止本 host 为它运行的任务，之后不再有别的写入，再重新读取这一行；
     2. 检查进程身份，写 `lease.inspected`；
     3. 经执行器端口发原生取消（`Executor::cancel`），写 `lease.native_cancel`，事件记录是否发出；
     4. 等原生取消的宽限期；
     5. 向进程组发 SIGTERM（`lease.sigterm`），宽限期后发 SIGKILL（`lease.sigkill`），确认组长退出且进程组清空（`lease.reaped`）；
     6. 按 reconcile 的规则处置（`reconcile.attempt`，cause=`lease_expired`）：工作效果已 STARTED 的，查到则完成，否则为 UNKNOWN_EFFECT。
     - 结束（包括 UNKNOWN_EFFECT）时释放租约，随后的调度轮（同一 tick 或下一 tick）再以 epoch+1 授予（-257）。
     - 每一步单独提交，所以事件顺序就是执行顺序。
   - **无法回收或无法确认**：进程无法回收或无法确认时什么都不迁移，租约继续被占用，不授予新的写租约。执行循环每 60 s 再看一次，结论与上一轮相同时不再写事件（M2T05R-157）。
   - **过期的 PREPARED Attempt**：它已无法启动，写者启动需要未过期的租约，因此处置为 `Ended`（CANCELLED，Task 回到 READY），而不是重投。启动 reconcile 同样适用这条规则。
   - **事件 id**：一个 Attempt 被多次处置时（重投、无法回收），事件 id 带处置序号，每次各自独立（events.event_id 唯一）。
   - **TEST-041-02**：在测试进程内运行 host，代理忽略 SIGTERM（SIG_IGN 会被子进程继承）。事件顺序依次为 inspected、native_cancel、sigterm、sigkill、reaped，之后授予 epoch 5。授予时 A1 的进程组为空。A1 迟到的 TaskResult 返回 STALE_LEASE_EPOCH，Task revision 不变，并写一条历史事件；旧 host_epoch 的写入失败，信息为"0 rows changed"。

8. **最小执行循环**（`hoh-app` 的 `host/runner.rs`，AC-041-01）。
   - **何时启动**：配置了 `RunnerConfig { executor, context }` 才启动。产品在 M2-T07 绑定角色之前没有执行器，所以 host 不派发任何东西。
   - **启动顺序**：执行循环在 reconcile 之后启动，与监听器一起停止，并在 store 关闭之前结束。因此它做出或接收的每个派发都在 `reconcile.completed` 之后。
   - **每个 tick**（被提交唤醒，或每 200 ms）：
     1. 为每个工作中的 Run 运行调度轮，直到不再派发。不选任何任务的轮不写任何东西。
     2. ACK 等待中的 run.started 通知。
     3. 把 Attempt 仍为 PREPARED 的派发通知交给执行器；同一 host 内用一个在途集合防止重复处理。
   - **单个 Attempt 的步骤**（每步一个事务）：
     1. 交付派发，执行器的回答即 ACK；
     2. 写收据（consumer `runner`），通知改为 ACKED，Attempt 改为 STARTING，工作效果写为 PREPARED；
     3. 启动进程，进程停在启动门前；读出完整身份，读不到就不开门，按启动失败处理；
     4. 一个事务写入：Attempt 改为 RUNNING 并带上进程身份，工作效果改为 STARTED（预写），Task 改为 RUNNING；
     5. 打开启动门；
     6. 进程结束后，工作效果改为 OBSERVED（带结果）；执行器报告进程组已确认为空（`Outcome::group_gone`，第三、四版设计修正）才继续，否则写 `runner.unreaped`，Attempt 留在 RUNNING；
     7. 工作效果改为 COMMITTED；Attempt 改为 SETTLED、Task 改为 IMPLEMENTED，或者 Attempt 改为 FAILED、Task 回到 READY。
     - 任何一步不再适用（例如该 Attempt 已被处置）就停下。
   - **崩溃后**：
     - 没收到派发：通知仍为 PENDING、Attempt 仍为 PREPARED，于是重投。
     - 有收据但工作效果未 STARTED：证明工作从未开始。
     - 工作效果已 STARTED：只按 marker 查询，绝不重做。
   - **注入点**：`HostHooks::runner(RunnerPoint)` 依次是 BeforeSend、AfterSend、AfterAck、AfterSpawn（进程已启动、身份尚未记录）、Settling（一次结算开始，见第三版第 7 条）、AfterEffectStarted（RUNNING 事务和开门之后、OBSERVED 之前）、AfterEffectCommitted（任务迁移之前）。产品实现什么也不做。
   - **TEST-041-01**：5 个点各跑 10 次，测试中的 FakeExecutor/FakeAgent 每次执行都把 effect_key 追加到计数文件，结束时写 marker，测试中的 Markers 观察者按 marker 查找。证据中各点的处置如下：
     - 前三个点为 redeliver；
     - AfterEffectStarted 为 unknown_effect；
     - AfterEffectCommitted 为 completed；
     - 没有任何 key 被计数两次。
   - **失败的工作**：Task 回到 READY，没有退避和预算。重试与预算归 M2-T19。产品没有执行器，所以不会出现热循环。
   - **设计修正（第一轮审查，单写者一类，M2T05R-01..04、-52）**：原则是，只有证明持有者的进程不可能再运行，才释放它的槽位。从记录缺失推断进程已不在，不算证明。
     - **启动门**：`Executor::start` 返回停在启动门前的进程（`Started { pid, gate, ended }`）。执行循环用一个事务写入以下内容，之后才打开门；门在打开之前被丢弃时，进程读到 EOF，代理不会运行。所以"没有记录身份"就证明代理从未运行，测试点 AfterSpawn 固定了这一窗口。
       - Attempt 改为 RUNNING 并带上进程身份；
       - 工作效果改为 STARTED（预写）；
       - Task 改为 RUNNING。
     - **无法确认**（`Process::Uncertain`）：处置为 Unreaped，即不发信号、租约继续占用、写一条诊断，执行循环 60 s 后再看。两种情况属于无法确认：
       - 组长已不在而组内仍有成员（`identity::presence` 返回 `Leaderless`）：这些成员是本 Attempt 的后代，还是复用该 pid 的后来进程留下的，无法分辨；
       - RUNNING 却没有记录进程身份（异常记录）。
     - **处置前等任务结束**：结算（settle）前先中止并等待本 host 为该 Attempt 运行的任务结束，再重新读取。重读是一个 writer 作业，排在该任务已经发出的写入之后。
     - **执行器丢失完成通知**：按过期租约的方式结算（cause `executor_lost`），不当作失败重跑。
     - **启动失败**：直接从 STARTING 改为 FAILED，Task 回到 READY，工作效果保持 PREPARED。
     - **结算事件 id**：带 host_epoch 和序号（`<cause>/<host epoch>/<pass>/<step>`），中途失败后的重试不会撞上唯一键（M2T05R-06）。
     - **结果按记录处置**（M2T05R-05、-53）：OBSERVED 事件记录 success。reconcile 读取它，只有 RUNNING 且成功才处置为 Completed，记录的失败处置为 Ended(FAILED, READY)。STARTING 永远不会变成 SETTLED，没有记录结果的 COMMITTED 视为未知。
     - **适配器**：三个适配器自己在 spawn 之后才写 RUNNING，没有启动门。它们在 M2-T07 接入执行循环时必须改走启动门，在此之前 host 不运行它们。
   - **设计修正（第二轮审查，同一类第二次，M2T05R-100..102、-150..152）**：第一轮的原则没有落到每一条释放路径上。释放槽位只有两条路：Attempt 的终态迁移，以及 UNKNOWN_EFFECT 迁移。它们只来自执行循环的正常结束和 reconcile/结算的处置；适配器自己的迁移在 M2-T07 之前不由 host 运行。这两条路一律要求同一个释放证明：
     1. **身份完整**：开门前必须读到完整身份（pid、boot_id、启动时间），读不到就丢弃启动门，按启动失败处理（代理从未运行）。记录中有 pid 却缺 boot_id 或启动时间时，一律视为无法确认，绝不当作"另一个 boot"或"另一个进程"（-100）。
     2. **钉住 pidfd**（第三轮已撤销，前提不成立，见下一条设计修正）：执行循环从 spawn 之后起就持有组长的 pidfd，直到确认整个进程组清空为止。原以为被钉住的 pid 号不会被复用，所以这期间向该进程组发信号是安全的。
        - 正常结束时，组长退出后先经钉住的 pidfd 停止并清空整个组，确认清空才写结束迁移；清不空就不迁移，写一条诊断，留给过期链处理（-101）。
        - 结算从在途条目里接过钉住的 pidfd。没有钉住的 pidfd 时（host 已重启），组长已不在而组内仍有成员，仍视为无法确认。
     3. **同一个映射**：启动 reconcile 与执行循环的结算共用同一套检查与结束函数 `inspect`/`end`（-151，-257）。
     4. **在途条目随任务结束**：attempt 任务以任何方式结束都移除自己的在途条目。出错时立即结算（cause `runner_error`；"带着钉住的 pidfd"随第三版第 4 条撤销）；结算也失败时停止续约，租约过期后由过期链处理。续约只覆盖仍在运行的条目（-102、-150）。
     5. **重试只在结论改变时写事件**：重试时结论与上一轮相同，就不再写事件（-157）。
   - **设计修正（第三轮审查，同一类第三次，M2T05R-200..202、-258）**：第二版的第 2 条前提不成立。pidfd 只引用进程，不保留它的 pid 号：组长一旦被回收，即使 pidfd 还开着，这个号也会释放并可能被复用（内核 `free_pid` 先 `idr_remove`；已在本机验证：僵尸状态下 `pidfd_send_signal(0)` 成功，回收后返回 ESRCH，fdinfo 显示 `Pid: -1`）。改为：
     1. **只在组长仍占着 pid 时向组发信号**（第四版撤销：组内成员同样占着组号，见下一条设计修正）：组长活着或是僵尸时，`pidfd_send_signal(0)` 成功，这时组号不会被复用，组内成员属于本组。`Found::stop` 在每次组信号之前都核对这一点。组长已被回收而组内仍有成员时，一律视为无法确认，不发信号，槽位保留。
     2. **扫描出错不算"空"**（第四版起，判空改用内核查询，扫描只作诊断与测试证据）：`identity::group_left` 返回扫描结果或错误，并排除组长本身。只有完整扫描且为空，才算组已清空（-200）。inspect 把检查出错映射为无法确认，不让 host 启动失败。
     3. **由执行器清空进程组**（约定的措辞由第四版第 5 条更正）：执行器端口的约定是，先在组长仍是僵尸时清空它的进程组，再回收组长，并在 `Outcome::group_gone` 中报告是否清空。M2-T07 的产品执行器将使用它。执行循环只在 `group_gone` 时写结束迁移，否则写 `runner.unreaped`，Attempt 留在 RUNNING，槽位保留。
     4. **去掉钉住的 pidfd**：组长被回收后它不再有用；组长活着时，按记录重新打开 pidfd 并核对启动时间，效果相同（-201）。
     5. **runner_error 的结算在移除在途条目之前完成**，期间 tick 不会重投；启动门无法打开时自行结算后正常返回，不重复结算（-260）。
     6. **余项**（第四版撤销，这是第 1 条自己造成的倒退，M2T05R-351）：组长对 SIGTERM 退出并被回收，而组内成员忽略 SIGTERM 时，这些成员不会收到 SIGKILL，结算判为无法回收，槽位保留。
     7. **测试接缝**：`ReconcileSettings::retry`（默认 60 s）供 -157 的测试使用；`RunnerPoint::Settling`（产品中为空操作）供测试在结算开始时打开门闩（-256）。
   - **设计修正（第四轮审查，同一类第四次，M2T05R-300..303、-350..360）**：第三版有两处错。一是判空：逐项扫描 /proc 不是原子快照，组长为僵尸时，已列出的成员可以在读它的 stat 之前 fork 出新成员再退出，扫描就会漏掉新成员而判空（-300）。二是组号：前提"组长一旦被回收，组号就不再受保护"在组内还有成员时不成立（-351）。正确的模型如下：
     1. **组号何时属于本 Attempt**：内核只在没有任何进程以某个号作为 pid、进程组号或会话号时才释放它（`detach_pid` → `free_pid`）；pidfd 只引用进程，不占号。组 N 从组长通过身份核对（pidfd 先打开，再读启动时间）起属于本 Attempt，直到组被观察到为空为止：组长未被回收时（活着或是僵尸，pidfd 的 fdinfo 显示 `Pid: N`），组长自己占着 N；组长被回收后，组内成员占着 N（已在本机验证：成员 M 的 pgrp 仍为 N，`kill(-N,0)` 成功，`killpg(N, SIGKILL)` 杀死 M 之后才返回 ESRCH）。
     2. **判空用内核查询**：组已清空，当且仅当 `kill(-N, 0)` 返回 ESRCH（rustix `test_kill_process_group`）。这是内核对组的一次查找，包括僵尸，不是逐项扫描；其他错误（如 EPERM）都表示组内还有进程。`group_left` 的扫描只用于诊断和测试证据，其错误照样传出。
     3. **何时可以按组号发信号**：每次组信号之前都看一眼组（`Found::look`），结果为三者之一：
        - **Held**：组长未被回收；或组长已被回收、组不为空，且上一次 Held 距今不超过 `HELD_FOR`（100 ms）。只有 Held 才发信号，发的是 `kill(-N, sig)`；SIGKILL 另经 pidfd 发给组长本身。
        - **Empty**：组已清空（第 2 条）。
        - **Lost**：组长已被回收、组不为空，但上一次 Held 已超过 `HELD_FOR`，无法知道这些成员还是不是本 Attempt 的。此时不再发信号，停止判为未回收（步骤 `lost_track`），处置为 Unreaped，槽位保留。
        - 停止过程中每 10 ms 看一次；原生取消的宽限期也是这样等，等到 Empty 或 Lost 为止，不只等组长退出（-354）。
        - 步骤只在信号确实发出时才记录（-355）。组长已退出但还没被回收、组内也没有其他进程时，`kill(-N,0)` 无法把僵尸和成员区分开，所以仍会向该组发 SIGTERM（发给僵尸，无害），直到组长被回收。
     4. **余项（接受，有界；措辞由第五版更正，M2T05R-453）**：信号按组号发出，内核按号查找组。误发给别的组要同时满足四件事：
        - 本组在两次观察之间（间隔不超过 `HELD_FOR`），或在最后一次观察与发信号之间清空了；后一段窗口只受调度约束，没有时间上界；
        - 号 N 因此被释放；
        - pid 分配器把 N 重新分了出去。分配器从游标起取第一个空闲号，所以要等游标走到 N。游标离 N 多远取决于当时的分配位置：若分配刚回绕、游标正好在 N 之前，可能很快就到 N，不能假定很远；
        - 得到 N 的新进程自己建了进程组 N（`setpgid`/`setsid`）。否则 `kill(-N, 0)` 返回 ESRCH，判为 Empty，不会再发信号。

        按 struct pid 发信号可以消除这个窗口：`pidfd_send_signal(..., PIDFD_SIGNAL_PROCESS_GROUP)`，需要 Linux ≥ 6.9。但 rustix 1.1.6（当前最新版）的 `pidfd_send_signal` 不带 flags，nix 0.31.3 没有这个调用，而本仓库禁止 unsafe（AC-062-05）。Ubuntu 24.04 的 GA 内核是 6.8（CONTRACT 第 15 条支持它）。记为后续：一旦有安全的绑定，就在运行时探测内核是否支持，支持才用它，并保留盯组的做法作为回退。
     5. **执行器约定的措辞**（-303、-359）：组长结束后，执行器在组长仍是未回收的僵尸时向其进程组发 SIGKILL（僵尸占着组号，信号只会到达本组），然后回收组长，再等到组被确认为空（`kill(-pgid, 0)` 返回 ESRCH），并在 `Outcome::group_gone` 中报告。这与 hoh-agents 进程底座 `supervise` 的顺序一致：组 SIGKILL → reap → `group_gone`。测试执行器 `reaping` 也按这个顺序。
     6. **去重键稳定**：无组长的组的结论不再带成员数（`leader_gone_group_not_empty`），重试时同一结论不会被当成新结论（-302、-350）。
   - **设计修正（第五轮审查，同一类第五次，M2T05R-400、-401、-452）**：第四版的模型不变，但它的两处"观察"实现不对：一是把读不出来当成了否定的观察，二是记下的观察时刻晚于观察本身。原则：一次观察只证明它确实读到的东西，它的时刻取在读之前。
     1. **组长状态三分**（-400）：pidfd 的 fdinfo `Pid:` 是组长自己的 pid，才算未回收；是 -1，才算已回收（本机 Linux 7.0 已验证；单元测试 `a_zombie_leader_holds_its_group_until_it_is_reaped` 在每个跑测试的内核上固定这一点，CI 为 ubuntu-24.04）。读失败、缺字段、另一个 pid 命名空间里的 0 或其他数，都不能说明任何事，判为 Lost：不发信号，不算回收，保留槽位。只有组长确认已回收且 `kill(-N, 0)` 返回 ESRCH，才是 Empty。
     2. **观察时刻取在读之前**（-401）：`find` 在读启动时间之前取时刻；`look` 在读 fdinfo 之前取时刻，并用两次读之后的当前时间与上一次 Held 比较。读与记录之间无论停顿多久，下一次 look 都不会把旧观察当成新观察。
     3. **结算一气呵成**（-452）：执行循环的结算把 inspect、原生取消、宽限和停止放在同一个阻塞段里做完，中间没有数据库写入；`lease.inspected`、`lease.native_cancel` 与各步骤事件在此之后按原顺序放在同一个提交里写入，AC-041-02 要求的顺序不变。提交失败的一轮不留任何记录（停止已经做了），下一轮按自己看到的情况记录；M2T05R-06 的测试相应改为断言被截断的一轮不留记录、下一轮看到进程已不在。剩下的间隔只有执行器 `cancel` 本身，它的约定是发出请求后立即返回。
