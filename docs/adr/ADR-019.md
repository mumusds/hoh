# ADR-019 · 启动 reconcile、effect ledger、租约 fencing 与 kill -9 恢复矩阵

状态：采纳（M2-T05，随任务分步补全）

## 背景

M2-T05 要求 host 在 kill -9 后按固定顺序 reconcile（REQ-041），一次迁移中的 state、event、outbox 要么全在、要么全无（REQ-036 AC-036-02），旧 host_epoch 与过期租约的写入被拒（AC-041-02），PID 复用不得误杀（AC-041-03），外部效果走 effect ledger（AC-041-05），并且 recovery 检查要能落地。事实与缺口见 `.hoh-dev/evidence/m2t05-prep/analysis.md`。

## 决定

1. **写入的故障点**（REQ-036，CR-006 F2/F4）。
   - writer 的每个请求带一个上下文 `Ctx`，内容是请求名（"Decide"、"Commit"……）、故障钩子和 host 栅栏（决定 2）。它取代了原来的 `after_events` 闭包。
   - 每个写事务都从 `writer::begin` 开始。唯一的例外是 `begin_host`，它本身就是推进 epoch 的那一步。
   - `FaultHooks::at(job, point)` 依次报告五个点：
     - `Begun`：事务已开始，栅栏已核对；
     - `StateWritten`：状态 CAS 之后；
     - `EventsWritten`：事件之后；
     - `OutboxWritten`：发件箱之后；
     - `Committed`：提交之后、回复之前。
   - 这五个点对应 AC-036-02 的"BEGIN后、state UPDATE后、event INSERT后、outbox INSERT后、COMMIT后ACK前"。
   - 产品实现 `NoFaults` 什么也不做。制造故障的实现（例如进程自发 SIGKILL）只在测试目标里。钩子扫描（`only_the_no_op_fault_hooks_are_in_product_code`）不需要改，因为新方法是已有 trait 的默认方法。
2. **host_epoch 栅栏**（REQ-041 失败模式 4，M2T12R-183）。
   - writer 在 `begin_host` 成功后记下这次 host 的 (project_id, host_epoch)。
   - 此后每个写事务都在 `begin` 中、持有写锁的前提下核对项目的当前 epoch，不一致就以 IntegrityViolation 失败。失败信息注明"0 rows changed"，事务回滚，状态不变。
   - 核对在写锁下进行，所以新 host 不可能在核对与提交之间推进 epoch。
   - 没有开始过 host 的 store（例如测试或 scratch）不受栅栏约束。
   - 核对用 SELECT，不用自赋值 UPDATE：后者会让每个空闲的领取事务也写一页 WAL。
3. **Run 开始运行的通知**（AC-036-02 的迁移）。
   - 决策把 Run 迁入 RUNNING 时，在同一事务中写一条运行时通知 `{"notice":"runtime","kind":"run.started"}`。这条通知发给 `runtime`，指向该决策的 `decision.applied` 事件。
   - 它是 host 循环可以派发该 Run 就绪任务的持久信号：迁移提交之后崩溃，重启后的 host 仍会看到它。
   - 所以"READY→RUNNING 会派发 T1"的含义是：这条迁移的一个事务恰好写入状态、1 个事件和 1 行 outbox。T1 的派发由 host 循环消费这条通知后的调度轮完成（决定 8）。
   - 调度轮仍各自写 `schedule.round` 事件（ADR-017 决定 6 不变）。
   - 这条通知不是 HCP 消息，HCP 投递循环不领取它（ADR-018 决定 4）。
10. **recovery 检查**。
    - `scripts/product/recovery.sh` 运行 `cargo test -p hoh-app --test recovery`，并写出 test-results.jsonl。`tests/check-plan.json` 的 recovery 项改为指向它。
    - 每个 host 都是这个测试二进制自己的一个进程（`recovery_host` 入口），注入点由环境变量选择。这只是测试代码，产品入口不读这些变量。
    - TEST-036-02 的做法：
      1. 从同一份模板数据库恢复；
      2. 子进程启动 host 并提交 READY→RUNNING 的决策，在选定的点自发 SIGKILL；
      3. 不发任何命令，重启 host，等它发布自己的 host.json（被杀的 host 会留下旧的 host.json），再以 SIGTERM 停下；
      4. 读库核对。
      - 5 个点各跑 20 次，证据写入 `test-036-02.json`。

（决定 4–9：进程身份、启动 reconcile 的处置、effect ledger、租约续约与过期链、最小执行循环、AC-027-03，随后续步骤补入。）

## 不在本任务内

- `hoh_app::host::run` 在 `Host::start` 写出 host.json 之后才注册 SIGTERM/SIGINT 处理。二者之间到达的 SIGTERM 会按默认动作终止进程，留下 host.json 与 socket；下次启动能处理这些残留。这个窗口只有微秒级，归 M2-T06（后台 host 生命周期）处理：信号应在 `Host::start` 之前注册，并用一个确定性的钩子测试固定。
