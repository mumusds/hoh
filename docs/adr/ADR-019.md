# ADR-019 · 启动 reconcile、effect ledger、租约 fencing 与 kill -9 恢复矩阵

状态：采纳（M2-T05，随任务分步补全）

## 背景

M2-T05 要求 host 在 kill -9 后按固定顺序 reconcile（REQ-041），一次迁移中的 state、event、outbox 要么全在、要么全无（REQ-036 AC-036-02），旧 host_epoch 与过期租约的写入被拒（AC-041-02），PID 复用不得误杀（AC-041-03），外部效果走 effect ledger（AC-041-05），并且 recovery 检查要能落地。事实与缺口见 `.hoh-dev/evidence/m2t05-prep/analysis.md`。

## 决定

1. **写入的故障点**（REQ-036，CR-006 F2/F4）。
   - writer 的每个请求带一个上下文 `Ctx`，内容是请求名（"Decide"、"Commit"……）、故障钩子和 host 栅栏（决定 2）。它取代了原来的 `after_events` 闭包。
   - 每个写事务都从 `writer::begin` 开始。唯一的例外是 `begin_host`，它本身就是推进 epoch 的那一步。
   - `FaultHooks::at(job, point)` 依次报告五个点：
     - `Begun`：事务已开始，栅栏已核对；
     - `StateWritten`：状态 CAS 之后；
     - `EventsWritten`：事件之后；
     - `OutboxWritten`：发件箱之后；
     - `Committed`：提交之后、回复之前。
   - 这五个点对应 AC-036-02 的"BEGIN后、state UPDATE后、event INSERT后、outbox INSERT后、COMMIT后ACK前"。
   - 产品实现 `NoFaults` 什么也不做。制造故障的实现（例如进程自发 SIGKILL）只在测试目标里。钩子扫描（`only_the_no_op_fault_hooks_are_in_product_code`）不需要改，因为新方法是已有 trait 的默认方法。
2. **host_epoch 栅栏**（REQ-041 失败模式 4，M2T12R-183）。
   - writer 在 `begin_host` 成功后记下这次 host 的 (project_id, host_epoch)。
   - 此后每个写事务都在 `begin` 中、持有写锁的前提下核对项目的当前 epoch，不一致就以 IntegrityViolation 失败。失败信息注明"0 rows changed"，事务回滚，状态不变。
   - 核对在写锁下进行，所以新 host 不可能在核对与提交之间推进 epoch。
   - 没有开始过 host 的 store（例如测试或 scratch）不受栅栏约束。
   - 核对用 SELECT，不用自赋值 UPDATE：后者会让每个空闲的领取事务也写一页 WAL。
3. **Run 开始运行的通知**（AC-036-02 的迁移）。
   - 决策把 Run 迁入 RUNNING 时，在同一事务中写一条运行时通知 `{"notice":"runtime","kind":"run.started"}`。这条通知发给 `runtime`，指向该决策的 `decision.applied` 事件。
   - 它是 host 循环可以派发该 Run 就绪任务的持久信号：迁移提交之后崩溃，重启后的 host 仍会看到它。
   - 所以"READY→RUNNING 会派发 T1"的含义是：这条迁移的一个事务恰好写入状态、1 个事件和 1 行 outbox。T1 的派发由 host 循环消费这条通知后的调度轮完成（决定 8）。
   - 调度轮仍各自写 `schedule.round` 事件（ADR-017 决定 6 不变）。
   - 这条通知不是 HCP 消息，HCP 投递循环不领取它（ADR-018 决定 4）。
10. **recovery 检查**。
    - `scripts/product/recovery.sh` 运行 `cargo test -p hoh-app --test recovery`，并写出 test-results.jsonl。`tests/check-plan.json` 的 recovery 项改为指向它。
    - 每个 host 都是这个测试二进制自己的一个进程（`recovery_host` 入口），注入点由环境变量选择。这只是测试代码，产品入口不读这些变量。
    - TEST-036-02 的做法：
      1. 从同一份模板数据库恢复；
      2. 子进程启动 host 并提交 READY→RUNNING 的决策，在选定的点自发 SIGKILL；
      3. 不发任何命令，重启 host，等它发布自己的 host.json（被杀的 host 会留下旧的 host.json），再以 SIGTERM 停下；
      4. 读库核对。
      - 5 个点各跑 20 次，证据写入 `test-036-02.json`。

4. **进程身份**（REQ-041 b3，`hoh_agents::identity`）。
   - attempts 进入 RUNNING 时记下 pid、`boot_id`（/proc/sys/kernel/random/boot_id）和 `process_start_id`（/proc/<pid>/stat 第 22 字段，即开机以来的时钟滴答）。三个适配器的四处 STARTING→RUNNING 都改用 `identity::running(pid)` 填这些事实。`AttemptRow` 可以读出它们。
   - 只有 pid、boot 与启动时间都相符，才算"是这个 Attempt 的进程"。查找时先打开 pidfd，再重读启动时间。所以核对和之后的每个信号指向同一个进程，PID 复用也改变不了这一点。
   - 不相符时给出依据，不发任何信号：`no_pid`、`boot_id_differs`、`no_process`、`start_time_differs`。
   - 停止流程：
     1. 向它的进程组发 SIGTERM；
     2. 宽限期过后，向进程组发 SIGKILL，并经 pidfd 向组长发 SIGKILL；
     3. 再等组长退出、进程组清空。孤儿进程由新的父进程回收。
     - 只有组长仍存活（pidfd 不可读）或组内还有成员时，才向进程组发信号：进程组 id 在还有成员时不会被复用。
5. **启动 reconcile 的处置**（REQ-041 b1–b2，`hoh_core::reconcile::dispose`，纯函数）。
   - **时机**：`begin_host` 之后、绑定任何监听之前执行，所以完成前不接受写命令。事件顺序是 `reconcile.started` → 每个未完成 Attempt 一条 `reconcile.attempt` → `reconcile.completed`（计数）。
   - **单个 Attempt**：每个 Attempt 的处置写在一个事务里，包括效果迁移、Attempt 迁移（结束时释放租约）、Task CAS 和事件。`reconcile.attempt` 记录处置、找到的进程（依据或停止步骤）、记录的身份和效果迁移。
   - **处置**：
     - 进程停了却没回收干净 → `Unreaped`：什么都不迁移，租约继续占用，因此不会授予新的写租约，并写一条 `reconcile.diagnostic`（PROCESS_NOT_REAPED）。（失败模式 5）
     - STARTED 效果：查到了 → COMMITTED，并记下 external_ref；查不到或无法查询 → UNKNOWN。OBSERVED → COMMITTED。
     - 有效果为 UNKNOWN → Attempt 置为 UNKNOWN_EFFECT。Task 原地不动，不自动新增 Attempt，并写一条 `reconcile.diagnostic`（UNKNOWN_EFFECT），列出这些 effect_key。（失败模式 1）
     - Attempt 自己的工作效果（`work_key(attempt)`）已 COMMITTED → SETTLED；Task 若是 RUNNING，则改为 IMPLEMENTED。
     - PREPARED 且没有已开始的效果 → `Redeliver`：保持原状，它的派发会重投（"确认未发送才重投"）。
     - 其余情况（工作未确认完成，开始过的效果都已查到，或者一个也没开始）→ `Ended`：STARTING 改为 CANCELLED，RUNNING 改为 FAILED，Task 回到 READY，等待新的 Attempt。副作用的 key 对每个逻辑效果稳定，新 Attempt 会按 marker 找到旧 Attempt 已做的部分。
   - **修订 ADR-017 决定 4**：UNKNOWN_EFFECT 也算持有者已结束，进入该状态时释放租约。只有进程已经不在时才会进入 UNKNOWN_EFFECT（适配器在 agent 消失后、reconcile 在确认进程不在之后），未知的是效果，不是仍在运行的写者。原来的规则下，一个 UNKNOWN_EFFECT 会永远挡住所有写任务。
   - 每次 host 启动都写 reconcile 事件，未完成数为 0 时也写，作为每个 host_epoch 的恢复留痕。host 测试里统计"这条命令恰好写了一个事件"的断言，因此把 `reconcile.%` 事件排除在外。
6. **effect ledger**（REQ-041 b6）。
   - 状态依 SQL：PREPARED→STARTED→OBSERVED→COMMITTED，或进入 UNKNOWN。迁移用 CAS，条件是原状态与 attempt_id。
   - 键：
     - Attempt 自己的工作用 `<attempt>/work`，每个 Attempt 一个。执行循环在 agent 执行前写 STARTED（预写），见决定 8。
     - 副作用（例如 PR）的键对每个逻辑效果稳定，它也是远端查找用的 run marker。
   - reconcile 不会重做任何效果，只经端口 `hoh_core::reconcile::Observer` 按 marker 查询。产品实现 `NoObserver` 一律答"无法查询"，结果是 UNKNOWN（失败即关闭）。测试中的 FakeRemote 实现同一端口，并记录查询与创建调用。
   - host 的 `ReconcileSettings` 带停止的宽限时间（默认各 5 s）和 observer。

8. **最小执行循环**（`hoh-app` 的 `host/runner.rs`，AC-041-01）。
   - **何时启动**：配置了 `RunnerConfig { executor, context }` 才启动。产品在 M2-T07 绑定角色之前没有执行器，所以 host 不派发任何东西。
   - **启动顺序**：执行循环在 reconcile 之后启动，与监听器一起停止，并在 store 关闭之前结束。因此它做出或接收的每个派发都在 `reconcile.completed` 之后。
   - **每个 tick**（被提交唤醒，或每 200 ms）：
     1. 为每个工作中的 Run 运行调度轮，直到不再派发。不选任何任务的轮不写任何东西。
     2. ACK 等待中的 run.started 通知。
     3. 把 Attempt 仍为 PREPARED 的派发通知交给执行器；同一 host 内用一个在途集合防止重复处理。
   - **单个 Attempt 的步骤**（每步一个事务）：
     1. 交付派发，执行器的回答即 ACK；
     2. 写收据（consumer `runner`），通知改为 ACKED，Attempt 改为 STARTING，工作效果写为 PREPARED；
     3. 工作效果改为 STARTED（预写，在进程启动之前）；
     4. 启动进程；
     5. Attempt 改为 RUNNING 并带上进程身份，Task 改为 RUNNING；
     6. 进程结束后，工作效果改为 OBSERVED（带结果），再改为 COMMITTED；
     7. Attempt 改为 SETTLED、Task 改为 IMPLEMENTED，或者 Attempt 改为 FAILED、Task 回到 READY。
     - 任何一步不再适用（例如该 Attempt 已被处置）就停下。
   - **崩溃后**：
     - 没收到派发：通知仍为 PENDING、Attempt 仍为 PREPARED，于是重投。
     - 有收据但工作效果未 STARTED：证明工作从未开始。
     - 工作效果已 STARTED：只按 marker 查询，绝不重做。
   - **注入点**：`HostHooks::runner(RunnerPoint)` 依次是 BeforeSend、AfterSend、AfterAck、AfterEffectStarted（RUNNING 事务之后、OBSERVED 之前）、AfterEffectCommitted（任务迁移之前）。产品实现什么也不做。
   - **TEST-041-01**：5 个点各跑 10 次，测试中的 FakeExecutor/FakeAgent 每次执行都把 effect_key 追加到计数文件，结束时写 marker，测试中的 Markers 观察者按 marker 查找。证据中各点的处置如下：
     - 前三个点为 redeliver；
     - AfterEffectStarted 为 unknown_effect；
     - AfterEffectCommitted 为 completed；
     - 没有任何 key 被计数两次。
   - **失败的工作**：Task 回到 READY，没有退避和预算。重试与预算归 M2-T19。产品没有执行器，所以不会出现热循环。

7. **租约续约与过期链**（REQ-041 b4，AC-041-02）。
   - **时钟**：执行循环的时钟是端口 `HostConfig::clock`。产品用系统时钟，测试传入假时钟（CR-006 F2"换时钟"）。
   - **续约**：每 30 s 为在途 Attempt 续约一次，到期时间设为 now + 120 s。只续仍未过期的租约，过期的租约只能按下面的过期链处置，不能复活。
   - **过期链**：每个 tick 先查过期链，再运行调度轮。持有者尚未结束而租约已过期时，过期本身不能证明旧进程已死，依次执行：
     1. 先中止本 host 为它运行的任务，之后不再有别的写入，再重新读取这一行；
     2. 检查进程身份，写 `lease.inspected`；
     3. 经执行器端口发原生取消（`Executor::cancel`），写 `lease.native_cancel`，事件记录是否发出；
     4. 等原生取消的宽限期；
     5. 向进程组发 SIGTERM（`lease.sigterm`），宽限期后发 SIGKILL（`lease.sigkill`），确认组长退出且进程组清空（`lease.reaped`）；
     6. 按 reconcile 的规则处置（`reconcile.attempt`，cause=`lease_expired`）：工作效果已 STARTED 的，查到则完成，否则为 UNKNOWN_EFFECT。
     - 结束（包括 UNKNOWN_EFFECT）时释放租约，同一 tick 的调度轮再以 epoch+1 授予。
     - 每一步单独提交，所以事件顺序就是执行顺序。
   - **无法回收**：进程无法回收时什么都不迁移，租约继续被占用，不授予新的写租约。这个持有者只写一次诊断，留到下一个 host 再处理。
   - **过期的 PREPARED Attempt**：它已无法启动，写者启动需要未过期的租约，因此处置为 `Ended`（CANCELLED，Task 回到 READY），而不是重投。启动 reconcile 同样适用这条规则。
   - **事件 id**：一个 Attempt 被多次处置时（重投、无法回收），事件 id 带处置序号，每次各自独立（events.event_id 唯一）。
   - **TEST-041-02**：在测试进程内运行 host，代理忽略 SIGTERM（SIG_IGN 会被子进程继承）。事件顺序依次为 inspected、native_cancel、sigterm、sigkill、reaped，之后授予 epoch 5。授予时 A1 的进程组为空。A1 迟到的 TaskResult 返回 STALE_LEASE_EPOCH，Task revision 不变，并写一条历史事件；旧 host_epoch 的写入失败，信息为"0 rows changed"。

9. **超大帧只让本 Attempt 失败**（AC-027-03，检查 `integration`）。
   - 三个适配器的 `Outcome` 都新增 `max_buffered`，取值为进程底座报告的 stdout 读取器最大缓冲，作为测试探针。
   - 三个适配器各有一个 TEST-027-03 测试（`test_027_03_{claude,codex,pi}_…`）：
     - 正常帧之后接一行 8 MiB 且无 LF 的数据，同时另一个 Attempt 在同一个 store 上并行运行一次正常回合；
     - 断言：最大缓冲 ≤ 1 MiB + 64 KiB；超大帧 Attempt 为 FAILED，原因 PROTOCOL_FRAME_TOO_LARGE，诊断含长度、前缀 sha256 和前 4096 字节；并行的 Attempt 为 SETTLED；store 的 writer 仍在运行。
   - **"同一 host"的解读**：在 M2-T07 把角色绑定到适配器之前，Engine host 不运行适配器回合（产品没有执行器）。所以这里的"host"是同时运行两个回合和 store 的那个进程，"host 进程未退出"按该进程与 writer 仍在运行来判定。M2-T07 把适配器接入执行循环之后，应在 host 内重测一次。



## 不在本任务内

- `hoh_app::host::run` 在 `Host::start` 写出 host.json 之后才注册 SIGTERM/SIGINT 处理。二者之间到达的 SIGTERM 会按默认动作终止进程，留下 host.json 与 socket；下次启动能处理这些残留。这个窗口只有微秒级，归 M2-T06（后台 host 生命周期）处理：信号应在 `Host::start` 之前注册，并用一个确定性的钩子测试固定。
