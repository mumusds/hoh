## 已采纳决定

1. `spec.drafting` 只记录一次创建；`spec.draft_completed` 绑定最终摘要与实际起草会话。
   T06 合入后改起草者读者，不能重复创建事件或回填不可变历史；此前保留 T06 的夹具。
2. 三个批准入口最终归一为一次事务、一次 revision 的 ApproveSpec；来源失败为 403
   `SPEC_APPROVAL_NOT_USER`、摘要冲突为 409 `SPEC_CONFLICT`，全回滚，不能转成 202 输入拒绝。
   S2 先保护已有直接入口；AnswerQuestion/REPLY 的起草批准接线属于 S5。
3. 后续 PLAN/AUTO 起草以持久 generation 去重：进入 PLAN、用户要求修改、AUTO 内容缺项
   各有原因与 base；同原因/base 不重复，REJECT 复用 Task、新建 Attempt；缺审查不触发起草。
4. 每个请求从真实 listener 对端重新取证；缺证明、非唯一映射、已识别服务/代理都为
   `origin_unknown`。不信客户端 header、token 所有权或 interactive 字段，不要求用户有 TTY。
   同 uid 进程若脱标记、脱祖先链并离开 Attempt cgroup，仍可能不可区分，用户指南公开此限制。
5. 无规格时明确答复 draft 以既有 SetMode 语义进入 PLAN；已有修订时 draft 等同 adopt，不改 mode。
6. T04 交只读 discovery 接缝与 CREATED→DISCOVERING→SPECIFYING 顺序；T07 补 baseline
   内容与离开守卫，T08 在 git init 后补模板 effect。DISCOVERING 不创建 Attempt/effect。
7. 写集取起点到终点提交、跟踪修改/删除及未跟踪路径的完整 Git 字节集合，保留起点观测。
   ignored 文件不能静默省略；不能证明归属/完整性即阻塞。链接不能证明允许写目标，非 UTF-8
   路径可逆显示；不自动还原文件，不声称 Git 观察等于 OS 隔离。
8. 用户批准 draft 时在同一事务走 IMPLEMENTED→VERIFYING→ACCEPTED；不建候选/验证轮次，
   不扩大通用生命周期边。与 T06 最终 Runtime 完成接口合入时核对。
9. 首修订竞争与旧 base 必须事务重查：先 adopt 当前修订、提绑定新 base 的 CR、重新确认；
   旧批准不跨内容/base 生效。历史 NULL 不改写，同摘要按 ADR-033 处理，不能强造空 CR。
10. draft 的 BLOCKED/用户决定请求由 Runtime 转 Run 问题，保存当时 resume_state；
    note 传下一 Attempt，不唤醒无 spec Commander。无结构化问题时显示真实 summary，不猜选项。

## S2：连接来源与批准守卫（AC-008-05 来源部分）

来源是 host 注入的内部类型，不进入 Command JSON。UDS 以 SO_PEERCRED 获取 uid/pid，
绑定进程 start time；TCP 保存已接受 socket 的双向地址，再以本机连接表与 fd inode 找进程。
每命令复查存活、uid、start time、连接归属、环境、祖先及 cgroup；任何不确定性拒绝批准。
标记优先级为当前进程 marker、祖先 ancestor_marker、Attempt cgroup attempt_cgroup；
未知为 origin_unknown。任意 Attempt 均算，不能只查当前 Run/项目。

对端与祖先的身份在取证前后核对，连接建立与请求之间退出/复用、fd 交接、祖先变化、
证据读取失败均不能从异常变为 user。服务/代理有可识别证据时拒绝；无标记的同 uid 任意
进程没有普遍真人证明，这属于上述公开限制。进程读取与连接表读取在 host，SQLite 事务内
只消费来源结论；直接 ApproveSpec 在幂等命中前检查来源，阻止重放用户回执绕过权限。
拒绝时不写 commands、events、specs、Run 或派发。普通命令不受批准权限影响。

2026-11-22 CTO 对“S2 ancestor scan end”的答复已采纳：从对端起向上扫描，包含最后一个
属于 host uid 的祖先，在第一个其他 uid 的祖先或 PID 1 之前停止读取环境/cgroup；边界进程
的 uid、pid、ppid、启动时间仍核对稳定性。扫描内同 uid 的 environ 或 cgroup 不可读就是
`origin_unknown`，不能以它和 host 共祖先而豁免。进程 uid 读取 status 的 Uid 四元组，
不拿 `/proc/<pid>` 的目录所有者替代：不可 dump 的同 uid 进程可能具有 root 所有的目录。
跨 uid 再返回的链（Attempt → sudo/su → 原用户 → approve）不在祖先扫描的可见范围内；
cgroup 模式下，只要仍在 Attempt cgroup，其成员归属检查仍能识别。此限制也写入 docs/12。

UDS 除 SO_PEERCRED 外，以内核 UNIX_DIAG_PEER 查询已接受 socket 的 peer inode，
再核对 `/proc` 中可观察到的 fd 持有者；TCP 以已接受 socket 的双向地址查本机连接表，
要求 ESTABLISHED、同 uid、唯一 inode，再查 fd 持有者。连接建立时绑定 pid/start time/inode，
每个可能批准的命令前后重复核对。fork 到 exec 之间会短暂继承 CLOEXEC fd，实际并发回归已复现
因此误拒普通客户端；不完整的连接映射最多取三次新观测、间隔 10 ms，最后仍不唯一或
找不到则 unknown。已绑定身份改变、同 uid 祖先证据不可读不重试、不放行。netlink 查询有
250 ms 超时；不支持/超时也是 unknown，不退回只信 SO_PEERCRED。

2026-11-23（FLK-05，审查 FLK05-53）：上面的 fork 窗口说的是描述符在 fork 与 exec 之间被短暂复制。
批准夹具里 `tcp_inode` 查的是客户端 socket 的 inode：`tcp_match` 以对端地址为本端、以监听地址为远端。
这个 socket 由 `sudo -n env -i` 启动的 python 在 exec 之后自己 `connect` 创建，python 不 fork。
测试二进制 fork 出的子进程只复制服务端已经 accept 的 socket，那是另一个 inode，不会让客户端 inode
出现第二个持有者。因此“客户端 inode 的持有者不唯一”，以及“把 3×10 ms 再加长”，都不能解释这些夹具里的
`origin_unknown`，也不能当作修复。重试次数与间隔保持不变。

识别服务/代理采用对端的 systemd 服务环境（INVOCATION_ID/LISTEN_FDS/LISTEN_PID）和
明确的代理/服务可执行文件名；INVOCATION_ID 还须结合 cgroup 最内层的 service/scope，
因为 systemd-run 的用户 scope 也设置此变量，不能因此误拒用户。不把继承的 `.service` cgroup 名称单独当作服务身份或用户
身份，否则普通 incus/SSH 登录下的用户进程也会被误判。上述证据不是任意服务的完整分类。
另外，宿主实际存在同 uid 的不可 dump 的 systemd 管理进程，其 fd 无法读取；映射只声明
**可观察持有者唯一**。无关进程的不可读 fd 不使所有连接失败，已选中对端及扫描内祖先
的不可读证据仍拒绝。不可观察进程持有被转交的 fd 不能被本机扫描完整排除；这与同 uid
进程脱离标记、祖先链和 cgroup 的风险一起公开，不声称这是 OS 身份隔离。
测试包括真实 TCP/UDS、标记进程与清除自身标记的后代、cgroup 证据、unknown 矩阵，
以及确定性注入的 PID/祖先/连接竞争和批准重放。夹具证据标为 product 自测；不运行 live Agent，
不声称完成 AC-008-05 的三入口端到端验收。独立审查由主会话另行安排；本委派不启动子审查，冻结后不再修改该候选。

## S2 实施记录（2026-11-22，续作基线 eddfc466）

## S2 CI 夹具更正（2026-11-22，PR #99）

两个真实祖先链测试原来分类测试进程自身，隐含了启动者的同 UID 祖先证据全部可读、
且对端不是服务的假设。GitHub 的失败日志只有 `Unknown != User`，没有祖先取证详情，
不能据它指认 runner 的具体 PID 或失败读取。给断言加入真实分类器的读取轨迹之后，
本机以 `systemd-run --user --pipe --wait --collect` 启动测试二进制，两个断言均失败：
连接映射成功，但同 UID 的 `systemd --user` 祖先的 `environ` 与 `exe` 返回
`PermissionDenied`。`observe` 在读取祖先证据时即返回 None，尚未到对端服务判断；
这证明测试错误依赖启动环境，并非不同 UID 的扫描边界或连接映射应放宽。

正例现在以 `sudo -n -u #<当前 uid>` 启动清空环境的 Python helper，断言其直接父进程
为 root，再分类 helper。TCP 与 UDS 均由 helper 建立真实连接，核对解析得到的 PID/启动
身份，保持重复请求、PID 复用拒绝及关闭连接后的拒绝；关闭 socket 后 helper 仍存活，
避免把连接寿命测试混同于进程退出。管道握手确定就绪及关闭顺序，EOF 释放 helper，
正常路径检查退出码，异常路径也回收；helper 自带期限。缺少 sudo 是测试失败，不跳过。

独立负例由相同的 root 边界启动一个同 UID、不可 dump 的服务父进程及可读取的干净子进程，
确认父进程 `environ` 的读取确为 `PermissionDenied`，并要求子进程来源仍为 Unknown。
原有纯夹具的服务/代理与读取失败负例保留。生产分类规则及受锁契约均未修改。
修复后的 origin 八项测试通过；同一用户服务启动方式下三项真实进程测试通过。
诊断与红绿记录位于 `.hoh-dev/self-tests/m3t04-ci1/`，属于 product 自测，非验收。

## S2 集成夹具更正（2026-11-22，PR #99 续作）

同类审计覆盖所有测试中的批准请求与真实来源分类，包括 host、attach、product、
spec_source、doctor 和 recovery。`spec_source/origin.rs` 的 marker/cgroup 请求仍沿
测试启动器的祖先链取证；`world::exchange` 与 recovery 的 HTTP 夹具也从测试进程
直接批准。基线在同 UID user service 中，spec_source 的 37 项全部失败，恢复测试的
批准最小用例同样收到 `403 SPEC_APPROVAL_NOT_USER(origin_unknown)`。

集成夹具共用 `tests/world/approval.rs`：通过 `sudo -n -u #<当前 uid>`、空环境和
隔离 Python 启动真实同 UID 对端，发送前核对自身 UID 与 root 父进程。marker 放在
该对端，ancestor marker 放在保留标记的已知同 UID Python 父进程，其子进程清除标记。
service、共享 socket、cgroup 移动及同一连接上重算权限的负例继续保留原断言。
普通 ApproveSpec 请求经同一 helper；其他 HTTP 请求仍沿既有夹具发送。恢复测试的
UDS 批准也如此，涵盖批准提交后杀死 host、重启与取消证明；HTTP 字节与幂等键不变。
辅助进程带期限，由创建它的 `output()` 回收；缺少 sudo 或边界不符合假设时明确失败。

额外的 scope 启动审计发现，服务负例原先仅设置 `INVOCATION_ID`，在 `.scope` 中会按
产品规则正确地视为用户，夹具却要求拒绝（202 对 403）。该负例改用明确的 socket
