# ADR-023 · 安装与部署：安装/卸载脚本、systemd --user unit 与崩溃重启

状态：采纳（M2-T14，随任务分步补全）

## 背景

M2-T14 的验收是 AC-005-04（TEST-005-04，检查 `recovery`）与 AC-005-06（TEST-005-06，检查 `deployment`）。done_when 另要求：

- systemd --user unit（Restart=on-failure、有界 StartLimit、Delegate=yes；CR-011：host 在受委托的 cgroup 中运行，Attempt 以其 cgroup 证明终结）随安装脚本落地；
- deployment 检查脚本落地：tests/check-plan.json 不再指向 not-implemented.sh，并产出 test-results.jsonl。

需求依据：

- REQ-005 行为 6：长期服务由 systemd --user 托管（Restart=on-failure、有界 StartLimit，ExecStart 为隐藏 daemon 入口）；logout 后持续运行仅在用户明确启用 linger 时配置。
- REQ-005 决定 4：StartLimitBurst=5、StartLimitIntervalSec=300、RestartSec=5 s（初值）。
- REQ-005 行为 2：Shell 退出、SSH 断开不影响已接受任务。
- REQ-005 行为 4、失败模式 4、5：host 先取项目锁、host_epoch+1、reconcile，之后才接受写命令；同项目并发启动只留一个 host；崩溃后由 systemd 重启，先 reconcile。
- docs/11「生产构建目标」：安装到 ~/.local/bin，资源按版本目录，current 原子切换，现有用户覆盖文件不覆盖。
- docs/11「后台运行」：ExecStart 只用已安装的受支持隐藏入口，unit 带 `Delegate=yes`。

起点（main b1da7a6，M2-T07 已合入）：

- **打包**：`scripts/product/build.sh` 在 run_check 下打 `hoh-release.tar.gz`（hoh/bin/hoh、LICENSE、THIRD_PARTY_NOTICES.md、resources/）。`scripts/install.sh` 存在时，它被放进包里作 `hoh/install.sh`。
- **检查计划**：`deployment` 指向 not-implemented.sh；`recovery` 只跑 `cargo test -p hoh-app --test recovery`；integration 跑 `--test '*'`。
- **版本**：`help::version()` 输出 `hoh <semver>\ncore <v>, agents <v>\n`，没有 commit。AC-062-05 的扫描禁止 workspace 中有任何 build script（`persistence_scan.py`，M2T01R-33），所以不能用 build.rs 嵌入 commit。
- **客户端**：`client::ensure` 先探测，再对项目目录加 flock（最多 10 s，每 20 ms 一次），锁内再探测一次，然后 `start`。`start` 在 cgroup v2、`$XDG_RUNTIME_DIR/systemd/private`、linger、systemd-run 都满足时用受委托 scope，否则直接拉起。就绪的判定：`host.json` 的 pid 等于子进程 pid，且 `/healthz` 返回 200（ADR-021 决定 2）。
- **host 的退出码**：SIGTERM 或 SIGINT 为 0；writer 结束为 1；参数不对为 64；项目被另一个 host 持有为 69；位置或 WAL 拒绝为 78。HTTP 停止宽限 5 s（`SHUTDOWN_GRACE`）。
- **M2-T07**：`__host` 用 `HostConfig::product(project, config, gate = current_exe(), path = $PATH)`。执行器按 host 的 PATH 找 claude/codex/pi，经 `hoh __gate` 启动。ADR-022 决定 17：host 崩溃后，STARTED 而没有观察到结果的 Attempt 由 reconcile 记为 UNKNOWN_EFFECT。
- **预研**（`.hoh-dev/evidence/m2t14-prep/`）：在 `systemd-run --user --scope -p Delegate=yes` 内可以运行一个私有的 `systemd --user`（env -i、临时 HOME、短 XDG_RUNTIME_DIR）。`systemctl --user` 以同一环境与它通信，它能加载并启动 unit；`Delegate=yes` 的服务能在自己的 cgroup 下建子 cgroup；kill -9 MainPID 后 NRestarts=1；`systemctl --user exit` 之后，真实管理器中不留下 unit。2026-11-09 在本 VM（systemd 259）与 GitHub 的 ubuntu-24.04 runner（systemd 255，run 42690870866，临时分支，日志在 `ci-spike/`）上各跑一次，结果相同。私有管理器会在运行时目录下建权限为 000 的 `systemd/inaccessible/*`，拆除时须先 `chmod -R u+rwX` 再删除。

## 决定

1. **unit 模板 `hoh-host@.service`**（REQ-005 行为 6、决定 4；CR-011）

   内容由二进制生成（`hoh __unit template`，见决定 5）。安装脚本把它写到 `$XDG_DATA_HOME/systemd/user/hoh-host@.service`，默认 `~/.local/share/systemd/user`；systemd.unit(5) 把这个目录定为「在家目录中安装的软件包的 unit」。

   ```ini
   # Written by the HoH installer at each install, removed by `install.sh --uninstall`.
   # Local changes belong in drop-ins: systemctl --user edit hoh-host@.service
   [Unit]
   Description=HoH host (project %i)
   StartLimitIntervalSec=300
   StartLimitBurst=5

   [Service]
   Type=exec
   EnvironmentFile=<安装根>/hosts/%i.env
   ExecStart="/home/<user>/.local/bin/hoh" __host ${HOH_PROJECT}
   Restart=on-failure
   RestartSec=5
   RestartPreventExitStatus=64 69 78
   Delegate=yes
   KillMode=control-group
   TimeoutStopSec=15
   StandardInput=null
   StandardOutput=null
   StandardError=append:%t/hoh-host@%i.stderr

   [Install]
   WantedBy=default.target
   ```

   取舍：

   - **重启与限速**：Restart=on-failure、RestartSec=5、StartLimitBurst=5、StartLimitIntervalSec=300，都是 REQ-005 行为 6 与决定 4 的原值。
   - **ExecStart**：
     - 已安装的 `$HOME/.local/bin/hoh`（AC-005-06：「ExecStart 指向已安装二进制」），加上 ADR-021 决定 1 的 `__host <项目绝对路径>`，不新增 daemon 入口。
     - 生成时写成加双引号的绝对路径，只把 `%` 转义为 `%%`。程序路径中的 `$` 不做变量展开，原样写（写成 `$$` 时 systemd 照字面找 `$$`）。
     - systemd 拒绝含 `"`、`\`、`'` 的程序路径（「Executable path contains special characters」，转义也不行），也不允许控制字符。所以 HOME 不是 UTF-8、或含这几种字符时，模板不生成，安装以 78 退出。
     - 以上在私有管理器中逐个字符验证过（2026-11-09，systemd 259；`.hoh-dev/evidence/m2t14-prep/`）：空格、`$`、`%`、反引号、`;`、`:`、`~`、`#`、`*`、`?`、`[`、`!`、`&`、`(`、`{`、`<`、`|`、`=` 与中文都能运行。
     - 不用 `%h`：它是「运行该管理器的用户的家目录」。私有管理器下若它取 passwd 而不取 `$HOME`，ExecStart 就会指到真实 HOME 中的 hoh，破坏测试隔离。
   - **`${HOH_PROJECT}`**：整个值作一个参数（systemd.service(5)），路径中的空格保留。
   - **Type=exec**：exec 失败时 `systemctl start` 就失败。就绪仍由客户端判断（决定 6），不实现 sd_notify：reconcile 可能先停旧进程（每级 5 s），Type=notify 的启动超时会与它耦合。
   - **RestartPreventExitStatus=64 69 78**：这三种退出不是崩溃，重启也不会改变结论。不阻止的话，它们每 5 s 重试一次，直到碰到 StartLimit。
     - 64：参数不对，例如项目目录已删除；
     - 69：项目已被另一个 host 持有（REQ-005 失败模式 4）；
     - 78：位置或 WAL 拒绝。

     SIGKILL、退出码 1（writer 结束，M2T12R-150）与 panic 照常重启。
   - **Delegate=yes**：done_when 与 CR-011 的要求。host 的 `Delegated::detect` 在自己的 cgroup（`…/hoh-host@<h>.service`）下建 `attempt-*`。不启用 controller，所以 host 留在该 cgroup 的根上，不违反 no-internal-process 规则。不用 DelegateSubgroup（systemd 254 才有）。
   - **KillMode=control-group**（默认值，显式写出）：
     - host 崩溃或被停止时，systemd 对 unit cgroup 中剩下的进程（各 Attempt）发 SIGTERM，TimeoutStopSec 之后发 SIGKILL，cgroup 清空后才重启。
     - 所以新 host 的 reconcile 看到旧 Attempt 的 cgroup 已删除或为空，按 ADR-021 决定 8d 直接得到证明。M2T06R-1001 关于同名 scope 重建的规则，对同名 service cgroup 同样适用。
     - 不用 process 或 none：进程会逃出 unit 的生命周期（systemd.kill(5)），停止 unit 或卸载都停不掉 Agent。
     - 不用 mixed：崩溃时剩下的进程直接收到 SIGKILL，没有宽限。
   - **TimeoutStopSec=15**：
     - 正常停止需要 HTTP 的 5 s 宽限，加上 writer 的最后一次写；
     - 同时为崩溃路径设上界：Agent 忽略 SIGTERM 时，从 kill 到重启最坏约 15 + 5 s，加上 host 启动，仍在 AC-005-04 的 30 s 之内。
   - **标准流**：
     - stdin、stdout 为 /dev/null（ADR-021 决定 1）；
     - stderr 在 ready 之前追加到 `%t/hoh-host@<h>.stderr`。该文件在运行时目录中，管理器退出时清除；
     - ready 之后，host 照旧把 stderr dup2 到 `.hoh/host.log`；
     - 客户端读这个文件的末行取得拒绝的码，与直接拉起时读管道相同，不依赖 journald。
   - **启用**：`WantedBy=default.target`，启用的实例随用户管理器启动；有 linger 时即开机启动。

2. **实例名与项目**（AC-005-06：`hoh-host@<项目 hash>.service`）
   - **实例名**：项目规范路径的字节取 sha256，前 16 个十六进制字符。规范路径用 `canonicalize`，与客户端的 `here()` 一致；命名方式与 Attempt cgroup 相同。实例名只由 `hoh_app::unit::instance` 计算。
   - **映射**：每个实例一个 EnvironmentFile `<安装根>/hosts/<h>.env`（安装根即 `$XDG_DATA_HOME/hoh`，见设计修正 1；初版为 `%S/hoh/hosts/%i.env`，已废弃）。
     - 文件权限 0600，目录 0700。
     - 内容两行：`HOH_PROJECT="…"`、`PATH="…"`，双引号内按 systemd.exec(5) 的规则转义 `\ " $` 与反引号。已验证：含首尾空格、`$`、`%i`、`"`、`\`、反引号与 `${HOME}` 的路径经 `${HOH_PROJECT}` 原样成为一个参数（值中不展开说明符与变量）。
     - systemd 拒绝的字符（NUL、U+FEFF、Unicode 非字符）出现时不写文件，按不能用于 unit 处理。
     - systemd 要求该文件是 UTF-8。路径或 PATH 不是 UTF-8 时不用 unit（决定 6 回退）。
     - 先写临时文件再 rename：自动重启时 systemd 会在启动前重读它。
     - 同一 hash 的文件中已经是另一个路径时（碰撞），拒绝，不覆盖。
   - **缺失时**：没有该文件，实例无法启动；`HOH_PROJECT` 指向的目录不存在时，`__host` 以 64 退出，不重启。
   - **PATH 如何到达 host**：用户管理器的环境里没有登录 shell 的 PATH，而执行器按 host 的 PATH 找 Agent（ADR-022 决定 10、17）。
     - `install.sh --project` 写入安装时的 PATH；
     - 客户端每次经 unit 拉起 host 之前写入自己的 PATH。这在项目锁内进行，此时没有 host 在运行；
     - 这与 ADR-021 直接拉起时 host 继承客户端环境的语义一致；开机启动的实例用最近一次写入的 PATH。
   - **只传 PATH 与 HOH_PROJECT**：不复制 API key、代理等环境变量，HoH 不把凭证写进文件（docs/11）。
     - 原生登录（凭证在 HOME 下）不受影响；
     - 依赖环境变量认证的用户，用 `~/.config/environment.d/*.conf` 或 `systemctl --user edit` 的 drop-in；
     - docs/11、docs/12 写明。

3. **安装脚本 `scripts/install.sh`**（包内为 `hoh/install.sh`）

   用法：`install.sh [--project <目录>]... [--linger]`，以及 `install.sh --uninstall`。

   - **root**：euid 为 0 时以 77 退出，什么也不写（与 bootstrap 同理）。全程不调用 sudo（AC-005-06）。
   - **布局**（XDG 变量未设时取默认值）：

     ```
     $XDG_DATA_HOME/hoh/versions/<semver>-<sha256(bin/hoh) 前 12 位>/   包的全部内容（bin/hoh、resources/、LICENSE、
                                                                          THIRD_PARTY_NOTICES.md、install.sh、web/ 若有）
     $XDG_DATA_HOME/hoh/current -> versions/<…>                           新符号链接 rename 覆盖（mv -T），原子切换
     $HOME/.local/bin/hoh -> $XDG_DATA_HOME/hoh/current/bin/hoh
     $XDG_DATA_HOME/systemd/user/hoh-host@.service                        `hoh __unit template` 的输出，内容变化时才 rename 覆盖
     $XDG_DATA_HOME/hoh/hosts/<h>.env                                     每个实例一个（决定 2，设计修正 1）
     ```

     `~/.local/bin` 是 AC-005-06 规定的位置（`command -v hoh` = `$HOME/.local/bin/hoh`）。
   - **版本目录**：按二进制内容命名，一旦写成就不再修改。
     - 先复制到 `versions/.tmp.<pid>`，再 rename；同名目录已存在即为同一内容，跳过。
     - 旧版本目录保留到卸载：运行中 host 的 `current_exe()` 与 `__gate` 都指向它自己的版本目录，删除后它就不能再启动 Agent；回滚也需要（docs/11）。
   - **不覆盖用户的东西**（docs/11）：
     - `~/.local/bin/hoh` 已存在且不是指向本安装的符号链接时，以 1 退出，什么也不改；
     - 从不写 drop-in（`~/.config/systemd/user/hoh-host@.service.d/`）、`~/.config/hoh/` 与项目的 `.hoh/`；
     - 存在整份覆盖的 `~/.config/systemd/user/hoh-host@.service` 时照常安装，但提示它优先于安装的模板。
   - **管理器可达时**（`$XDG_RUNTIME_DIR/systemd/private` 存在）：
     - 执行 `systemctl --user daemon-reload`；
     - 再用 `systemctl --user show -p FragmentPath,LoadState hoh-host@x.service` 确认管理器读到的就是刚写的文件。管理器的 XDG_DATA_HOME 与 shell 不同时读不到，此时以 69 退出，已写的文件保留。
   - **`--project <目录>`**（可重复）：
     - 对每个目录执行已安装的 `hoh __unit enable <目录>`：写 env 文件，执行 `systemctl --user enable hoh-host@<h>.service`。
     - 不加 `--now`：host 在第一次客户端调用或下次管理器启动时启动。
     - 只在用户已开启 linger 时启用。否则管理器在最后一个会话结束时连同 host 一起停止，SSH 断开会中断已接受的任务（REQ-005 行为 2，M2T06R-453）。这时报错并提示 `--linger`，以 69 退出，已装文件保留。
   - **`--linger`**：执行 `loginctl enable-linger "$USER"`，是否允许由 polkit 决定，不用 sudo。只在用户明确给出时配置（REQ-005 行为 6）。
   - **不给 `--project`**：不启用任何实例，也不从当前目录推断。
   - **幂等**：同一个包再执行一次，文件、链接、模板与启用状态都不变；模板相同时不重写，也不 daemon-reload。
   - **输出**：结尾打印版本（`hoh --version` 的前两行）、linger 状态与启用的实例。
   - **后来的修正**（设计修正 2、5、7、8、9、10、11、12）：布局另有运行锁 `R/.lock` 与安装器锁 `$XDG_DATA_HOME/hoh.lock`；安装在安装器锁之下进行，不运行任何程序就能判定的拒绝在它之前，要运行包内二进制的拒绝（版本探测，64；unit 能否使用 HOME 与安装根，78）在它之后、写入任何安装物之前；最后的版本探测失败时以 69 退出；没有自己说法的失败以 74 退出。安装的完整顺序以「现行协议」为准。
   - **自删除**：脚本主体包在 `main "$@"; exit` 中，bash 先读完整个脚本；卸载会删除 `current/install.sh` 自己。

4. **卸载 `install.sh --uninstall`**（AC-005-06：二进制与 unit 删除，项目 `.hoh/` 原样保留）

   > 以下步骤是初版，已被设计修正 1 第 4 条、设计修正 2 第 2 条、设计修正 5、7、8、9、10、11 与 12 取代（现行做法见「现行协议」）：现行做法是先停止并核对实例；管理器不可达而仍有启用的实例、或取不到安装锁时以 69 退出且不删除任何东西；在两把锁之下再以管理器的回答核对一次启用状态；删除只限安装器写入之处，并逐项报告。下文保留初版原文，以便对照第 1、2 轮审查。

   按顺序（初版）：

   1. 管理器可达时，取实例集合：`hosts/*.env` 的名字，并上 `systemctl --user list-units --all --plain --no-legend 'hoh-host@*.service'` 列出的。逐个执行 `disable --now`：host 正常停止，KillMode 停掉它的 Attempt 进程。最后执行 `reset-failed`。
   2. 删除模板，执行 `daemon-reload`；删除 `hosts/` 与 `$XDG_RUNTIME_DIR/hoh-host@*.stderr`。
   3. 删除 `~/.local/bin/hoh`（只在它是指向本安装的链接时）与 `$XDG_DATA_HOME/hoh/`。
   4. 不动 linger、drop-in、`~/.config/hoh/` 和任何项目的 `.hoh/`。脚本根本不读项目路径。
   5. 仍在运行、不受 unit 管理的 `hoh __host` 进程只列出提示，不杀。

   没有安装时什么也不做，以 0 退出。

5. **隐藏入口 `hoh __unit`**

   与 ADR-021 决定 1 的做法相同：`main` 在 `cli::parse` 之前识别它，帮助与补全中不出现，参数不对时以 64 退出。

   - `hoh __unit template`：按 `$HOME` 与本二进制所在的安装根 R 输出决定 1 的模板；不是已安装的二进制时以 78 退出（设计修正 1；初版只按 `$HOME`）。
   - `hoh __unit check <HOME> <安装根>...`（设计修正 9）：对每个安装根调用生成模板的同一函数，不合格时以 78 退出并说明；不要求是已安装的二进制，安装器在写入任何安装物之前用包内二进制调用它。
   - `hoh __unit enable <目录>`：
     1. 规范化目录，计算实例名；
     2. 核对管理器读的 EnvironmentFiles 中恰有 `R/hosts/<h>.env`，只写这个文件（设计修正 1；初版取管理器给出的路径并写入，见 M2T14R-02）；
     3. 执行 `systemctl --user enable`。

     管理器不可达或用户没有 linger 时以 69 退出；路径不能用于 unit（不是 UTF-8，或 hash 碰撞）时以 78 退出。
   - 模块 `hoh_app::unit` 是实例名、模板、env 文件格式与 `systemctl show` 解析的唯一实现，客户端与 doctor 共用。

6. **客户端拉起 host**（修订 ADR-021 决定 2 的第 4 步；启动锁与就绪判定不变）

   在项目锁内、再次探测没有 host 之后：

   1. **unit**。以下条件全部满足时使用：
      - ADR-021 已有的条件：cgroup v2、`$XDG_RUNTIME_DIR/systemd/private` 存在、用户已开启 linger；另外 `systemctl` 在 PATH 上；
      - 本进程就是已安装的 hoh：`current_exe()` 的规范路径等于 `$HOME/.local/bin/hoh` 的规范路径。所以开发构建与 cargo 测试不会碰用户安装的 unit，也不会去查询真实管理器；
      - `systemctl --user show -p LoadState,ExecStart,EnvironmentFiles hoh-host@<h>.service`（经 probe runner，限时 2 s）得到 loaded，且 ExecStart 恰以 `{ path=$HOME/.local/bin/hoh ; argv[]=` 开头（按前缀比对，不拆字段：路径中可以有 ` ; `）；
      - 项目路径与 PATH 都是 UTF-8。

      使用时的步骤：
      1. 写 env 文件；
      2. 执行 `systemctl --user start hoh-host@<h>.service`，限时到 10 s 期限；
      3. 读 `MainPID`；
      4. 每 20 ms 查看一次，直到 `host.json` 的 pid 等于 MainPID 且 `/healthz` 返回 200。这就是 ADR-021 决定 2 第 5 步的判定，只把子进程 pid 换成 MainPID。
   2. **否则按 ADR-021 决定 2**：先尝试受委托 scope，不行再直接拉起。不用 unit 的原因经新环境变量 `HOH_HOST_UNSUPERVISED` 交给 host，与 `HOH_HOST_UNSCOPED` 的做法相同。

   失败的处理：

   - **unit 可用但 `systemctl start` 失败**（StartLimit 已满、exec 失败、env 文件读不了）：以 69 退出，消息带 unit 的 `Result`，并提示 `systemctl --user status hoh-host@<h>.service`。不回退：StartLimit 是有意设的刹车（「有界 StartLimit」），回退会让崩溃循环换个方式继续。
     - systemd 259 的实际表现（私有管理器中验证，2026-11-09）：崩溃循环在限速处停下后，unit 为 failed，`Result` 保留最后一次退出的 `exit-code`；之后窗口内的手动 start 被拒绝，进程不运行，systemctl 报「control process exited with error code」，不是 `start-limit-hit`。所以客户端不靠 `Result` 的取值判断限速，只照实转述 `Result` 与 systemctl 的原话；host 若运行过，再附上它在 stderr 文件中的最后一行。
     - 限速计数随单元被回收而清零（systemd.unit(5)）：停下后无人引用的实例很快被回收，此后的启动不受此前计数影响。所以限速只约束崩溃循环，不约束间隔正常的停止与启动。
   - **期限到时 `systemctl start` 仍未结束**（M2T14R-52；怎样说明以管理器的回答为准，见设计修正 2 第 4 条与设计修正 4）：崩溃后 unit 先停上一个 host 留下的进程，最长 TimeoutStopSec（15 s），start 的 job 在这期间等待。这不是拒绝：客户端以 69 退出，说明启动仍在管理器中进行、稍后再执行 hoh 即可。被杀掉的只是 systemctl，job 不受影响。客户端的期限仍是 10 s（REQ-005 决定 1）；AC-005-04 的 Then 只要求重启与 reconcile 的时序，不要求这次 attach 成功。
   - **MainPID 在就绪之前结束**：读 `ExecMainStatus`。
     - 69：另一个 host 持有项目，再探测并连接它；
     - 78：码取 stderr 文件末行（`refused_code`）；
     - 其他：以 69 退出，消息带该末行。

     systemd 自动重启时 MainPID 会变，客户端跟随新的 MainPID，直到期限。
   - **只有一个 host**：systemd 自动重启的 host 与客户端回退拉起的 host 同时出现时，由 `.hoh` 上的 flock 决定，输者以 69 退出。unit 的 host 因 RestartPreventExitStatus 不再重启；客户端按第 6 步连接胜者。所以仍然只有一个 host（AC-005-02 的性质）。
   - **没有启用的实例**：照样可以 start。崩溃重启只要求 unit 在运行，不要求启用。
   - **RestartSec 窗口内调用客户端**：`systemctl start` 立即启动，取消自动重启的计时。结果相同：一个 host，先 reconcile。

## 设计修正 1（第 1 轮审查：M2T14R-01、-02、-03）

初版把管理器报告的路径当成本安装的：客户端与 `__unit enable` 写入 `systemctl show` 给出的 EnvironmentFiles（多个文件时取到最后一行，即用户 drop-in 加的那个，覆盖了它，-02）；卸载对该路径的父目录 `rm -rf`（drop-in 把它指到项目的 `.hoh/` 时删掉了项目数据，-01）。两者同属一类：写入与删除的目标来自管理器的合并配置。另有 -03：停止实例失败时卸载照样删除版本目录并报告成功，运行中的 host 失去了自己的二进制。修正如下，取代决定 2、4、5、6 中相应的部分：

1. **归属只由安装根决定**。安装根 R = `$XDG_DATA_HOME/hoh`（install.sh 按 XDG 规则取）。已安装的二进制由 `current_exe()` 的规范路径 `R/versions/<v>/bin/hoh` 反推 R；结构不符即不是已安装的 hoh。HoH 写入或删除的路径都在 R 之下，或是安装器自己写的固定位置（`~/.local/bin/hoh` 链接、`$XDG_DATA_HOME/systemd/user/hoh-host@.service`），从不取自管理器的配置。管理器报告的路径（EnvironmentFiles、FragmentPath）只用于核对。
2. **实例文件**为 `R/hosts/<h>.env`。模板写绝对路径 `EnvironmentFile=<R，% 写作 %%>/hosts/%i.env`：私有管理器中验证过空格、`%%` 与 `$` 原样读出（`.hoh-dev/evidence/m2t14-prep/quoting/spike-envfile.sh`）。R 含 `"`、`\`、`'` 或控制字符时不生成模板（78），与 HOME 的规则相同。卸载删除 R 时实例文件随之删除。
3. **核对**。客户端与 `__unit enable` 读 `systemctl show -p EnvironmentFiles` 的全部行：drop-in 可以再加文件（多行），也可以重置后换成别的（已验证）。其中须恰有 `R/hosts/<h>.env (ignore_errors=no)`。没有时：客户端不用 unit，回退到 ADR-021 决定 2，并记录原因；`__unit enable` 以 69 退出。两者都什么也不写。用户加的文件照常由 systemd 读入 host 的环境，HoH 从不写它。
4. **卸载**按顺序：
   1. 管理器可达时，对每个实例执行 `disable --now`，再用 `systemctl show -p ActiveState` 确认每个都是 inactive 或 failed；
   2. 列出本用户中 `/proc/<pid>/exe` 位于 R 之下的进程：unit 外直接拉起的 host、Agent 的启动门 `__gate`，以及没停下的实例。
   3. 第 1 步有失败，或第 2 步列出了进程时，以 69 退出，不删除任何安装物。已停的实例保持禁用，处理掉这些进程后再执行卸载即可继续。
   4. 之后才删除：模板（随后 `daemon-reload`）、`R/hosts`、`R/versions`、`R/current`、`~/.local/bin/hoh`（仅当它是本安装的链接）、`$XDG_RUNTIME_DIR/hoh-host@*.stderr`；最后 `rmdir R`，R 中有别的文件时保留并说明。
   5. 消息按实际结果输出。

## 设计修正 2（第 2 轮审查：M2T14R-100、-101、-102）

第 2 轮 Codex 复现：卸载在 `/proc` 扫描之后、删除之前暂停时，新起的 host（经 unit 或直接拉起）照样启动，卸载随后删除了它的二进制并以 0 退出（-100）。这与第 1 轮的 -03 同属一类，连续第二次出现：「先检查、再删除」中间总有窗口，再加一次扫描也补不上。修正如下：

1. **安装锁**。已安装的 hoh 的每一次运行（客户端、`__host`、`__gate`、`__unit`、WAL 自检子进程）在做任何事之前，对 `R/.lock` 取共享 flock（非阻塞），持有到进程结束。fd 带 close-on-exec，所以 Agent 不会继承它。取不到时（卸载正持有排他锁），以 69 退出，说明本安装正在卸载。（已由设计修正 8 第 3 条收紧：只有 EWOULDBLOCK 才是正在卸载，其他失败说明无法加锁；见「现行协议」。）
2. **卸载**：
   1. 管理器可达时，对每个实例执行 `disable --now` 并核对其状态（设计修正 1 第 4 条）；
   2. 对 `R/.lock` 取排他 flock（非阻塞）。取不到，说明还有本安装的进程在运行：以 69 退出，列出这些进程，不删除任何东西。（已由设计修正 8 第 3 条收紧：只有冲突码 75 才说有进程在运行；设计修正 9 第 1 条在其后再核对一次实例；见「现行协议」。）`/proc` 扫描（`exe` 位于 R 之下的进程）也是一道防线，不只是说明：它覆盖已 exec、尚未取锁的进程；有这样的进程时同样以 69 退出（M2T14R-252，已用测试固定）；
   3. 持有排他锁期间删除安装物，最后删除锁文件与 R。此时新起的本安装进程拿不到共享锁，在做任何事之前就退出：unit 拉起的 host 以 69 退出，不重启；客户端拉起的 host 同样退出。检查与删除由同一把锁连成一体，中间没有窗口。
3. **EnvironmentFile 的通配**（-101）：`EnvironmentFile=` 接受通配表达式，路径中的 `*`、`?`、`[` 会被当作模式。所以安装根含这些字符时，模板不生成（78）。install.sh 在写入任何东西之前就检查安装根（含其规范路径）与 HOME，有这些字符或 `"`、`\`、`'` 时以 78 退出。
4. **超时的说法**（-102）：systemctl 在期限到时还没结束，不能证明 job 已到达管理器。客户端随后用 1 s 查看 unit 的 `Job` 与 `ActiveState`：
   - 有 job，或处于 activating、deactivating、reloading：说明启动仍在管理器中进行；
   - 否则：说明管理器里没有这次启动，请重试。
   - 管理器没有回答时的处理见设计修正 4。

## 设计修正 3（第 3 轮审查：Codex 会话的部分发现）

第 3 轮 Codex 会话在给出报告前被平台中止，原因是其延迟系统调用的实验被判为网络安全风险（attempt NATIVE_FAILED）。它最后的消息指出：卸载完成后，新进程仍可能越过安装锁。按设计修正 2 推演，这有两个窗口，都已用 strace 的系统调用延迟重现：

1. 一个进程在卸载删除期间 exec 并打开了 `R/.lock`，但它的 flock 晚于卸载结束才执行。这时它拿到的是已删除文件上的共享锁，照样运行已删除的二进制。
2. 一个进程读自己的路径（`/proc/self/exe`）晚于卸载删除二进制，读到「… (deleted)」，规范化失败，于是被当作「不是已安装的二进制」，不持锁继续运行。

修正如下：

1. 锁文件由 install.sh 在安装时创建，二进制的运行从不创建它。打开时：锁文件不在、二进制也不在，视为正在卸载；锁文件不在而二进制仍在，说明锁文件缺失、请重新运行发布包的 install.sh（M2T14R-352）；其他失败照实说明（M2T14R-250）。
2. 取得共享锁之后，核对所持文件仍是 `R/.lock` 路径上的那个文件（同一设备与 inode，且未被删除），之后二进制仍在（这一项已被设计修正 6 的运行映像检查取代）。否则以 69 退出。
3. 自己的路径带「(deleted)」或无法规范化，而原路径位于某个安装的 `versions/<v>/bin/hoh` 时，同样以 69 退出。
4. 于是，一个运行要么在卸载取排他锁之前就持有共享锁（卸载因此拒绝），要么在其后退出（还有一个窗口，见设计修正 6）。测试：卸载暂停在删除之前；用 strace 把一个已安装 hoh 的 flock 或 readlink 延迟 4 s，等到卸载完成之后才执行（修正前进程照常输出版本，修正后以 69 退出，并给出各自的理由）；同样的两个延迟跨过卸载与重装（b403d6a：inode 检查与已删除二进制的检查只在这里是唯一的拒绝）；一个已 exec、尚未取锁的运行让卸载以 69 拒绝（M2T14R-252）。

## 设计修正 4（第 3 轮审查：M2T14R-251）

-102 的同类问题第二次出现：客户端在没有得到管理器回答时，仍然断言它的状态。查询 `Job` 与 `ActiveState` 失败、超时（1 s）、非零退出或没有 ActiveState 一行时，结果是空映射，客户端便说「管理器里没有这次启动」，而实际上 job 还在。规则是：只转述管理器的回答，没有回答就说没有回答。结果分三种：

1. 回答中有 job，或处于 activating、deactivating、reloading：启动仍在进行；
2. 回答完整，没有 job，状态已定：管理器里没有这次启动；
3. 没有回答：管理器没有回答启动是否仍在进行，请稍后再执行 hoh。

测试：drop-in 让启动需要 14 s，桩 systemctl 只把这次查询拖住 3 s，客户端说「did not answer」。

## 设计修正 5（第 4 轮审查：M2T14R-300、-301）

这是安装、卸载与运行之间生命周期一类问题的第四次出现（-03、-100、第 3 轮的观察，以及本次）。前几次修正只覆盖「运行」与「卸载」之间，安装器本身之间没有互斥：

- 两个卸载之间夹一次重装时，后一个卸载取到的是已删除的旧锁，照样删除了新安装正在运行的二进制（-300）；
- 安装进行到一半时，卸载可以把它清空，而安装仍以 0 退出（最后的版本探测失败被 printf 掩盖，-301）。

修正后的协议分两把锁，两者互不嵌套于运行：

1. **操作锁**（锁的对象已由设计修正 7 改为 `$XDG_DATA_HOME/hoh.lock`）：每次 install 与 uninstall，在写入任何东西之前（字符检查之后），对 `$HOME` 目录本身取排他 flock，持有到结束；最多等 60 s，否则以 69 退出。于是安装器之间轮流执行，谁也看不到另一个做了一半的结果。锁加在一个从不删除的目录上，所以不会落在已删除的文件上。之所以选 `$HOME` 而不是 `$XDG_DATA_HOME`，是因为后者可能还不存在，而为了加锁先建目录就违背了「拒绝时什么也不写」。hoh 的运行从不取这把锁，所以安装器运行已安装的二进制（`__unit template`、`__unit enable`、`--version`）不会死锁。
2. **运行锁** `R/.lock`（设计修正 2、3）：在操作锁之下，卸载取排他锁之后，也核对所持的文件仍是 `R/.lock` 路径上的那个，且没有被删除；不符即以 69 退出，什么也不删。卸载以只读方式打开它（0400 也能取，M2T14R-351；已被设计修正 7 第 2 条改为能写就以读写方式打开，否则只读）。锁文件不在时，不可能有运行持有它（每个运行都会拒绝），卸载靠 `/proc` 扫描兜底。
3. **失败要如实区分**（第 5 轮，M2T14R-400、-401）：
   - 卸载核对锁身份的每次查询（两次 stat 与链接数）都检查退出状态与输出；任何一次失败都按「无法确认」处理，以 69 退出，什么也不删。
   - 操作锁区分两种情况：在 60 s 内一直被占用（`flock -E 75`），说明 HOME 一直被锁着（持有者不一定是安装器）；根本加不上锁，则照实给出 flock 的退出码与消息。（锁的对象已由设计修正 7 改为 `hoh.lock`，现在说的是该锁一直被持有；两把锁的取锁结果按设计修正 8 第 3 条区分。）
   - **支持边界**（已被设计修正 7 取代：安装器锁改为可写方式打开的文件，HOME 不再加锁）：目录只能以只读方式打开，而 Linux 的 NFS 客户端要求排他 flock 以可写方式打开（flock(2)）。所以 HOME 位于 NFS 时，安装器明确以 69 退出，说明需要本地文件系统上的 flock，不会在没有互斥的情况下继续。这与项目数据拒绝网络文件系统（DB_ON_NETWORK_FS）的做法一致。需求从未要求 HOME 位于 NFS，这不是削减范围。
4. **安装的结果**：最后的版本探测失败时，安装以 69 退出，不再报告成功。从已安装的副本运行 install.sh 时，若锁文件缺失，先补建锁文件，再运行任何已安装的二进制（M2T14R-352）。

测试：
- 安装暂停在发布模板之前时启动的卸载，一直等到安装结束，然后完整卸载；
- 一个 flock 替身在卸载取锁的瞬间换掉锁文件，卸载以 69 退出，什么也不删；
- 0400 的锁可以卸载；锁丢失时，运行说明「锁文件缺失」，已安装的 install.sh 能补上它。

## 设计修正 6（第 4 轮审查：M2T14R-350）

-250 一类（按路径而不是按运行中的映像判断二进制）第二次出现。设计修正 3 之后还剩一个窗口：一个运行读到并规范化了自己的路径，此时还不带「(deleted)」；在它打开锁之前，卸载删除了它的二进制，并重装了同一个包。于是它打开新锁、通过全部按路径的检查，运行的却是已删除的映像。

修正：取得共享锁并核对锁文件之后，以运行中的映像为准，判断运行的仍是安装的二进制：`stat("/proc/self/exe")` 的 nlink 大于 0，且设备与 inode 等于规范路径上的文件。否则以 69 退出，说明「本运行的二进制已被删除或替换」。这一判断取代了原先的 `exists()` 检查。路径里的「(deleted)」仍用来先认出所属的安装，并提早拒绝。

测试：用 strace 只延迟对 `R/.lock` 的那次 openat（8 s），期间完成卸载与重装。修正前该运行照常输出版本，修正后以 69 退出并给出这一理由。

## 设计修正 7（第 5 轮审查：M2T14R-400、-401、-450 至 -457）

两位审查者都认为，前六次修正合起来已经闭合了卸载与运行、安装器与安装器之间的窗口。剩下的问题大多出在操作锁选在了 `$HOME` 目录上：

- 项目目录就是 `$HOME` 时，它与客户端拉起 host 时对项目目录的启动锁是同一把锁（-450）；
- HOME 不可读时脚本以 bash 的报错与 1 结束（-452）；
- HOME 位于 NFS 时，只读打开的目录取不到排他锁（-401）；
- 它以 HOME 为键，安装根却由 XDG_DATA_HOME 决定（-454）。

修正：

1. **操作锁改为文件 `$XDG_DATA_HOME/hoh.lock`**：与安装根同目录、同键；以读写方式打开（NFS 客户端要求排他锁以写方式打开）；任何 hoh 运行都不锁它；卸载不删除它，所以它的锁永远不会落在已删除的文件上。卸载后留下的这个空文件已写进脚本说明与 docs/12。install 在拒绝类检查（字符、外来的 `~/.local/bin/hoh`、`--project` 需要管理器）全部通过后才创建它。（数据目录不存在时卸载不取锁的例外，已由设计修正 8 第 1 条取消。）打不开或加不上锁时照实说明，以 69 退出；在 60 s 内一直被占用时，说明该锁一直被持有（`flock -E 75`）。
2. **运行锁的打开**：卸载对 `R/.lock` 能写就以读写方式打开（NFS），否则以只读方式打开（0400 也能取）；打不开时照实说明（-451、-453）。只有 flock 本身失败时，才说「有程序还在运行」（已由设计修正 8 第 3 条收紧为只在冲突码 75 时这样说）。核对锁身份的每次 stat 都检查退出状态与输出，失败即以 69 退出（-400）。
3. 测试：
   - 安装器持锁期间 `$HOME` 本身仍可加锁；
   - 加不上锁与一直被占用各有消息；
   - stat 失败、锁打不开时卸载什么也不删，且不说有程序在运行；
   - 最后的版本探测失败时安装以 69 退出（-455）；
   - 两个 readlink 测试断言的拒绝理由与修正 6 的不同（-456）。
4. 记录与说明的更正见第 5 轮记录（-456、-457）。

## 设计修正 8（第 6 轮审查：M2T14R-500、-501、-550 至 -554）

两类问题又出现了：

- **生命周期一类**（-03、-100、第 3 轮的观察、-300/-301，本次 -500）：修正 7 留下一个例外，数据目录不存在时卸载不取安装器锁，却照样进入删除。一个悬空的、指向本安装的 `~/.local/bin/hoh` 就能让它走到删除；这时并发的首次安装建好安装根、取得运行锁、启动 `__gate`，卸载随后在锁外把它整个删掉，`__gate` 运行的是已删除的映像（Codex 用命令替身复现）。
- **锁的失败被说成有人持有**，第三次（-401、-453，本次 -501/-551）：运行锁的 `flock -n -x` 任何失败都被说成「有程序还在运行」。

修正：

1. **会改动东西的安装器一律先持锁，没有例外**。卸载先不加锁地看一次：安装根与模板都不在，`~/.local/bin/hoh` 也不是指向本安装的链接时，报告 `not installed`，以 0 退出，什么也不写，也不取锁。这样的卸载只读、什么也不改；安装先建安装根，再发布模板与链接，所以它看到的「三者都不在」在它第一次查看时同时成立，等价于发生在任何安装之前（-550：在常见的家目录里，没装时卸载不留下 `hoh.lock`）。三者有任何一个在时，先建数据目录（与安装相同）、取安装器锁，再在锁下从头判断一次，然后才停止、核对与删除。修正 7 中「数据目录不存在就不取锁」的例外取消。
2. **拒绝都在锁之前**：安装的拒绝类检查（root 77；HOME 与安装根的字符 78；包内没有可执行的 `bin/hoh` 64；外来的 `~/.local/bin/hoh` 1；`--project` 而管理器不可达 69）都在建数据目录与锁文件之前，所以它们什么也不写（-550）。只有一项在锁之后：包内二进制的版本号不合格（64）（设计修正 9 第 2、3 条又加了一项，HOME 与安装根由模板生成器的规则判定，78；版本探测的任何失败都是 64）。判断它要运行该二进制，而从已安装的副本运行 install.sh 时，那是已安装的二进制，要先在锁下补建可能丢失的运行锁才能运行；这时留下的只有安装器锁文件。
3. **取锁的结果按冲突码区分**：install.sh 的两把锁都经同一个函数 `take_lock` 取锁，flock 带 `-E 75`。只有 75 表示被他人持有：安装器锁是 60 s 内一直被持有，运行锁是有程序还在运行。其他退出码照实给出 flock 的退出码与消息，不说有人持有，也不叫用户去停止程序。运行在 Rust 中取共享锁也一样，只有 EWOULDBLOCK 表示正在卸载，其他错误说明「无法加锁」并给出错误（`unit::lock_refusal`）。
4. 测试：
   - 数据目录不存在、有指向本安装的悬空链接时，卸载暂停在查看链接处，这时启动的首次安装要等它结束；之后安装完整，命令可以运行。修正前安装先完成，卸载随后把它删掉。
   - 运行锁的 flock 以非冲突的错误失败时，卸载说无法加锁、给出 flock 的消息，什么也不删，不说有程序在运行。
   - flock 替身只在收到 `-E 75` 时以 75 表示冲突，否则像真 flock 一样以 1 退出，所以去掉 `-E 75` 会被测出。
   - 安装器锁打不开时（同名目录占位），以 69 并说明理由，而不是 bash 的报错与 1。
   - 锁被换掉、无法确认锁身份的测试，也断言不说有程序在运行。
   - 在 `~/.local/share` 已存在的家目录里，没装时卸载什么也不写；缺少 `bin/hoh` 的包被拒绝时什么也不写。
   - `lock_refusal` 的单元测试：EWOULDBLOCK 说正在卸载；EIO、ENOLCK 说无法加锁。
5. 说明的更正（-553、-554）：
   - 决定 3、决定 4、修正 5 与修正 7 中被取代的段落都标明，并指向「现行协议」；
   - 「现行协议」补上安装的顺序与安装器锁的生命周期；
   - docs/12 与 install.sh 的退出码说明补全。

## 设计修正 9（第 7 轮审查：M2T14R-600 至 -602、-650 至 -655）

第 7 轮的问题有三类：

- **生命周期一类又一次出现**（-600）。卸载先停用实例，再取排他运行锁。在这两步之间，直接执行已安装的 `__unit enable` 可以重新启用一个实例；它结束后，启用状态（`*.wants` 链接）留了下来。运行锁只管正在运行的进程，管不到运行结束后留下的持久状态。结果卸载照样以 0 退出，留下指向已删除模板的链接。
- **一条规则有两份实现**（-601、-650）。路径能否被 unit 使用，shell 的 `check_paths` 只看引号、反斜杠与通配符；Rust 的模板生成器（`unit::text_of`、`unit_path`）还看 UTF-8、控制字符、U+FEFF 与非字符。两者不一致：HOME 或安装根含 TAB、换行、U+FEFF 或非 UTF-8 字节时，要到发布模板那一步才以 78 拒绝，这时版本目录、`current` 与命令链接已经写下。
- **失败的说法不实**（-602、-651、-652）：
  - 第一次版本探测失败时，`set -e` 让脚本以该二进制的退出码直接结束，没有说明；
  - 卸载的每种拒绝都以「stop what is named above」收尾，即使列出的只是锁的问题。

修正：

1. **卸载在两把锁之下最后核对一次持久状态**（-600）。取得排他运行锁、核对锁身份并扫描 `/proc` 之后，再枚举一次实例（`R/hosts/*.env` 与 `*.wants/hoh-host@*.service`；设计修正 10 改为与第一遍同一集合，并以 `is-enabled` 核对，不再只看 `.wants`），逐个停用并核对，一个也不能剩下，否则以 69 退出，什么也不删。持有排他运行锁时，任何运行都无法开始（每个运行先取共享锁），所以这一次看到的就是删除时的状态。运行能留下的持久状态只有两样：实例文件在 R 之下，随 R 删除；启用状态由这一步处理。
2. **路径规则只有一份，以模板生成器为准**（-601、-650）。
   - 安装取得安装器锁、补建丢失的运行锁之后，在写入任何安装物之前，用包内二进制执行 `hoh __unit check <HOME> <安装根> <安装根的规范路径>`。它对每个安装根调用 `unit::template`，与发布模板时完全相同，不合格即以 78 退出，只留下安装器锁文件。
   - shell 的 `check_paths` 保留为加锁之前的子集：引号、反斜杠与通配符，不运行任何程序就能判定，拒绝时什么也不写。
   - 包内二进制要在锁之后运行，因为从已安装的副本执行 install.sh 时，它就是已安装的二进制，要先在锁下补建可能丢失的运行锁才能运行（设计修正 8 第 2 条）。

1. **删除所依据的观察一律三态：是、否、无法判断；无法判断就拒绝**（69，什么也不删，说明是哪个观察）。

   - **枚举**：
     - 实例集合（`instance_units`）与启用链接（`enabling_links`）都收集到数组，每个来源的状态都检查：`R/hosts` 不可读、`find` 失败（`wait "$!"` 取进程替换的退出码）、`list-units` 失败，都算无法判断。（`find` 与进程替换已由设计修正 12 第 0 条取代：安装器不再用 find。）
     - 启用链接在用户 unit 配置目录与运行时目录（`$XDG_RUNTIME_DIR/systemd/user`）中查找，用 `find -L`，跟随本身是链接的目录（已由设计修正 12 第 0 条改为按 systemd 读取的那一层列出，不再用 find；设计修正 13 第 3 条再限于 `.wants`、`.requires`、`.upholds` 三类目录）。
2. **决定所依据的值不来自会丢失失败的写法**。
   - 不用进程替换喂循环。
   - 不把命令替换放在参数位置；能用参数展开的就不用外部命令（`basename`、`dirname`、`head`、`tr`）。

3. **收尾按原因说**（续修正 9 第 4 条）：无法判断的情况说「上面所说的无法判断」，不叫用户去停止什么。
4. **hoh 的退出码只沿用 install.sh 自己的那几个**（`refused_by`，-851）：hoh 以 64、69 或 78 拒绝时照用；其他码（崩溃的 101、外来命令链接的 1、不能执行的 126）一律改为该步骤自己的码，并写明原码。包内二进制的 `__unit check` 用 64，已安装二进制的 `__unit template` 与 `__unit enable` 用 69。
5. **不运行程序就能判定的拒绝都在写入之前**：`--project` 不是目录时，在第 1 步以 64 拒绝（-853）。
6. 测试：

   - `id -u` 失败时以 69 退出，什么也不写。

## 设计修正 12（第 10 轮审查：M2T14R-900 至 -904、-950 至 -955）

修正 11 的规则（无法判断就拒绝）在三处没有贯彻到底：

- **管理器的回答**：`is-enabled` 只看文字，不看退出码。一个输出 `disabled` 却以 23 退出的回答被当作「未启用」（-900）。`masked` 被当作「未启用」，可是被屏蔽的实例自己的启用链接可能还在：disable 不删它们，`is-enabled` 也看不见（-901）。
- **存在与否**：bash 的 `-e`、`-L`、`-d` 在不存在时回答「否」，在看不了时（路径上某个目录不可搜索）也回答「否」。所以：
  - 配置目录的父目录不可搜索时，这个目录被当作不存在（-902）；
  - `~/.local/bin` 不可搜索时，命令链接被当作不是本安装的（-903）。
- **测试**：权限测试在临时根删除之后才恢复权限，每次留下 151 MiB（-904）。
- **同一轮 Claude 的发现**：
  - 修正 11 的 `find -L` 会 stat 每个链接的目标，用户配置里任何一个与 HoH 无关、目标无法 stat 的链接都让卸载以「列不出」拒绝（-950，修正 11 引入的回归）；
  - `/proc` 扫描用的安装根解析失败时被并入「否」（-951）；
  - 停用后无法判断时，收尾仍叫用户停止（-952）；
  - `enabled` 在实例之间没有清空，消息里可能是上一个实例的回答（-953）；
  - `refused_by` 沿用 64、69 的两支没有测试（-954）；
  - 若干文字没有跟上（-955）。

修正：

0. **启用链接按 systemd 读取的那一层列出**（-950）：只看单元目录下第一层子目录中名为 `hoh-host@<…>.service` 的条目。按名字识别，跟随作为链接的目录，但不看任何链接的目标。单元目录本身或其中某个子目录读不了或搜索不了时，算无法判断。安装器不再使用 find。（子目录已由设计修正 13 第 3 条限于 `.wants`、`.requires`、`.upholds` 三类；`-d` 不认作目录的子目录按 `there` 判断。）
1. **存在与否也是三态**：`there` 跟随链接，回答在、不在（指向不存在之处的链接也算不在：它被看见了）或无法判断。只有离它最近的、存在的祖先可以搜索（或不是目录）时，才回答「不在」。（「指向不存在之处」的判断已由设计修正 13 第 0 至 2 条取代：`-e` 看不到目标的链接由安装器读出目标再判断，途中的链接也一样。）删除所依据的每个存在判断都经过它，并且都在拒绝检查之前完成：
   - 安装根、模板、命令链接、运行锁、`R/hosts`；
   - 配置目录与运行时目录。
   无法判断就拒绝（69，说明是哪一项）。
2. **管理器的回答要文字与退出码相符**：enabled 与 enabled-runtime 须为 0；未启用的几种状态：
   - disabled 须为 1；
   - static、indirect、generated、transient 须为 0；
   - not-found 须为 4。
   其他组合都算无法判断，包括 masked 与 masked-runtime：被屏蔽的实例使卸载拒绝，解除屏蔽后再卸载即可，用户的屏蔽不被改动。
2a. **其他**：
   - `/proc` 扫描先解析安装根，解析失败算无法判断（-951；已由设计修正 13 第 5 条、设计修正 14 第 3 条细化：安装根不在而解析失败时按它自己的路径找）；扫描中读不到的程序路径，是已结束的进程或别的用户的进程，后者一旦持有运行锁就会让卸载在锁处拒绝。
   - 停用后无法判断的实例单独记为无法判断，不叫用户停止什么（-952）。
   - 每个实例的消息只用它自己的回答（-953）。
3. **测试的清理**：改了权限的测试用一个守卫 `Restore`。它在临时根之后声明，所以先于临时根被丢弃；不论测试怎样结束，权限都先恢复。这些测试还断言临时根已经删除。
4. 测试：
   - `is-enabled` 输出 `disabled` 却以 23 退出（替身，持运行锁之后）时，卸载以 69 退出，什么也不删（私有管理器）。
   - 被屏蔽的实例使卸载以 69 拒绝，解除屏蔽后卸载完成（私有管理器）。
   - `~/.config/systemd` 不可搜索时，卸载以 69 拒绝。
   - `~/.local/bin` 不可搜索时，卸载与安装都以 69 拒绝。
   - 上述测试与原有的权限测试都不留下临时目录。
   - 用户配置里与 HoH 无关的自指链接与悬空链接（顶层与 `.wants` 中）不妨碍卸载完成（-950）。
   - `readlink -f` 失败（替身）时，卸载以 69 拒绝（-951）。
   - 两个实例中除第一个外的停用都失败时，每个停不下来的实例只报它自己的回答（-953）。
   - hoh 以 69、64 拒绝时，安装照用这两个码，不写原码（-954）。
   - fe36f74 补充：`default.target.wants` 本身是链接时，其中的启用链接被读到，没有管理器时拒绝；单元目录本身不可读时以 69 拒绝；模板所在目录不可搜索时以 69 拒绝，什么也不删（-1053）。

## 设计修正 13（第 11 轮审查：M2T14R-1000、-1001、-1050 至 -1055）

问题：修正 12 让 `there` 回答三态，可它仍用 bash 的 `-e`、`-d` 判断经过符号链接的路径。这类测试在目标不存在时答「否」，在目标路径上有目录不可搜索时也答「否」。这是同一类问题连续第三轮出现（-902/-903 之后）：
- 路径本身是链接、`-e` 看不到它的目标时，`there` 一律当作指向不存在之处的链接，回答「不在」（-1000、-1050）；
- 向上找祖先时，一个目标看不到的链接被当作「不是目录」，也回答「不在」；
- `enabling_links` 对子目录仍用二态的 `-d`，目标看不到的 `.wants` 链接被跳过。

于是在没有管理器时，只要某个目录（`~/.config/systemd`、`~/.config/systemd/user`、`.wants`、`~/.local/bin`、模板所在目录）是指向不可搜索之处的链接，卸载就以 0 退出：安装被删除，留下的启用链接、命令链接或模板指向已删除的安装（两位审查者共复现了五处）。

同一轮的其他发现：
- 枚举把单元目录下的每个子目录都当作可能存放启用链接之处，包括别的 unit 的 `.d` drop-in 目录。一个读不了的无关 drop-in 目录让卸载以 69 拒绝（-1001）。本机 systemd.unit(5)：WantedBy=、RequiredBy=、UpheldBy= 只在 `.wants/`、`.requires/`、`.upholds/` 中建链接，`.d/` 只读 `.conf`。
- disable 成功后 `show -p ActiveState` 没有回答，仍被说成「停不下来」，叫用户去停止东西（-1051）。
- 安装根是悬空链接、模板与命令链接还在时，`/proc` 扫描前的 `readlink -f` 解析失败，卸载以 69 拒绝；修正 12 之前这种情况会删掉残留并以 0 退出。ADR 与测试都没写到（-1052）。
- 若干文字没跟上（-1053）；`there` 的「或不是目录」一支没有测试（-1054）；测试辅助代码中一段文档注释挂错了位置（-1055）。

修正：

0. **链接由安装器自己逐个跟随**：任何判断都不经过一个看不清目标的链接。
   - `there`（跟随链接）：路径在，即为「在」；路径是链接而 `-e` 看不到目标时，用 `readlink` 读出目标（相对目标按链接所在目录解析），再对目标问同一个问题（目标在时的回答已由设计修正 14 第 4 条改为无法判断）。
   - 跟随至多 40 个链接，与内核的上限相同：内核解析原路径时跟随的链接至少有这么多，超过时任何进程（包括 systemd）都解析不到，所以算「不在」。
   - 读不出链接算无法判断。
1. **只有看见了才说「不在」**：一个既不在、也不是链接的路径，向上找离它最近的、存在的祖先。
   - 祖先是可搜索的目录，或不是目录：回答「不在」；
   - 祖先是不可搜索的目录：回答无法判断；
   - 途中遇到一个看不到目标的链接时，由 `there` 跟随它：它不在，路径也不在；它无法判断，路径也无法判断。
2. **用在哪里**：删除所依据的每个存在判断都用 `there`：安装根、模板、命令链接、运行锁、`R/hosts`、配置目录与运行时目录。
   - 命令链接本身指向不存在之处时，`there` 说不在，`link_state` 照旧读出它，判断是否本安装的；
   - 它指向的路径上有目录不可搜索时，算无法判断，安装与卸载都以 69 拒绝，什么也不写也不删。这样的布局下，卸载删除安装根、安装运行已安装的二进制本来也会失败；先拒绝，免得删到一半以 74 结束。
3. **启用链接只在 systemd 读的那几类目录中找**：单元目录下第一层中名字以 `.wants`、`.requires` 或 `.upholds` 结尾的目录，包括以点开头的名字（unit 名可以以点开头，systemd 的 `unit_name_is_valid`）。
   - 其中 `-d` 不认作目录的，按 `there` 判断：无法判断即拒绝，在而不是目录、或不在，则跳过；
   - `.d` drop-in 目录与其他子目录不再列出（-1001）。
4. **停用后的回答**：disable 成功之后，ActiveState 没有回答或 `is-enabled` 无法判断（且两者都没有明确说出仍在运行或仍启用）时，记为无法判断，不叫用户停止什么（-1051）。disable 失败、ActiveState 是 inactive 与 failed 以外的状态、或 `is-enabled` 明确说仍启用时，记为停不下来。
5. **不在的安装根不需要解析**（已由设计修正 14 第 3 条取代：这一条的前提不成立，见 -1150；安装根总是先解析）：`there` 说安装根不在时（例如它是悬空链接），`/proc` 扫描只按它自己的路径找（一个从已删除的安装运行的程序，路径仍以它开头），不算无法判断。这时安装根下没有东西可删，模板与命令链接照常删除，以 0 退出（-1052，恢复修正 12 之前的行为）。安装根在而解析失败时，仍是无法判断（-951）。
6. 文字：修正 11、12 中被取代的段落已标注；现行协议的第 2、4a 步注明修正 12、13；安装第 1 步写上「`~/.local/bin/hoh` 是否在无法判断（69）」（-1053）。`Restore` 的文档注释移到正确位置（-1055）。
7. 测试：
   - 卸载以 69 拒绝、什么也不删的情形：
     - `~/.config/systemd/user` 或 `~/.config/systemd` 是指向不可搜索之处的链接，其中有启用实例的链接；
     - `default.target.wants` 是这样的链接；
     - 模板所在目录是这样的链接；
     - `~/.local/bin` 是这样的链接（安装也以 69 拒绝，什么也不写）。
   - `.upholds` 目录或以点开头的 `.wants` 目录中的启用链接，没有管理器时同样拒绝。
   - 一个读不了的无关 drop-in 目录不妨碍卸载完成（-1001）。
   - `~/.config/systemd/user` 是指向自身的链接时，不在，卸载完成；`~/.config` 是普通文件时也一样（-1054）。
   - disable 成功、ActiveState 没有回答时，以 69 拒绝，说无法判断，不叫用户停止（-1051）。
   - 安装根是悬空链接、模板与命令链接还在时，卸载删除它们，以 0 退出（-1052）。

## 设计修正 14（第 12 轮审查：M2T14R-1100 至 -1103、-1150 至 -1152）

问题：
- **路径的字节**：命令替换会去掉输出末尾的所有换行。路径末尾可以有换行，于是：
  - XDG 目录经 `$(xdg …)` 取得，末尾有换行的 `XDG_CONFIG_HOME` 被扫描成另一个目录。没有管理器时，卸载以 0 退出，留下启用链接；`XDG_DATA_HOME` 同样被换成另一个目录（-1100）。
  - `readlink` 读出的命令链接目标也会去掉末尾换行。指向 `$current/bin/hoh` 再加一个换行的外来链接被当作本安装的：安装以 0 退出并保留它，卸载把它删除（-1101）。
- **卸载最后的 daemon-reload**：失败时只打印一句，仍以 0 退出。管理器仍载着已删除的模板，调用方却看不出来（-1102）。
- **已知不是目录的东西**：`~/.config/systemd/user` 是一个可读的普通文件时，卸载说「列不出」，以 69 拒绝。可它之下不可能有启用链接（-1103）。
- **修正 13 第 5 条的回归**：安装根不在时，扫描只按它自己的路径找。可是 `/proc/<pid>/exe` 记的是物理路径：
  - 安装根或 `~/.local/share` 是链接、安装目录被手工删掉时，从它运行的程序路径不以安装根开头，扫描看不见它；
  - 这样的安装根用 `readlink -f` 仍解析得到；
  - 结果卸载删除模板与命令链接，以 0 退出，而修正 12 之前会以 69 拒绝。第 5 条的前提与「恢复修正 12 之前的行为」都不成立（-1150）。
- **内核的 40 个链接**：内核一次查找最多跟随 40 个链接，`there` 读出的每个链接都由内核重新查找，各有 40 个的额度。所以一条总共超过 40 个链接的路径，内核整条查找时报 ELOOP，`there` 却会说「在」，`way` 会说无法判断。记录把 `way` 的这一支说成只有并发改动才走得到，并不属实（-1151）。
- 修正 10 第 1 条与修正 12 第 2a 条中被修正 13 取代的段落没有标注（-1152）。

修正：

0. **路径逐字节传递**：删除所依据的路径都直接取自变量，或者取自保留末尾换行的命令替换（输出后再打印一个 `x`，取值时去掉这个 `x` 与命令自己加的那一个换行），从不经过会去掉末尾换行的命令替换。
   - XDG 目录直接取自变量；
   - 包所在目录（`pwd -P`）、命令链接与 `current` 的目标（`readlink`）、安装根的规范路径（`readlink -m`、`readlink -f`）都这样取。
   - 于是：末尾有换行的 XDG 配置目录按它本身被扫描；末尾有换行的安装根，或解析后末尾有换行的安装根，由 `__unit check` 以 78 拒绝（控制字符）；目标末尾多一个换行的命令链接是外来的（安装以 1 拒绝，卸载保留它）。
1. **卸载最后的 daemon-reload 失败时**：其余照删，逐项报告，然后说明 reload 失败（管理器的退出码与原话），叫用户自己运行 `systemctl --user daemon-reload`，以 69 结束，不说「什么也没删」（-1102）。
2. **已知不是目录的，不必列**：`there` 说在、`-d` 说不是目录时，它之下没有东西：
   - 单元配置目录或运行时目录这样时，没有启用链接，跳过；
   - `R/hosts` 这样时，没有实例文件，跳过（删除时照删）；
   - 是目录而读不了或搜索不了，仍算无法判断（-1103）。
3. **安装根总是先解析**（取代修正 13 第 5 条）：扫描先用 `readlink -f` 解析安装根（已由设计修正 15 改为 `readlink -m`），成功就按解析结果与它自己的路径找。解析失败时：
   - 安装根在：算无法判断（-951）；
   - 安装根不在：只按它自己的路径找，安装根下没有东西可删（-1052，按 4c995c9 的做法）。
4. **内核没有走到的，不说「在」**：`there` 只在内核自己的查找走到这个路径时（`-e`）回答「在」。安装器跟随链接走到了、内核却没有走到时，可能是这期间有改动，也可能是整条路径的链接多于 40 个；bash 的测试分不出这两种情况，所以回答无法判断（-1151）。安装器自己逐个跟随时数到 40 个，仍回答「不在」：这时内核对任何进程都报 ELOOP。`way` 中「这期间出现」的一支因此只有并发改动才走得到。
5. 文字：修正 10 第 1 条、修正 12 第 2a 条、修正 13 第 5 条中被取代的段落已标注；现行协议的退出码与第 4 步已更新（-1152）。
6. 测试：

   - 末尾有换行的 `XDG_DATA_HOME`、解析后末尾有换行的安装根，安装都以 78 拒绝，只留下拒绝本来就会留下的锁文件；

## 设计修正 15（第 13 轮审查：M2T14R-1200 至 -1203、-1250 至 -1252，以及 CI 中一个新测试的失败）

问题：
- **窗口中留下的启动 job**（-1200，high）：最后一遍只看 `is-enabled`，未启用的实例一律跳过。可是运行留下的不只有启用状态：客户端提交的启动在管理器中是一个 job，客户端在 10 s 时限后退出，job 仍在进行。卸载暂停在第一遍之后、取运行锁之前时，客户端可以提交这样一个启动（模板带一个慢的 `ExecStartPre`）。最后一遍看到实例未启用就跳过，卸载以 0 退出，而管理器中这个实例仍处于 activating，引用已删除的安装。这是窗口类问题（修正 9、10）的又一种状态：修正 9 第 4a 步「运行能留下的其他状态都在 R 之下」的推论不完整。
- **扫描的观察失败**（-1201）：`/proc/<pid>/exe` 读不到时 `|| true` 一律当作已结束或别人的进程。一个本用户、仍在运行的进程读不到时（替身让 readlink 对它失败），卸载以 0 退出。
- **rmdir 的失败**（-1202）：删除安装根的 `rmdir` 无论因何失败，都说成「其中有安装器没写过的文件」，以 0 退出；数据目录不可写时，安装根其实是空的。
- **普通文件**（-1203）：`.wants` 目录中名为 `hoh-host@….service` 的普通文件被当作启用链接，没有管理器时卸载以 69 拒绝。systemd 只认符号链接（「is not a symlink, ignoring」），私有管理器对这种布局回答 disabled。
- **扫描对安装根的解析**（-1251）：修正 14 第 3 条用 `readlink -f` 解析安装根，它要求路径中除最后一级外的部分都存在。安装根是指向 `<d>/inst` 的链接（安装接受这种布局），本安装的程序在运行时 `<d>` 连同内容被删掉，解析就会失败。扫描于是只按安装根自己的路径找，看不见按物理路径运行的程序，卸载删除模板与命令链接，以 0 退出。这与 -1150 同属一类，连续第二轮出现：扫描能不能看见一个程序，取决于它能推出的路径。
- **版本目录名**（-1250）：`sha256sum -- <文件>` 遇到含换行或反斜杠的文件名时会转义输出。修正 14 让末尾有换行的包目录可以安装之后，版本目录名变成「反斜杠 + 11 位十六进制」。
- **文字**（-1252）：docs/11 没有写 daemon-reload 失败时的 69；修正 13 第 0 条被修正 14 第 4 条取代，没有标注；`there` 的注释过时。
- **CI**：-1150 的新测试用 `std::fs::copy` 制作要执行的程序。多线程测试中，另一个线程此时 fork 的子进程继承了写句柄，执行时偶尔得到 ETXTBSY（e016cda 的 push 运行 42775489697）。仓库的约定是用 `installed::executable`（在另一个进程中用 cat 写出），这个测试没有遵守。

修正：

0. **「停下」也看 job**（-1200）：一个实例停下，是指管理器回答 ActiveState 为 inactive 或 failed，并且没有排队或进行中的 job（`show -p ActiveState -p Job`，按 `键=值` 读，不依赖输出顺序）；没有回答算无法判断。
   - 第一遍停用后，按这个标准核对；
   - 最后一遍在两把锁之下，对同一集合中每个实例都问一次：既未启用、又停下的，不必再动；否则停用并停止（`disable --now`，stop 取代进行中的 start），再核对；
   - 一个只是被重新启动的实例报告「stopped …: it was started again while the uninstall ran」，被重新启用的照旧报告「disabled …: it was enabled again …」。
   - 修正 9 第 4a 步的推论改为：运行能在管理器中留下的状态是启用与启动（含它结束后仍在进行的 job），两者都由最后一遍处理；其他状态都在 R 之下或属于项目。
1. **扫描中读不到的程序路径**（-1201）：只有下面几种算与扫描无关：
   - 进程已不在，或 `/proc/<pid>` 不属于本用户（别的用户的，或被设为不可转储的）；
   - 内核拒绝本用户查看（C locale 下 `readlink -v` 的原因为 `Permission denied`）：它的凭据或状态超出本用户的普通进程，例如带着一项能力的本用户 systemd 管理器。安装的二进制不带任何能力，本安装的运行都不是这样的进程；
   - 已结束而未被回收（状态 Z 或 X），什么也不运行。
   其他读不到的本用户进程算无法判断（69）。运行一旦持有运行锁，就由运行锁兜住。
2. **rmdir**（-1202）：安装根中仍有条目（含以点开头的）时，照旧保留并说明；否则删除失败照实说明（rmdir 的原话），在其余都已删除、逐项报告之后以 74 结束。
3. **只有符号链接算启用**（-1203）：`.wants`、`.requires`、`.upholds` 中名为 `hoh-host@….service` 的条目，只有符号链接（包括悬空的）才算启用链接。
4. **扫描用 `readlink -m` 解析安装根**（-1251）：不要求路径的任何部分存在。
   - 链接还在时，解析结果就是程序运行时的物理路径（除非链接途中还有被删掉的链接），所以 -1150 与 -1251 的布局都能找到程序；
   - `readlink -m` 失败时（GNU 与 uutils 对自指链接的回答不同），按修正 14 第 3 条处理：安装根在，算无法判断；不在，只按它自己的路径找。
5. **扫描的边界，写明**：`/proc/<pid>/exe` 记的是程序 exec 时的物理路径。卸载能推出的只有两条路径：安装根自己的路径，以及沿着现存的链接解析出来的路径。
   - 程序运行期间，安装根途中的某个链接被手工删掉或改指它处，就没有任何路径还能指向这个程序，扫描找不到它。
   - 这时卸载按现存路径删除的东西，都不是这个程序要用的：它用的是原处（已不可达）的文件；实例已经先由管理器停用；直接运行的程序不用模板，也不用命令链接。这一点写进「已知边界」，不当作无法判断。理由：安装根不在原处时，任何路径都无法证明没有程序在运行；若当作无法判断，卸载就永远清不掉残留的模板与命令链接（-1052 的情形）。
6. **版本目录名由二进制的内容决定**（-1250）：`sha256sum` 从标准输入读，不经过文件名。
7. 文字（-1252）：docs/11 写上 daemon-reload 失败时的 69；修正 13 第 0 条、修正 14 第 3 条中被取代的部分已标注；`there` 的注释已改；脚本头部写上 74 的新情形。
8. 测试：
   - 卸载暂停在第一遍之后，客户端在窗口中启动实例（慢的 `ExecStartPre`），在时限处以 69 退出：最后一遍停止它，卸载完成时实例 inactive、没有 job（私有管理器）；
   - 本安装的程序在运行而它的路径读不到（替身）：69；本用户的僵尸进程不妨碍卸载完成；
   - 数据目录不可写、安装根删不掉：其余照删，以 74 结束，说出 rmdir 的原话；
   - `.wants` 中同名的普通文件不妨碍卸载完成，文件保留；
   - 安装根是指向 `<d>/inst` 的链接，程序在运行时删掉 `<d>`：卸载以 69 拒绝，说出 pid；
   - 末尾有换行的包目录安装后，`current` 指向 `versions/<semver>-<二进制 sha256 前 12 位>`；
   - -951 的测试改为让替身的 `readlink -m` 失败；
   - 制作程序的测试都用 `installed::executable`，安装测试连续运行五次都通过。

## 现行协议（安装、卸载与运行；设计修正 1 至 15 的合并结果）

参与者：
- **安装器**：install.sh 的安装与卸载；
- **运行**：已安装二进制的每次执行，包括客户端、unit 或客户端拉起的 `__host`、`__gate`、`__unit`，以及 WAL 自检子进程。

两把锁：
- **安装器锁** `$XDG_DATA_HOME/hoh.lock`：只有安装器取，排他，持有整个操作期间（最多等 60 s）。安装器因此轮流执行。它由第一个要改动东西的安装器创建（先建数据目录），以读写方式打开，从不删除：卸载删除的「安装器写入之处」不包括它，所以它的锁不会落在已删除的文件上。
- **运行锁** `R/.lock`（R = `$XDG_DATA_HOME/hoh`）：由安装创建。运行在做任何事之前取共享锁，持有到进程结束（close-on-exec，Agent 不继承）。卸载在安装器锁之下取排他锁。
- **取锁的结果**：flock 带 `-E 75`，只有 75（Rust 中的 EWOULDBLOCK）表示被他人持有；其他失败照实说明为无法加锁（设计修正 8）。
- **观察都是三态**（设计修正 11 至 14）：卸载删除所依据的每个观察都回答是、否或无法判断，无法判断就拒绝。只有看见了才说「不在」：可搜索的目录中没有这个名字，途中某处不是目录，或链接多于内核跟随的 40 个；看不清目标的链接由安装器读出目标后再判断；内核自己没有走到的路径不说「在」。路径逐字节传递，不经过会去掉末尾换行的命令替换（设计修正 14）。这些观察包括：
  - 存在与否（`there`，跟随链接）、命令链接的归属（`link_state`）；
  - 管理器的启用回答（`enablement_of`，文字与退出码须相符）；
  - 实例与启用链接的枚举（启用链接只在 `.wants`、`.requires`、`.upholds` 目录中找，含以点开头的名字）。

一次安装，依次：
1. 不写任何东西的拒绝：root（77；`id -u` 失败时 69）；`~/.local/bin/hoh` 读不到，或它是否在无法判断（69）；`--project` 不是目录（64）；安装根是指向自身或不存在之处的链接，或无法解析（78）；HOME 不是绝对路径，或 HOME 含 `"`、`\`、`'`，或安装根（含其规范路径）含这三个字符或 `*`、`?`、`[`（78）；包内没有可执行的 `bin/hoh`（64）；`~/.local/bin/hoh` 存在且不是指向本安装的链接（1）；给了 `--project` 而管理器不可达（69）；
2. 建数据目录，取安装器锁（建不了、打不开、加不上或 60 s 内一直被持有：69）；
3. 安装根已在而 R/.lock 丢失时，先补建它，再运行任何二进制；
4. 运行包内二进制，拒绝时只留下安装器锁文件（以及第 3 步补建的运行锁，若刚补建）：`--version` 失败或版本号不合格时以 64 退出；`__unit check` 按模板生成器的规则判定 HOME 与安装根（含其规范路径）：不是 UTF-8、含控制字符、U+FEFF、非字符或上一步的字符时以 78 退出（设计修正 9）；
5. 建 `R/versions` 与 R/.lock（不在时）；
6. 版本目录：复制到临时目录再 rename，同名已在即跳过，写成后不再修改；旧版本保留到卸载；
7. 以新链接 rename 覆盖的方式切换 `current` 与 `~/.local/bin/hoh`；
8. 模板由已安装的二进制按本 HOME 与 R 生成，内容不同时才写入；管理器可达时 daemon-reload 并核对管理器读的就是它（任一失败或读的不是它：69，已装的文件保留）；
9. `--linger` 时请 logind 开启 linger；每个 `--project` 由已安装的 `hoh __unit enable` 核对并启用（失败时沿用它的 64、69 或 78，其他码改为 69 并写明原码，已装的文件保留，设计修正 11）；
10. 最后运行已安装的 `hoh --version`，失败即以 69 退出，不报告成功。

一次运行开始时，依次：
1. 由 `/proc/self/exe` 的路径认出所属安装；路径带「(deleted)」或无法规范化时拒绝。
2. 以只读方式打开 R/.lock：
   - 不在，且二进制也不在：正在卸载；
   - 不在，而二进制仍在：锁文件缺失；
   - 其他错误：照实说明。
3. 非阻塞取共享锁：被排他持有（EWOULDBLOCK）即正在卸载；其他失败说明无法加锁。
4. 核对所持文件仍是路径上的 R/.lock，且未被删除。
5. 核对运行映像：`/proc/self/exe` 的 nlink 大于 0，设备与 inode 等于规范路径上的二进制。

任何一步不过，都以 69 退出，并说明理由。

安装器的退出码：0 完成；1 外来的 `~/.local/bin/hoh`；64 用法或坏的包；69 管理器、锁、仍在运行的东西，或删除所依据的某项无法判断（以上都什么也不删）；卸载最后的 daemon-reload 失败时，已删的照删、照实说明，也以 69 结束（设计修正 14）；77 root；78 unit 不能用的路径；74 已清空的安装根删不掉（说明 rmdir 的原话，设计修正 15），或脚本没有自己说法的失败（ERR trap 给出命令、退出码与行号，设计修正 10）。

一次卸载，依次：
0. 不加锁地查看：安装根与模板都不在、`~/.local/bin/hoh` 明确不是指向本安装的链接时，报告 `not installed`，以 0 退出，什么也不写（读不到的链接按「在」处理，在锁下拒绝）；
1. 建数据目录，取安装器锁，在锁下从头判断一次（这时已没有安装就报告 `not installed`）；
2. 停止并禁用实例（`R/hosts` 中的、配置目录或运行时目录中任何链接启用的、管理器已加载的），逐个以管理器的回答核对：ActiveState 为 inactive 或 failed，`is-enabled` 明确为未启用（设计修正 10、11、12：文字与退出码相符，masked 算无法判断），并且没有排队或进行中的 job（设计修正 15）；disable 成功而 ActiveState 没有回答时算无法判断（设计修正 13）；管理器不可达而有任何链接启用的实例时拒绝；任何一项列不出或无法判断时拒绝；
3. 取运行锁的排他锁（能写就以读写方式打开，否则只读），并核对锁身份（每次查询都检查）；锁被持有（75）说有程序还在运行，打不开、加不上锁或无法确认身份则照实说明。R/.lock 不在时，没有运行能持有它（每个运行都会拒绝），由第 4 步的扫描兜底；
4. 扫描 `/proc`，找已 exec、尚未取锁的运行（按安装根解析后的路径与它自己的路径；安装根总是先用 `readlink -m` 解析，不要求路径的任何部分存在；解析失败时：安装根在，算无法判断；不在，只按它自己的路径。读不到程序路径的本用户进程，除已结束、内核拒绝查看者外，算无法判断，设计修正 12 至 15）；
4a. 在两把锁之下再看一次同一集合，不是「明确未启用并且已停下、没有 job」的逐个停用、停止并核对（设计修正 9 至 12、15）：一个运行在第 2 步之后、第 3 步之前重新启用的实例（不论由哪种链接启用），或重新启动的实例（包括客户端退出后仍在管理器中进行的启动 job），都在这里被处理；
5. 第 2 至 4a 步有任何问题，都以 69 退出，什么也不删；有进程、锁被持有或实例停不下来时叫用户停止列出的东西；只有某项无法判断，或只有锁的问题时，只叫用户按理由处理（设计修正 9、11、12）；
6. 在两把锁之下，删除安装器写入之处（安装器锁文件除外），并逐项报告；删除模板后的 daemon-reload 失败时，其余照删，最后说明 reload 的失败，以 69 结束（设计修正 14）；安装根已空却删不掉时，照实说明 rmdir 的原话，以 74 结束（设计修正 15）。

窗口与兜底：
- 在卸载取排他锁之前取得共享锁的运行，让卸载在第 3 步拒绝；
- 已 exec、尚未取锁的运行，由第 4 步的扫描兜住；
- 在卸载之后才取锁的运行，由运行的第 2 至 5 步拒绝，跨过重装也一样（第 4、5 步）。
- 一个在第 2 步之后、第 3 步之前开始并结束的运行留下的启用状态（`__unit enable`）或启动（客户端提交、它结束后仍在进行的启动 job），由第 4a 步在两把锁之下停用、停止：此时任何运行都无法开始，看到的就是删除时的状态（设计修正 9、10、15）。运行能留下的其他状态都在 R 之下（实例文件）或属于项目（`.hoh/`，按 AC-005-06 保留）。
- 安装不删除旧版本，所以升级不影响仍在运行的旧映像；install 与 uninstall 由安装器锁串行；只有什么也不改的卸载（第 0 步）不取锁。

已知边界：
- 卸载的 `/proc` 扫描只能按安装根自己的路径与沿现存链接解析出的路径找程序。程序运行期间，安装根途中的链接被手工删掉或改指它处，就找不到它；这时卸载按现存路径删除的东西都不是这个程序要用的（设计修正 15 第 5 条）。
- 同一个 `XDG_DATA_HOME` 的安装器才会互斥。
- 运行锁与安装器锁在 NFS 上依赖客户端的锁支持。运行的共享锁只需读权限；卸载在可写时以写方式取排他锁。

## 风险与待定

1. **顺序**：TEST-005-04 依赖 M2-T07 的产品执行器，M2-T07 已合入（b1da7a6）。
2. **CI**：systemd 255 在受委托 scope 内运行 `systemd --user` 已在 runner 上验证（背景）。runner 镜像变化导致它不再可用时，这些测试失败而不是跳过（docs/09）。
3. **TEST-005-06 的哈希**：第 4 步先停 host 再取哈希。若审查认为 AC 要求 host 运行时卸载、哈希仍不变，两条规格事实上冲突：停 host 必然改动它的运行时文件。那时需要 CR-014（CR-003 D1 类：修正规格之间的不一致）来澄清 pass criteria。
4. **install.sh 的参数**：AC 的 When 没有写参数，本设计需要 `--project`。若审查要求无参调用，改为启用当前目录，不涉及契约。
5. **T2 的重投**：产品中 T2 为 UNKNOWN_EFFECT，不重投，「判定未执行后才重投」只是空真。
6. **journalctl**：私有管理器下 `journalctl --user` 不一定看得到该 unit，以 `manager.log` 与 stderr 文件代替。这只影响观察项，不影响通过条件。
7. **凭证环境变量**：环境变量形式的凭证与代理不会到达 unit 托管的 host，在 shell 中可用的 Agent 在 unit 下可能 BLOCKED_AUTH。
8. **commit 的重编**：若 cargo 不追踪 `option_env!` 的变化，包里可能是旧的 commit。TEST-005-06 会因此失败，不会假通过。
9. **XDG 不一致**：shell 与管理器的 XDG 环境不一致时，安装报错退出 69；客户端回退到 ADR-021 的拉起方式，并记录原因。
