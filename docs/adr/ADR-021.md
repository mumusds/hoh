# ADR-021 · 后台 host、detach/attach、暂停与取消

状态：采纳（M2-T06，随任务分步补全）

## 背景

M2-T06 的验收为 AC-005-02、-03、-05 与 REQ-043 的全部 AC（AC-043-01..05）。AC-005-01 经 CR-010 改归 M2-T13：它要求由 `hoh -p --detach` 拉起的 host 经 FakeAgent 运行 Attempt，产品在 M2-T07/M2-T08 之前没有这条路径。

本任务开始时（main e34be8f）已有的部分：

- CLI 解析已完成：`-p`、`--detach`、`--output`、`attach [id]`。但 `-p` 与 `attach` 都输出 NOT_IMPLEMENTED，以 3 退出。
- host 的启动顺序已就位：位置检查 → `.hoh` 上的 flock → store → host_epoch+1 → 只读连接自检 → reconcile → 监听 → `host.json`。
- 命令只处理 PauseRun。StartRun、ResumeRun、CancelRun 都返回 422。
- 写者只有一条队列。
- settle 已经有原生中断 → SIGTERM → SIGKILL 的顺序（ADR-019 决定 8）。但它把 Attempt 结束为 FAILED，Task 回到 READY，没有取消的处置，也没有可注入时钟的取消状态机。
- TUI 只能离线使用：它的 Ctrl+C 只有「脱离」一项。

事实与缺口见 `.hoh-dev/evidence/m2t06-prep/analysis.md`，决定草稿见同目录的 `adr-021-draft.md`。

## 决定

1. **隐藏的 host 入口**：`hoh __host <项目绝对路径>`。
   - 入口与参数：
     - `main` 在 `cli::parse` 之前识别它，与 `__wal-probe` 相同；
     - 参数形状不对时以 64 退出，什么也不创建；
     - 帮助与补全中都不出现它，`daemon` 一词仍被拒绝。
   - 启动顺序：
     1. 第一条语句调用 `setsid()`。已是会话首进程时跳过（systemd 拉起时），返回 EPERM 时记警告后继续。
     2. 把 SIGHUP 设为"忽略并记日志"。
     3. 启动运行时与 `host::run`。
   - 标准流：
     - stdin、stdout 指向 `/dev/null`；
     - stderr 在 ready 之前连到拉起它的客户端，ready 之后以 `dup2` 指向 `.hoh/host.log`（追加，0600）。
   - 余项：从 exec 到 `setsid` 之间的 SIGHUP 仍会终止 host。要封住它，就得用 unsafe 代码屏蔽信号。
2. **客户端拉起 host 并等它 ready**（REQ-005 行为 4、失败模式 4）：
   1. 对项目做规范化，并做只读的位置检查。拒绝时以 78 退出，什么也不创建。
   2. 快速探测：读 `host.json`，连接其 socket，请求 `GET /healthz`。
   3. 没有 host 应答时，以非阻塞方式对**项目目录本身**加 flock：每 20 ms 重试，最多 10 s。拿到锁后再探测一次。
   4. 拉起 `__host`：不另建进程组，cwd 为项目目录。用户级 systemd 管理器可用时（`$XDG_RUNTIME_DIR/systemd/private` 存在，且有 `systemd-run`），经 `systemd-run --user --scope -p Delegate=yes --quiet --collect --expand-environment=no -- <hoh> __host <项目>` 拉起，host 因而在受委托的 cgroup 中（决定 8d 的 cgroup 方式；`--scope` 执行命令本身，pid 不变）。`systemd-run` 失败（没有到达 host 的 ready）时，改为直接拉起。
   5. 每 20 ms 轮询，直到 `host.json` 写着该子进程的 pid、`/healthz` 返回 200，然后释放锁。
   6. 子进程先退出时：退出码 69 表示项目已被另一个 host 持有，重新探测；78 原样转出；其他退出码以 69 退出。

   只有客户端会取这把启动锁，host 不取，所以不会与等子进程的客户端互锁。并发启动时，竞争失败的客户端不会留下任何 host 进程（AC-005-02："首个 ready 后全程恰 1 个 host"）。
3. **端口**：`HostConfig::new` 仍用 8787。它被占用（EADDRINUSE）时，host 改绑端口 0，并把实际端口写入 `host.json`。客户端只走 Unix socket。进程内的测试 host 仍用端口 0。
4. **客户端传输**：
   - 协议：std `UnixStream` 上的阻塞 HTTP/1.1，带读写超时，`Connection: close`。
   - 解析：状态行与头部用 `httparse` 解析（它已在 Cargo.lock 中，此处改为直接依赖）；客户端自己解码 Content-Length 与 chunked 的正文，并带一个只认 `id:`、`data:` 的小型 SSE 解析器。
   - 令牌：取自 `host.json`，放在 `X-HoH-Token` 头中。遇到 403 时重读 `host.json`：若答话的已是另一个 host（另一个令牌），命令以同一个 key、逐字节相同的正文发给它（M2T06R-04）。
   - 路径与查询：用户给的 run id 放进路径段或查询值之前，除 RFC 3986 的非保留字符外逐字节百分号编码，所以它只指名那个 Run（M2T06R-54）。
   - 错误码：拒绝的正文没有 code 时，按状态取 openapi Error 的码（400 BAD_REQUEST、403 FORBIDDEN、404 NOT_FOUND、409 CONFLICT、422 UNPROCESSABLE，其余 GONE）；host 启动以 78 被拒时，取它最后一行所带的码（DB_ON_NETWORK_FS、DB_WAL_UNSUPPORTED 等），没有时为 GONE（M2T06R-60、-61）。
   - 幂等：每个用户动作取一个新的 UUIDv4，同时作为 `command_id` 与 `idempotency_key`。在 10 s 之内，以同一个 key 和逐字节相同的正文重试（发出后连接中断，或返回可重试的 503）。
   - 不引入新 crate：hyper 的 client 特性所需的 `want` 不在 Cargo.lock 里，也不在离线 registry 里。
5. **StartRun**：在 `submit` 中新增一个分支，整个过程在一个事务里完成：
   1. 查幂等记录；
   2. 由 host 分配 run_id；
   3. 写入 run 行：CREATED，mode 取自载荷，revision 为 0，`config_snapshot_json` 为空对象（调度轮对缺省的键取内置默认值，CR-007）；
   4. 追加事件 `run.created`；
   5. 写入 commands 行，其 `result_json` 为确切的 202 正文：`{command_id, run_id, revision: 0, status: "ACCEPTED"}`。

   `expected_revision` 必须为 0。没有执行器时（M2-T07 之前的产品），Run 停在 CREATED，可以附着、暂停、取消。

   客户端的 `-p '<目标>' --detach`：
   - 只在收到 202 之后输出：json 模式输出 202 正文加换行；text 模式在 stdout 输出 run_id，在 stderr 提示 `hoh attach <id>`。
   - `--detach --output stream-json` 在解析阶段以 64 拒绝。
   - 失败时 stdout 为空，stderr 写 `hoh: <code>: <message>`（AC-005-05）。code 取以下之一：收到的 Error.code；启动失败的 code；无法连接 host 时为 openapi 已有的 `GONE`。没有新增原因码，所以不需要 CR。
   - 退出码：不可达时 69，位置或 WAL 检查失败时 78，其他拒绝为 1。

   不带 `--detach` 的 `-p` 仍归 M2-T13。
6. **attach**（REQ-005 行为 3、5，失败模式 2、3；REQ-003 行为 7）：
   - 选择 Run：
     - 没有 `.hoh/state.db`：没有 Run，不拉起任何东西；未给 id 时以 64 退出，给了 id 时报 RUN_NOT_FOUND。
     - 否则先确保 host 在运行，再请求 `GET /v1/runs`（新路由，按 openapi listRuns：`Page`，最新的在前，cursor 不透明）。
     - 给了 id：请求 `GET /v1/runs/{id}`，404 时在 stderr 写 `RUN_NOT_FOUND`，以 64 退出。
     - 未给 id：沿 `next_cursor` 读完全部分页，再取非终态的 Run（M2T06R-05、-51）。恰有一个时附着它；为零个或多于一个时以 64 退出，并在 stderr 列出全部候选。在 M2-T13 的选择器之前，有 TTY 时也这样处理。
     - 选定之后才订阅。
   - 输出方式（AC-005-02 要求 PAUSED 的 Run 上保持 10 s，所以 PAUSED、BLOCKED、INCOMPLETE、WAITING_EXTERNAL 都不结束附着）：

     | 条件 | 行为 |
     |---|---|
     | stdin 与 stdout 都是 TTY，且为 text | TUI（决定 10） |
     | `stream-json` | `/v1/events?run_id=R&after=0`：先回放，再接 live，每行一个 Event |
     | 无 TTY 的 text | 进度写 stderr，最后一行写 stdout |
     | `--output json` | 输出一次快照对象，以 0 退出 |

     流式的两种方式跟随 Run，直到出现以下情况之一：
     - 收到该 Run 的结束事件（`run.completed`、`run.failed`、`run.cancelled`），退出码按 REQ-004 的表。以结束事件为准而不以当前状态为准：附着前已结束的 Run，其全部事件都先回放完（M2T06R-03）。没有结束事件就进入终态的 Run（目前没有这样的路径），在 5 s 没有新事件之后按状态结束；
     - 客户端收到信号，以 129、130 或 143 退出。
   - 其他：
     - 断线后从最后见到的 seq 之后重新订阅（`after`），host 已不在时重新走拉起流程；
     - 每条 SSE 流持有一个计数守卫，`Host::subscribers()` 在进程内读取它（与 `diagnostics` 相同，ADR-016 决定 10）；
     - attach 不发送任何命令，也不建 Run、Task 或 Attempt。
7. **host 循环、暂停与恢复**：
   - **host 循环**：reconcile 之后总是运行，没有执行器时也运行。它由以下三者唤醒：水位、命令处理器的通知、200 ms 的 tick。调度轮、派发、续租与 ADR-020 的节奏作业只在有执行器时运行；暂停与取消的推进总在运行，否则产品中的 Run 会一直停在 PAUSE_REQUESTED 或 CANCEL_REQUESTED。
   - **暂停事务**：沿用 ADR-016 决定 4，置 PAUSE_REQUESTED 与 `resume_state`。
   - **PREPARED 守卫**：执行循环接收派发时，在同一事务中确认 Run 处于工作中的状态（CREATED、DISCOVERING、SPECIFYING、READY、RUNNING、VERIFYING），否则什么也不启动；暂停中、已暂停、取消中与终态都不启动。
   - **安全点**：`Store::pace_control` 每个 tick 处理 PAUSE_REQUESTED 的 Run。
     - 先撤回尚未领取的 PREPARED：Attempt 置为 CANCELLED，Task 回到 READY，释放租约，确认其派发通知，写 `pause.withdrawn`。不计数，不退避（ADR-020 决定 3）。
     - 没有 STARTING 或 RUNNING 的 Attempt 时，在一个事务里：Run 置为 PAUSED，追加 `run.paused`，确认暂停通知。UNKNOWN_EFFECT 不阻止进入 PAUSED。
     - 运行中的 Attempt 不会收到信号。
   - **ResumeRun**：只能从 PAUSED 发起，全部在一个事务里：
     1. 一次限于该 Run 的 reconcile：确认 Run 没有未结束的 Attempt（有就返回 409 ILLEGAL_TRANSITION，什么也不写），并列出其 UNKNOWN_EFFECT 与租约；
     2. 写一条带 run_id 的 `reconcile.run` 事件，id 为 `child_id(run, "resume/<command_id>")`；
     3. CAS 回到 `resume_state`；
     4. 追加 `run.resumed`。ResumeRun 不写运行时通知：恢复之后只有调度轮在等它，它们看的是 Run 的状态。

     派发只来自之后的调度轮，所以 reconcile 事件的 seq 总小于任何新派发。
   - **优先级**：CANCEL_REQUESTED 期间的 Pause 返回 409 ILLEGAL_TRANSITION；PAUSE_REQUESTED 或 PAUSED 期间的 Cancel 被接受（REQ-043 行为 8）。
8. **取消**。
   - **a. 优先通道**：写者增加第二条有界队列（16 个槽位），每处理一个主队列作业之前先把它排空。
     - 加急的发送同时向主队列 `try_send` 一个 Wake 作业，以唤醒阻塞在 `blocking_recv` 上的写者。
     - 它承载 CancelRun 与取消的最终提交。
   - **b. 取消事务**：
     - Run 置为 CANCEL_REQUESTED；
     - 其 PREPARED、STARTING、RUNNING 的 Attempt 置 `cancel_requested = 1`；
     - 写入 `run.cancel_requested`、`run.control` 通知与 commands 行；
     - 终态的 Run 返回 409。
   - **c. 取消状态机**：hoh-core 的 `cancel` 模块，是一个纯状态机。
     - 输入：host 时钟的 `now`，与 `ProcessControl` 的一次观察（Held、Empty 或 Lost）。输出：要执行的动作。
     - 顺序：
       1. 先发原生中断；
       2. 10 s 后仍为 Held，发 SIGTERM；
       3. 再过 5 s，发 SIGKILL；
       4. 此后仍为 Held，每 5 s 再发一次 SIGKILL。
     - Lost 表示不再发信号，但继续观察。只有观察到 Empty 之后才写 CANCELLED（REQ-043 行为 5、失败模式 2、AC-043-05）。
     - 产品的 `ProcessControl` 包装 ADR-019 的 `Found::look`、新的公开 `Found::send`（只在一次 Held 的观察之后立即发信号）与 `Executor::cancel`。它在 `spawn_blocking` 中运行，每 10 ms 观察一次。
     - 一轮的各步（`cancel.native_cancel`、`cancel.sigterm`、`cancel.sigkill`，以及结束的 `cancel.reaped`、`cancel.lost` 或 `cancel.unreaped`）按顺序一起提交（ADR-019 决定 7）。
     - 一轮没有以 Empty 结束时，Run 保持 CANCEL_REQUESTED，下一步（间隔 1 s）再来一轮。同一 Attempt 连续以 Lost 结束且没有发出信号的轮只记一次（每个发现一条记录）。
     - 两段宽限期在 M2-T07 读取配置之前为常量 10 s 与 5 s。
   - **d. Attempt 的进程与终结证明**（REQ-043 决定 3 经 CR-011 修订，CONTRACT §7 单写者；第 5 版，M2T06R-01、-100、-101、-200、-300、-301）：
     - **Attempt 的进程**：leader 的进程组，加上它在组外的后代。组信号到不了离开进程组的后代（setsid、setpgid）。
     - **一条规则，四条路径**：凡是结束 Attempt 或释放其写者租约的路径，都先取得终结证明；没有证明，就不结束 Attempt，也不释放租约。四条路径是：
       1. 取消（决定 8c）；
       2. 执行器报告 leader 结束、进程组已空（`Outcome.group_gone`），在记 COMMITTED 之前；
       3. 租约到期或执行器丢失的 settle；
       4. host 启动时的 reconcile。

       没有证明时：取消让 Run 保持 CANCEL_REQUESTED；第 2 条记 `runner.unreaped`，Attempt 与槽位保留，之后由 settle 接手；第 3、4 条记为 `Stopped{reaped: false}`，处置为 Unreaped。
     - **两种跟踪方式**，每个 Attempt 在启动门打开之前定下其一，记入事件 `attempt.tracking`：
       - **cgroup（证明）**：host 启动时读 `/proc/self/cgroup`（v2）。若自己所在的 cgroup 受委托（可写、能建子 cgroup），则每个 Attempt 在其下有一个专属子 cgroup，名为 `attempt-<sha256(<project_id>/<attempt_id>) 的前 16 个十六进制字符>`。
         - leader 在启动门打开前（它还没运行任何代理代码）写入该 cgroup 的 `cgroup.procs`，其后代都继承这个 cgroup，任何 fork、setsid、线程或环境变化都离不开它。
         - 事件里记下 cgroup 的路径，所以下一个 host 即使在另一个 scope 里，也能找到它。
         - 停止：SIGTERM 发给进程组与 cgroup 的每个成员；宽限之后写 `cgroup.kill`，由内核一次杀尽，包括同时 fork 出的进程。
         - 终结证明：进程组为空，且 `cgroup.events` 为 `populated 0`。证明之后删除该子 cgroup。
         - 取消路径按决定 8c 的阶梯（SIGTERM 一级发给成员，SIGKILL 一级用 `cgroup.kill`）；第 2 至 4 条路径在停止进程组之后，对 cgroup 再走一遍 SIGTERM、term_grace、`cgroup.kill`、kill_grace。
         - 建子 cgroup 或移入失败时，这个 Attempt 退回 proc 方式，原因记入事件。
       - **proc（降级）**：没有受委托的 cgroup 时（例如 host 由客户端直接拉起而 `systemd-run` 不可用，或测试进程内的 host），按第 4 版的扫描尽力查找：
         - 查找依据：`/proc` 父链，以及执行器以 `HOH_ATTEMPT_ID=<project_id>/<attempt_id>`（`Work::marker`）启动 leader 后被后代继承的环境标记；
         - 用 pidfd 固定找到的进程，并核对启动时刻；leader 按记录固定，只在活着时作为父链的根；
         - 扫描先读 `ns_last_pid`，列出 `/proc`，读标记，再逐个检查期间分配的 pid，直到不再有新分配；一次扫描中找到过带标记的进程，这次扫描就不算安静；主线程已退出时，查看其存活线程的环境；
         - 证明的条件：进程组为空，没有存活的固定进程，且组空之后连续两次完整扫描都没有找到组外进程。

         这种方式**不是证明**：`/proc` 不是原子快照，蓄意躲避的进程可以避开它。已知的情形有：
         - 最后一次读 `ns_last_pid` 之后，一个已检查过的进程 fork 后退出（M2T06R-300、-350）；
         - 在第一次读 `ns_last_pid` 之前已分配、却还没挂到 `/proc` 的 pid；
         - 线程的种种变化；
         - 标记被清掉或环境不可读（M2T06R-153）；
         - `hidepid`（M2T06R-255）。

         所以每个这样的 Attempt 都记为 `tracking: proc` 的降级，由 `hoh doctor` 报告（CR-011）。
     - 扫描与观察的时机（proc 方式）：进程组存活时，至少每 100 ms 扫一次，且不计入证明；进程组为空之后，每次观察都扫。一轮之内信号送不到任何进程时，这一步照样计入阶梯的时刻，不会原地重试（M2T06R-201）。
     - 历史：
       - 第 1 版只在一轮开始时沿父链扫一次（M2T06R-01）；
       - 第 2 版只用于取消路径（M2T06R-100、-101）；
       - 第 3 版只有列表一步（M2T06R-200）；
       - 第 4 版以 `ns_last_pid` 补扫，仍被最后一次读取之后的 fork 与线程击穿（M2T06R-300、-301）；
       - 第 5 版按 CR-011 改以 cgroup 为证明，/proc 只作有记录的降级。
     - 产品执行器（M2-T07）必须设置标记；产品 host 由 M2-T14 的 systemd unit（`Delegate=yes`）或客户端经 `systemd-run` 拉起，在受委托的 cgroup 中运行（决定 2）。
   - **e. 取消优先于其他处置**：适用于 `runner_finished`、reconcile 的 `dispose` 与 settle。`cancel_requested` 在施加处置的写事务里重读，不取扫描时的值：扫描之后才提交的 CancelRun 照样优先（M2T06R-02）。
     - 带 `cancel_requested` 的 Attempt 结束为 CANCELLED；其未观察到的 STARTED 工作效果记为 UNKNOWN。
     - 不经过 `fail_task`：不计数，不重试。
     - Unreaped 照旧不移动任何东西。
   - **f. 最终事务**：在 Run 不再有 PREPARED、STARTING、RUNNING 的 Attempt 之后执行。先在事务之外计算工作区记录，然后在一个事务里：
     1. 写 `cancel.workspace`，内容为 `{head, head_tree, diff_sha256, untracked_sha256, untracked_unhashed, status_sha256, workspace_sha256, logs: [{attempt_id, raw_log_path}], host_log}`；
     2. 非终态的 Task 置为 CANCELLED，残留的 PREPARED Attempt 置为 CANCELLED，释放租约，确认待处理的运行时通知；
     3. Run 置为 CANCELLED，追加 `run.cancelled`。

     不写 candidates，所以未完成的候选不会被标为 verified。
   - **g. 工作区哈希**：只读的 git 命令，以 argv 方式运行，带 `--no-optional-locks` 与 `-c core.fsmonitor=false`，每条限时 5 s：
     - `rev-parse HEAD` 与 `HEAD^{tree}`；
     - `diff --binary --no-ext-diff --no-textconv HEAD`（没有 HEAD 时对空树），在进程内求哈希；
     - `ls-files -z --others --exclude-standard`，逐项在进程内求哈希，不跟随链接，也不打开普通文件以外的东西（M2T06R-06、-53）：符号链接取其目标路径；FIFO、socket、设备与目录只记类型；普通文件以 `O_NOFOLLOW|O_NONBLOCK` 打开，`fstat` 仍为普通文件时才流式读取；
     - `status --porcelain -z`。

     未跟踪文件内容的哈希共有 5 s 预算：超出预算后，剩下的文件按大小与修改时刻记录，`untracked_unhashed` 记下这样记录的文件数（M2T06R-102）。整个记录在阻塞线程上计算，不占异步工作线程。它们都不写对象、索引或引用。目录不是 git 工作树或 git 失败时，记下错误，取消照常完成。不用 `write-tree` 加临时索引或 `stash create`：两者都会向用户的对象库写入。
   - **h. 标签**：`lifecycle::label` 把 CANCEL_REQUESTED 映射为 `"CANCELLING"`，其余状态原样，作为 `projection.label` 输出。projection 是自由格式，不需要 CR。
   - **时间预算**：AC-043-02 的场景（小工作区，没有组外进程）中，SIGKILL 约在第 15 s 发出，进程组在毫秒级内清空，git 约 1 s 以内，总计约 15.5 s，在 17 s 的限额之内。最坏情况更长，17 s 只对该场景成立（M2T06R-256、-355）：
     - 工作区记录的 git 命令共 5 条，每条最多 5 s；未跟踪内容的哈希最多 5 s。
     - 取消路径中，组外进程（cgroup 成员或 proc 方式找到的进程）随进程组的阶梯一起收到信号，不另加时间。
     - 执行器报告结束、settle 与启动 reconcile 三条路径，在进程组之后对组外进程再走 term_grace 与 kill_grace 两级（各 5 s）。
9. **与 Commander 无关**（REQ-043 行为 7）：暂停、恢复与取消的路径不经过 Commander 端口，不发送 HCP Message，不创建 Task 或派发。`run.control` 是只由 host 循环消费的运行时通知（ADR-016 决定 5、ADR-018 决定 4）。

   TEST-043-04 用一个计数器记录 Commander 的入口：执行器对 commander 角色的投递与启动一律失败并计数。本任务的 host 还没有 Commander 的 HCP 投递循环，World 里也没有 commander 绑定或 Task，所以「FakeCommander 调用次数 = 0」这一项目前不可能失败（M2T06R-56）；到 M2-T08 有了 Commander 路径之后要重新核对 TEST-043-04。
10. **TUI attach**（AC-043-03）：有 TTY 的 `hoh attach` 打开绑定到该 Run 的 Workspace。
    - 显示：头部显示 run id 与标签，时间线显示 `#seq kind`。
    - 事件读取：一个读线程经阻塞的 `UnixStream` 读 SSE，送入 mpsc；poll(2) 循环每个 100 ms 的间隔取走收到的事件（不另设自管道）；断线后从最后见到的 seq 之后重新订阅。
    - host 重启：读线程与命令共用最后找到的 host。流打不开（host 已不在，或以另一个令牌重启）时重新寻找 host（没有时拉起），从最后见到的 seq 之后继续；GET 得到 403 或没有应答时，向重新找到的 host 再发一次（M2T06R-04）。
    - Ctrl+C：在空闲的顶层，它打开「脱离 / 暂停 / 取消任务」三选一。
      - 「暂停」「取消任务」以当前 revision 发送 PauseRun 或 CancelRun；遇到 STALE_REVISION 时重读后重试；发送后保持附着。
      - 裸 `hoh` 没有 Run，只提供「脱离」。
    - 退出：SIGHUP、SIGTERM 与「脱离」都只做三件事：关闭流，恢复终端（ADR-014），分别以 129、143、0 退出。它们不发送任何东西（REQ-043 行为 6、失败模式 5；REQ-005 行为 7）。
