# ADR-020 · 重试、退避、预算与等待

状态：采纳（M2-T19，随任务分步补全）

## 背景

M2-T19 要求（REQ-042，AC-042-01/02/03/05/06）：外部 429/5xx 与超时按 Retry-After 或 full-jitter 退避并持久 next_retry_at，重启不清计数与预算；鉴权、能力缺失直接 BLOCKED；同一外部故障最多重试 8 次后 BLOCKED 并产生 need_decision；本地修复与协议纠正有次数上限；预算或 deadline 耗尽即停止派发并 INCOMPLETE；配置了费用上限而价格未知时派发前 BLOCKED（BUDGET_UNENFORCEABLE）。事实、缺口与待定点见 `.hoh-dev/evidence/m2t19-prep/analysis.md`。

M2-T05 留下的状态：Attempt 失败时 Task 直接回到 READY（ADR-019 决定 8），没有退避；执行器端口的 `Outcome` 只有 success；产品没有执行器（M2-T07 起才有），所以不存在热循环，但 M2-T07 不能先于本任务落地。

## 决定

1. **失败分类进入执行器端口**。`Outcome` 新增 `class: FailureClass`（hoh-core `retry` 模块）：
   - `Transient { retry_after }`：429、503 等 5xx、超时，以及执行器无法归类的进程失败。`retry_after` 只来自 429/503 的 Retry-After。
   - `Auth`：鉴权缺失。
   - `Capability`：运行时才发现的 CLI 能力不兼容。
   - 成功时不看分类。适配器字符串（Codex 的 TRANSIENT_EXTERNAL/BLOCKED_AUTH、Claude 的鉴权、Pi 的错误文本）到分类的映射在 M2-T07 接入产品执行器时完成；本任务的测试执行器直接报告分类。
   - **无法归类按瞬时处理**：退避并计数，8 次重试后升级为 need_decision。它不会被当成"确认未执行"去立即重试，也不会无限重试（REQ-042 行为 3"不无限隐藏重试"）。启动失败与读不到进程身份两条路径同样是 `Transient { retry_after: None }`。
   - 分类与 Retry-After 随 OBSERVED 记录写入效果事件（`effect.observed` 的 detail 增加 `class`、`retry_after_ms`）。host 在 OBSERVED 之后崩溃时，reconcile 按记录的分类处置，不会把一次 429 变成没有计数的立即重试。 OBSERVED 记录同时带上工作结束的时刻（`ended_at`，执行循环的时钟）。工作效果已 COMMITTED（进程组已确认为空）时，reconcile 用它作为 Attempt 的结束时刻、已用时长的终点和重试的起点，而不是 reconcile 自己的时刻（第一轮审查 M2T19R-03）。以下两种情况结束时刻未知，按 reconcile 的时刻计，这是对预算更保守的一侧：
     - 只有 OBSERVED、没有 COMMITTED：leader 结束时进程组尚未确认为空，或崩溃发生在两者之间，这不是工作的结束（M2T19R-155）；
     - 没有记录。

     跨 host 生命周期时的下限见决定 4。

2. **重试策略是纯函数**（hoh-core `retry::after_failure`），输入为：失败后的 `attempt_count`、分类、失败时刻（注入时钟的整秒）、Retry-After、一次均匀抽样；输出三种之一（成功不调用它）：
   - 等待到 `next_retry_at`；
   - 阻塞，并给出原因（BLOCKED_AUTH 或 BLOCKED_CAPABILITY）；
   - 重试用尽；

   具体规则：
   - `attempt_count` 是该 Task 已失败的 Attempt 数，每次失败加 1，本任务内不清零（返工循环归 M2-T16）。第 n 次失败（n 从 0 计）的上界是 `min(300 s, 2 s·2^n)`。第 9 次失败（首次失败后已重试 8 次）为重试用尽。base、cap 与 8 次都是初值常量，只能经 CR 修改（REQ-042 决定 1），不设配置键。
   - **整秒存储下的取整**（store 时间是整秒，ADR-017）：失败时刻取注入时钟的整秒（即 attempts.ended_at），延迟向上取整到秒，于是 `next_retry_at − ended_at ∈ [0, 上界]` 恰好成立。429 的 `next_retry_at = ended_at + Retry-After`，Retry-After 不受 300 s 上界限制，只受 deadline 约束（决定 8）。
   - **抽样**：hoh-core 不引入随机数依赖。调用方传入一个 32 位均匀抽样 u，延迟 = `floor(u·(上界ms+1) / 2^32)` 毫秒。hoh-app 的执行循环持有一个 SplitMix64，host 启动时用 getrandom 取种子；测试传入固定种子。每次排期写一条 `task.retry_scheduled` 事件，记录 n、上界、抽样与 Retry-After，作为证据可复核。

3. **每条失败路径共用同一个持久化函数**（persistence `retry::fail_task`）。它在结束 Attempt 的同一事务里写入 tasks.attempt_count、next_retry_at、Task 状态（READY 等待，或 BLOCKED 带 blocked_reason）与 need_decision 事件。Run 的状态（WAITING_EXTERNAL、BLOCKED、INCOMPLETE）取决于它的全部 Task，所以不在这里判定，而在每个 tick 的一个统一作业里判定（第 4、5、7 条）。M2-T05 那一类缺陷就是因为一条条路径分别修补（分析 F13）。使用它的路径：
   - 执行循环的正常失败结束（runner_finished）；
   - 启动失败；
   - 读不到进程身份；
   - reconcile 与过期链处置为 Ended(FAILED)。

   以下情况不计数、不退避，按 ADR-019 原样处理：
   - Ended(CANCELLED)：STARTING 时 host 崩溃，工作从未开始；
   - Redeliver；
   - UNKNOWN_EFFECT。

4. **等待与 WAITING_EXTERNAL**。
   - 调度轮的候选排除 `next_retry_at > now` 的 READY Task（不派发，也不计入老化）。`now` 与写入失败时刻来自同一个注入时钟，执行循环为每次节奏作业与每个调度轮现取时间，不沿用一个 tick 开始时取的时间（M2T19R-04）。
   - **节奏作业**（`Store::pace_run`）在每个 tick 的调度轮之前运行，统一处理以下情况：
     - **唤醒**：WAITING_EXTERNAL 的 Run 只要有 Task 的 `next_retry_at <= now`，就回到 resume_state，然后由同一 tick 的调度轮派发；
     - **停泊**：一个工作中的 Run 没有未结束的 Attempt、没有到期可派发的 Task、没有在途的 Task（LEASED、RUNNING、IMPLEMENTED、VERIFYING：Run 不必等重试就还能推进的工作），且至少有一个 Task 在等重试时，进入 WAITING_EXTERNAL。这对应 CR-003 的"仅当 Run 内没有其他可派发 Task 时"；
     - **停泊后无可等**：停泊中的 Run 已没有任何在等的 Task（例如最后一个等待的 Task 因修复超限被阻塞）时，若有被阻塞的 Task 就进入 BLOCKED，否则回到 resume_state（M2T19R-05）。
   - **单调计时**（REQ-042 行为 2，M2T19R-06、-100）：产品 host 的时钟是 `MonotonicClock`，即 host 启动时的系统时间加上此后的启动时钟（CLOCK_BOOTTIME：单调，并且计入挂起，不像 CLOCK_MONOTONIC 那样在挂起期间停走，所以挂起之后它的时间仍是真实时间）。host 运行期间系统时钟跳变，既不会提前、也不会推迟等待；host 重启后重新锚定，从持久的 UTC `next_retry_at` 重新判定，不会立即重试（REQ-042 失败模式 1）。绝对期限 `deadline_at` 按墙钟判定（`Clock::wall`、`Context::wall`）。**余项**（接受，有界）：系统时钟本身在 host 运行期间被校正时（例如落后 1 小时后被 NTP 一步调正），此前写入的时间以错误的墙钟为基准，下一个 host 重启后按校正后的墙钟判定，这些等待会按校正量提前或推迟，每个等待受影响一次，预算与重试上限照常约束。任何以墙钟写入时间的做法都有这一项。缓解措施是 host 启动前先完成时间同步，由部署检查验证；这是 M2-T14 的后续项，记在审查记录的延期项里（M2T19R-253），M2-T14 的 done_when 目前还没有这一条。
   - **跨 host 生命周期的时刻**（设计修正，M2T19R-200；与 -100 同类的第二次，按 docs/19 先修正设计再实现）。
     - 问题：同一个 host 生命周期写下的时刻彼此一致（同一锚点，加 CLOCK_BOOTTIME），不同生命周期的时刻之间只隔着墙钟。墙钟在两次之间被往回校正时，后一个生命周期的时刻会落在前一个写下的时刻之前。
     - 规则：后一个生命周期给前一个生命周期的 Attempt 定结束时刻、或计算它已运行的时长时，终点不早于该 Attempt 自己的生命周期为它记录的最后时刻（`retry::recorded_until`）。这个最后时刻取以下三者中最晚的：
       - started_at；
       - 工作的 OBSERVED 记录中的 ended_at；
       - 它持有的租约最后一次续期的时刻，即 expires_at − LEASE_TTL。
     - 由此得到：
       - reconcile 写入的 ended_at 与累加的时长，至少是那个生命周期确实看到的运行时长，不会把倒序的区间记为 0；
       - 重试从这个终点与 reconcile 自身时刻中较早的一个起算，不会因为旧时刻领先而多等一个校正量；
       - 判定停止时，未结束 Attempt 的预留时长同样以此为下限；
       - reconcile 自身的时刻落后于记录时，`reconcile.attempt` 事件记下落后的毫秒数（`clock_behind_ms`），作为诊断。
     - 墙钟往前校正时，跨生命周期的区间会多计校正量，这是往停得早的一侧失败（决定 7）。
     - 等待中 Task 的 `next_retry_at` 是目标时刻而不是区间，仍按上一条的余项处理。

5. **阻塞**（ADR-011 的阻塞集合；本任务加入写入阻塞的一半，解除仍归 M2-T08/M2-T15）。
   - Task 级：鉴权失败、运行时能力失败、重试用尽、修复超限时，Task 进入 BLOCKED，并写 tasks.blocked_reason（依次为 BLOCKED_AUTH、BLOCKED_CAPABILITY、NEED_DECISION、NEED_DECISION），`next_retry_at` 为空。
   - 调度前能力检查（AC-042-03 R2）：到期可派发的 Task 的角色所需能力不全在绑定会话的探测结果里时，节奏作业在任何租约之前把它改为 BLOCKED（BLOCKED_CAPABILITY），不创建 Attempt；调度轮不再静默跳过它。M2-T15 的 fallback 选择会放在这一步之前。
   - **Run 的停滞判定**：一个工作中的 Run 没有任何能推进的 Task 时，进入 BLOCKED。能推进是指：可派发、在途（LEASED/RUNNING/IMPLEMENTED/VERIFYING），或在等重试。判定还要求至少一个 Task 为 BLOCKED。阻塞集合取这些 Task 的原因，`blocked_reason` 按 BlockedReason 的优先级取最高者。这样一个角色缺员不会阻塞其他还能推进的角色（M2-T15），单 Task 的 R1/R2/R3 都按 AC 进入 BLOCKED。
   - BUDGET_UNENFORCEABLE 是 Run 级的（决定 7），在任何派发之前直接写入。
   - 阻塞后排期中的重试照常进行（CR-003）：等重试的 Task 本身就算"能推进"，所以只有在没有任何等待项时才会阻塞。

6. **need_decision**：事件 kind `need_decision`，payload 包含 run_id、task_id、`reason`（`retries_exhausted`/`local_repairs_exhausted`/`protocol_repairs_exhausted`）、计数与说明。M2-T08 的监督触发器消费它，向用户提问的回复归 M2-T13。

7. **预算**（budgets 表，scope 为 run）。
   - 上限来源：`iterations`（max_iterations）、`wall_seconds`（max_duration_hours·3600）、`usd`（max_usd，price_known 标记价格是否已知），以及 runs.deadline_at。由配置加载写入这些行（M2-T07）；没有行表示没有该项上限，本任务的测试直接写入。
   - 停止判定是纯函数（`budget::stop`）。用量加预留达到上限，或墙钟时间 `>= deadline_at` 时，停止新派发。调度轮、节奏作业与 decide 路径共用同一条规则（`retry::budget_stop`，M2T19R-01）。Run 没有未结束的 Attempt 时，节奏作业把它置为 INCOMPLETE，`run.incomplete` 事件列出未完成的 Task。
   - **时长的度量**（M2T19R-157）：max_duration_hours 度量的是代理工作的时长，即各 Attempt 运行时长之和。并行的 Attempt（一个写者、两个读者）各自计入，所以它比 Run 的活跃墙钟时间消耗得快，往停得早的一侧失败。规格没有定义这一度量；若项目所有者要的是 Run 的活跃墙钟时间（各运行区间的并集），由 CR 修改。
   - 用量：wall_seconds 在 Attempt 结束的事务里累加该 Attempt 的时长（ended_at − started_at，两端都取执行循环的时钟，M2T19R-53；由后一个 host 生命周期结算时，终点以决定 4 的下限为准）。判定停止时，未结束 Attempt 已运行的时长计为预留，所以一个长时间运行的 Attempt 在结束之前就计入时长，之后的派发不会越过上限；结束时结算进已用，不会重复计（M2T19R-02）。它只在 Attempt 结束时变化，所以等待中的 Run 在 kill -9 与重启前后逐值相等（AC-042-02），停机时间不计入，deadline 另行约束绝对时间。iterations 的增量由迭代边界写入（M2-T16）；本任务只读它、判定它，并保证持久。
   - BUDGET_UNENFORCEABLE：Run 有 usd 上限而 price_known=0 时，节奏作业在任何租约之前把 Run 置为 BLOCKED（BUDGET_UNENFORCEABLE），调度轮与 decide 路径也不派发，不创建 Attempt。产品暂无价格表，所有模型价格都未知（CR-002 决定）。

8. **Retry-After 晚于 deadline**：`next_retry_at` 照常写入；deadline 一到，决定 7 的停止判定就把 Run 置为 INCOMPLETE，不会越过 deadline 等待（REQ-042 失败模式 4）。

9. **费用**：没有价格表时，attempts.cost_usd 为空，绝不以 CLI 的估算冒充账单。
   - Run 的费用由投影 `Store::run_cost` 计算：Run 的价格已知（Run 级 usd 行 price_known=1）且每个 Attempt 都有 cost_usd 时为 `known` 并求和（没有 Attempt 时为 0），否则为 `unknown` 且 cost_usd 为空（CR-009）。
   - RunResult 加入 `cost_usd`、`cost_status`（CR-009），`--output json` 的输出归 M2-T13（AC-042-04）。

10. **修复次数**（AC-042-05）：`Store::request_repair` 处理两种请求，同一 issue fingerprint 的本地修复，或同一 Attempt 的协议纠正。
    - 未超限时写一条 `repair.local` 或 `repair.protocol` 事件并返回准许；计数即这些只追加事件的条数，重启后不变。
    - 超限时不派发，写一条 need_decision（决定 6），并把相关 Task 置为 BLOCKED（NEED_DECISION）。
    - 上限为 [budget] 的 max_local_repairs、max_protocol_repairs（初值 3、2，由调用方传入）。调用方（QA 返工循环、协议纠正）随 M2-T16/M2-T07 接入。

11. **Commander 的派发**：decide 路径对 `next_retry_at > now` 的 Task 以 `RETRY_NOT_DUE` 拒绝（CR-009），对预算已停止或费用上限无法执行的 Run 以 `BUDGET_NOT_RESERVABLE` 拒绝（M2T19R-01）。在 ADR-011 的派发拒绝顺序中（M2T19R-59）：RETRY_NOT_DUE 在 ILLEGAL_TRANSITION 之后、ROLE_CAPABILITY_MISSING 之前；Run 预算的停止与 BUDGET_NOT_RESERVABLE 的余量检查同处一位，先于余量检查。

12. **测试安排**（检查归属见 tests/check-plan.json 与 cargo-tests.sh）。
    - TEST-042-01、TEST-042-05 是 hoh-core 的库内单元测试，使用临时文件 store、FakeClock 与固定种子。
    - TEST-042-03、TEST-042-06 是 hoh-app 的 integration 目标，使用脚本化执行器报告分类，以及能力探测 fixture。
    - TEST-042-02 在 recovery 目标里：子 host 的时钟由测试经环境变量注入（CR-006 F2；产品使用 `MonotonicClock`，见决定 4），用 SIGKILL 杀掉后重启。

## 不在本任务内

- 适配器错误文本到 `FailureClass` 的映射与产品执行器（M2-T07）。
- 配置加载与适配器的费用（M2-T07，M2T19R-64）：budgets.price_known 在 SQL 中默认为 1，没有价格表时加载必须写入 price_known=0，否则 BUDGET_UNENFORCEABLE 不会触发；Claude CLI 报告的 total_cost_usd 是估算，不得写入 attempts.cost_usd，否则 run_cost 会被误判为已知。
- 阻塞的解除、监督触发器消费 need_decision（M2-T08）、fallback 与缺员（M2-T15）。
- iterations 的计数边界与返工循环（M2-T16），`--output json` 的 RunResult 输出（M2-T13）。
- 价格表与 token 上限（没有配置键；价格表随相应集成提供）。
