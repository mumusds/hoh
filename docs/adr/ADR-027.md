## 第三版的更正（设计审查第 2 轮：Codex M2T10D-100..105，Claude M2T10D-150..162）

## 决定

1. **模块划分。** `hoh_core::verification`（纯：候选清单、规范身份、执行记录、Evidence、`valid` 及封闭的原因枚举、计划查找、acceptance_results 的聚合）；`hoh_core::persistence::candidates`（SQL：候选行、STALE、evidence、acceptance_results、事件）；hoh-app 的冻结与检查驱动（git、文件哈希、经 hoh-agents 的进程底座执行）。SQL 只在 persistence（AC-062-05）。驱动的 API 分开传被测检出目录与 `.hoh/` 状态根（M2-T16 的读槽运行目录复用，-67）。

2. **身份。** 与 `tools/candidate.py` 逐字节相同：`CAND-` + sha256(去掉 candidate_id 的清单，键排序、紧凑、非 ASCII 不转义)。集成测试用 Python jsonschema 按受锁的 candidate.schema.json 校验产品导出，并用 tools/candidate.py 算出相同的 id（S1 已实现：2e33b37）。

3. **`.hoh/` 永远被 git 忽略（-03、-51）。** 产品在创建 `.hoh/` 的每处（host 启动建库、对象目录）先写 `.hoh/.gitignore`，内容为 `*`：它在 `.hoh/` 自身之内，所以只锚定项目根的这一个目录，链接工作树与子模块里同样成立，不改任何跟踪文件、不碰 `.git`。每次打开 store 时确保它存在（已有的、用户改过的不覆盖）。冻结与核对的守卫逐项检查 HoH 写入的路径（`state.db*`、`objects/`、`evidence/`、`attempts/`、`sessions/`、`first-inputs/`、`host.*`、`input-history.jsonl`）被忽略且未被跟踪，不成立即拒绝并说出哪一项；用户可以跟踪 `.hoh/config.toml` 与提示词文件（-154）。所有 git 调用沿用 ADR-021 g 的只读参数（`--no-optional-locks`、`-c core.fsmonitor=false`），不写索引、对象或引用（-153）。

4. **冻结（行为 1、2，失败模式 5，决定 2）。** 拒绝：`git status --porcelain --untracked-files=all` 非空；`git ls-files -v` 显示 assume-unchanged（小写标记）或 skip-worktree（`S`）的文件（-04：否则未提交内容可被当作已提交）；`git ls-files -s -z` 中 120000/160000 的条目（报出路径）；跟踪文件不是普通文件。spec 与 test plan 须是候选的跟踪文件；environment 可以是跟踪文件，也可以是 `.hoh/` 下的普通文件（HoH 生成的环境描述，被忽略、按摘要绑定；与 tools/candidate.py 一致，-69）。本任务的驱动以路径接收它；产品里的生成者是 M2-T16，它须字节稳定（不含时间戳，内容变了才重写），否则每次重启 host 都会让检查以失败模式 3 被拒（-260）。清单算出之后再核对一次 HEAD 与工作区（防中途提交，-67）。导出写成对象并登记 artifacts 行，`candidates.source_path` 记对象路径；spec、environment、test plan 的工作文件字节也各写成对象，之后的核对与计划查找读这些对象（按摘要核对），不读 git blob（`.gitattributes` 的换行转换下两者不同，-104）。

5. **候选行与 Run（-05、-63）。** 内容身份不含 run_id（导出 schema 不允许加），`candidates` 的主键是 candidate_id 且每行属于一个 Run：同一 Run 内同内容再冻结返回已有 id 与它的状态，不新增行（REQ-052 决定 1），由调用方（M2-T16）按状态处理；同内容的 STALE/INVALID/REJECTED 行不复活；另一 Run 的同内容拒绝，并给出出路（产生新提交）。这把决定 1 的“返回已有 id”限定在同一 Run：候选行属于一个 Run（`run_id NOT NULL`，主键只有 candidate_id，`current_candidate` 按 Run 读），跨 Run 返回旧行，新 Run 既读不到它，又无处登记自己的验证；所以由 CR-017（CR-003 D1 的细化：决定 1 与受锁 SQL 的不一致）写进 REQ-052 决定 1。新 Run 没有新提交就不能冻结（如取消后重验），由 M2-T16 处理（-159）。插入事务里把该 Run 更早的 FROZEN/VERIFYING/ACCEPTED 候选置 STALE，写 `candidate.frozen{candidate_id, superseded}`；`current_candidate`（最新 FROZEN 或 VERIFYING）对它的全部读者保持一致。本任务写三种迁移：冻结时的 FROZEN、被取代时的 STALE，以及 outcome 为 INVALID（被否决）的证据在同一事务里把它的候选从 FROZEN、VERIFYING、ACCEPTED 或 STALE 置 INVALID（原则一，-400）；INVALID 是终态，M2-T16 的迁移都带原状态条件（如 `AND state = 'VERIFYING'`），从不覆盖它；`valid` 的 S 是候选自己的 spec 摘要，Run 的规格在检查途中变化由 M2-T16/M2-T18 按 REQ-053 行为 7 置 STALE，不是否决（-554）；VERIFYING、ACCEPTED、REJECTED 由 M2-T16 的验证流程迁移，同一 Run 同内容遇到 STALE/INVALID 行时须新提交才能再冻结，这个情形也由 M2-T16 处理（-260）。不记“基准提交”（-12、-62）：M2-T16 需要改动文件时由被取代候选的 commit 或它自己的任务起点计算。

6. **检查前后核对（行为 4、5，失败模式 4、6，-68）。** 前核对逐项算出并分别命名：清单身份、`checkout changed`、`worktree dirty`、源文件清单与逐文件 hash、spec/environment/test_plan 摘要（`test_plan_sha256 mismatch` 与脏检查独立，AC-052-03 变体 1）、`check_id not in the frozen plan`、`argv differs from the frozen plan`、生产者不符（原则二的 PRODUCER_MISMATCH 与 PRODUCER_NOT_INDEPENDENT）；计划从冻结时写下的计划对象读（核对其摘要），不读可能被改过的工作文件，也不比较 git blob；检查计划的 `mode=bundle` 在产品里拒绝（evidence.mode 只允许 mock/live/product，-64）。任一不符即不运行命令、不写记录。后核对同样逐项；不符则 `source_unchanged=false`、evidence.outcome=INVALID，即使退出码为 0。前后的工作区观察沿用 ADR-021 g 的工作区哈希（HEAD、tree、`diff --binary` 的哈希、未跟踪内容的哈希），不写对象，所以改写一个跟踪文件而不提交也能看出前后不同（M2-T16 的 AC-037-03 用它）。驱动拒绝时返回 outcome INVALID 与原因、不写记录，供 M2-T16 记录。命令经 hoh-agents 的进程底座运行（argv、进程组、截止时间的升级）：底座的结束原因与退出状态是两个维度，记录按原因取（-700）：到达截止时间 → `timed_out` 为 true，退出码照实；被取消或丢弃（Cancelled、Abandoned）→ 退出码记 130（与 run_check 的中断约定相同），不论子进程自己以什么退出，所以被取消的运行从不“声称成功”；自行结束 → 退出码照实，被信号终止记为负的信号号（与 run_check 的 Python 约定相同，如 -15）；取消或中断时照样写记录：命令开始之后，运行、后核对、记录与入库属于一个独立的收尾任务，调用方丢弃它的 future 即请求取消命令，记录照样写出（退出码 130）；后核对本身失败（如 git 不可读）记为不能排除的改动（`source_unchanged=false`），从不丢弃记录；对文件只按普通文件、非阻塞地读取，FIFO、设备等记为改动（实现审查第 1 轮 M2T10R-02..04）。`duration_seconds` 取单调钟的耗时（-701）：CLOCK_MONOTONIC，即 `std::time::Instant`，与进程底座和 run_check 的 `time.monotonic` 相同，不计主机挂起；不是 host 的 `MonotonicClock`，那是计入挂起的 CLOCK_BOOTTIME（ADR-020 决定 4），用它会把挂起计入 soak 的时长（-850）；`started_at` 取开始时的墙钟，`finished_at` 取 `started_at` 加单调耗时（-750）：区间与时长按构造相符、从不倒置，墙钟前跳或回拨都不改变时长；soak 的 min(墙钟, 时长) 取的仍是单调钟的时长，墙钟前跳后的时间线事件落在窗口之外，门禁照样拒绝；结束时实际的墙钟写进 `evidence.recorded` 的 `clock{wall_finished_at, monotonic_seconds}` 供审计。run_check 自己用单调钟计时、墙钟记起止，两者不符时按规则 9 只是不完整、无结论，同一候选上重跑可以补上（-655）。驱动给被测命令设置与 run_check 相同的六个变量（`HOH_EVIDENCE_DIR` 指向本记录的 artifacts 目录），从该目录读 test-results.jsonl（-66）。

7. **完整性事件（-09、-54）。** 后核对发现源码或候选被改（source_unchanged=false、checkout changed、清单身份不符），驱动在写证据的同一事务里写 `integrity_violation{candidate_id, check_id, record_id, reasons, tree_before, tree_after}`，事件 id `<record_id>/integrity`（幂等）；监督器的封闭种类里已有它，同一步骤即唤醒 Commander（测试断言）。

8. **执行记录与证据（行为 6、7，-06、-52、-55、-60、-10、-11）。**
   - 记录按 execution.schema.json 1.1（受锁，不加字段）；它引用的 stdout、stderr 与声明工件都是本记录目录 `.hoh/evidence/<candidate>/<check>/<record>/` 里不可覆盖的文件（release_gate 要求引用在记录目录内，-11）；同时把它们写成对象并登记 artifacts 行（数据库引用对象路径）。
   - evidence 行要求生产者 Attempt（`attempt_id` NOT NULL，外键 attempts）与一条 artifacts 行（记录本身）：驱动的 API 以产出它的 Attempt id 为参数（M2-T16 的 QA/Reviewer Attempt；本任务测试用夹具 Attempt），前核对与持久层入库时都核对该 Attempt 属于候选的 Run 且是 qa 或 reviewer 的 Attempt（原则二），否则拒绝。同一事务写 `evidence.recorded{evidence_id, record_id, attempt_id, check_id, outcome, outcome_reason, tree_before, tree_after, clock, observations, reasons, artifacts}`（outcome 与原因供 M2-T18 的检查级状态，clock 见决定 6，-852）。写入次序：记录的字节先存为对象，判定之后先把整条待入库内容写成记录目录里的 `recording.json`，再以临时文件加链接写出 `execution.json`（整份或没有），最后提交事务；提交失败或中途崩溃时，下一次检查运行前的对账（`check::reconcile`）补记这些记录（缺 `execution.json` 时由待入库内容写出），所以后来的运行从不取代较早的失败（M2T10R-05、-56），事件 id `<record_id>/evidence`：它是 valid 之后重算的输入来源（前后 tree、观察、原因），也是多检查 Attempt 的生产者登记（一个 Attempt 每个记录一条，不复用 `attempt.artifacts` 的固定 id，-10）。`persistence::context::references` 把一个 Attempt 的 `attempt.artifacts` 与它的各条 `evidence.recorded` 按事件次序合并、去重、限量读取，所以检查的输出也能成为交接引用（-102、-161；ADR-026 决定 10 加注记）。
   - observations（与原则一规则 12 同一定义，-602）：有结果行时是这些行；没有结果行时（计划没有声明 test-results.jsonl，或声明了而它为空）是找到的声明工件的引用加记录自身的退出结论（-60）；按记录里实际有什么选择，不按检查名（-202）；什么都没有才是 INSUFFICIENT（AC-052-04 变体 6）。
   - **outcome 与原因（-254、-302、-401、-402、-451）。** 证据的 outcome 由原则一的 outcome 函数给出，产品与复刻函数是同一张表；超时与退出码是结论，不是 `valid` 的原因；退出 0、3、1 各与有无降级依据、可否降级、超时、缺插件组合测试。outcome 为 INVALID 时同一事务把候选置 INVALID。
   - `valid(e, c, s)` 的原因是封闭枚举，即原则一表中“否决”与“入库”的各行（规则 12 只在声称成功时；规则 9 的时长不是原因，属 outcome 的“完整”），AC-052-04 的 11 个是必测的最小集合（-156）；原因码包括 RECORD_ID_REUSED、LIVE_SESSIONS_MISSING、RESULT_LINE_INVALID、CHECK_NOT_IN_POLICY、PLAN_MODE_NOT_POLICY 与下列：stderr 与每个声明工件的 sha256、声明工件集合与计划一致、声称成功（退出 0 且未超时，规则 11）时没有 FAIL 行（EXIT_INCONSISTENT，-900）、command/mode/cwd 与冻结计划一致、check_id 在计划中、记录 schema、candidate_manifest 引用与候选一致、起止时间有效且不倒置（INTERVAL_INVALID；时长与区间是否相符不是原因，-852）、runner 的工具名属于门禁的 EVIDENCE_TOOLS（产品写出的记录取 `hoh`）且 `runner.euid` 不为 0（-255）、引用都在本记录目录内且与其他记录目录不重叠、live 检查的 live-sessions 绑定本检查与本候选、生产者属于候选的 Run（PRODUCER_MISMATCH）且是独立验证角色（PRODUCER_NOT_INDEPENDENT）；每个原因各有单元测试。另有兼容测试：产品写出的执行记录按受锁的 execution.schema.json 校验，并以它自己的清单引用通过 release_gate 的逐记录检查与复刻函数（-255）。这些原因是 `evidence.recorded` 与 `integrity_violation` 载荷里 `reasons` 字段的字符串，随事件经 `/v1/events` 原样发出，事件种类就是它们的命名空间；它们不进以 ReasonCode 为类型的字段（REQ-052 决定 3 规定 INSUFFICIENT 写在原因里，ADR-022 的 PROMPT_UNAVAILABLE 是同样的先例），所以现在不需要 CR，docs/22 写明这一解释（-71、-260）。

9. **acceptance_results（-01、-50、-105、-152、-354、-356、-400、-403）。** 每个 (AC, evidence) 至多一行（主键所限），reason 列出测试名与原因；行只追加。行就是原则一结论函数的结果：对证据的每个 AC 求 `conclude(证据, 该 AC 的 TEST)`（AC 声明的 test_id 映射，不按编号推断，-70），不为“无结论”时写一行，状态即结论（INVALID、FAIL、PASS、DEGRADED）；被否决的证据为它检查的场景 AC 与它的结果行提到的 AC 写 INVALID，全局的否决由候选的 INVALID 状态承担（决定 5）。于是（各形态的结果见原则一的推导表，-800）：失败来自哪个检查都写 FAIL；只有场景检查能写 PASS 或 DEGRADED；结论为无结论的不写行，即受阻、超时、不完整（缺工件、缺会话或时长不符）、跳过、缺行，以及完整而只有 PASS 行的非零退出（AC-053-02：`[]` 投影为 NOT_RUN），同一候选上重跑可以补上；完整而合规的降级不论退出码（包括中断的 130）写 DEGRADED；DEGRADED 证据里全为 PASS 的 AC 不写行（门禁 :208、:226 下它既不能 PASS 也不能 DEGRADED）。decide.rs 对任一非 PASS 行、没有行或候选不是 VERIFYING/ACCEPTED 都不判通过。测试覆盖结论函数的每一条，并与 traceability 的 TEST 状态对照（同一组成员，两边结论一致）。

10. **traceability 检查（-07、-08、-56、-57、-59、-61、-70）。** `bash scripts/product/traceability.sh <profile>`：对每个范围内 TEST id，读本候选的**全部**成员（搜索根限定 `.hoh-dev/` 与产品的 `.hoh/evidence/`），按原则一的规则表、outcome、结论函数与 TEST 状态判定（先失败后通过记为 FLAKY，不回退到较早的成功）；policy 与 profile 来自候选的 `contracts/release-policy.json` 与脚本参数。脚本的顺序：先运行自测，把结果写进本次的 test-results.jsonl；再判定其他检查的成员；最后写报告并退出，run_check 随后封装记录。**自测集合按 spec 推导**（-253）：范围内场景检查为 traceability 的 TEST（v0.1 是 TEST-052-05，v1 另有 TEST-032-01、TEST-069-01），各按名称含 `test_NNN_MM` 在 tests/bundle 里定位并运行，找不到时不写行（受锁的 test-result.schema.json 只允许 PASS、FAIL、DEGRADED、SKIPPED，-303），该 TEST 在报告里为 NOT_RUN、不满足；这些 TEST 的**满足**只取本次的自测行；较早的 traceability 成员照原则一参与否决与结论函数 (2)(3)（-455、-504）。需求的 release_class 为 degradable 时按原则一（门禁 :203-228）接受合规的 DEGRADED，其场景检查（只限可降级的检查）可以非零退出，报告标 degraded。报告 `traceability-report.json{candidate_id, profile, tests:{id: {check, members, passing:[测试名], status}}, unsatisfied:[{id, status}], invalid:[{path, check_id, damaged, reasons}]}`，status 取 PASS、DEGRADED、MISSING、FAIL、FLAKY、INVALID、NOT_RUN；**退出 0 当且仅当每个范围内 TEST 的 status 都是满足的（PASS，或可降级需求上的 DEGRADED）且 invalid 为空**（损坏的成员也在其中），FAIL、FLAKY、INVALID、NOT_RUN、MISSING 的 TEST 都进 unsatisfied（-250、-300、-654）。门禁不读这份报告（release_gate 受锁），在 docs/22 写明；把 argv 改成 v1 由写者任务 M7-T02 承接（写进它的移交，M7-T04 是 writer=false 的 verify 任务）。TEST-052-05 是 tests/bundle 下名称含 `test_052_05` 的真实测试：在临时的夹具 ROOT（git 仓库、夹具规格与夹具测试）上**经 run_check 运行真实的 traceability.sh**，所以参数、先自测后判定的顺序、test-results.jsonl、报告工件与退出码映射都在测试内（-253）；夹具规格里有一个以 traceability 为场景检查的夹具 TEST，它的自测是夹具自己的测试，不是 test_052_05，所以没有递归；候选 C 齐全时退出 0；C' 真实删除一个 v0.1 AC 的夹具测试源、重新冻结、经 scripts/product/test_results.py 重新生成结果时非零并列出缺失 id；另断言只有 FAIL 成员与 FAIL→PASS 时退出非零（-250）；两份报告各绑定自己的候选；临时目录清理。本任务候选上的真实 traceability 预期非零（大量 TEST 未写），按原则一 TEST-052-05 在本候选上也不算满足：完成记录写明 AC-052-05 是测试层面的 PASS，按门禁的验收在 V01-T01（-260）。

11. **independent-qa / independent-review（-02、-53、-65、-61）。** `bash scripts/product/independent.sh <qa|reviewer> <profile>`：上下文 JSON 由助手从 `$HOH_CANDIDATE_FILE` 与原则一的判定结果（全部成员，含无效与损坏的成员及其原因，各 TEST 的状态）生成，用 tools/render_prompt.py 渲染。每次尝试不传 `--output-dir`（检查内默认 `attempts/<uuid>/`，各自唯一、保留），各自的 `--report-out`；从 agent_task 的结果取成功那次的 attempt 记录，复制为 native-attempt.json、raw-session.jsonl 与 independent-report.json，并核对与报告引用的 sha256 一致。回退只在未产出报告时（容量错误、会话开始前就结束）；写出报告（含 FAIL/UNKNOWN）即停止，不换 Agent 找 PASS。顺序：qa 先 pi 后 claude；reviewer 先 codex，再 codex `--model gpt-6.1-sol`，再 claude；grok 被 agent_task 在检查内拒绝。每次尝试的 `--timeout` 按剩余预算（计划超时减 run_check 的 15 s 宽限）。退出 0 当且仅当报告 PASS 且无 critical/high；3（BLOCKED）当且仅当每次尝试都没有产出报告且都可归为外部阻塞：在 CLI 启动前结束（agent_task 的 127/78/64），或 attempt 记录里有该 CLI 的鉴权、配额、容量失败的已记录模式（-155）；否则 1。假 CLI 的套件测试在临时的 ROOT 副本里运行，永不写入真实的 `.hoh-dev/`。提示词要求不改跟踪文件、不在未被忽略处新建文件，输出写到字面给出的 observations 目录。CI 没有认证，只跑带假 CLI 的套件测试；假 Agent 的结果永不报为 live。本任务候选上的真实会话预期报告 FAIL/UNKNOWN（许多 AC 未实现），done_when 要求的是会话与四个文件。

12. **测试的非空真（-58）。** TEST-052-02、-03 各带正对照：同一夹具检查在干净候选上得到 valid 证据、PASS 行（-02）与哨兵文件（-03）；变体里断言 C 有至少 1 行 INVALID、0 行 PASS（-02），没有执行记录且哨兵不存在（-03）。TEST-052-02 的正对照放在独立的仓库与数据库，变体保留场景的字面计数（-158）。另有未打标签的测试：`checkout changed`、check_id 不在计划、未提交的跟踪改动、assume-unchanged、`.hoh/` 中 HoH 写入的路径未被忽略、`.hoh/` 下的 environment 被改与 spec 被改（失败模式 3）、符号链接与子模块（失败模式 5）、证据目录只追加（行为 8）、记录按不同清单路径的 FAIL→PASS 与 PASS→FAIL、超时后重跑、CRLF 计划的干净候选（-157、-101、-104）；同一候选的 FAIL 成员其后 stderr 或 test-results 被改、再有 PASS 时仍不满足，不能解析而字节含 C 的成员、声明 C 而 spec 不符的成员、引用的清单文件被删的 PASS 成员（-200）；同一候选的 FAIL 成员其后 check_id 被改成计划外的值、再有 PASS 时整份报告仍不满足，非场景检查里的 FAIL 行使 TEST 不满足、PASS 行不使它满足（-300）；outcome 表的退出 0、3、1 与降级依据、可否降级的组合（-302）；缺失自测时 test-results.jsonl 仍合受锁 schema、报告为 NOT_RUN（-303）；规则表每一行各一个负例，原则一列出的每项预期差异在门禁对照里各有用例（-350、-351、-405）；FAIL 运行后全量重跑通过记为 FLAKY 且不满足，受阻、超时、中断或未实现的运行（缺工件）后重跑通过则满足、不写它们的行、候选不被否决（-351、-354、-450）；超时的合规降级不满足（-401）；requires_plugins 的检查缺插件不满足（-402）；不合规的 DEGRADED 行在验收行与 TEST 状态里都是 FAIL（-403、-452）；DEGRADED 证据里全为 PASS 的 AC 不写行（-356）；无验收行的检查（build）被否决时候选为 INVALID、decide.rs 不判通过（-400）；较早 traceability 成员的 FAIL 自测行使该 TEST 为 FLAKY（-455）；场景检查的有效证据里没有该 AC 的行时不写行、decide.rs 不判通过，同一候选上补跑出 PASS 后判通过（-251、-406、-454）；Developer Attempt 作生产者被前核对拒绝、命令未运行（-252、-256）；一个 Attempt 跑多个检查后交接，引用含检查的输出、去重、限量（-259）。
