# ADR-027 · 冻结候选、证据有效性与三项验证检查

状态：第二版（设计审查第 1 轮之后的设计更正；M2-T10）

## 背景

M2-T10 的验收是 REQ-052 的 AC-052-01 至 -05（TEST-052-01、-02、-03 属 `integration`，-04 属 `unit`，-05 属 `traceability`）；done_when 另要求 independent-qa、independent-review 两项检查经 run_check→agent_task 运行全新原生会话并产出 live-sessions.json、independent-report.json、native-attempt.json、raw-session.jsonl，traceability 检查逐条核对范围内 TEST id 的 test-results.jsonl 通过记录，三项检查不再指向 not-implemented.sh。

起点（预研笔记 `.hoh-dev/evidence/m2t10-prep/analysis.md`，按 main ab2dc29 复核：`reverify-2026-11-11.md`）：引导期工具 candidate.py、run_check.py、release_gate.py 已有冻结、前后核对与门禁的 Python 实现（受锁）；产品侧没有冻结、证据与 acceptance_results 的写者；`artifacts` 表与内容寻址对象目录已由 M2-T09 提供（`hoh_core::objects`、`persistence::runner::register`、`attempt.artifacts` 生产者事件）；`current_candidate` 被监督摘要、上下文收集与交接包共用；ADR-025 决定 10 把 `integrity_violation` 的产生方交给 M2-T10 与 M2-T16。

## 第二版的更正（设计审查第 1 轮：Codex M2T10D-01..12，Claude M2T10D-50..71）

两位审查者都判 FAIL，大部分发现重合：acceptance_results 的主键与逐行写入冲突（-01、-50）；`.hoh/` 到冻结时才忽略太晚、字面 `.git/info/exclude` 在链接工作树里不可写（-03、-51）；`assume-unchanged` 能让未提交内容通过（-04）；`valid` 只认 AC 的 11 个变体，弱于 docs/07 §6 与受锁门禁（-06、-52）；“最新有效记录”掩盖失败历史（-07、-56）；v1 的合规降级不可达（-08、-57）；没有承接 `integrity_violation`（-09、-54）；回退复用固定输出目录（-02、-53）；跨 Run 同内容的处理（-05、-63）；观察与前后 tree 无处存放（-55）；多检查的生产者登记（-10）；执行记录引用的路径（-11）；基准提交（-12、-62）；测试的正对照与自证（-58、-59）；无逐测试结果的检查（-60）；以及低级别的承接、模式、退出码、接口、来源与命名（-61、-64..-71）。下面各决定逐条吸收。

## 决定

1. **模块划分。** `hoh_core::verification`（纯：候选清单、规范身份、执行记录、Evidence、`valid` 及封闭的原因枚举、计划查找、acceptance_results 的聚合）；`hoh_core::persistence::candidates`（SQL：候选行、STALE、evidence、acceptance_results、事件）；hoh-app 的冻结与检查驱动（git、文件哈希、经 hoh-agents 的进程底座执行）。SQL 只在 persistence（AC-062-05）。驱动的 API 分开传被测检出目录与 `.hoh/` 状态根（M2-T16 的读槽运行目录复用，-67）。

2. **身份。** 与 `tools/candidate.py` 逐字节相同：`CAND-` + sha256(去掉 candidate_id 的清单，键排序、紧凑、非 ASCII 不转义)。集成测试用 Python jsonschema 按受锁的 candidate.schema.json 校验产品导出，并用 tools/candidate.py 算出相同的 id（S1 已实现：2e33b37）。

3. **`.hoh/` 永远被 git 忽略（-03、-51）。** 产品在创建 `.hoh/` 的每处（host 启动建库、对象目录）先写 `.hoh/.gitignore`，内容为 `*`：它在 `.hoh/` 自身之内，所以只锚定项目根的这一个目录，链接工作树与子模块里同样成立，不改任何跟踪文件、不碰 `.git`。冻结与核对只以 `git check-ignore -q .hoh/` 作守卫，不成立即拒绝并说明原因。

4. **冻结（行为 1、2，失败模式 5，决定 2）。** 拒绝：`git status --porcelain --untracked-files=all` 非空；`git ls-files -v` 显示 assume-unchanged（小写标记）或 skip-worktree（`S`）的文件（-04：否则未提交内容可被当作已提交）；`git ls-files -s -z` 中 120000/160000 的条目（报出路径）；跟踪文件不是普通文件。spec 与 test plan 须是候选的跟踪文件；environment 可以是跟踪文件，也可以是 `.hoh/` 下的普通文件（HoH 生成的环境描述，被忽略、按摘要绑定；与 tools/candidate.py 一致，-69）。清单算出之后再核对一次 HEAD 与工作区（防中途提交，-67）。导出写成对象并登记 artifacts 行，`candidates.source_path` 记对象路径。

5. **候选行与 Run（-05、-63）。** 内容身份不含 run_id（导出 schema 不允许加），`candidates` 的主键是 candidate_id 且每行属于一个 Run：同一 Run 内同内容再冻结返回已有 id 与它的状态，不新增行（REQ-052 决定 1），由调用方（M2-T16）按状态处理；同内容的 STALE/INVALID/REJECTED 行不复活；另一 Run 的同内容拒绝，并给出出路（产生新提交）。这把决定 1 的“返回已有 id”限定在同一 Run：跨 Run 返回旧行会让新 Run 读到另一 Run 的验证与验收（CONTRACT 第 7 条不得复用旧验收），所以由 CR-017（CR-003 D1 的细化：解决规格之间的不一致）写进 REQ-052 决定 1。插入事务里把该 Run 更早的 FROZEN/VERIFYING/ACCEPTED 候选置 STALE，写 `candidate.frozen{candidate_id, superseded}`；`current_candidate`（最新 FROZEN 或 VERIFYING）对它的全部读者保持一致。不记“基准提交”（-12、-62）：M2-T16 需要改动文件时由被取代候选的 commit 或它自己的任务起点计算。

6. **检查前后核对（行为 4、5，失败模式 4、6，-68）。** 前核对逐项算出并分别命名：清单身份、`checkout changed`、`worktree dirty`、源文件清单与逐文件 hash、spec/environment/test_plan 摘要（`test_plan_sha256 mismatch` 与脏检查独立，AC-052-03 变体 1）、`check_id not in the frozen plan`、`argv differs from the frozen plan`；计划从候选 commit 里的计划 blob 读（核对其摘要），不读可能被改过的工作文件；检查计划的 `mode=bundle` 在产品里拒绝（evidence.mode 只允许 mock/live/product，-64）。任一不符即不运行命令、不写记录。后核对同样逐项；不符则 `source_unchanged=false`、evidence.outcome=INVALID，即使退出码为 0。驱动给被测命令设置与 run_check 相同的六个变量（`HOH_EVIDENCE_DIR` 指向本记录的 artifacts 目录），从该目录读 test-results.jsonl（-66）。

7. **完整性事件（-09、-54）。** 后核对发现源码或候选被改（source_unchanged=false、checkout changed、清单身份不符），驱动在写证据的同一事务里写 `integrity_violation{candidate_id, check_id, record_id, reasons, tree_before, tree_after}`，事件 id `<record_id>/integrity`（幂等）；监督器的封闭种类里已有它，同一步骤即唤醒 Commander（测试断言）。

8. **执行记录与证据（行为 6、7，-06、-52、-55、-60、-10、-11）。**
   - 记录按 execution.schema.json 1.1（受锁，不加字段）；它引用的 stdout、stderr 与声明工件都是本记录目录 `.hoh/evidence/<candidate>/<check>/<record>/` 里不可覆盖的文件（release_gate 要求引用在记录目录内，-11）；同时把它们写成对象并登记 artifacts 行（数据库引用对象路径）。
   - evidence 行要求生产者 Attempt（`attempt_id` NOT NULL，外键 attempts）与一条 artifacts 行（记录本身）：驱动的 API 以产出它的 Attempt id 为参数（M2-T16 的 QA/Reviewer Attempt；本任务测试用夹具 Attempt）。同一事务写 `evidence.recorded{evidence_id, record_id, attempt_id, check_id, tree_before, tree_after, observations, reasons, artifacts}`，事件 id `<record_id>/evidence`：它是 valid 之后重算的输入来源（前后 tree、观察、原因），也是多检查 Attempt 的生产者登记（一个 Attempt 每个记录一条，不复用 `attempt.artifacts` 的固定 id，-10）。
   - observations：有 test-results.jsonl 的检查是它的各行；没有逐测试结果的检查（build、deployment、independent-*）是声明工件的引用加记录自身的退出结论（-60）；两者都没有才是 INSUFFICIENT。
   - `valid(e, c, s)` 的原因是封闭枚举，AC-052-04 的 11 个是必测的最小集合，另有：stderr 与每个声明工件的 sha256、声明工件集合与计划一致、`timed_out`、退出码与结论一致、command/mode/cwd 与冻结计划一致、check_id 在计划中、记录 schema；每个原因各有单元测试。原因只进事件载荷与 acceptance_results.reason，不进以 ReasonCode 为类型的字段，所以现在不需要 CR；M2-T18 若经 API 发出，届时由它做细化 CR（-71）。

9. **acceptance_results（-01、-50）。** 每个 (AC, evidence) 一行（主键所限），聚合该证据里该 AC 的全部 test-result 行（AC 声明的 test_id 映射，不按编号推断，-70）：全 PASS 为 PASS；有 FAIL 为 FAIL；无 FAIL 而有 DEGRADED 为 DEGRADED；只有 SKIPPED 为 NOT_RUN；无效证据为 INVALID；reason 列出测试名与原因。行只追加。测试覆盖同一 TEST 的 PASS 与 FAIL 混合。

10. **traceability 检查（-07、-08、-56、-57、-59、-61、-70）。** `bash scripts/product/traceability.sh <profile>`：对每个范围内 TEST id，读它的场景检查在本候选上的**全部**记录（绑定本候选：清单引用 path+sha256、candidate_id、spec 一致；搜索根限定 `.hoh-dev/` 与产品的 `.hoh/evidence/`），每条记录先过与门禁相同的逐记录校验（导入受锁 release_gate.py 的 verify_ref、schema 校验与 load_test_results，不复制规则）；任一记录在该 TEST 上有非 PASS 行即不满足（先失败后通过记为 FLAKY），不回退到较早的成功。需求的 release_class 为 degradable 时按 release_gate.py:203-229 接受 PASS/DEGRADED 且至少一条 DEGRADED，其场景检查（只限可降级的检查）可以非零退出，报告标 degraded。报告 `traceability-report.json{candidate_id, profile, tests:{id: {check, records, passing:[测试名], status}}, missing, flaky}`；退出 0 当且仅当 missing 为空。门禁不读这份报告（release_gate 受锁），在 docs/22 写明；把 argv 改成 v1 由写者任务 M7-T02 承接（写进它的移交，M7-T04 是 writer=false 的 verify 任务）。TEST-052-05 是源码里可定位、名称含 `test_052_05` 的真实测试（tests/bundle 下：临时仓库，候选 C 齐全时退出 0；C' 真实删除一个 v0.1 AC 的夹具测试源、重新冻结、经 scripts/product/test_results.py 重新生成结果时非零并列出缺失 id；两份报告各绑定自己的候选；临时目录清理），traceability.sh 运行它并转成 test-result 行；本任务候选上的真实 traceability 预期非零（大量 TEST 未写），完成记录写明 AC-052-05 由夹具证明。

11. **independent-qa / independent-review（-02、-53、-65、-61）。** `bash scripts/product/independent.sh <qa|reviewer> <profile>`：上下文 JSON 由助手从 `$HOH_CANDIDATE_FILE` 与上一决定同法找到的全部记录（含失败）生成，用 tools/render_prompt.py 渲染。每次尝试不传 `--output-dir`（检查内默认 `attempts/<uuid>/`，各自唯一、保留），各自的 `--report-out`；从 agent_task 的结果取成功那次的 attempt 记录，复制为 native-attempt.json、raw-session.jsonl 与 independent-report.json，并核对与报告引用的 sha256 一致。回退只在未产出报告时（容量错误、会话开始前就结束）；写出报告（含 FAIL/UNKNOWN）即停止，不换 Agent 找 PASS。顺序：qa 先 pi 后 claude；reviewer 先 codex，再 codex `--model gpt-6.1-sol`，再 claude；grok 被 agent_task 在检查内拒绝。每次尝试的 `--timeout` 按剩余预算（计划超时减 run_check 的 15 s 宽限）。退出 0 当且仅当报告 PASS 且无 critical/high；3 当且仅当每次尝试都在会话开始前结束（缺认证、找不到 CLI），否则 1。提示词要求不改跟踪文件、不在未被忽略处新建文件，输出写到字面给出的 observations 目录。CI 没有认证，只跑带假 CLI 的套件测试；假 Agent 的结果永不报为 live。本任务候选上的真实会话预期报告 FAIL/UNKNOWN（许多 AC 未实现），done_when 要求的是会话与四个文件。

12. **测试的非空真（-58）。** TEST-052-02、-03 各带正对照：同一夹具检查在干净候选上得到 valid 证据、PASS 行（-02）与哨兵文件（-03）；变体里断言 C 有至少 1 行 INVALID、0 行 PASS（-02），没有执行记录且哨兵不存在（-03）。另有未打标签的测试：`checkout changed`、check_id 不在计划、未提交的跟踪改动、assume-unchanged、`.hoh/` 未被忽略。
