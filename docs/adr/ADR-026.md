# ADR-026 · 上下文装箱：四层 Prompt、强制项、份额、引用与重装箱

状态：设计审查中（M2-T09；事实已按合并 M2-T08 之后的代码核对）

## 背景

M2-T09 的验收是 REQ-039 的 AC-039-01 至 -04（TEST-039-01、-02 属检查 `unit`，-03、-04 属 `integration`）；done_when 为“REQ-039 全部 AC 通过”。需求依据见 `contracts/requirements.json` REQ-039（行为 1 至 8、失败模式 1 至 4、决定 1 至 2），算法依据 docs/07 §4，记录依据 docs/15 第 7 行。

起点（预研笔记 `.hoh-dev/evidence/m2t09-prep/README.md`；事实按 M2-T08 的最终提交 11ad4d3 核对）：

- 产品的 Prompt 是“职位契约 + 交接包 + 任务头”（`host/product.rs` `prompt_text`），四个占位符 `{{GOAL}}` 等原样发出，没有预算、计数、分层、引用。
- 记录只有 `prompt_revisions` 与 `attempts.prompt_sha256`（结束提交写，ADR-022 决定 11）；`attempts.resource_bundle_version` 有列无写者；没有输入引用与截断策略的存处。
- 没有内容寻址对象目录；`artifacts`、`handoffs` 表无写者；ContextHandoff 的 `references` 永远为空、`budget_tokens` 是常量 32 000。
- Commander 的唤醒摘要（ADR-025 决定 7）在准备时读活状态，载荷按 2 000 字节截头，不可重放。
- `CONTEXT_BUDGET_TOO_SMALL` 已在 ErrorCode 中；`BlockedReason` 不含它；`FailureClass` 只有 Transient、Auth、Capability。

## 决定

1. **纯核心 `hoh_core::context`（无 I/O）。** `estimate(text) = ceil(utf8 字节数 / 3)`：确定、单调、次可加（各段估算之和 ≥ 整段估算），所以分段计账的总和不超过预算时整段也不超过；所有计数标 `estimated: true`（REQ-039 决定 2），估算器 id `utf8-bytes/3` 写进截断策略。`pack(template, mandatory, entries, budget) -> Result<Packed, TooSmall{required, available}>`；`Packed{prompt, layers, stats{per_class, mandatory, total, estimated}, index, policy}`。同一输入两次 `pack` 字节相同：不用 HashMap 迭代、时间、浮点（份额用整数 floor）。

2. **四层与模板。** 四层即四个占位符：`{{GOAL}}`、`{{PROJECT_CONTEXT}}`、`{{TASK_CONTEXT}}`、`{{EVIDENCE_CONTEXT}}`，按模板自身的顺序填充（QA 的偏差控制依赖“证据最后读”，各职位顺序不同，不统一重排）；缺占位符、空值、填充后残留占位符都是错误（与 `tools/render_prompt.py` 同义）。不含占位符的覆盖契约（如 TEST-018-05 的 `security.md`）原样在前，四层按 GOAL、PROJECT、TASK、EVIDENCE 附在其后。职位契约 = 模板去掉占位符后的各段，逐段原样出现（AC-039-01 的“强制项逐字节出现”按段判定）。

3. **强制项（永不裁剪，REQ-039 行为 2）。** 合计为 M，装箱前算出，与候选条目无关：
   - 职位契约各段；GOAL 层：Run 的 goal，只有一个来源——StartRun 命令的 goal（`results::started_goal`），空白时写“（未给出）”（统一今天三处不同的来源与文案）。
   - PROJECT 层：spec 身份（spec_sha256 与 revision，没有 spec 时写“尚无 spec”而不省略）。docs/15 的四层构成把“规格”放在 Project Context、把“目标/范围/候选/AC”放在 Task Context，这里照此分层。
   - TASK 层：任务范围（task id、title、role、writer、依赖）；全部 in-scope AC 的正文（`task_requirements ⋈ acceptance_criteria`）；candidate 身份（id、commit、tree，或“尚无候选”）；输出 Schema：该职位输出契约（TaskResult、IndependentReport、DecisionPayload）的 JSON Schema 正文，紧凑序列化，内联它引用的 `$defs`；首个输入欠着时的交接包（REQ-019 行为 4 不可丢；位置从“契约之后、任务头之前”改到 TASK 层的开头，修订 ADR-024 决定 4）；Commander turn 的唤醒头部（causation_id、expected_revision、role_epoch、nonce、输出文件路径、Task 快照 revision，ADR-025 决定 7 的“永不丢”）。
   - 固定文本：各层标题、条目标题行格式、引用索引的指针行（指针行按 64 位十六进制的固定长度计入 M）。
   - 预算 < M：`TooSmall{required: M, available: budget}`，不生成 Prompt（决定 9）。

4. **份额与排序（REQ-039 行为 3、决定 1，失败模式 2）。** 剩余 R = 预算 − M；代码 `floor(R×45/100)`、证据 `floor(R×35/100)`、知识 `floor(R×20/100)`，硬上限，不挪用。类到层：代码 → TASK 层（在强制项之后），知识 → PROJECT 层，证据 → EVIDENCE 层。条目 `Entry{class, path, sha256, text, summary, relevance, recency, causal, kind}`，分值为 0..=100 的整数；类内排序键 (relevance 降、causal 降、recency 降、path 升、sha256 升)。REQ-039 行为 3 列出三个因素但没有规定先后；先 causal 后 recency 是因为 docs/07 §3 要求监督摘要超预算时“按严重性/因果链选取”，ADR-025 决定 7 也已承诺“严重度、因果链、最新”的次序（决定 11），统一用一个键。分值由收集输入的一方给出（决定 12），装箱器不解释条目内容。QA 的偏差控制（docs/07 §4：先需求、AC、工件，后开发自测和建议）由收集方给开发者自述的条目（TaskResult 的 summary、自测结果、建议）较低的 relevance 段实现，装箱器不为职位特判。依次尝试：全文（带标题行 `path sha256`）→ 条目自带的摘要（装箱器不自己摘要）→ 只进引用。严格前缀：一旦某条既放不下全文也放不下摘要，它与其后的全部只进引用（失败模式 2 的“只装入排序靠前的条目”）。条目的标题行计入其类的份额。`kind = memory` 的条目在标题里标“经验”，不作验收事实（行为 7 的后半；Skill 短索引属 M3-T03）。

5. **引用与索引（行为 4）。** 未装入全文的条目（只引用或以摘要代替）各有一个索引项 `{path, sha256, class, disposition, tokens}`；索引写成对象（决定 6），Prompt 里只有一行固定格式的指针（计入 M），所以份额为 0 时引用也有处可放。AC-039-01 的“被省略条目数 == 引用索引条目数”即索引项数。

6. **内容寻址对象目录。** `.hoh/objects/sha256/<前 2 位>/<64 位>`；写法同首个输入（暂存文件、硬链接、目录 fsync），同内容幂等；读回校验 sha256。装箱的每个输入条目、索引与装箱清单（决定 7）都是对象；`artifacts` 行在 Attempt 的结束提交里登记（`INSERT OR IGNORE`，UNIQUE(sha256, path)），执行器不写库（ADR-022 决定 11 不变）；执行器写了对象而 host 在结束提交前崩溃留下的对象无害（内容寻址），回收不在本任务。M2-T10 复用这个目录与登记写法；`handoffs` 表行不在本任务（没有 AC 要求，记为 M2-T16 的移交）。

7. **记录与重装箱（行为 1、8，AC-039-04，失败模式 4）。** 装箱清单对象 = 模板（路径与 sha256）、强制项的值（含 nonce、桥文件路径、attempt id 这些本 attempt 特有的值）、条目引用列表、预算、截断策略、资源包版本。结束提交写：`attempts.prompt_sha256`（已有）、`attempts.resource_bundle_version`（已有列）、一条 `context.packed{prompt_sha256, resource_bundle_version, budget_tokens, estimated, policy{estimator, shares:[45,35,20], order, rule:"prefix"}, manifest, index, inputs:[{path, sha256, class, disposition, tokens}], layer_tokens}` 事件（事件 kind 开放，不改 schema）。`repack(manifest)` 只读对象目录与编译进二进制的资源，资源包版本不同即拒绝；同版本时逐字节相同。资源包版本 = `<CARGO_PKG_VERSION>+<sha256(按路径排序的 (路径, sha256) 列表)>`，覆盖编译进二进制的 `resources/prompts/*.md` 与输出 Schema。覆盖契约文件（项目层）不在资源包里，可能在磁盘上被改写，所以装箱时把它的内容也写成对象，清单按 sha256 引用；`prompt_revisions.content_sha256` 照旧记录它。

8. **预算的来源。** 每个 Attempt 用常量 `handoff::BUDGET_TOKENS`（32 000）；由交接驱动的 Prompt 用交接包的 `budget_tokens`（今天同值）。REQ-018 的配置键表没有上下文预算键，加键需要 CR，本任务不加；用户遇到 CONTEXT_BUDGET_TOO_SMALL 时目前无处可调，记为余项。

9. **预算不足（失败模式 1）。** 执行器的 `start` 以 Refusal `CONTEXT_BUDGET_TOO_SMALL` 拒绝，`attempt.start_refused` 的载荷带结构化 `{required, available, estimated: true}`（docs/05 的 `details`）；Attempt 从 STARTING 结为 FAILED，进程不启动、不进入 RUNNING，不写 Prompt 记录。新增内部失败类别 `FailureClass::Decision`：确定性失败不重试，任务直接 BLOCKED(NEED_DECISION)，`failure_reason` 为 CONTEXT_BUDGET_TOO_SMALL（不改 BlockedReason 枚举，不需要 CR）；reconcile 读回持久化的类别时认得它。这是对 ADR-020 决定 1 的补充：前三类不变，第四类只由执行器在启动前、对同一输入必然再次失败的拒绝给出（今天只有预算不足），与 Exhausted 一样落到 NEED_DECISION，只是不先花掉 8 次重试。

10. **交接只传引用（行为 5，AC-039-03，失败模式 3）。** `handoff::verification` 与 `role_change` 填 `references`（候选清单、TaskResult、原始日志等对象的 ArtifactRef）与 `budget_tokens`，从不内联原始日志；证据条目的来源按事件种类与字段白名单取值，`adapter.*` 事件的原始帧永不成为条目。M2-T16 之前产品没有 QA 的派发：TEST-039-03 的 QA 半边在 store 级测试里用 `accept_task_result` 生成验证交接包，再调用执行器用的同一个装箱函数；Commander 半边经产品执行器与假 pi（照 TEST-019-02）。“QA 派发必须经同一装箱函数”移交 M2-T16。

11. **Commander 的唤醒摘要（修订 ADR-025 决定 7）。** 唤醒头部是强制项（决定 3）；唤醒的事件、Task 快照之外的状态、其他待执行的唤醒、各职位绑定与最近被拒的回答是证据条目，按决定 4 装入，`SHOWN_PAYLOAD` 的截头改为“摘要 + 引用”；摘要读的活状态在准备时写成对象，重装箱只读对象。ADR-025 决定 7 留给本任务的“按因果链”一步：relevance 由严重度给出（integrity、critical、high、其余），causal 为该事件是否在唤醒的触发链上（触发器记下的事件 id 与它们的 causation 链），recency 为 seq 的名次；有界（Task 列表与其他唤醒各至多 50 条并给总数）与“永不丢”的值不变。

12. **候选的来源。** M2 里代码类没有产品来源（Task 没有路径范围）：类与份额照常实现，AC-039-01、-02 用固定夹具覆盖三类；代码类的来源随 M3-T02、M3-T04 的规格追踪加入。知识类今天只有项目里的文档引用与（M5 的）memory。这是来源的分期，不是 REQ-039 的范围删减：REQ-039 的四个 AC 都判定装箱器本身。

## 实施切片

S1 纯核心（估算、份额、排序、严格前缀、索引、确定性；TEST-039-01、-02）；S2 模板渲染（六个内置模板与无占位符的覆盖契约）；S3 对象目录与资源包版本；S4 收集输入（强制项与白名单条目，`Assignment` 带装箱输入）；S5 执行器接线（Refusal、`FailureClass::Decision`、记录与 `context.packed`、既有布局测试按原意改写）；S6 交接只传引用（TEST-039-03）；S7 重装箱（TEST-039-04）；S8 冻结候选、检查与审查。每片先写失败测试；测试名带 `test_039_NN`。

## 受影响的既有测试（实施时逐个记下改动与理由，断言的性质不变）

- `host/product/tests.rs` 的布局测试、TEST-018-05（契约在前、`sent_sha256` 等于发出文本的 sha256）、TEST-019-02 与 `a_new_developers_first_turn_starts_from_its_handover_package`（契约 < 交接包 < 任务；交接包移入 TASK 层后仍在契约之后、唤醒与任务之前）。

## 风险与余项

- 强制项没有上界：in-scope AC 的正文、交接包的 `state` id 列表、覆盖契约文件都可能很大。按 REQ-039 行为 2 它们不裁剪，超出预算即 CONTEXT_BUDGET_TOO_SMALL、任务 BLOCKED(NEED_DECISION)；在常量预算下用户无处调大（决定 8 的余项）。实施时在 S5 测量六个内置职位在典型输入下的 M（契约约 1 500 到 2 000 估算 token，DecisionPayload 内联 `$defs` 后约 1 000），写进本 ADR。
- 估算 ≤ 预算不保证真实 tokenizer ≤ 模型窗口：REQ-039 决定 2 接受以估算为准，只标 estimated；`utf8 字节数 / 3` 对中文约为每字 1 token，对英文偏保守。
- 对象目录的孤儿对象（执行器写了、结束提交没发生）不回收，回收属后续任务。
