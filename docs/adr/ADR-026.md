# ADR-026 · 上下文装箱：四层 Prompt、强制项、份额、引用与重装箱

状态：第四版（设计审查第 3 轮之后的设计更正；M2-T09）

## 背景

M2-T09 的验收按 CR-016 为 REQ-039 的 AC-039-01、-02、-04（TEST-039-01、-02 属检查 `unit`，-04 属 `integration`）；AC-039-03 要求“Runtime 为 QA 生成 ContextHandoff 与 Prompt”，产品的 QA 派发属 M2-T16，按 CR-004 的归属规则改归 M2-T16（CR-016）。需求依据见 `contracts/requirements.json` REQ-039（行为 1 至 8、失败模式 1 至 4、决定 1 至 2），算法依据 docs/07 §3、§4，四层构成依据 docs/15。

起点（预研笔记 `.hoh-dev/evidence/m2t09-prep/README.md`；事实按 main e72f9c0 核对）：

- 产品的 Prompt 是“职位契约 + 交接包 + 任务头 + 唤醒段”（`host/product.rs` `prompt_text`、`supervision_text`），四个占位符 `{{GOAL}}` 等原样发出，没有预算、计数、分层、引用。
- 记录只有 `prompt_revisions` 与 `attempts.prompt_sha256`，在结束提交里写（ADR-022 决定 11）；`attempts.resource_bundle_version` 有列无写者；没有输入引用与截断策略的存处。
- 没有内容寻址对象目录；`artifacts`、`handoffs` 表无写者；ContextHandoff 的 `references` 永远为空、`budget_tokens` 是常量 32 000。
- Commander 的唤醒摘要（ADR-025 决定 7）在准备时读活状态，载荷按 2 000 字节截头，不可重放。
- `CONTEXT_BUDGET_TOO_SMALL` 已在 ErrorCode 中；`BlockedReason` 不含它；`FailureClass` 只有 Transient、Auth、Capability。

- 验收归属（-05、-50）：M2-T09 的依赖闭包里没有 QA 派发，AC-039-03 改归 M2-T16（CR-016）。

## 第四版的更正（设计审查第 3 轮：Codex M2T09D-200..202）

强制项的上界第二次出问题（第 2 轮 -154，第 3 轮 -201、-202），按 docs/19 不再逐条补，先写清原则再改：

- **强制项只按 REQ-039 行为 2 的清单定，照原样放入，不为凑上界而截断或改归证据。** 超出预算就是 CONTEXT_BUDGET_TOO_SMALL，这是需求规定的结果。第三版把 Commander 非主题 Task 的 AC 改作证据，本是为了上界；但普通聚合唤醒的快照 Task 全都是主题（-202），这条既不带来上界，又让重新触发的唤醒漏掉主题（-200：`supervisor.retrigger` 用 `task_ids` 数组）。第四版撤回它：监督 turn 的 in-scope AC 是快照里全部 Task 的 AC，全文放入（决定 3）；唤醒主题只用于因果排序，并按 Runtime 实际写出的形状读（`task_id` 与 `task_ids`，决定 11）。
- **不在强制项清单里的东西可以有上界，但表示必须不会被当成原物（-201）。** 第 4 轮（-250）补充：交接包虽不在 REQ-039 行为 2 的清单里，REQ-019 行为 4 却要求它完整地进入新持有者的首个输入，所以它与强制项同样不截断（决定 3）。
- **常量预算下装不下的唤醒是已知的容量限制，登记为延期（-202）。** Run 因 `context` 不可用而 BLOCKED(COMMANDER_UNAVAILABLE)，界面上有 required 与 available；补救路径（上下文预算的配置键，改 REQ-018 的键表需要 CR）登记在 PROGRESS 的待办里，v1 soak 之前处理。实施时测量六个内置职位的 M，以及装不下时的阈值（一个唤醒的快照 Task 带多少条多长的 AC），写进本 ADR。

## 决定

1. **纯核心 `hoh_core::context`（无 I/O）。** `estimate(text) = ceil(utf8 字节数 / 3)`：确定、单调、次可加。计账以渲染后的字节为准（-55）：M = 只放强制项、不放任何条目时整份 Prompt 的估算（契约各段、各层的强制项、它们之间的分隔、指针行都在里面）；每个条目的花费 = 它渲染后的块（含块前的分隔）的估算；放入条目只在 Prompt 里追加这些块的字节，所以整份估算 ≤ M + 各块估算之和 ≤ 预算。`pack(template, mandatory, entries, budget) -> Result<Packed, PackError>`；`PackError::{TooSmall{required, available}, Template, EmptyLayer}`；`Packed{prompt, sha256, stats, inputs, index, index_object, index_sha256}`。所有计数标 `estimated: true`（REQ-039 决定 2），估算器 id `utf8-bytes/3` 写进截断策略。同一输入两次 `pack` 字节相同，输入条目的先后不影响结果：不用 HashMap 迭代、时间、浮点（份额用整数 floor，在 u128 里算）。装箱格式有常量 `context::FORMAT`（`hoh-context/1`），见决定 7。

2. **四层与模板。** 模板的四个占位符 `{{GOAL}}`、`{{PROJECT_CONTEXT}}`、`{{TASK_CONTEXT}}`、`{{EVIDENCE_CONTEXT}}` 按模板自身的顺序填充（QA 的“证据最后读”依赖它，不统一重排）。只校验模板本身（-06、-53）：四个已知占位符各恰好一次，或一个也没有；有其他形如 `{{NAME}}` 的占位符、只有其中几个、或某个出现两次，都是模板错误。按模板里的位置单遍替换，填进去的值是数据，不再扫描或解释（goal、AC 正文里出现字面的 `{{GOAL}}` 照样放入）；这与 `tools/render_prompt.py`（引导期工具，扫描填充后的全文）不同，产品不沿用它。没有占位符的契约（如 TEST-018-05 的覆盖文件）去掉末尾空白后原样在前，四层按 GOAL、PROJECT、TASK、EVIDENCE 附在其后，各带固定标题。每层的值永不为空（-54）：GOAL、PROJECT、TASK 的强制项总有内容（决定 3，空白即 `EmptyLayer`），EVIDENCE 总以指针行结尾（决定 5）。模板错误或某层强制项为空（`EmptyLayer`）时执行器以 Refusal `PROMPT_UNAVAILABLE` 拒绝启动，类别 Decision（决定 9；同一份输入会再被拒）。层的统计按 REQ-039 行为 1 与 docs/15 的四层命名（-65b）：`role_contract`（契约各段）、`project`、`task`（GOAL 的值属于 Task Context）、`evidence`。

3. **强制项（永不裁剪，REQ-039 行为 2）与作用域（-03）。** M 在装箱前算出，与候选条目无关：
   - 职位契约各段。
   - **GOAL 的值**：Run 的 goal，只有一个来源——StartRun 命令的 goal（`results::started_goal`），空白时写“（未给出）”（统一今天三处不同的来源与文案）。Commander 的 turn 另写本次唤醒要回答的问题：唤醒 id、种类、严重度、指纹（commander.md 把“当前目标”定义为本次唤醒要回答的问题，-65a）。
   - **首个输入（-04、-61、-154、-201、-250）**：首个输入欠着时，整个交接包（原包的 JSON）放在模板**第一个占位符**的值里、该层自己的强制项之后、任何条目之前，与强制项一起计入 M：REQ-019 行为 4 要求新持有者的首个输入就是完整的 checkpoint 交接包，所以它不截断、不以摘要代替；装不下即 CONTEXT_BUDGET_TOO_SMALL（Commander 的 `context` 不可用），与第四版的容量延期同一处理。（第四版曾在列表超过 50 个时改为摘要加路径；第 4 轮 -250 指出新持有者可以不读完整对象就付清首个输入，撤回。）
   - **PROJECT 的值**：spec 身份（spec_sha256 与 revision；没有 spec 时写“尚无 spec”，不省略）。docs/15 把“规格”放在 Project Context。
   - **TASK 的值**：作用域、全部 in-scope AC 的正文、candidate 身份（id、commit、tree，或“尚无候选”）、输出 Schema。作用域按 Attempt 的种类：
     - 工作任务：该 Task（id、title、role、是否写者、依赖），in-scope AC = `task_requirements ⋈ acceptance_criteria`，取 Run 当前 spec 下的。
     - 监督 turn（内部 Task `<wake>/turn/<n>` 没有 `task_requirements`）：唤醒在分配时记下的完整快照（每个 Task 的 id 与分配时的 revision，不按展示上限截断）与 title。in-scope AC 是快照里**全部** Task 的 AC，全文放入（第四版，-200、-202：重新触发的唤醒的快照就是 `task_ids`，所以它的 Task 的 AC 一定在内）；装不下即 CONTEXT_BUDGET_TOO_SMALL（决定 9 的 `context`）。不涉及具体 Task 的唤醒写明“本唤醒不涉及具体任务”，不列 AC。唤醒的事件、Task、其他唤醒的总数也在这里。不把内部 Task 没有关联行当成“没有 in-scope AC”。再加唤醒头部：causation_id、expected_revision、role_epoch、nonce、输出文件的路径（准备时实际给出的那个）、快照的 revision（ADR-025 决定 7 的“永不丢”）。
     - 验证交接驱动的 turn（M2-T16 的 QA/Reviewer）：交接包的 `acceptance_ids` 的 AC 正文。收集函数在本任务实现并测试，派发属 M2-T16。
   - **输出 Schema（-65c、-159）**：该职位亲手交回 Runtime 的 schema，紧凑序列化，内联它引用的 `$defs`：Commander 为 Message 与 DecisionPayload；developer、cto、researcher 为 TaskResult；qa 为 TaskResult、acceptance-observation 与独立报告；reviewer 为 TaskResult 与独立报告。独立报告只给 Agent 自己写的 `hoh-report` 块的子集（role、status、scope、findings 四个属性取自 independent-report.schema.json），桥填写的字段不给，免得与契约“自己写会被拒绝”相矛盾。工具生成的记录（candidate manifest、execution 记录）不是 Agent 交回的，不列。交接包的 `output_contract` 只名主要的一种，与此不矛盾。这些 schema 文件编译进二进制，进资源包（决定 7）。放在 TASK 的值里（模板在契约正文之后没有别的位置），层统计计入 `role_contract`（docs/15 把输出 Schema 归 Role Contract）。
   - 固定文本：没有占位符时的层标题、条目标题行、指针行（指针行里的 sha256 固定 64 位，所以 M 与索引内容无关）。
   - 预算 < M：`TooSmall{required: M, available: budget}`，不生成 Prompt（决定 9）。

4. **份额与排序（REQ-039 行为 3、决定 1，失败模式 2）。** 剩余 R = 预算 − M；代码 `floor(R×45/100)`、证据 `floor(R×35/100)`、知识 `floor(R×20/100)`，硬上限，不挪用（一类用不完，另一类也不能多用）。类到层：代码 → TASK，知识 → PROJECT，证据 → EVIDENCE，各在该层强制项之后（EVIDENCE 在指针行之前）。条目 `Entry{class, kind, path, text, summary, relevance, recency, causal}`，三个分值都是 u64，由收集方给出，装箱器不解释条目内容；装箱器自己算正文的 sha256。类内排序键按 REQ-039 行为 3 与 docs/07 §4 的列举次序（-63）：(relevance 降、recency 降、causal 降、path 升、sha256 升)；同一 (类, path, sha256) 只算一次：先按它归并、保留全序中最先的那条，再排序（-157）。需要“先严重度、再因果、再新近”的 Commander 摘要由它的收集方把严重度与因果折进 relevance（决定 11），装箱器不为职位特判。QA 的偏差控制（docs/07 §4：先需求、AC、工件，后开发自测与建议）也由收集方给开发者自述的条目较低的 relevance。依次尝试：全文（带标题行）→ 条目自带的摘要（装箱器不自己摘要）→ 只进引用。严格前缀：一旦某条既放不下全文也放不下摘要，它与同类其后的全部只进引用（失败模式 2 的“只装入排序靠前的条目”）。条目的标题行与块前分隔计入其类的份额。`kind = memory` 的条目在标题里标“经验，不作验收事实”（行为 7 的后半；Skill 短索引属 M3-T03）。

5. **引用与索引（行为 4）。** 未装入全文的条目（只引用或以摘要代替）各有一个索引项 `{path, sha256, class, disposition, tokens}`，`sha256` 是正文的；索引写成对象（决定 6），Prompt 里只有一行固定格式的指针，在 EVIDENCE 的值的末尾、前面总有一个空行，给出索引对象的项目相对路径 `.hoh/objects/sha256/<2>/<64>`（-158；Commander 在项目外运行，TASK 里给出项目根），长度固定、计入 M，所以份额为 0 时引用也有处可放。AC-039-01 的“被省略条目数 == 引用索引条目数”由测试独立核对：被省略 = 正文不是 Prompt 子串的条目（-60a）。

6. **内容寻址对象目录（-09、-51）。** `hoh_core::objects`：`.hoh/objects/sha256/<前 2 位>/<64 位>`。多写者的写法：每次写入用独占的暂存名（进程号加进程内计数，`create_new`；名字已被占用——例如进程号复用后崩溃留下的——就换下一个，从不复用或删除别人的暂存，-102）；写完 fsync，再硬链接到位；位置上已有文件时读回校验，字节符合名字即取用，不符合（损坏）则用已 fsync 的暂存 rename 覆盖、再校验；然后从对象所在目录起逐级 fsync 到 `.hoh`，所以新建的目录链在掉电后仍在。读取只在字节符合名字时成功。崩溃留下的暂存不妨碍后来的写入（名字不重）；回收不在本任务。写满等 I/O 错误原样返回，执行器以瞬时类拒绝启动。执行器的 `start` 由 runner 放在阻塞线程上调用，对象写入不占异步线程（-163）。`artifacts` 行（`INSERT OR IGNORE`，UNIQUE(sha256, path)）的 path 是项目相对的对象路径 `.hoh/objects/sha256/<2>/<64>`，登记后再读回该行核对。M2-T10 复用这个模块与登记写法。`handoffs` 表的写入（ADR-018、ADR-024 决定 3 曾分给 M2-T09/T10）改由 M2-T16 承接：它需要的工件存储由本任务提供，但没有 AC 需要这张表；两份 ADR 加注记。

7. **记录与重装箱（行为 1、8，AC-039-04，失败模式 4；-02、-07、-56、-57）。**
   - **清单（manifest）对象**：`{format, resource_bundle_version, template{layer, path, sha256}, mandatory{goal, project, task, evidence}, entries[{class, kind, path, sha256, summary_sha256, relevance, recency, causal}], budget, policy}`。强制项按渲染后的字符串记下（准备时读的活状态、nonce、输出文件路径、attempt id 都已在其中），条目的正文与摘要各是一个对象。所以重装箱不再调用 `assignment()` 或 `supervision_input()`，只读对象。模板正文也是对象：内置契约随资源包，覆盖文件可能被改写，按 sha256 引用其对象。
   - **资源包版本** = `<CARGO_PKG_VERSION>+<sha256>`，sha256 覆盖：按路径排序的编译进二进制的资源（六个内置契约、输出 Schema 所在的 schema 文件）各自的 sha256，以及装箱格式 `context::FORMAT`。工作区版本号一直是 0.0.0（`Cargo.toml`），所以格式常量是区分渲染代码的唯一手段：一个金样测试固定一组输入的 Prompt sha256，渲染代码改了而 `FORMAT` 没改，测试即失败。
   - **何时写**：执行器的 `start` 在 spawn 之前写好对象，`Started` 带回 Prompt 记录（模板来源、清单 sha256、Prompt sha256、资源包版本、统计）；runner 在把 Attempt 记为 RUNNING 的那个提交里（启动门打开之前）写 `prompt_revisions`、`attempts.prompt_revision/prompt_sha256/resource_bundle_version`、`context.packed{prompt_sha256, resource_bundle_version, format, manifest, index, budget_tokens, estimated, policy{estimator, shares:[45,35,20], order, rule:"prefix"}, inputs:[{kind, path, sha256, class, disposition, tokens}], layers}` 事件（kind 开放，不改 schema）与 `artifacts` 行。所以启动门打开过的 Attempt 都有记录，结束提交前崩溃、由 reconcile 结算的也一样；启动门没开的 Attempt 没有发出 Prompt，没有记录也无妨（它的对象无害）。这修订 ADR-022 决定 11（“在结束提交里写”改为“在 RUNNING 的提交里写”），执行器仍不写库。
   - **输入引用列表（-152）**：`inputs` 依次是模板（kind `template`，内置契约按资源路径、覆盖文件按对象）、首个输入交接包对象（kind `lead`，如有）、清单对象（kind `manifest`）与每个条目（kind `entry`），所以永不为空，也包含重装箱实际要读的全部对象。
   - **重装箱** `repack(project, manifest_sha256)`：读清单与它引用的对象，资源包版本与当前不同即拒绝；相同则调用同一个 `pack`，结果逐字节相同。
   - **装箱参数进 Run 配置（-67、-103、-151）**：只有 StartRun 写配置快照（`team.rs` 今天如此），带 `context{budget_tokens, shares}`；checkpoint 与 ConfigureTeam 不改它。`pack` 接受份额参数。快照没有该项的旧 Run 用冻结的命名默认值 `CONTEXT_V1`（32 000，45/35/20），它以后不改；默认值要变时另立 `CONTEXT_V2`，只给新 Run。估算器与装箱格式是代码的身份，不是 Run 的参数：它们随每个 Attempt 的资源包版本与 `policy` 记下。所以运行中的 Run 不因二进制升级静默改变份额与预算（docs/07 开篇）。
   - **金样与反例（-160）**：金样测试按 `FORMAT → sha256` 的表核对，输入覆盖每个渲染分支（有占位符与无占位符、摘要、经验标签、路径里的控制字符、证据强制项为空、首个输入）；首次发布之前 `hoh-context/1` 的金样可随渲染改动更新并经审查，发布之后改渲染必须换 FORMAT。重装箱的反例有两条：对象损坏时重装箱失败；清单指向另一个对象时 sha256 不同。

8. **预算的来源。** Run 配置快照的 `context.budget_tokens`，写入时取常量 `handoff::BUDGET_TOKENS`（32 000）；由交接驱动的 Prompt 用交接包的 `budget_tokens`（今天同值）。REQ-018 的配置键表没有上下文预算键，加键需要 CR，本任务不加；用户遇到 CONTEXT_BUDGET_TOO_SMALL 时目前无处调大，记为余项。

9. **预算不足（失败模式 1；-01、-52、-64）。** 执行器的 `start` 以 Refusal `CONTEXT_BUDGET_TOO_SMALL` 拒绝，`attempt.start_refused` 的载荷带结构化 `details{required, available, estimated: true}`（docs/05）；Attempt 从 STARTING 结为 FAILED，进程不启动、不进入 RUNNING，没有 Prompt 记录。新增失败类别 `FailureClass::Decision`（ADR-020 决定 1 的补充：前三类不变，第四类只由执行器在启动前、对同一输入必然再被拒的拒绝给出：预算不足与模板错误），持久化为 `{"class": "decision"}`，reconcile 读回时认得它。两条路径：
   - **工作任务**：`AfterFailure::Decide`，不重试，任务 BLOCKED(NEED_DECISION)，写 `need_decision{reason: "refused_deterministically", ...}`（唤醒 Commander 的事件，REQ-021 行为 1）与 `task.blocked`；Attempt 的 `failure_reason` 与 `attempt.start_refused` 写明原因与数值。
   - **监督 turn**：它的内部 Task 照 ADR-025 决定 3 结为 CANCELLED、写 `supervisor.turn_failed{failure: {"class": "decision"}}`。ADR-025 的不可用原因表加一行 `context`（与 `capability` 同型）：对象是当前 epoch 的 turn；事实是有 turn 以 Decision 类失败，且按 turn 的次序其后没有该 epoch 的 turn SETTLED；恢复事实是此后该 epoch 有 turn SETTLED，或换 epoch。所以第一次拒绝即判为不可用，Run 照 ADR-025 决定 5 声明 COMMANDER_UNAVAILABLE（有 need_decision 义务时另声明 NEED_DECISION），不按退避重做。半开试探照旧（冷却期一次）：唤醒的强制项会变（Task 快照、spec 的 AC 集合随规格修订而变，首个输入随 epoch 而变），试探是它恢复的途径；一次被拒的试探在任何进程启动之前就结束，不调用 Agent。`supervisor.unavailable` 的观察带被拒的 attempt id。

10. **交接只传引用（行为 5，失败模式 3；-08、-58）。**
    - **谁写引用对象、谁是生产者（-100、-101、-150）**：登记 `artifacts` 行的同一事务写 `attempt.artifacts{attempt_id, run_id, role, session_id, items:[{artifact_id, sha256, path, mime, kind, name}]}` 事件（kind 开放，不改 schema），它记下生产者；`artifacts` 行照旧按内容去重，两个 Attempt 的相同字节共用一行、各有自己的事件。执行器在 turn 结束时把该 Attempt 的原始日志文件写成对象（决定 6），随结果交给 runner；runner 在把工作效果记为 OBSERVED 的那个事务里登记它们（与 Commander 桥接输出的登记同一处），所以效果提交后、结束提交前崩溃也不丢。结束从未被观察到的 Attempt（host 在 OBSERVED 之前崩溃）的原始日志留在 `.hoh/attempts/<attempt>/`，不登记、不被引用（余项）。交接包在 store 的事务里生成，只沿 `attempt.artifacts` 事件取引用，不读文件内容：`verification` 取产出候选的 Developer Attempt 的；`role_change` 取该职位前任持有者（前一 epoch 的会话）在本 Run 里各 Attempt 的，按事件次序最新的至多 20 条。引用不读原始日志内容，ADR-024 决定 1 的结构性保证（交接包不含旧会话内容）不变。`ArtifactRef.path` 是项目相对的对象路径，所以“文件存在”可按项目根核对。`budget_tokens` 取 Run 配置快照的值。
    - **只供引用的种类**：原始日志、`adapter.*` 事件的原始帧、完整的 TaskResult 对象，只以 ArtifactRef 或索引项出现，永不成为条目的正文或摘要。证据条目的来源按事件种类与字段白名单取值；开发者自述的可展示部分只取 TaskResult 的 `status` 与 `summary`，标“开发者自述，仅作线索”，relevance 低于需求、AC 与工件。
    - **验证（M2-T09 内）**：Commander 半边经产品执行器与假 pi（照 TEST-019-02）：哨兵放进前任的原始日志开头、`adapter.unknown_event` 与 `adapter.diagnostic` 的帧、TaskResult 的非白名单字段，新 Commander 的 Prompt 中哨兵 0 次，references 非空、每项 64 位十六进制且文件存在，Prompt 的估算 ≤ 交接包的 `budget_tokens`。QA 半边的收集与装箱有函数级测试。这些不计为 AC-039-03 的证据：正式的 TEST-039-03 由 M2-T16 经产品 QA 派发实现（CR-016）。

11. **Commander 的唤醒摘要（修订 ADR-025 决定 7；-59）。** 唤醒的问题在 GOAL、唤醒头部在 TASK，都是强制项（决定 3）；唤醒的事件、Task 快照之外的状态、其他待执行的唤醒、各职位绑定与最近被拒的回答是证据条目，按决定 4 装入，`SHOWN_PAYLOAD` 的截头改为“摘要 + 引用”：事件载荷整个是条目正文（对象），摘要是固定字段（种类、seq、task_id、attempt_id、原因码）的紧凑 JSON。有界（Task 列表与其他唤醒各至多 50 条并给总数）与“永不丢”的值不变。ADR-025 决定 7 留给本任务的“按因果链”：
    - **唤醒主题（-153、-200）**：触发器各事件（`event_seqs`）载荷里 task_id、issue_id、attempt_id、role、candidate_id 五个字段的取值，加上 `task_ids` 数组的每个元素（记作 task_id；`supervisor.retrigger` 只写这个数组，`persistence/supervise.rs` 也读它），之并。`supervise.rs` 的指纹取其中第一个存在者；自带 fingerprint 的事件也按这些字段取。主题只用于因果排序，不决定哪些 AC 是强制项。
    - causal：条目（事件载荷、Task、绑定、被拒的回答）的这五个字段中有取值落在唤醒主题里为 2；经 task_id 或 attempt_id 关联到快照里的 Task 为 1；其余为 0。events 表没有 causation 列，所以按这些字段算。
    - **整载荷与白名单（-162）**：只有唤醒的事件（supervise.rs 分类的封闭种类）以整个载荷为条目正文；其中 `task_result_json` 这类内嵌完整 TaskResult 的字段只供引用，正文里换成引用。其他来源一律按白名单取字段。
    - relevance = 严重度档（integrity 3、critical 2、high 1、其余 0）× 3 + causal；recency = seq。于是摘要按严重度、因果、新近排序，与 ADR-025 决定 7 的承诺一致。

12. **候选的来源与承接（-62）。** M2 产品里代码类没有来源：Task 没有路径范围，产品也还没有候选（`accept_task_result` 无产品调用者，候选冻结属 M2-T10）。类与份额照常实现，TEST-039-01、-02 用固定夹具覆盖三类。承接：M2-T16（CR-016 起含 REQ-039）为 QA、Reviewer 与返工的 Developer 加入代码类来源——冻结候选相对其基准改动的文件，在候选的 commit 上读取——并在其审查中核对；按任务范围选代码随 M3-T02、M3-T04 的规格追踪加入。知识类今天只有项目里的文档引用与（M5 的）memory。这是来源的分期，不删 REQ-039 的范围：装箱器本身的行为与三个 AC 在本任务判定，代码来源的承接写进 PROGRESS 的移交项。

## 风险与余项

- 强制项的上界：交接包在 Prompt 里有上界（决定 3 的摘要）；in-scope AC 正文（工作任务自己的，监督 turn 的快照全部 Task 的）与覆盖契约文件没有。按 REQ-039 行为 2 它们不裁剪，超出预算即 CONTEXT_BUDGET_TOO_SMALL（工作任务 BLOCKED(NEED_DECISION)，Commander 不可用、Run BLOCKED(COMMANDER_UNAVAILABLE)）；在常量预算下用户无处调大（决定 8 的余项）。这是登记的延期（第四版）：上下文预算的配置键（需要改 REQ-018 键表的 CR）在 v1 soak 之前处理。实施时测量六个内置职位的 M 与装不下的阈值，写进本 ADR。
- 估算 ≤ 预算不保证真实 tokenizer ≤ 模型窗口：REQ-039 决定 2 接受以估算为准，只标 estimated；`utf8 字节数 / 3` 对中文约为每字 1 token，对英文偏保守。
- 对象目录的孤儿对象（执行器写了、启动门没开）与崩溃留下的暂存不回收，回收属后续任务。
- 结束从未被观察到的 Attempt 的原始日志不登记（决定 10）。
