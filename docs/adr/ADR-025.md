# ADR-025 · Commander 监督：触发器、去抖、唤醒与 Commander 不可用

状态：采纳（第十二版，修正复审第 11 轮之后；M2-T08）

## 背景

M2-T08 的验收是 REQ-021 的 AC-021-01 至 -04（TEST-021-01、-02 属检查 `unit`，-03 属 `recovery`，-04 属 `integration`），done_when 另要求：Commander 不可用时 Run 进入 BLOCKED（COMMANDER_UNAVAILABLE）的单元测试。AC-021-05 与 AC-035-05 需要 QA/Review 派发，归 M2-T16。

需求依据（REQ-021，`contracts/requirements.json`）：行为 1 只有重要事件集合唤醒 Commander（need_decision、critical/high issue、no_progress、预算风险、角色失效、规格变更、milestone_ready、release_request），balanced 另在轮次边界唤醒；行为 2 token 增量、工具输出、心跳、medium/low issue、常规 candidate_ready 不唤醒（candidate_ready 由 Runtime 交给 QA 与 Review）；行为 3 按 (run_id, problem_fingerprint, spec_revision) 聚合，安静 2 s 触发，自第一个事件起最多 10 s，不同键分别触发；行为 4 IntegrityViolation 跳过去抖，在同一调度 tick 唤醒；行为 5 持久化 last_handled_seq，Commander 只收到它之后的摘要与证据引用，超出预算按严重性与因果链取舍，但保留 spec_sha256 与 candidate_id；行为 6 decision 带 expected_revision 与 role_epoch，任一过期不 apply，REJECTED，按当前状态重新触发；行为 7 每个触发器与决策可查询（去重键、event_seqs、首个事件时间、唤醒时间、决策时间、单调时钟的延迟、决策状态）；行为 8 reserve_supervisor_slot=true 时写者、读者槽满不延误唤醒；Commander 不可用时已授权的低风险动作照常，新的重大决策使 Run 进入 BLOCKED。决定 1 至 5 见需求。

起点（main b90aa0c）：表 `supervisor_triggers`、`supervisor_cursor` 与租约种类 `supervisor` 在 001_initial.sql 中已存在（基线锁定），产品代码不用它们；`decide` 按 Run 的 revision 核对 expected_revision（ADR-011）；产品没有 Commander 的执行路径，Agent 的输出也没有进入 HCP 的桥（docs/06 第 29 行）；`need_decision`、`team.binding_blocked`、`team.binding_refused` 是今天仅有的重要事件来源。预研：`.hoh-dev/evidence/m2t08-prep/README.md`（事实已按 main b90aa0c 核对后写入本 ADR）。

ADR-024 留给本任务的义务：Commander 的第一个 turn 以保存的首个输入开头（决定 4，M2T17R-54）；Commander 的在途 turn 让 ADR-022 决定 8 的在途查询看得到（决定 5）；HCP 投递循环不在首个输入交付之前向新持有者投递（M2T17R-153）；consume 对重用 id 的 Commander 消息给 KeyReuse，投递循环届时把它结算为拒绝（M2T17R-254）；“稍后再派”的原因（M2T17R-352）。


## 决定（第十二版）

第一至第四版各经两个独立会话的设计审查（第 1 至 4 轮：M2T08D-01 至 -16、-50 至 -67、-100 至 -112、-150 至 -167、-200 至 -208、-250 至 -269、-300 至 -309、-350 至 -363；均 FAIL，high 依次 14、15、7、7）。第 11 轮（第十一版的修正复审）：Codex PASS（M2T08D-1000，medium），Claude PASS（-1054，medium；-1050 至 -1053、-1055 至 -1057，low），设计收敛；第十二版逐条改正（重新触发按事件种类识别；失败按当前 Commander epoch 计，试探选已封顶的唤醒；合并并入任何不在途的同键唤醒；抢占在写 woken 的事务里决定；不会饿死的论证补全；工作目录首次创建时记下），并记下 S3 的实施（`Change::Unblock`）。第 10 轮（第十版的修正复审）：Codex M2T08D-900（high，S2 代码：上限截断后提前触发，已在 `966feac` 修正）、-901，Claude -950（high）、-951 至 -955；第十一版：失败按唤醒计、同键待执行的唤醒合并、抢占按边沿、上界只写可证的性质、目录不依赖 TMPDIR、重新触发链的键在未知 revision 下也固定（`-954` 的代码修正）。第 9 轮（第九版的修正复审）：Codex M2T08D-800（high）、-801、-802，Claude -850（high，与 -800 同）、-851 至 -855；第十版让抢占与分配次序成为同一条规则：抢占记录指名接手的 integrity 唤醒，目标停下后槽先给它，一个非 integrity 唤醒至多被抢占一次，等待上界按唤醒如实写。第 8 轮（第八版的修正复审）：Codex M2T08D-700（high）、-701，Claude -750（high）、-751 至 -755；第九版：一个 turn 只处理一个唤醒（不再合批），退避移到分配准入，等待上界如实改写，Commander 写写者工作区的余项交所有者确认。第 7 轮（第七版的修正复审）：Codex M2T08D-600、-601，Claude -650（high，与 -601 同）、-651 至 -655；两个 high 都由第七版自己的修正引入，第八版去掉跨 Run 抢占、撤回信封预检。第 6 轮：Codex M2T08D-500（high）、Claude -550 至 -558（PASS，medium 与 low），第七版逐条改正。第五版是一次设计更正（第 5 轮：Codex M2T08D-400 至 -402、Claude -450 至 -460，各只剩 1 个 high，第六版逐条改正，见各条括号）。第五版是一次设计更正：“被拒的回答自动重新触发并以上限、转交真人防循环”这一类问题已连续出现四次（-106、-157、-267、-350，-302、-351 同类），不再打补丁，回到需求原文：只有过期的决策重新触发（REQ-021 行为 6），其他被拒或无效的回答只进历史（REQ-035），去掉上限与转交；pace 的阻塞声明按停滞整体重算（恢复 ADR-020 决定 5 的语义）。保留的方向：纯函数核心、持久触发器与摄入游标、提交时刻计时、触发与执行分开、唤醒是 Commander 职位的一个 Attempt、Run revision 的 CAS 加 Task 快照栅栏（CR-015 已撤回）、阻塞原因的声明。括号里是它回应的发现。

1. **纯函数核心 `hoh_core::supervise`。** `classify(policy, kind, payload, 当前 spec revision)`；`Pending`/`due_at`：最后一个事件后 2 s，自第一个事件起最多 10 s，integrity 立即到期。唤醒种类是 REQ-021 行为 1 的封闭集合（-262）：`need_decision`、`issue.opened`（critical/high）、`integrity_violation`、`no_progress`、`budget.risk`、`team.binding_blocked`（角色失效）、`spec.changed`、`milestone_ready`、`release_request`，以及决定 6 的 `supervisor.retrigger`（REQ-021 行为 6 的“重新触发”：只为 expected_revision 与 role_epoch 过期的决策）；策略的轮次边界：balanced 加 `iteration.completed`，intensive 再加 `task.implemented`（risk_reduction ≥ 4）。其余都不唤醒（`team.binding_refused`、交接、首个输入的付清只进入下一次唤醒的摘要，决定 7）。相对 `a862760` 的改动：binding_refused 不再唤醒；加 `supervisor.retrigger`；spec revision 在项目里没有行时指纹加 `@r<revision>`。2 s 与 10 s 是常量（docs/07 §3 的“可调”需 REQ-018 的 CR，本任务不加）。产生方：`task.implemented` 由本任务在 Attempt 结为 SETTLED 的共用完成规则里写（决定 3）；`issue.opened` M2-T18；`integrity_violation` M2-T16、M2-T10；`iteration.completed` M2-T16；`no_progress`、`milestone_ready`、`release_request` 与用户输入交给 Commander 属 M3-T04；`spec.changed` M3-T02；`budget.risk`：REQ-042 没有定义“预算风险”，没有实现它的任务；这是规格缺口，唯一负责方是 PROGRESS 后续项“budget.risk 细化 CR 与实现”（主开发会话，M2-T11 开始之前完成，-264a、-360b、-458）。

2. **触发器、游标与时间。**
   - **提交时刻（-202、-301、-357）。** 写入器在每个请求的事务 `COMMIT` 成功之后、回复调用者之前读 store 的时钟，把“之前的 seq、最后的 seq、该时刻”登记进索引：写入器的回复改为在登记之后发出（每个请求的处理先算出结果，再登记，再回复），所以每条写事件的路径——包括 reconcile 的 apply——都由结构保证，不依赖各处调用钩子。索引保留最近 100 000 个事务（按数量有界）。store 的时钟是 host 的单调时钟（`MonotonicClock`：启动时锚定系统时间、按启动以来的单调时间推进，ADR-020 决定 4），所以同一 host 生命周期内的窗口与延迟按单调时钟计，系统时钟的跳变不影响（-457）；查不到提交时刻的事件按摄入时刻计，`latency_basis: "across_restart"`（否则 `"commit"`）。测试让 COMMIT 本身耗时（在 COMMIT 与回复之间推进时钟），断言用的是 COMMIT 之后的时刻。
   - **游标与上限。** “已摄入”游标；摄入后、触发前崩溃的触发器是持久的 PENDING 行（失败模式 3 的读法）。一步按批摄入，每批至多 10 000 个事件、一个事务，游标推进到该批看过的最大 seq；一步一直摄入到追上此刻已提交的全部事件，才判定并触发到期的触发器，所以不会只凭已提交事件的前一部分就触发（同键的后续事件被拆开、上限之后的 integrity 被漏掉，-263c、-900）。取舍（-1051）：追赶的全部批次在一个写者作业里做完，ADR-021 决定 8a 的优先通道（取消、暂停）只在作业之间排空，所以一个历史很长、游标为 0 的 Run 的第一步会推迟它们（每批 10 000 个事件）；平时一步只摄入上一步之后提交的事件。S7 量出每批的耗时并记下积压的预期上限；若它威胁 AC-043-02 的时限，再把批次拆成各自的写者作业。毫秒 UTC 定宽时刻。键：`specs(project_id, revision)` 解析 `spec_id`，没有行时 `spec_id` NULL 且指纹加 `@r<revision>`；`dedup_key = {run_id, fingerprint, spec_id, spec_revision}`。
   - **重新触发的键（-205、-263b、-459）。** `supervisor.retrigger` 带原唤醒的基础指纹（去掉任何 `#retrigger` 后缀）与它所关注的全部 task_id；键固定为“基础指纹#retrigger”，链再长也不增长；重新触发按事件种类识别（`classify` 对 `supervisor.retrigger` 给出标记），不按指纹的后缀：producer 给的、恰好以 `#retrigger` 结尾的普通指纹在未知 revision 下照常加 `@r<revision>`，不同 revision 不合并（-1000、-1052）；同键的普通事件不并入；按普通去抖到期（REQ-021 行为 3；Commander 写错信封的退避不在触发上，而在分配上，决定 6，-700、-752）。重新触发的唤醒在分配时照常记下这些 Task 的快照（决定 3，-754），所以 TEST-021-04 的“摘要中 revision=8”是 Task 的 revision，不靠 Run 的 revision 恰好相同。
   - **每条 `supervisor.*` 事件都带触发器记录**：trigger_id、dedup_key、event_seqs、first_event_at、latency_basis 与此刻的 latency_ms（-161）。

3. **触发与执行；唤醒是 Commander 职位的一个 Attempt。**
   - **触发。** 到期即触发：触发器置 HANDLED，写 `supervisor.woken`（触发器记录与唤醒 id）；同一去重键已有不在途的待执行唤醒（尚未分配，或最近一次分配已重新武装）时，新触发的这一批事件并入那个唤醒（`supervisor.woken` 记 `merged_into`），不另起一个唤醒；合并后唤醒的严重度取两者的最大值，合并使它成为 integrity 时，这次合并就是它的 integrity 边沿（下文的抢占在这个事务里判定）。所以同一问题持续出现时至多占在途的一个 turn 加之后的一个（-951、-1053）；不看 supervisor 槽、不看 Commander 是否 active。只受 Run 状态（下表）与“Commander 不可用”（决定 5）限制。
   - **决策义务（-203、-250）。** 一个 Run 未完成的决策义务 = 需要决策的 PENDING 触发器 ∪ 待执行的唤醒（已 woken、尚未分配，或最近一次分配已结束且非 SETTLED）。待执行由事件定义：`supervisor.woken`、`supervisor.allocated{wake, generation}`、`supervisor.rearmed`、`supervisor.superseded`；重启后从事件重建。
   - **分配与代次（-201、-253、-265）。** 每一步，当 Run 准入、该 Run 没有在途的监督 Attempt、supervisor 槽空闲（`reserve_supervisor_slot=true`；false 时取一个空闲读者槽）、Commander active（`decide::load_binding(run, commander).active`）且预算准入时，把该 Run 的一个待执行唤醒交给一个 Commander turn（一个 turn 只处理一个唤醒，-750：一个 turn 只能有一条决策 APPLIED，决定 6；合批会让同批其他唤醒随 SETTLED 一起结清而无人回答），按下面的次序选；其余的留到下一个 turn：监督 Task 与 Attempt 的 id 由这个唤醒与本 Run 的分配代次派生（`<唤醒>/turn/<n>`，n 为该 Run 已有的 `supervisor.allocated` 数），不会与之前已 CANCELLED 的监督 Task 冲突；写 runtime 派发通知与 `supervisor.allocated{wake, generation, attempt_id, snapshots, nonce}`（`wake` 恰好一个，-852）。分配时重查准入。分配、监督 Task/Attempt 的迁移与槽都不 Touch(Run)。
   - **Task 快照在分配时记下（-260）。** `snapshots` 是这个唤醒所关注的全部 Task（触发器各事件的 task_id，合并了不同 Task 的触发器记下每一个，-558）此刻的 revision，连同本 turn 给出的 Run revision 与 Commander epoch，正是摘要里给 Commander 看的值；决定 6 的栅栏用它。
   - **integrity 抢占（-105、-156、-268、-305、-352、-358、-401、-600、-651、-800、-850）。** 只抢占本 Run 自己在途的非 integrity 监督 Attempt，且只在它的唤醒从未被抢占过时（一个非 integrity 唤醒至多被抢占一次；被抢占过的唤醒之后的 turn 受保护，跑完为止，-800）：integrity 唤醒在它被触发（woken）的那一步（边沿：之后它仍待执行也不再触发抢占，所以受保护的 turn 跑完之后次序的选择不会被它推翻，-953）、它的 Run 在目标停下之后能分配（准入、Commander 可用、预算准入、`retry_not_before` 已过；active 按“目标已不在途”判断，所以新持有者的首个 turn 也能被抢占）时，在写这个 `supervisor.woken`（或使它成为 integrity 的合并）的同一个事务里写 `supervisor.preempt{target_attempt, wake}`，`wake` 指名接手的 integrity 唤醒；两者不分开提交，所以崩溃不会让一个唤醒过了边沿却没有抢占（-1056，S7 有这个崩溃点的测试）。目标停下之后 supervisor 槽的下一次分配先给这个被指名的唤醒（它仍可分配时；它的 Run 被暂停、取消或不能分配时，按下面的次序照常分配，-850），被抢占的唤醒回到待执行、排在它之后，所以抢占不会白做，也不会活锁。不跨 Run 抢占。integrity 不抢占 integrity，也不抢占受保护的 turn：这时 integrity 唤醒等它跑完（至多一个 turn 时限加停止链），再按次序优先。host 的 runner 对有 preempt 的目标：PREPARED 时在 store 里像暂停那样撤回（CANCELLED、释放槽、确认派发通知）；STARTING/RUNNING 时以原因 `preempted` 直接走 settle（abort、原生取消、宽限、SIGTERM/SIGKILL、终止证明），不等租约到期；不用 `cancel_requested`。被抢占的结束重新武装，原因 preempted，不计失败。新持有者首个 turn 被抢占时首个输入仍欠着，下一个 turn 按首输入屏障分配并带交接包。
   - **supervisor 槽的分配次序（-460、-500、-550、-600、-651、-701、-751、-801、-851）。** 槽空闲时，若有指名接手的抢占（上条）先给它；否则按三级次序选出一个唤醒，不等待任何特定的 Run：(1) 已等待超过一个 turn 时限（15 min）的唤醒，按等待时长；(2) integrity 唤醒，按唤醒时刻；(3) 其他唤醒，按唤醒时刻。同一级之内跨 Run 轮转（刚分配过的 Run 排在其他有待执行唤醒的 Run 之后）。等待时长从唤醒第一次被触发（woken）算起，被抢占或重新武装不重置（-952c）。不写固定的等待上界（第 9、10 轮的两个公式都被反例推翻，-801、-851、-901、-952）：同级轮转会让别的 Run 更晚老化的唤醒排到前面；排在前面的每个唤醒可以占多个 turn：被抢占的那次、接手的 integrity、受保护的重跑，以及至多 `MAX_RETRIES` 个失败的 turn（之后它的 Run 不可用，决定 5）；已封顶的 Run 每个冷却期还有一次半开试探；准入、Commander active、预算与 `retry_not_before` 也会推迟分配。可证的性质是：不会饿死——唤醒 W 的 Run 保持准入、Commander active 时，W 至多等 15 min 进入第 1 级，第 1 级按首次触发的时刻排、只会被有限个更早的唤醒与同级轮转插入，而每类插入都有限（每个唤醒至多被抢占一次、每个 integrity 至多抢占一次、每个唤醒至多 `MAX_RETRIES` 次失败）或每个冷却期至多一次，所以 W 在有限次分配之后得到一个不会被抢占的 turn（不保证它 SETTLED，-1055）；S4 的有界次数测试包括失败与试探。一个不断产生 integrity 事件的 Run 不能让别的 Run 一直分配不到，也不能抢占别的 Run 的 turn。`reserve_supervisor_slot=false` 时取读者槽，次序相同；读者槽被工作占满时写 `supervisor.deferred{reason: NO_SLOT}`。
   - **turn 的时限（-04、-268）。** 监督 Attempt 在途超过 `SUPERVISION_TURN = 15 min`：runner 以原因 `turn_limit` 直接走 settle（PREPARED 的按撤回）；结束后重新武装，原因 failure（计失败）。
   - **准入（按 Run 状态）。** 工作态、BLOCKED、WAITING_EXTERNAL：触发并可分配。PAUSE_REQUESTED、PAUSED、INCOMPLETE：不触发、不分配，义务保留；已 PREPARED 的唤醒由暂停撤回（监督 Task 置 CANCELLED），回到待执行，不计失败。CANCEL_REQUESTED 与终态：PENDING 触发器与待执行的唤醒置 SUPERSEDED。
   - **runner 与 BLOCKED（-200、-251、-308、-361、-452）。** 派发按来源分两类（-555）：Runtime 规则类正面列出——监督唤醒、已排的重试（`next_retry_at` 非空）、candidate_ready 之后的 QA/Review 验证派发（M2-T16 实现时标为此类，CR-003）；其余一切派发（调度轮的首次派发、返工或撤回后回到 READY 的再派发、Commander 的 dispatch）都是决策类。runtime 派发通知带 `origin` 标记，runner 据此放行。Run 进入 BLOCKED 的那个事务里，像暂停那样撤回它的决策类 PREPARED 派发（不计次）；BLOCKED 与 WAITING_EXTERNAL 下 runner 的待派发查询、`received` 事务与派发枚举只放行 Runtime 规则类；host 的 tick 对 BLOCKED 的 Run 也调用 pace 与调度轮。
   - **“暂不活跃”（-158、-257、-309）。** Commander 可用但不 active 时待执行的唤醒等待，写一次 `supervisor.deferred{reason}`。“变更待生效”与“首个输入在途”是在等一个活着的 turn（受 turn 时限约束），不计时；“无会话”“session.start 未交付”连续超过 `DEFER_LIMIT = 30 min`（大于 turn 时限与 TTL 之和）按决定 5 视为不可用。
   - **生命周期计数与停滞判定（-450）。** 两个计数（-554）：含监督 Attempt 的在途计数用于预算停止与各在途查询；只计工作 Attempt 的计数用于停滞判定与 RUNNING→WAITING_EXTERNAL 的判定。停滞判定（pace 的“没有任何 Task 能推进”，决定 5 的 `pace` 声明）只看工作 Task 与工作 Attempt：监督 Attempt 不算“能推进”，也不阻止停滞；它只在预算停止时被等待（工作分支、WAITING_EXTERNAL 分支与 BLOCKED 分支都等 `unfinished == 0` 再 INCOMPLETE，-102、-152、-256），并计入暂停、`resume_reconcile`、取消、启动 reconcile、团队 checkpoint 的在途查询。**不变量：** 监督的触发、分配、监督 Task/Attempt 的迁移、重新武装与 supervisor 槽都不改变 Run 的状态或 revision；所以一个 Commander turn 的开始与结束不会让 Run 在 BLOCKED 与工作态之间来回，也不会让它自己的决策过期（测试：停滞的 Run 上一个监督 turn 前后 Run 的 state 与 revision 不变）。唯一的例外是半开试探成功时释放声明（决定 5）：Run 因此回到 resume_state，试探 turn 的决策按构造过期，按决定 6 重新触发，在下一个 turn 里回答（多一个 turn，不丢东西，-553）。
   - **Commander turn 的工作目录（-551、-652）。** 监督 Attempt 的工作目录在项目之外：host 为每个 Commander 会话用一个只由项目摘要与会话 id 决定、不依赖 TMPDIR 的路径（用户级状态目录：`$XDG_STATE_HOME/hoh/commander/<project 摘要>/<session>`，未设时 `~/.local/state/...`，-955），会话第一次用它时把绝对路径记进 `commander.workdir{session_id, path}` 事件，之后的 turn 用记下的路径（环境变量在 shell 与 unit 之间不同也不移动它，-1057），每个 turn 之前确保它存在（host 重启后同一会话得到同一路径，Claude 的 `--resume` 续接照常，-855）；测试把 `XDG_STATE_HOME` 与 `HOME` 指到临时目录，不写用户真实的状态目录；会话结束时删除，所以从工作目录向上找不到项目的 git 仓库或 cargo 清单，也不会加载项目的 AGENTS.md/CLAUDE.md；提示里给它需要读的路径（只读）。Commander 按规格的权限档（yolo-vm：Codex 为 approvalPolicy=never、sandbox=danger-full-access，docs/02）运行，仍能按绝对路径写写者的工作区；写者工作区由 Developer 并发修改，事后的 tree 核对无法归属差异（-753）。这是 CONTRACT 第 7 条单写者在 Commander 上的余项，只靠提示约束；把 Commander 改为只读沙箱会改变规格的权限档，须项目所有者决定（已列为待所有者确认的余项，不阻塞本任务的实施）。Codex 0.166.0 在该标志下不检查 trusted directory，所以项目之外的工作目录不影响默认的 Codex Commander（-755）；S6 为三种 Agent 各写一个在私有目录里启动 Commander turn 的适配器测试（非 live）。
   - **完成的共用规则（-207、-261）。** Attempt 结为 SETTLED 的每条路径（runner 的结束、settle、启动 reconcile 判为完成）在同一事务里调用同一个完成规则：工作 Task 写 `task.implemented{task_id, risk_reduction}`；监督 Task 置 IMPLEMENTED 并停在那里。
   - **其他结局与重新武装（-12、-13、-54、-261b、-304）。** 监督 Attempt 以 FAILED、CANCELLED、UNKNOWN_EFFECT 结束，或被 reconcile 判为结束或结果未知，或被抢占、撤回：监督 Task 置 CANCELLED（不走 `fail_task`；`request_repair` 拒绝监督 Task）；监督器写 `supervisor.rearmed{attempt_id, generation, reason, failures, retry_not_before}`（id 由 Attempt 派生；reason 为 failure、preempted、withdrawn），该唤醒回到待执行。待执行的定义：没有分配，或最近一次分配有它的 `supervisor.rearmed`。`failures` 按唤醒计：当前 Commander epoch 下该唤醒连续的 reason=failure 次数（`supervisor.rearmed` 记 `role_epoch`，之前 epoch 的失败不计，所以换绑之后不写事件也从 0 开始，-1054a）；reason 为 preempted、withdrawn 的重新武装既不计数也不打断连续（-1054c）；只有这个唤醒自己的 turn SETTLED 才归零；同一 Run 别的唤醒的成功不清它的计数（-950：按 Run 计时，一个次次失败的唤醒会因别的唤醒成功而被无限重试，永远到不了不可用）；`retry_not_before` 按 ADR-020 的退避，分配时遵守。SETTLED 的 turn 不重新武装（它的输出按决定 8 处置；无效的输出只进历史，决定 6）。

4. **没有 spec 的 Run。** 不能有监督 Task，也不能有有效决策：到期的触发器保持 PENDING，每个写一次 `supervisor.deferred{reason: NO_SPEC}`；先于决定 5。

5. **阻塞原因的声明、Commander 不可用与 BLOCKED 下的运作（-01、-51、-103、-151、-154、-155、-203、-204、-208、-250、-251、-252、-255、-256、-257）。**
   - **阻塞声明（-208、-252、-353、-360a、-360d）。** Run 级阻塞原因改为“声明”：`run.blocker_claimed{reason, source}` 与 `run.blocker_released{reason, source}`（事件，同一事务里更新 `runs.blocked_reasons_json` 与 `blocked_reason`），阻塞集合是尚未释放的声明的原因之并集。来源：`pace`（停滞判定：没有任何 Task 能推进时，pace 声明从被阻塞的 Task 派生的原因，NEED_DECISION、BLOCKED_CAPABILITY、BLOCKED_AUTH；pace 每步按停滞整体重算，有 Task 能推进时释放它的全部声明，恢复 ADR-020 决定 5“一个角色缺员不阻塞其他还能推进的角色”）、`budget`（BUDGET_UNENFORCEABLE，pace 在预算可执行时释放）、`supervisor`（COMMANDER_UNAVAILABLE 与不可用时为需要真人的义务加的 NEED_DECISION）、`commander:<decision_id>`（request_user_decision，决定 8，由 M2-T13 的 AnswerQuestion 释放）。每个来源只释放自己的声明；集合空了 Run 回到 resume_state。旧行（只有 `blocked_reasons_json`、没有声明事件，M2-T19 写的）在 pace 第一次看到时把其中的原因记为 `pace` 与 `budget` 的声明（事件带 `migrated: true`）。Run 离开 BLOCKED 只经写入器的 `Change::Unblock(to)`：同一条 UPDATE 清空集合、迁回 resume_state（BLOCKED 行必须有 blocked_reason，CHECK 不允许先清集合再迁移），写入器在本提交的事件写入之后核对该 Run 的声明已全部释放，否则整个提交 ILLEGAL_TRANSITION；集合变化而状态不变时 Touch(Run)（S3 实施，`persistence/blockers.rs`）。
   - **何为不可用（-360c）：** commander 绑定 BLOCKED；或注册表在其最近一次观察里报告其 Agent 不可用或缺登录；或该 Run 任一待执行唤醒的 `failures` 达到 `MAX_RETRIES`（8）；或一个监督 Attempt 以 Auth 或 Capability 类失败；或“暂不活跃”超过上界。每次判为不可用写 `supervisor.unavailable{reason, observation}`。没有 commander 绑定的 Run（只出现在测试夹具里；产品的 StartRun 为每个职位绑定）不受监督：不触发、不阻塞。
   - **阻塞（-203、-250）：** Commander 不可用而 Run 有需要决策的未完成义务（决定 3 的定义，不论触发器是否已触发）时，声明 COMMANDER_UNAVAILABLE（来源 supervisor），义务里有 need_decision 时另声明 NEED_DECISION（来源 supervisor）；写 `supervisor.blocked{触发器记录}`；常规触发器在不可用期间 SUPERSEDED。所以“启动即失败”的 Commander（AC-035-05）在失败封顶或 Auth 失败之后，即使义务已是待执行的唤醒，Run 也进入 BLOCKED。
   - **离开（-204、-257、-306、-355）：** 按原因匹配的恢复事实：绑定回到 ACTIVE；注册表的观察身份 `(host_epoch, n)`（host 每次实际观察——探测或登录检查——n 加一；缓存未变不算观察）按字典序在 `supervisor.unavailable` 记下的观察之后且报告可用、已登录（新 host 的任何实际观察都在旧 host 的之后）；Commander 换了 epoch（之前 epoch 的失败不计，决定 3）；“暂不活跃”的原因消失。`failures` 封顶或 Auth/Capability 失败的不可用另有半开试探：距不可用记录超过 ADR-020 的最大退避后允许一次试探分配（`supervisor.probe{observation, wake}` 持久，每个冷却期一次），试探分给该 Run 已封顶的唤醒中最老的那个（没有封顶的唤醒时按决定 3 的次序，-1054b）；试探成功后若仍有封顶的唤醒，下一个立即可试探（Commander 刚证明可用，不再等冷却期），一次失败重新开始冷却；supervisor 的声明只在没有封顶的唤醒时释放；试探在 BLOCKED 的 Run 上进行，不先离开 BLOCKED；成功（SETTLED）时先释放 supervisor 的声明（Run 若因此离开 BLOCKED 便回到 resume_state），再处置该 turn 的输出，所以试探 turn 的回答在 Run 恢复之后才判定，不因 BLOCKED 被拒（-454）；失败再封顶。
   - **BLOCKED 下的运作（-151、-251、-255、-256、-300、-303、-354、-363）。** CR-003：BLOCKED 只停 Commander 决策类派发。pace 在 BLOCKED 的 Run 上运行：排重试、判断预算（停止时等 `unfinished == 0`）、按停滞重算 `pace` 的声明；不把 BLOCKED 迁为 WAITING_EXTERNAL。调度轮在 BLOCKED 的 Run 上只派发已排的重试：`fail_task` 写下的 `next_retry_at` 非空且已到期的 READY Task；`next_retry_at` 在派发时不清空（撤回、租约过期的 PREPARED 回到 READY 时重试身份仍在），由完成的共用规则（Attempt SETTLED）清空，所以成功过的 Task 经返工或 QA 失败回到 READY 不会被当作重试。ResumeRun 时阻塞声明不为空：Run 回到 BLOCKED（保留 resume_state），不再被拒（今天 ResumeRun 只试工作态，写入器因集合非空而拒）。这四处改变 M2-T19（ADR-020 决定 5、7）的行为：ADR-020 加更正注记，附录列出受影响的测试（TEST-042-03 的完成条件、TEST-042-06 的前提：pace 的停止判定仍用 `budget::stop`）。
   - **Task 级 BLOCKED(NEED_DECISION) 的解除**（request_user_decision、AnswerQuestion）属 M2-T13。

6. **决策（-06、-101、-106、-107、-153、-157、-254、-259、-260、-267、-269）。**
   - **expected_revision 是 Run 的 revision**（ADR-011、AC-035-01/02），加 **Task 快照栅栏**：回答某个唤醒（causation_id 是该唤醒）的决策，若该唤醒在分配时记下的 Task 的 revision 已变，拒为 STALE_REVISION。AC-021-04 按原文成立：Run 与 Task 都从 7 开始，Runtime 的推进是一次调度轮的租约（两者同到 8；fixture 不启动被租出 Task 的 Attempt，否则 Task 会到 9，-269）；第一条决策 STALE_REVISION，提交那一刻 outbox 增量为 0（重新触发要等去抖）；恰好一个新触发器，摘要里 Task revision 为 8；第二条 APPLIED。另有测试覆盖 runner 只推进 Task 的情形。
   - **入口：** 只经 `decide`（带 causation_id）。桥接输出的 decision_id 由 Attempt 与 Message 的 message_id 派生（`<attempt>/<message_id>`），不同 turn、不同 Run 里重用同一 message_id 不冲突（-259）；同一 decision_id 内容相同为重放，不同为 KeyReuse；`decide` 不再因主键冲突给 IntegrityViolation。`decision.applied`/`decision.rejected` 带 `causation_id` 与 `decided_at`。AC-035-02 的“原样再提交”是新的 decision id。
   - **非工作态（-101、-153、-254）：** BLOCKED 与 WAITING_EXTERNAL 下只判定 `transition_task` 与 `record_assumption`；`dispatch` 与 `transition_run` 拒为 ILLEGAL_TRANSITION（ADR-011 §3.4：Run 的迁移 from 须在 W，WAITING_EXTERNAL、BLOCKED 及其恢复属用户命令与 Runtime 事实）。PAUSE_REQUESTED、PAUSED、INCOMPLETE 期间输出不处置，留到 Run 回到可处置的状态；CANCEL_REQUESTED 与终态时输出置 superseded。
   - **只有过期的决策重新触发（REQ-021 行为 6；-106、-157、-267、-302、-350、-351 的设计更正；-451）。** 决策照常经 decide（不在桥上预检信封；-601、-650）：回答某个唤醒的决策因 STALE_REVISION 或 STALE_ROLE_EPOCH 被拒（含 Task 快照栅栏给出的 STALE_REVISION，任一快照 Task 变化即过期；也包括 Commander 自己写了比分配时更旧的值，如 AC-035-01 的第 3 例），decisions 行为 REJECTED，在 decide 的同一事务里写 `supervisor.retrigger{decision_id, reason, 基础指纹, task_ids, 原触发器记录, own_mistake, n}`（task_ids 是原唤醒的全部快照 Task，重新触发的唤醒照此记快照，-654），每条过期决策恰好一条，没有上限、没有转交（需求要求每次都重新触发）。重新触发的触发器按普通去抖到期（REQ-021 行为 3）。信封里的值不等于分配时给出的 Run revision 与 Commander epoch（Commander 自己写错，`own_mistake`）时，退避加在分配上，不加在触发上：该重新触发的唤醒的 `retry_not_before` = 它被触发（woken）的时刻 + 退避（n 为该 Run 连续 own_mistake 的次数，2 s 起加倍、至多 300 s；n 持久在 `supervisor.retrigger` 里，该 Run 有任一决策 APPLIED 时归零，归零只影响之后的退避，不缩短已记下的）；两条重新触发并入同一个触发器时取较晚的 `retry_not_before`（-552、-700、-752、-853）。重新触发一条不少、按时触发，一条写错信封的重新触发链每 5 min 至多再付一个 turn，直到 Commander 改正或预算停止；新的普通唤醒照常各付一个 turn。一个 turn 里的多条决策：每条 APPLIED 都推进 Run 的 revision（ADR-011、AC-035-02），所以同一 turn 里信封相同的后续决策按构造过期并重新触发（状态变化，普通去抖），在下一个 turn 里以新的 revision 回答；commander.md 要求一个 turn 只给一条决策；决定 3 一个 turn 只处理一个唤醒，与此一致（-750）。SPEC_MISMATCH 不在其内（REQ-021 行为 6 只说 expected_revision 与 role_epoch；Task 级的 SPEC_MISMATCH 与状态无关，重新触发只会再被拒）。其他原因的拒绝与无效的输出只进历史（REQ-035：记为 REJECTED 历史），不自动重新唤醒：问题本身由已有机制承载（Task 的阻塞、Run 的停滞声明、下一次唤醒的摘要里列出该 Run 最近被拒与无效的回答）。M2T17R-352（首个输入未付清时派发被拒）不需要 Commander 再派：付清之后调度轮照常派发 READY 的 Task。

7. **Commander 的输入（-05、-110、-262）。** 职位契约在前；首个输入欠着时交接包紧随其后（分配要求 active）；然后本 turn 那一个唤醒的摘要（带唤醒 id 与分配时的 Task 快照；同一 Run 其他待执行的唤醒只列出它们的 id 与种类，供 Commander 知道之后还有什么，不在本 turn 回答，-852）。摘要确定、有界：按 integrity、critical、high，再按因果链，再按最新；永不丢 spec_sha256、candidate_id、Run 与快照的 revision；包含各职位绑定的状态（含 `first_input_pending`、被拒的修改）。某职位要“稍后再派”（M2T17R-352）不需要 Commander 再派：首个输入付清之后调度轮照常派发 READY 的 Task（决定 6）。

8. **Commander 的输出（-07、-100、-109、-150、-206、-258、-259、-263a、-266）。** M2-T08 负责 decision 的闭环；steer、query、handoff 的路由与投递属 M2-T16。
   - **文件桥与 nonce（-266、-307、-359）。** 分配时为本 turn 生成随机 nonce：明文放进本 turn 的 runtime 派发通知（重启后同一 Attempt 重新投递时执行器从通知取得同一个 nonce，-455），`supervisor.allocated` 只记它的 sha256；Commander 把每条 HCP Message 包成 `{"nonce": …, "message": …}` 逐行写到 `.hoh/attempts/<attempt>/messages.jsonl`；产品执行器在 turn 结束时读它放进 `Outcome.messages`（FakeExecutor 直接给出）；nonce 不符的行判为 invalid。nonce 防的是误投与串线，不是秘密：同 uid 的其他 Agent 能读提示所在的目录，信任边界仍是 CR-013 的同 uid 余项。`resources/prompts/commander.md` 在 S6 改写（中文优先）：只用 kind=decision 与 DecisionPayload，不提交 TaskResult，需要真人时用 request_user_decision，文件的位置、格式与 nonce。
   - **只登记成功 turn 的输出（-100、-258）。** runner 把工作效果记为 OBSERVED 且结果为成功的那个事务里，把每条输出写成 `supervisor.output`（id 由 Attempt 与行号派生）；失败 turn 的输出不登记（写 `supervisor.output_discarded` 诊断），它的唤醒按失败重新武装；reconcile 据成功的 OBSERVED/COMMITTED 判为完成时输出已在库里。
   - **每条输出恰好一个终态，谓词与边界写清（-109、-150、-206、-263a、-362、-400、-456）。** 输出的终态是二者之一：一条带它 `output_id` 的 `decision.applied`/`decision.rejected`（它经 decide 处置的第一次），或一条 `supervisor.output_disposed{output_id, outcome}`（其余一切处置）；待处置 = 有 `supervisor.output`、两者都没有的输出。监督步骤逐条处置，每条一个事务：kind 不是 decision → `output_disposed{deferred}`；nonce、run、sender_role、causation 不符或格式不对 → `output_disposed{invalid, reason}`（只进历史，决定 6）；decision → 在同一事务里执行 decide 的事务体（`decide` 拆成可在调用方事务里执行的函数），decisions 行、它的效果与带 `output_id` 的 decision 事件一起提交（AC-035-02 的“events+1”不变）；同一 decision_id 再出现（同一 turn 两行相同的 Message，或重启后重做）：内容相同为重放，写 `output_disposed{replay, decision_id}`，不再执行；内容不同为 `output_disposed{invalid, KEY_REUSE}`。`request_user_decision`（decide 今天给 Unsupported）→ 同一事务里写 `output_disposed{unsupported, decision_id, payload_sha256}` 并声明 NEED_DECISION（来源 `commander:<decision_id>`）；同 id 再出现同样按重放或 KEY_REUSE。`create_tasks` → `output_disposed{unsupported}`（M3 的规划路径）。一条输出的处置以数据库以外的原因失败时写 `supervisor.output_failed{output_id, n}`（持久计数），第 3 次以 `output_disposed{invalid, INTERNAL}` 终结；处置失败按 Run 隔离并记诊断，不中止该 tick 的其他工作。

9. **配置。** `supervision.policy` 在 StartRun 时冻结进 Run 的快照（缺省 balanced）；`execution.reserve_supervisor_slot` 见决定 3；`execution.writer_slots` 已校验为 1；`delivery.max_delivery_attempts` 在投递循环接入前没有消费者（M2-T16）：ADR-022 第 71 行在本任务里改正（-263d）。

10. **义务的承接与移交（-166、-264）。** 承接：TEST-019-02 改为断言假 pi 实际收到的输入（ADR-024 决定 4，M2T17R-54）；TEST-043-04 在有 Commander 路径后重新核对（暂停与取消不唤醒 Commander，FakeCommander 计数为 0）。移交 M2-T16（投递循环）：当前 epoch 的 steer/query 的路由、M2T17R-153、M2T17R-254、M2T17R-154（哪些 Commander 消息还要核对接收方的 epoch）；移交 M2-T13：M2T03R-156（计划导入路由把计划错误映射为 4xx）；AC-002-01（M2-T13）要求 `hoh -p` 新建的 Run 在规格阶段由 Commander 提出 requires_user 的请求，而没有 spec 的 Run 不能有监督 Task（`tasks.spec_id` 非空，决定 4）：这条规格阶段的 Commander 路径归 M2-T13，可能需要 CR（-356）；`budget.risk` 见决定 1 的唯一负责方。合并时在 PROGRESS 的后续项里逐条记下（-557）：事件产生方 `issue.opened`（M2-T18）、`integrity_violation`（M2-T16、M2-T10）、`iteration.completed`（M2-T16；在它之前 balanced 的轮次边界唤醒在产品里不会发生）、`no_progress`/`milestone_ready`/`release_request` 与用户输入交给 Commander（M3-T04）、`spec.changed`（M3-T02）、`budget.risk`（细化 CR 与实现）；QA/Review 验证派发的 `origin` 标记（M2-T16）；AnswerQuestion 释放来源为 `commander:<decision_id>` 的声明并解除 Task 级 BLOCKED(NEED_DECISION)（M2-T13，-655）；以上各项在对应任务的审查里核对，未满足即算该任务的缺口。Commander 能按绝对路径写写者工作区这一余项（决定 3）写进 reports/reviews/M2.md 本任务的审查表，并向项目所有者提问是否接受（-802、-854）。ADR-011 §3 与 ADR-021 决定 7 加更正注记（决定 6、8 的 decision_id 与 Unsupported 处置；决定 3、5 的 BLOCKED 准入与 ResumeRun，-556）。

## 附录：监督 Task 与监督 Attempt 在各处的处理（代码普查，main b90aa0c；设计审查补全）

标记：`role='commander'`。Commander 不执行工作 Task（CONTRACT 6、docs/06），计划导入拒绝 role 为 commander 的 Task 与依赖一个监督 Task 的 Task，以后的 create_tasks 决策同样适用（不缩小范围，不需要 CR，-66）。

从“工作进度”排除（监督 Task）：

- `retry::pace` 的 Task 扫描：排除监督 Task，所以它不进 `in_flight`、`due`、`remaining`、`blocked_reasons` 与能力检查；在途 Attempt 分两个计数（决定 3）：含监督 Attempt 的用于预算停止，只计工作 Attempt 的用于停滞判定与 RUNNING→WAITING_EXTERNAL。
- `retry::fail_task`、reconcile 的 Ended：监督 Task 置 CANCELLED，不 READY，不计次，不写 need_decision；`retry::request_repair` 拒绝监督 Task。
- 调度轮 `rounds::candidates`：只取 READY/PENDING，监督 Task 从不处于这两个状态；测试断言。
- 计划导入（plan.rs、dag.rs）：见上。
- Commander 决策（decide.rs、decision.rs）：以监督 Task 为对象的派发与迁移被拒。
- TaskResult（results.rs）：role 为 commander 的结果被拒（尚未接入 host，规则先写上）。
- 墙钟预算：Commander turn 的时长照常计入 Run 的 `wall_seconds`；预算准入见决定 3。

照常包含（监督 Attempt）：

- runner：`runner::waiting` 的待派发查询、`received` 事务与工作 Run 的枚举按决定 3 的两类准入（BLOCKED、WAITING_EXTERNAL 下只放行 Runtime 规则类：监督唤醒、已排的重试、QA/Review 验证派发）；超过 `SUPERVISION_TURN` 或有 `supervisor.preempt` 时以原因 `turn_limit`/`preempted` 直接走 settle（PREPARED 的按撤回）。
