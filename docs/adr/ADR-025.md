# ADR-025 · Commander 监督：触发器、去抖、唤醒与 Commander 不可用

状态：采纳待设计审查（M2-T08；先审设计，再写 S2 以后的代码）

## 背景

M2-T08 的验收是 REQ-021 的 AC-021-01 至 -04（TEST-021-01、-02 属检查 `unit`，-03 属 `recovery`，-04 属 `integration`），done_when 另要求：Commander 不可用时 Run 进入 BLOCKED（COMMANDER_UNAVAILABLE）的单元测试。AC-021-05 与 AC-035-05 需要 QA/Review 派发，归 M2-T16。

需求依据（REQ-021，`contracts/requirements.json`）：行为 1 只有重要事件集合唤醒 Commander（need_decision、critical/high issue、no_progress、预算风险、角色失效、规格变更、milestone_ready、release_request），balanced 另在轮次边界唤醒；行为 2 token 增量、工具输出、心跳、medium/low issue、常规 candidate_ready 不唤醒（candidate_ready 由 Runtime 交给 QA 与 Review）；行为 3 按 (run_id, problem_fingerprint, spec_revision) 聚合，安静 2 s 触发，自第一个事件起最多 10 s，不同键分别触发；行为 4 IntegrityViolation 跳过去抖，在同一调度 tick 唤醒；行为 5 持久化 last_handled_seq，Commander 只收到它之后的摘要与证据引用，超出预算按严重性与因果链取舍，但保留 spec_sha256 与 candidate_id；行为 6 decision 带 expected_revision 与 role_epoch，任一过期不 apply，REJECTED，按当前状态重新触发；行为 7 每个触发器与决策可查询（去重键、event_seqs、首个事件时间、唤醒时间、决策时间、单调时钟的延迟、决策状态）；行为 8 reserve_supervisor_slot=true 时写者、读者槽满不延误唤醒；Commander 不可用时已授权的低风险动作照常，新的重大决策使 Run 进入 BLOCKED。决定 1 至 5 见需求。

起点（main b90aa0c）：表 `supervisor_triggers`、`supervisor_cursor` 与租约种类 `supervisor` 在 001_initial.sql 中已存在（基线锁定），产品代码不用它们；`decide` 按 Run 的 revision 核对 expected_revision（ADR-011）；产品没有 Commander 的执行路径，Agent 的输出也没有进入 HCP 的桥（docs/06 第 29 行）；`need_decision`、`team.binding_blocked`、`team.binding_refused` 是今天仅有的重要事件来源。预研：`.hoh-dev/evidence/m2t08-prep/README.md`（事实已按 main b90aa0c 核对后写入本 ADR）。

ADR-024 留给本任务的义务：Commander 的第一个 turn 以保存的首个输入开头（决定 4，M2T17R-54）；Commander 的在途 turn 让 ADR-022 决定 8 的在途查询看得到（决定 5）；HCP 投递循环不在首个输入交付之前向新持有者投递（M2T17R-153）；consume 对重用 id 的 Commander 消息给 KeyReuse，投递循环届时把它结算为拒绝（M2T17R-254）；“稍后再派”的原因（M2T17R-352）。

## 决定

1. **纯函数核心 `hoh_core::supervise`。** `classify(policy, kind, payload, 当前 spec revision)` 给出唤醒与否、键与严重性；`Pending` 与 `due_at` 给出去抖：最后一个事件后 2 s（`QUIET`），自第一个事件起最多 10 s（`CAP`），严重性 integrity 立即到期。重要事件的 kind（REQ-021 决定 4 的初始值）：`need_decision`、`issue.opened`（payload.severity 为 critical 或 high）、`integrity_violation`、`no_progress`、`budget.risk`、`team.binding_blocked`、`team.binding_refused`（角色失效）、`spec.changed`、`milestone_ready`、`release_request`；balanced 另加 `iteration.completed`（轮次边界，M2-T16 之前没有来源）；intensive 再加 risk_reduction ≥ 4 的 `task.implemented`。其余一律忽略。键：事件的 `fingerprint` 与 `spec_revision`，没有时用 kind/主体（task_id、issue_id、attempt_id、role、candidate_id 中第一个有的）与 Run 当前的 spec revision。严重性对应表的 `severity` 列（integrity、critical、high、normal）。2 s 与 10 s 是常量（没有配置键；加键属 REQ-018 的 CR）。

2. **触发器与游标（store，一个事务一步）。** `Store::supervise(run, Context)`：读 `supervisor_cursor` 之后该 Run 的事件（按 seq），逐个分类；唤醒的事件按键加入该键 PENDING 的触发器（唯一索引保证每键至多一个），没有就新建；游标推进到本次扫描到的最大 seq（包括被忽略的事件），所以一万条 token 事件只花一次游标更新、不写任何行。游标是“已摄入”游标（D2）：游标以下的每个事件要么在某个触发器里，要么被判为不唤醒。时间取 host 的时钟（`Context.now/wall`，测试用 FakeClock）：触发器的 `created_at` 是首个事件被摄入的时间，`due_at` 每次加入时按决定 1 重算。事件自己的 `created_at` 是写入器的墙钟，不用于去抖。延迟（行为 7）以摄入时间计；跨重启摄入的触发器记 `latency_basis: across_restart` 与 UTC 区间，不算单调差。

3. **唤醒是 Commander 职位的一个 Attempt。** 到期的触发器在一个事务里：置 HANDLED；写一个监督 Task（id 由触发器派生，role `commander`，writer 0，spec 取 Run 的 spec，直接 LEASED）与它的 PREPARED Attempt（Commander 绑定此刻的 epoch、会话、Agent），持有 `supervisor` 租约（`execution.reserve_supervisor_slot=true` 的实现；false 时改用一个读者槽）；写一条 runtime 派发通知与 `supervisor.woken` 事件（dedup_key、event_seqs、first_event_at、woken_at、wake_latency_ms）。runner 照常把这个 Attempt 交给执行器。于是 ADR-022 决定 8 的在途查询、取消、租约到期、启动 reconcile 与 UNKNOWN_EFFECT 都覆盖 Commander 的 turn（ADR-024 决定 5），不需要另写。监督 Task 不是工作。标记：`role='commander'`；Commander 不执行工作 Task，所以计划导入拒绝 role 为 commander 的 Task，Commander 的决策与 TaskResult 也不能以监督 Task 为对象（今天的 plan schema 允许任何 role 字符串，产品与测试都没有 commander 的工作 Task；这条拒绝是本 ADR 加的规则）。凡是把一个 Run 的 Task 或 Attempt 一并读取或计数的地方，逐处决定是否排除（附录，由设计审查核对）。监督 Task 的结局：Attempt SETTLED 时 runner 照常把 Task 记为 IMPLEMENTED，停在那里（处处被排除）；Attempt 没有完成（FAILED、CANCELLED，或启动 reconcile 判为结束）时 Task 直接置 CANCELLED，不走重试策略（`fail_task` 不碰监督 Task，所以它永远不会 READY，调度轮也就永远看不到它）；UNKNOWN_EFFECT 时 Task 留在原处（被排除）。没有完成时监督器重新武装：把那次唤醒的 event_seqs 并回该键 PENDING 的触发器（没有就新建），到期时间按重试退避；同一键连续失败到 `MAX_RETRIES` 视为 Commander 不可用（决定 5）。Commander 有在途的唤醒时，到期的触发器不再唤醒，继续吸收事件（每键至多一个未处理的触发器）。一个项目只有一个 supervisor 槽：同一项目不同 Run 的 Commander turn 轮流（v1 可接受，说明在此）。

4. **没有 spec 的 Run。** `tasks.spec_id` 非空，HCP Message 的 spec_sha256 必填：没有 spec 的 Run 不能有唤醒 Task，也不能有有效的决策。这样的 Run 到期的触发器保持 PENDING，写一条 `supervisor.deferred{reason: NO_SPEC}`（每个触发器一次）；这样的 Run 没有 Task，也就没有 need_decision（与 ADR-024 决定 10 一致）。

5. **Commander 不可用（D5、D6）。** 不可用：Run 的 commander 绑定不是 ACTIVE（BLOCKED，或注册表报告其 Agent 不可用或缺登录）；或唤醒的 Attempt 以 Auth 或 Capability 类失败；或同一触发器的唤醒连续失败达到 `MAX_RETRIES`。尚未绑定会话不算不可用（“还没有”）；卡住的 turn 由租约到期处理（REQ-041，120 s），不另设超时。“新的重大决策”= 一个到期的触发器：Run 以 `block_run` 进入 BLOCKED，原因 COMMANDER_UNAVAILABLE，触发器里有 need_decision 时另加 NEED_DECISION；触发器保持 PENDING，不写 decisions 行，不唤醒。CR-003：BLOCKED 只停 Commander 决策类派发，Runtime 的自动规则（candidate_ready→QA/Review、已排的重试、pause/cancel）照常。离开：监督器每步在唤醒之前判断，Commander 重新可用时移除 COMMANDER_UNAVAILABLE（同一事务），由 Run 的阻塞集合规则回到 resume_state；监督器加的 NEED_DECISION 在回答该触发器的决策 APPLIED 后移除。Task 级 BLOCKED(NEED_DECISION) 的解除（request_user_decision 与 AnswerQuestion）属 M2-T13，记在此处。

6. **决策与唤醒相连（D7）、过期决策重新触发（行为 6）。** Commander 的 decision Message 以 `causation_id` = 唤醒 id；`Proposal` 从信封带上它；`decide` 把它写进 `decision.applied`/`decision.rejected` 的 payload（不加列）。回答某个唤醒的决策因 STALE_REVISION、SPEC_MISMATCH 或 STALE_ROLE_EPOCH 被拒时，监督器在自己的事务里为它重新触发一次（事件 id 由决策 id 派生，所以每个决策至多一次），新触发器的摘要按当前状态；`decide` 本身仍只写一条事件。expected_revision 的含义不变：Run 的 revision（ADR-011；D1）。TEST-021-04 里 Run 与 Task 都从 7 开始，Runtime 的推进在一次提交里移动 Task 并 Touch Run，所以 then 子句都按字面成立。同一 id 的决策再来一次返回它第一次的结果（ADR-018 第 128 行），不重复执行。过期 epoch 的 steer/query（`commander_message`）不重新触发。

7. **Commander 的输入（D9、D11）。** 产品执行器为监督 Task 的 turn 组装：职位契约（第 1 层）在前；会话的首个输入还欠着时（ADR-024 决定 4），交接包紧随其后；然后是唤醒摘要。摘要是确定的、有界的：按 integrity、critical、high 排序，再按因果链，再按最新；永不丢 spec_sha256、candidate_id 与各 revision；它是一个由 Rust 类型核对的 runtime 通知 JSON（不加协议 `$defs`，不需要 CR）。上下文装箱属 M2-T09（REQ-039）。

8. **Commander 的输出进入 HCP（D12）。** 没有这条桥，产品里的 Commander turn 不起作用。执行器的 `Outcome` 加 `messages`：测试的 FakeExecutor 直接给出；产品从文件桥读：Commander 按它的提示把 HCP Message 逐行写到 `.hoh/attempts/<attempt>/messages.jsonl`，runner 在 turn 结束、结算之后把每条交给 `consume`（ADR-018 决定 2），decision 经 `decide`。消息必须以本 Attempt 的 run、Commander 的 epoch 与 causation 为准，不符合的拒绝并记事件。（若设计审查认为这属于别的任务，则延后并在此写明 owner；不能静默删掉。）

9. **配置（D10、D13）。** `supervision.policy` 在 StartRun 时冻结进 Run 的快照（缺省 balanced；docs/07）；`execution.reserve_supervisor_slot` 由决定 3 实现；`execution.writer_slots` 已校验为 1，无需接线；`delivery.max_delivery_attempts` 在投递循环接入前没有消费者（M2-T16），更正 ADR-022 第 71 行，不接死代码。

10. **当前 epoch 的 steer/query 的路由（D15）、M2T17R-153、-254。** REQ-021 不需要；交给咨询路由（docs/06 第 29 行），owner 写在此处：投递循环（M2-T16）。

## 附录：监督 Task 的排除清单（代码普查，main b90aa0c）

改变决定的地方：

- `retry::pace`（retry.rs 的 Task 扫描、`in_flight`、`unfinished`、`remaining`、`blocked_reasons`、`due`、能力检查）：Task 扫描与在途 Attempt 计数排除监督 Task。否则 IMPLEMENTED 的监督 Task 永远算在途，Run 不能进入 WAITING_EXTERNAL、BLOCKED、INCOMPLETE；在途的唤醒也会拖住 INCOMPLETE。
- `retry::fail_task`（runner 的结束与 reconcile 调用）：监督 Task 不进重试策略，置 CANCELLED（不计 attempt_count，不写 need_decision）；重新武装由监督器做。
- reconcile 的处置（`reconcile::dispose` 与 persistence/reconcile.rs 的 apply）：Ended 时监督 Task 置 CANCELLED 而不是 READY；Completed 照常 IMPLEMENTED；UnknownEffect 留在原处。
- 调度轮 `rounds::candidates`：只取 READY/PENDING，监督 Task 从不处于这两个状态（上两条保证），无需改动；测试断言这一点。
- 暂停 `control::pause_step`：撤回 PREPARED 的唤醒时监督 Task 置 CANCELLED（不是 READY）；暂停不等在途的 Commander turn（在途计数排除），它此后的决策因 Run 不在工作状态被拒。
- 取消：CancelRun 设 `cancel_requested`、`running_attempts` 驱动的取消 pass、`finish_cancel`、`resume_reconcile` 都照常包含监督 Attempt：取消一个 Run 也停掉它的 Commander turn（它们是这个 Run 的进程；host/control.rs 模块头“Neither touches the Commander”改为“取消不唤醒、不等待 Commander 的决策”）。AC-043-04（Commander 失效时暂停、取消照常，Commander 从不被调用）仍成立：暂停与取消不产生唤醒。

只影响计数或展示的地方：

- 墙钟预算：Commander turn 的时长照常计入 Run 的 `wall_seconds`（它是这个 Run 的 Agent 时间）；迭代与 usd 本来不由 Attempt 累加。
- `run_cost`：未计价的唤醒照常使成本未知（与其他 Attempt 一致）。
- 计划导入（plan.rs、dag.rs）：拒绝 role 为 commander 的 Task，拒绝依赖一个监督 Task。
- Commander 的决策（decide.rs、decision.rs）：以监督 Task 为对象的派发、迁移被拒（ILLEGAL_TRANSITION 类的拒绝原因）。
- TaskResult（results.rs）：role 为 commander 的结果被拒（还没有接入 host，规则先写上）。
- 团队 checkpoint 的在途查询：包含监督 Attempt，正是 ADR-024 决定 5 要的。
- 交接：监督 Attempt SETTLED 清掉首个输入的欠账（它的 turn 以交接包开头，决定 7）；交接包里未确认的 outbox 包括唤醒的派发通知。
- 用户可见：getRun、listRuns 只读 runs；team 页只读绑定；没有 listTasks 端点；`/v1/events` 里能看到唤醒 Attempt 与 Task 的事件（如实）。

租约：`free_slot` 只给 writer 与 reader-k；监督器直接 `grant` 种类 `supervisor`，不经 `lease_task`；一个项目一个 supervisor 槽。监督 Attempt 不持写租约，被中断结束时不需要工作区记录（ADR-024 决定 9）。
