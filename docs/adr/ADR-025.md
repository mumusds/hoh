# ADR-025 · Commander 监督：触发器、去抖、唤醒与 Commander 不可用

状态：采纳（第三版，设计审查第 2 轮之后；M2-T08）

## 背景

M2-T08 的验收是 REQ-021 的 AC-021-01 至 -04（TEST-021-01、-02 属检查 `unit`，-03 属 `recovery`，-04 属 `integration`），done_when 另要求：Commander 不可用时 Run 进入 BLOCKED（COMMANDER_UNAVAILABLE）的单元测试。AC-021-05 与 AC-035-05 需要 QA/Review 派发，归 M2-T16。

需求依据（REQ-021，`contracts/requirements.json`）：行为 1 只有重要事件集合唤醒 Commander（need_decision、critical/high issue、no_progress、预算风险、角色失效、规格变更、milestone_ready、release_request），balanced 另在轮次边界唤醒；行为 2 token 增量、工具输出、心跳、medium/low issue、常规 candidate_ready 不唤醒（candidate_ready 由 Runtime 交给 QA 与 Review）；行为 3 按 (run_id, problem_fingerprint, spec_revision) 聚合，安静 2 s 触发，自第一个事件起最多 10 s，不同键分别触发；行为 4 IntegrityViolation 跳过去抖，在同一调度 tick 唤醒；行为 5 持久化 last_handled_seq，Commander 只收到它之后的摘要与证据引用，超出预算按严重性与因果链取舍，但保留 spec_sha256 与 candidate_id；行为 6 decision 带 expected_revision 与 role_epoch，任一过期不 apply，REJECTED，按当前状态重新触发；行为 7 每个触发器与决策可查询（去重键、event_seqs、首个事件时间、唤醒时间、决策时间、单调时钟的延迟、决策状态）；行为 8 reserve_supervisor_slot=true 时写者、读者槽满不延误唤醒；Commander 不可用时已授权的低风险动作照常，新的重大决策使 Run 进入 BLOCKED。决定 1 至 5 见需求。

起点（main b90aa0c）：表 `supervisor_triggers`、`supervisor_cursor` 与租约种类 `supervisor` 在 001_initial.sql 中已存在（基线锁定），产品代码不用它们；`decide` 按 Run 的 revision 核对 expected_revision（ADR-011）；产品没有 Commander 的执行路径，Agent 的输出也没有进入 HCP 的桥（docs/06 第 29 行）；`need_decision`、`team.binding_blocked`、`team.binding_refused` 是今天仅有的重要事件来源。预研：`.hoh-dev/evidence/m2t08-prep/README.md`（事实已按 main b90aa0c 核对后写入本 ADR）。

ADR-024 留给本任务的义务：Commander 的第一个 turn 以保存的首个输入开头（决定 4，M2T17R-54）；Commander 的在途 turn 让 ADR-022 决定 8 的在途查询看得到（决定 5）；HCP 投递循环不在首个输入交付之前向新持有者投递（M2T17R-153）；consume 对重用 id 的 Commander 消息给 KeyReuse，投递循环届时把它结算为拒绝（M2T17R-254）；“稍后再派”的原因（M2T17R-352）。


## 决定（第三版）

第一版（`b412b42`）与第二版（`8cd84f3`）各经两个独立会话的设计审查（第 1 轮 M2T08D-01 至 -16、-50 至 -67；第 2 轮 -100 至 -112、-150 至 -167，均 FAIL）。第三版整体如下；保留的方向：纯函数核心、持久触发器与摄入游标、提交时刻计时、“唤醒是 Commander 职位的一个 Attempt”。括号里是它回应的发现。CR-015 撤回（决定 6）。

1. **纯函数核心 `hoh_core::supervise`。** `classify(policy, kind, payload, 当前 spec revision)` 给出唤醒与否、键与严重性；`Pending`/`due_at`：最后一个事件后 2 s，自第一个事件起最多 10 s，integrity 立即到期。需要决策的种类（REQ-021 决定 4 的初始名）：`need_decision`、`issue.opened`（critical/high）、`integrity_violation`、`no_progress`、`budget.risk`、`team.binding_blocked`（角色失效）、`spec.changed`、`milestone_ready`、`release_request`、`supervisor.retrigger`（决定 6）。常规种类（normal）：`team.binding_refused`、`handoff.first_input_taken`（决定 7）；balanced 另加 `iteration.completed`；intensive 再加 `task.implemented`（risk_reduction ≥ 4）。2 s 与 10 s 是常量（docs/7 §3 的“可调”需要 REQ-018 的 CR，本任务不加）。相对 `a862760` 的改动（第 2 轮 -164）：binding_refused 改为常规；新增 `supervisor.retrigger` 与 `handoff.first_input_taken`；`handoff.delivered` 不再唤醒（-110）；spec revision 在项目里没有行时指纹加 `@r<revision>`。这些改动先写失败测试。种类的产生方：`task.implemented` 由本任务在 runner 的成功结束里写（带 Task 的 `risk_reduction`，-112）；`issue.opened` M2-T18；`integrity_violation` M2-T16、M2-T10；`iteration.completed` M2-T16；`no_progress`、`milestone_ready`、`release_request` 与用户输入交给 Commander M3-T04；`spec.changed` M3-T02；`budget.risk` M2-T15。

2. **触发器、游标与时间。** 写入器在每个请求开始时读 store 的时钟（`Options.clock`，host 传 `HostClock`），为它提交的每个事务记下“之前的 seq、最后的 seq、提交时刻”，保留最近 100 000 个事务（按数量有界，不按游标，-111、-165）。监督步骤按事件的提交时刻计时：首事件与末事件的提交时刻决定 `due_at = min(末 + 2 s, 首 + 10 s)`，integrity 为它的提交时刻；查不到提交时刻的事件（早于本写入器，或超出窗口）按摄入时刻计，`latency_basis: "across_restart"`（否则 `"commit"`）。游标是“已摄入”游标；摄入后、唤醒前崩溃的触发器是持久的 PENDING 行，重启后照常触发（失败模式 3 的读法）。一步至多摄入 10 000 个事件。时刻是固定宽度的毫秒 UTC。键：spec revision 按 `specs(project_id, revision)` 解析为 `spec_id`，没有行时 `spec_id` 为 NULL 且指纹加 `@r<revision>`；`dedup_key = {run_id, fingerprint, spec_id, spec_revision}`。
   **每条 `supervisor.*` 事件都带触发器记录**（-161）：trigger_id、dedup_key、event_seqs、first_event_at、latency_basis 与此刻的 `latency_ms`；所以 Commander 不可用时从不唤醒的触发器（AC-021-05）也能在 GetEvents 里读到。

3. **触发与执行分开；唤醒是 Commander 职位的一个 Attempt（-104、-105、-108、-156）。**
   - **触发。** 到期的触发器在到期的那一步触发：置 HANDLED，写 `supervisor.woken`（触发器记录与唤醒 id，唤醒 id 由触发器派生）。触发不看 supervisor 槽、不看 Commander 是否 active，所以自首事件起 10 s 的上界与 integrity 的“同一步”对触发总成立（行为 3、4）。触发只受 Run 状态限制（下表）与 Commander 不可用（决定 5）。
   - **待执行的唤醒**是持久的：有 `supervisor.woken`、还没有唤醒 Task 的唤醒。重启后监督步骤从事件重建它们（-108）。
   - **分配。** 每一步，当 supervisor 槽空闲（`execution.reserve_supervisor_slot=true`；false 时取一个空闲读者槽）、Run 准入、Commander active（`decide::load_binding(run, commander).active`）且预算准入（`retry::budget_stop`）时，把该 Run 全部待执行的唤醒交给**一个** Commander turn：一个监督 Task（id 由最早的唤醒派生，role commander，writer 0，Run 的 spec，直接 LEASED）与它的 PREPARED Attempt，持有槽；一条 runtime 派发通知；`supervisor.allocated{wakes, attempt_id}`。integrity 的唤醒排在前面。分配时重查准入（暂停、取消、不可用）。唤醒、分配、监督 Task/Attempt 的迁移与槽都不 Touch(Run)。
   - **integrity 抢占。** integrity 唤醒在 supervisor 槽被一个非 integrity 的监督 Attempt 占着时，同一步写 `supervisor.preempt{target_attempt}`（持久意图）。host 的 runner 每个 tick 对“有 preempt、目标仍在途”的 Attempt：经执行器发原生取消；超过原生宽限仍在途则不再给它续租，租约到期后走现有 settle（终止证明）。不使用 `cancel_requested`（它只服务 CancelRun，租约到期的 settle 会跳过它，-156）。抢占不要求 Commander active（-105）：新持有者首个 turn 在途时同样抢占；被抢占的 turn 没有完成，首个输入仍欠着，下一个 turn（integrity 的）按首输入屏障分配并带交接包。被抢占的结束按决定 3 末段重新武装，不计失败。
   - **准入（按 Run 状态）。** 工作态与 BLOCKED、WAITING_EXTERNAL：触发并可分配；runner 的待派发查询、接收事务与工作 Run 的枚举只为 `role='commander'` 的监督通知放行 BLOCKED 与 WAITING_EXTERNAL。PAUSE_REQUESTED、PAUSED、INCOMPLETE（-162）：不触发，触发器保持 PENDING；已 PREPARED 的唤醒由暂停撤回（监督 Task 置 CANCELLED），其唤醒回到待执行，不计失败。CANCEL_REQUESTED 与终态：PENDING 触发器与待执行的唤醒置 SUPERSEDED（`supervisor.superseded`）。
   - **“暂不活跃”有上界（-158）。** Commander 可用但不 active（变更待生效、无会话、首个输入未交付或在途）时待执行的唤醒等待，写一次 `supervisor.deferred{reason}`；同一原因连续超过 `DEFER_LIMIT = 10 min`（或 Commander 的 `handoff.undelivered` 达到 3 次）则按决定 5 视为不可用。
   - **turn 的时限（-04）。** 监督 Attempt 在途超过 `SUPERVISION_TURN = 15 min` 时 runner 不再续租，租约到期后（至多再 120 s）走 settle；结束后按失败重新武装。实际结束可能晚于 15 min（剩余 TTL 与停止链的时间），文字不承诺严格 15 min。
   - **生命周期计数。** 监督 Attempt 计入 pace 的在途 Attempt（`unfinished`）——**工作分支与 WAITING_EXTERNAL 分支都看它**：预算停止时有在途的监督 Attempt 则等它结束再 INCOMPLETE（-102、-152）；计入暂停的在途计数、`resume_reconcile`、取消、启动 reconcile、团队 checkpoint 的在途查询（ADR-024 决定 5）。监督 Task 只从“工作进度”的集合排除（附录）。
   - **结局与重新武装（-12、-13、-54、-163）。** SETTLED：Task IMPLEMENTED 并停在那里（被排除），它的输出按决定 8 处置；没有决策回答也算处理完。其他结束（FAILED、CANCELLED、UNKNOWN_EFFECT、reconcile 判为结束、被抢占）：Task 置 CANCELLED（不走 `fail_task`；`request_repair` 拒绝监督 Task）；监督器从持久事实重新武装：找出“已分配、Attempt 已结束且非 SETTLED、还没有 `supervisor.rearmed`”的唤醒，把它们回到待执行（不新建触发器，所以没有 id 冲突，-163），写 `supervisor.rearmed{attempt_id, failures, retry_not_before}`（id 由 Attempt 派生）。`failures` 是该 Run 连续的、可归因于 Commander 的失败次数（暂停撤回、抢占、准入挡下不算），SETTLED 的 turn 归零；`retry_not_before` 按 ADR-020 的退避，分配时遵守。

4. **没有 spec 的 Run。** 不能有监督 Task，也不能有有效决策：到期的触发器保持 PENDING，每个触发器写一次 `supervisor.deferred{reason: NO_SPEC}`；先于决定 5（不因 Commander 不可用而 BLOCKED；这样的 Run 没有 Task，也就没有 need_decision）。

5. **Commander 不可用（-01、-51、-59、-103、-151、-155）。**
   - **何为不可用：** commander 绑定 BLOCKED；或注册表报告其 Agent 不可用或缺登录；或 Run 的 `failures` 达到 `MAX_RETRIES`（8）；或一个监督 Attempt 以 Auth 或 Capability 类失败；或“暂不活跃”超过上界（决定 3）。
   - **只有需要决策的触发器阻塞：** 不可用时到期的这类触发器：Run 以 `block_run` 进入 BLOCKED，加 COMMANDER_UNAVAILABLE，触发器里有 need_decision 时另加 NEED_DECISION；`supervisor.blocked{added, 触发器记录}` 记下监督器自己加的原因；触发器保持 PENDING，不写 decisions 行。常规触发器在不可用期间置 SUPERSEDED。
   - **离开（半开试探）：** 不可用的原因消失时监督器在触发之前、同一事务里移除 COMMANDER_UNAVAILABLE 与它自己加的 NEED_DECISION。原因消失的判定：绑定回到 ACTIVE；注册表在不可用记录之后看过该 Agent 且报告可用、已登录；Commander 换了 epoch（`failures` 清零）；`failures` 封顶时，距上次失败超过 ADR-020 的最大退避就允许一次试探分配，成功（SETTLED）清零，失败再封顶。所以短暂故障之后 Run 能恢复，不会永久 BLOCKED，也不会每步反复（试探有间隔）。
   - **BLOCKED 下已排的重试（-151）：** ADR-020 决定 5 让 Run 级阻塞只在没有等待中的重试时发生，COMMANDER_UNAVAILABLE 是第一个会与已排重试并存的 Run 级阻塞。CR-003（BLOCKED 只停 Commander 决策类派发）要求已排的重试照常，所以本任务让调度轮在 BLOCKED 的 Run 上只派发重试（`attempt_count > 0`、重试已到期的 READY Task），pace 在 BLOCKED 的 Run 上照常排重试与判断预算；首次派发的工作 Task 在 BLOCKED 下不派。
   - **Run 级派生原因的移除（-154）：** ADR-011 与 ADR-020 决定 5 把它交给 M2-T08/M2-T15：本任务让 pace 在没有任何 Task 仍带某原因时移除它从 Task 派生的 Run 级原因（NEED_DECISION、BLOCKED_CAPABILITY），集合空了 Run 回到 resume_state。Task 级 BLOCKED(NEED_DECISION) 的解除（request_user_decision、AnswerQuestion）属 M2-T13。

6. **决策（-06、-08、-101、-106、-107、-153、-157、-160）。**
   - **expected_revision 是 Run 的 revision**（ADR-011、AC-035-01/02），不变。**另加唤醒的 Task 快照栅栏**：唤醒记下它所关注的 Task（触发器事件的 task_id）及其此刻的 revision；回答该唤醒（causation_id 为该唤醒）的决策，若这些 Task 的 revision 已变，拒为 STALE_REVISION。所以 runner 只推进 Task（不 Touch Run）的情形也会过期（比原来更严，-107）。AC-021-04 按原文成立（Run 与 Task 都从 7 开始；Runtime 的推进是一次调度轮的租约，两者同到 8；第一条决策 STALE_REVISION、无派发；恰好一个新触发器，摘要里 Task revision 为 8；第二条 APPLIED），另有一个测试覆盖 runner 只推进 Task 的情形。**CR-015 撤回**：不需要改 AC-021-04（-160 的两项通过标准按原文保留）。
   - **入口：** Commander 的 decision 只经 `decide`（带 causation_id），不经 `consume`。`decide` 对同一 decision_id：内容相同返回第一次的结果（重放），不同为 KeyReuse；不再给 IntegrityViolation。`decision.applied`/`decision.rejected` 带 `causation_id` 与 host 时钟的 `decided_at`。AC-035-02 的“原样再提交”是新的 decision id（现有测试即如此），不受重放影响（-167）。
   - **非工作态（-101、-153）：** BLOCKED 与 WAITING_EXTERNAL 下 `validate` 只拒 `dispatch`（CR-003：决策类派发；原因 ILLEGAL_TRANSITION 照旧），`transition_task`、`transition_run`、`record_assumption` 照常判定。PAUSE_REQUESTED、PAUSED、INCOMPLETE 期间输出不裁决，留到 Run 回到可裁决的状态（决定 8），不丢；CANCEL_REQUESTED 与终态时输出置 superseded。
   - **被拒的回答都重新触发（-106、-153、-157）：** 回答某个唤醒的决策被拒（任何原因），写 `supervisor.retrigger{decision_id, reason, 原触发器记录}`，它是需要决策的唤醒事件（决定 1），经游标摄入，键为原触发器的指纹加当前 spec revision；没有次数上限，到期按 ADR-020 的退避逐次拉长（首次 2 s，之后加倍，至多该退避的上限）；摘要带上被拒的原因，Commander 据此改正。所以“恰好一次重新触发”对每个过期决策成立，问题不会因封顶而静默丢失。过期 epoch 的 steer/query 不重新触发。

7. **Commander 的输入（-05、-63、-110）。** 职位契约在前；会话的首个输入还欠着时交接包紧随其后（分配要求 active，保证此时它已交付）；然后是本 turn 的各唤醒摘要（每个唤醒一节，带唤醒 id 供 causation_id 引用）。摘要确定、有界：按 integrity、critical、high，再按因果链，再按最新；永不丢 spec_sha256、candidate_id、Run 与快照 Task 的 revision；包含各职位绑定的状态（含 `first_input_pending`）。某职位新持有者的会话第一次有 Attempt SETTLED（首个输入付清，ADR-024 决定 4）时 runner 写 `handoff.first_input_taken{role, session, epoch}`，它唤醒 Commander（常规），这才是“可以派了”的时刻（-110，M2T17R-352）。runtime 通知 JSON 由 Rust 类型核对，不加协议 `$defs`；上下文装箱属 M2-T09。

8. **Commander 的输出（-07、-57、-100、-109、-150、-159、-167）。** M2-T08 负责 decision 的闭环；steer、query、handoff 的路由与投递属投递循环（M2-T16）。
   - **文件桥：** Commander 按提示把 HCP Message 逐行写到 `.hoh/attempts/<attempt>/messages.jsonl`；产品执行器在 turn 结束时读它放进 `Outcome.messages`（FakeExecutor 直接给出）。`resources/prompts/commander.md` 在 S6 改写（中文优先）：只用 kind=decision 与 DecisionPayload，不提交 TaskResult，需要真人时用 request_user_decision（见下），写文件的位置与格式（-159）。
   - **与成功记录同一事务登记（-100）：** runner 把工作效果记为 OBSERVED 的那个事务（`runner_effect`，成功结果第一次持久化之处）同时把每条消息写成一条 `supervisor.output`（id 由 Attempt 与行号派生，带完整消息）；reconcile 据 OBSERVED/COMMITTED 判为完成时输出已在库里。没有 OBSERVED 就结束的 turn（崩溃、失败）没有输出，按决定 3 重新武装。
   - **每条输出恰好一个处置（-109、-150、-167）：** 待处置 = 有 `supervisor.output`、没有 `supervisor.output_disposed` 的输出。监督步骤按 seq 处置：kind 不是 decision → `deferred`（投递循环，M2-T16）；run、sender_role 或 causation_id 不符、格式不对 → `invalid{reason}`；否则交给 `decide`（每条一个事务，按 id 重放/KeyReuse），结果为 `decided{outcome}`；KeyReuse → `invalid{KEY_REUSE}`；`request_user_decision`（目前 Unsupported）→ `unsupported`，并把需要真人这件事落到 Run：加 NEED_DECISION（来源记为 commander_requested_user，`supervisor.blocked` 记下），由 M2-T13 的 AnswerQuestion 回答；`create_tasks` → `unsupported`（M3 的规划路径）。处置事件与 decide 的结果在同一事务（decide 返回后由监督步骤在下一事务写处置；崩溃在两者之间时，重做时 decide 重放第一次的结果，处置照写，不重复执行）。Run 在暂停中：输出保持待处置；取消或终态：`superseded`。任何一条输出的处置失败只影响它自己，不中止该 tick 的其他工作（监督步骤的错误按 Run 隔离并记诊断）。

9. **配置。** `supervision.policy` 在 StartRun 时冻结进 Run 的快照（缺省 balanced）；`execution.reserve_supervisor_slot` 见决定 3；`execution.writer_slots` 已校验为 1；`delivery.max_delivery_attempts` 在投递循环接入前没有消费者（M2-T16），更正 ADR-022 第 71 行。

10. **交给其他任务的义务（-166）。** 当前 epoch 的 steer/query 的路由、M2T17R-153（投递循环不在首个输入交付前投递）、M2T17R-254（KeyReuse 结算为拒绝）归 M2-T16，记入 PROGRESS 的后续项。本任务承接：TEST-019-02 改为断言假 pi 实际收到的输入（ADR-024 决定 4，M2T17R-54）；TEST-043-04 在有 Commander 路径后重新核对（ADR-021）：暂停与取消不唤醒 Commander，FakeCommander 计数为 0。

## 附录：监督 Task 与监督 Attempt 在各处的处理（代码普查，main b90aa0c；设计审查补全）

标记：`role='commander'`。Commander 不执行工作 Task（CONTRACT 6、docs/06），计划导入拒绝 role 为 commander 的 Task 与依赖一个监督 Task 的 Task，以后的 create_tasks 决策同样适用（不缩小范围，不需要 CR，-66）。

从“工作进度”排除（监督 Task）：

- `retry::pace` 的 Task 扫描：排除监督 Task，所以它不进 `in_flight`、`due`、`remaining`、`blocked_reasons` 与能力检查；pace 的在途 Attempt 计数（`unfinished`）**不**排除监督 Attempt（决定 3）。
- `retry::fail_task`、reconcile 的 Ended：监督 Task 置 CANCELLED，不 READY，不计次，不写 need_decision；`retry::request_repair` 拒绝监督 Task。
- 调度轮 `rounds::candidates`：只取 READY/PENDING，监督 Task 从不处于这两个状态；测试断言。
- 计划导入（plan.rs、dag.rs）：见上。
- Commander 决策（decide.rs、decision.rs）：以监督 Task 为对象的派发与迁移被拒。
- TaskResult（results.rs）：role 为 commander 的结果被拒（尚未接入 host，规则先写上）。
- 墙钟预算：Commander turn 的时长照常计入 Run 的 `wall_seconds`；预算准入见决定 3。

照常包含（监督 Attempt）：

- runner：`runner::waiting` 的待派发查询、`received` 事务与工作 Run 的枚举按决定 3 的准入表放行监督通知（BLOCKED、WAITING_EXTERNAL 也放行，只放行它们）；续租在 `SUPERVISION_TURN` 之后或有 `supervisor.preempt` 且超过原生宽限时停止。
- 调度轮与 pace 在 BLOCKED 的 Run 上：调度轮只派发重试，pace 照常排重试、判断预算并移除不再成立的派生原因（决定 5）；pace 的 WAITING_EXTERNAL 预算分支看在途 Attempt（决定 3）。
- 暂停 `control::pause_step`：在途计数包含监督 Attempt（暂停等它）；撤回 PREPARED 的唤醒时监督 Task 置 CANCELLED（不是 READY），触发器重新武装、不计失败。
- `resume_reconcile`：照常（与暂停一致）。
- 取消：CancelRun 的 `cancel_requested`、取消 pass、`finish_cancel` 照常包含；host/control.rs 模块头改为“取消与暂停不唤醒 Commander，也不等待它的决策”。AC-043-04 仍成立。
- 启动 reconcile：照常处置；结束（非 SETTLED）后由监督器重新武装。
- 团队 checkpoint 的在途查询：包含（ADR-024 决定 5）。
- 交接：监督 Attempt SETTLED 清掉首个输入的欠账（它的 turn 以交接包开头）；交接包里未确认的 outbox 包括唤醒的派发通知。
- 写租约：监督 Attempt 不持写租约，被中断结束时不需要工作区记录（ADR-024 决定 9）。
- 用户可见：getRun、listRuns、team 页不受影响；`/v1/events` 里如实可见唤醒的 Attempt 与 Task 事件。
