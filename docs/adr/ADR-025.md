# ADR-025 · Commander 监督：触发器、去抖、唤醒与 Commander 不可用

状态：采纳（第二版，设计审查第 1 轮之后；M2-T08）

## 背景

M2-T08 的验收是 REQ-021 的 AC-021-01 至 -04（TEST-021-01、-02 属检查 `unit`，-03 属 `recovery`，-04 属 `integration`），done_when 另要求：Commander 不可用时 Run 进入 BLOCKED（COMMANDER_UNAVAILABLE）的单元测试。AC-021-05 与 AC-035-05 需要 QA/Review 派发，归 M2-T16。

需求依据（REQ-021，`contracts/requirements.json`）：行为 1 只有重要事件集合唤醒 Commander（need_decision、critical/high issue、no_progress、预算风险、角色失效、规格变更、milestone_ready、release_request），balanced 另在轮次边界唤醒；行为 2 token 增量、工具输出、心跳、medium/low issue、常规 candidate_ready 不唤醒（candidate_ready 由 Runtime 交给 QA 与 Review）；行为 3 按 (run_id, problem_fingerprint, spec_revision) 聚合，安静 2 s 触发，自第一个事件起最多 10 s，不同键分别触发；行为 4 IntegrityViolation 跳过去抖，在同一调度 tick 唤醒；行为 5 持久化 last_handled_seq，Commander 只收到它之后的摘要与证据引用，超出预算按严重性与因果链取舍，但保留 spec_sha256 与 candidate_id；行为 6 decision 带 expected_revision 与 role_epoch，任一过期不 apply，REJECTED，按当前状态重新触发；行为 7 每个触发器与决策可查询（去重键、event_seqs、首个事件时间、唤醒时间、决策时间、单调时钟的延迟、决策状态）；行为 8 reserve_supervisor_slot=true 时写者、读者槽满不延误唤醒；Commander 不可用时已授权的低风险动作照常，新的重大决策使 Run 进入 BLOCKED。决定 1 至 5 见需求。

起点（main b90aa0c）：表 `supervisor_triggers`、`supervisor_cursor` 与租约种类 `supervisor` 在 001_initial.sql 中已存在（基线锁定），产品代码不用它们；`decide` 按 Run 的 revision 核对 expected_revision（ADR-011）；产品没有 Commander 的执行路径，Agent 的输出也没有进入 HCP 的桥（docs/06 第 29 行）；`need_decision`、`team.binding_blocked`、`team.binding_refused` 是今天仅有的重要事件来源。预研：`.hoh-dev/evidence/m2t08-prep/README.md`（事实已按 main b90aa0c 核对后写入本 ADR）。

ADR-024 留给本任务的义务：Commander 的第一个 turn 以保存的首个输入开头（决定 4，M2T17R-54）；Commander 的在途 turn 让 ADR-022 决定 8 的在途查询看得到（决定 5）；HCP 投递循环不在首个输入交付之前向新持有者投递（M2T17R-153）；consume 对重用 id 的 Commander 消息给 KeyReuse，投递循环届时把它结算为拒绝（M2T17R-254）；“稍后再派”的原因（M2T17R-352）。


## 决定（第二版）

第一版（`b412b42`）经两个独立会话的设计审查（Codex M2T08D-01 至 -16，Claude M2T08D-50 至 -67，均 FAIL）后整体重写如下；保留的方向：纯函数核心、持久触发器与游标、“唤醒是 Commander 职位的一个 Attempt”。各条后括号里是它回应的审查发现。

1. **纯函数核心 `hoh_core::supervise`（未变，`a862760`）。** `classify(policy, kind, payload, 当前 spec revision)` 给出唤醒与否、键与严重性；`Pending`/`due_at` 给出去抖：最后一个事件后 2 s，自第一个事件起最多 10 s，严重性 integrity 立即到期。重要事件（REQ-021 决定 4 的初始名）：`need_decision`、`issue.opened`（severity 为 critical 或 high）、`integrity_violation`、`no_progress`、`budget.risk`、`team.binding_blocked`（角色失效）、`spec.changed`、`milestone_ready`、`release_request`，以及决定 6 的过期决策（`decision.rejected` 带唤醒 causation，原因 STALE_REVISION、SPEC_MISMATCH、STALE_ROLE_EPOCH）；常规（normal）的还有 `team.binding_refused`（被拒的修改，旧绑定照常工作，不算失效，-65b）与 `handoff.delivered`（某职位的新持有者收到了首个输入，-63）；balanced 另加 `iteration.completed`，intensive 再加 risk_reduction ≥ 4 的 `task.implemented`。2 s 与 10 s 是常量：docs/07 §3 说“可调”，加配置键属 REQ-018 的 CR，本任务不加（-65c）。今天没有产生方的种类及其负责方（-64）：`issue.opened` 由 M2-T18（finding→issue），`integrity_violation` 由 M2-T16（验证期间候选被改）与 M2-T10，`iteration.completed` 由 M2-T16，`no_progress`、`milestone_ready`、`release_request` 由 M3-T04，`spec.changed` 由 M3-T02，`budget.risk` 由 M2-T15；在它们出现之前，产品里三种策略只在已有种类上有差别。

2. **触发器、游标与时间（-09、-14、-60、-61、-62）。**
   - **提交时刻。** REQ-021 决定 4 要求延迟从首个事件的提交时刻按单调时钟计。写入器在每个事务提交之后，以 host 的时钟（`Options.clock`，host 传入 `HostClock`；测试传 FakeClock；默认系统时钟）记下“本事务最大 seq → 提交时刻”，存在内存里（本 host 生命周期内的索引，裁掉所有 Run 的游标都已越过的部分）。监督步骤给每个唤醒事件查它的提交时刻；去抖与延迟都按提交时刻：触发器的首事件时刻与末事件时刻是提交时刻，`due_at = min(末 + 2 s, 首 + 10 s)`，integrity 为它自己的提交时刻；摄入晚了不会重新开始窗口，到期已过的在摄入的同一步就触发。本 host 启动之前提交的事件（重启跨越）查不到提交时刻：按摄入时刻计，触发器与 `supervisor.woken` 记 `latency_basis: "across_restart"` 与事件的 UTC `created_at`，不报单调差。
   - **游标。** `supervisor_cursor.last_handled_seq` 是“已摄入”游标：游标以下的每个事件要么在某个触发器里，要么被判为不唤醒。失败模式 3（“seq ≤ last_handled_seq 不再唤醒”）读作：已摄入的事件不会再被摄入；摄入后、唤醒前崩溃的触发器是持久的 PENDING 行，重启后照常触发一次（-62b）。一步摄入至多 10 000 个事件，更多的下一步继续。查询按 `(run_id, kind, seq)` 索引读唤醒种类，最大 seq 另取；以 EXPLAIN 核实不扫全表（-62d，测试里断言查询计划）。
   - **精度与键。** 触发器的 `created_at`、`due_at` 与 `supervisor.*` 事件里的时刻都是固定宽度的毫秒 UTC（`time::rfc3339_millis_utc`/`parse_rfc3339_millis`，`9dcb8d9`），从不与整秒字符串作文本比较。键的 spec revision 按 `specs(project_id, revision)` 解析为 `spec_id`；项目里没有该 revision 的行时 `spec_id` 为 NULL，revision 编进指纹（`<指纹>@r<revision>`），不同 revision 永不合并。`dedup_key` 的格式：`{run_id, fingerprint, spec_id, spec_revision}`。“每键至多一个未处理触发器”指 PENDING（-65d）。

3. **唤醒是 Commander 职位的一个 Attempt，按准入表（-02、-05、-10、-11、-50、-52、-53、-67）。**
   - **形状。** 到期的触发器触发时，在一个事务里：置 HANDLED；写一个监督 Task（id 由触发器派生，role `commander`，writer 0，spec 取 Run 的，直接 LEASED）与它的 PREPARED Attempt（Commander 绑定此刻的 epoch、会话、Agent），持有 `supervisor` 租约（`execution.reserve_supervisor_slot=true`；为 false 时取一个空闲的读者槽，没有就等）；写一条 runtime 派发通知与 `supervisor.woken`（dedup_key、event_seqs、first_event_at、woken_at、wake_latency_ms、latency_basis、attempt_id）。这一切不 Touch(Run)：唤醒、重新触发、监督 Task/Attempt 的迁移与 supervisor 租约都不改 Run 的 revision（-56）。
   - **准入（按 Run 状态）。** 工作态（RUNNING、VERIFYING 等）与 BLOCKED、WAITING_EXTERNAL：触发并唤醒；runner 的待派发查询、接收事务与工作 Run 的枚举放行 `role='commander'` 的监督通知（只放行它们；CR-003：BLOCKED 只停 Commander 决策类派发）。PAUSE_REQUESTED、PAUSED：不触发，触发器保持 PENDING，不计失败；已 PREPARED 的唤醒由暂停撤回（监督 Task 置 CANCELLED），触发器重新武装、不计失败；不对暂停中的 Run 做 `block_run`（-50）。CANCEL_REQUESTED 与终态：PENDING 触发器置 SUPERSEDED（写 `supervisor.superseded`）。
   - **Commander 准入。** 唤醒要求 `decide::load_binding(run, commander)` 为 active（绑定 ACTIVE、有会话、checkpoint 不待生效、本 epoch 的首个输入已交付、首个输入欠着时没有在途 Attempt）。不 active 而 Commander 可用（“暂不活跃”：变更待生效、无会话、首个输入未交付或在途）：触发器保持 PENDING，不计失败，写一次 `supervisor.deferred{reason}`；Commander 不可用见决定 5（-05、-52）。
   - **预算准入。** 唤醒之前按 Run 的预算规则（`retry::budget_stop`：截止时间、迭代、时长、费用）判断；预算不许新工作时不唤醒，触发器保持 PENDING，由 pace 按预算规则结束或阻塞 Run（-11）。
   - **在途与 integrity 抢占。** 一个项目一个 supervisor 槽，同时至多一个监督 Attempt 在途。槽被占时到期的普通触发器保持 PENDING、继续吸收事件。到期的 integrity 触发器在同一步触发（HANDLED、`supervisor.woken`），并对在途的非 integrity 监督 Attempt 发取消（经执行器的原生取消与现有停止链，取消算该唤醒的结束，其触发器重新武装、不计失败）；它的 Attempt 在槽空出的那一步创建（`supervisor.woken` 记 `preempted`）。所以 REQ-021 行为 4 的“同一调度 tick 唤醒”读作：触发与抢占在同一步，Agent 的 turn 在被抢占的 turn 停下后开始（-10、-53）。integrity 不抢占 integrity。
   - **turn 的时限（-04）。** 监督 Attempt 有时限 `SUPERVISION_TURN = 15 min`（常量；改为配置属 REQ-018 的 CR）：runner 对超过时限的监督 Attempt 不再续租，租约到期后走现有的 settle（原生取消、SIGTERM、SIGKILL、终止证明），结束后按失败重新武装。
   - **生命周期计数（-11、-03、-58）。** 监督 Attempt 照常计入：pace 的在途 Attempt（`unfinished`：Commander 在跑时 Run 不结束为 INCOMPLETE）、暂停的在途计数（暂停等 Commander 的 turn 结束，与 REQ-043 行为 1 一致；`resume_reconcile` 因此也一致）、取消（取消一个 Run 也停掉它的 Commander turn）、启动 reconcile、团队 checkpoint 的在途查询（ADR-024 决定 5）。监督 Task 只从“工作进度”的集合里排除（附录）。
   - **结局与重新武装（-12、-13、-54）。** Attempt SETTLED：Task 照常 IMPLEMENTED 并停在那里（被排除）；回答了它的决策按决定 6 处理；没有决策回答也算处理完（Commander 判断无需动作）。Attempt 以其他方式结束（FAILED、CANCELLED、UNKNOWN_EFFECT，或 reconcile 判为结束）：Task 置 CANCELLED（不走 `fail_task`，不计 attempt_count；`request_repair` 拒绝监督 Task，-15）；监督器从持久事实重新武装：每一步找出“`supervisor.woken` 的 Attempt 已结束、非 SETTLED、还没有 `supervisor.rearmed`”的唤醒，把它的 event_seqs 并回该键 PENDING 的触发器（没有就新建），写 `supervisor.rearmed{attempt_id, failures, retry_not_before}`（id 由 Attempt 派生，重做无害）。UNKNOWN_EFFECT 也重新武装：Commander 的 turn 除了决策没有外部效果，决策按 id 幂等、受栅栏保护（-54）。`failures` 是该键连续的、可归因于 Commander 的失败次数（暂停撤回、准入挡下、抢占不算），在 `supervisor.rearmed` 里持久，SETTLED 的唤醒归零；`retry_not_before` 按 ADR-020 的退避，新事件并入时到期时间取 `max(去抖结果, retry_not_before)`。

4. **没有 spec 的 Run（-65a）。** 没有 spec 的 Run 不能有监督 Task（`tasks.spec_id` 非空）也不能有有效决策：到期的触发器保持 PENDING，每个触发器写一次 `supervisor.deferred{reason: NO_SPEC}`；这一条先于决定 5（这样的 Run 不因 Commander 不可用而 BLOCKED；它没有 Task，也就没有 need_decision）。首个规划路径（M3）给 Run 写 spec 之后才有唤醒。

5. **Commander 不可用（-01、-51、-59）。**
   - **何为不可用。** Run 的 commander 绑定为 BLOCKED；或注册表报告它的 Agent 不可用或缺登录（`Availability`）；或某键连续可归因于 Commander 的失败达到 `MAX_RETRIES`（8）；或一个唤醒的 Attempt 以 Auth 或 Capability 类失败。“暂不活跃”（决定 3）不是不可用。
   - **只有需要决策的触发器才阻塞。** 不可用时，到期的触发器若属需要决策的种类（need_decision、critical/high issue、integrity、no_progress、budget.risk、team.binding_blocked、spec.changed、milestone_ready、release_request、过期决策的重新触发）：Run 以 `block_run` 进入 BLOCKED，加 COMMANDER_UNAVAILABLE，触发器里有 need_decision 时另加 NEED_DECISION；写 `supervisor.blocked{added: [...]}` 记下监督器自己加的原因（阻塞集合本身只有字符串，来源记在事件里）；触发器保持 PENDING，不写 decisions 行，不唤醒。常规触发器（策略的检查点、binding_refused、handoff.delivered）在不可用期间置 SUPERSEDED 并写事件，不阻塞（-59）。
   - **离开。** 监督器每一步在触发之前判断：Commander 重新可用时，在同一事务里移除 COMMANDER_UNAVAILABLE 与它自己加的 NEED_DECISION（按 `supervisor.blocked` 的记录；pace 若因 Task 仍需决定而需要 NEED_DECISION，它下一次判断时自会重新加上）；阻塞集合空了就按 Run 的规则回到 resume_state；随后触发器在工作态的 Run 上唤醒，回答它的决策可以 APPLIED。没有循环依赖（-01、-51）。
   - **不变的部分与负责方。** CR-003：BLOCKED 只停 Commander 决策类派发，Runtime 的自动规则（candidate_ready→QA/Review、pause/cancel、持久化）照常。今天的代码里已排的重试也只经调度轮派发，而调度轮只在 RUNNING/VERIFYING 运行：CR-003 所说“已排的重试照常”在 BLOCKED 下并不成立，这是先前就有的差距，归 M2-T15（缺员 BLOCKED 不阻塞其他角色）；第一版对此的断言撤回（-02、-59）。Task 级 BLOCKED(NEED_DECISION) 的解除（request_user_decision、AnswerQuestion）属 M2-T13。

6. **决策（-06、-08、-55、-56、-62c）。**
   - **expected_revision 是 Run 的 revision（ADR-011、AC-035-01/02，D1）。** AC-021-04 的文字以 Task 的 revision 叙述，与 AC-035 不一致：精化 CR-015 把它改为 Run 的 revision 的叙述（CR-003 D1 预授权的一类：修正规格之间的不一致，不删 AC、不放宽检查；经独立审查 PASS 后批准）。runner 对 Task 的推进不 Touch(Run)，所以针对这些推进的决策由 validate 的状态检查判断（例如派发要求 READY），不是由 revision 栅栏；测试里的“Runtime 推进”是一次调度轮的租约（它 Touch Run），CR-015 写明。
   - **入口。** Commander 的 decision 只经 `decide`（ADR-011；带 causation_id）；不经 `consume`（consume 比较 Task 的 revision、写 message.rejected，且回执的外键指向 outbox，两者不能串接，-08、-57）。同一 decision_id 再来一次：内容相同返回第一次的结果（重放），不同则 KeyReuse；`decide` 不再因主键冲突给 IntegrityViolation。`decision.applied`/`decision.rejected` 的 payload 带 `causation_id` 与 host 时钟的 `decided_at`（毫秒）。
   - **过期重新触发。** 回答某个唤醒（causation_id 是一个唤醒）的决策因 STALE_REVISION、SPEC_MISMATCH 或 STALE_ROLE_EPOCH 被拒时，`decision.rejected` 就是一个唤醒事件（决定 1），经游标摄入，键为原触发器的指纹加当前 spec revision；所以“恰好一次重新触发”由持久事件保证，不依赖内存（-55）。同一键连续的过期重新触发至多 3 次，之后写 `supervisor.stale_loop` 诊断并等待新的事件（-55）。AC-021-04 的“无派发”指工作 Task 的派发；重新触发产生的唤醒通知不算（-56）。过期 epoch 的 steer/query（`commander_message`）不重新触发。

7. **Commander 的输入（-05、-63）。** 产品执行器为监督 Task 的 turn 组装：职位契约在前；会话的首个输入还欠着时交接包紧随其后（决定 3 的准入保证此时它已交付）；然后是唤醒摘要。摘要确定、有界：按 integrity、critical、high 排序，再按因果链，再按最新；永不丢 spec_sha256、candidate_id 与各 revision；包含各职位绑定的状态（含 `first_input_pending`，M2T17R-352：Commander 据此知道某职位要稍后再派；该职位收到首个输入时 `handoff.delivered` 再唤醒它）；以 Rust 类型核对的 runtime 通知 JSON（不加协议 `$defs`）。上下文装箱属 M2-T09。

8. **Commander 的输出（-07、-57）。** M2-T08 负责 decision 的闭环；steer、query、handoff 的路由与投递属投递循环（M2-T16，M2T17R-153、-254 的义务一并在那里）。
   - **产品的文件桥。** Commander 按它的提示把 HCP Message 逐行写到 `.hoh/attempts/<attempt>/messages.jsonl`；产品执行器在 turn 结束、结算之前读它，放进 `Outcome.messages`（测试的 FakeExecutor 直接给出）。
   - **结束时持久登记。** runner 结算监督 Attempt 的同一事务里，把每条消息写成一条 `supervisor.output` 事件（id 由 Attempt 与行号派生，带完整消息）；不是 kind=decision 的写 `supervisor.output_deferred{reason: routed by the delivery loop (M2-T16)}`，不静默丢弃；格式不对的写 `supervisor.output_invalid`。
   - **逐条裁决、可恢复。** 监督器每一步按 seq 处理已登记、尚未裁决（没有同 id 的 decisions 行）的 decision：核对它的 run、sender_role commander、causation_id 等于本唤醒，然后交给 `decide`（各自一个事务，按 id 幂等）；崩溃后重启从持久登记继续，不丢、不重复（-07）。

9. **配置（-65c）。** `supervision.policy` 在 StartRun 时冻结进 Run 的快照（缺省 balanced）；`execution.reserve_supervisor_slot` 由决定 3 实现；`execution.writer_slots` 已校验为 1；`delivery.max_delivery_attempts` 在投递循环接入前没有消费者（M2-T16），更正 ADR-022 第 71 行。

## 附录：监督 Task 与监督 Attempt 在各处的处理（代码普查，main b90aa0c；设计审查补全）

标记：`role='commander'`。Commander 不执行工作 Task（CONTRACT 6、docs/06），计划导入拒绝 role 为 commander 的 Task 与依赖一个监督 Task 的 Task，以后的 create_tasks 决策同样适用（不缩小范围，不需要 CR，-66）。

从“工作进度”排除（监督 Task）：

- `retry::pace` 的 Task 扫描：排除监督 Task，所以它不进 `in_flight`、`due`、`remaining`、`blocked_reasons` 与能力检查；pace 的在途 Attempt 计数（`unfinished`）**不**排除监督 Attempt（决定 3）。
- `retry::fail_task`、reconcile 的 Ended：监督 Task 置 CANCELLED，不 READY，不计次，不写 need_decision；`retry::request_repair` 拒绝监督 Task。
- 调度轮 `rounds::candidates`：只取 READY/PENDING，监督 Task 从不处于这两个状态；测试断言。
- 计划导入（plan.rs、dag.rs）：见上。
- Commander 决策（decide.rs、decision.rs）：以监督 Task 为对象的派发与迁移被拒。
- TaskResult（results.rs）：role 为 commander 的结果被拒（尚未接入 host，规则先写上）。
- 墙钟预算：Commander turn 的时长照常计入 Run 的 `wall_seconds`；预算准入见决定 3。

照常包含（监督 Attempt）：

- runner：`runner::waiting` 的待派发查询、`received` 事务与工作 Run 的枚举按决定 3 的准入表放行监督通知（BLOCKED、WAITING_EXTERNAL 也放行，只放行它们）；续租在 `SUPERVISION_TURN` 之后停止。
- 暂停 `control::pause_step`：在途计数包含监督 Attempt（暂停等它）；撤回 PREPARED 的唤醒时监督 Task 置 CANCELLED（不是 READY），触发器重新武装、不计失败。
- `resume_reconcile`：照常（与暂停一致）。
- 取消：CancelRun 的 `cancel_requested`、取消 pass、`finish_cancel` 照常包含；host/control.rs 模块头改为“取消与暂停不唤醒 Commander，也不等待它的决策”。AC-043-04 仍成立。
- 启动 reconcile：照常处置；结束（非 SETTLED）后由监督器重新武装。
- 团队 checkpoint 的在途查询：包含（ADR-024 决定 5）。
- 交接：监督 Attempt SETTLED 清掉首个输入的欠账（它的 turn 以交接包开头）；交接包里未确认的 outbox 包括唤醒的派发通知。
- 写租约：监督 Attempt 不持写租约，被中断结束时不需要工作区记录（ADR-024 决定 9）。
- 用户可见：getRun、listRuns、team 页不受影响；`/v1/events` 里如实可见唤醒的 Attempt 与 Task 事件。
