# ADR-013 · Pi 适配器的会话与静止判定

状态：M1-T05 采纳（CTO 设计决定，细化 REQ-026，不改变 CONTRACT 或已锁定契约）。日期：2026-11-04。

## 背景

REQ-026 要求 Pi 以 `--mode rpc` 和持久会话运行，按 prompt disposition 与 agent_settled（或状态核验）判定完成，并能在 kill -9 后恢复同一会话；但没有规定会话 id 由谁决定、恢复时如何发现"会话已丢失"、没有 agent_settled 的版本何时发起状态查询，也没有规定哪些计时器可以存在。实现在 `hoh_agents::pi`。

## 决定

1. **会话由 HoH 决定，会话文件由 pi 自己选，HoH 核对**：每个 HoH session 固定一个 `--session-dir`（位于 `.hoh/` 下）和一个 `--session-id`（HoH 生成），每一轮都传同样的两个参数，从不传 `--no-session`；目录写入 sessions.native_path，id 写入 sessions.native_id。pi 1.5.0 的 `--session-id` 找不到会话时会用该 id 新建会话。为此最初尝试在 HoH 中重写 pi 的查找规则（文件头解析、cwd 比较），三轮独立审查都找出新的差异（JSON.parse 的接受范围、file:// 与 `~` 规范化等），说明这条路无法收敛；改为不预测、只核对（M1T05R-03/06/10/11）：恢复前记下目录中所有 `*.jsonl` 普通文件（规范路径、设备号、inode），一个都没有则不启动（SESSION_NOT_FOUND）；启动后 `get_state` 必须报告所请求的 sessionId，且 sessionFile 必须正是事先记下的文件之一（设备号与 inode 相同）。pi 新建的文件、已消失的文件、尚未写出的路径都不是恢复，attempt=FAILED（SESSION_MISMATCH），不发 prompt，旧目录原样保留。目录中的 `*.jsonl`（跟随符号链接后）若是 FIFO、socket 或设备，pi 自己的查找会阻塞或读个不停，因此不启动（SESSION_DIR_UNSAFE，M1T05R-08/12）；目录（包括无权访问的目录）和悬空链接会让 pi 的读取立即失败并跳过，HoH 同样跳过，不拒绝（M1T05R-15）。
2. **一轮的顺序**：先 `get_state`（核对会话、记录模型），再发带唯一 id 的 `prompt`。prompt 的 response 只表示接受：`success=false` 立即结束（`No API key found` → BLOCKED_AUTH，`Model not found` → MODEL_UNAVAILABLE，其余 PERMANENT_EXTERNAL，docs/13），对应输入记 REJECTED；`handled` 立即 SETTLED；`started`/`queued` 等待 `agent_settled`，`agent_end` 之后的重试、压缩不算结束。接受之后的 provider 失败（最后一条 assistant 消息 `stopReason="error"`）在静止后判定为 FAILED；之后有成功消息（重试成功）则清除（M1T05R-04）。分类：HTTP 状态码优先（401/403 → BLOCKED_AUTH，404 且提到 model → MODEL_UNAVAILABLE，408/429/5xx 中的 500/502/503/504/529 → TRANSIENT_EXTERNAL，其余 4xx → PERMANENT_EXTERNAL）。状态码只从 pi 写它的位置读取（pi-ai `error-body.js` 的 `formatProviderError`）：开头的 `<label> error (NNN):`（如 `OpenAI API error (429):`、`Azure OpenAI API error (503):`、`llama.cpp error (500):`）或 `NNN:`；原始 SDK 消息开头的 `NNN` 后接空白、冒号或结尾（如 `429 Too Many Requests`、`403 status code (no body)`）；否则是以完整单词出现的 `HTTP NNN`、`status NNN`、`status code NNN`。没有状态码时按明确短语（先去掉前导空白）：`No API key found`、invalid/incorrect API key、unauthorized、authentication failed → BLOCKED_AUTH，`Model not found` → MODEL_UNAVAILABLE，rate limit、too many requests、overloaded、超时 → TRANSIENT_EXTERNAL，其余 PERMANENT_EXTERNAL。消息体、key、模型名、请求 id 或时间单位中的数字（`sk-test429`、`429abc`、`400ms`）不参与判断（M1T05R-09/13/14/16）。
   输入状态按事实推进，不按到达顺序：prompt 被接受 → DELIVERED，其运行开始（`agent_start`，或 `handled`）→ APPLIED，两个事实谁先到都按 QUEUED→DELIVERED→APPLIED 的顺序提交（AC-026-01 允许 `agent_start` 先于 response，M1T05R-01）。输入若已被别处推进（迁移被拒），记诊断事件，本轮不再动它，也不因此中断。
3. **没有 agent_settled 的版本**：每次 `agent_end` 之后发一次 `get_state`，`isStreaming=false`、`isCompacting=false` 且 `pendingMessageCount=0` 时才 SETTLED。忙则在下一个"工作结束"事件（`agent_end`、`compaction_end`、`auto_retry_end`、`queue_update`、`turn_end`、`message_end`、`tool_execution_end`）后再查；查询在途期间已有工作结束事件到达时，忙的回答一到就立即再查（M1T05R-02）。同一时间只有一个查询在途。从不用计时器推测空闲。
4. **计时器**：一轮自己的计时器只有 deadline 和 abort 宽限，经注入的 `Clock` 运行（AC-026-02 用冻结时钟证明完成不依赖计时器）。stdin 关闭后等待进程退出的宽限属于进程生命周期，与进程底座的升级宽限一样使用 tokio 时间。
5. **扩展 UI（headless）**：对话类请求（select/confirm/input/editor）立即回 `{"type":"extension_ui_response","id":…,"cancelled":true}`，不带任何选项值，并记 `adapter.ui_request`（decision=cancelled）；其他请求（notify、setStatus 等）不回应，只记 `adapter.ui_data`。
6. **取消**：发 `abort`，等待 native grace 内的 `agent_settled`，超时再对进程组 SIGTERM → SIGKILL；终态经 CancelLatch 提交。turn 在 agent_settled 之前结束：有工具开始执行（`tool_execution_start`）则 UNKNOWN_EFFECT，否则 FAILED（PROTOCOL_INCOMPLETE）。
7. **订阅**：每条解析出的记录按到达顺序交给调用方的订阅通道（docs/13 的 subscribe()），包括先于 prompt response 到达的 `agent_start`。

## 未采用

- 让 pi 自己生成会话 id 再回读：恢复时无法区分"恢复成功"与"静默新建"。
- 在 HoH 中重写 pi 的会话查找：与 pi 的 JSON、路径实现无法逐字对齐（见决定 1）。
- 以 agent_end 后静默一段时间判定空闲：正是 REQ-026 禁止的 sleep 推测。

## 已知限制

pi 的 bash 工具同样在独立进程组中运行命令（与 ADR-012 所记 codex、claude 相同）；`abort` 由 pi 自己结束它们，进程组 SIGKILL 到达不了组外后代。live 检查会把仓库内的任何残留进程判为 FAIL。
