# ADR-036 · 模式切换与运行中输入的宿主投递

状态：采纳（M3-T09 提前开发，2026-11-21）。依据为 CR-026 的 REQ-007、REQ-017、REQ-018 与 CTO 已采纳的准备清单默认决定。起点为 main `b6681e9d`；提前开发时不复制 M3-T02 的在途代码。S7 已 rebase 到 `b6729a3f`，接入合入后的 ADR-033 实现。

## 范围与边界

客户端位于 `hoh-client`：只解析交互、构造共享命令、读取宿主投影。宿主语义位于 `hoh-app` 与 `hoh-core`，客户端不依赖 `hoh-app`。不扩充 shell 子命令，不修改受锁契约、检查计划或 SQL。

最初的提前开发只交付 S1–S3。S4（turn 内 steer）、S6（kill/restart 投递恢复）分别需要两名互补审查者；S5 的角色选择与 Slash 选择器留待输入通道完成；S7 的 CHANGE 必须等 M3-T02 合入。Plan 的规格起草及模式对产品任务的准入属于 M3-T04，本任务只处理切换待生效期间的写派发闸门。

## 决定

1. **SetMode 的唯一写者是命令事务。** 核对 Run 未终结、`expected_revision` 与幂等键。没有 PREPARED/STARTING/RUNNING 写 Attempt 时，更新 `runs.mode`，追加 `run.mode_changed{from,to,command_id}` 并 Touch revision；否则追加 `run.mode_change_pending`，Touch revision，返回 202。过期返回 409 STALE_REVISION。待生效期间再次提交采用后写覆盖，历史事件保留；兑现时从当前模式切到最后目标。
2. **安全点兑现。** 调度轮与写派发入口在存在未兑现 pending 时不派新写 Attempt；只读任务照旧。宿主 tick 在调度之前运行幂等模式步骤：无在途写 Attempt 即兑现最新 pending，事件 id 从 command_id 派生，Touch revision。启动对账之后也走同一步骤，不以进程内标志保存 pending。
3. **配置与 TUI。** `[ui] mode_cycle` 缺省为 `["PLAN", "BUILD", "AUTO"]`，只接受 2–3 个不重复的合法模式；加载器、快照和 example 在 S1 同提交加入并重跑 TEST-018-01。已附着的 `/plan`、`/build`、`/auto` 与 Shift+Tab 经 SetMode API 修改当前 Run，顶栏读当前 Run 模式；未附着时只改下一次由本 TUI 启动的 Run 模式，不改项目默认或发送命令。未知 Slash 不发送。ADR-031 与用户指南的旧句在 S2 同步更正。
4. **输入骑在 outbox 上。** 接受事务同时写 input_queue 与 `message_id=input_id`、`notice:"input"` 的 outbox 行。复用领取守卫、退避、代次、收据与死信；不另建传输账本。输入保持 QUEUED→DELIVERED→APPLIED/REJECTED。投递耗尽时 outbox 为 DEAD_LETTER，输入为 REJECTED；通常原因为 delivery_exhausted，但已有未完成 turn 预留时保留 UNKNOWN_DELIVERY，不把未知外部效果解释为未送达。
5. **只读 ASK 与 Commander。** 普通无目标输入默认交给 Commander。按 REQ-017 行为 1/2，将 `input.queued` 加入 ADR-025 的监督事件集合，产生 normal 的 `user_input` 唤醒，键含 input_id；token、心跳、工具日志等不唤醒清单不变。只有输入投递成功才允许相应唤醒执行，提示携带问题。成功监督 turn 的最终文本作为回答写入 `input.applied{answer}`。工作态 ASK 不修改 tasks/runs 的 revision，不创建工作 Attempt；停止态命令按 ADR-031 决定 7 / E3 推进 Run revision 并以新的 `run.result` 收尾；监督 Attempt 与回答不作为任务变更决策。
6. **职位代次与首输入。** 入队载荷保存目标绑定的 role_epoch；消费时核对，迟到拒绝为 STALE_ROLE_EPOCH。session.start 未 ACKED 或新持有者仍欠首个输入时，不消费普通投递、不计数，按领取归还语义等待（M2T17R-153）。Commander 的 ASK/STEER 只进入新的监督 turn，该 turn 同时携带尚欠的首输入包；因此 session.start 已 ACKED 且没有首输入 turn 在途时可领取这类输入，不要求该 turn 先完成。首输入债务仍由 SETTLED 结清，其他职位与 HCP 消息没有此例外。Commander 自己发出的消息按 commander 绑定核对，沿用 ADR-024 决定 6（M2T17R-154），不新增例外。
7. **后续投递片的已采纳决定。** consume 的 KeyReuse 结算为一次拒绝，不重试到死信（M2T17R-254）；领取永不取验证交接。S4 将 mid_turn_steer 能力分流为 turn/next_attempt 边界；后一种统一并入下一 Attempt 的提示词，Pi 的原生输入状态机保留，产品不再单独喂数。接管后的 query/steer 路由取代 deferred，历史 deferred 不补投，改写冻结候选仍拒绝并登记 Issue。
8. **后续输入与菜单决定。** CONTROL 在接受事务内按暂停/pause、恢复/resume、取消/cancel 翻译，归一大小写与全半角空格；未知文本拒绝为 unknown_control。CHANGE 在接受后的宿主步骤复用 M3-T02 propose 的摘要、影响闭包与冲突语义，成功才 APPLIED。`/status` 显示当前状态，`/help` 显示键位，`/team`、`/model` 先显示当前值与设置范围说明；不虚构编辑能力。不增 ASK/CHANGE/CONTROL 的专用 TUI 语法，种类通过 API 表达。

## S4：投递与 Attempt 的确定性顺序（2026-11-22）

本次委派追加 S4、S6，不重写已送审的 S1–S3；S5、S7 不在本次范围。输入循环成为独立的宿主任务，沿用 Store 单写线程、outbox 领取和结算；控制循环不等待模型回执。所有角色的 ASK/STEER 都可领取，Commander 保持既有只读监督路径。

输入的 `after_attempt` 保存受理时该职位已 STARTING/RUNNING 的最大 Attempt 序号。运行中 STEER 只有在唯一目标 Attempt 的会话支持 `mid_turn_steer`、库内仍 RUNNING、epoch 相同时才预留到该 Attempt；预留在外部发送前提交。Codex runner 的 sender 属于确切 Attempt，随 turn 结束关闭；取消在适配器 select 中优先于新 steer。ASK 从不进入 steer 端口。

适配器成功回执才写 `input.delivered{boundary:"turn",attempt_id}`；Attempt SETTLED 后写 APPLIED。回执与结算的两种顺序都检查相同的持久事实。明确的 NotNow/CapabilityUnsupported 转到 `next_attempt`；明确拒绝写 REJECTED；回执丢失或超时写 UNKNOWN_DELIVERY 拒绝，不盲目再次发送外部效果。宿主在预留之后崩溃时，重投看到未完成预留也走 UNKNOWN_DELIVERY；这类外部效果未知与已写消费收据、只丢 outbox ACK 的可安全重投不同。

不支持 turn 内引导时，收据只确认路由已持久化，输入仍 QUEUED。下一次符合边界的 STARTING Attempt 在提示词构造前，通过一个 Store 事务预留输入，保持 QUEUED，写 `input.reserved{boundary:"next_attempt",attempt_id}`。输入按受理顺序成为强制上下文，受原有提示词预算检查约束；相同 Attempt 重读得到同一输入，其他 Attempt 不会同时取得。只有 Attempt 转为 RUNNING 的同一事务才写 `input.delivered{boundary:"next_attempt",attempt_id}`，随后运行器打开进程 gate。未到 RUNNING 就结束的 Attempt 释放预留，追加 `input.released{reason:"attempt_not_started"}`，保留原收据与入队顺序，后续 Attempt 可领取；已经 RUNNING 的失败或取消仍终结输入，不再次投递。首输入门仍在领取和消费两处核对。没有新建工作 Attempt 来处理 ASK。

验证者的新 query/非改写 steer 在请求事务里入 input_queue 与 outbox，响应 queued；源 Attempt 和职位 epoch 再核对，重复请求比较完整来源消息。改写冻结候选仍拒绝并开 Issue。历史 `request.deferred` 优先返回原结果，永不补投。

## S6：收据、重投与进程死亡（2026-11-22）

输入收据新增不可变输入摘要（id、run、kind、目标职位、epoch、正文、来源消息），不包含 state、answer 或路由元数据。普通消费与路由消费均先核对领取信封，再读取收据；同键异文返回类型化 `KeyReuse`。S3 已有的无摘要收据仍可原样重放，但不能绕过信封核对；不迁移、不覆盖历史收据。

Dispatcher 将 KeyReuse 结算为一次终态拒绝：input 为 REJECTED(KEY_REUSE)，outbox 为 ACKED，清空退避；当前领取的计数归还，不占 `max_delivery_attempts`。`outbox.rejected` 与 `input.rejected` 使用不同的派生事件 id，重复或迟到结算不重复记录、不进死信。冲突若来自 Commander 的 decisions 历史且尚无 receipt，结算事务写一条 KEY_REUSE 拒绝回执；已有异文 receipt 保留为冲突证据，不拿拒绝结果覆盖它。

可安全重投的窗口是**消费事务已提交、outbox ACK 未提交**。收据与业务状态在同一事务内，重投返回原收据；它不再次运行消费者业务。旧代次的迟到失败不能把新代次的成功退回 PENDING。它与 S4 的外部 steer 已预留、却没有成功回执的窗口不同：后一种只能标 UNKNOWN_DELIVERY，不承诺外部模型效果恰一次。

## 首轮审查修复（M3F-01、M3F-02，2026-11-22）

停止态 ASK 原先跳过 Touch 与 result_due，在 INCOMPLETE 撞上 writer::finish 的命令守卫；BLOCKED/PAUSED 则缺少客户端所等的新结果。恢复 ADR-031 的停止态命令事务约定，运行中 ASK 的只读约定不变。`test_017_01_ask_on_a_stopped_run_publishes_a_new_result` 覆盖三种停止态、事件尾部、幂等重放及无工作 Attempt。

空闲 Run 换绑 Commander 后，普通投递等待首 turn 完成，而 user_input 唤醒等待投递完成，形成互等。Commander ASK/STEER 采用上文决定 6 的窄例外；领取和消费使用同一判定。`test_017_01_idle_commander_rebind_answers_ask_in_its_first_input_turn` 经真实换绑、会话绑定与 session.start 交付，验证 ASK 所创建的监督 turn 保留 first_input、回答一次、收据一次，未交付 session.start 与已有首 turn 的门仍关闭。普通职位首输入门的测试改用 developer，断言不变。


## 第二轮审查修复（M3H-01、M3H-50、M3H-51、M3H-52，2026-11-22）

- **M3H-01：次数上限不改变外部效果的分类。** `max_delivery_attempts=1` 时，未完成 turn 预留到期仍保持 DEAD_LETTER:1，但输入拒绝原因是 UNKNOWN_DELIVERY；迟到成功不覆盖这个终态。无预留的普通投递耗尽仍为 delivery_exhausted。
- **M3H-50：预留与送达分开。** Take 只写 QUEUED 的 Attempt 归属，收据确认路由落库；RUNNING 转换才确认送达。所有 Attempt 状态转换共用这个事务边界，正常结束和恢复对账均释放从未运行的预留；扫尾也覆盖 QUEUED 的 next_attempt 预留。输入状态机没有 DELIVERED→QUEUED 的反向迁移，没有新增 SQL 迁移或改变受锁契约。RUNNING 已提交但 gate 尚未打开的窗口仍保守地视为可能送达，不据进程内记忆重发。
- **M3H-51：已交给原生写入器而未获应答的 steer 不可重发。** 进程死亡、截止期 kill、超大帧、取消等结束时，Pending::Steer 返回 `Rejected{reason:"UNKNOWN_DELIVERY"}`，沿既有宿主拒绝路径持久化。即使收到匹配的 userMessage item，也不能替代相关联的 RPC 应答：目前 item 按文本匹配，不能证明本请求成功，因此仍为 UNKNOWN_DELIVERY。此处比审查建议的“见 item 即 Delivered”更保守，符合本 ADR 的回执规则与本次委派要求。交给异步写入器后无法证明未发送的请求同样未知；不会把部分写入当作安全重试。
- **M3H-52：可证明未发送的请求安全归还。** 尚在 mpsc inbox 的请求由接收端关闭时排空，逐条回 NotNow；包含正常结束、gate 关闭和提前返回。握手前已取出但尚未发送的 held 请求仍按原规则回 NotNow。对端明确拒绝继续保留原拒绝语义。

## 设计修正：所有输入共用业务拒绝出口（M3I-100，2026-11-22）

**一个决定：每个已受理的 SendInput，无论种类（普通输入、ASK、STEER、CHANGE、
CONTROL）和 Run 状态，最终只能是 APPLIED 或带稳定原因的持久化 REJECTED 输入。
所有业务拒绝共用输入状态变更与 `input.rejected` Record 出口；拒绝事务保持 Run
全行、revision、既有 `run.result` 与任务不变。** QUEUED / DELIVERED 是等待消费者、
安全点或恢复的中间状态，不是最终成功。此决定取代按 unknown CONTROL 单独补例外、
按已知 CONTROL 非法状态回滚整个受理事务的旧规则（M3F-01、M3I-50、M3I-100）。

受理边界仍遵守 ADR-031 决定 7：不存在的 Run、终态 COMPLETED / FAILED / CANCELLED、
过期 expected_revision、复用不同载荷的幂等键及无效命令信封，在受理前明确拒绝，
不生成输入或命令回执；终态矩阵必须逐格验证这一拒绝。受理后的业务拒绝包含
`unknown_control`、`illegal_transition`（另存 `details.from`、`details.to`、原始原因
及守卫详情）、`SPEC_CONFLICT`、`SPEC_INVALID`、`BAD_REQUEST`、`STALE_ROLE_EPOCH`
等。相同请求的重放返回原回执，不重复应用或记录。

应用必须复用既有命令与生命周期判定，不能复制控制迁移表。受理后的应用步骤在
事务保存点内执行：业务拒绝先撤回该步骤的事件、子命令、状态变更及临时推进登记，
再通过同一个输入拒绝出口保存输入、Record、投递结算及幂等回执。未知 CONTROL
直接进入这个出口。异步 CHANGE 的业务拒绝也隔离其子命令应用，避免失败后遗留
`temp.command_run`。角色代次等消费拒绝继续使用相同输入状态变更出口。

拒绝不登记推进命令、不写 `input.accepted` / `input.queued` 进度事件，不通过 Touch
伪造进展。已发布停止态的 Record 按既有规则写到项目历史，载荷保留 run_id；
`writer::finish`、停止态与输入状态机守卫保持原样。只有存储失败与状态机不变量
违规使整个事务回滚；业务上的 Run 迁移不允许是输入拒绝，非法输入自身迁移、
完整性错误等仍是守卫错误，不能吞掉后记成业务成功。

验证采用从 `RunState::ALL` 生成的种类 × 全生命周期状态 × 控制文本矩阵：普通
REPLY、定向 REPLY、ASK、STEER、CHANGE、CONTROL，文本含 pause / resume / cancel
及未知值。非 CONTROL 的这些文本不得误译为控制命令；中间队列使用真实产品消费者
结算为应用或明确拒绝。逐格检查结果类别、稳定原因、拒绝时 Run/Task/result 不变、
幂等重放，尤其覆盖 INCOMPLETE/pause、PAUSED/pause、BLOCKED 未解阻/resume。
另外验证受理前 revision 栅栏、拒绝记录落盘失败的原子回滚及恢复后同请求重试。

实现把 SendInput 的应用与 CHANGE 的子命令包在 `inputs::application` 保存点内，
用 `Rejection::from_error` 统一识别业务拒绝；新输入与后续消费共用 `transition`
更新状态和写 Record。`AnswerQuestion` 的直接命令出口保持原契约。没有新增控制
迁移表，也没有修改 writer 的停止态守卫、AC、基线或检查计划。

## L3 清理：宿主投递的配置与并发（M3F-03a、M3H-53，2026-11-24）

投递上限使用宿主启动时的有效 `HostConfig.config.delivery`，运行期间不反复读取磁盘配置。

之后损坏不阻断已有输入，也不改变其重试上限。新 Run 的配置校验沿原路径进行。

输入循环至多同时推进 32 个职位；每个职位仍使用原 Dispatcher 串行领取至多 32 条。
一个职位等待外部 steer 回执时，其他职位与周期扫尾继续推进。同职位不并发，因此顺序、

turn 预留仍由恢复按 UNKNOWN_DELIVERY 分类。控制循环仍独立。

## L3 清理：Commander 输入的终结（M3F-04，2026-11-24）

失败或单次撤回仍保留 DELIVERED 输入供原 wake 重试；不把可恢复的 turn 取消当作输入
失败。只有 ADR-025 的重试与探测机会全部耗尽，或监督器明确丢弃 trigger/wake 时，才在
同一事务通过原输入状态出口写 REJECTED。原因分别是 `commander_retries_exhausted`、
`commander_unavailable` 或 `commander_wake_closed`。拒绝幂等，原投递收据不改写。

耗尽输入不会清除当前 Commander epoch 的失败预算；重启仍保持 BLOCKED 且不分配
额外 turn。换代后沿原 epoch 栅栏处理。测试
`test_017_01_commander_input_rejects_only_after_the_last_retry` 覆盖全部重试、终结及重启；
`test_017_01_dropped_commander_wake_rejects_input_but_withdrawal_retries` 覆盖撤回可重试、
Run 取消与 unavailable 时丢弃 trigger。自测，非验收。
