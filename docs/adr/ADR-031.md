## 待所有者确认（Q1、Q2）

两项牵涉 CONTRACT 第 4 条“非交互自动规划不是跳过规格”的解释与 M2 的范围，本 ADR 按预研清单的建议写成决定 1、2，**在所有者确认前不算最终决定**。

- **Q1 `hoh -p` 新建的 Run 从哪里得到规格。** 今天 StartRun 只插一行 runs、`spec_id` 为空（crates/hoh-core/src/persistence/commands.rs:144），Commander 的分配只选 `spec_id IS NOT NULL` 的 Run（persistence/wakes.rs:777），监督 Task 要求 `tasks.spec_id` 非空（contracts/sql/001_initial.sql 的 tasks 表；wakes.rs:971-973），产品里没有 specs 的写者（ADR-024 决定 10，docs/adr/ADR-024.md:65：spec 由 ProposeSpecChange/ApproveSpec 带来，属 M3-T02）。所以 `-p` 的 Run 永远停在 CREATED，AC-002-01/02、AC-004-02/03/04、AC-005-01、AC-042-04 都做不到。
  - **建议并写为决定 1 的 (a)**：StartRun 在同一事务里采用项目当前最新的已批准规格（specs 按项目编号，`UNIQUE(project_id, revision)`），写 `spec.changed` 唤醒 Commander；项目没有规格时 Run 以 BLOCKED(NEED_DECISION){reason: no_spec} 停下，`-p` 退出 3 而不是永远挂起。采用已批准的规格不是跳过规格；没有规格时如实阻塞。不改受锁文件。
  - (b) host 为每个 Run 造一个“临时 spec”（目标摘要、无需求）：占用项目的 spec revision、没有需求就没有 AC（completion 会以 no_acceptance_criteria 阻塞，验证不可能），等于自动生成规格——与 ADR-024 决定 10 相违，可能触及 CONTRACT 第 4 条。若所有者选它：决定 1 改为写 specs 行，需 CONTRACT 层面的确认；AC-042-04、AC-002-02 仍做不到。
  - (c) 按 CR-010 的先例写 CR，把 AC-002-01/02、AC-004-02/03/04、AC-005-01、AC-042-04 改归 M3-T02 之后的任务。若所有者选它：本 ADR 只保留决定 3–8 的机制、TUI、attach 与 AC-001-01/02、AC-002-03（K 由 SQL 播种）、AC-003-03；需要一份改 `contracts/development-tasks.json` 的 CR（不在锁内，但改归属按 CR-010/CR-020 的做法写 CR）；v0.1 的发布推迟到这些 AC 有承接任务为止。
- **Q2 开发 Task 从哪里来**（AC-002-02、AC-004-02/03/04、AC-005-01、AC-042-04 都要开发 Task、冻结与验证轮次）。今天 create_tasks 过栅栏而不应用（crates/hoh-core/src/decision.rs:92-97；ADR-025:177“create_tasks 等 M3 的规划路径”），`Store::import_plan`（persistence/mod.rs:1538，persistence/plan.rs:23）只有测试调用。
  - **建议并写为决定 2 的 (a)**：decide 应用 create_tasks，经 `plan::import` 的同一校验（ADR-017 决定 4，M2-T03），与决策同一事务。
  - (b) 测试在 Run 建好后用 SQL 播种 Task：与活的 host 竞争，不是产品路径。若所有者选它：决定 2 撤销，create_tasks 仍不应用，测试计划中依赖开发 Task 的各项改为播种（并在审查记录中说明它们不是产品路径的证据）。
  - (c) 随 Q1(c) 一起推迟。
- **确认之前与选 (c) 时（M2T13D-55）**：依赖 Q1、Q2 的切片（S2，以及 S5 中依赖已采用规格或开发 Task 的 TEST）在所有者确认之前可以开发与审查，但不合入 main。若所有者选 (c)：按 CR-010 的先例写 CR 改这些 AC 的归属，并重排 v0.1——v0.1 必须通过的 AC 移到 M3 之后，与 M2 → v0.1 → M3 的任务顺序（CR-003 D2）成环，要配套调整发布与任务依赖；这要所有者批准，不属于 CR-003 D1。

### 更正 B：把 Run 带回工作态的提交留下持久的继续义务（M2T13D-01 → M2T13D-101）

第 1 轮是被拒的结束决定之后没有唤醒，第 2 轮是恢复之后没有唤醒；根因相同：Commander 推进的阶段（CREATED、DISCOVERING、SPECIFYING、READY）没有调度轮派发（rounds.rs:40 只在 RUNNING、VERIFYING 派发，pace 只看 persistence/runner.rs:480-484 的状态），只有唤醒能让下一步发生，而 `reconcile.run`、`run.resumed`、受理事件都不是唤醒（supervise.rs:20-33），已结清的 turn 也不再欠（wakes.rs:103-119）。今天从 PAUSED 恢复同样不满足：ResumeRun 的提交只写 `reconcile.run`、受理事件与 CAS（commands.rs:213-298），暂停在 SPECIFYING、turn 已结清时，恢复之后什么也不发生。更正：

- **不变量 E15**：一个提交把 Run 从停止状态（PAUSED、INCOMPLETE、BLOCKED、WAITING_EXTERNAL）移进工作态 W，而提交之后该 Run 没有未结束的 Attempt（`retry::unfinished_attempts`）、没有 PENDING 的触发器或欠下的唤醒（`wakes::of_run` 的 `owed`），本提交也没有 KINDS 中的事件（例如决定 7 的 `need_decision{answered}`）时，同一提交写 `supervisor.retrigger{reason: "RESUMED", base_fingerprint: "run_resumed", from, to, command_id|null, spec_revision}`，事件 id `child_id(run_id, "resumed/<本提交之后的 runs.revision>")`。`classify` 以 `run_resumed#retrigger` 为键（同键至多一个 PENDING：几次恢复并成一个触发器），High；到期（`due_at`，crates/hoh-core/src/supervise.rs:199-204）后的步骤触发它，分配给它的 turn 在当前状态上继续。它是持久的事件与触发器行，跨重启（游标之后的事件重新纳入）；命令的重放什么也不写（commands.rs:108-127），所以幂等。已有触发器、欠下的唤醒或本提交自己的唤醒时不写：那些已经保证下一个 turn。
- **唯一的写处**是 `writer::write`，与 run.result 同一处（决定 3）：它看得见本提交每个 Run 的 from→to（`Change::Run` 与 `Change::Unblock`）与本提交的事件，所以 ResumeRun（四种停止状态，决定 16）、答复使 BLOCKED 的 Run 解除（决定 7）与 Runtime 的解除（`blockers::follow` 的调用者：pace、staffing、Commander 恢复可用）一处覆盖，不靠各路径记得写。**例外**：pace 在重试到期时把 WAITING_EXTERNAL 的 Run 放回工作态（retry.rs:754-772 中 `blocked` 为假的一支；同一处 BLOCKED 的 Unblock 照规则写）不写——WAITING_EXTERNAL 只从 RUNNING、VERIFYING 进入（pace 的 `working`，:778-799），回去时有到期的 Task，同一 tick 的调度轮派发它（host/runner.rs:752-753）；否则每次瞬时故障的等待都多一个 Commander turn。
- 不选“只在 ResumeRun 写”：答复与 Runtime 的解除回到 Commander 推进的阶段时同样会卡住（例如在 SPECIFYING 因 BUDGET_UNENFORCEABLE 而 BLOCKED、价格变为已知后解除）；不选新的唤醒种类：REQ-021 行为 1 的集合封闭，`supervisor.retrigger` 已在其中（未采用 22）。
- 用于：决定 3、7、16，E15，出口表，测试计划（Commander 在 SPECIFYING 决定 INCOMPLETE 后恢复、不注入唤醒、跨重启；PAUSED、Runtime 解除与答复各一；WAITING_EXTERNAL 的到期不写），受影响的既有测试（control/tests.rs:340 的事件种类），S1。

## 决定

1. **Run 的规格：采用项目最新的已批准规格（Q1 (a)，待所有者确认）。**
   - StartRun 的事务（commands.rs:130-170 的 `RunTarget::Start` 分支）在插入 runs 行时取 `SELECT spec_id, revision, sha256 FROM specs WHERE project_id = ? ORDER BY revision DESC LIMIT 1`。specs 行按构造都是已批准的：唯一的写者将是 M3-T02 的 ApproveSpec；在此之前由 fixture 写入（验证要求它的 sha256 等于项目 `contracts/requirements.json` 的摘要，ADR-028 决定 4 的约定路径，否则冻结时 SPEC_MISMATCH）。受锁的 specs 表没有批准状态的列（contracts/sql/001_initial.sql:10），查询不能按批准过滤，所以这条前提写进移交：ApproveSpec 只插入已批准的修订，规格草稿不是 specs 行（M2T13D-59）。
   - **有规格**：runs 行带 `spec_id`；`run.created` 之后在同一提交写 `spec.changed{run_id, spec_id, spec_revision, spec_sha256, from: null, cause: "adopted"}`（REQ-021 行为 1 的“规格变更”：Run 的规格从无变为 s；`classify` 按 payload 的 `spec_revision` 取键），由它唤醒 Commander。M3-T02 产生的 `spec.changed` 才会置候选 STALE；`cause: "adopted"` 的 Run 还没有候选。
   - **没有规格**：同一事务声明 `runtime:no_spec` 的 NEED_DECISION（Claims，blockers.rs 的机制），写 `question.asked{question_id: <本事件 id>, reason: "no_spec", text: "项目还没有已批准的规格：先在 TUI 用 /plan 生成并批准规格（M3），或在项目中放入已批准的规格后答复本问题", choices: [adopt]}`，`blockers::follow` 把 CREATED 置 BLOCKED（CREATED 是工作态，lifecycle.rs:106-114），决定 3 的 run.result 随之。它不是 `need_decision` 事件：没有规格的 Run 不能有监督 Task，写成唤醒只会留下永不分配的触发器。
   - 202 体的 `revision` 改为本事务之后 Run 的实际 revision（有规格 0，无规格 1）；今天 StartRun 恒为 0（commands.rs:169 的 `(0, …)`）。这与该字段已有的含义相同：openapi 对 202 体的 `revision` 只给类型、没有描述（openapi.json:67-69），docs/05-data-api.md:33 只说 202 含 revision；其余运行命令今天返回的就是本事务 CAS 之后 Run 的 revision（commands.rs:308），ConfigureTeam 返回团队的 r+1（ADR-022:61）。改变的只是 ADR-021 决定 5 第 5 步写死的 `revision: 0`（ADR-021:69，见注记）。
   - Run 的推进仍是 Commander 的：transition_run CREATED→DISCOVERING→SPECIFYING→READY→RUNNING（每步一次 revision 栅栏），之后调度轮派发。REQ-002 行为 6 的“规格/readiness 流程”在 M2 里就是 Commander 对已采用规格的审阅（可以在 SPECIFYING 中提问，AC-002-01）；Runtime 自动推进阶段属于 M3 的规格流程，不在本任务。
   - **Commander 的提示**：resources/prompts/commander.md:49 今天要求“每次唤醒只提交一条决策”，而应用的决策不是唤醒（supervise.rs:20-33），所以真实的 Commander 走完上面四步之前就没有下一次唤醒。本任务把该句改为：一个 turn 可以按顺序提交多条决策，每条应用的决策使 Run 的 revision 加一（decide.rs:440-494 的每个效果都推进它一次），后一条的 expected_revision 写前一条应用之后的值；写错的那条以 STALE_REVISION 拒绝，由 REQ-021 行为 6 的过期重新触发再唤醒（中文优先，产品内容）。运行时本就逐条处置一个 turn 的多行输出（ADR-025 决定 8），不需改代码；FakeAgent 的 Commander 照此提交。

2. **create_tasks 经 plan::import 的校验应用（Q2 (a)，待所有者确认）。**
   - `plan::import` 拆出 `plan::check(tx, run, raw) -> Result<ValidPlan, PlanError>` 与 `plan::import_in(tx, run, ValidPlan) -> Imported`：`import_in` 不自带事务，只写 tasks、task_dependencies、task_requirements 与 `plan.imported`，**不做 Run 的 CAS 或 Touch**（今天 import 在 persistence/plan.rs:211-217 对 Run 做 `Change::Touch`；两处都 Touch 会使同一 turn 后续决策的 expected_revision 差一，M2T13D-51）；`Store::import_plan` 保留为二者加一个事务与那一次 Touch 的包装，行为不变。
   - `decide_in`（decide.rs:169 起）对 create_tasks：在写 decisions 行**之前**调用 `plan::check`；计划无效时返回 `PersistError::Plan`，输出处置为 `supervisor.output_disposed{outcome: "invalid", reason: "PLAN", code: <PlanError 的 ErrorCode 或 null>, detail}`，不写 decisions 行——与今天 InvalidProposal→`invalid PAYLOAD` 同类（outputs.rs:516）。DAG_CYCLE 等是 ErrorCode，不是 RejectionReason，不能写进 decisions.reason_code（`$defs.RejectionReason` 描述该列），所以不做成 REJECTED。
   - 计划有效时照常过 epoch、revision 与 Task 快照栅栏；通过即 `Effect::CreateTasks`：`import_in` 写 tasks、依赖、需求与 `plan.imported`，decisions 行 APPLIED、`decision.applied`，Run 只有决策的一次 Touch（支撑测试断言应用之后 runs.revision 恰加一）。`Proposal::applicable`（decision.rs:92-97）只对 request_user_decision 为假（它仍过栅栏而不应用，由答复应用，决定 7）。
   - ADR-017 的移交 M2T03R-156（计划路由把计划错误映射为 4xx）：M2-T13 不加计划路由，decide 路径上的计划错误以上述处置带着它的码；义务留给将来加路由的任务（M3 前没有计划）。

3. **run.result：写在进入停止状态的那个提交里（Q3 (a)）。**
   - 记 E = {COMPLETED, FAILED, BLOCKED, INCOMPLETE, CANCELLED, PAUSED}（RunResult.state 的全集），其中 T = {COMPLETED, FAILED, CANCELLED} 为**终态**（没有出边：REQ-036 行为 3，lifecycle.rs:264，ADR-011:40；决定 4 的守卫只看 T），{BLOCKED, PAUSED, INCOMPLETE} 为**停留态**。INCOMPLETE 不是终态：REQ-036 的决定写明“INCOMPLETE是否终态未定；本选择终态仅COMPLETED/CANCELLED/FAILED，INCOMPLETE/BLOCKED/WAITING_EXTERNAL/PAUSED可经ResumeRun回到resume_state”，迁移表中它有出边 W、CANCEL_REQUESTED、FAILED（lifecycle.rs:254-263，ADR-011:39）。停留态的 Run 在它的 run.result 之后还可以有事件，但只来自受理的命令（决定 4、7）。
   - **唯一的写者**是 `writer::write`（writer.rs:1145 起）：在本提交的 CAS 与事件之后、outbox 之前，对本提交中 `Change::Run(to)` 且 to ∈ E 的每个 Run（去重），以及 `Commit.results`（新字段：命令请求结果的 Run，决定 7）中此刻处于停留态的每个 Run，追加一条 `run.result`，作为本提交的最后事件。所以六条路径（blockers、decide、pace、control 两处、commands）一处覆盖，各结束点不必记得写。它也必须是**本事务中该 Run 的最后事件**：同一事务里在它之后还要写该 Run 事件的调用方合并为一次 `writer::write`——已知的只有 `person()` 之后的 `output_disposed{unsupported}`（outputs.rs:496-499、:524-570），改为由 `person()` 把处置事件放进同一个 Commit；终态由决定 4 的守卫兜住，停留态（含 INCOMPLETE）由各路径的支撑测试兜住。
   - 载荷是 `$defs.RunResult`，由 `results::compute(tx, run_id, seq)` 在事务内求：state、`exit_code`（REQ-004 的表；映射从 crates/hoh-app/src/exit.rs:38-56 移到 hoh-core 的 `exit::run_code(state)`，hoh-app 的 `exit_code` 调用它，TEST-004-01 不变）、`blocked_reason`（BLOCKED 时为 runs.blocked_reason，Claims 在 CAS 之前已写入，blockers.rs:235-251；否则 null）、spec_revision、accepted/total/remaining（决定 5）、cost（决定 5）、`last_event_seq` = 它自己的 seq。
   - **自己的 seq**：插入前取 events 的下一个自增值（`sqlite_sequence` 中 events 的值加一，表为空时 1），写进载荷，插入后核对 `last_insert_rowid()` 相等，不等即 IntegrityViolation、整个提交回滚。预测不会被别的插入抢先：events 的 seq 是 `INTEGER PRIMARY KEY AUTOINCREMENT`（contracts/sql/001_initial.sql:37），产品中没有删改 events 或 sqlite_sequence 的语句；决定 4 列出的六处插入都只经写者 actor 唯一的读写连接（writer.rs:1-4；`open_checked` 把这一条连接交给写者，persistence/mod.rs:788-799，读者连接为只读，:687-688），且都在 BEGIN IMMEDIATE 的事务里（`writer::begin`，writer.rs:314-320；命令，commands.rs:428），预测与它自己的插入在同一事务中相邻。选它而不是前一条事件的 seq：stream-json 的末行与 json 的对象说的是同一个位置，从 `last_event_seq` 之后续读不会再见到这条结果。
   - 事件 id `child_id(run_id, "result/<本提交之后的 runs.revision>")`：每个写结果的提交都推进 revision（CAS 或 Touch），所以唯一。
   - Touch 而状态不变（BLOCKED 的原因集合变化，blockers.rs:324-330、retry.rs:715-723）不写；`Change::Unblock` 与 WAITING_EXTERNAL 不写（客户端在 WAITING_EXTERNAL 期间继续等待）。
   - 同一处还追加更正 B 的继续义务：本提交把某 Run 从停止状态移进 W 且满足 E15 的条件时，在 run.result 之前写 `supervisor.retrigger{reason: "RESUMED", base_fingerprint: "run_resumed"}`（进入 W 的提交不写 run.result，所以两者不会同时出现在同一个 Run 上）。

4. **终态之后不再有该 Run 的事件；INCOMPLETE 之后只有受理的命令写该 Run 的事件。**
   - **进入终态与 INCOMPLETE 只在安静时**：pace 的预算停止已要求没有未结束的 Attempt（retry.rs:564-576 的 `unfinished == 0`），取消与暂停在 Attempt 结束之后才落定。新增：Commander 的 transition_run 到 COMPLETED、FAILED、INCOMPLETE 在该 Run 有任何未结束（PREPARED/STARTING/RUNNING）的 Attempt 时——工作 Attempt 与监督 Attempt 都算，与预算停止的计数相同（retry.rs:547-556）——以 `decision.rejected{ILLEGAL_TRANSITION}` 拒绝（decision.rs 的 `transition_run` 读快照的新字段 `attempts_unfinished`，即 `retry::unfinished_attempts(tx, run)`：该 Run 未结束的 Attempt 数，从 pace 的计数 retry.rs:549-556 抽出，pace、快照与下一条的步骤共用），同一提交留下再决策的义务（下一条）。决策被处置时它自己的 turn 已经结束（输出只在 turn 成功之后登记，ADR-025 决定 8），所以不会因自身而被拒。监督 Attempt 也要算，因为唤醒分配不等前一 turn 的输出处置完，只跳过有 turn 在途的 Run（wakes.rs:845）：turn T1 以“COMPLETED”SETTLED，T2 随即被分配并运行，T1 的输出随后被处置；若只数工作 Attempt，结束的提交会在 T2 在途时落下——T2 的唤醒不是欠下的，(1) 不 supersede 它，`close_due` 不成立，T2 结束时的 settle 与输出事件被守卫以 `RunEnded` 拒绝，而 runner 已不再选该 Run。取消已等全部 STARTING/RUNNING 的 Attempt（control.rs:428-440），预算停止数全部 Attempt，所以只有 Commander 的决定需要补上。所以 Run 进入 T 或 INCOMPLETE 时没有在途的 Attempt（工作或监督）会在它的 run.result 之后写事件（AC-004-02 的 seq 集合相等，E2）。
   - **被拒的结束决定留下持久的再决策义务（M2T13D-01）**：拒绝之后不能指望还有唤醒——`decision.rejected` 与监督 Attempt 的结束都不是唤醒（supervise.rs:20-33 的 KINDS），decide 只为 STALE_REVISION、STALE_ROLE_EPOCH 写重新触发（decide.rs:287-298）；T2 正常结束而不提结束决定时，两个唤醒都已结清，Run 停在工作态，前台客户端等不到结果。所以拒绝的提交（`decide_in` 的拒绝分支，decide.rs:279-312，同一事务）另写 `supervisor.retrigger{decision_id, reason: "ILLEGAL_TRANSITION", until: "quiet", to, unfinished, base_fingerprint: "run_end", spec_revision}`——只对这一种拒绝写：`transition_run` 的安静判定在它的 `Rejection`（decision.rs:321-324）上加一个 `not_quiet` 标记，其余 ILLEGAL_TRANSITION（非法的边等）不写——事件 id 与过期的重新触发相同（`child_id(decision_id, "retrigger")`，decide.rs:320 起；一条决策只因一个原因被拒，重放什么也不写，所以每条被拒的决策恰一条）。这个种类已在唤醒集合中（REQ-021 行为 6 的重新触发），不新增唤醒种类。`classify`（crates/hoh-core/src/supervise.rs:114 起）对 `until = "quiet"` 的载荷以 `run_end#quiet` 为键（`#quiet` 与 `#retrigger` 一样是 Runtime 的后缀，普通指纹的 `#` 已转义，supervise.rs:155-160），所以一个 Run 的多次拒绝并入同一个 PENDING 触发器（同键至多一个 PENDING，001_initial.sql:45-47）。步骤的 `fire`（persistence/supervise.rs:586 起）在 Fire 的状态下把键以 `#quiet` 结尾的触发器留作 PENDING，**在既已到期（`due_at` ≤ now；High 为最后一条事件之后 2 s、至迟首条之后 10 s，crates/hoh-core/src/supervise.rs:12-15、:199-204）又在同一事务里 `retry::unfinished_attempts(tx, run)` 为 0 的第一个步骤**才触发它（M2T13D-150）：它成为欠下的唤醒，分配（wakes.rs:845 只跳过有 turn 在途的 Run）给它一个新 turn，turn 的上下文带着这条事件（被拒的决策、目标状态、当时未结束的 Attempt 数），Commander 在安静的 Run 上重新决定。每个未结束的 Run 每 tick 都跑一次步骤（runner.rs:502-507 的被监督列表、host/runner.rs:759），所以义务在最后一个 Attempt 结束之后、触发器到期的第一个 tick 触发（到期早于结束时即结束后的下一个 tick；Attempt 短于去抖时等到到期），不依赖别的事件；它是持久的事件与触发器行，host 重启后照样（游标之后的事件重新纳入，supervise.rs:305 起）。Run 先结束（另一个 turn 的结束决定被应用）时，它随结束提交的 (1) SUPERSEDED；Run 进入 Hold 时保留到离开。安静之前它不触发，所以工作 Attempt 运行期间不会每 tick 分配一个 Commander turn 再被拒一次。revision 与 epoch 的栅栏不变：新 turn 的决策照常带它读到的 expected_revision 与 role_epoch。
   - **尾部并入终态的提交**：进入 COMPLETED、FAILED、CANCELLED 的提交在本提交自己的事件之后、run.result 之前（所以正被处置的那条输出已有它的 `decision.applied`，不算等待），把监督器本会在之后写的东西在同一事务按序写完：(1) 该 Run 的 PENDING 触发器置 SUPERSEDED 与欠下的唤醒的 `supervisor.superseded`（supervise.rs:670-698 抽成 `supersede_in(tx, run, state)`）；(2) 等待处置的输出写 `output_disposed{superseded}`（outputs.rs 抽成 `supersede_in`）；(3) 在同一事务里（看得见 (1)(2) 写下的行）求 `close` 的谓词——没有 PENDING 触发器、没有既未结清也未 SUPERSEDED 的唤醒、没有等待处置的输出、上次 `supervisor.closed` 之后有 `supervisor.woken` 或 `supervisor.output`（supervise.rs:185-243 的条件抽成 `close_due(tx, run) -> Option<last>`，`close` 与合并共用）——成立即写 `supervisor.closed{state, at}`，事件 id 与 `close` 的相同（`supervisor/closed/<last>`）。没有过监督（没有 woken、output）的 Run 谓词不成立，照旧不写。写下之后该 Run 不会再有 woken 或 output（守卫），close 的谓词对它不再可能成立，监督步骤与处置步骤对它无事可做，不写。runner 选择被监督的 Run 时（runner.rs:502-507）另外排除处于 T 且最新事件是它进入 T 时的 run.result 的 Run：结束提交已把待办的 supersede 并关闭，之后任何步骤也不能再为它写事件（守卫），不再每 tick 试一次。`wakes::advance_horizon`（wakes.rs:1607-1670；今天由步骤与处置在 `close` 之后调用，supervise.rs:123-131、:158-171）**有意不并入**：地平线只限定活着的 Run 每个 tick 的工作量（ADR-025 第十九、二十版），结束的 Run 不再被选，合并的 supersede 使地平线前移也不必记录。**INCOMPLETE 不并入**：它对监督与处置是 Hold（supervise.rs:530-541、:672，outputs.rs:278-283），欠下的义务原样保留到 Run 离开 INCOMPLETE；Hold 期间这两个步骤不写该 Run 的事件（含地平线，下下条）。
   - **结束 Run 的处置批在结束提交之后停下（M2T13D-06）**：`outputs::dispose` 在循环之前取出待处置的列表（outputs.rs:223-255），每项一个事务（:256 起）；一个 dispose 是写者的一个 job，写者串行执行 job，所以批内只有本批自己的处置能改变 Run 的状态。某项的决策使 Run 进入 T 时，结束提交已把仍在等待的输出写成 `output_disposed{superseded}`（上条的 (2)），缓存列表里的下一项再写 `<output_id>/disposed` 会被守卫以 `RunEnded` 拒绝或撞上重复的事件 id。所以：每项在它自己的事务里读 Run 的状态（今天已读，:268-282），处于 T 即结束本批、返回“没有剩余”，不写；每项另先核对它的输出仍在 `outputs::waiting` 中（还没有它的 `output_disposed`），不在即跳过。`supervise::dispose`（persistence/supervise.rs:147-180）在 `outputs::dispose` 返回之后，于收尾维护的事务里读 Run 的状态：处于 T 或 Hold 时不调用 `close` 与 `advance_horizon`——结束的 Run 的关闭已并入，Hold 见下一条。
   - **Hold 也挡住地平线（M2T13D-04）**：监督步骤在 Hold 时仍调用 `wakes::advance_horizon`（supervise.rs:123，在 `fire` 于 :672 返回之后），处置返回之后也调用（:166），而它不看 Run 的状态（wakes.rs:1607-1670）。旧唤醒已结清、较新唤醒的 turn 已 SETTLED 而输出待处置时，预算停止先写下 INCOMPLETE 的 run.result，同一 tick 随后的监督（host/runner.rs:752 的 pace 在 :759 的监督之前）仍会越过旧唤醒写 `supervisor.horizon`，破坏 E2 与 AC-004-02 的 seq 集合相等。改为 `advance_horizon` 先在它的事务里读 Run 的状态：PAUSE_REQUESTED、PAUSED、INCOMPLETE（Hold）与 T 中的状态返回 None。两条调用路径与今后的调用方都经过它；判定与写入在同一事务，所以 tick 开始时算出的被监督列表（runner.rs:502-507）或已经开始的 job 也越不过它。地平线只限定活着的 Run 每个 tick 的工作量（ADR-025 第十九、二十版），Hold 期间不前移只多读几行；Run 离开 Hold 之后的第一个步骤照常前移。
   - **守卫（只看 T）**：写者连接上装一个临时触发器（与 `guard_append_only` 同一处安装，persistence/mod.rs:519 起）：插入 run_id 为 R、kind 不是 `run.result` 的事件时，若 R 处于 T 且 R 的最新事件是 `payload.state` 在 T 中的 `run.result`，以固定消息 RAISE(ABORT)，映射为 `PersistError::RunEnded(R)`（HTTP 409 ILLEGAL_TRANSITION）。要看那条结果的 state，而不只是“R 处于 T 且最新事件是 run.result”：`writer::write` 先做全部 CAS 再插事件（writer.rs:1151-1153），一个从停留态直接进入 T 的提交（迁移表允许 BLOCKED、PAUSED、INCOMPLETE→FAILED，lifecycle.rs:226-263；今天只有 Commander 从工作态决定 FAILED，但不应依赖它）在插入自己的事件时，R 已处于 T 而最新事件是停留态的旧 run.result，只看后者会误挡。T 没有出边，所以它不挡任何合法的后续；M2-T13 之前就已结束、没有 run.result 的 Run 不受它挡。它覆盖一切插入事件的路径（writer.rs:1130、:1165，candidates.rs:135，evidence.rs:254，issues.rs:54，reports.rs:605），不必逐个改。
   - **INCOMPLETE 不受守卫，由构造与测试守住**：受理的命令必须能在 INCOMPLETE 的 run.result 之后写事件，而触发器分不出一条事件出自哪个命令。所以：(1) Runtime 的步骤在 INCOMPLETE 期间不写该 Run 的事件——监督、处置与地平线 Hold（上面三条），`close` 只处理 Supersede 的 Run（supervise.rs:200），pace 跳过 INCOMPLETE（retry.rs:482-486），每 tick 的工作 Run 只取 RUNNING、VERIFYING、WAITING_EXTERNAL、BLOCKED（runner.rs:480-484），唤醒分配与 staffing 不选 INCOMPLETE（wakes.rs:777-779，staffing.rs:119）；S1 的性质测试找出其余的（支撑测试“守卫”）。(2) 之后的事件只来自受理的命令：ResumeRun（决定 16，CR-023）——它的提交先做 CAS 离开 INCOMPLETE、再插事件（writer.rs:1151-1153），所以它的 `reconcile.run` 与受理事件都在 Run 离开 INCOMPLETE 之后；SendInput/AnswerQuestion——像对 BLOCKED、PAUSED 一样受理（决定 7），提交以 run.result 结尾（E3），所以停留的 Run 的最新事件又是它的 run.result。
   - 已知会在终态之后写事件的，除上面并入的三项，按“对终态的 Run 无事可做”跳过它们（每个按 Run 遍历的对账、清扫只选不在 T 中的 Run，对 INCOMPLETE 的 Run 按 Hold 不写）；S1 的守卫测试与性质测试逐个找出（见“实施切片”S1），找出的写者若确有必须在终态或 INCOMPLETE 之后写的内容，写一份设计更正，不放宽守卫。

5. **RunResult 的计数与成本（Q4 (a)，CR-020）。**
   - spec = runs.spec_id；`spec_revision` 为它的 revision，没有规格为 null。
   - `total` = 该 spec 的全部需求数；`accepted` = 该 Run 每个 ACCEPTED 候选的 `requirements_passed(tx, run, spec, c)` 之并与该 spec 需求之交的大小（ADR-029 决定 12；它已要求候选的 spec 摘要等于 Run 当前 spec 的摘要，所以只数“在它之下”接受的；ADR-029 决定 5：只在候选 ACCEPTED 时计数）；`remaining_requirements` = spec 的需求减去 accepted 的部分，升序、各一次，长度 = total − accepted；spec 为 null 时 0、0、[]。不用 `AcceptanceView` 的按 AC 计数。
   - `requirements_passed` 已接受 `&Connection`（事务可解引用为它），改为 `pub(crate)`；`run_cost` 的 SQL 抽成接受 `&Connection` 的函数，`Reader::run_cost` 调用它；`results::compute` 用这两者。cost_usd/cost_status 照 CR-009：价格未知即 null 与 unknown，从不估算。

6. **待答问题（Q7 (a)）。** 问题不是物化的表，是函数 `questions::open(tx, run) -> Vec<Question>` 的值，按出现的 seq 升序：
   - **Commander 的**：每个仍被持有的声明 `commander:<decision_id>` 对应一个；question_id = decision_id；text 为 payload.question，choices 为 payload.choices（choice_id、label），没有缺省选项。`person()`（outputs.rs:524-570）在同一提交写 `question.asked{question_id, commander_question_id, question, choices, requires_user}`，所以 AC-002-01 的“events 含问题原文”是这条事件的 `payload.question`（测试解析 JSON 比较，不做子串匹配）。requires_user=false 的请求照样阻塞：可由默认值决定的事项应由 Commander 写 record_assumption（REQ-002 行为 4，resources/prompts/commander.md 已这样要求）。
   - **Run 级的 Runtime 问题**：声明 `runtime:no_spec`（决定 1）；question_id 为它的 `question.asked` 事件 id；选项 `adopt`。
   - **Task 级的 Runtime 问题**：Run 中每个 BLOCKED 且 blocked_reason 为 NEED_DECISION 的 Task 一个，由它的**锚点**——一条 `need_decision` 事件——定义：Task 有未清除的修复拒绝（`verification::refused`，verification.rs:373-392：最近一次 `repair.refusal_cleared` 之后、原因为 local_repairs_exhausted、protocol_repairs_exhausted 或 reverify_exhausted 的 need_decision）时，锚点是其中最新的那条；否则是它最近一次被阻塞之后的那条 need_decision。question_id = 锚点的 event_id；`reason` 取锚点的 `reason`，**从不改写**（第二版以 `repair_refused` 覆写它，丢掉了轮次链耗尽的 reverify_exhausted——`refused` 包括它，由 retry.rs:982-1004 的 `repair_in` 与 closing.rs:1604-1658 的 `reverify_source` 写下——使决定 8 的 reverify 出口不可达，也使验证者的耗尽无法路由，M2T13D-02）；“尚有未清除的修复拒绝”是单独的字段 `refusal: bool`；`subject` 为 `verifier`（`verification::round_of_task` 找到它是某轮的 qa 或 reviewer Task，verification.rs:300 起）、`source`（锚点的原因为 join_gate_refused、reverify_exhausted 或 flaky 的非验证 Task）或 `work`（其余）；问题带锚点载荷中的 round_id、round_root、join_id、candidate_id（有则带），source 另带它的当前轮次（`closing::current`，closing.rs:1351）与该轮候选的状态；选项按决定 8 的表由 (reason, subject, 候选状态) 决定。拒绝未清除时 Task 的再次阻塞——completion.rs:119-127 的 `need_decision{repair_refused}`、runner.rs:631-681 的 `runner.refused`、closing.rs:742-768 的 `task.blocked{refusal_holds}`——不另成问题：锚点仍是拒绝的那条，问题与选项不变。**每个在没有未清除的拒绝时把 Task 置为 BLOCKED(NEED_DECISION) 的写者都在同一提交写 need_decision**——更正 A 的写者清单 W1–W12 逐个列出它们与它们产生的 (subject, reason)——由守卫与性质测试守住（E4、E16）；上面几处再阻塞只在拒绝未清除时发生，由锚点的第一种情形覆盖，不需补写。

7. **答复：AnswerQuestion 与 SendInput（Q7、Q9 (a)）。** host 受理两种命令（不再 422）；每个在一个 IMMEDIATE 事务里（commands.rs 新的 `RunTarget::Input`）：
   - 先判：Run 存在（否则 409 RUN_NOT_FOUND，与今天的 store_error 一致）、不在 T（COMPLETED、FAILED、CANCELLED；否则 409 ILLEGAL_TRANSITION“Run 已结束”，`details: {state}`——客户端据 `details.state` 而不是 message 的文本判 64，决定 9，M2T13D-54；INCOMPLETE 与 BLOCKED、PAUSED 一样受理）、`expected_revision` 等于 Run 的 revision（否则 409 STALE_REVISION）。
   - **AnswerQuestion{question_id, answer, choice_id}**：问题须在 `questions::open` 中（否则 409 ILLEGAL_TRANSITION“问题 … 不是待答的”）；`choice_id` 给出时须是该问题的选项之一（否则 400 BAD_REQUEST）；为 null 时，答复文本去掉首尾空白后与某个选项的 choice_id 或 label 相同（不分大小写）即选它，否则取缺省选项（Runtime 问题的第一项；Commander 问题为自由答复）。然后按决定 8 应用出口。
   - **出口的前提**：决定 8 中注明前提的出口（INVALID_HANDOFF 的重建、SESSION_NOT_INDEPENDENT 的换代、reverify），前提在本事务中不成立时整个命令以 409 ILLEGAL_TRANSITION 拒绝，`details: {question_id, precondition, detail}`，什么也不写，Task 仍 BLOCKED、问题仍待答（E5、E13）：从不迁到一个下一次 admission 必然再拒的 READY（M2T13D-03）。SendInput 作为唯一问题的答复时同样被拒。
   - **SendInput{text, target_role, input_kind}**：input_kind 为 REPLY、target_role 为 null、且 `questions::open` 恰有一个（两类合计）时，等价于 AnswerQuestion{该问题, answer = text, choice_id = null}，另写 `input_queue` 行（kind REPLY、state APPLIED、payload {text, question_id}）；否则写 `input_queue` 行（REPLY 按 REQ-002 决定改记为 STEER；其余照给定的 kind）state QUEUED——STEER/ASK/CHANGE 的投递与交给 Commander 是 M3-T04 的（ADR-025 决定 10 的移交），本任务只持久受理。
   - 事件：本提交的第一条是受理事件 `input.accepted{command_id, input_id, kind, question_id|null}`（AnswerQuestion 为 `question.answer_accepted{command_id, question_id}`），带 command_id（决定 9 据此找它）；答复另写 `question.answered{question_id, source, task_id, reason, choice_id, answer, command_id, exit}`。每个受理的这两种命令都推进 Run 的 revision（迁移或 Touch），并把 Run 放进 `Commit.results`：提交之后 Run 若处于停留态即带 run.result（E3）；Run 回到工作态则不写，之后再进入 E 时由决定 3 写。
   - **Commander 问题的出口**：decisions 行 PROPOSED→APPLIED，写 `decision.applied{decision_id, kind: "request_user_decision", answered_by: command_id}`（不带 output_id，不影响输出的处置谓词，outputs.rs:86-130）；释放声明 `commander:<decision_id>`；`blockers::follow` 在集合空时 `Change::Unblock` 回 resume_state，否则 Touch（Run 为 PAUSED 或 INCOMPLETE 时 follow 不迁移它，blockers.rs:257：Run 留在原状态，revision 由命令的 Touch 推进）；唤醒 Commander：写 `need_decision{run_id, reason: "answered", question_id, decision_id, answer, choice_id, fingerprint: "answer/<decision_id>"}`——need_decision 属于 REQ-021 行为 1 的封闭集合（High），唤醒的上下文带整条载荷（persistence/context.rs:495-545），所以答复进入下一 turn（Run 为 PAUSED 或 INCOMPLETE 时，它的触发器在 Hold 中保留到 Run 离开该状态）。不新增唤醒种类。
   - **Runtime 问题的出口**之后，在同一事务按 pace 的同一谓词重算 PACE 声明（retry.rs:680-693 的停滞判定抽成 `retry::stall_reasons(tx, run, at)`，pace 与答复共用）：答复让 Task 能动时声明清空、Run 在同一提交 Unblock，不会先写一条 BLOCKED 的结果再在下一 tick 解除。
   - **解除之后的继续（更正 B）**：答复使 BLOCKED 的 Run 解除回到 W 时，写者按 E15 追加 `run_resumed` 的重新触发——Commander 问题的答复本提交已有 `need_decision{answered}`，不另写；Runtime 问题的答复在没有在途 Attempt、PENDING 触发器与欠下的唤醒时写——所以解除之后下一个 Commander turn 不依赖别的唤醒。

   - **修复拒绝（M2T13D-02、-62）**：问题的 `refusal` 为真时，**每一个**出口（含 cancel 与 redispatch）都在迁移 Task 之前于同一事务调用 `clear_repair_refusal_in(tx, task, command_id)`（写 `repair.refusal_cleared{task_id, decision_id: command_id}`；`Store::clear_repair_refusal`，persistence/mod.rs:1444-1465，改为它加一个事务的包装）。答复之后该 Task 不再在 `verification::refused` 中，所以调度轮（rounds.rs:91）、派发（runner.rs:631）、完成（completion.rs:119）与对账（closing.rs:742）都不再按拒绝挡它；第二版只在一般 rework 行清除，reverify 与验证者的 redispatch 之后 Task 仍会被挡住。done_when 的“同一事务调用 `Store::clear_repair_refusal`”由此满足：那个包装自带事务，在答复里直接调用它就不是同一事务。

   - **SESSION_NOT_INDEPENDENT：换到独立的 HoH 会话（M2T13D-03）**。admission 比较的是该角色绑定的 HoH 会话（role_bindings.session_id，rounds.rs:146-153）与源 Attempt、Commander、Developer、另一验证者的会话（`conflicting_sessions`，verification.rs:617-642）；新 Attempt 照旧继承绑定的会话（`lease_task`，decide.rs:543-555），验证者每次新起的只是原生会话（team.rs:897-901），消不掉 HoH 会话的冲突。HoH 会话 id 由 run、角色与 epoch 导出（`team::session_id`，team.rs:1010-1012），所以换会话就是换代：答复的事务按 staffing 的 Rebind（persistence/staffing.rs:577-599：`apply` 以 `Cause::Rebind` 把绑定移到下一 epoch——同一 agent 与 model，会话置空，ACTIVE，写 `team.binding_applied{cause: "rebind"}`——再以 `handover` 写该 epoch 的交接）把该验证角色的绑定移到 epoch+1。之后 staffing 以 `bind_session`（team.rs:1091 起）授予 `session_id(run, role, epoch+1)`，admission 把旧 epoch 的交接在新 epoch 重新签发（verification.rs:560 起），同一角色其余轮次的交接在各自的 admission 里同样处理，与任何换代之后相同（ADR-024、ADR-030）。前提：该角色在本 Run 没有未结束的 Attempt（staffing 对在途的角色只写待定的变更，staffing.rs:578-587；答复不排队），且新 id 不在本事务算出的 `conflicting_sessions` 中；不成立即按决定 7 拒绝答复。

   - 汇合级与轮次级的问题（source 的各行）不提供 cancel，也没有“在同一编号下回到 VERIFYING”的出口：done_when 只给重新验证与返工，二者都产生新的栅栏编号（E6，CR-020）。要放弃可以取消整个 Run。
   - **Task 迁移表加 BLOCKED→VERIFYING**（crates/hoh-core/src/lifecycle.rs:303 的 `Blocked` 一行与 ADR-011 的 Task 表；没有它 reverify 在 CAS 处被拒，M2T13D-61），只供答复的 reverify 出口：Runtime 专用（不进 `COMMANDER_TASK_MOVES`，decision.rs:360-368），条件是 Task 当前轮次的候选为 VERIFYING、该轮已关闭、同一事务为它开下一轮；迁移之前 blocked_reason 已清。没选“回 READY 再要求同内容冻结”（未采用 1）。

9. **前台 `hoh -p`（Q6 (a)、Q14 (a)）。**
   - **之前**：用法错误照旧在任何连接之前判定（cli.rs）。`hoh_core::config::load(项目)` 在连接之前：文件存在而无效即 78，stderr 指出文件与位置，stdout 0 字节，不启动 host（REQ-001 失败模式 4、REQ-004 失败模式 4）；缺文件取默认。mode 取配置的 `default_mode`（缺省 AUTO），detach 同样（修 session.rs:57）。`ensure`（client.rs:216 起）失败照旧 69（DB_ON_NETWORK_FS 为 78）。
   - **`--resume K`**：项目没有 `.hoh/state.db` 即 64 RUN_NOT_FOUND，不启动 host（与 session.rs:120-131 相同）；否则 `GET /v1/runs/K`：404 → 64 RUN_NOT_FOUND；读到的 `state` 在 T（COMPLETED、FAILED、CANCELLED）→ 64，stderr“Run 已结束（<state>），不能重开；请新建 Run”，不提交命令（64 只由状态判定，M2T13D-54）。其余状态（工作态、WAITING_EXTERNAL、BLOCKED、PAUSED、INCOMPLETE 等）提交 SendInput{text, target_role: null, input_kind: REPLY}，`expected_revision` 取刚读到的 revision；STALE_REVISION 时重读再交，至多到 `client::WAIT`（10 s）；INCOMPLETE 之后另提交 ResumeRun（下文）。`--detach --resume K` 走同一提交，受理后输出 202 体（json）或 run_id（text）并退出 0（修 main.rs:204-220）；Run 为 INCOMPLETE 时同样在 SendInput 之后提交 ResumeRun，输出最后一个被受理的命令的 202 体，ResumeRun 因停止项被拒时 stderr 写明（同下文），仍以 0 退出（输入已受理）。
   - **FAILED、CANCELLED 的 64 是对 REQ-002 失败模式 3 的解释（M2T13D-56；设计审查第 1 轮两名审查者都接受）**：REQ-002 失败模式 3 与决定 3 只写 COMPLETED（docs/05-data-api.md:13 同样只说 COMPLETED 不得重开）。本 ADR 把“不得重开”解释为覆盖另外两个终态：它们同样没有出边（REQ-036 行为 3，lifecycle.rs:264，ADR-011:40），对它们的 SendInput 无论如何会被决定 7 以 409 ILLEGAL_TRANSITION（`details.state` 在 T 中）拒绝，而那个拒绝在 `submit` 中也映射为 64（见“提交的拒绝”）；客户端只是把这个必然的拒绝提前到提交之前。不新增或删去命令、不改变任何状态、没有可重开的出边被关上，所以不是范围或交互的改动。
   - **`--resume` 到 INCOMPLETE 的 Run（决定 16，CR-023；M2T13D-07、-50）**：先照常提交 SendInput（决定 7：恰有一个待答问题时作为它的答复，否则以 STEER 排队，QUEUED，M3-T04 投递）；它的提交以 run.result{INCOMPLETE} 结尾（E3）。受理之后再提交 ResumeRun{expected_revision = SendInput 的 202 体中的 revision}（STALE_REVISION 时重读再交，至多到 `client::WAIT`）。先答复后恢复：答复在 INCOMPLETE 中释放的声明不会让恢复先落到 BLOCKED。ResumeRun 受理时，客户端改以它的受理事件为 A 跟随（E7）：Run 回到 resume_state（阻塞集合非空时到 BLOCKED，带 run.result），之后与任何跟随相同。ResumeRun 以 409 ILLEGAL_TRANSITION 拒绝且 `details.state` 为 INCOMPLETE、带 `details.stop` 时（使它停下的预算或期限仍耗尽，决定 16），A 仍是 SendInput 的受理事件，客户端以它之后的那条 run.result{INCOMPLETE} 退出 4；stderr 写明输入的去向（“已答复问题 <id>”或“已排队，待 M3-T04 投递”）、仍耗尽的预算项与剩余需求，并说本版本没有提高一个 Run 的预算或期限的入口（二者只在 StartRun 写入，persistence/team.rs:85-135），请以 `hoh -p` 新建 Run 继续剩余需求。
   - **提交的拒绝**（`client::submit`，client.rs:792-839）：400 INVALID_TEAM_CONFIG → 78；404/409 RUN_NOT_FOUND → 64；409 ILLEGAL_TRANSITION 且 `details.state` 在 T 中 → 64（Run 在 GET 与提交之间结束）；ResumeRun 的 409 ILLEGAL_TRANSITION 且 `details.state` 为 INCOMPLETE → 上一条的处理；其余 409（问题不是待答的、出口的前提不成立，决定 7）→ 1，stderr 写出 message 与 details；503 照旧 69；其余照旧 1。码只由状态码、错误码与 `details` 判定，从不匹配 message 的文本（M2T13D-54：否则“问题不是待答的”等别的 409 会被误判为 64）。json 模式的一切失败 stdout 为 0 字节。
   - **跟随**：受理后从 `after` 打开该 Run 的事件流——StartRun 与 stream-json 从 0（stream-json 要输出全部事件），json/text 的 `--resume` 从 GET 时的 watermark（受理事件必在其后）。`payload.command_id` 等于客户端**最后一个被受理的命令**（SendInput，或其后受理的 ResumeRun）的第一条事件即受理事件 A；**只以 seq > A.seq 的第一条 `run.result` 决定结束与退出码**（REQ-002 决定 CR-003，E7）；202 体受锁、不含 seq，不为它写 CR（未采用 6）。host 重启时照旧在 `last` 之后续读（session.rs:249-262）。WAITING_EXTERNAL：见到 `run.waiting` 即在 stderr 写“等待外部恢复，下次重试 <next_retry_at>”。
   - **退出**：码取 run.result 的 `exit_code`。退出码为 3 且原因是 NEED_DECISION 时，stderr 列出 `projection.questions`（id、原文、选项）与提示 `hoh -p '<答复>' --resume <run_id>`。SIGINT/SIGTERM/SIGHUP：130/143/129，stderr 写 run_id 与 `hoh attach <run_id>`，不发任何命令（REQ-004 失败模式 2，E8）；受理之前收到信号时只说没有提交成功或已提交的 run_id（若已知）。
   - **不读 stdin**：`-p` 的路径从不打开、读取或轮询 stdin，也不改终端模式（REQ-002 行为 2）；有 TTY 时同样不进 alternate screen。

10. **输出（Q5、F5）。**
    - **json**：stdout 恰为 run.result 的载荷（RunResult）加一个 LF；之前什么也不写。
    - **text**：stdout 只有一行 `<run_id> <state>`，BLOCKED 时再加 ` <blocked_reason>`，INCOMPLETE 时再加 ` 剩余 <remaining_requirements 以逗号连接>`；进度（`#seq kind`）写 stderr。任何模式都不输出 ANSI 转义。

    - host 的 `event_json`（http.rs:1255-1267）的 `attempt_id` 取载荷中字符串型的 `attempt_id`，否则 null（Event 允许 string|null，不需 CR）。

## 不变量

- **E1** Run 每次经 `Change::Run` 进入 E 的提交里恰有一条该 Run 的 `run.result`，是该事务中该 Run 的最后事件；载荷合 `$defs.RunResult`，`last_event_seq` 等于它自己的 seq，`exit_code` 按 REQ-004 的表，`blocked_reason` 恰在 BLOCKED 时非空。
- **E2** 进入 T 或 INCOMPLETE 只在该 Run 没有任何未结束的 Attempt（工作与监督）时；被这一条拒绝的结束决定留下再决策的义务（E12）。Run 处于 T 且最新事件是它进入 T 时的 run.result 时，不再有该 Run 的任何事件（守卫拒绝；监督的收尾——superseded、output_disposed 与谓词成立时的 supervisor.closed——已并入进入 T 的提交，当次处置批在结束提交之后停下、不做收尾维护，runner 不再选它，决定 4）；Run 处于 Hold 的状态（PAUSE_REQUESTED、PAUSED、INCOMPLETE）时，Hold 只覆盖三样：监督触发器的触发、输出的处置与 `supervisor.horizon`，判定在写入的事务里（M2T13D-102）。PAUSE_REQUESTED 中在途的 Attempt 照常结束并持久化它的结果（settle、完成、重试的判定），暂停控制照常写——`pause_step`（control.rs:213-279）撤回未开始的派发，在不再有 STARTING/RUNNING 的 Attempt 时写 `run.paused` 与 PAUSED（安全点暂停，REQ-043 行为 1）；所以 PAUSE_REQUESTED 期间该 Run 仍有 Runtime 的事件。**run.result 之后的限制只对 INCOMPLETE 与 T**：INCOMPLETE 只在安静时进入（决定 4），之后 Runtime 的步骤不写该 Run 的事件（Hold 加上 pace、调度轮、唤醒分配与 staffing 都不选它，决定 4），之后的事件只来自受理的命令（ResumeRun 先以 CAS 离开 INCOMPLETE，决定 16；SendInput/AnswerQuestion 的提交以 run.result 结尾，E3），由测试守住。所以客户端在 T 或 INCOMPLETE 的 run.result 处退出时，它的 stream-json 行与该 Run 在 DB 中的事件 seq 集合相等（INCOMPLETE 的 Run 到下一个受理的命令为止）。
- **E3** 受理的 SendInput/AnswerQuestion 的提交之后，Run 处于停留态（BLOCKED、PAUSED、INCOMPLETE）即该提交带 run.result，停留的 Run 的最新事件因而又是它的 run.result；Run 回到工作态则之后再进入 E 时有 run.result。所以每个受理的命令之后，客户端要么等到一条 seq 更大的 run.result，要么 Run 仍在工作。
- **E4** 待答问题只是 `questions::open` 的值；每个 NEED_DECISION 的来源（Commander 声明、`runtime:no_spec` 声明、BLOCKED(NEED_DECISION) 的 Task）恰对应一个问题；每个 BLOCKED(NEED_DECISION) 的 Task 恰有一个锚点（有未清除的修复拒绝时为拒绝的那条 need_decision，否则为它最近一次被阻塞之后的那条），问题的 reason 是锚点的原始 reason，未清除的拒绝只体现为 `refusal`，从不改写 reason；锚点的 (subject, reason) 是更正 A 写者清单的 22 对之一。
- **E5** 一个答复是一个事务：命令行、受理事件、出口的迁移、（Task 有未清除的修复拒绝时，任何出口）`repair.refusal_cleared`、声明的释放与 Run 的迁移、PACE 的重算、run.result（若停留）；任一项失败或出口的前提不成立都全部回滚，命令未受理、问题仍待答。
- **E6** 轮次级与汇合级问题的每个出口都产生新的栅栏编号：reverify 使候选上的轮数加一，rework 产生新的候选；同内容守卫看轮次与汇合的 flaky；没有在已汇合的编号下回到 VERIFYING 的出口（ADR-029 J9）。
- **E7** 前台客户端的退出码只来自 seq 大于它最后一个被受理的命令（SendInput，或其后受理的 ResumeRun）的受理事件的 run.result，或 130/143/129（信号）、64（用法、Run 不存在或处于 T——由读到的 state 或 409 的 `details.state` 判定，不看错误文本）、69（host）、78（配置）、74（输出失败）、1（命令被拒而不属上述情形）；json 模式只有在输出 RunResult 时 stdout 非空。
- **E8** `-p` 从不读 stdin；`-p` 与 attach 的跟随从不发 CancelRun/PauseRun，信号只退订。
- **E9** stream-json 的每行合 `$defs.Event`（CR-022 之后含可选 replay），seq 严格递增，U+2028/2029 转义，无 0x1B；stdout 只有结果数据，原生 stderr 与进度只走 stderr，stderr 阻塞不阻塞 stdout 的进展。
- **E10** create_tasks 只经 `plan::check` 与 `import_in`：无效计划什么也不写入 tasks/decisions；有效计划与决策同一事务。
- **E11** 打开 TUI、列出 Run、附着与脱离不写任何行（只读与订阅）；Enter 之前不写 commands/input_queue；`/` 命令不提交 StartRun。
- **E12** 被安静条件拒绝的每个结束决定在同一提交写一条 `supervisor.retrigger{until: quiet}`；一个 Run 至多一个 `run_end#quiet` 的 PENDING 触发器，它在 Run 有未结束的 Attempt 时不触发，在既已到期（`due_at`）又安静的第一个步骤触发（Run 先进入 T 时被 supersede，Hold 时保留）。所以被拒的结束决定在 Run 安静之后总会得到一个新的 Commander turn，不依赖别的唤醒，也不在 Attempt 运行期间反复分配 turn。
- **E13** 答复的 redispatch 之后，下一次 admission 不会以同一原因再拒：INVALID_HANDOFF 的出口留下一条通过同一检查的当前交接，SESSION_NOT_INDEPENDENT 的出口留下下一 epoch 的绑定；做不到时答复被拒、Task 仍 BLOCKED、问题仍待答，从不迁到必然再拒的 READY。
- **E14** ResumeRun 对四种停止状态是同一条规则：先 reconcile；该状态自己的停止谓词（PAUSED 没有；INCOMPLETE 为预算或期限；WAITING_EXTERNAL 为重试未到期；BLOCKED 为阻塞集合非空）仍成立即 409、`details` 写明、什么也不写；否则阻塞集合非空时到 BLOCKED（带 run.result），空时到 resume_state 并按 E15 留下继续义务。
- **E15** （更正 B）一个提交把 Run 从停止状态移进 W，而提交之后该 Run 没有未结束的 Attempt、没有 PENDING 的触发器或欠下的唤醒、本提交也没有唤醒 Commander 的事件时，同一提交有一条 `supervisor.retrigger{reason: RESUMED}`（键 `run_resumed#retrigger`）；唯一的例外是 pace 在重试到期时放回 WAITING_EXTERNAL 的 Run。所以每次回到工作态之后，下一个 Commander turn 不依赖之后的任何唤醒，跨重启亦然。
- **E16** （更正 A）Task 级问题的 (subject, reason) 恰是写者清单的 22 对之一，每一对在决定 8 中有出口；`questions::route` 对 (Subject, Reason) 穷举且不为 Impossible 的对等于 `questions::PRODUCED`；Task 阻塞的 need_decision 只经 `need::task_event` 构造。答复不清零任何计数。

> # CR-023 · ResumeRun 从停止状态恢复的例外边界与它的承接
>
> 基线：修改受锁文件 `contracts/requirements.json`（REQ-036 的第 2 条决定）与不在锁内的 `contracts/development-tasks.json`（M2-T13、M2-T11 的 done_when），重新上锁。

> 背景：REQ-036 的决定写明“INCOMPLETE/BLOCKED/WAITING_EXTERNAL/PAUSED 可经 ResumeRun 回到 resume_state”，行为 3 要求“恢复回到 resume_state 并先 reconcile”，REQ-036 属 v0.1 与 v1 的 required 范围。这条决定与另外几条受锁的规定冲突：REQ-042 行为 6 规定预算耗尽或 deadline 到达即停止新派发、Run=INCOMPLETE，行为 2 规定 `next_retry_at` 之前不得派发；ADR-011 与 docs/06（CR-003）规定 Run 进入任何工作态都要求阻塞集合为空。照字面实现，预算仍耗尽的 INCOMPLETE、重试未到期的 WAITING_EXTERNAL 被 ResumeRun 放回工作态之后，pace 会在下一 tick 把它停回去，中间没有任何工作，只多一对状态与结果（ADR-031 未采用 18）；BLOCKED 则根本不能在阻塞集合非空时回到工作态。本版本没有提高一个 Run 的预算或期限的入口（二者只在 StartRun 写入）。另外，REQ-036 的 AC-036-01..04 分属 M2-T02、M2-T05、M2-T16、M2-T12，没有一条覆盖从这四种状态的 ResumeRun，产品今天只从 PAUSED 恢复（ADR-021 决定 7），没有任务的 done_when 承接它。ADR-031 的设计审查第 1 轮（M2T13D-07、-50）要求承接有契约载体，第 2 轮（M2T13D-151）要求例外边界写进受锁的决定本身，使受锁文本与 done_when 一致。

22. **回到工作态之后的继续的其他做法**（M2T13D-101）：只在 ResumeRun 写——答复与 Runtime 的解除回到 Commander 推进的阶段时同样卡住；新的唤醒种类 `run.resumed`——REQ-021 行为 1 的集合封闭，要 CR，而 `supervisor.retrigger` 已在其中；每次回到工作态都写、不看在途 Attempt 与已有的触发器——已有触发器或在途 Attempt 时多出无用的 Commander turn，pace 的重试到期还会每次都多一个；把 Commander 推进的阶段交给 Runtime 自动推进——那是 M3 的规格流程（决定 1）。
