## 待所有者确认（Q1、Q2）

两项牵涉 CONTRACT 第 4 条“非交互自动规划不是跳过规格”的解释与 M2 的范围，本 ADR 按预研清单的建议写成决定 1、2，**在所有者确认前不算最终决定**。

- **Q1 `hoh -p` 新建的 Run 从哪里得到规格。** 今天 StartRun 只插一行 runs、`spec_id` 为空（crates/hoh-core/src/persistence/commands.rs:144），Commander 的分配只选 `spec_id IS NOT NULL` 的 Run（persistence/wakes.rs:777），监督 Task 要求 `tasks.spec_id` 非空（contracts/sql/001_initial.sql 的 tasks 表；wakes.rs:971-973），产品里没有 specs 的写者（ADR-024 决定 10，docs/adr/ADR-024.md:65：spec 由 ProposeSpecChange/ApproveSpec 带来，属 M3-T02）。所以 `-p` 的 Run 永远停在 CREATED，AC-002-01/02、AC-004-02/03/04、AC-005-01、AC-042-04 都做不到。
  - **建议并写为决定 1 的 (a)**：StartRun 在同一事务里采用项目当前最新的已批准规格（specs 按项目编号，`UNIQUE(project_id, revision)`），写 `spec.changed` 唤醒 Commander；项目没有规格时 Run 以 BLOCKED(NEED_DECISION){reason: no_spec} 停下，`-p` 退出 3 而不是永远挂起。采用已批准的规格不是跳过规格；没有规格时如实阻塞。不改受锁文件。
  - (b) host 为每个 Run 造一个“临时 spec”（目标摘要、无需求）：占用项目的 spec revision、没有需求就没有 AC（completion 会以 no_acceptance_criteria 阻塞，验证不可能），等于自动生成规格——与 ADR-024 决定 10 相违，可能触及 CONTRACT 第 4 条。若所有者选它：决定 1 改为写 specs 行，需 CONTRACT 层面的确认；AC-042-04、AC-002-02 仍做不到。
  - (c) 按 CR-010 的先例写 CR，把 AC-002-01/02、AC-004-02/03/04、AC-005-01、AC-042-04 改归 M3-T02 之后的任务。若所有者选它：本 ADR 只保留决定 3–8 的机制、TUI、attach 与 AC-001-01/02、AC-002-03（K 由 SQL 播种）、AC-003-03；需要一份改 `contracts/development-tasks.json` 的 CR（不在锁内，但改归属按 CR-010/CR-020 的做法写 CR）；v0.1 的发布推迟到这些 AC 有承接任务为止。

## 决定

1. **Run 的规格：采用项目最新的已批准规格（Q1 (a)，待所有者确认）。**
   - StartRun 的事务（commands.rs:130-170 的 `RunTarget::Start` 分支）在插入 runs 行时取 `SELECT spec_id, revision, sha256 FROM specs WHERE project_id = ? ORDER BY revision DESC LIMIT 1`。specs 行按构造都是已批准的：唯一的写者将是 M3-T02 的 ApproveSpec；在此之前由 fixture 写入（验证要求它的 sha256 等于项目 `contracts/requirements.json` 的摘要，ADR-028 决定 4 的约定路径，否则冻结时 SPEC_MISMATCH）。
   - **有规格**：runs 行带 `spec_id`；`run.created` 之后在同一提交写 `spec.changed{run_id, spec_id, spec_revision, spec_sha256, from: null, cause: "adopted"}`（REQ-021 行为 1 的“规格变更”：Run 的规格从无变为 s；`classify` 按 payload 的 `spec_revision` 取键），由它唤醒 Commander。M3-T02 产生的 `spec.changed` 才会置候选 STALE；`cause: "adopted"` 的 Run 还没有候选。
   - **没有规格**：同一事务声明 `runtime:no_spec` 的 NEED_DECISION（Claims，blockers.rs 的机制），写 `question.asked{question_id: <本事件 id>, reason: "no_spec", text: "项目还没有已批准的规格：先在 TUI 用 /plan 生成并批准规格（M3），或在项目中放入已批准的规格后答复本问题", choices: [adopt]}`，`blockers::follow` 把 CREATED 置 BLOCKED（CREATED 是工作态，lifecycle.rs:106-114），决定 3 的 run.result 随之。它不是 `need_decision` 事件：没有规格的 Run 不能有监督 Task，写成唤醒只会留下永不分配的触发器。
   - 202 体的 `revision` 改为本事务之后 Run 的实际 revision（有规格 0，无规格 1）；今天 StartRun 恒为 0（commands.rs:169 的 `(0, …)`）。这与该字段已有的含义相同：openapi 对 202 体的 `revision` 只给类型、没有描述（openapi.json:67-69），docs/05-data-api.md:33 只说 202 含 revision；其余运行命令今天返回的就是本事务 CAS 之后 Run 的 revision（commands.rs:308），ConfigureTeam 返回团队的 r+1（ADR-022:61）。改变的只是 ADR-021 决定 5 第 5 步写死的 `revision: 0`（ADR-021:69，见注记）。
   - Run 的推进仍是 Commander 的：transition_run CREATED→DISCOVERING→SPECIFYING→READY→RUNNING（每步一次 revision 栅栏），之后调度轮派发。REQ-002 行为 6 的“规格/readiness 流程”在 M2 里就是 Commander 对已采用规格的审阅（可以在 SPECIFYING 中提问，AC-002-01）；Runtime 自动推进阶段属于 M3 的规格流程，不在本任务。
   - **Commander 的提示**：resources/prompts/commander.md:49 今天要求“每次唤醒只提交一条决策”，而应用的决策不是唤醒（supervise.rs:20-33），所以真实的 Commander 走完上面四步之前就没有下一次唤醒。本任务把该句改为：一个 turn 可以按顺序提交多条决策，每条应用的决策使 Run 的 revision 加一（decide.rs:440-494 的每个效果都推进它一次），后一条的 expected_revision 写前一条应用之后的值；写错的那条以 STALE_REVISION 拒绝，由 REQ-021 行为 6 的过期重新触发再唤醒（中文优先，产品内容）。运行时本就逐条处置一个 turn 的多行输出（ADR-025 决定 8），不需改代码；FakeAgent 的 Commander 照此提交。

2. **create_tasks 经 plan::import 的校验应用（Q2 (a)，待所有者确认）。**
   - `plan::import` 拆出 `plan::check(tx, run, raw) -> Result<ValidPlan, PlanError>` 与 `plan::import_in(tx, run, ValidPlan) -> Imported`（不自带事务与 run 的 CAS）；`Store::import_plan` 保留为二者加一个事务的包装。
   - `decide_in`（decide.rs:169 起）对 create_tasks：在写 decisions 行**之前**调用 `plan::check`；计划无效时返回 `PersistError::Plan`，输出处置为 `supervisor.output_disposed{outcome: "invalid", reason: "PLAN", code: <PlanError 的 ErrorCode 或 null>, detail}`，不写 decisions 行——与今天 InvalidProposal→`invalid PAYLOAD` 同类（outputs.rs:516）。DAG_CYCLE 等是 ErrorCode，不是 RejectionReason，不能写进 decisions.reason_code（`$defs.RejectionReason` 描述该列），所以不做成 REJECTED。
   - 计划有效时照常过 epoch、revision 与 Task 快照栅栏；通过即 `Effect::CreateTasks`：`import_in` 写 tasks、依赖、需求与 `plan.imported`，decisions 行 APPLIED、`decision.applied`，Run 只有决策的一次 Touch。`Proposal::applicable`（decision.rs:92-97）只对 request_user_decision 为假（它仍过栅栏而不应用，由答复应用，决定 7）。
   - ADR-017 的移交 M2T03R-156（计划路由把计划错误映射为 4xx）：M2-T13 不加计划路由，decide 路径上的计划错误以上述处置带着它的码；义务留给将来加路由的任务（M3 前没有计划）。

3. **run.result：写在进入停止状态的那个提交里（Q3 (a)）。**
   - 记 E = {COMPLETED, FAILED, BLOCKED, INCOMPLETE, CANCELLED, PAUSED}（RunResult.state 的全集），其中 T = {COMPLETED, FAILED, CANCELLED} 为**终态**（没有出边：REQ-036 行为 3，lifecycle.rs:264，ADR-011:40；决定 4 的守卫只看 T），{BLOCKED, PAUSED, INCOMPLETE} 为**停留态**。INCOMPLETE 不是终态：REQ-036 的决定写明“INCOMPLETE是否终态未定；本选择终态仅COMPLETED/CANCELLED/FAILED，INCOMPLETE/BLOCKED/WAITING_EXTERNAL/PAUSED可经ResumeRun回到resume_state”，迁移表中它有出边 W、CANCEL_REQUESTED、FAILED（lifecycle.rs:254-263，ADR-011:39）。停留态的 Run 在它的 run.result 之后还可以有事件，但只来自受理的命令（决定 4、7）。
   - **唯一的写者**是 `writer::write`（writer.rs:1145 起）：在本提交的 CAS 与事件之后、outbox 之前，对本提交中 `Change::Run(to)` 且 to ∈ E 的每个 Run（去重），以及 `Commit.results`（新字段：命令请求结果的 Run，决定 7）中此刻处于停留态的每个 Run，追加一条 `run.result`，作为本提交的最后事件。所以六条路径（blockers、decide、pace、control 两处、commands）一处覆盖，各结束点不必记得写。它也必须是**本事务中该 Run 的最后事件**：同一事务里在它之后还要写该 Run 事件的调用方合并为一次 `writer::write`——已知的只有 `person()` 之后的 `output_disposed{unsupported}`（outputs.rs:496-499、:524-570），改为由 `person()` 把处置事件放进同一个 Commit；终态由决定 4 的守卫兜住，停留态（含 INCOMPLETE）由各路径的支撑测试兜住。
   - 载荷是 `$defs.RunResult`，由 `results::compute(tx, run_id, seq)` 在事务内求：state、`exit_code`（REQ-004 的表；映射从 crates/hoh-app/src/exit.rs:38-56 移到 hoh-core 的 `exit::run_code(state)`，hoh-app 的 `exit_code` 调用它，TEST-004-01 不变）、`blocked_reason`（BLOCKED 时为 runs.blocked_reason，Claims 在 CAS 之前已写入，blockers.rs:235-251；否则 null）、spec_revision、accepted/total/remaining（决定 5）、cost（决定 5）、`last_event_seq` = 它自己的 seq。
   - **自己的 seq**：插入前取 events 的下一个自增值（`sqlite_sequence` 中 events 的值加一，表为空时 1），写进载荷，插入后核对 `last_insert_rowid()` 相等，不等即 IntegrityViolation、整个提交回滚。预测不会被别的插入抢先：events 的 seq 是 `INTEGER PRIMARY KEY AUTOINCREMENT`（contracts/sql/001_initial.sql:37），产品中没有删改 events 或 sqlite_sequence 的语句；决定 4 列出的六处插入都只经写者 actor 唯一的读写连接（writer.rs:1-4；`open_checked` 把这一条连接交给写者，persistence/mod.rs:788-799，读者连接为只读，:687-688），且都在 BEGIN IMMEDIATE 的事务里（`writer::begin`，writer.rs:314-320；命令，commands.rs:428），预测与它自己的插入在同一事务中相邻。选它而不是前一条事件的 seq：stream-json 的末行与 json 的对象说的是同一个位置，从 `last_event_seq` 之后续读不会再见到这条结果。
   - 事件 id `child_id(run_id, "result/<本提交之后的 runs.revision>")`：每个写结果的提交都推进 revision（CAS 或 Touch），所以唯一。
   - Touch 而状态不变（BLOCKED 的原因集合变化，blockers.rs:324-330、retry.rs:715-723）不写；`Change::Unblock` 与 WAITING_EXTERNAL 不写（客户端在 WAITING_EXTERNAL 期间继续等待）。

4. **终态之后不再有该 Run 的事件；INCOMPLETE 之后只有受理的命令写该 Run 的事件。**
   - **进入终态与 INCOMPLETE 只在安静时**：pace 的预算停止已要求没有未结束的 Attempt（retry.rs:564-576 的 `unfinished == 0`），取消与暂停在 Attempt 结束之后才落定。新增：Commander 的 transition_run 到 COMPLETED、FAILED、INCOMPLETE 在该 Run 有任何未结束（PREPARED/STARTING/RUNNING）的 Attempt 时——工作 Attempt 与监督 Attempt 都算，与预算停止的计数相同（retry.rs:547-556）——以 `decision.rejected{ILLEGAL_TRANSITION}` 拒绝（decision.rs 的 `transition_run` 读快照的新字段 `attempts_unfinished`，该 Run 未结束的 Attempt 数），Commander 在之后的唤醒里再决定。决策被处置时它自己的 turn 已经结束（输出只在 turn 成功之后登记，ADR-025 决定 8），所以不会因自身而被拒。监督 Attempt 也要算，因为唤醒分配不等前一 turn 的输出处置完，只跳过有 turn 在途的 Run（wakes.rs:845）：turn T1 以“COMPLETED”SETTLED，T2 随即被分配并运行，T1 的输出随后被处置；若只数工作 Attempt，结束的提交会在 T2 在途时落下——T2 的唤醒不是欠下的，(1) 不 supersede 它，`close_due` 不成立，T2 结束时的 settle 与输出事件被守卫以 `RunEnded` 拒绝，而 runner 已不再选该 Run。取消已等全部 STARTING/RUNNING 的 Attempt（control.rs:428-440），预算停止数全部 Attempt，所以只有 Commander 的决定需要补上。所以 Run 进入 T 或 INCOMPLETE 时没有在途的 Attempt（工作或监督）会在它的 run.result 之后写事件（AC-004-02 的 seq 集合相等，E2）。
   - **尾部并入终态的提交**：进入 COMPLETED、FAILED、CANCELLED 的提交在本提交自己的事件之后、run.result 之前（所以正被处置的那条输出已有它的 `decision.applied`，不算等待），把监督器本会在之后写的东西在同一事务按序写完：(1) 该 Run 的 PENDING 触发器置 SUPERSEDED 与欠下的唤醒的 `supervisor.superseded`（supervise.rs:670-698 抽成 `supersede_in(tx, run, state)`）；(2) 等待处置的输出写 `output_disposed{superseded}`（outputs.rs 抽成 `supersede_in`）；(3) 在同一事务里（看得见 (1)(2) 写下的行）求 `close` 的谓词——没有 PENDING 触发器、没有既未结清也未 SUPERSEDED 的唤醒、没有等待处置的输出、上次 `supervisor.closed` 之后有 `supervisor.woken` 或 `supervisor.output`（supervise.rs:185-243 的条件抽成 `close_due(tx, run) -> Option<last>`，`close` 与合并共用）——成立即写 `supervisor.closed{state, at}`，事件 id 与 `close` 的相同（`supervisor/closed/<last>`）。没有过监督（没有 woken、output）的 Run 谓词不成立，照旧不写。写下之后该 Run 不会再有 woken 或 output（守卫），close 的谓词对它不再可能成立，监督步骤与处置步骤对它无事可做，不写。runner 选择被监督的 Run 时（runner.rs:502-507）另外排除处于 T 且最新事件是它进入 T 时的 run.result 的 Run：结束提交已把待办的 supersede 并关闭，之后任何步骤也不能再为它写事件（守卫），不再每 tick 试一次。`wakes::advance_horizon`（wakes.rs:1607-1670；今天由步骤与处置在 `close` 之后调用，supervise.rs:123-131、:158-171）**有意不并入**：地平线只限定活着的 Run 每个 tick 的工作量（ADR-025 第十九、二十版），结束的 Run 不再被选，合并的 supersede 使地平线前移也不必记录。**INCOMPLETE 不并入**：它对监督与处置是 Hold（supervise.rs:530-541、:672，outputs.rs:278-283），欠下的义务原样保留到 Run 离开 INCOMPLETE；Hold 期间这两个步骤不写该 Run 的事件。
   - **守卫（只看 T）**：写者连接上装一个临时触发器（与 `guard_append_only` 同一处安装，persistence/mod.rs:519 起）：插入 run_id 为 R、kind 不是 `run.result` 的事件时，若 R 处于 T 且 R 的最新事件是 `payload.state` 在 T 中的 `run.result`，以固定消息 RAISE(ABORT)，映射为 `PersistError::RunEnded(R)`（HTTP 409 ILLEGAL_TRANSITION）。要看那条结果的 state，而不只是“R 处于 T 且最新事件是 run.result”：`writer::write` 先做全部 CAS 再插事件（writer.rs:1151-1153），一个从停留态直接进入 T 的提交（迁移表允许 BLOCKED、PAUSED、INCOMPLETE→FAILED，lifecycle.rs:226-263；今天只有 Commander 从工作态决定 FAILED，但不应依赖它）在插入自己的事件时，R 已处于 T 而最新事件是停留态的旧 run.result，只看后者会误挡。T 没有出边，所以它不挡任何合法的后续；M2-T13 之前就已结束、没有 run.result 的 Run 不受它挡。它覆盖一切插入事件的路径（writer.rs:1130、:1165，candidates.rs:135，evidence.rs:254，issues.rs:54，reports.rs:605），不必逐个改。
   - **INCOMPLETE 不受守卫，由构造与测试守住**：受理的命令必须能在 INCOMPLETE 的 run.result 之后写事件，而触发器分不出一条事件出自哪个命令。所以：(1) Runtime 的步骤在 INCOMPLETE 期间不写该 Run 的事件——监督与处置 Hold（上条），`close` 只处理 Supersede 的 Run（supervise.rs:200），pace 跳过 INCOMPLETE（retry.rs:482-486），每 tick 的工作 Run 只取 RUNNING、VERIFYING、WAITING_EXTERNAL、BLOCKED（runner.rs:480-484），唤醒分配与 staffing 不选 INCOMPLETE（wakes.rs:777-779，staffing.rs:119）；S1 的性质测试找出其余的（支撑测试“守卫”）。(2) 之后的事件只来自受理的命令：ResumeRun——先做 CAS 离开 INCOMPLETE、再插事件；**今天不可用**：ResumeRun 只从 PAUSED 恢复，其余状态以 ILLEGAL_TRANSITION“only a paused run resumes”拒绝（commands.rs:218-233，ADR-021 决定 7，docs/adr/ADR-021.md:111），REQ-036 决定允许的 INCOMPLETE→resume_state 没有产品路径发出（本 ADR 不补，见“移交”）；SendInput/AnswerQuestion——像对 BLOCKED、PAUSED 一样受理（决定 7），提交以 run.result 结尾（E3），所以停留的 Run 的最新事件又是它的 run.result。
   - 已知会在终态之后写事件的，除上面并入的三项，按“对终态的 Run 无事可做”跳过它们（每个按 Run 遍历的对账、清扫只选不在 T 中的 Run，对 INCOMPLETE 的 Run 按 Hold 不写）；S1 的守卫测试与性质测试逐个找出（见“实施切片”S1），找出的写者若确有必须在终态或 INCOMPLETE 之后写的内容，写一份设计更正，不放宽守卫。

5. **RunResult 的计数与成本（Q4 (a)，CR-020）。**
   - spec = runs.spec_id；`spec_revision` 为它的 revision，没有规格为 null。
   - `total` = 该 spec 的全部需求数；`accepted` = 该 Run 每个 ACCEPTED 候选的 `requirements_passed(tx, run, spec, c)` 之并与该 spec 需求之交的大小（ADR-029 决定 12；它已要求候选的 spec 摘要等于 Run 当前 spec 的摘要，所以只数“在它之下”接受的；ADR-029 决定 5：只在候选 ACCEPTED 时计数）；`remaining_requirements` = spec 的需求减去 accepted 的部分，升序、各一次，长度 = total − accepted；spec 为 null 时 0、0、[]。不用 `AcceptanceView` 的按 AC 计数。
   - `requirements_passed` 已接受 `&Connection`（事务可解引用为它），改为 `pub(crate)`；`run_cost` 的 SQL 抽成接受 `&Connection` 的函数，`Reader::run_cost` 调用它；`results::compute` 用这两者。cost_usd/cost_status 照 CR-009：价格未知即 null 与 unknown，从不估算。

6. **待答问题（Q7 (a)）。** 问题不是物化的表，是函数 `questions::open(tx, run) -> Vec<Question>` 的值，按出现的 seq 升序：
   - **Commander 的**：每个仍被持有的声明 `commander:<decision_id>` 对应一个；question_id = decision_id；text 为 payload.question，choices 为 payload.choices（choice_id、label），没有缺省选项。`person()`（outputs.rs:524-570）在同一提交写 `question.asked{question_id, commander_question_id, question, choices, requires_user}`，所以 AC-002-01 的“events 含问题原文”是这条事件的 `payload.question`（测试解析 JSON 比较，不做子串匹配）。requires_user=false 的请求照样阻塞：可由默认值决定的事项应由 Commander 写 record_assumption（REQ-002 行为 4，resources/prompts/commander.md 已这样要求）。
   - **Run 级的 Runtime 问题**：声明 `runtime:no_spec`（决定 1）；question_id 为它的 `question.asked` 事件 id；选项 `adopt`。
   - **Task 级的 Runtime 问题**：Run 中每个 BLOCKED 且 blocked_reason 为 NEED_DECISION 的 Task 一个；question_id = 它最近一次被阻塞之后的那条 `need_decision` 事件的 event_id；reason 取该事件的 `reason`（Task 有未清除的修复拒绝时以 `repair_refused` 计，verification.rs:373 的 `refused`）；选项按决定 8 的表。**每个把 Task 置为 BLOCKED(NEED_DECISION) 的写者都在同一提交写 need_decision**（今天对账的“带着未清除拒绝的 READY/PENDING 开发 Task 置 BLOCKED”一步若只写 task.blocked，S2 补上），由性质测试守住（E4）。
   - Run 级的 PACE 声明由 Task 的原因推出，不另算问题。getRun 的 `projection` 加 `questions: [{question_id, source, task_id, reason, text, choices, default}]`（自由对象，不需 CR），供 TUI 与客户端在退出 3 时列出。

7. **答复：AnswerQuestion 与 SendInput（Q7、Q9 (a)）。** host 受理两种命令（不再 422）；每个在一个 IMMEDIATE 事务里（commands.rs 新的 `RunTarget::Input`）：
   - 先判：Run 存在（否则 409 RUN_NOT_FOUND，与今天的 store_error 一致）、不在 T（COMPLETED、FAILED、CANCELLED；否则 409 ILLEGAL_TRANSITION“Run 已结束”；INCOMPLETE 与 BLOCKED、PAUSED 一样受理）、`expected_revision` 等于 Run 的 revision（否则 409 STALE_REVISION）。
   - **AnswerQuestion{question_id, answer, choice_id}**：问题须在 `questions::open` 中（否则 409 ILLEGAL_TRANSITION“问题 … 不是待答的”）；`choice_id` 给出时须是该问题的选项之一（否则 400 BAD_REQUEST）；为 null 时，答复文本去掉首尾空白后与某个选项的 choice_id 或 label 相同（不分大小写）即选它，否则取缺省选项（Runtime 问题的第一项；Commander 问题为自由答复）。然后按决定 8 应用出口。
   - **SendInput{text, target_role, input_kind}**：input_kind 为 REPLY、target_role 为 null、且 `questions::open` 恰有一个（两类合计）时，等价于 AnswerQuestion{该问题, answer = text, choice_id = null}，另写 `input_queue` 行（kind REPLY、state APPLIED、payload {text, question_id}）；否则写 `input_queue` 行（REPLY 按 REQ-002 决定改记为 STEER；其余照给定的 kind）state QUEUED——STEER/ASK/CHANGE 的投递与交给 Commander 是 M3-T04 的（ADR-025 决定 10 的移交），本任务只持久受理。
   - 事件：本提交的第一条是受理事件 `input.accepted{command_id, input_id, kind, question_id|null}`（AnswerQuestion 为 `question.answer_accepted{command_id, question_id}`），带 command_id（决定 9 据此找它）；答复另写 `question.answered{question_id, source, task_id, reason, choice_id, answer, command_id, exit}`。每个受理的这两种命令都推进 Run 的 revision（迁移或 Touch），并把 Run 放进 `Commit.results`：提交之后 Run 若处于停留态即带 run.result（E3）；Run 回到工作态则不写，之后再进入 E 时由决定 3 写。
   - **Commander 问题的出口**：decisions 行 PROPOSED→APPLIED，写 `decision.applied{decision_id, kind: "request_user_decision", answered_by: command_id}`（不带 output_id，不影响输出的处置谓词，outputs.rs:86-130）；释放声明 `commander:<decision_id>`；`blockers::follow` 在集合空时 `Change::Unblock` 回 resume_state，否则 Touch（Run 为 PAUSED 或 INCOMPLETE 时 follow 不迁移它，blockers.rs:257：Run 留在原状态，revision 由命令的 Touch 推进）；唤醒 Commander：写 `need_decision{run_id, reason: "answered", question_id, decision_id, answer, choice_id, fingerprint: "answer/<decision_id>"}`——need_decision 属于 REQ-021 行为 1 的封闭集合（High），唤醒的上下文带整条载荷（persistence/context.rs:495-545），所以答复进入下一 turn（Run 为 PAUSED 或 INCOMPLETE 时，它的触发器在 Hold 中保留到 Run 离开该状态）。不新增唤醒种类。
   - **Runtime 问题的出口**之后，在同一事务按 pace 的同一谓词重算 PACE 声明（retry.rs:680-693 的停滞判定抽成 `retry::stall_reasons(tx, run, at)`，pace 与答复共用）：答复让 Task 能动时声明清空、Run 在同一提交 Unblock，不会先写一条 BLOCKED 的结果再在下一 tick 解除。

   - Run 为 PAUSED 或 INCOMPLETE 时（决定 7 照样受理），各行的出口照常迁移 Task、写事件与释放声明，表中的“Unblock”不发生（follow 只解除 BLOCKED 的 Run，blockers.rs:257）：Run 留在原状态，提交以它的 run.result 结尾（E3）。
   - 汇合级与轮次级的问题不提供 cancel，也没有“在同一编号下回到 VERIFYING”的出口：done_when 只给重新验证与返工，二者都产生新的栅栏编号（E6）。要放弃可以取消整个 Run。
   - **ADR-011 的 Task 迁移表加 BLOCKED→VERIFYING**，只供答复的 reverify 出口：Runtime 专用（不进 `COMMANDER_TASK_MOVES`），条件是 Task 当前轮次所在的候选为 VERIFYING、该轮已关闭、同一事务为它开下一轮。没选“回 READY 再要求同内容冻结”（未采用 1）。

9. **前台 `hoh -p`（Q6 (a)、Q14 (a)）。**
   - **之前**：用法错误照旧在任何连接之前判定（cli.rs）。`hoh_core::config::load(项目)` 在连接之前：文件存在而无效即 78，stderr 指出文件与位置，stdout 0 字节，不启动 host（REQ-001 失败模式 4、REQ-004 失败模式 4）；缺文件取默认。mode 取配置的 `default_mode`（缺省 AUTO），detach 同样（修 session.rs:57）。`ensure`（client.rs:216 起）失败照旧 69（DB_ON_NETWORK_FS 为 78）。
   - **`--resume K`**：项目没有 `.hoh/state.db` 即 64 RUN_NOT_FOUND，不启动 host（与 session.rs:120-131 相同）；否则 `GET /v1/runs/K`：404 → 64 RUN_NOT_FOUND；状态在 T（COMPLETED、FAILED、CANCELLED）→ 64，stderr“Run 已结束（<state>），不能重开；请新建 Run”，不提交命令。其余状态（工作态、WAITING_EXTERNAL、BLOCKED、PAUSED、INCOMPLETE 等）提交 SendInput{text, target_role: null, input_kind: REPLY}，`expected_revision` 取刚读到的 revision；STALE_REVISION 时重读再交，至多到 `client::WAIT`（10 s）。`--detach --resume K` 走同一提交，受理后输出 202 体（json）或 run_id（text）并退出 0（修 main.rs:204-220）。
   - **FAILED、CANCELLED 的 64（提请设计审查确认）**：REQ-002 失败模式 3 与决定 3 只写 COMPLETED（docs/05-data-api.md:13 同样只说 COMPLETED 不得重开）。本 ADR 把它推广到另外两个终态：它们同样没有出边（REQ-036 行为 3，lifecycle.rs:264，ADR-011:40），对它们的 SendInput 无论如何会被决定 7 以 409 ILLEGAL_TRANSITION 拒绝，而那个拒绝在 `submit` 中也映射为 64（见“提交的拒绝”）；客户端只是把这个必然的拒绝提前到提交之前。不新增或删去命令、不改变任何状态、没有可重开的出边被关上，所以不是范围或交互的改动。
   - **`--resume` 到 INCOMPLETE 的 Run**：SendInput 照收（决定 7）：恰有一个待答问题时作为它的答复（决定 8 的出口；Run 仍 INCOMPLETE），否则以 STEER 排队（QUEUED，M3-T04 投递）。受理的提交以 run.result{INCOMPLETE} 结尾（E3），所以客户端在受理事件之后的第一条 run.result 处以 4 退出。stderr 写明输入的去向（“已答复问题 <id>”或“已排队，待 M3-T04 投递”）、剩余需求与续跑的现状，只说已有的东西：本版本没有能让 INCOMPLETE 的 Run 继续的入口——ResumeRun 只经 HTTP `POST /v1/commands` 提交（http.rs:795-801），且只恢复 PAUSED 的 Run（commands.rs:218-233）；CLI 没有发 ResumeRun 的子命令（cli.rs:216-220 把 `resume` 当作用法错误），TUI 只发 PauseRun、CancelRun（tui.rs:256-282），`hoh web` 未实现（main.rs:232、:252-256）。所以 stderr 建议以 `hoh -p` 新建 Run 继续剩余需求，不声称可以恢复。
   - **提交的拒绝**（`client::submit`，client.rs:792-839）：400 INVALID_TEAM_CONFIG → 78；404/409 RUN_NOT_FOUND → 64；409 ILLEGAL_TRANSITION（Run 已结束）→ 64；503 照旧 69；其余照旧 1。json 模式的一切失败 stdout 为 0 字节。
   - **跟随**：受理后从 `after` 打开该 Run 的事件流——StartRun 与 stream-json 从 0（stream-json 要输出全部事件），json/text 的 `--resume` 从 GET 时的 watermark（受理事件必在其后）。找到 `payload.command_id` 等于本命令的第一条事件即受理事件 A；**只以 seq > A.seq 的第一条 `run.result` 决定结束与退出码**（REQ-002 决定 CR-003，E7）；202 体受锁、不含 seq，不为它写 CR（未采用 6）。host 重启时照旧在 `last` 之后续读（session.rs:249-262）。WAITING_EXTERNAL：见到 `run.waiting` 即在 stderr 写“等待外部恢复，下次重试 <next_retry_at>”。
   - **退出**：码取 run.result 的 `exit_code`。退出码为 3 且原因是 NEED_DECISION 时，stderr 列出 `projection.questions`（id、原文、选项）与提示 `hoh -p '<答复>' --resume <run_id>`。SIGINT/SIGTERM/SIGHUP：130/143/129，stderr 写 run_id 与 `hoh attach <run_id>`，不发任何命令（REQ-004 失败模式 2，E8）；受理之前收到信号时只说没有提交成功或已提交的 run_id（若已知）。
   - **不读 stdin**：`-p` 的路径从不打开、读取或轮询 stdin，也不改终端模式（REQ-002 行为 2）；有 TTY 时同样不进 alternate screen。

10. **输出（Q5、F5）。**
    - **json**：stdout 恰为 run.result 的载荷（RunResult）加一个 LF；之前什么也不写。
    - **text**：stdout 只有一行 `<run_id> <state>`，BLOCKED 时再加 ` <blocked_reason>`，INCOMPLETE 时再加 ` 剩余 <remaining_requirements 以逗号连接>`；进度（`#seq kind`）写 stderr。任何模式都不输出 ANSI 转义。
    - **stream-json**：每条事件一行 `$defs.Event`，以单个 0x0A 结束，seq 严格递增（重复或倒退的 seq 丢弃并记 stderr）；末行是那条 run.result。`--resume` 与 attach 中 seq ≤ A.seq（attach 为 ≤ 附着时的 watermark）的历史事件带 `"replay": true`（REQ-002 决定 CR-003），新事件不带该键——**这需要 CR-022**；CR-022 批准之前不写该键（AC-004-02 的 `-p` 没有历史事件，不受影响），批准后由 S3 打开。
    - 每行（json 的对象也一样）由同一函数序列化：`serde_json::to_string` 之后把 U+2028、U+2029 替换为 `\u2028`、`\u2029`（serde_json 只在字符串内输出它们，所以逐字替换合法）；doctor/report.rs:125-133 改用这一函数。
    - host 的 `event_json`（http.rs:1255-1267）的 `attempt_id` 取载荷中字符串型的 `attempt_id`，否则 null（Event 允许 string|null，不需 CR）。
    - `Events::next`（client.rs:870-905）对有 data 而解析失败的事件返回错误，不再吞成 `Ok(None)`；跟随遇到它即以 69 退出、stderr 写出该事件的 SSE id——静默丢弃会造成缺口（REQ-004 行为 3）。
    - 写 stdout 失败（EPIPE 等）：停止跟随，stderr 一行，退出 74，不 panic、不发命令（REQ-004 失败模式 6）。

11. **原生 Agent 的 stderr 到客户端的 stderr（Q10 (a)）。** 前台 `-p` 与非 TTY 的 attach 跟随时，一个转发线程从事件中收集本 Run 出现过的 attempt_id（决定 10 的 `attempt_id` 或载荷字段），每 100 ms 读 `.hoh/attempts/<component(id)>/` 下名字以 `stderr.log` 结尾的文件新增的字节（`component` 与 `attempt_logs`，host/product.rs:981-983，改为 `pub` 供客户端用），按 64 KiB 块原样写到客户端 stderr。客户端的进度与诊断也经同一线程的有界队列写 stderr（队列满时丢弃并计数，最后写一行“省略了 N 字节”）；主线程（读事件、写 stdout）从不等待 stderr。见到 run.result 之后再做一次读尽（至多 1 s）再退出。host 不转发、不发事件（那会进 stream-json 的 stdout，违反 AC-004-02），也不加端点（openapi 受锁）。同机的 Unix socket 客户端才能读这些文件，这是 docs/04 的部署前提。

12. **attach（Q11、Q15；ADR-021 的移交）。**
    - 无 id：可附着 = 不在 T（与今天相同；INCOMPLETE 可附着，ADR-021:85 的“非终态”）。无 TTY 且 ≥2：64、stdout 0、stderr 列出全部完整 id，不订阅（今天已如此，TEST-003-03 加精确断言）；有 TTY 且 ≥2：进 TUI 的选择器（决定 13），选中即附着，Esc 或 Ctrl+C 的“脱离”以 0 退出。恰一个照旧直接附着（REQ-003 决定 2）。
    - **`--output json`**：一个对象，含 REQ-004 行为 1 的键——run_id、state、`exit_code`（该状态在表中的码，非停止状态为 null）、blocked_reason、spec_revision、accepted、total、`last_event_seq`（= getRun 的 watermark）——另加 label、revision、remaining_requirements、cost_usd、cost_status；由 host 用 `results::compute` 的同一函数在 getRun 的 `projection.result` 中给出（自由对象）。它是快照：立即输出、以 0 退出（attach 成功；AC-005-06 的“attach 退出码 0”依赖它，M2-T14）。不声称是 RunResult（exit_code 可为 null）。
    - **stream-json、text 的跟随**：附着时记 watermark W0。结束于第一条 seq > W0 的 run.result；Run 在附着时已处于 T 时结束于它最新的那条 run.result（回放之中；T 之后没有事件，E2）；M2-T13 之前就已结束、没有 run.result 的 Run 保留 QUIET 兜底（session.rs:283-299）。停留态（BLOCKED、PAUSED、INCOMPLETE）的 Run 不因回放中旧的 run.result 结束：它可能被答复或恢复，继续跟随到 seq > W0 的 run.result（与 ADR-021:87 的“PAUSED、BLOCKED、INCOMPLETE、WAITING_EXTERNAL 都不结束附着”一致；TEST-005-02 的 PAUSED 跟随 10 s 不变）。`ending()`（session.rs:23-31）删去，`ended()`（:14-21）只留作“可附着”的判定。

13. **TUI（Q11 (a)，AC-001-01、-02）。**
    - **启动**：信号先登记（照旧）；`config::load` 无效即 78（在改终端之前）；在工作线程里 `ensure` host，主线程每 100 ms 看信号标志（SIGTERM→143、SIGINT→130、SIGHUP→129，不碰终端）；失败 69，stderr 带诊断，不进 TUI（REQ-001 失败模式 2）。然后读完 `GET /v1/runs` 的全部分页，再进入 alternate screen。打开、列出与脱离只读，不写任何行（E11）。
    - **未附着的工作区**：顶栏“host 已连接”、模式、`run 无`；正文列出 Run，不在 T 者在前、各组内按创建时间新者在前，每行 `<短ID>  <label>  <blocked_reason?>  <goal 截断>`；短 ID = run_id 的前 8 个字符（run_id 由 host 的 `new_id` 给出，是 UUID）；list_runs 的 items 加 `goal`（取 run.created 的载荷，`results::started_goal`；Page 的 items 自由，不需 CR）。
    - **Enter（未附着）**：文本以 `/` 开头是 TUI 命令：`/resume` 打开选择器（与 attach 的同一个），选中即附着；其余 `/…` 显示“M3 前未提供”，不发送。否则提交 StartRun{goal = 文本, mode = 顶栏的模式, interactive = true}（`client::submit`），受理后像 `tui::attach` 一样附着新 Run（Link、RUN_CHOICES）；失败只显示原因。历史照旧在 Enter 时记入（AC-001-02 的 Ctrl+R）。
    - **Enter（已附着）**：提交 SendInput{text, target_role: null, input_kind: REPLY}（与 `--resume` 同一语义），消息栏显示“已答复 <question_id>”或“已排队（M3-T04 投递）”；替换 app.rs:271 的“输入尚未接入”。
    - **状态栏**：已附着时显示“事件 <收到的条数> · #<最新 seq>”。客户端按 seq 严格递增去重，所以条数等于该 Run 在 (0, 最新 seq] 中的事件数时，收到的集合就是该区间的全部（TEST-005-01 的“覆盖”据此判定，屏幕只显示最近几行不够）。
    - 脱离（Ctrl+C→“脱离”）以 0 退出、不发命令；暂停与取消照旧（tui.rs:258-282）。

## 不变量

- **E1** Run 每次经 `Change::Run` 进入 E 的提交里恰有一条该 Run 的 `run.result`，是该事务中该 Run 的最后事件；载荷合 `$defs.RunResult`，`last_event_seq` 等于它自己的 seq，`exit_code` 按 REQ-004 的表，`blocked_reason` 恰在 BLOCKED 时非空。
- **E2** 进入 T 或 INCOMPLETE 只在该 Run 没有任何未结束的 Attempt（工作与监督）时。Run 处于 T 且最新事件是它进入 T 时的 run.result 时，不再有该 Run 的任何事件（守卫拒绝；监督的收尾——superseded、output_disposed 与谓词成立时的 supervisor.closed——已并入进入 T 的提交，runner 不再选它，决定 4）；Run 处于 INCOMPLETE 时，Runtime 的步骤不写该 Run 的事件（监督与处置 Hold，由测试守住），之后的事件只来自受理的命令（ResumeRun 先以 CAS 离开 INCOMPLETE；SendInput/AnswerQuestion 的提交以 run.result 结尾，E3）。所以客户端在 T 或 INCOMPLETE 的 run.result 处退出时，它的 stream-json 行与该 Run 在 DB 中的事件 seq 集合相等（INCOMPLETE 的 Run 到下一个受理的命令为止）。
- **E3** 受理的 SendInput/AnswerQuestion 的提交之后，Run 处于停留态（BLOCKED、PAUSED、INCOMPLETE）即该提交带 run.result，停留的 Run 的最新事件因而又是它的 run.result；Run 回到工作态则之后再进入 E 时有 run.result。所以每个受理的命令之后，客户端要么等到一条 seq 更大的 run.result，要么 Run 仍在工作。
- **E4** 待答问题只是 `questions::open` 的值；每个 NEED_DECISION 的来源（Commander 声明、`runtime:no_spec` 声明、BLOCKED(NEED_DECISION) 的 Task）恰对应一个问题；每个 BLOCKED(NEED_DECISION) 的 Task 在它最近一次被阻塞之后有一条 need_decision。
- **E5** 一个答复是一个事务：命令行、受理事件、出口的迁移、（有修复拒绝时）`repair.refusal_cleared`、声明的释放与 Run 的迁移、PACE 的重算、run.result（若停留）；任一项失败全部回滚，命令未受理、问题仍待答。
- **E6** 轮次级与汇合级问题的每个出口都产生新的栅栏编号：reverify 使候选上的轮数加一，rework 产生新的候选；同内容守卫看轮次与汇合的 flaky；没有在已汇合的编号下回到 VERIFYING 的出口（ADR-029 J9）。
- **E7** 前台客户端的退出码只来自 seq 大于其命令受理事件的 run.result，或 130/143/129（信号）、64（用法、Run 不存在或处于 T）、69（host）、78（配置）、74（输出失败）；json 模式只有在输出 RunResult 时 stdout 非空。
- **E8** `-p` 从不读 stdin；`-p` 与 attach 的跟随从不发 CancelRun/PauseRun，信号只退订。
- **E9** stream-json 的每行合 `$defs.Event`（CR-022 之后含可选 replay），seq 严格递增，U+2028/2029 转义，无 0x1B；stdout 只有结果数据，原生 stderr 与进度只走 stderr，stderr 阻塞不阻塞 stdout 的进展。
- **E10** create_tasks 只经 `plan::check` 与 `import_in`：无效计划什么也不写入 tasks/decisions；有效计划与决策同一事务。
- **E11** 打开 TUI、列出 Run、附着与脱离不写任何行（只读与订阅）；Enter 之前不写 commands/input_queue；`/` 命令不提交 StartRun。

**CR-022 草案（属 CR-003 D1：修正规格之间的不一致，不删范围、不降门槛）**

> # CR-022 · stream-json 的回放标记与 TEST-002-02 的 assumption 措辞
>
> 基线：修改受锁文件 `contracts/protocol.schema.json`、`contracts/acceptance-scenarios.json`，重新上锁。
>
> 背景：REQ-002 决定（CR-003）要求“stream-json 回放的历史事件带 replay=true”，REQ-004 行为 2 要求 stream-json 的每行符合 `$defs.Event`，而 `$defs.Event` 为 `additionalProperties:false`、没有 replay，二者不能同时成立（ADR-031 决定 10）。TEST-002-02 的通过条件写“decisions 行 payload 含 assumption=true 与依据引用”，而受锁的 `$defs.DecisionPayload` 的 record_assumption 分支只有 kind、statement、basis 且封闭（ADR-031 决定 14）。
>
> 决定：(1) `$defs.Event.properties` 加 `"replay": {"const": true, "description": "Present only on a line of a client's stream-json output that replays an event committed before the client's own command was accepted (or before an attach began); never stored, never sent by the host (REQ-002, CR-022)."}`，不加入 required。(2) TEST-002-02 的 pass_criteria 第 5 条改为“每个 run 的 decisions 至少1行 state=APPLIED、payload.kind=record_assumption 且 basis 非空（依据引用）”。（若 vt100 不可得，(3) TEST-001-01 的 fixture 改为“PTY 字节流的终端模拟快照”，断言不变。）
>
> 不变的部分：不删需求或 AC，不改 required/degradable；Event 只多一个可选键，现有事件不变；assumption 的判定与原意等价、可判定。
>
> 验证方式：设计审查判定其属细化；`python3 tools/gen_spec_views.py`、`python3 tools/baseline.py relock --cr CR-022`、`bash scripts/check.sh --bundle`。
