# ADR-032 · Commander 的只读工作区档：决策经最终消息交付、各底座的只读启动、read_only_workspace 能力与余项

状态：提议（2026-11-16；第一版，待设计审查。受锁文字见 docs/cr/CR-024-commander-read-only-profile.md，状态 PROPOSED；它改 CONTRACT 第 7 条，须所有者批准，不属 CR-003 D1）

## 决定

### 1. 输出通道：决策在最终消息的 `hoh-decisions` 块里（选项 B）

- **监督 turn 的输出 = 最终助手消息（`Facts.final_text`）里最后一个 ```` ```hoh-decisions ```` 块的非空行，按出现顺序。** 每行是今天桥文件的一行：`{"nonce": "<唤醒头给的 nonce>", "message": {…HCP Message…}}`。行的校验、登记与处置完全不变（outputs.rs:27-70、:493-530：FORMAT、NONCE、RUN、SENDER、CAUSATION、PAYLOAD；M2-T13 的“一个 turn 可按顺序提交多条决策”照旧）。
- **解析**：hoh-core 新增纯函数 `supervise::decision_lines(final_text) -> (Vec<String>, bool)`，与 `verification::report::block`（report.rs:16-50）同一条 fence 规则：`(?s)```hoh-decisions[ \t]*\n(.*?)\n```` 取最后一个匹配；块内去掉空白行，按 `BRIDGE_LINES`=1 000 行、`BRIDGE_BYTES`=1 MiB（product.rs:270-272）截取，返回是否截断——与 `read_bridge` 同一边界与同一 `messages_truncated` 语义。一行 JSON 不会提前结束块：块的结束要求行首的 ```` ``` ````，而合法的单行 JSON 里的换行必须转义。最终消息只有一帧，帧本身受 1 MiB 帧上限约束（REQ-026 行为 2 等）。
- **执行器**：turn 结束时，监督 turn 的 `Outcome.messages` 取 `decision_lines(facts.final_text)`，不再读文件（T13 树 product.rs:897-901 的分支）；工作 turn 照旧读它的桥文件（ADR-028 决定 2）。没有块、没有最终消息（turn 在给出最终消息前失败）就没有输出——与今天桥文件不存在时相同（`read_bridge` 返回空，product.rs:282-283）；之后照 ADR-025 决定 8 处理（成功而无决策的 turn、失败 turn 的重新武装都不变）。
- **只认这一处**：中间消息里的块、写进任何文件的行、steer 的答复，都不登记。codex 的 `reply` 是最后一个完成的 `agentMessage`，claude 是 result 帧，pi 是最后一条非错误的助手消息，所以“最终消息”在三个底座上各有唯一的来源（背景所列行号）。
- **`messages.jsonl` 在监督 Attempt 上不再有写者，也不再有读者（与倾向不同，见文末）。** host 不把这个路径告诉 Commander，不读它，也不写解析结果的副本。turn 结束时监督 Attempt 的目录里若有这个文件——只能来自绕过只读档的写入或别的同 uid 进程——不登记任何输出，并在该 turn 结束的提交里记一条 `supervisor.bridge_ignored{attempt_id, bytes, sha256}`（经 `Observed.events`，persistence/runner.rs:1306 写在结束的提交里）；文件本身照 `keep_logs`（product.rs:981）留作对象。这样这个路径上的任何一行都是只读档被突破的可见证据，而不是与 host 副本混在一起。
- **审计与恢复不受影响**：最终消息在原始 stdout 日志里，`keep_logs` 把它留为对象（raw_log）；每一行另有 `supervisor.output{text}` 事件。重启：监督 turn 的输出只在成功 turn 的 OBSERVED 事务里登记（ADR-025 决定 8，T13 树 ADR-025.md:182）；reconcile 从不读 Commander 的桥（host/reconcile.rs:278-281 只为验证者读，:291-293 经 completion::recover 只为写者读，completion.rs:410-441）；host 在 turn 中途停止时执行器不做结束处理（product.rs:880-884），下一个 host 的 reconcile 结束它而不登记输出、照决定 8 重新武装。选项 B 下原始日志里的最终消息没人再解析，与今天磁盘上的桥文件没人再读等价。

### 2. 哪些 turn 用只读档，怎样选，不回退

- 适配器新增启动档 `hoh_agents::Profile { Yolo, ReadOnly, Plain }`：`Yolo` 是今天的 `yolo: true`，`Plain` 是今天的 `yolo: false`（只给 doctor `--live`）。`claude::Launch`、`codex::Launch` 的 `yolo: bool` 换成 `profile`，`pi::Launch` 加 `profile`。
- **监督 turn 用 `ReadOnly`，其余 turn 一律 `Yolo`。** 判定与工作目录用同一个条件 `a.supervision.is_some()`（product.rs:633）；`Spec`（agents.rs:1130-1146）加 `profile`，`Ready::turn`（:1158-1238）把它交给适配器，不再写死。监督 Task 就是 role=commander 的 Task（persistence/wakes.rs:173-180 `is_supervision`），所以“Commander 的 turn”与“监督 turn”是同一个集合。
- **不回退**：`ReadOnly` 需要的任一选项不在被测 help/schema 里，构建函数就拒绝（`Blocked`），prepare 以 BLOCKED_CAPABILITY、Capability 类拒绝（product.rs:660-662 的现有映射），不改用 YOLO 启动，也不去掉缺的那项照样启动。选人阶段由决定 4 的能力先挡住，这里是第二道。
- `execution.profile = "yolo-vm"` 的含义写明为：Commander 用只读工作区档，其余职位全权限。不加配置键（REQ-018 的键表不变），ADR-022 :45、:87 加注记。

### 3. 各底座的只读启动

每个选项只在被测 help/schema 声明时使用（与 YOLO 同一规则，M1R-03：构建函数与探测共用同一判断）。

- **codex App Server**：thread/start 与 thread/resume 的参数为 `{"approvalPolicy": "never", "sandbox": "read-only"}`（`requests::thread_params`，requests.rs:29-50）。依据：录制的 0.166.0 schema 中 ThreadStartParams.json、ThreadResumeParams.json 都有 `sandbox`，其 `SandboxMode` 枚举为 read-only、workspace-write、danger-full-access。turn/start 不带 `sandboxPolicy`（线程级已定，续会话时每次显式给出）。`approvalPolicy: never` 使 codex 不发审批请求，HoH 对审批请求本来就一律拒绝（codex.rs:226 `headless_answer`，REQ-024 行为 7）。
- **codex exec**：新会话 `exec --json --sandbox read-only --skip-git-repo-check [--model m] -`；续会话 `exec resume --json -c sandbox_mode="read-only" --skip-git-repo-check [--model m] <thread> -`。依据：`codex exec --help` 的 `-s, --sandbox` 列出 read-only（录制品 help-exec.txt:53-56），`--skip-git-repo-check`（:87）；本机 `codex exec resume --help` 没有 `--sandbox`，只有 `-c, --config`（预研 §3a），也有 `--skip-git-repo-check`。`--skip-git-repo-check` 是因为 Commander 的工作目录不是 Git 仓库：YOLO 下 bypass 选项跳过了这项检查（ADR-025 -755，T13 树 ADR-025.md:145），只读档没有它。`sandbox_mode` 这个配置键 help 不列出，判不了，交给活体检查的 exec 一段（余项 R5）。
- **codex 的强制方式**：模型运行的命令由 codex 自带的 Linux 沙箱（随包的 bubblewrap，`codex-resources/bwrap`）以只读挂载执行。预研 §3a 在本 VM 上离线、不调模型地实测：`codex sandbox -P :read-only` 下写项目、工作目录与 /tmp 都得到 EROFS（Read-only file system），读正常。codex 的 `apply_patch` 是否同样受限，由活体检查判定（决定 8 让 Agent 尝试它的每一种写法）。
- **claude**：`-p --output-format stream-json --verbose --tools Read,Grep,Glob --allowedTools Read,Grep,Glob --permission-mode dontAsk --strict-mcp-config [--resume id] [--model m]`，不加 `--dangerously-skip-permissions`。依据（录制的 2.1.318 help，与 2.1.325 相同）：`--allowedTools`（:23-25），`--permission-mode` 的 choices 含 `"dontAsk"`（:151-154），`--strict-mcp-config` 只用 `--mcp-config` 给的 MCP 服务器、不传 `--mcp-config` 即没有（:230-231），`--tools` 指定内置工具集（:255-259）。dontAsk 的语义来自已安装的 2.1.325 二进制内的 SDK 说明：“'dontAsk' - Don't prompt for permissions, deny if not pre-approved”；`--allowedTools` 就是这种预先批准，所以三个读工具预批准、其余一切被拒。会话里没有 Bash、Edit、Write、NotebookEdit、WebFetch、Agent 等工具，模型没有写文件的途径。各选项的值各占一个参数（逗号连接）；`--tools`、`--allowedTools` 是可变参数，claude 的提示走 stdin，argv 末尾没有位置参数（claude.rs:140-141），不会被吞。工具名 Read、Grep、Glob 不在 help 里（help 只举例 "Bash,Edit,Read"），见余项 R6。
- **不传 `--add-dir`（与倾向不同，见文末）**：读权限由 `--allowedTools` 预批准，不需要把项目设成工作目录；把项目设成工作目录还会在环境里有 `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD` 时加载项目的 CLAUDE.md（2.1.325 二进制按此变量加载附加目录的 CLAUDE.md；help :56-57 在 `--bare` 下把 `--add-dir` 列为 CLAUDE.md 目录），违背 ADR-025 决定 3“不会加载项目的 AGENTS.md/CLAUDE.md”。在私有工作目录里读项目文件确实可用，由活体检查的读探针证明（决定 8）；若证明不可用，回到设计更正，不在实施中临时加选项。
- **claude 的强制方式**：Claude Code 进程内的工具集与权限判定，没有操作系统级屏障（余项 R4）。根用户限制只针对 bypass（REQ-025 失败模式 4），只读档不受影响。
- **pi**：`--mode rpc --session-dir … --session-id … --tools read,grep,find,ls --no-mcp [--provider] [--model]`。依据（录制的 1.5.0 help，与本机相同）：`--tools` 是允许清单，且“Keeps MCP tools unless an entry starts with mcp__”（:37-39），所以另加 `--no-mcp`（:45）；内置工具名 read、grep、find、ls 在 `Built-in Tool Names:` 段（:188-195；后三个默认关闭，列入清单即开启）；help 自己的示例称之为只读模式（:119-120）。安装包代码：允许清单在 core/sdk.js:145-160 生效，agent-session.js:1151-1157 的 `_isAllowedTool` 对扩展注册的工具同样过滤。
- **不传 `--no-extensions`**：v1 的三个 Pi 插件（CONTRACT 第 10、11 条）照常加载；它们注册的工具不在允许清单里，因而不活跃；它们的钩子照常运行（余项 R3）。
- **pi 的强制方式**：pi 进程内的工具允许清单，没有操作系统级屏障；扩展代码以用户的完整权限运行（余项 R3）。pi 自己的会话文件仍由 pi 进程写到 `<project>/.hoh/sessions/<session>`（REQ-026 行为 1，product.rs:653-655）：这是底座进程自己的状态（HoH 指定的、gitignored 的 `.hoh/` 下的会话目录），不是模型经工具的写入，也不在写者提交的工作树里；TEST-021-07 只容许项目里这一处变化。

### 4. 能力 `read_only_workspace`

- REQ-027 行为 2 的能力列表加 `read_only_workspace`：适配器能以只读工作区档启动该底座（CR-024）。`probe::CAPABILITIES` 加它。
- **测量**（只由被测二进制得出，每条规则以未改动的录制品为正对照，每个反例只改一处；与构建函数共用同一判断）：
  - codex App Server：只读档的 thread/start 与 thread/resume 请求（requests.rs 的同一构建函数）对被测 `ClientRequest.json` 用探测的三值校验器 `valid` 校验，不放开 `params`（与 command_execution 的第 (1) 项同一做法，probe.rs:1802-1807）：两者都“是”为 true，有“否”为 false，否则 null。正对照：录制的 0.166.0 导出。
  - codex exec：`exec --help` 声明 `--sandbox` 且其说明列出 `read-only`（`option_text` adapter.rs:1146 + `lists_name` :1180），并声明 `--skip-git-repo-check`；help 列出 `resume` 子命令时（`lists_command` :1211），`exec resume --help` 另须声明 `--config` 与 `--skip-git-repo-check`，读不到它为 null。
  - claude：help 声明 `--tools`、`--allowedTools`、`--strict-mcp-config`，且 `--permission-mode` 的说明列出 `dontAsk`（`lists_name`，剥去引号与逗号）。工具名不可测（R6）。
  - pi：help 声明 `--tools` 与 `--no-mcp`，且 `pi::builtin_tools`（pi.rs:95）有 read、grep、find、ls；没有该段为 null。
- **会话记录不随职位变化。** `sessions.capabilities_json` 的 `read_only_workspace` = 探测值 ∧ 只读档的构建函数对这份 help/schema 不拒绝（加进 `of_session` 的 supported 表）；`command_execution` 仍按 YOLO 启动测量。会话记录描述“这个底座的会话能以哪些档启动”，不描述本会话所属职位实际用的档。理由：`Usable.session` 是每个 Agent 一份（staffing.rs:79-92），`fresh` 拿它与会话记录比较（:319-327）；若 Commander 的会话按只读档记录，它与 Agent 级的 `Usable.session` 永远不等，每个 tick 都会 Rebind。代价：Commander 会话行上的 `command_execution` 是该适配器全权限下的能力，而 claude、pi 的 Commander turn 本身没有命令工具——docs/13 写明。
- **职位所需**：`staffing::required` 对 commander 合同另要 `read_only_workspace`（与 resume 同一处，staffing.rs:115-127；REQ-020 决定 1）。缺它的 Agent 不被选为 Commander，判决行 `<agent>:CAPABILITY_UNSUPPORTED:read_only_workspace`，按 fallback 换绑或职位 BLOCKED（ADR-030 决定 3-7），Commander 连 fallback 都没有时照旧是 COMMANDER_UNAVAILABLE。默认团队的 codex 在录制版本上为 true。
- 引用 `builtin:commander` 合同的自定义职位也得到这项要求（它只缩小可选的 Agent）；它的 turn 不是监督 turn，仍用 YOLO。
- **升级**：会话记录多一个键，所以升级后第一次查看时每个已有会话都不再 `fresh`，在 checkpoint 换一次新会话（ADR-030 决定 4 的既有路径；HoH 升级后兼容套件本来就要重跑，ADR-030 决定 10 的套件集摘要）。

## 不变量

1. 监督 turn 从不以 YOLO 档启动：要么以只读档启动，要么不启动（BLOCKED_CAPABILITY）。其余 turn 的启动与今天逐字节相同。
2. 监督 turn 的输出恰为其最终消息中最后一个 `hoh-decisions` 块的非空行（有界、按序）；任何文件都不是它的输出来源。
3. host 从不写监督 Attempt 的 `messages.jsonl`；turn 结束时那里有文件即记 `supervisor.bridge_ignored`，不登记输出。
4. 只读档用到的每个选项、每个固定取值都由被测 help/schema 声明（例外只有两处，help 无从声明：codex exec 续会话的配置键 `sandbox_mode`，R5；claude 的工具名，R6；两者由 TEST-021-07 实测）；能力测量与构建函数是同一个判断，所以“能力为 true 而启动被拒”不会发生在同一份 help/schema 上。
5. 会话能力记录不随职位的档变化（`fresh` 保持稳定）。
6. 输出行的校验与处置（nonce、身份、causation、decide 的栅栏、只登记成功 turn 的输出）不变。

## 失败模式

- **Agent 缺只读档的选项**（版本过旧、help 改了）：`read_only_workspace` 为 false 或 null，不被选为 Commander；有 fallback 换绑，否则 Commander 职位 BLOCKED，判决行写出缺项，Commander 不可用的处理不变（REQ-021 行为 8）。
- **能力为 true 而启动时被拒**（查看之后 help 变了）：prepare 以 BLOCKED_CAPABILITY 拒绝（Capability 类），注册表的下一次查看与兼容闸门照常处理（ADR-030 决定 9）。
- **turn 在只读档下失败**（如 codex 不肯在非 Git 目录开线程）：FAILED，按 ADR-025 决定 8 重新武装、计失败、退避；反复失败按监督器的失败上限处理。TEST-021-07 在发布前把这类情形暴露出来。
- **没有块、块格式错、nonce 不符**：没有输出，或该行 `supervisor.output_disposed{invalid, FORMAT|NONCE|…}`，与今天桥文件里的坏行相同。
- **块超过 1 000 行或 1 MiB**：截取，`messages_truncated` 照今天处理；超过 1 MiB 的单帧本来就使 turn FAILED（PROTOCOL_FRAME_TOO_LARGE）。
- **模型把决策写进文件、或写进中间消息**：不登记；写进 `messages.jsonl` 的另记 `supervisor.bridge_ignored`。turn 成功而无决策，照决定 8 处理。
- **只读档被突破**（R2 的不受限、R3/R4 的扩展或钩子写入）：写者工作区出现非写者的改动；tree 核对照旧（ADR-028）；`messages.jsonl` 出现即有 `supervisor.bridge_ignored` 作证据。
- **升级**：所有会话各换一次新会话（决定 4）；Commander 的新会话从交接包开始（REQ-019 行为 4）。

## 未采用

- **A：保留文件桥，给 Commander 一个可写目录。** pi 没有按路径限制写入的机制，给它 write 工具就等于没有只读；codex 的 workspace-write 允许写 /tmp（预研 §3a 的实测：`:workspace` 下写 /tmp 成功），还要再加 `writableRoots` 与两个排除开关；claude 要靠按路径的写规则，规则匹配的正确性又多一层。B 让三个底座都没有写工具，更简单也更强。
- **host 把解析出的行写一份到 `messages.jsonl`。** 多余：登记用内存里的 `Outcome.messages`，审计有原始日志与 `supervisor.output`，reconcile 不读 Commander 的桥；而且会让“那个文件里的行是谁写的”说不清，丢掉决定 1 的突破证据。
- **HoH 自建沙箱**（用 bwrap 或 Landlock 包住 Agent 进程）：CONTRACT 第 7 条与 docs/00 的非目标；三种底座各有自己的状态目录要放行，复杂度高。
- **claude `--restricted`**：忽略用户、项目与本地设置，会改变底座的默认模型等（help :195-209）；docs/13 已不以它为依据。
- **claude `--add-dir <项目>`**：见决定 3。
- **claude `--setting-sources` 置空**：同样改变用户设置下的默认值；用户的钩子与插件记为余项 R4。
- **pi `--no-extensions`**：会悄悄关掉 v1 插件（CONTRACT 第 10 条“不可偷偷省略”）。
- **codex thread/start 的 `config` 去掉 MCP**：schema 不声明 `config` 的键，属于凭记忆拼参数。
- **codex turn/start 的 `sandboxPolicy`**：线程级的 `sandbox` 已足够，续会话时每次显式给出。
- **按职位的档分别记录会话能力**：见决定 4，会使 Commander 的会话每个 tick 都被判为不新鲜。
- **doctor 的 codex 检查参与选人**：见决定 7，它依赖 help 未列出的档名。
- **把检查放进兼容套件**：兼容套件判的是二进制，不是主机；沙箱能否建立是主机的事实。
- **把 Reviewer、Researcher 也改为只读**：所有者的决定只涉及 Commander；Reviewer 还要经请求助手写请求文件（ADR-028 决定 7）。
- **按职位配置档的新配置键**：REQ-018 的键表不变，所有者也没有要求可配置。

## 与倾向不同之处

CTO 在任务说明里给了 8 项倾向。按倾向采纳的：输出通道 B；codex、pi 的启动选项；能力 `read_only_workspace` 与 commander 的要求；余项的分类；TEST-021-07 的做法与先红；TEST-021-06 与兼容套件的反例；提示的两处修改。不同之处：

1. **`messages.jsonl` 不写副本**（倾向：host 写解析出的副本，供审计、reconcile 与 OBSERVED 登记）。依据：reconcile 不读 Commander 的桥（reconcile.rs:278-281 只为验证者，:291-293 与 completion.rs:410-441 只为写者）；OBSERVED 登记用的是内存里的 `Outcome.messages`（host/runner.rs:1900-1915 → persistence/runner.rs:868-877）；审计有原始日志对象与每行的 `supervisor.output`。不写副本，这个路径上的任何行就是突破的证据（决定 1）。
2. **claude 不传 `--add-dir`，改为 `--allowedTools Read,Grep,Glob`**（倾向：`--add-dir` 给上下文提到的路径）。依据：dontAsk 是“未预先批准即拒绝”（2.1.325 二进制内的 SDK 说明），`--allowedTools` 就是预先批准；`--add-dir` 会把项目变成工作目录，在 `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD` 存在时加载项目的 CLAUDE.md，与 ADR-025 决定 3 相违。读得到项目由 TEST-021-07 的读探针证明。
3. **codex 沙箱建不起来时 fail-closed 与否，由 doctor 的检查给出，而不是兼容套件，且不作闸门**（倾向：doctor 或兼容探测来决定）。依据：兼容套件判二进制，这是主机的事实；检查依赖 help 未列出的档名，作闸门会在改名时挡住所有 codex Commander。
4. 补充（不是相反）：会话能力记录不随职位的档变化（决定 4），否则 `fresh` 会让 Commander 的会话每个 tick 都 Rebind。
