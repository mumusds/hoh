## 设计修正 1（活体证明的覆盖）

**起因。** 同一类问题连续两轮出现：活体证明不靠覆盖的证据就能 PASS。

- 第 1 轮（-02、-50、-52）：判定只看某个名字的文件不存在。
- 第二版改成要证据，第 2 轮（-100）仍找到缺口：判定分别统计“每种写法都有拒绝记录”与“每个目标都被某种写法尝试过”，没有要求两者的组合。shell 在十二个目标上全被拒、`apply_patch` 只在一个另有保护的区域被拒，而 `apply_patch` 对普通项目文件的写入从未被尝试——这时所有条件仍然满足。
- 补丁的 `failed` 也被当作拒绝，而录制的 schema 把 `failed` 与 `declined` 分开（ItemCompletedNotification.json:695 的 `PatchApplyStatus`）：操作失败不证明权限被限制。

按 docs/19，同一类第二次出现，先修正设计，再改文字。

**根因。** 证明的单位不对：判定按聚合量计数（每种写法、每个目标各自出现过没有），覆盖的是投影而不是组合；又把“操作失败”当成了“权限拒绝”。

**修正：证明的单位是格（cell）。**

1. **格** = (Agent 与通道) × (新会话 | 续会话) × (该会话中存在的写机制) × (区域：P 的工作树、`P/.git/`、`P/.hoh/`、W) × (操作：创建、修改、删除，以该机制能做的为限)。
2. **写机制取自该会话自己的可用性证据**，不取自提示，也不凭假设：
   - claude：init 帧的 `tools`；
   - codex：thread/start、thread/resume 响应的 `sandbox`（App Server），加上 codex 会话固有的两种写机制，即 shell 命令与 `apply_patch`（两个通道都有）；
   - pi：观察扩展报告的活跃工具及其来源。

   已知不能写的只有各档自己的读工具：claude 的 Read、Grep、Glob，pi 的 read、grep、find、ls（来源为 builtin）。可用集合里的其余工具一律按“能写”处理，不认识的也是。每个能写的机制，它的全部格都是必需的。
3. **没有能写机制的会话**（只读档下的 claude、pi）没有机制格，它的证明是可用性证据加快照。可用集合里一旦出现能写的工具，它的格即成为必需；测试不知如何驱动的工具，其格无法满足，即覆盖不足。
4. **每个必需的格要三样都有**，缺一即覆盖不足，覆盖不足从不 PASS：
   1. **尝试**：原始日志中有这次尝试，含机制、目标路径与可核对的载荷——shell 为下文脚本的命令条目与其输出行，补丁为补丁全文与 fileChange 条目的 `path`、`kind`、`diff`。
   2. **归类为权限拒绝的结果**：补丁为 `declined`；或者针对该目标路径的沙箱拒绝，即 EROFS、EACCES、EPERM（Read-only file system、Permission denied、Operation not permitted）。语法错误、路径不存在、上下文不符这类操作错误什么也不证明；补丁只有 `failed` 而读不到原因时，也不算。
   3. **全权限对照**：同一机制 × 同一操作，在普通工作树文件上成功——命令输出成功且快照相应变化，补丁为 `completed` 且快照相应变化。
5. **快照**：四个区域每轮前后各取一次全量快照（路径、类型、大小、sha256），本段会话目录之外的任何变化都是突破。
   - `.git/` 不豁免任何文件。只读档下 git 也无法刷新 `.git/index`：在本 VM（git 2.53.0）实测，`codex sandbox -P :read-only` 里的 `git status`、`git diff` 在需要刷新索引时退出码 0、没有报错、索引不变；同一个 `git status` 在沙箱外改写了索引。所以索引的变化就是一次穿透的写入（-151）。
   - 测试自己在两次快照之间不运行 git。
6. **让格尽量确定**：
   - **shell 格**：测试在四个区域之外写一个脚本，要求模型逐字运行它（一次 shell 调用）。脚本对每个区域的 shell 目标逐一建、改、删，每格打印一行可机读的结果：区域、操作、目标、退出码、错误文本。测试把这些行与原始日志里该命令条目的输出逐行核对，再与快照交叉核对。
   - **补丁格**：测试给出每格补丁的全文，按 codex 二进制内的 apply_patch 语法（`*** Begin Patch`、`*** Add File:`、`*** Update File:` 加 `@@` 与 `-`/`+` 行、`*** Delete File:`、`*** End Patch`）。每个补丁一次独立的 apply_patch 调用，各有自己的目标文件。shell 格与补丁格的目标互不相同，一种机制的结果不能顶替另一种。
   - claude、pi 的可用集合若出现 Bash/bash、Write/write、Edit/edit，按同样方式驱动：shell 型运行同一个脚本，写与改型给出确切的调用参数。
7. **重做**：覆盖不足的一轮可以换新会话重做，每段至多三次。任何穿透的写入（快照差异，或某格的结果为成功）立即 FAIL，从不重做。

**后果。** 决定 8、AC-021-07 与 TEST-021-07 按这个模型重写（第三版），AC 的 then 与 TEST 的判据同构（-150）。考虑过而不采用的做法记在“未采用”。

## 设计修正 2（证据格式的出处）

**起因。** 第 3 轮里同一类问题出现三次：判定读的证据格式与 Agent 实际发出的不一致，正确的只读会话也永远到不了 PASS。

- -200：0.166.0 的 codex exec 把补丁的 `declined` 与 `failed` 都记为 `failed`，并丢掉 `diff`。依据是上游 rust-v0.166.0 的 exec_events.rs:157-176 与 event_processor_with_jsonl_output.rs:171-194（Codex 第 3 轮审查所引）；已安装二进制的字符串中补丁状态的变体名只有 `InProgressCompletedFailed` 连写，没有 Declined。
- -251：TEST-021-07 写的是 errno 的宏名，实际的 stderr 是英文短语。
- -252：fileChange 的 `kind` 是对象，操作名在 `kind.type`（录制 schema 的 PatchChangeKind）；`diff` 的文字形态 schema 没有规定。

这与设计修正 1 方向相反：那一类会空过，这一类会永远拒识。两者都不改变“只认权限拒绝、覆盖不足不判 PASS”的标准。

**根因。** 字段名、状态字符串与报错短语是从 schema 的片段或经验推出的，每一项都没有写明它在已安装版本里的出处；而且它们写进了受锁的 AC 与 TEST，实录一旦不同，就只能改 CR。

**修正。**

1. **分层。**
   - 受锁文字（REQ-021 行为 9 之外的 AC-021-07、TEST-021-07）只写**要证明什么**：每个必需的格三项俱全；拒绝必须是权限拒绝，不是其他任何错误；覆盖不足从不判 PASS；可用性证据必须来自该会话自己的原始日志。
   - 它们不写字段名、状态字符串或报错短语，而是写“按 ADR-032 的证据表判定”。
   - REQ-021 行为 9 照旧逐项给出 argv：那是 HoH 自己发出的启动，不是 Agent 的输出格式。
2. **证据表。** 决定 8 的证据表按 Agent 与通道逐行写出：读什么、确切的格式、它在已安装版本中的出处（录制的 schema 路径、已安装版本标签下的源文件，或二进制的字符串）、本仓库的实测记录，以及这一行是否还需录制品或 S2 的实录确认。
3. **可判定。** AC 与 TEST 引用的是“受测候选的提交中 ADR-032 的证据表”。表随候选冻结，所以审查者对照同一份表判一次运行的结论。表是封闭的：没有“或类似的格式”。
4. **实录不同时。** S2 或之后的实录若与某一行不同，在 ADR 中以设计更正改这一行，不改 CR。改动仍然从严：
   - 新格式必须出自已安装版本的一次真实录制，并写明出处；
   - 从不因此把非权限的结果算作拒绝；
   - 改动经一次设计审查。
5. **判定函数的测试夹具用真实格式。**
   - App Server 的帧先对录制的 schema 校验（三值 `valid`）再用作夹具，例如 `kind.type` 为 `add` 的 fileChange、`status` 为 `declined` 的条目；
   - shell 格的行取自本仓库的离线实测（.hoh-dev/evidence/commander-readonly/shell-cells-readonly.txt，dash 与 GNU rm 的原文）；
   - exec 的条目按上游 0.166.0 的定义（`status` 为 `failed`、没有 `diff`）。
   夹具与表同出处，表一改，夹具随之更新。
6. **exec 的补丁格（-200）。**
   - 同一原生会话里保留拒绝原因的候选来源，只有该线程在 `CODEX_HOME/sessions` 下的会话记录。
   - 但已安装二进制的字符串显示 0.166.0 的会话存储有分页与压缩的形式（`legacy_to_paginated_v1`、`paginated.zstd`、`.jsonl.zst`），App Server 的 `Thread.path` 也标为“[UNSTABLE]”。离线无法确认 exec 线程写出可读的记录，也无法确认其中 apply_patch 的输出带拒绝原因。
   - 所以 exec 的补丁格**没有已确认的证据来源**，只能是覆盖不足，exec 段永远到不了 PASS。`failed` 不算拒绝。
   - 这是所有者问题 Q-exec（决定 10）。若 S2 证实了上述会话记录及其内容，可经设计更正把它列为 exec 补丁格的来源，再问一次所有者。

**后果。**

- 决定 8 改为证据表加格模型；AC-021-07 与 TEST-021-07 只写要证明什么。
- exec 的去留按 Q-exec 的建议写入决定 10，并标为待所有者确认。

## 设计修正 3（证据表由录制确立）

**起因。** 证据格式这一类连续第二轮出现：第 4 轮的 -300、-301、-350 都是表中的行出自 schema、源码或说明文字，而不是出自 Agent 在那条路径上实际发出的东西。

- -300：按上游 rust-v0.166.0 的源码，只读且 `approvalPolicy=never` 时，有效补丁在 `assess_patch_safety` → `patch_approval_requirement` 处就被拒绝，提前返回，尚未创建任何 fileChange 事件。E6 要求的 `declined` 在这条路径上根本不会出现。况且 `declined` 也不专指权限：该版本的事件转换把部分非权限的拒绝也记为 Declined，而真正的沙箱拒绝在其测试里是 Failed。
- -301、-350：E2 接受单凭 `is_error` 的拒绝；E9 只列字段，没有谓词；E1、E8 的“符合”只要求读工具在场。

按 docs/19，同一类第二次出现，先修正设计。

**根因。** 设计修正 2 要求每行写出处，却把 schema、源码与二进制字符串都当作出处。它们说明一个字段**可能**出现，不说明只读拒绝这条路径上**实际**出现什么。

**修正。**

1. **一行证据有效，当且仅当它引用已安装版本在恰好那条路径上的一次真实录制**：一个确实尝试了那一格的只读会话（或对照会话），原始字节完整保留。schema、源码与二进制字符串可以解释一行，从不确立一行。没有录制的行，它对应的格是覆盖不足。
2. **录制先行。** 在 CR 上锁、判定函数写成之前，先跑一次录制（切片 S0，现在就跑）：
   - 环境：本机安装的 claude 2.1.325、codex 0.166.0（App Server；exec 只为记下它显示什么）与 pi 1.5.0，各在一个检出目录之外的临时 Git 项目里，以只读档的 argv 运行。
   - 输入：项目有四个区域，会话收到格提示（shell 驱动与补丁全文）；每个 Agent 另以全权限档跑一次对照。
   - 机制：沿用 tests/fixtures/protocol/record.py 的设施——每个子进程在自己的 systemd 用户 scope 里，去掉父会话变量，保留原始 stdout、stderr 与 meta。
   - 未登录或额度用尽：该 Agent 的行记为 BLOCKED 并写明是哪一种，其余照跑。额度用尽时等它重置，Agent 报了重置时间就记下来。
3. **分类与映射分开（-352）。** 什么算权限拒绝、什么算突破、什么算覆盖不足，由受锁的 AC 固定，只能经 CR 改。ADR 的证据表只把这个分类映射到字段路径与文字；改一个字段路径须引用一次新的录制，并经一次设计审查。
4. **录制与机密。** 原始帧可能带本机路径、插件清单、限额元数据与账号标识。
   - 提交之前，在新文件里查找电子邮件地址、账号或用户 id 与令牌。
   - 带有其中任何一项的原始录制只留在本地 .hoh-dev/evidence/commander-readonly/spike/ 下，不提交。
   - 夹具只放去敏的摘录，标明是摘录，并以来源文件命名。
   - 从不打印或复制凭证，也不碰用户的 .hoh/。
5. **codex 的补丁格。** 从录制中找只读补丁的拒绝在哪里可见。候选有三：
   - App Server 的 `rawResponseItem/completed` 通知。它要 initialize 的 `capabilities.experimentalApi` 与 thread/start 的 `experimentalRawEvents`，出自 `codex app-server generate-json-schema --experimental` 生成的 schema，不在录制的稳定 schema 里。
   - fileChange 以外的条目种类。
   - turn 自己的条目。

   若 host 能读的流里都没有专属于权限的补丁拒绝，就找一个能把补丁工具从会话里去掉的只读 argv（须有 schema 或录制证明的配置键），这样就没有补丁格。两者都不行，就是所有者问题，给出选项；不放宽。

**后果。** 证据表按录制重写（第五版）；判定函数的夹具是录制的摘录；切片 S0 是这次录制，CR 上锁改为其后的 S0b。

## 决定

### 1. 输出通道：决策在最终消息的 `hoh-decisions` 块里（选项 B）

- **监督 turn 的输出 = 最终助手消息（`Facts.final_text`）里最后一个 ```` ```hoh-decisions ```` 块的非空行，按块内行序。**
  - 每行是今天桥文件的一行：`{"nonce": "<唤醒头给的 nonce>", "message": {…HCP Message…}}`。
  - 行的校验、登记与处置完全不变（outputs.rs:27-70、:493-530：FORMAT、NONCE、RUN、SENDER、CAUSATION、PAYLOAD）。
  - M2-T13 的“一个 turn 可按顺序提交多条决策”照旧，顺序就是块内的行序。
- **解析**：hoh-core 新增纯函数 `supervise::decision_lines(final_text) -> (Vec<String>, bool)`，与 `verification::report::block`（report.rs:16-50）同一条 fence 规则。
  - 用 `(?s)```hoh-decisions[ \t]*\n(.*?)\n```` 取最后一个匹配，块内去掉空白行。
  - 按 `BRIDGE_LINES`=1 000 行、`BRIDGE_BYTES`=1 MiB（product.rs:270-272）截取，并返回是否截断——与 `read_bridge` 同一边界、同一 `messages_truncated` 语义。
  - 一行 JSON 不会提前结束块：块的结束要求行首的 ```` ``` ````，而合法的单行 JSON 里的换行必须转义。
  - 最终消息只有一帧，帧本身受 1 MiB 帧上限约束（REQ-026 行为 2 等）。
- **执行器**：
  - turn 结束时，监督 turn 的 `Outcome.messages` 取 `decision_lines(facts.final_text)`，不再读文件（T13 树 product.rs:897-901 的分支）；工作 turn 照旧读它的桥文件（ADR-028 决定 2）。
  - 没有块、或没有最终消息（turn 在给出最终消息前失败），就没有输出——与今天桥文件不存在时相同（`read_bridge` 返回空，product.rs:282-283）。
  - 之后照 ADR-025 决定 8 处理：成功而无决策的 turn、失败 turn 的重新武装都不变。
- **只认这一处**：
  - 中间消息里的块、写进任何文件的行、steer 的答复，都不登记。
  - 三个底座的“最终消息”各有唯一的来源（背景所列行号）：codex 是最后一个完成的 `agentMessage`，claude 是 result 帧，pi 是最后一条非错误的助手消息。
- **`messages.jsonl` 在监督 Attempt 上不再有写者，也不再有读者。**
  - host 不把这个路径告诉 Commander，不读它，也不写解析结果的副本。
  - turn 结束时监督 Attempt 的目录里若有这个文件——只能来自绕过只读档的写入或别的同 uid 进程——不登记任何输出，并在该 turn 结束的提交里记一条 `supervisor.bridge_ignored{attempt_id, bytes, sha256}`（经 `Observed.events`，persistence/runner.rs:1306 写在结束的提交里）。文件本身照 `keep_logs`（product.rs:981）留作对象。
  - 这样这个路径上的任何一行都是只读档被突破的可见证据，不会与 host 副本混在一起。
- **审计与恢复不受影响**：
  - 审计：最终消息在原始 stdout 日志里，`keep_logs` 把它留为对象（raw_log）；每一行另有 `supervisor.output{text}` 事件。
  - 重启：监督 turn 的输出只在成功 turn 的 OBSERVED 事务里登记（ADR-025 决定 8，T13 树 ADR-025.md:182）。reconcile 从不读 Commander 的桥：host/reconcile.rs:278-281 只为验证者读，:291-293 经 completion::recover 只为写者读（completion.rs:410-441）。
  - host 在 turn 中途停止时执行器不做结束处理（product.rs:880-884）；下一个 host 的 reconcile 结束它而不登记输出，照决定 8 重新武装。
  - 选项 B 下原始日志里的最终消息没人再解析，与今天磁盘上的桥文件没人再读等价。

### 2. 哪些 turn 用只读档，怎样选，不回退

- 适配器新增启动档 `hoh_agents::Profile { Yolo, ReadOnly, Plain }`：`Yolo` 是今天的 `yolo: true`，`Plain` 是今天的 `yolo: false`（只给 doctor `--live`）。`claude::Launch`、`codex::Launch` 的 `yolo: bool` 换成 `profile`，`pi::Launch` 加 `profile`。
- **监督 turn 用 `ReadOnly`，其余 turn 一律 `Yolo`。**
  - 判定与工作目录用同一个条件 `a.supervision.is_some()`（product.rs:633）。
  - `Spec`（agents.rs:1130-1146）加 `profile`，`Ready::turn`（:1158-1238）把它交给适配器，不再写死。
  - 监督 Task 就是 role=commander 的 Task（persistence/wakes.rs:173-180 `is_supervision`），所以“Commander 的 turn”与“监督 turn”是同一个集合。
- **不回退**：`ReadOnly` 需要的任一选项不在被测 help/schema 里，构建函数就拒绝（`Blocked`），prepare 以 BLOCKED_CAPABILITY、Capability 类拒绝（product.rs:660-662 的现有映射）。不改用 YOLO 启动，也不去掉缺的那项照样启动。选人阶段由决定 4 的能力先挡住，这里是第二道。
- `execution.profile = "yolo-vm"` 的含义写明为：Commander 用只读工作区档，其余职位全权限。不加配置键（REQ-018 的键表不变），ADR-022 :45、:87 加注记。

### 3. 各底座、各通道的只读启动（唯一的 argv 清单）

下表是唯一的清单（-51）。REQ-021 行为 9、REQ-025/026 与 AC-021-06 逐字引用它。codex 只经 App Server 运行 Commander 的 turn（决定 10，Q-exec 按建议 (A)）；pi 一行含 `--no-extensions`（决定 11，Q-pi-ext 按建议 (A)）。S0 以这张表的 argv 录制了三个底座的只读会话（决定 8 的证据表）。

- 只读档相对全权限启动**只替换 YOLO 选项所在的部分**（表中加粗；pi 没有 YOLO 选项，是追加）。
- 其余 argv 规则一律照旧（-153）。`[…]` 中的项按今天的规则出现：claude 在需要实时增量且 help 提供时加 `--include-partial-messages`（REQ-025 行为 1，claude.rs:101-109）；有 model 时加 `--model`；续会话时加续会话的参数。

| 底座与通道 | 只读档的启动 |
|---|---|
| codex App Server | 进程 `codex app-server --listen stdio://`（同今天）。thread/start 的参数为 **`"approvalPolicy": "never", "sandbox": "read-only"`**，加上今天已有的 `model`（有 model 时）；thread/resume 的参数为同样两项，加上今天已有的 `threadId` 与 `model`（有 model 时）。逐项相等包含这些今天已有的字段（-250；requests.rs:29-50） |
| codex exec | **不启动 Commander 的 turn**（决定 10） |
| claude | `claude -p --output-format stream-json --verbose [--include-partial-messages]` **`--tools Read,Grep,Glob --allowedTools Read,Grep,Glob --permission-mode dontAsk --strict-mcp-config`** `[--resume <session_id>] [--model <m>]`；不带 `--dangerously-skip-permissions` |
| pi | `pi --mode rpc --session-dir <dir> --session-id <id>` **`--tools read,grep,find,ls --no-mcp --no-extensions`** `[--provider <p>] [--model <m>]` |

**规则**（不变量 4）：每个选项与固定取值只在被测 help/schema 声明时使用（与 YOLO 同一规则，M1R-03：构建函数与探测共用同一判断）。

- 只有一处 help 无从声明：claude 的工具名 Read、Grep、Glob（余项 R6），由 TEST-021-07 实测。
- 若所有者在 Q-exec 选 (B)，exec 续会话的配置键 `sandbox_mode` 是第二处（R5，决定 10）。
- 缺任何一项（例外除外）该 turn 不启动（BLOCKED_CAPABILITY）。

依据与强制方式：

- **codex App Server**：
  - 依据：录制的 0.166.0 schema 中 ThreadStartParams.json、ThreadResumeParams.json 都有 `sandbox`，其 `SandboxMode` 枚举为 read-only、workspace-write、danger-full-access。
  - turn/start 不带 `sandboxPolicy`：线程级已定，续会话时每次显式给出。
  - `approvalPolicy: never` 使 codex 不向客户端请求审批，HoH 对审批请求本来就一律拒绝（codex.rs:226 `headless_answer`，REQ-024 行为 7）。
- **codex exec**：不作 Commander 的通道，见决定 10；若所有者选 (B)，exec 两行与其依据也在决定 10 里。
- **codex 的强制方式**：模型运行的命令由 codex 自带的 Linux 沙箱（随包的 bubblewrap，`codex-resources/bwrap`）以只读挂载执行。
  - 预研 §3a 在本 VM 上离线、不调模型地实测：`codex sandbox -P :read-only` 下写项目、工作目录与 /tmp 都得到 EROFS（Read-only file system），读正常。
  - Codex 的第 1 轮审查另外实测了修改与删除同样被拒，以及注入 `unshare=EPERM` 时目标命令根本不运行（审查文本 .hoh-dev/review-cmdro-d1-codex.md）。
  - 本机沙箱能否建立是主机的事实，由决定 4 的检查判定。
  - S0 录制（决定 8 的 E3–E7）：只读线程的新会话、续会话里，格脚本的十二格都得到 Read-only file system，十二份补丁都被拒（拒绝写在线程的 rollout 里），快照不变；全权限对照里同样的二十四格都写成。TEST-021-07 在每次发布时重测。
  - 录制还显示，只读线程里模型可用的工具包括账号启用的应用连接器（`mcp__codex_apps__…`），它们在沙箱之外运行（余项 R1）。
- **claude**：
  - 依据（录制的 2.1.318 help，与 2.1.325 相同）：
    - `--allowedTools`（:23-25）；
    - `--permission-mode` 的 choices 含 `"dontAsk"`（:151-154）；
    - `--strict-mcp-config` 只用 `--mcp-config` 给的 MCP 服务器，不传 `--mcp-config` 即没有（:230-231）；
    - `--tools` “指定内置工具集中可用的工具”（:255-259）。
  - dontAsk 的语义来自已安装的 2.1.325 二进制内的 SDK 说明：“'dontAsk' - Don't prompt for permissions, deny if not pre-approved”；`--allowedTools` 就是这种预先批准。
  - 各选项的值各占一个参数（逗号连接）。`--tools`、`--allowedTools` 是可变参数，claude 的提示走 stdin，argv 末尾没有位置参数（claude.rs:140-141），不会被吞。
  - S0 录制（E1、E2）：只读档的新会话、续会话，init 帧的 `tools` 恰为 Glob、Grep、Read，`mcp_servers` 为空，`permissionMode` 为 dontAsk；在私有工作目录里用 Read 读到了项目里的 token。把 Write 加进 `--tools` 而不预先批准时，Write 的调用被拒，拒绝有专门的帧（E2）。
  - 不传 `--add-dir`：读权限由 `--allowedTools` 预批准，不需要把项目设成工作目录。设成工作目录还会在环境里有 `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD` 时加载项目的 CLAUDE.md（2.1.325 二进制按此变量加载附加目录的 CLAUDE.md；help :56-57 在 `--bare` 下把 `--add-dir` 列为 CLAUDE.md 目录），违背 ADR-025 决定 3。在私有工作目录里读得到项目由 TEST-021-07 的读探针证明；证明不了即回到设计更正。
- **claude 的强制方式**：Claude Code 进程内的工具集与权限判定，没有操作系统级屏障。
  - `--tools` 的说明只覆盖内置工具集；插件、用户或项目设置带来的、已被预先批准的工具是否也被它排除，help 没有说（-53）。
  - 干净配置下的工具集由 TEST-021-07 从 init 帧实测（决定 8）；用户的插件与钩子记为余项 R4。
  - 根用户限制只针对 bypass（REQ-025 失败模式 4），只读档不受影响。
- **pi**：
  - 依据（录制的 1.5.0 help，与本机相同）：
    - `--tools` 是允许清单，且“Keeps MCP tools unless an entry starts with mcp__”（:37-39），所以另加 `--no-mcp`（:45）；
    - 内置工具名 read、grep、find、ls 在 `Built-in Tool Names:` 段（:188-195；后三个默认关闭，列入清单即开启）；
    - help 自己的示例称之为只读模式（:119-120）；
    - `--no-extensions`：“Disable extension discovery and built-in extensions (explicit -e paths still work)”（:44）。
  - 安装包代码：允许清单在 core/sdk.js:145-160 生效。
  - 传 `--no-extensions`（决定 11，Q-pi-ext 按建议 (A)）：用户自装的、配置的扩展与 pi 的内置扩展都不加载，显式 `-e` 的照常加载。HoH 自己的 v1 插件（CONTRACT 第 10、11 条）若要在 Commander 会话里生效，由 REQ-048–051 的集成以 `-e` 显式传入，argv 表随之写明，不悄悄省略。
  - S0 录制（E8、E10）：只读档的新会话、续会话，观察扩展报告的活跃工具恰为 read、grep、find、ls，来源都是 builtin；加上 `--no-extensions` 后同样如此（观察扩展经 `-e` 照常加载），快照只有 pi 自己的会话文件。不加 `--no-extensions` 时，本机用户自装的一个扩展在每个会话里往 W 写了日志文件（`.pi-lens-probe-home/*.log`），它的钩子还在 write 工具的结果后面附加了自己的文字。
- **pi 的强制方式**：只有 pi 进程内**按工具名**的允许清单，没有操作系统级屏障（-04，已安装 1.5.0 的 core/agent-session.js）：
  - 扩展注册的工具只按名字过滤（:2901）；
  - 同名的扩展工具在注册表里覆盖内置工具（:2940-2943）；
  - 名字在清单里的即被激活（:2945-2951）；
  - 内置工具也经扩展运行器包装（`wrapRegisteredTools(…, runner)`，:2931-2939），扩展的钩子包着每次工具调用。

  所以加载了的扩展若注册 `read`、`grep`、`find` 或 `ls`，模型调用的就是扩展的实现，它以用户的完整权限运行；扩展的钩子也能在模型的读工具调用上产生副作用，扩展自己也能在会话里写文件（S0 录制的正是这种情形）。pi 自己的安全说明把“没有内置沙箱”和“用户安装的扩展的行为”列在其安全边界之外（docs/security.md:99）。`--no-extensions` 把这一面收窄到显式加载的扩展；余下的是余项 R3。
- **pi 的会话文件**：仍由 pi 进程写到 `<project>/.hoh/sessions/<session>`（REQ-026 行为 1，product.rs:653-655）。这是底座进程自己的状态（HoH 指定的、gitignored 的 `.hoh/` 下的会话目录），不是模型经工具的写入，也不在写者提交的工作树里；TEST-021-07 只容许项目里这一处、且只是本次原生会话的那个目录有变化。S0 录制中，新会话在这个目录下建了一个会话文件，续会话改写了同一个文件。

### 4. 能力 `read_only_workspace`：按档的符合性与本机检查

- REQ-027 行为 2 的能力列表加 `read_only_workspace`：适配器能以只读工作区档启动该底座（CR-024）。`probe::CAPABILITIES` 加它。
- **选人用的 `read_only_workspace`（`Usable.granted` 中）为 true，当且仅当下列四项都成立**；任一为 false 即 false，判不了即不为 true。会话记录里的值是前三项之与（见下“在哪里算、谁读”）：
  1. 探测规则（只由被测二进制得出，与构建函数共用同一判断）：
     - codex App Server：只读档的 thread/start 与 thread/resume 请求对被测 `ClientRequest.json` 用三值校验器 `valid` 校验为“是”（与 command_execution 的第 (1) 项同一做法，probe.rs:1802-1807）；
     - codex 的传输为 exec（help 没有 app-server，或 App Server 不可用）：为 false，理由见决定 10；只读档的构建函数对 exec 一律拒绝；
     - claude：help 声明 `--tools`、`--allowedTools`、`--strict-mcp-config`，且 `--permission-mode` 的说明列出 `dontAsk`；
     - pi：help 声明 `--tools`、`--no-mcp` 与 `--no-extensions`（决定 11），且 `pi::builtin_tools`（pi.rs:95）有 read、grep、find、ls。

     每条以未改动的录制品为正对照，每个反例只改一处。
  2. 只读档的构建函数对这份 help/schema 不拒绝（会话能力的 `of_session` 相与）。
  3. **兼容清单里该 Agent 的 `read_only` 用例为 PASS**（见下“按档的符合性”）。
  4. **codex 另须本 host 的两项事实都允许**：本机沙箱检查不为 unconfined 或 unavailable（见下“本机沙箱检查”），且 App Server 没有在本 host 运行中降级为 exec（决定 10）。第 4 项是主机的事实，只在选人时作用（见下“在哪里算、谁读”）。
- **按档的符合性（-01）。**
  - YOLO 套件（`probe` 与六类用例，各自的 YOLO 启动变体）一项不变，它的汇总 `suite.status` 照旧是该 Agent 一切职位的兼容闸门（ADR-030 决定 9、10）。
  - 只读档的请求符合性是一个单独的用例 `read_only`。它像 `live` 一样在汇总之后加入 `suite.cases`（suite.rs:274-288 的位置），**不参与 `suite.status`**。
    - 它对四个只读变体（`new-read-only`、`new-model-read-only`、`resumed-read-only`、`resumed-model-read-only`，即今天四个变体加 `profile: read_only`），用同一组构建函数构建请求或 argv，对被测二进制核对。核对的是 codex App Server 的全部请求对 `ClientRequest.json`，以及各 argv 对被测 help：选项须声明，`read-only`、`dontAsk` 这些固定取值须列出。
    - 每个变体都构建、都核对，不跳过。
    - 结果：全“是”为 PASS；有“否”为 FAIL；判不了为 NOT_RUN。“否”分两种，都写进该用例的 findings：一是被测 help/schema 不提供某项，构建函数拒绝——只读档不受支持；二是构建出的请求被被测 schema 判为不合法——只读档不符合。
  - **`read_only` 用例的 FAIL 或 NOT_RUN 只使 `read_only_workspace` 不为 true**。该 Agent 的兼容判决仍由 `suite.status` 决定，Developer、QA 等职位照常可用。Commander 缺员的判决行是 `<agent>:CAPABILITY_UNSUPPORTED:read_only_workspace`，按 fallback 换绑或职位 BLOCKED（ADR-030 决定 3-7）。
  - 不把失败改成 PASS，不跳过变体，YOLO 套件的门槛一项不少。
  - 套件集摘要随之变化（变体表与构建出的消息都在摘要里，ADR-030 决定 10），每个 Agent 重跑一次套件。
- **本机沙箱检查（只 codex，-03、-58、-101）。**
  - **做法**：
    - 在注册表自己的临时目录里，以临时 `CODEX_HOME` 运行 `codex sandbox -P :read-only -C <临时>/ws -- /bin/sh -c 'cat <临时>/ws/token; echo x > <临时>/ws/probe'`。临时 `CODEX_HOME` 意味着不读用户配置与凭证（AC-006-02 的约束不变）。
    - 超时同其他探测命令，进程组照常回收。
    - 它报告的只是“本机能否建立 codex 的默认只读沙箱”，不是 Commander 的 thread/start 或 exec 启动本身：`-P` 在 help 中是配置栈里的权限档名（`codex sandbox --help`），`:read-only` 这个档名只见于已安装二进制（预研 §3a 用它实测）。
    - doctor 调用同一个函数。
  - **何时测（-101）**：结论与测的时刻存在注册表里该 Agent 的状态上（`Known`，不在某一次查看的 `Seen` 里），有自己的刷新规则，与 help/schema 的缓存无关：
    - host 启动后第一次查看 codex 时测；codex 的文件变了、注册表重新查看时也测（`record`，agents.rs:866-897）。
    - 结论不是 confined 时，至多每 `HOST_CHECK_EVERY = 60 s` 再测一次（测试里可缩短）。由注册表查看 Agent 的同一处做，在 tick 与写者作业之外——staffing 从不在 tick 里运行探测。
    - 结论是 confined 之后不再定时重测，直到上面两种情形之一。
    - 检查本身出错（启动不了、超时、输出读不懂）记为 unknown，**从不**变成该 Agent 的探测失败：`Seen.outcome` 照旧，Developer 等职位不受影响。
  - **四种结论各自的处理**：

    | 结论 | 判据 | 对选人用的 `read_only_workspace` | 理由 |
    |---|---|---|---|
    | confined | token 打出，probe 不存在 | 不影响 | 本机能建立只读沙箱 |
    | unconfined | probe 存在 | **去掉** | 已观察到不受限的写入；`approvalPolicy: never` 不能代替文件系统约束 |
    | unavailable | token 没打出：目标命令根本没运行，沙箱建立失败。Codex 第 1、2 轮审查以注入 `unshare=EPERM` 实测过这一路径 | **去掉** | 命令不运行是 fail-closed，不会越界写入；但 codex 读项目只能经命令，这样的 Commander 读不到项目，只凭提示里的摘要做决定。HoH 不让它悄悄失明：按 fallback 换绑或职位 BLOCKED，判决行与证据写出“本机无法建立 codex 沙箱”。用户修好主机后，下一次刷新（至多 60 s）即恢复 |
    | unknown | 超时，或档名不被接受（codex 把 `-P :read-only` 当作未知档，在运行目标命令前退出），或别的错误 | 不影响 | 检查依赖一个 help 未列出的档名；若以 unknown 为 false，codex 一改名就挡住所有 codex Commander。此时这台主机上的保证由 codex 自己的强制方式承担：发布 VM 上由 TEST-021-07 实测，unavailable 的 fail-closed 由上面的实测支持。这台主机上 R2 照旧是余项，doctor 与判决证据写出 unknown 与原因；它不是 confined，所以每 60 s 重测 |

- **在哪里算、谁读（-101）。**
  - 会话记录（`Usable.session`，以及授予会话时记下的 `sessions.capabilities_json`）里的 `read_only_workspace` 是前三项之与，都是二进制的事实。
  - 第 4 项是主机的事实，只作用于 `Usable.granted`：注册表组装 `Usable` 时（`fact`，agents.rs:428-452），本机检查为 unconfined 或 unavailable，或该实现在本 host 运行中已降级为 exec，就从 `granted` 里去掉 `read_only_workspace`。
  - 读这个 `granted` 的有三处：staffing 的 `verdict`（staffing.rs:256 以 `granted` 判缺项）、prepare 对监督 turn 的核对（`check`，T13 树 product.rs:739 起：缺它即 BLOCKED_CAPABILITY、Capability 类），以及 doctor。
  - 因此本机检查的结论变化只改变 Commander 的可选性。它不改会话记录，不会使任何会话不再 `fresh`（staffing.rs:319-327 比较的是会话记录），Developer、QA、Reviewer 的会话从不因它换绑。
  - 恢复时（如 unavailable 之后主机修好），下一次刷新使 `granted` 重新含有该能力，commander 绑定由 staffing 照常解除阻塞（Unblock 或 Grant，ADR-030 决定 4）。
- **会话记录不随职位变化。** `sessions.capabilities_json` 描述“这个底座的会话能以哪些档启动”，不描述本会话所属职位实际用的档。`command_execution` 仍按 YOLO 启动测量。
  - 理由：`Usable.session` 是每个 Agent 一份，`fresh` 拿它与会话记录比较（:319-327）。若 Commander 的会话按只读档记录，它与 Agent 级的值永远不等，每个 tick 都会 Rebind。
  - 代价：Commander 会话行上的 `command_execution` 是该适配器全权限下的能力，而 claude、pi 的 Commander turn 本身没有命令工具——docs/13 写明。
  - 前三项中任一项变化（如清单重跑后 `read_only` 用例的结论变了）使已有会话不再 `fresh`，在 checkpoint 换绑（ADR-030 决定 4 的既有路径）；第 4 项的变化不会。
- **prepare 的拒绝按来源分类（-201）。** 注册表给出 `granted` 时同时给出缺失的来源（二进制的事实，或主机的事实），prepare 据此选原因码与类别，从不按字符串推断。
  - **二进制的事实**：会话记录没有 `read_only_workspace`，或只读档的构建函数拒绝。原因码 BLOCKED_CAPABILITY、类别 `FailureClass::Capability`（今天的映射，product.rs:660-662）。这是该版本的永久事实，`staffing::turn_failed` 按 Capability 写排除记录是对的。
  - **主机的事实**：本机检查为 unconfined、unavailable，或决定 10 的 exec 降级。原因码 AGENT_UNAVAILABLE、类别 `FailureClass::Unavailable`——prepare 对“Agent 此刻不能运行”的既有分类（ADR-030）。
  - 后续路径（T13 树）：
    1. `fail_task` 对监督 Attempt 调用 `staffing::turn_failed`（persistence/retry.rs:81-84）。`turn_failed` 只对 Auth、Capability、Model 写阻塞与排除，其余类别什么都不写（persistence/staffing.rs:716-735 的 match），所以**不写 `team.binding_excluded`**。
    2. 监督器只把 auth、capability、model、decision 类的失败当作持续的不可用原因（persistence/wakes.rs:1334-1348）。unavailable 类按普通失败重新武装、退避、计入失败上限（ADR-025 决定 5）。
    3. 同一或下一个 tick 的 staffing 看到 `granted` 缺 `read_only_workspace`，判 `CapabilityUnsupported`：换到 fallback，或把绑定 BLOCKED（`team.binding_blocked`，不是排除记录）。
    4. 主机修好，下一次刷新使 `granted` 重新含有该能力。绑定为 BLOCKED 时 `Unblock`（会话仍 `fresh`），同一版本的 Commander 再被派发。
  - `staffing::verdict` 先查排除记录（staffing.rs:251-255）。因为主机的事实从不写排除记录，这一步不会挡住恢复。
- **职位所需（-155、-253）。** `read_only_workspace` 的要求按**职位名**加，与只读启动是同一个判定：Task 的职位是 commander，即监督 Task（persistence/wakes.rs:173-180 的 `is_supervision`）。
  - `staffing::required(contract)`（T13 树 staffing.rs:115-127）改为 `required(role, contract)`：职位是 commander 时另要 `read_only_workspace`；resume 仍按合同（commander、reviewer 合同），即把今天同在一臂的两者（:118-120）拆开。调用处 persistence/staffing.rs:231 有职位可传。
  - 引用 `builtin:commander` 合同的自定义职位既不要求这项能力，也不以只读档启动：它的 turn 是工作 turn，要往自己的桥文件写 TaskResult（ADR-028 决定 2），只读档下写不了。
  - 默认团队的 codex（App Server）在录制版本与本 VM 上满足。
- **升级**：会话记录多一个键，所以升级后每个已有会话各换一次新会话。HoH 升级后兼容套件本来就要重跑（ADR-030 决定 10）。

**每格的三项证据**（设计修正 1 第 4 条；只 codex 有格）：

1. **尝试**：shell 格是 E4 的条目里按 E5 的该格一行，区域、操作与目标同脚本逐一相符；补丁格是 E6 的一次调用。

### 10. codex exec 不作 Commander 的通道（Q-exec，待所有者确认；前提已变）

**问题。** 第四版的问题是：已安装的 codex 0.166.0 在 exec 的 `--json` 流里不保留补丁被拒的原因，exec 段永远到不了 PASS（设计修正 2 第 6 条）。

**S0 改变了前提**（第四版在这里约定，前提一变就再请所有者考虑）：

- 录制证实 exec 的流里补丁不留任何条目（E7，codex/exec-ro-new 的 `.stdout`）。
- 但也证实了第四版未能离线确认的那件事：exec 线程在 `CODEX_HOME/sessions` 下写出可读的 rollout，每次补丁的调用与拒绝文字都在，形态与 App Server 线程的 rollout 相同（codex/exec-ro-new 的 `.rollout`，turn_context 为 `read-only`、`never`）。
- 所以 exec 上的补丁拒绝**可以**证明。差别在于找到这个文件的方式：App Server 的响应直接给出 `thread.path`；exec 不告诉 host 文件在哪里，只能按线程 id 在 `CODEX_HOME/sessions` 下按文件名（`rollout-*-<线程 id>.jsonl`）查找，这是没有任何接口声明的约定。

**选项。**

- **(A)（建议，本 ADR 与 CR-024 按它写）：Commander 不经 codex exec 运行。**
  - 静态：codex 的传输为 exec（help 没有 app-server，或 App Server 不可用）时，`read_only_workspace` 的探测规则为 false。只读档的构建函数对 exec 一律拒绝（`Blocked`，二进制的事实）。这样的 codex 不被选为 Commander，判决行 `codex:CAPABILITY_UNSUPPORTED:read_only_workspace`；它在其他职位照常可用。
  - 运行中：App Server 在本 host 运行中降级为 exec 后，执行器按实现记下 `exec_only`（T13 树 product.rs:626-629 读、:891-896 写，host 运行期间不清除）。执行器同时告诉注册表，注册表把它当作主机的事实：从 codex 的 `granted` 去掉 `read_only_workspace`，不改会话记录。
    - staffing 因而换到 fallback 或阻塞绑定；host 重启或换版本后 App Server 重新被尝试，恢复。
    - 在 staffing 看到之前已分配的监督 turn，prepare 以 AGENT_UNAVAILABLE、`Unavailable` 拒绝（决定 4 的主机事实分类），不在 exec 上启动，也不写排除记录。
  - 代价：App Server 不可用的主机上 codex 当不了 Commander，须修好或配置 fallback。没有新余项。
- **(B)：允许 exec 当 Commander，另记余项 R8。**
  - exec 的启动为：新会话 `codex exec --json --sandbox read-only --skip-git-repo-check [--model <m>] -`；续会话 `codex exec resume --json -c sandbox_mode=read-only --skip-git-repo-check [--model <m>] <thread_id> -`。依据：`-c` 与 `sandbox_mode=read-only` 是两个参数，`-c` 的值按 TOML 解析、失败即按原字符串（help-exec.txt:19-22）；`sandbox_mode` 键见 ConfigReadResponse.json:641；`--skip-git-repo-check` 见 help-exec.txt:87。
  - TEST-021-07 加 exec 段，判据与 App Server 段相同：可用性取 rollout 的 turn_context（E3 的后一半）；shell 格取 `item.completed` 的 `command_execution` 条目的 `aggregated_output`（codex/exec-ro-new 的 `.stdout`）；补丁格取按线程 id 找到的唯一 rollout 文件，按 E6 判。找不到恰好一个文件即覆盖不足。
  - R8：exec 的 rollout 只能按文件名约定找到，约定一变，exec 段即为覆盖不足（不会误判 PASS）。R5（`sandbox_mode` 不在 help 中）同时适用。
  - CR-024 按其附录一改。

**建议 (A) 的理由。**

- (B) 现在可以证明，但比 App Server 多两处靠约定的依赖：rollout 的位置（R8）与续会话的配置键（R5）。
- exec 是降级通道，0.166.0 有 App Server。
- (A) 不新增余项，只在罕见的主机上缩小 Commander 的可选 Agent。

### 11. pi 的只读档不加载发现或配置的扩展（Q-pi-ext，待所有者确认）

**问题。** S0 录制中，pi 以第四版的只读档（`--tools read,grep,find,ls --no-mcp`）运行时：

- 本机用户自装的一个扩展在每个会话里往私有工作目录 W 写日志文件：pi/ro-new、ro-resumed、ordinary-error、control 的 `.meta` 中 `snapshot_diff` 都有 `W/.pi-lens-probe-home/*.log`；
- 它的钩子在 write 工具的结果后面附加了自己的文字（pi/ro-plus-write 的 `.stdout`）。

按 E10 这是突破：在装有这类扩展的主机上，pi 段 FAIL。这不再是余项 R3 所说的“可能”，而是录到的写入。本 VM 就装有这样的扩展，所以按第四版的 argv，TEST-021-07 的 pi 段在发布 VM 上 FAIL。

**选项。**

- **(A)（建议，本 ADR 与 CR-024 按它写）：pi 的只读档加 `--no-extensions`。**
  - 依据：录制的 1.5.0 help :44，“Disable extension discovery and built-in extensions (explicit -e paths still work)”；安装包 docs/cli.md:196-197。
  - 录制（pi/ro-no-extensions）：活跃工具恰为 read、grep、find、ls，来源都是 builtin；观察扩展经 `-e` 照常加载；快照只有 pi 自己的会话文件，W 不变。
  - 用户自装的与配置的扩展、pi 的内置扩展（CLI 的 codemode、tool_search 与 MCP，安装包 docs/sdk.md:116；llama.cpp 提供方，docs/llama-cpp.md:132）都不进 Commander 会话。
  - HoH 自己的 v1 插件（CONTRACT 第 10、11 条）：REQ-048–051 的集成若让它们在 Commander 会话里生效，就以 `-e` 显式传入，argv 表随之写明，TEST-021-07 按那时的 argv 实测；不悄悄省略。
  - R3 收窄为显式加载的扩展（决定 7）。探测规则加“help 声明 `--no-extensions`”（决定 4），录制的 help 有它（adapter.rs 的 `the_recorded_pi_declarations_are_all_declarations` 已断言）。
  - 代价：用户扩展的工具与钩子不进 Commander 会话；只靠扩展注册的模型提供方（如 llama.cpp）当不了 pi 的 Commander——它的 turn 失败（FAILED），照 ADR-025 决定 8 处理，docs/12 写明。
- **(B)：保持发现扩展，余项 R3 照第四版。**
  - 快照规则不放宽：装有会写区域的扩展的主机上 pi 段 FAIL。要在本 VM 上 PASS，须所有者从发布 VM 卸下这类扩展；否则接受 v1 的 adapter-live 在 pi 段 FAIL。
  - 用户主机上，pi Commander 的会话里扩展照常写文件；R3 记为已观察到的写入。
- **(C)：pi 不当 Commander。** `read_only_workspace` 对 pi 恒为 false，pi 的 Commander 职位按 fallback 换绑或 BLOCKED。这缩小 v1 的范围，须所有者决定。

(B)、(C) 下 CR-024 按其附录二改。

**建议 (A) 的理由。**

- 它是 pi 自己的、help 声明的选项，不是 HoH 自建的机制；录制证明它去掉了录到的写入，也不妨碍观察。
- 它不放宽任何判据，也不让发布的结论取决于 VM 上装了什么扩展。
- 默认 Commander 是 codex（CONTRACT 第 5 条）。pi 当 Commander 时少了用户扩展，是为只读付的明确代价，写在 docs/12。

## 不变量

1. 监督 turn 从不以 YOLO 档启动：要么以只读档启动，要么不启动——因二进制的事实不启动为 BLOCKED_CAPABILITY（Capability 类），因主机的事实（本机沙箱检查、运行中的 exec 降级）不启动为 AGENT_UNAVAILABLE（Unavailable 类，不写排除记录）（-353）。其余 turn 的启动与今天逐字节相同。
2. 监督 turn 的输出恰为其最终消息中最后一个 `hoh-decisions` 块的非空行（有界、按行序）；任何文件都不是它的输出来源。
3. host 从不写监督 Attempt 的 `messages.jsonl`；turn 结束时那里有文件即记 `supervisor.bridge_ignored`，不登记输出。
4. 只读档用到的每个选项、每个固定取值都由被测 help/schema 声明。例外只有 claude 的工具名（R6），由 TEST-021-07 实测；Q-exec 选 (B) 时另有 `sandbox_mode`（R5）。能力测量与构建函数是同一个判断，所以“能力为 true 而启动被拒”不会发生在同一份 help/schema 上。
5. 会话能力记录只含二进制的事实，不随职位的档变化，也不随主机的事实（本机检查、本 host 运行中的 exec 降级）变化，`fresh` 因此保持稳定。选人用的 `granted` 在注册表的 `fact` 里由一个函数算出，staffing、prepare 与 doctor 读的是同一个值。主机的事实只影响 Commander 的可选性，从不使任何会话换绑，也从不写排除记录。
6. 只读档的符合性从不进入 YOLO 套件的 `suite.status`；YOLO 套件的门槛与今天相同。只读档的任何失败只使 `read_only_workspace` 不为 true。
7. 输出行的校验与处置（nonce、身份、causation、decide 的栅栏、只登记成功 turn 的输出）不变。
8. （按 Q-exec 的建议 (A)）Commander 的 turn 从不在 codex exec 上启动。
9. 判定活体证据只认 ADR-032 证据表中的字段路径与文字；表中每行引用已安装版本在该路径上的一次录制（设计修正 3）。什么算权限拒绝、突破或覆盖不足由受锁的 AC-021-07 固定，只能经 CR 改（-352）。

## 失败模式

- **Agent 缺只读档的选项**（版本过旧、help 改了）：
  - 探测规则为 false 或 null，`read_only` 用例 FAIL（构建函数拒绝），`suite.status` 不受影响。
  - 该 Agent 不被选为 Commander：有 fallback 换绑，否则 Commander 职位 BLOCKED，判决行写出 `<agent>:CAPABILITY_UNSUPPORTED:read_only_workspace`。
  - 它在别的职位照常可用。Commander 不可用的处理不变（REQ-021 行为 8）。
- **构建出的只读请求不符合被测 schema**：`read_only` 用例 FAIL（不符合），后果同上，只影响 `read_only_workspace`。
- **只读用例判不了**：NOT_RUN，`read_only_workspace` 不为 true，后果同上；下次 CLI 或 HoH 变化时重跑（ADR-030 决定 10）。
- **pi 的 help 不声明 `--no-extensions`**：同“Agent 缺只读档的选项”（决定 11 (A)）。
- **本机沙箱检查**：unconfined 与 unavailable 从 codex 的 `granted` 中去掉 `read_only_workspace`，判决证据写出检查结论；unknown 不影响，记录原因。结论不是 confined 时每 60 s 重测，主机修好后在下一次刷新时恢复；检查出错从不变成该 Agent 的探测失败，其他职位不受影响（决定 4）。
- **已分配之后失去能力**（刷新在分配与 prepare 之间得到 unavailable，或 App Server 在其间降级）：prepare 以 AGENT_UNAVAILABLE、`Unavailable` 拒绝，不写排除记录；staffing 随后换绑或阻塞；主机修好后同一版本恢复（决定 4 的 -201）。
- **codex 的传输为 exec**（决定 10 (A)）：不被选为 Commander，在其他职位照常可用；运行中降级为 exec 的，host 重启或换版本后恢复。
- **能力为 true 而启动时被拒**（查看之后 help 变了）：prepare 以 BLOCKED_CAPABILITY 拒绝（Capability 类），注册表的下一次查看与兼容闸门照常处理（ADR-030 决定 9）。
- **turn 在只读档下失败**（如 codex 不肯在非 Git 目录开线程）：FAILED，按 ADR-025 决定 8 重新武装、计失败、退避；反复失败按监督器的失败上限处理。TEST-021-07 在发布前把这类情形暴露出来。
- **没有块、块格式错、nonce 不符**：没有输出，或该行 `supervisor.output_disposed{invalid, FORMAT|NONCE|…}`，与今天桥文件里的坏行相同。
- **块超过 1 000 行或 1 MiB**：截取，`messages_truncated` 照今天处理；超过 1 MiB 的单帧本来就使 turn FAILED（PROTOCOL_FRAME_TOO_LARGE）。
- **模型把决策写进文件、或写进中间消息**：不登记；写进 `messages.jsonl` 的另记 `supervisor.bridge_ignored`。turn 成功而无决策，照决定 8 处理。
- **只读档被突破**（R1、R4 的用户配置，R3 的显式加载的扩展，R2 的主机）：写者工作区出现非写者的改动；tree 核对照旧（ADR-028）；`messages.jsonl` 出现即有 `supervisor.bridge_ignored` 作证据。
- **TEST-021-07 读不到 codex 的 rollout**（`thread.path` 缺失或改名、文件不在、行格式不在证据表中）：补丁格覆盖不足，不判 PASS；以新的录制经设计更正改表（决定 8）。
- **只靠扩展注册的模型提供方的 pi 当 Commander**（决定 11 (A) 的代价）：该 turn 失败（FAILED），照 ADR-025 决定 8 重新武装、计失败；docs/12 写明。
- **升级**：所有会话各换一次新会话（决定 4）；Commander 的新会话从交接包开始（REQ-019 行为 4）。

## 未采用

- **A：保留文件桥，给 Commander 一个可写目录。**
  - pi 没有按路径限制写入的机制，给它 write 工具就等于没有只读。
  - codex 的 workspace-write 允许写 /tmp（预研 §3a 的实测：`:workspace` 下写 /tmp 成功），还要再加 `writableRoots` 与两个排除开关。
  - claude 要靠按路径的写规则，规则匹配的正确性又多一层。
  - B 让三个底座都不给写工具，更简单也更强。
- **host 把解析出的行写一份到 `messages.jsonl`。** 多余：登记用内存里的 `Outcome.messages`，审计有原始日志与 `supervisor.output`，reconcile 不读 Commander 的桥；而且会让“那个文件里的行是谁写的”说不清，丢掉决定 1 的突破证据。
- **只读变体直接进 YOLO 套件的汇总**（第一版的写法，-01）：只缺一项只读选项的 Agent 会整体 FAIL、在一切职位上 COMPAT_UNVERIFIED。
- **HoH 自建沙箱**（用 bwrap 或 Landlock 包住 Agent 进程）：CONTRACT 第 7 条与 docs/00 的非目标；三种底座各有自己的状态目录要放行，复杂度高。
- **产品在运行时核对生效的工具集**（claude 的 init 帧 `tools`、codex 响应的 `sandbox`、pi 的观察扩展）：
  - claude 的 init 帧在模型开始之后才能据以取消，只是检出，不是保证；
  - codex 响应的 `sandbox` 在 schema 里注明为“Legacy sandbox policy retained for compatibility”；
  - pi 的观察扩展挡不住之后才注册的同名工具。

  三者都留作 TEST-021-07 的证据来源，不作产品闸门；余项照实记录（所有者的方向）。
- **本机检查为 unknown 时视为 false**：见决定 4 的表。
- **本机检查只在 host 重启时重测**：用户修好主机后还要重启 host，Commander 才恢复；改为结论不是 confined 时每 60 s 重测（-101）。
- **把本机检查的失败当作该 Agent 的探测失败**：会让 Developer 等职位也跟着等待或换绑；检查只作用于选人用的 `granted`（-101）。
- **把本机检查写进会话记录**：它的每次变化都会使该 Agent 的一切会话不再 `fresh`，在 checkpoint 换绑；放在 `granted` 上只影响 Commander（-101）。
- **把字段名、状态字符串与报错短语写进受锁的 AC 与 TEST**（第三版的写法）：实录一旦不同，只能改 CR；放进带出处的证据表（设计修正 2）。
- **以 `CODEX_HOME/sessions` 下的会话记录作 exec 补丁格的证据**（第四版因无法离线确认而不采用）：S0 已录到 exec 线程的 rollout 及其中的拒绝，见决定 10 的“S0 改变了前提”与 Q-exec 的 (B)。
- **以 App Server 的实验性原始事件作补丁格的来源**：initialize 的 `capabilities.experimentalApi` 加 thread/start 的 `experimentalRawEvents` 时，`rawResponseItem/completed` 通知带着补丁调用与拒绝文字（S0 录制 codex/app-ro-new 的 `.stdout`）。但 thread/resume 没有这个参数，续会话的流里补丁什么也不留（codex/app-ro-resumed），而且它改了产品的请求。rollout 对两轮都有，且不改请求（E6）。
- **寻找去掉补丁工具的只读参数**（设计修正 3 第 5 条的第二条路）：录制的 schema 里没有这样的已声明键（与 apply_patch 有关的只有审批请求），thread/start 的 `config` 是不声明键的开放对象；rollout 已给出拒绝，不需要它。
- **E5 也接受 Permission denied、Operation not permitted**（第四版的写法）：S0 只录到 Read-only file system；没有录制的短语不进表（设计修正 3）。
- **exec 的补丁格以 `failed` 加快照不变为证**：这是 Q-exec 的 (B)，证明不了权限拒绝，须所有者接受余项 R8（决定 10）。
- **主机的事实导致的 prepare 拒绝沿用 Capability 类**（第三版的写法，-201）：会写永久排除记录，主机修好后同一版本也恢复不了。
- **只读能力的要求按合同、只读启动按职位**（-253 的另一边）：两个判定不一致，引用 commander 合同的自定义职位会被这项能力挡住却仍以全权限运行。
- **引用 commander 合同的自定义职位也以只读档启动**：它的 turn 是工作 turn，要往自己的桥文件写 TaskResult，只读档下写不了。
- **活体证明按聚合量计数**（第二版的写法：每种写法有拒绝记录、每个目标被某种写法尝试过）：覆盖的是投影不是组合，-100 的反例可以通过；改为格（设计修正 1）。
- **让模型自己写每格的命令或补丁**：结果依赖模型的写法，同一格可能因命令写错而“失败”；改为逐字运行测试写出的脚本与给出的补丁全文。
- **把补丁的 `failed` 或 `declined` 当作拒绝**：录制中只读下被拒的补丁根本不产生 fileChange 条目（-300），全权限下写失败才是 fileChange `failed`（codex/app-control-ordinary-error）；只认 E6 录到的拒绝文字。
- **快照排除 git 自己会刷新的文件**（`index`、`index.lock`、`logs/`，-151 的一个修正方向）：实测只读档下 git 的索引刷新静默失败、索引不变（设计修正 1 第 5 条），排除它们只会藏起真正穿透的写入。
- **由文档或假设决定一个会话有哪些写机制**：不同配置、插件、版本的工具集不同；只取该会话自己的可用性证据。claude、pi 的可用性必须恰为读工具，多出的工具不再按格判定（-350）。
- **claude `--restricted`**：忽略用户、项目与本地设置，会改变底座的默认模型等（help :195-209）；docs/13 已不以它为依据。
- **claude `--add-dir <项目>`**：见决定 3。
- **claude `--setting-sources` 置空**：同样改变用户设置下的默认值；用户的钩子与插件记为余项 R4。
- **pi 保持发现扩展**（第四版的写法，Q-pi-ext 的 (B)）：第四版以为 `--no-extensions` 会悄悄关掉 v1 插件；但显式 `-e` 照常加载（录制 pi/ro-no-extensions），v1 插件可以显式传入而不省略；而保持发现时，录到用户扩展在每个会话里写 W（决定 11）。
- **codex thread/start 的 `config` 去掉 MCP**：schema 不声明 `config` 的键，属于凭记忆拼参数。
- **codex turn/start 的 `sandboxPolicy`**：线程级的 `sandbox` 已足够，续会话时每次显式给出。
- **按职位的档分别记录会话能力**：见决定 4，会使 Commander 的会话每个 tick 都被判为不新鲜。
- **把本机检查放进兼容套件**：兼容套件判的是二进制，不是主机；沙箱能否建立是主机的事实。
- **把 Reviewer、Researcher 也改为只读**：所有者的决定只涉及 Commander；Reviewer 还要经请求助手写请求文件（ADR-028 决定 7）。
- **按职位配置档的新配置键**：REQ-018 的键表不变，所有者也没有要求可配置。
