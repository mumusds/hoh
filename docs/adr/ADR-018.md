# ADR-018 · Outbox 投递、收据去重、HCP 消息与验证交接包

状态：M2-T04 采纳（CTO 设计决定，细化 REQ-022、REQ-062，不改变 CONTRACT 或受锁契约）。日期：2026-11-07。

## 背景

REQ-022 规定了以下几点，但没有规定它们的实现形式：

- HCP 消息必须经 schema 校验；
- 状态更新、事件与 outbox 在同一事务中完成；
- 接收方以 (consumer, message_id) 收据去重；
- 未 ACK 的消息按持久化的次数与时间重试，超过上限进入 DEAD_LETTER；
- candidate 冻结后生成发往 qa 与 reviewer 的验证交接；
- 栅栏不符的消息被拒并写收据。

下面的决定补上这些细节。实现在 `crates/hoh-core/src/delivery.rs`（投递循环与端口）、`handoff.rs`（交接包，纯函数）、`persistence/outbox.rs`（取件、结算、消费、无效消息）、`persistence/results.rs`（TaskResult → candidate_ready 与交接）。

## 决定

1. **消费者与收据**。
   - 消费者就是接收角色（`receipts.consumer = outbox.recipient_role`）。
   - `Store::consume` 在一个 IMMEDIATE 事务里依次做：
     1. 先查收据：已有收据则原样返回其 `result_json`（逐字节），什么都不写。
     2. 没有收据则按栅栏判定（第 2 条）。
     3. 被拒：写一条 kind=rejected 的回复作为收据，再写一条 `message.rejected` 事件。
     4. 通过：执行消费者给出的效果（compare-and-set、事件、新 Attempt），再写一条 `message.applied` 事件和一条 kind=ack 回复的收据。
   - 任一步出错，整个事务回滚，收据也不留，于是下次投递重新判定。
   - 回复存为字符串，重放时原样返回，不重新序列化。
   - 收据的外键指向 outbox，所以收据只对 outbox 中的消息成立。
2. **栅栏顺序**（第一个不符者给出原因）：role_epoch（与接收角色在该 Run 的当前绑定比较；没有绑定也算过期）→ expected_revision（与消息所指 Task 的 revision 比较；Task 不存在时 current_revision 为 null）→ spec_sha256（与 Run 当前 spec 比较）→ candidate_id（消息带 candidate 时，与该 Run 当前候选比较）。
   - 当前候选是该 Run 中状态为 FROZEN 或 VERIFYING、created_at 最新（同时按 candidate_id）的候选。把旧候选置为 STALE 属于 M2-T10。
   - 直接调用 `Store::consume` 的消息同样要求整个信封是合法的 Message（M2T04R-102）。
   - 交接消息的 payload 必须与信封一致（Message::check_payload：run、task、角色、epoch、spec；verification 的候选必须与信封的 candidate_id 相同，信封不能为 null），不一致的消息无效。与当前值的比较在栅栏中进行：spec_revision 必须是 Run 当前 spec 的 revision；候选的六个身份字段必须与当前候选逐一相等，而不只是 id 相等（M2T04R-04）。
   - 拒绝回复的 `reason_code` 在信封顶层（Message schema 的 allOf 要求如此）；payload 为 `{current_revision, current_role_epoch, current_spec_sha256, current_candidate_id, detail}`。
   - RejectionReason 的 description 写的是“payload.reason_code”，与结构不一致。这是受锁契约中的措辞，留待下一次协议 CR 修正，已记入 M2 的审查记录与 PROGRESS 的后续项（M2T04R-60）。
3. **schema 无效的消息**：解码失败时写一条 `message.invalid` 事件，记录 violations，没有原因码（新增原因码需要 CR），也不写收据。来自 outbox 的此类消息直接进入 DEAD_LETTER。入队时 `NewOutbox::hcp` 已经校验过 Message，交接消息还要校验 payload 是 ContextHandoff，所以 acceptance_ids 为空的交接无法入队。
4. **投递循环**（`delivery::Dispatcher::tick`，没有内部睡眠，时钟与传输都是端口；设计修正，M2T04R-01..03、-05）。
   - **一次只领一条，领了就投**。每条消息的领取都在自己的事务中完成，领取后立即交给传输，tick 循环至多 batch 次。因此一次领取对应一次真实投递，被取消的 tick 只影响正在投的那一条（M2T04R-02）。
   - **领取交到传输之前仍归 store**（设计修正，M2T04R-100、-200、-300、-301；四轮同一类问题）。
     - **计数时机**：一次投递在 dispatcher 把行交给传输（`Claimed::start`）时计数。这一步在内存中完成，没有可能丢失回复的写入，所以挂住的传输照样被计数（M2T04R-03）。
     - **登记簿**：领取由 writer 线程登记在一个登记簿中。领取的结果是守卫 `Claimed`。
       - `start` 从登记簿中取走自己的条目并交出行。条目已不在（store 关闭时已被收回）时，返回 None，不投递。
       - 守卫在 `start` 之前被丢弃时，只把条目移到"已交还"列表，不经过任何通道，也不需要 writer 还在运行。丢弃的位置不论是 writer 的回复、通道里未读的回复、还是 dispatcher 手里，都一样。
     - **撤销并进领取的事务**（M2T04R-400、-401、-450、-451；第五轮）：已交还的领取由下一次领取在它自己的 IMMEDIATE 事务里撤销，撤销之后才选可领的行。
       - 该事务无法执行时（例如 SQLITE_BUSY），整个领取以 DB_BUSY 失败，已交还的条目原样保留。因此一行在它的待撤销撤完之前，不可能被重新领取并多计。
       - 领取跳过仍有存活守卫（既未交出、也未交还）的消息。被泄漏、长期不释放的守卫会挡住它那一条，直到 store 关闭时被收回。
       - 其他作业不做撤销，所以不会因为待撤销而多等 busy_timeout，REQ-062 的 DB_BUSY 时限不变。
     - **撤销与较早代次的结算交叉**（M2T04R-500；第六轮，同一类问题，先列状态再改）：设第 k 代已交还、尚未撤销。第 k 代从未交给传输，所以没有人以第 k 代结算它；下一次领取先撤销再选行，所以这一行也不会再被领取。这段时间里能改动该行的只有较早代次的结算：失败不是当前代次，被忽略；送达把它改为 ACKED，计数不变。所以撤销时该行一定处于第 k 代，状态是 DELIVERING 或 ACKED，不会是其他状态。撤销在这两种状态下都把计数减一（第 k 代从未投递）。只有 DELIVERING 的行回到 PENDING，ACKED 保持终态和收据。store 关闭时的撤销用同一条语句。
     - **关闭**：store 关闭时，writer 在处理完队列之后、关闭连接并释放项目锁之前，用一个事务撤销所有尚未交给传输的领取，包括守卫仍然存活的（M2T04R-301）。
     - **登记簿失效**：writer 线程以任何方式结束（含 panic）都会使登记簿失效，之后 `start` 一律返回 None（M2T04R-402）。
     - **结果**：交给传输之前发生的任何取消都不消耗投递次数。交给传输之后的取消或崩溃计为一次投递，等同于一次被中断的投递。
     - **残留**（都由投递上限兜底；ADR 早先只列了第一种，M2T04R-452）：
       1. 关闭时撤销失败。
       2. 领取提交之后、交接之前进程崩溃或 writer panic：计数已在库中，无人撤销。
       3. 已交还的领取在下一次领取之前，读者会看到它仍是 DELIVERING 且多计一次。这只影响显示，不影响领取。
   - **领取**：
     - 可领取的行：PENDING 且 next_retry_at 为空或已到；或者 DELIVERING 且 next_retry_at 已到（上次投递当作丢失）。
     - 只领已注册消费者的角色，并排除运行时内部通知。内部通知的 payload 带显式标记 `"notice": "runtime"`，只有这个确切的值才排除，`notice` 的其他值照常领取校验（M2T04R-201）。三个生产者的测试固定了这一标记（M2T04R-251）。包括决策与调度轮的派发通知和 PauseRun 的 `run.control`。它们由启动 Attempt 的一方和 host 循环（M2-T05/T06）消费，HCP 投递循环不碰它们，它们保持 PENDING（M2T04R-05）。其余每一行都会被领取并校验，所以本应是 HCP 消息却缺字段的行会被记为无效，不会被静默跳过（M2T04R-101）。
     - 领取时 state=DELIVERING、attempt_count+1，这次投递的代次就是新的 attempt_count；next_retry_at 设为 now 加上退避（第 k 次为 min(2^(k-1), 60) 秒，不加抖动）。
     - 已用尽次数的行（attempt_count ≥ 上限）在领取事务中直接进入 DEAD_LETTER 并写死信事件，不再投递。这样崩溃或超时中断的投递也受上限约束（M2T04R-03）。
   - **结算绑定代次**（M2T04R-01）：
     - 送达（ACK 或 rejected 都算送达）→ ACKED。只要消息尚未结算（DELIVERING 或 PENDING），任何代次的送达都算数，因为收据已经提交，消息确实送到了。已进入 DEAD_LETTER 后才到达的送达同样改为 ACKED，并在死信事件之外再写一条 `outbox.delivered_late` 事件（M2T04R-103）。
     - 失败：只有代次等于当前 attempt_count 的结算才生效。次数未到上限 → PENDING，记下 last_error，next_retry_at 保留；到上限 → DEAD_LETTER 并写死信事件。较早代次迟到的失败被忽略，不会盖过后来的成功。
     - 无效：同样只有当前代次生效，直接进入 DEAD_LETTER。
     - 记录从不删除。
   - 上限取 `delivery.max_delivery_attempts`（初值 5），配置解析随 M2-T07，调用方作为参数传入。
   - ACK 只表示送达，不迁移 Task（REQ-022 b5）。
   - 本任务不把投递循环接入 host：host 的停止与锁的顺序（ADR-016 决定 12）由 M2-T05/T06 一起处理。
5. **Developer 的 TaskResult**（`Store::accept_task_result`）。
   - **不处理、也不记录**的情况（返回错误，什么都不写）：
     - status 不是 COMPLETED：返回 Unsupported，由 M2-T16/T19 处理；
     - Attempt 不属于该 Task：IntegrityViolation，属于调用方的错误；
     - 有验证角色未绑定，或者该 Task 在当前 spec 下没有 AC：整体拒绝。没有 AC 就不创建 QA attempt。
   - **重放与键复用**：
     - 以 `child_id(attempt_id, "result")` 为事件 id，事件 payload 中以规范文本保存完整的 TaskResult。比较的是文本，不是重新解析后的数值（M2T04R-152）。
     - 同一 Attempt 再提交相同的结果：原样返回结果，不重复生成交接。
     - 同一 Attempt 提交不同的结果：KEY_REUSE（REQ-022 b4，M2T04R-52）。被拒的结果同样处理。
   - **拒绝**（写一条 `task_result.rejected` 事件，不改任何状态），按以下顺序判定，第一个不符者给出原因：
     1. 该 Task 不是结果所报角色的：ILLEGAL_TRANSITION。
     2. role_epoch 不等于该角色的当前绑定，或不等于该 Attempt 运行时的 epoch：STALE_ROLE_EPOCH。
     3. Attempt 不是该 Task 的现行 Attempt：STALE_LEASE_EPOCH（M2T04R-53）。现行 Attempt 指状态为 RUNNING 或 SETTLED，并且该 Task 之后没有更新的 Attempt。更新指插入顺序（attempts 的 rowid；attempts 只插入、从不删除。今后若重建该表，迁移必须保留 rowid 顺序），不是 attempt_id 的文本顺序：`attempt-10` 比 `attempt-9` 新（M2T04R-252）。失败、取消、或已被同一 Task 的更新 Attempt 取代的，都不是。判定不看租约行：租约行是项目级槽位，Attempt 结束后可能被其他 Task 的 Attempt 取得（M2T04R-150）。
     4. Task 不在 RUNNING：ILLEGAL_TRANSITION。
     5. 候选不是该 Run 的 FROZEN 候选，或 spec 与 Run 当前 spec 不符，或不是 Run 的当前候选：CANDIDATE_MISMATCH 或 SPEC_MISMATCH。当前候选的定义与消费栅栏共用同一个函数，即最新的 FROZEN 或 VERIFYING 候选（M2T04R-54）。
   - **通过**时在一个事务内：
     1. Task RUNNING→IMPLEMENTED→VERIFYING；
     2. 候选 FROZEN→VERIFYING（带条件的 UPDATE）；
     3. 写 `candidate_ready` 事件（payload 为 task_id、candidate_id、attempt_id、交接 id 与 TaskResult）；
     4. 写两条 outbox 交接消息，收件角色为 qa 与 reviewer，都指向该事件。
   - **交接的来源**：本任务里交接只由 TaskResult 产生。M2-T08/T16 的测试若直接注入 candidate_ready，须经由 TaskResult，或者在那些任务中新增一条幂等的规则：candidate_ready 事件产生交接（M2T04R-62）。
6. **验证交接包**（`handoff::verification`）。
   - ContextHandoff 各字段的来源：

     | 字段 | 来源 |
     |---|---|
     | `run_id`、`task_id` | TaskResult |
     | `role` | qa 或 reviewer |
     | `role_epoch` | 该角色的当前绑定 |
     | `spec_sha256`、`spec_revision` | Run 当前 spec |
     | `candidate` | candidates 行的 6 个身份字段 |
     | `acceptance_ids` | task_requirements 与 acceptance_criteria 在当前 spec 下的交集，排序 |
     | `references` | 空：QA 从 spec 与冻结工件出发（docs/06） |
     | `output_contract` | qa 为 `TaskResult`，reviewer 为 `IndependentReport` |
     | `goal` | Run 的 StartRun 命令中的 goal；没有时为一句固定的中文说明 |
     | `budget_tokens` | 常量，上下文装箱随 M2-T09 |
     | `handoff_kind` | `verification` |

   - 信封各字段：

     | 字段 | 取值 |
     |---|---|
     | `sender_role` | `runtime` |
     | `attempt_id` | Developer 的 Attempt |
     | `causation_id` | candidate_ready 的事件 id |
     | `correlation_id` | 候选 id |
     | `message_id`、`idempotency_key` | `child_id(候选, "verify/<角色>")`，有长度上限（M2T04R-55） |
     | `expected_revision` | VERIFYING 之后的 Task revision |
     | `candidate_id` | 候选 id |

   - 两条交接带同一个 expected_revision：qa 与 reviewer 的产品消费者（M2-T16）不得移动 Task 的 revision，否则后到的一条会以 STALE_REVISION 被拒。
   - `handoffs` 表需要工件存储（package_artifact_id），由 M2-T09/T17 写入。

## 不在本任务内

- 投递循环接入 host；
- 产品的 qa/reviewer 消费者（创建 QA Attempt，M2-T16）；
- 角色重新绑定与 epoch 递增（M2-T07）；
- 候选冻结与 STALE（M2-T10）；
- Commander 决策的重复投递回放（M2-T08）。
