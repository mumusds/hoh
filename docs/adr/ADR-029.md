# ADR-029 · 验收投影、独立报告的入库与候选汇合

状态：提议（2026-11-12；M2-T18；第七版）

## 第七版的更正（设计审查第 6 轮：Codex M2T18D-500..502 FAIL，Claude M2T18D-550..556 PASS）

- **事实不依赖轮次的类别与先后**（-502、-550）：absent 事实按条目由本轮两方自己的报告决定，在轮次的任何关闭（不论类别）写；验收失败的 Issue 不再用 absent 事件，而由状态函数直接看更新候选上该 AC 的展示投影是否满足（行只追加，行本身是验证者的观察）；INVALID 候选上的 absent 与满足不算，候选变为 INVALID 时重算（决定 10）。
- **以 Issue id 再报即仍存在**（-500、-551）：finding 的 id 等于某个 Issue 的 id 时，另按该 Issue 的指纹写 present，不论新 finding 的 severity 与措辞（决定 10，恢复第三版 -150 的规则）。
- **状态函数只决定是否已解决**（-501、-552）：REOPENED 是“曾经 RESOLVED、现在未解决”的历史标签，性质测试比较是否已解决（决定 10，J6）。
- **每个指纹各自重算，observation_id 确定**（-553）；**全范围验证是 absent 的另一来源**（-554，CR-020）；**REQ-055 的 flaky 处置交给 M5-T02，在此之前汇合级 flaky 的出口是要求新提交的返工**（-555，CR-020）；**汇合按当时的状态重算参与者可确认的 critical/high 集合**（-556，决定 11）。

## 第六版的更正（设计审查第 5 轮：Codex M2T18D-400..403 FAIL，Claude M2T18D-450..455 FAIL）

- **设计修正：Issue 的状态是观察事实的函数**（-401、-402、-451、-452、-453；同一类问题第三次出现——-254、-300/-351——按 docs/19 先定规则再改）。“仍存在”（present）与“已修复”（absent）的观察都写成带候选的事实；Issue 是否 RESOLVED 由一个状态函数从事实的**集合**求出（最新的观察按候选的冻结次序取，同一候选上 present 优先），唯一的写者在每次写入事实的事务里重算该指纹的全部 Issue。终态只取决于事实的集合，与结算、关闭的先后无关；决定 9 的 REOPENED 并入这一个写者（决定 9、10，J6）。
- **Runtime 导出的 native_attempt 状态为 COMPLETED**（-400、-450）：`report_of` 只为 COMPLETED 的结果构造报告与导出，导出的 `status` 由固定的 `SETTLED` 改为受锁 release-policy 接受的 `COMPLETED`，并有经 host 结算的报告行为 CURRENT 的产品路径断言（决定 7）。
- **REJECTED 报告不产生观察事实**（-452）。
- **CR-020 在收敛之前为 PROPOSED**（-403、-454）；**汇合级 flaky 的出口是要求新提交的返工或 REQ-055 的处置**（-455）。

## 第五版的更正（设计审查第 4 轮：Codex M2T18D-300..302 FAIL，Claude M2T18D-350..359 PASS）

- **确认的对象是送达的 Issue id，“仍存在”在结算时成为事实**（-300、-350、-351）：条目 = 本轮 `confirm_set` 中同指纹的 Issue id，送达时固定（`confirm_ids`），之后不因兄弟轮次改变状态而重选；RESOLVED 只写这些 id 中仍为 OPEN/REOPENED 的；验证者的结算事务把“仍存在”（确认条目 OPEN，或以 id、指纹再报）写成 `issue.observed_present`，RESOLVED 要求同一或更新候选上没有这样的事实，已 RESOLVED 的则由它在同一事务置 REOPENED——两种关闭顺序终态相同（决定 9、10）。
- **测试计划**（-302、-353、-354）：兄弟轮次的类别按送达与 severity 断言；取消源的轮次产生 critical finding 时断言 R1 failed、C REJECTED、无汇合、T2 refreeze，决定 11 写明后果；R3 跑另一个 AC 的检查；J6 与快照的残留文字（-301、-352）。
- **ReportIntake 带 native 的 session_ids 与 status**（-355）；**扫描的允许位置按函数**（-356）；**TEST-053-05 的退路只在明确的 v0.1 标志下 PASS**（-357）；**M5-T02 的出口不含豁免**（-358）；**重跑的要求只给 QA**（-359）。

## 第四版的更正（设计审查第 3 轮：Codex M2T18D-200..203 PASS，Claude M2T18D-250..261 PASS）

- **确认分批推进、按指纹去重**（-200、-251）：确认条目按指纹合并（确认一个指纹即确认它的全部 Issue）；轮次的 `unconfirmed` 只看本轮带描述送达的条目；汇合另要求确认集合里 critical/high 的指纹全部 RESOLVED，否则 inconclusive、重新验证送下一批（决定 10、11）。
- **unconfirmed 的精确定义**（-254）：恰为 RESOLVED 写入条件的否定，passable 要求它为 false、flaky 优先不变；写入与分类读同一报告集；同一候选上任一轮次观察到仍存在即不写 RESOLVED（决定 10）。
- **验收失败的 Issue 由满足解决**（-250）：每个 passable 关闭（轮次与汇合）对范围内、在该候选上展示投影满足（PASS 或合规 DEGRADED）的 AC 解决更早候选上的验收失败 Issue；id 按 (候选, AC, 测试)、幂等（-253），唤醒标注同改写请求（-258）（决定 9、10）。
- **汇合等候选上的每个轮次关闭**（-252），含源 Task 全部取消的轮次（决定 11）。
- **返工上下文按指纹加载 Issue**（-201）；**原生会话不相交的核对移到 store 侧**，与 SESSION_NOT_INDEPENDENT 同一出口（-256）（决定 7、11）。
- **重新验证的强制作用域写明重跑范围内 AC 的场景检查**（-261）；**快照的 qa 只把 PASS 降为 UNKNOWN**（-203、-255）；**决定 2 与决定 14 的规则 16 文字一致**（-202）；**扫描的允许位置写明**（-257）；**CR-020 也改 M5-T01 的拆分条款**（-259）；**TEST-053-05 用默认绑定（QA 为 pi），v0.1 的两个 claude 只作退路并记入 verdict**（-260）。

## 第三版的更正（设计审查第 2 轮：Codex M2T18D-100..102 FAIL，Claude M2T18D-150..164 FAIL）

- **仍存在的 critical/high Issue 使轮次 failed，未确认的使它不可通过**（-150、-153）：确认集合里 critical/high 的 X 被任一方写 OPEN 或以它的 id、指纹再报 → 本轮失败输入（项 `issue:<X 的指纹>`），与新 finding 的 severity 无关；两方都送达而没有一方确认 RESOLVED → 本轮不可通过（inconclusive，重新验证有上限，用尽交决策）；Task 取消后留下的由 M5-T02 的全范围验证确认（决定 10、11，CR-020）。

- **REPLACE 也被拒**（-152）：每个连接另执行 `PRAGMA recursive_triggers = ON`（决定 6）。

- **只有带描述送达的才算送达**（-156），critical/high 优先进入 50 条（决定 10）。
- **验收失败的 Issue 每个 (候选, AC, 测试) 一条**（-157），跨候选靠指纹（决定 9）。
- **门禁谓词写明 spec 摘要一致**（-158）；**INSUFFICIENT 不限报告状态**（-159）；**快照的 QA 汇总要求每个范围内 AC 有观察**（-163）；**host 核对 native_attempt 的 session_ids 与开发会话不相交**（-162）。
- **计数的 AC 集合一个**（-102）：passing、accepted、total 同一集合（决定 5）。
- **移交**（-161）：CR-020 给 M2-T13 加对 M2-T18 的依赖，并写明汇合级 NEED_DECISION 的出口（重新验证或返工，都开新的栅栏编号）；UI 的进度按需求计。测试接缝与 TEST-054-05 的补充断言（-164），S8 的余项措辞（-160）。

## 第二版的更正（设计审查第 1 轮：Codex M2T18D-01..05 FAIL，Claude M2T18D-50..61 FAIL）

- **RESOLVED 要验证者的正向观察**（-02、-04、-05、-50）：确认清单进入验证者 Prompt 的强制作用域、不可裁剪，实际送达的 Issue id 记入该 Attempt 的上下文记录；只确认来源轮次已关闭的 Issue；passable 的轮次里至少一方在 TaskResult.issues 里正向确认、两方都没有再报才 RESOLVED；REOPENED 只由冻结晚于解决它的候选的观察触发（决定 10、9）。
- **汇合的幂等与返工上下文**（-01、-03、-53、-61）：汇合以自己的 `verification.joined` 事件判幂等，栅栏成立而没有汇合事件即汇合（含 M2-T16 留下的状态）；返工上下文能解析汇合来源；写 ACCEPTED 的行数不为 1 时写 integrity_violation 并跳过这次汇合，不回滚整个对账（决定 11）。
- **检查级状态**（-51、-52）：有 FAIL 结果行的检查证据按有结论的 FAIL 计；轮次的检查维度与 AC 维度同一可见性（开轮时已有的加本轮的）；重新验证轮次的强制上下文列出候选上缺结论的检查（决定 4）。
- **验收失败的 Issue**（-55）：轮次以 failed 关闭时，Runtime 为每个 AC 失败项开一条 Issue（source acceptance），与 finding 的 Issue 并存；它由之后候选上的 PASS 行（验证者的证据）正向解决（决定 9、10）。
- **只追加由数据库强制**（-56）：每个连接装 TEMP 触发器拒绝对 `acceptance_results` 的 UPDATE 与 DELETE，仓储接口真正发出 UPDATE 并观察到拒绝；扫描加 UPSERT（决定 6）。
- **未观察的声明更窄**（-57）：只在 QA 报告 PASS、且该轮没有该 AC 场景检查的任何证据时成立（决定 3）。
- **已验收计数**（-58）：`accepted` 只在候选 ACCEPTED 时计数，另给 `passing`；total 不含已取消的 Task；M2-T13 的 RunResult 用 `requirements_passed`（决定 5，CR-020）。
- **STALE 的翻转在对账里兜底**（-60）：冻结的事务里翻转之外，每个对账按状态翻转，M3-T02 不再需要移交（决定 8）。
- **测试**（-54、-59）：adapter-live.sh 对 qa 特殊处理；TEST-054-05 也断言 `checks` 对空列表与只有无结论的列表为 Inconclusive。

## 决定

1. **模块与范围。** 纯函数在新模块 `hoh_core::verification::acceptance`（展示投影、检查级聚合、指纹的规范化）；SQL 在 persistence：新文件 `persistence/reports.rs`（报告入库、finding→Issue、STALE 标记、RESOLVED/REOPENED）与 `persistence/join.rs`（汇合）；`Reader::acceptance`、`Reader::issue_chain` 与两个 HTTP 列表。M2-T18 不另派验证：AC-054-02 的重派 Review 就是 C2 冻结时已开的轮次（ADR-028 -658）。

2. **展示投影（Q1，AC-053-02，ADR-027:170，done_when）。** `acceptance::display(standing, &Observation, profile: Option<&Profile>) -> Shown{label, why}`，`Observation{rows: Vec<RowFact>, degradable, unobserved_claim}`，`RowFact{status: classify::Row, check_id: Option<String>, live_agents: Option<BTreeSet<String>>}`。标签是封闭集合 PASS、DEGRADED、FLAKY、FAIL、UNKNOWN、BLOCKED、INVALID、STALE、NOT_RUN；`why` 只有 INSUFFICIENT、CANDIDATE_INVALID、CANDIDATE_STALE。求值：
   - `standing`：候选 INVALID → 每个 AC 为 INVALID（CANDIDATE_INVALID）；候选 STALE → STALE（CANDIDATE_STALE）；FROZEN、VERIFYING、ACCEPTED、REJECTED 按行求值（R0：候选 INVALID 即全不满足）。
   - 有 profile 时先按决定 14 删去不满足规则 16 的、outcome 为 PASS 的证据产生的 PASS 行（与 ADR-027 结论 (4) 的“无结论”相同；DEGRADED 行不受影响）。
   - 可降级需求以外的 DEGRADED 行当作 FAIL 行（R8）；然后按次序取第一条成立的：FLAKY（有 FLAKY 行，或 FAIL/UNKNOWN/BLOCKED 行与 PASS/DEGRADED 行并存）> FAIL > UNKNOWN > BLOCKED > INVALID > STALE > NOT_RUN（有 NOT_RUN 行，或没有行；没有行且 `unobserved_claim` 时为 INVALID(INSUFFICIENT)，决定 3）> DEGRADED（只有 PASS 与合规 DEGRADED、至少一条 DEGRADED）> PASS（只有 PASS）。
   - 次序与原则一的 TEST 状态一致（先 FAIL/FLAKY 后 INVALID，ADR-027 -901）；PASS/DEGRADED 之外的任一行使 AC 不满足（原则一）。行的多重集决定结果，与顺序无关。
   - **与裁决投影同一满足集合**（CR-018，ADR-028 -956）：`satisfied(label) ⇔ label ∈ {PASS, DEGRADED}`；对每个多重集、`degradable`、`unobserved_claim`，在 `standing` 可用且 profile 为 None 时 `satisfied(display) ⇔ classify::project(rows) == Ac::Satisfied`（两边都是“行非空、全为 PASS/DEGRADED、DEGRADED 只在可降级需求上”）。`classify::project` 不改；两者只在标签上不同（如 [FAIL, PASS] 展示为 FLAKY、裁决为 Failed；[NOT_RUN, PASS] 展示为 NOT_RUN、裁决为 Flaky）。
   - AC-053-02 的八个序列依次得到 FLAKY、FLAKY、FAIL、UNKNOWN、NOT_RUN、NOT_RUN、PASS、INVALID，只有 [PASS] 为 PASS。

3. **空观察（Q2，REQ-053 失败模式 2，CR-018）。** 只在投影里，从不写行（`acceptance_results.evidence_id` 必须引用证据，而 INVALID 证据会把候选置 INVALID，ADR-027 决定 5；这不是否决）。AC-X 在候选 C 上有**未观察的声明**，当且仅当存在 C 上已关闭、结论不是 superseded 的轮次 R：AC-X 在 R 的范围内，R 的 QA 交了报告（非 REJECTED，任何 status：REQ-053 行为 3 与失败模式 2 说的是“完成而证据为空”，第三版 -159），R 的验证 Attempt 没有任何 check_id 等于 AC-X 场景检查的证据（不论 outcome：受阻、超时的检查有证据而无行，是 NOT_RUN 而不是 INSUFFICIENT，ADR-027 -651），且 `acceptance_results` 里没有 (AC-X, C) 的行出自 R 的验证 Attempt 的证据（第二版，-57）。只算已关闭的轮次（本轮的行在关闭时才写，ADR-028 决定 1）；只算 QA（REQ-053 是 QA 的义务；Reviewer 审代码，它的证据不覆盖每个 AC 是常态）。声明只替换“没有行”的 NOT_RUN，不压过任何行：之后的重新验证写出 PASS 时投影是 PASS——否则展示与裁决的满足集合会不同。裁决侧不变：`project([])` 为 Undetermined，轮次 inconclusive、在同一候选上重新验证，不返工（CR-018“没有观察的 AC 为未定，不返工”）。

4. **检查级状态与历史聚合（R10，ADR-027:170 的移交）。** `acceptance::check_label(runs)` 对一个 check_id 在候选上的全部 `kind = 'check'` 证据（`CheckRun{outcome, reason, fail_lines}`，`fail_lines` = 该证据 `evidence.recorded` 的 observations 有 status 为 FAIL 的结果行；有 FAIL 结果行的证据不论原因都按有结论的 FAIL 计——ADR-027:170“FAIL 行或原因为空的 FAIL 为 FAIL”，第二版 -51）按次序：有 INVALID → INVALID；有结论的 FAIL（outcome FAIL 且原因不在 {TIMED_OUT, NOT_STARTED, INTERRUPTED, INCOMPLETE, PLUGINS_MISSING}，原因为空也算）且另有 PASS/DEGRADED → FLAKY；有结论的 FAIL → FAIL；有 DEGRADED → DEGRADED；有 PASS → PASS；有 BLOCKED → BLOCKED；其余（无结论的 FAIL、其他 outcome）→ UNKNOWN；没有证据 → NOT_RUN。受阻、超时之后重跑通过即满足（ADR-027 原则一）。`acceptance::checks(runs) -> classify::Checks`：任一检查 FAIL/FLAKY → Failed；非空且每个检查 PASS/DEGRADED → Passed；否则 Inconclusive。无结论集合从 closing.rs:24-30 移入 acceptance.rs。**轮次的检查维度也改用它，只读本轮证据**（closing.rs:777-795 换成 `acceptance::checks(本轮证据)`；第三版撤回第二版的“开轮时已有的历史”——那会把兄弟轮次的检查失败算到本轮的源上，并与延迟发布的证据冲突，-101）：同一轮内超时或受阻之后重跑通过的检查由 Inconclusive 变为 Passed，这是原则一的本义，不是放宽（有结论的 FAIL 与 FAIL 结果行仍使轮次 failed）。**失败判定与失败项同源**（第三版，-100）：`acceptance::check_failures(runs) -> Vec<(check_id, reason)>` 给出标签为 FAIL 或 FLAKY 的检查及其原因（outcome 的原因；只因 FAIL 结果行而失败的为 `FAIL_LINES`），`checks` 的 Failed ⇔ 它非空；closing.rs:778-784 的 `conclusive_fail` 与 :865-875 的 check-fail 项都改用它：没有被 FAIL 行定位的失败检查登记 `check-fail:<check>:<原因>`（归全部源，ADR-028 决定 12），所以 failed ⇔ 至少一个有主项（ADR-028 I6、实施更正 6）。汇合读候选上的全部证据（决定 11），轮次只读自己的；二者不同源是有意的：汇合因此 inconclusive 时，重新验证的轮次由下面的上下文得知要重跑哪项。**重新验证轮次的上下文**：以 reverify 开出的轮次（轮次的与汇合的），验证者的强制作用域列出该候选上标签为 BLOCKED 或 UNKNOWN 的检查（有无结论的证据）及其最近的原因，以及范围内投影未定的 AC 的场景检查，要求重跑，并在 **QA** 的强制作用域写明“本轮须重跑范围内每个 AC 的场景检查：轮次只看本轮的证据”（第四版 -261；第五版 -359：Reviewer 不重复执行，轮次的检查维度读两方的证据，QA 的即可）；计划里有而从没运行、也不是这些 AC 的场景检查的（如 soak、需要鉴权的 adapter-live）不列（第三版 -154；persistence/context.rs 的 verification 事实，与纠正原因同一位置）。

   - **验收失败的 Issue**（第二版，-55；REQ-053 行为 5、失败模式 1）：轮次以 failed 关闭、登记 `ac-fail:<AC>:<测试>` 失败项的同一事务里（closing.rs 对账第 2 步；汇合 failed 时同样），Runtime 为每个这样的项开一条 Issue：`issue_id = child_id(候选, "acceptance/<AC>/<测试>")`（`INSERT OR IGNORE`：同一候选上共享该 AC 的两个轮次只有一条，第四版 -253）、`candidate_id` = 该轮候选、severity `high`、description “`<AC>` 在候选 `<C>` 上 FAIL：`<测试>`（证据 `<evidence_id>`）”、report_id 与 finding_id 为 NULL、指纹 `issue_fingerprint("high", "ac-fail <AC> <测试>", [])`；每个 (候选, AC, 测试) 各一条（同一失败在新候选上再现时新候选也有自己的 OPEN Issue，AC-053-01 在每个候选上成立；跨候选的追踪靠指纹，REQ-054 决定 2；第三版 -157）。事件 `issue.opened{…, source: "acceptance"}` 不带 round_id，也没有 report_id，所以它不是任何轮次或汇合的失败输入（该轮已经 failed）；它照常唤醒 Commander，唤醒摘要同改写请求与 finding 一样标注“轮次关闭后由 Runtime 返工”（context.rs:507-511，第四版 -258）。与 finding 的 Issue 并存：QA 写不写 finding，REQ-053 失败模式 1 的 OPEN Issue 都在。
   - **REOPENED**：由决定 10 的唯一写者按状态函数写（第六版；第二版的“只由冻结晚于解决它的候选的观察触发”与第五版的 `issue.observed_present` 一路都并入它）。新的 finding 照样另有一行（每条 finding 都要能回溯到自己的报告）。

10. **RESOLVED 与 REOPENED：状态是观察事实的函数（Q8，CR-018“须有验证者的观察确认修复”，ADR-028 -555；第二版起逐版细化，第六版按设计修正重写）。**
    - **可确认与送达**（不变）：
      - **可确认**：state 为 OPEN 或 REOPENED，candidate_id 不是本轮候选，由一个源 Task 含本轮源之一的更早轮次开出（改写请求按 `issue.opened` 的 round_id，finding 按 report_id → Attempt → 轮次），且开出它的轮次已关闭（-04）。`confirm_set(tx, run, sources, candidate, before_seq)` 是这一个谓词（`before_seq` 取本轮 `round_opened` 的 seq）。
      - **条目**：同指纹的、在本轮 `confirm_set` 里的 Issue 合成一个条目，对象是这些 Issue id，severity 取其中最高（-251、-350）。
      - **送达**：条目进验证者 Prompt 的强制作用域（persistence/context.rs:704 改为扩展 `facts.scope`，不可裁剪；每条只含 Issue id、severity 与 description 的前 300 字符，按 severity 再按开出次序至多 50 条带描述，超出的只以 id 列出），带描述写进的条目的 Issue id 记入该 Attempt 的 `context.packed` 载荷 `confirm_ids`，送达后固定；只以 id 列出的不算送达（-156），本轮不确认，下一批再送。
      - **确认条目**：验证者在 TaskResult 的 `issues`（受锁 protocol schema 允许任意对象）里对每个送达的条目写 `{"issue_id": X, "state": "RESOLVED" | "OPEN", "observed": "<怎样确认的>"}`；完成提交把合法的确认条目记入 `verification.report` 的 `confirmations`（未送达的 id、格式不符的条目丢弃并写诊断，不使结果无效）。
    - **观察事实**（第六版；第七版改）：事件 `issue.observation{observation_id, fingerprint, polarity, candidate_id, issue_ids, source, attempt_id?, round_id?}`，只写不改；`observation_id` = `child_id(<Attempt 或轮次>, "observation/<polarity>/<fingerprint>")`，重放幂等（-553）：
      - `present`（仍存在）：**非 REJECTED** 报告的每条 finding，按它的指纹；它的 id 等于 Run 中某个 Issue 的 id 时**另按该 Issue 的指纹**写一条（不论新 finding 的 severity 与措辞，-500、-551）；确认条目 `OPEN`，按条目的指纹；以上在验证者的结算事务里写，REJECTED 报告不写（-452）。轮次或汇合以 failed 关闭时每个 AC 失败项，按验收失败的指纹（决定 9），在关闭事务里写。
      - `absent`（已修复，只用于 finding 与改写请求的 Issue）：轮次关闭时（**任何**结论，含 superseded，只要两方都有非 REJECTED 的报告；第七版 -550），对本轮送达的每个条目 X：两方 `confirm_ids` 中 X 的 id 交集非空、至少一方确认 `RESOLVED`、且**本轮两方的报告**都没有写 X 的 `OPEN`、没有以 X 的 id 或指纹再报 → 写 absent，`issue_ids` = 该交集（-453）。它只取决于本轮自己的两份报告，不读兄弟轮次，所以与兄弟的结算先后无关；兄弟的 present 由状态函数裁决。
    - **状态函数**（第七版：只决定是否已解决）：候选按 Run 中 `candidate.frozen` 的 seq 排序（`≤` 即冻结不晚于）；INVALID 的候选上的事实与行只对 present 有效，对“已修复”无效（-550）。
      - finding 与改写请求的 Issue i（指纹 f，候选 c_i）**已解决** ⇔ 存在 `absent` 事实 a：i ∈ a.issue_ids、cand(a) 冻结晚于 c_i、cand(a) 不是 INVALID，并且**不存在** f 的 `present` 事实 n 使 cand(a) ≤ cand(n)（同一候选上 present 优先）。
      - 验收失败的 Issue i（AC a、测试 t、指纹 f，候选 c_i）**已解决** ⇔ 存在冻结晚于 c_i、不是 INVALID 的候选 c，a 在 c 上的展示投影满足（决定 2：PASS 或合规 DEGRADED；行只追加，行本身是验证者的观察，不要求出自 passable 的关闭，-250、-502），并且不存在 f 的 present 事实 n 使 c ≤ cand(n)。
      - 状态：已解决 → RESOLVED；未解决 → 曾经 RESOLVED 的为 REOPENED（历史标签），否则保持 OPEN 或 REOPENED（-501、-552）。“已解决”是事实与行的集合的函数，与结算、关闭的先后无关；标签 REOPENED 记录历史，不参与任何判定（分类与门禁只看 OPEN/REOPENED 与 RESOLVED 之分）。
    - **唯一的写者**：`issues::settle_fingerprint(tx, run, f)` 在写入 f 的任何观察事实、登记 f 的新 Issue、在含 a 的范围的关闭发布 a 的行（验收失败的 Issue 的指纹各自调用，-553）、以及候选变为 INVALID（对该候选上有事实或行的指纹）的同一事务里调用，按状态函数重算 Run 中 f 的全部 Issue，只对“已解决”改变的写 `issue.resolved{issue_id, observation_id | evidence_ids}` 或 `issue.reopened{issue_id, by}`（事件 id 由 (issue, 依据) 确定，重放幂等）。没有改变即什么也不写。决定 9 的 REOPENED 不另写。
    - **全范围验证**（M5-T02，-554）：发布门禁的全范围验证对遗留的 critical/high Issue 的确认按同一条目规则写 absent、经同一写者，验收失败的 Issue 由它写出的行按同一状态函数解决（CR-020）。
    - **进入分类**（-150、-153、-254）：对轮次 R 的送达条目 X——`still_present(X)` ⇔ 存在 X 的指纹的 `present` 事实，候选为本轮候选或冻结更晚（含本轮两方结算时写下的）；`confirmed(X)` ⇔ 两方 `confirm_ids` 中 X 的 id 交集非空、至少一方确认 `RESOLVED`、不是 still_present（分类用它；absent 事实只看本轮两方的报告，见上）；`unconfirmed(X)` ⇔ 两方都带描述送达了 X 的某个 id、不是 still_present、也不是 confirmed。X 为 critical/high 时 still_present → `failing_issues`（项 `issue:<X 的指纹>` 归全部源），有 unconfirmed → 输入 `unconfirmed = true`；`classify` 的次序 failed > flaky > passable（另要求 `unconfirmed` 为 false）> inconclusive。medium/low 的 X 不进分类。
    - **分批推进**（-200、-251）：轮次只为本轮送达的条目负责；汇合另有输入（决定 11）：J 的各轮的确认集合之并（Issue id）里仍有 critical/high 的 Issue 不是 RESOLVED → `unconfirmed = true` → 汇合 inconclusive → 各链重新验证，下一轮的清单不再含已 RESOLVED 的、送下一批；REVERIFY_LIMIT 限制批数，用尽交决策。
    - **角色契约**（resources/prompts/qa.md:57、reviewer.md:55，产品内容，不是受锁契约）：送达的每个条目写一条确认条目；已修复的不写 finding，仍存在的以该 Issue 的 id 写 finding。

11. **汇合（Q11、Q12，AC-054-05，CR-018，ADR-028 I4、I5、移交）。** `join::join(tx, run, candidate, rounds, ctx)` 在对账里栅栏成立时调用（closing.rs:1343-1408）。幂等以汇合**自己的**提交判（第二版，-03）：join_id = `child_id(C, "join/<轮数>")`（与栅栏事件同一编号），汇合写 `verification.joined{join_id, …}`（事件 id `child_id(join_id, "joined")`）；栅栏事件已存在而没有 `verification.joined` 时照样汇合（M2-T16 留下的“栅栏已写、候选仍 VERIFYING”的库在第一个对账 tick 即被汇合），栅栏事件不存在时先写它再汇合，二者同一事务。迭代按决定 13 计，已由栅栏点的旧计数（M2-T16 的 closing.rs:1404）计过的候选不再计（`iteration` 本就按 `child_id(C, "iteration")` 幂等）。
    - **前提**（第四版 -252）：C 上的**每个**轮次都已关闭（后果，-353：源全部取消的轮次若 failed，C 照 ADR-028 被判 REJECTED，没有汇合；其余源经 refreeze 在同一树上冻结 C′，该轮的 Issue 的来源轮次源不含它们，不进 C′ 的确认集合，留给 M5-T02 的全范围验证确认），含源 Task 全部取消的轮次（它的验证者照常结算、轮次照常关闭，ADR-028 第 1 步只在候选不再 VERIFYING 或 Run 取消时取消验证者）；栅栏的条件（closing.rs:1343-1408）加这一条，所以汇合之后不会再有 C 上的报告或行发布。
    - **输入**：参与者 P = 在 C 上参与过轮次、不是 CANCELLED 的开发 Task（栅栏保证它们都 VERIFYING、当前轮次在 C 上且 passable、无未消费项）；J = 各 P 的当前轮次（即每条重新验证链的当前轮次）。QA、Review = `report_status(J, role)`（决定 5 的合并：任一 FAIL → Fail，否则任一 UNKNOWN → Unknown，否则任一缺 → NotRun，否则 Pass；C 为 VERIFYING 即最新候选，它的非 REJECTED 报告都是 CURRENT）；确定性检查 = `acceptance::checks`（C 上全部 `kind = 'check'` 证据，决定 4）；AC 覆盖 = J 的范围的并集，每个 AC 用 `classify::project` 投影 C 上该 AC 的**全部**行（原则一的历史；轮次只看开轮时已有加本轮的行，-754）；failing_issues = C 上全部轮次按来源谓词的未关闭 Issue（`round_issues` 对每个轮次取并集）；outside_failed = C 上范围之外的 AC 的 FAIL 行；unconfirmed = 按汇合时的状态重算的参与者可确认集合（`confirm_set` 对 P 与 C 在此刻求值，含送达之后才被 REOPENED 的，第七版 -556）里仍有 critical/high 的 Issue 不是 RESOLVED（决定 10 的分批推进）。输入与失败项由与 `classify_round`（closing.rs:753-890）共用的推导函数给出，所以 failed ⇔ 至少一个失败项（ADR-028 实施更正 6）。`class = classify(&input)`；写 `verification.joined{candidate_id, join_id, class, inputs, rounds, tasks}`。
    - **passable**：先对每个 P 求门禁谓词（决定 12 的 `requirements_passed(C)` ⊇ P 的需求，且 C 是 Run 唯一在用的候选）。全部成立：`UPDATE candidates SET state='ACCEPTED' WHERE candidate_id=C AND state='VERIFYING'`（改动行数不为 1 时——按构造不会——不回滚整个对账：这次汇合不写任何迁移，只写 `integrity_violation{candidate_id, join_id, reason: "join_candidate_not_verifying"}` 与 `verification.joined{class, outcome: "skipped"}`，其余对账照常提交，第二版 -61），`candidate.accepted{candidate_id, join_id}`；每个 P 以 CAS VERIFYING→ACCEPTED，`task.accepted{task_id, candidate_id, join_id, by: "runtime"}`；迭代按决定 13。任一不成立（按构造不会：passable 已要求范围内每个 AC 只有 PASS/合规 DEGRADED 行）：不写 ACCEPTED，写 `integrity_violation{candidate_id, join_id, tasks, reason: "join_gate_disagrees"}`，被拒的 P 置 BLOCKED（NEED_DECISION，`need_decision{reason: "join_gate_refused"}`），栅栏因此不再成立，等决策（fail-closed，候选不部分接受）。
    - **failed**：C 置 REJECTED（带原状态条件），`candidate.rejected{candidate_id, join_id}`；`verification.failures{round_id: join_id, candidate_id, items}`（AC 项归范围含该 AC 的 P，其余归全部 P；I6）；迭代按决定 13；随后同一事务再调用一次 `consume`（closing.rs:947），所以 VERIFYING 的主人当即返工，不留一个 tick 的空档。join_id 占 `round_id` 字段，消费与 `task.rework` 无需新路径；**返工上下文**（persistence/context.rs:830-870 的 `rework()`）对 `round_id` 找不到 `verification.round_opened` 时改读 `verification.joined`（candidate_id、参与 Task、各自范围），所以汇合失败后的下一个 Developer 同样拿到失败项、被拒候选、OPEN Issue 与代码基准（第二版，-01、-53）；对 `issue:<指纹>` 的项（轮次的与汇合的），返工上下文按指纹在整个 Run 里加载该指纹的 Issue（描述、来源报告与 finding id）及本轮的 `observed` 文字，不只看被拒候选上的 Issue（第四版 -201）；`issue:` 项的 `issue.consumed_by_rework` 按 C 上轮次的同指纹 Issue 写。
    - **inconclusive**：对 J 的每个轮次 r，按 r 的源 Task 请求 `Repair::Reverify{root: r.chain_root}`，action_id = `child_id(join_id, "reverify/<r>")`；准许即以 `verification::reverify` 开 r 的下一轮（同样的源与范围），拒绝即这些源 BLOCKED（NEED_DECISION，reverify_exhausted）。与 exits 的 reverify 一支（closing.rs:1186-1236）抽成同一函数。UNKNOWN 永不返工。
    - **flaky**：每个 P 置 BLOCKED（NEED_DECISION），`need_decision{reason: "flaky", candidate_id, join_id}`，与轮次的 flaky 一支（:1237-1263）同一函数。
    - **晚到的行（Q12）**：汇合读全部历史，所以轮次关闭之后才入库、仍在 VERIFYING 候选上的 FAIL 行会使汇合 failed 并登记有主的项。轮次关闭要等候选没有待入库事实（ADR-028 -601），这种行只在崩溃窗口后才可能出现；原则一说它让 AC 不满足，汇合不能越过它。ADR-028 决定 1 的“只作历史、不登记失败项”只约束它所属的轮次。

12. **门禁谓词换成投影（ADR-027:170 的移交，-751；ADR-011:102 的更正）。** `load_evidence` 的需求判定（decide.rs:851-867 的 SQL）抽成 `requirements_passed(tx, run, spec, candidate) -> BTreeSet<requirement>`：需求在当前 spec 下至少有一个 AC，且每个 AC 在 C 上的展示投影满足（决定 2，profile 为 None），且每条满足它的行引用的证据属于 C、check_id 等于该 AC 的 check_id、outcome 等于该行的状态（PASS 行配 PASS 证据，DEGRADED 行配 DEGRADED 证据，保留原有的“出自自己的场景检查”一项），且 C 的 spec_sha256 等于 Run 当前 spec 的摘要（ADR-011、decide.rs:855 现有的条件，抽取时保留，第三版 -158）。`load_evidence` 对 ACCEPTED 的候选调用它，汇合对 VERIFYING 的 C 调用它，所以“由 Runtime 按门禁谓词接受源 Task”与 Commander 的门禁是同一个函数。可降级需求上合规的 DEGRADED 从此计为通过（替换 decide.rs:863 与 ADR-011“DEGRADED 暂不计为通过”的临时规则）；不可降级需求上的 DEGRADED 投影为 FAIL，不通过。`Evidence::gate`（decision.rs:254-292）与“唯一在用候选”的规则不变。

13. **pace 与迭代（ADR-028 决定 10、11 的更正）。** 删去 retry.rs:597-606 的过渡例外（`|| joining.contains(..)`），`sources_and_joining` 只返回 sources（汇合与栅栏在同一事务，不存在“等汇合”的状态）。迭代：汇合点不再无条件计数（删去 closing.rs:1404）；汇合 passable 时以 verdict `passable`、failed 时以 `repair` 调 `iteration`（每候选至多一次，`child_id(C, "iteration")`，已由更早的 repair/invalidated 关闭计过即无操作）；inconclusive 与 flaky 不计（与轮次相同）。

14. **profile 与规则 16（Q6）。** `Profile{live_agents: BTreeMap<check_id, BTreeSet<agent>>}` 取自 release-policy 的 profile；给出时，`check_id` 在 profile 的 live_agents 里、而 `RowFact.live_agents`（该证据 live-sessions 的 agent 集合，没有为空）不包含所要求全部 agent 的、outcome 为 PASS 的证据产生的 PASS 行被删去（无结论）；DEGRADED 行不受影响（原则一结论 (4) 与 release_gate.py:186 只在 PASS 时核对，ADR-027 -503；第三版 -155）。产品的分类、门禁与快照一律传 None：候选门禁没有 profile（只有 `releases.profile`，SQL:36）；由发布门禁（M5-T02）传入，见“移交”。有 profile 时投影只会更严（满足 ⇒ 无 profile 也满足），不影响决定 2 的等价。

15. **追溯链（AC-054-04，done_when“可追溯到原始会话”）。** `Reader::issue_chain(issue_id) -> IssueChain{issue, report{report_id, state, path, sha256}, raw{path, sha256}}`（只读库）与 `verification::report::verify_chain(project, &IssueChain) -> ChainCheck{report_digest, finding_present, raw_digest, native_digest, session_in_native, stdout_is_raw}`：用 `objects::get`（按名重算摘要，objects.rs:293-304）读报告对象，找到 `finding_id` 的 finding，核对报告里 raw_session、native_attempt 的引用等于登记的 artifact 行并重算两个对象的摘要，native_attempt 的 `session_ids` 含报告的 session_id、`stdout_sha256` 等于 raw_session 的摘要。

- **J1** `acceptance_results` 只追加：每个连接的 TEMP 触发器拒绝 UPDATE 与 DELETE，源码里没有 UPDATE/DELETE/REPLACE/UPSERT（扫描保证），仓储的改写接口被数据库拒绝且行不变。
- **J2** 对每个行多重集，候选可用且无 profile 时 `satisfied(display) ⇔ project == Satisfied`；候选 INVALID/STALE 时没有 AC 满足；已验收计数、快照与门禁只经 `display`。
- **J3** 候选 ACCEPTED 只由汇合写，当且仅当 `classify(汇合输入) == Passable` 且每个参与者满足门禁谓词；候选与参与者在同一事务一起 ACCEPTED（ADR-028 I4、I5）。
- **J4** 非 REJECTED 报告的每条 finding 恰好一行 Issue，在记录该报告的结算事务里登记；REJECTED 报告没有 Issue；finding 与验收失败的 `issue.opened` 不带 round_id，low/medium finding 与验收失败的 Issue 永不使轮次或汇合 failed；每个 failed 关闭的 AC 失败项在该候选上恰有一条验收失败 Issue（id 按 (候选, AC, 测试)）。
- **J5** REJECTED 报告不进任何分类、快照与门禁；STALE ⇔ 之后有别的候选冻结或 `candidate.stale` 写着它的候选（冻结事务与每个对账 tick 保证）；汇合与快照只读最新候选上的 CURRENT 报告。
- **J6** Issue 的 RESOLVED/REOPENED 只由 `issues::settle_fingerprint` 写；“已解决”是观察事实、行与候选 INVALID 的集合的函数（与结算、关闭的先后无关），REOPENED 只是历史标签；absent 事实只取决于本轮两方自己的报告（任何结论的关闭），只及两方都送达的 id；验收失败的 Issue 由更新的、非 INVALID 候选上该 AC 的满足解决；present 事实来自非 REJECTED 报告的 finding（含按其 id 对应的 Issue 的指纹）、确认条目 OPEN 与 failed 关闭的 AC 失败项；确认集合里 critical/high 的条目 still_present 即失败输入，送达而未确认即轮次不可通过，汇合按此刻的状态要求可确认的 critical/high Issue 全部 RESOLVED。
- **J7** 验证 Task 不进范围内 AC、已验收计数与门禁；它们的 ACCEPTED 只表示验证工作完成（ADR-028 决定 10）。
- **J8** 失败的汇合按 I6 登记至少一个有主的项，并在同一事务被消费或附上；它的返工上下文经 `verification.joined` 解析。
- **J9** 汇合对每个 (候选, 栅栏编号) 至多一次，以 `verification.joined` 判；栅栏成立而没有它即汇合。

- **TEST-053-05（adapter-live，S7）**：crates/hoh-app/tests/verification_live.rs 里忽略的测试 `verification_live_candidate_to_qa`（名字不含 TEST id，与 scripts/product/adapter-live.sh:1-11 的约定相同；脚本加一行 `live qa verification_live verification_live_candidate_to_qa hoh-app` 与一个 case `('qa', 'TEST-053-05', …)` 读 `qa-live-verdict.json`；`live()` 对 qa 像 doctor 一样特殊处理：可用性看 claude 二进制，root 时 BLOCKED，第二版 -54；脚本的这一路径以假 claude 的 bundle 测试覆盖），默认绑定（Developer claude、QA pi、Reviewer codex，AC-053-05 的 given）；pi 或 codex 未装或未登录时，只有在明确的 v0.1 标志（`HOH_LIVE_PROFILE=v0.1`）下才退回 claude 并可 PASS（v0.1 允许两个 claude 会话），否则 BLOCKED；verdict 的 `agents` 记下实际绑定（第四版 -260，第五版 -357：规则 16 对整个检查的会话取并集，不能靠它挡住退路），Commander 为不提议的假 Agent；植入缺陷仓库中 AC-B 的确定性测试必然失败。verdict：PASS 当且仅当 QA 与 Developer 的 HoH 会话不同且 native_id 不同、都在 sessions；QA 报告行 candidate_id=C、native_attempt 的 session_ids 含其 session_id；AC-B 标签 ∈ {FAIL, UNKNOWN, NOT_RUN, INVALID}；C 不是 ACCEPTED。claude 缺失、未登录或以 root 运行为 BLOCKED（SKIPPED），从不由假 Agent 得 PASS；会话、版本与 resolved model 写进 verdict 的 sessions。

## 未采用

- **进库文件的 SQL 触发器**：要新迁移文件进 contracts/sql（受锁），需 CR；每个连接的 TEMP 触发器有同样的效果而不改受锁文件（决定 6）。
- **只靠 QA 的 finding 开 Issue**（第一版）：真实 QA 不写 finding 时 REQ-053 失败模式 1 的 OPEN Issue 不存在（-55）；改为 Runtime 另开验收失败的 Issue（决定 9），不带 round_id，不成为失败输入。
- **以“被问到而没有再报”确认修复**（第一版）：装箱可以裁掉清单、验证者可以忽略它，无法与“确认已修复”区分（-02、-50）；改为强制作用域 + 记录送达 + TaskResult.issues 的正向确认。
- **把没有 finding 的 FAIL 报告当作无效输出纠正**：会推翻 ADR-028 -403 已收敛的用例；该轮仍以报告项 failed、返工。
- **空观察写成不否决的 INVALID 行或新证据种类**：违反 ADR-027 决定 5（INVALID 证据否决候选）与文件扫描。
- **报告“候选不是 VERIFYING”即 STALE**：被兄弟轮次判 REJECTED 的候选上的轮次会丢掉它的报告项（-850）。
- **RESOLVED 在单份报告结算时写**：另一验证方可能在同一轮再报它；passable 关闭同时看到两方。
- **finding 的 Issue id 按序号**：finding_id 才是 AC-054-04 要的引用；重复 id 改为输出无效。
- **复制 finding evidence 进对象库**：路径多在已删除的运行目录，摘要指向摘录而非文件，核对不出有意义的东西；链只要求到 raw_session。
- **汇合只读各轮的行**：违反原则一的历史规则（ADR-027:170）。

## 与倾向不同之处

1. 轮次分类读本轮的非 REJECTED（CURRENT 或 STALE）报告，汇合与快照读 CURRENT：ADR-028 -850 要求被兄弟判 REJECTED 的候选照常分类（决定 7、8）。
2. STALE 按“之后有别的候选冻结或 `candidate.stale`”判，并在冻结时翻转已有的 CURRENT：SQL:34 的注释与 -850，而不是“候选不是 VERIFYING”。
3. 未观察的声明只取 QA，且只在没有行时生效：否则重新验证的 PASS 会被它压住，展示与裁决的满足集合不同（CR-018）。
4. RESOLVED 在 passable 的轮次关闭时由两方报告一起判，确认集合扩到两种来源、任何 severity；角色契约改为“已修复不写 finding，仍存在用 Issue id 再报”。
5. 指纹的 locator 去掉 `.hoh/` 下的路径，并删行号与候选、提交的十六进制。
6. 汇合点的迭代改在汇合的有结论结果上计（现行代码无条件计 passable）；失败的汇合在同一事务再 `consume`。
7. 轮次的检查维度也改用按检查的历史聚合（与汇合同一函数）。
