# ADR-029 · 验收投影、独立报告的入库与候选汇合

状态：提议（2026-11-12；M2-T18）

## 决定

1. **模块与范围。** 纯函数在新模块 `hoh_core::verification::acceptance`（展示投影、检查级聚合、指纹的规范化）；SQL 在 persistence：新文件 `persistence/reports.rs`（报告入库、finding→Issue、STALE 标记、RESOLVED/REOPENED）与 `persistence/join.rs`（汇合）；`Reader::acceptance`、`Reader::issue_chain` 与两个 HTTP 列表。M2-T18 不另派验证：AC-054-02 的重派 Review 就是 C2 冻结时已开的轮次（ADR-028 -658）。

2. **展示投影（Q1，AC-053-02，ADR-027:170，done_when）。** `acceptance::display(standing, &Observation, profile: Option<&Profile>) -> Shown{label, why}`，`Observation{rows: Vec<RowFact>, degradable, unobserved_claim}`，`RowFact{status: classify::Row, check_id: Option<String>, live_agents: Option<BTreeSet<String>>}`。标签是封闭集合 PASS、DEGRADED、FLAKY、FAIL、UNKNOWN、BLOCKED、INVALID、STALE、NOT_RUN；`why` 只有 INSUFFICIENT、CANDIDATE_INVALID、CANDIDATE_STALE。求值：
   - `standing`：候选 INVALID → 每个 AC 为 INVALID（CANDIDATE_INVALID）；候选 STALE → STALE（CANDIDATE_STALE）；FROZEN、VERIFYING、ACCEPTED、REJECTED 按行求值（R0：候选 INVALID 即全不满足）。
   - 有 profile 时先按决定 14 删去不满足规则 16 的 PASS/DEGRADED 行（与 ADR-027 结论 (4) 的“无结论”相同）。
   - 可降级需求以外的 DEGRADED 行当作 FAIL 行（R8）；然后按次序取第一条成立的：FLAKY（有 FLAKY 行，或 FAIL/UNKNOWN/BLOCKED 行与 PASS/DEGRADED 行并存）> FAIL > UNKNOWN > BLOCKED > INVALID > STALE > NOT_RUN（有 NOT_RUN 行，或没有行；没有行且 `unobserved_claim` 时为 INVALID(INSUFFICIENT)，决定 3）> DEGRADED（只有 PASS 与合规 DEGRADED、至少一条 DEGRADED）> PASS（只有 PASS）。
   - 次序与原则一的 TEST 状态一致（先 FAIL/FLAKY 后 INVALID，ADR-027 -901）；PASS/DEGRADED 之外的任一行使 AC 不满足（原则一）。行的多重集决定结果，与顺序无关。
   - **与裁决投影同一满足集合**（CR-018，ADR-028 -956）：`satisfied(label) ⇔ label ∈ {PASS, DEGRADED}`；对每个多重集、`degradable`、`unobserved_claim`，在 `standing` 可用且 profile 为 None 时 `satisfied(display) ⇔ classify::project(rows) == Ac::Satisfied`（两边都是“行非空、全为 PASS/DEGRADED、DEGRADED 只在可降级需求上”）。`classify::project` 不改；两者只在标签上不同（如 [FAIL, PASS] 展示为 FLAKY、裁决为 Failed；[NOT_RUN, PASS] 展示为 NOT_RUN、裁决为 Flaky）。
   - AC-053-02 的八个序列依次得到 FLAKY、FLAKY、FAIL、UNKNOWN、NOT_RUN、NOT_RUN、PASS、INVALID，只有 [PASS] 为 PASS。

3. **空观察（Q2，REQ-053 失败模式 2，CR-018）。** 只在投影里，从不写行（`acceptance_results.evidence_id` 必须引用证据，而 INVALID 证据会把候选置 INVALID，ADR-027 决定 5；这不是否决）。AC-X 在候选 C 上有**未观察的声明**，当且仅当存在 C 上已关闭、结论不是 superseded 的轮次 R：AC-X 在 R 的范围内，R 的 `round_closed.result_status.qa` 为 COMPLETED（QA 交了有效结果与报告），且 `acceptance_results` 里没有 (AC-X, C) 的行出自 R 的验证 Attempt 的证据。只算已关闭的轮次（本轮的行在关闭时才写，ADR-028 决定 1）；只算 QA（REQ-053 是 QA 的义务；Reviewer 审代码，它的证据不覆盖每个 AC 是常态）。声明只替换“没有行”的 NOT_RUN，不压过任何行：之后的重新验证写出 PASS 时投影是 PASS——否则展示与裁决的满足集合会不同。裁决侧不变：`project([])` 为 Undetermined，轮次 inconclusive、在同一候选上重新验证，不返工（CR-018“没有观察的 AC 为未定，不返工”）。

4. **检查级状态与历史聚合（R10，ADR-027:170 的移交）。** `acceptance::check_label(runs)` 对一个 check_id 在候选上的全部 `kind = 'check'` 证据（`CheckRun{outcome, reason}`）按次序：有 INVALID → INVALID；有结论的 FAIL（outcome FAIL 且原因不在 {TIMED_OUT, NOT_STARTED, INTERRUPTED, INCOMPLETE, PLUGINS_MISSING}，原因为空也算）且另有 PASS/DEGRADED → FLAKY；有结论的 FAIL → FAIL；有 DEGRADED → DEGRADED；有 PASS → PASS；有 BLOCKED → BLOCKED；其余（无结论的 FAIL、其他 outcome）→ UNKNOWN；没有证据 → NOT_RUN。受阻、超时之后重跑通过即满足（ADR-027 原则一）。`acceptance::checks(runs) -> classify::Checks`：任一检查 FAIL/FLAKY → Failed；非空且每个检查 PASS/DEGRADED → Passed；否则 Inconclusive。无结论集合从 closing.rs:24-30 移入 acceptance.rs。**轮次的检查维度也改用它**（closing.rs:777-795 换成 `acceptance::checks(本轮证据)`）：同一轮内超时后重跑通过的检查由 Inconclusive 变为 Passed，这是原则一的本义，不是放宽（FAIL 仍使轮次 failed）；失败项的推导（closing.rs:847-878）不变。

5. **快照、已验收计数与读取接口（Q3，AC-053-04，REQ-053 失败模式 5，docs/07:39）。**
   - **Run 的最新候选**：该 Run 最后一次 `candidate.frozen` 事件（按 seq）的候选，不论状态（`outbox::current_candidate` 只取 FROZEN/VERIFYING，outbox.rs:327-348，汇合 ACCEPTED 之后它为空，不能用）。
   - **范围内的 AC**：Run 的开发 Task（排除 `verifier_tasks`，persistence/verification.rs:452-467；它们本就没有 task_requirements，过滤是明写的防线）的 task_requirements 在 Run 的 spec 下的全部 AC。
   - `Reader::acceptance(run_id) -> AcceptanceView{candidate{candidate_id, state}, spec_id, acs: [{ac_id, requirement_id, label, why, rows}], accepted, total, qa, review, checks: [{check_id, label}], watermark}`：每个 AC 的标签是决定 2 对最新候选上该 AC 的全部行（spec 为 Run 的 spec）的投影；`accepted` = 标签满足的 AC 数（候选 INVALID 或 STALE 时为 0）；`qa`、`review` 为该角色的报告状态 `report_status(rounds, role)`（汇合同用，决定 11）：最新候选上各参与开发 Task 的当前轮次里该角色最新的 CURRENT 报告，合并规则 FAIL > UNKNOWN > NOT_RUN > PASS，没有为 NOT_RUN）；没有候选时 acs 全为 NOT_RUN、accepted 为 0。一个读事务。
   - HTTP（受锁 openapi 已声明，`Page` 的 items 是任意对象，不需 CR）：`GET /v1/runs/{run_id}/acceptance` 的 items 为 Run 每个候选（新者在前）的每个范围内 AC 的 `{spec_id, spec_revision, candidate_id, candidate_state, ac_id, label, why, latest}`；`GET /v1/runs/{run_id}/issues` 的 items 为 `{issue_id, candidate_id, severity, state, fingerprint, description, report_id, finding_id}`；分页、limit 1..500 与游标沿用 `list_runs`（http.rs:930-982）；getRun 的 `projection` 加 `acceptance{candidate_id, candidate_state, accepted, total}`（`projection` 是自由对象）。契约测试按受锁的 Page schema 校验两者（M2-T12 的“M2 用到的端点有契约测试”）。

6. **只追加（Q7，REQ-053 失败模式 4）。** 产品没有改写或删除 `acceptance_results` 的路径。仓储接口 `Store::update_acceptance_result(key, status)` 的契约就是拒绝：不开写事务，返回新的 `PersistError::AppendOnly("acceptance_results")`，行不变。`scripts/product/persistence_scan.py` 加一条规则：Rust 源码里出现作用于 `acceptance_results` 的 `UPDATE`、`DELETE`、`REPLACE`、`INSERT OR REPLACE` 即失败（与“SQL 只在 persistence”同一扫描，static 检查执行）。不加 SQL 触发器（见“未采用”）。

7. **报告的入库（Q5，REQ-054 行为 3、失败模式 1、3，AC-054-01）。** 在验证 Attempt 的结算事务里（`complete_verifier` 的 Settle 一支，completion.rs:242-262）：
   - **host 一侧（文件，提交之前）**：`report_of` 之后调用纯函数 `verification::report::verify(report_bytes, raw_bytes, native_bytes)`：报告合受锁 schema；raw_session、native_attempt 的摘要按对象字节重算并等于报告的引用；native_attempt 合 schema，`session_ids` 含报告的 session_id，`candidate_id`、`role` 与报告相同，`stdout_sha256` 等于 raw_session 的摘要；finding 的 id 在报告内唯一。任一不成立即输出无效：`verification.output_invalid` 与同一轮内的 `Repair::Protocol` 纠正（ADR-028 决定 15 的现有出口），不写行。`VerifierReport` 改为带解析后的 findings（id、severity、summary、evidence 的 path 与 sha256）与 raw_session 的 `ArtifactRow`。
   - **store 一侧（同一事务）** `reports::intake_in(tx, &ReportIntake{attempt_id, report: Value, report_artifact, raw_artifact, native_artifact})`；`Store::record_report(&ReportIntake)` 是它的单独事务形式（TEST-054-01 用），只做入库（行、事件、Issue），不迁移 Task 与 Attempt。报告的 session_id 是 HoH 会话 id（`independent_reports.session_id` 引用 `sessions`，ADR-028 -360），由 Runtime 填写（crates/hoh-app/src/host/completion.rs:213）。report_id = `child_id(attempt_id, "report")`；同 id 已有同内容为无操作，内容不同为 `KeyReuse`。依次求原因（封闭集合，固定次序，`reject_reason` 为 “`CODE: detail`” 以 “; ” 连接）：REPORT_ROLE_MISMATCH（报告 role 不是该 Attempt 的 Task 的 role）；REPORT_SESSION_MISMATCH（报告的 session_id 不是 `attempts.session_id`）；SESSION_ROLE_MISMATCH（`sessions.role` 不是报告的 role，detail 以 “session conflict:” 开头）；SESSION_NOT_INDEPENDENT（session 属于决定 7a 的冲突集合，detail 以 “session conflict:” 开头）；REPORT_CANDIDATE_MISMATCH（候选不是该 Attempt 所在轮次的候选）；REPORT_SPEC_MISMATCH（spec_sha256 不是该候选的）；REPORT_OBJECTS_MISMATCH（报告的 raw_session/native_attempt 引用与给出的 artifact 行的 path、sha256 不同）。有原因 → REJECTED；否则决定 8 判 STALE 或 CURRENT。
   - **7a 冲突集合（一个谓词、两处调用）**：`verification::conflicting_sessions(tx, run, round, role)` = 本轮源 Task 一切 Attempt 的会话 ∪ 此刻 commander、developer 与另一验证角色的绑定会话 ∪ 本轮另一验证 Task 一切 Attempt 的会话。派发的核对（persistence/verification.rs:577-608）改调它（多出 developer 绑定与另一方 Attempt 的会话，是加严）。按构造产品不会命中（会话按 (run, role, epoch) 分开，team.rs:1087）。
   - **写入**：三个 artifact 行照常登记（`register` 幂等，raw 在 OBSERVED 时已登记，runner.rs:797）；`independent_reports(report_id, run_id, candidate_id, role, session_id, spec_sha256, status, state, reject_reason, attempt_id, report_artifact_id, raw_session_artifact_id, created_at)`，artifact id 为 `artifact_id(sha256, path)`（runner.rs:272）；`verification.report` 事件照旧并加 `report_id`、`state`；REJECTED 另写 `report.rejected{report_id, attempt_id, reasons}`，STALE 写 `report.stale{report_ids, candidate_id, reason}`。session_id 不在 `sessions` 里（外键挡住，产品不会发生）时不写行，只写 `report.rejected{report_id: null, attempt_id, reasons: ["SESSION_UNKNOWN: …"]}`。
   - **验证 Task 的去向**：CURRENT 与 STALE 照常（Task→IMPLEMENTED，`finished_in` 的成功一支）；REJECTED（含 SESSION_UNKNOWN）时 Attempt 照常 SETTLED，Task 在 `finished_in` 之前置 BLOCKED（NEED_DECISION），同一事务写 `integrity_violation{attempt_id, report_id, reasons}` 与 `need_decision{reason: "report_rejected"}`——与派发时 SESSION_NOT_INDEPENDENT 的出口相同（ADR-028 决定 10，-361）：同一会话重试只会再被拒；解除归 M2-T13（CR-018）。`finished_in` 只在 Task 仍 RUNNING 时置 IMPLEMENTED（runner.rs:1296），所以不冲突。
   - **谁读哪种状态**：REJECTED 的行任何分类、快照与门禁都不读；轮次分类读**本轮验证 Attempt 的非 REJECTED 报告**（CURRENT 或 STALE），汇合与快照读 CURRENT。`report()`（closing.rs:222-257）改为：本轮 Attempt 中该角色最后一个非 REJECTED 的 `independent_reports` 行（按 Attempt 的 rowid），状态取该行，失败项用的 summary 取同一 Attempt 的 `verification.report` 事件。

8. **过期（Q5c，REQ-054 行为 4、失败模式 2，AC-054-02，SQL:34 的注释）。** 报告 STALE，当且仅当它的候选 C 之后该 Run 又有别的候选冻结（存在 `candidate.frozen`，seq 大于 C 自己的 `candidate.frozen`、candidate_id 不是 C），或 `candidate.stale` 写着 C（M3-T02 的规格变化、ADR-028 的 evidence_unrecoverable）。入库时按此判；之后成立时由一个函数 `reports::stale_reports(tx, run, candidates, reason, by)` 翻转（CURRENT→STALE，写一条 `report.stale{report_ids, reason, by}`，没有可翻转的行时不写）：冻结的插入路径（persistence/candidates.rs:101-148 的 `freeze_in`，与置 STALE 同一事务）对该 Run 新候选之外的一切候选调用它，reason `superseded`；写 `candidate.stale` 的路径（closing.rs:1609-1625，以及 M3-T02 的规格变化）对该候选调用它，reason `candidate_stale`。不按“候选不是 VERIFYING”判：被兄弟轮次判 REJECTED 的候选上的轮次照常分类（ADR-028 -850），它的报告此时仍属于它自己的候选；而 superseded 的轮次本就不分类，所以 STALE 不改变任何轮次的结论。C2 的 review 状态由决定 5 的 `report_status` 读出：C2 上没有 CURRENT 的 reviewer 报告即 NOT_RUN。

9. **finding→Issue、指纹与 REOPENED（Q4、Q9、Q10，REQ-054 行为 5、决定 2、3，REQ-053 行为 5）。**
   - **时机与范围**：在决定 7 的同一结算事务里（早于轮次关闭，ADR-028 -1051），CURRENT 与 STALE 报告的每条 finding 各登记一行 Issue；REJECTED 报告的 finding 不登记（不可信）。Issue 只来自报告的 finding（QA 与 Reviewer）与 M2-T16 的改写请求；Runtime 不为 FAIL 行另开 Issue（见“未采用”）。AC-053-01 的 Issue 由 QA FakeAgent 报告里的 finding 产生。
   - **行**：`issue_id = child_id(report_id, "finding/<finding.id>")`（id 在报告内唯一由决定 7 保证）、run_id、`candidate_id` = 报告的候选、fingerprint、severity、state OPEN、description = summary、report_id、finding_id = finding.id；事件 `issue.opened{issue_id, candidate_id, report_id, finding_id, severity, fingerprint, attempt_id, source: "finding"}`，**不带 round_id**：`round_issues` 的第一支（closing.rs:283-285）对带本轮 round_id 的 `issue.opened` 不看 severity，带上会使 low/medium finding 让轮次 failed；finding 按第二支（report_id → 报告的 Attempt → 本轮，只认 critical/high）归属。所以 low/medium 的 finding Issue 本身从不使轮次或汇合 failed，报告 status=FAIL 仍为 failed（REQ-054 决定 3，-461）。critical/high 的 `issue.opened` 照旧唤醒 Commander（supervise.rs:110，ADR-025 决定 1 的产生方即本任务）；唤醒摘要的“轮次关闭后由 Runtime 返工”（context.rs:507-511）对 `source = "finding"` 同样标注。
   - **指纹**：`issue_fingerprint(severity, text, locator: &[String])`（verification.rs:1081-1089 扩展，改写请求传空 locator）：规范化 = `CAND-<64 hex>` 换成 `CAND`、独立的 40/64 位十六进制换成 `<sha>`、路径式记号后的 `:行[-行][:列]` 删去、空白折叠、小写；locator = finding evidence 的 path 去重排序，去掉 `.hoh/` 下的路径（证据记录与 Attempt 目录含候选与记录 id，随候选变化），同样删行号；哈希输入为 `severity\n规范化文本`，locator 非空时再加 `\n` 与 locator 以 `\n` 连接。所以没有行号与十六进制的改写请求的指纹不变；同一缺陷换候选、换行号仍是同一指纹（REQ-054 决定 2）。
   - **finding 的 evidence**：只是引用，按报告原样留在报告对象里（`path`、`sha256`），不复制、不核对（它们多在已删除的运行目录里，ADR-028 决定 6）；AC-054-04 的链是 Issue → 报告对象 → raw_session 对象（决定 15）。
   - **REOPENED**：同一事务里，Run 中 state 为 RESOLVED、且 id 等于该 finding 的 id 或指纹等于它的指纹的 Issue 置 REOPENED，写 `issue.reopened{issue_id, by_issue, report_id}`。新的 finding 照样另有一行（每条 finding 都要能回溯到自己的报告）。

10. **RESOLVED（Q8，CR-018“须有验证者的观察确认修复”，ADR-028 -555）。**
    - **确认集合**（一个函数、两处调用）`confirm_set(tx, run, sources, candidate, before_seq)`：state 为 OPEN 或 REOPENED、candidate_id 不是 `candidate`、`issue.opened` 的 seq 小于 `before_seq`，且由一个源 Task 含 `sources` 之一的更早轮次开出（改写请求按 `issue.opened` 的 round_id，finding 按 report_id → Attempt → 轮次）的 Issue——两种来源、任何 severity。`context.rs` 的 `confirm_fixed`（:770-812）改调它，`before_seq` 取本轮 `round_opened` 的 seq，所以 Prompt 列出的与关闭时核对的是同一集合。
    - **观察与写入**：轮次 R 以 **passable** 关闭时（两方 CURRENT 报告都是 PASS，没有失败输入），在写 R 的 `round_closed` 的同一事务里（closing.rs 对账第 2 步），对 `confirm_set(R)` 的每个 Issue X：R 的报告里没有 finding 的 id 等于 X 的 id、也没有 finding 的指纹等于 X 的指纹 → X 置 RESOLVED，写 `issue.resolved{issue_id, round_id, candidate_id, reports}`；同指纹而 REOPENED 的 Issue 也在确认集合里，一并处理。非 passable 的轮次不确认（UNKNOWN 不是观察，failed 的候选会被替换），X 留在之后轮次的确认集合里。
    - **角色契约**（resources/prompts/qa.md:57、reviewer.md:55，产品内容，不是受锁契约）改为：标“请确认已修复”的 Issue 仍存在时写一条 finding，id 用该 Issue 的 id、severity 按现状；已修复的**不写** finding（写“已修复”的 finding 会登记为新的 Issue）。受锁报告 schema 没有“已修复”字段，所以确认是“被问到而没有再报”。

11. **汇合（Q11、Q12，AC-054-05，CR-018，ADR-028 I4、I5、移交）。** `join::join(tx, run, candidate, rounds, ctx)` 在 closing.rs:1390-1405 写 `verification.candidate_ready_for_join` 的同一事务里紧接着调用，join_id 即该事件 id（`child_id(C, "join/<轮数>")`，幂等：事件已存在不再汇合）。
    - **输入**：参与者 P = 在 C 上参与过轮次、不是 CANCELLED 的开发 Task（栅栏保证它们都 VERIFYING、当前轮次在 C 上且 passable、无未消费项）；J = 各 P 的当前轮次（即每条重新验证链的当前轮次）。QA、Review = `report_status(J, role)`（决定 5 的合并：任一 FAIL → Fail，否则任一 UNKNOWN → Unknown，否则任一缺 → NotRun，否则 Pass；C 为 VERIFYING 即最新候选，它的非 REJECTED 报告都是 CURRENT）；确定性检查 = `acceptance::checks`（C 上全部 `kind = 'check'` 证据，决定 4）；AC 覆盖 = J 的范围的并集，每个 AC 用 `classify::project` 投影 C 上该 AC 的**全部**行（原则一的历史；轮次只看开轮时已有加本轮的行，-754）；failing_issues = C 上全部轮次按来源谓词的未关闭 Issue（`round_issues` 对每个轮次取并集）；outside_failed = C 上范围之外的 AC 的 FAIL 行。输入与失败项由与 `classify_round`（closing.rs:753-890）共用的推导函数给出，所以 failed ⇔ 至少一个失败项（ADR-028 实施更正 6）。`class = classify(&input)`；写 `verification.joined{candidate_id, join_id, class, inputs, rounds, tasks}`。
    - **passable**：先对每个 P 求门禁谓词（决定 12 的 `requirements_passed(C)` ⊇ P 的需求，且 C 是 Run 唯一在用的候选）。全部成立：`UPDATE candidates SET state='ACCEPTED' WHERE candidate_id=C AND state='VERIFYING'`（改动行数必须为 1，否则 IntegrityViolation、整个对账事务回滚），`candidate.accepted{candidate_id, join_id}`；每个 P 以 CAS VERIFYING→ACCEPTED，`task.accepted{task_id, candidate_id, join_id, by: "runtime"}`；迭代按决定 13。任一不成立（按构造不会：passable 已要求范围内每个 AC 只有 PASS/合规 DEGRADED 行）：不写 ACCEPTED，写 `integrity_violation{candidate_id, join_id, tasks, reason: "join_gate_disagrees"}`，被拒的 P 置 BLOCKED（NEED_DECISION，`need_decision{reason: "join_gate_refused"}`），栅栏因此不再成立，等决策（fail-closed，候选不部分接受）。
    - **failed**：C 置 REJECTED（带原状态条件），`candidate.rejected{candidate_id, join_id}`；`verification.failures{round_id: join_id, candidate_id, items}`（AC 项归范围含该 AC 的 P，其余归全部 P；I6）；迭代按决定 13；随后同一事务再调用一次 `consume`（closing.rs:947），所以 VERIFYING 的主人当即返工，不留一个 tick 的空档。join_id 占 `round_id` 字段，消费、`task.rework` 与返工上下文无需新路径；`issue:` 项的 `issue.consumed_by_rework` 按 C 上轮次的同指纹 Issue 写。
    - **inconclusive**：对 J 的每个轮次 r，按 r 的源 Task 请求 `Repair::Reverify{root: r.chain_root}`，action_id = `child_id(join_id, "reverify/<r>")`；准许即以 `verification::reverify` 开 r 的下一轮（同样的源与范围），拒绝即这些源 BLOCKED（NEED_DECISION，reverify_exhausted）。与 exits 的 reverify 一支（closing.rs:1186-1236）抽成同一函数。UNKNOWN 永不返工。
    - **flaky**：每个 P 置 BLOCKED（NEED_DECISION），`need_decision{reason: "flaky", candidate_id, join_id}`，与轮次的 flaky 一支（:1237-1263）同一函数。
    - **晚到的行（Q12）**：汇合读全部历史，所以轮次关闭之后才入库、仍在 VERIFYING 候选上的 FAIL 行会使汇合 failed 并登记有主的项。轮次关闭要等候选没有待入库事实（ADR-028 -601），这种行只在崩溃窗口后才可能出现；原则一说它让 AC 不满足，汇合不能越过它。ADR-028 决定 1 的“只作历史、不登记失败项”只约束它所属的轮次。

12. **门禁谓词换成投影（ADR-027:170 的移交，-751；ADR-011:102 的更正）。** `load_evidence` 的需求判定（decide.rs:851-867 的 SQL）抽成 `requirements_passed(tx, run, spec, candidate) -> BTreeSet<requirement>`：需求在当前 spec 下至少有一个 AC，且每个 AC 在 C 上的展示投影满足（决定 2，profile 为 None），且每条满足它的行引用的证据属于 C、check_id 等于该 AC 的 check_id、outcome 等于该行的状态（PASS 行配 PASS 证据，DEGRADED 行配 DEGRADED 证据，保留原有的“出自自己的场景检查”一项）。`load_evidence` 对 ACCEPTED 的候选调用它，汇合对 VERIFYING 的 C 调用它，所以“由 Runtime 按门禁谓词接受源 Task”与 Commander 的门禁是同一个函数。可降级需求上合规的 DEGRADED 从此计为通过（替换 decide.rs:863 与 ADR-011“DEGRADED 暂不计为通过”的临时规则）；不可降级需求上的 DEGRADED 投影为 FAIL，不通过。`Evidence::gate`（decision.rs:254-292）与“唯一在用候选”的规则不变。

13. **pace 与迭代（ADR-028 决定 10、11 的更正）。** 删去 retry.rs:597-606 的过渡例外（`|| joining.contains(..)`），`sources_and_joining` 只返回 sources（汇合与栅栏在同一事务，不存在“等汇合”的状态）。迭代：汇合点不再无条件计数（删去 closing.rs:1404）；汇合 passable 时以 verdict `passable`、failed 时以 `repair` 调 `iteration`（每候选至多一次，`child_id(C, "iteration")`，已由更早的 repair/invalidated 关闭计过即无操作）；inconclusive 与 flaky 不计（与轮次相同）。

14. **profile 与规则 16（Q6）。** `Profile{live_agents: BTreeMap<check_id, BTreeSet<agent>>}` 取自 release-policy 的 profile；给出时，`check_id` 在 profile 的 live_agents 里、而 `RowFact.live_agents`（该证据 live-sessions 的 agent 集合，没有为空）不包含所要求全部 agent 的 PASS/DEGRADED 行被删去（无结论）。产品的分类、门禁与快照一律传 None：候选门禁没有 profile（只有 `releases.profile`，SQL:36）；由发布门禁（M5-T02）传入，见“移交”。有 profile 时投影只会更严（满足 ⇒ 无 profile 也满足），不影响决定 2 的等价。

15. **追溯链（AC-054-04，done_when“可追溯到原始会话”）。** `Reader::issue_chain(issue_id) -> IssueChain{issue, report{report_id, state, path, sha256}, raw{path, sha256}}`（只读库）与 `verification::report::verify_chain(project, &IssueChain) -> ChainCheck{report_digest, finding_present, raw_digest, native_digest, session_in_native, stdout_is_raw}`：用 `objects::get`（按名重算摘要，objects.rs:293-304）读报告对象，找到 `finding_id` 的 finding，核对报告里 raw_session、native_attempt 的引用等于登记的 artifact 行并重算两个对象的摘要，native_attempt 的 `session_ids` 含报告的 session_id、`stdout_sha256` 等于 raw_session 的摘要。

## 不变量

- **J1** `acceptance_results` 只追加：没有 UPDATE/DELETE/REPLACE 路径（扫描保证），仓储的改写接口一律拒绝且行不变。
- **J2** 对每个行多重集，候选可用且无 profile 时 `satisfied(display) ⇔ project == Satisfied`；候选 INVALID/STALE 时没有 AC 满足；已验收计数、快照与门禁只经 `display`。
- **J3** 候选 ACCEPTED 只由汇合写，当且仅当 `classify(汇合输入) == Passable` 且每个参与者满足门禁谓词；候选与参与者在同一事务一起 ACCEPTED（ADR-028 I4、I5）。
- **J4** 非 REJECTED 报告的每条 finding 恰好一行 Issue，在记录该报告的结算事务里登记；REJECTED 报告没有 Issue；finding 的 `issue.opened` 不带 round_id，low/medium finding 永不使轮次或汇合 failed。
- **J5** REJECTED 报告不进任何分类、快照与门禁；STALE ⇔ 之后有别的候选冻结或 `candidate.stale` 写着它的候选；CURRENT 的报告都在 Run 的最新候选上。
- **J6** Issue 的 RESOLVED 只在一个 passable 关闭、它在该轮确认集合里、且该轮报告没有重复它时写；REOPENED 只在之后的 finding 重复它时写。
- **J7** 验证 Task 不进范围内 AC、已验收计数与门禁；它们的 ACCEPTED 只表示验证工作完成（ADR-028 决定 10）。
- **J8** 失败的汇合按 I6 登记至少一个有主的项，并在同一事务被消费或附上。

- **汇合（integration 与 completion/tests.rs）**：单 Task passable → C、T ACCEPTED，Commander 随后的 Run→COMPLETED 通过门禁（正对照）；两个 Task 两条链 → 汇合只读各链当前轮次的报告（旧的 UNKNOWN 报告不计，-402）；栅栏后伪造一条晚到 FAIL 行 → 汇合 failed、C REJECTED、项归范围含该 AC 的 Task 且同一事务返工；伪造晚到的 UNKNOWN 行 → flaky → BLOCKED；检查只有无结论 → inconclusive、下一轮、`repair.reverify` 按链计数；门禁不一致（伪造无 AC 的需求）→ integrity_violation、无 ACCEPTED；迭代：passable 计一次 verdict passable，inconclusive 不计，repair 关闭之后的汇合不再计；pace：栅栏等待兄弟时 Run 按兄弟的原因阻塞，汇合后无“等汇合”在途。M2-T16 里只断言汇合点出现、候选仍 VERIFYING 的用例 `a_passable_round_waits_at_its_candidates_barrier_for_the_join`（persistence/completion/tests.rs:1691）改为断言汇合的结果，不删除。
- **门禁**：可降级需求的合规 DEGRADED → Task 接受通过；不可降级需求的 DEGRADED → EVIDENCE_GATE_UNMET。红：现行 SQL 拒绝 DEGRADED。
- **RESOLVED/REOPENED**：改写请求 Issue 在返工后的 passable 轮次关闭时 RESOLVED；该轮报告以该 Issue 的 id 再报 → 不 RESOLVED、新 Issue；inconclusive 轮次 → 不 RESOLVED、下一轮仍列出；RESOLVED 后同指纹再现 → REOPENED 且新行 OPEN；Prompt 列出的集合等于关闭时核对的集合。
- **快照与 HTTP**：契约测试按受锁 Page schema 校验 `/acceptance`、`/issues`；候选 INVALID → 全 INVALID、accepted 0；候选因 `candidate.stale` 而 STALE 且没有后继 → 全 STALE、accepted 0；验证 Task 的 ACCEPTED 不改变 accepted 与 total；`persistence_scan.py` 对一段 `UPDATE acceptance_results` 的夹具源码报错（正对照）。
- **TEST-053-05（adapter-live，S7）**：crates/hoh-app/tests/verification_live.rs 里忽略的测试 `verification_live_candidate_to_qa`（名字不含 TEST id，与 scripts/product/adapter-live.sh:1-11 的约定相同；脚本加一行 `live qa verification_live verification_live_candidate_to_qa hoh-app` 与一个 case `('qa', 'TEST-053-05', …)`），真实 claude 的 Developer、QA（v0.1 允许两个 claude 会话）与 Reviewer，Commander 为不提议的假 Agent；植入缺陷仓库中 AC-B 的确定性测试必然失败。verdict：PASS 当且仅当 QA 与 Developer 的 HoH 会话不同且 native_id 不同、都在 sessions；QA 报告行 candidate_id=C、native_attempt 的 session_ids 含其 session_id；AC-B 标签 ∈ {FAIL, UNKNOWN, NOT_RUN, INVALID}；C 不是 ACCEPTED。claude 缺失、未登录或以 root 运行为 BLOCKED（SKIPPED），从不由假 Agent 得 PASS；会话、版本与 resolved model 写进 verdict 的 sessions。

## 未采用

- **SQL 触发器 `BEFORE UPDATE ON acceptance_results`**：要新迁移文件进 contracts/sql（受锁），需 CR；产品本无改写路径，扫描与接口已足够。
- **Runtime 为每个 FAIL 行开 Issue**：会与 QA 的 finding 重复，且带 round_id 的 `issue.opened` 会让 low 也 failed；REQ-053 行为 5 把开 Issue 交给 QA。
- **把没有 finding 的 FAIL 报告当作无效输出纠正**：会推翻 ADR-028 -403 已收敛的用例；该轮仍以报告项 failed、返工。
- **空观察写成不否决的 INVALID 行或新证据种类**：违反 ADR-027 决定 5（INVALID 证据否决候选）与文件扫描。
- **报告“候选不是 VERIFYING”即 STALE**：被兄弟轮次判 REJECTED 的候选上的轮次会丢掉它的报告项（-850）。
- **RESOLVED 在单份报告结算时写**：另一验证方可能在同一轮再报它；passable 关闭同时看到两方。
- **finding 的 Issue id 按序号**：finding_id 才是 AC-054-04 要的引用；重复 id 改为输出无效。
- **复制 finding evidence 进对象库**：路径多在已删除的运行目录，摘要指向摘录而非文件，核对不出有意义的东西；链只要求到 raw_session。
- **汇合只读各轮的行**：违反原则一的历史规则（ADR-027:170）。

- **ADR-011 §3（:102）**：证据门禁由 ADR-029 决定 12 的 `requirements_passed` 替换；合规 DEGRADED 计为通过，“DEGRADED 暂不计为通过”作废。
- **ADR-027**：:170 的移交由 ADR-029 决定 2、4、14 实现；检查级聚合也用于轮次的检查维度；规则 16 的 profile 由 M5-T02 传入。
- **ADR-028**：决定 10 的 pace 过渡例外已删除；决定 11 的迭代在汇合的有结论结果上计（passable 或 repair），轮次的检查维度改用 `acceptance::checks`，`report()` 读 `independent_reports` 的非 REJECTED 行；决定 1 的“关闭之后入库的证据只作历史”只约束它的轮次，汇合读全部历史；决定 12 的 RESOLVED 由 ADR-029 决定 10 写，确认集合扩到同一 Task 更早轮次的全部 Issue；决定 15 的 `VerifierReport` 带 findings 与 raw artifact。

## 与倾向不同之处

1. 轮次分类读本轮的非 REJECTED（CURRENT 或 STALE）报告，汇合与快照读 CURRENT：ADR-028 -850 要求被兄弟判 REJECTED 的候选照常分类（决定 7、8）。
2. STALE 按“之后有别的候选冻结或 `candidate.stale`”判，并在冻结时翻转已有的 CURRENT：SQL:34 的注释与 -850，而不是“候选不是 VERIFYING”。
3. 未观察的声明只取 QA，且只在没有行时生效：否则重新验证的 PASS 会被它压住，展示与裁决的满足集合不同（CR-018）。
4. RESOLVED 在 passable 的轮次关闭时由两方报告一起判，确认集合扩到两种来源、任何 severity；角色契约改为“已修复不写 finding，仍存在用 Issue id 再报”。
5. 指纹的 locator 去掉 `.hoh/` 下的路径，并删行号与候选、提交的十六进制。
6. 汇合点的迭代改在汇合的有结论结果上计（现行代码无条件计 passable）；失败的汇合在同一事务再 `consume`。
7. 轮次的检查维度也改用按检查的历史聚合（与汇合同一函数）。
