# ADR-011 · 生命周期迁移表与 Commander 决策校验

状态：M2-T02 采纳（CTO 设计决定，细化 REQ-035/REQ-036，不改变 CONTRACT 或已锁定契约）。日期：2026-11-04。

## 背景

docs/05 只给出 Run 主链与"任一非终态可进入"的挂起类状态，Task 与 Attempt 只列出状态名；REQ-036 要求 hoh-core 有唯一迁移表，状态集合与 001_initial.sql 的 CHECK 枚举一致，并列出必拒对。REQ-035 要求 Runtime 在应用 Commander 提议前做确定性校验，但没有说明 Commander 能提议哪些迁移。本 ADR 把这些空白定下来；代码中的单一来源是 `hoh_core::lifecycle`（迁移表）与 `hoh_core::decision`（提议校验）。

> 更正（ADR-025 决定 6、8，M2-T08）：经 Commander 输出桥接的决策，decision_id 为 `<attempt>/<message_id>`；同一 decision_id 内容相同为重放、不同为 KeyReuse（不再因主键冲突报 IntegrityViolation）；Unsupported 的 request_user_decision 写 `supervisor.output_disposed{unsupported}` 并声明 NEED_DECISION；BLOCKED 与 WAITING_EXTERNAL 下只判定 transition_task 与 record_assumption。

> 更正（ADR-025 决定 8，M2-T08）：经输出桥的 decision 由登记的 `supervisor.output` 重做（不靠消息重投）；崩溃后从登记继续。

## 决定

### 1. 迁移表（`hoh_core::lifecycle`）

记号：W = 工作态 {CREATED, DISCOVERING, SPECIFYING, READY, RUNNING, VERIFYING}；自环一律非法（同状态不是迁移）。

**Run（15 个状态，87 条合法边）**

| from | 合法 to |
|---|---|
| CREATED | DISCOVERING |
| DISCOVERING | SPECIFYING |
| SPECIFYING | READY |
| READY | RUNNING |
| RUNNING | VERIFYING |
| VERIFYING | RUNNING（候选失败后修复/下一增量，REQ-036 已选）、COMPLETED |
| W 中每个状态另加 | PAUSE_REQUESTED、WAITING_EXTERNAL、BLOCKED、CANCEL_REQUESTED、INCOMPLETE、FAILED |
| WAITING_EXTERNAL | W（恢复）、BLOCKED、PAUSE_REQUESTED、CANCEL_REQUESTED、INCOMPLETE、FAILED |
| BLOCKED | W（恢复）、PAUSE_REQUESTED、CANCEL_REQUESTED、INCOMPLETE、FAILED |
| PAUSE_REQUESTED | PAUSED、CANCEL_REQUESTED、FAILED |
| PAUSED | W（恢复）、BLOCKED（暂停结束时阻塞仍在）、CANCEL_REQUESTED、INCOMPLETE、FAILED |
| CANCEL_REQUESTED | CANCELLED、FAILED |
| INCOMPLETE | W（恢复）、CANCEL_REQUESTED、FAILED |
| COMPLETED、CANCELLED、FAILED | 无（终态） |

"任一非终态可进入"按语义收窄：取消一旦请求不再被暂停或 INCOMPLETE 覆盖；暂停中的 Run 不进入 WAITING_EXTERNAL，暂停结束时若阻塞集合仍非空则回到 BLOCKED；BLOCKED 解除后先回 resume_state 再由 Runtime 重新判定是否 WAITING_EXTERNAL。

**阻塞集合**：`blocked_reason`/`blocked_reasons_json` 是事实，不随状态迁移清除（暂停、取消请求期间保留）；只有阻塞机制（M2-T08/M2-T15）在原因解除时移除。Run 进入任何工作态都要求阻塞集合为空，否则 ILLEGAL_TRANSITION；Task 从 BLOCKED 回到 PENDING/READY 同样要求 `blocked_reason` 为空。

**resume_state**：从 W 进入非工作的非终态时，`runs.resume_state` 记为离开的 W 状态；在非工作态之间移动时保持不变；从非工作态回到 W 时目标必须等于 resume_state（否则 ILLEGAL_TRANSITION），回到 W 后清空。写入方（persistence writer）在同一事务内执行这条规则。

**Task（9 个状态，26 条合法边）**

| from | 合法 to |
|---|---|
| PENDING | READY、BLOCKED、CANCELLED |
| READY | LEASED、PENDING、BLOCKED、CANCELLED |
| LEASED | RUNNING、READY（租约释放/启动前失败）、BLOCKED、CANCELLED |
| RUNNING | IMPLEMENTED、READY（Attempt 失败待重试，只新增 Attempt）、BLOCKED、CANCELLED |
| IMPLEMENTED | VERIFYING、READY（返工）、BLOCKED、CANCELLED |
| VERIFYING | ACCEPTED、READY（验证失败待修复）、BLOCKED、CANCELLED |
| BLOCKED | PENDING、READY、CANCELLED |
| ACCEPTED、CANCELLED | 无 |

规格变更不重开 ACCEPTED 的 Task；受影响的工作以新 spec 的新 Task 表达（tasks.spec_id）。

**Attempt（7 个状态，14 条合法边）**

| from | 合法 to |
|---|---|
| PREPARED | STARTING、FAILED、CANCELLED |
| STARTING | RUNNING、FAILED、CANCELLED、UNKNOWN_EFFECT |
| RUNNING | SETTLED、FAILED、CANCELLED、UNKNOWN_EFFECT |
| UNKNOWN_EFFECT | SETTLED、FAILED、CANCELLED（诊断/观察后定论） |
| SETTLED、FAILED、CANCELLED | 无 |

PREPARED 尚无外部副作用，故不进入 UNKNOWN_EFFECT；重试只新增 Attempt，旧 Attempt 不回到运行态。

**Input（4 个状态，4 条合法边，M1-T04 补充，依据 docs/06）**

| from | 合法 to |
|---|---|
| QUEUED | DELIVERED、REJECTED（如 steer 的 expectedTurnId 已过期） |
| DELIVERED | APPLIED、REJECTED |
| APPLIED、REJECTED | 无 |

input_queue 同样没有 revision 列：`Store::move_input` 以期望 state 比较，不符为 StaleState，表外迁移为 ILLEGAL_TRANSITION；入队与每次迁移在同一事务内追加 `input.queued`/`input.moved` 事件。

### 2. 持久层执行

persistence writer 的每个状态 compare-and-set 在同一 BEGIN IMMEDIATE 事务内读取当前 state/revision、resume_state 与阻塞集合，对照迁移表、resume_state 规则与阻塞集合规则，再 `UPDATE … WHERE id=? AND revision=? AND state=?`；非法迁移返回 ILLEGAL_TRANSITION，整个事务回滚，不写事件与 outbox。进入 BLOCKED 需要阻塞原因集合（runs CHECK 约束），该机制随 M2-T08/M2-T15 加入；在此之前对 Run 的 BLOCKED 写入因约束失败而整体回滚。attempts 表没有 revision 列，Attempt 迁移以期望的 state 作比较条件（M1-T03 随首个创建 Attempt 的适配器实现：`Store::create_attempt`/`move_attempt`，不符为 StaleState，表外迁移为 ILLEGAL_TRANSITION，均不写入）。

### 3. Commander 提议校验（`hoh_core::decision`）

提议来自 kind=decision 的 HCP Message：decision_id=message_id，role_epoch、expected_revision、spec_sha256 取自信封，payload 按 protocol.schema.json `$defs.DecisionPayload` 校验后才成为提议；写入 decisions.payload_json 前再次按 schema 编码校验。

记录与裁决在一个事务内完成：插入 decisions 行（PROPOSED）→ 在同一事务中读取快照并校验 → 置 APPLIED（迁移 CAS、Run revision+1、事件、派发 outbox）或 REJECTED（reason_code + 恰好 1 条 `decision.rejected` 事件，不改 tasks/runs，不写 outbox/attempts）。崩溃时整笔不存在，由消息重投（M2-T04）再次提交。

校验顺序（首个失败即为原因码）：

1. 公共：role_epoch ≠ 当前 commander 绑定的 epoch（或无绑定）→ STALE_ROLE_EPOCH；expected_revision ≠ runs.revision → STALE_REVISION；Run 已有 spec 且 spec_sha256 不同 → SPEC_MISMATCH。
2. dispatch：Task 不属于该 Run → ILLEGAL_TRANSITION；tasks.spec_id ≠ runs.spec_id → SPEC_MISMATCH；任一依赖非 ACCEPTED → DEPENDENCY_NOT_ACCEPTED；READY→LEASED 不合法 → ILLEGAL_TRANSITION；目标角色无 ACTIVE 绑定或其会话 capabilities_json 未覆盖 Task 角色的 required_capabilities → ROLE_CAPABILITY_MISSING；cost_estimate 超过可预留预算 → BUDGET_NOT_RESERVABLE。应用：Task READY→LEASED，Run revision+1，向目标角色（其当前 role_epoch）插入一条派发 outbox。（M2-T03 修订，见 ADR-017）同一事务中还创建该 Task 的 PREPARED Attempt（不另写事件）并授予它所需的租约；所需租约被占用时提议以 LEASE_UNAVAILABLE 拒绝（CR-007），检查排在其余原因之后。
3. transition_task：只接受 PENDING→READY、PENDING→CANCELLED、READY→PENDING、READY→CANCELLED、IMPLEMENTED→READY、IMPLEMENTED→CANCELLED、VERIFYING→ACCEPTED，其余（含 LEASED/RUNNING/IMPLEMENTED/VERIFYING/BLOCKED 等由 Attempt、QA barrier 与阻塞事实驱动的迁移）→ ILLEGAL_TRANSITION；到 READY 要求依赖全部 ACCEPTED；到 ACCEPTED 要通过证据门禁，否则 EVIDENCE_GATE_UNMET。
4. transition_run：只接受 from 与 to 都在 W ∪ {INCOMPLETE, FAILED, COMPLETED} 内、from 在 W 内且在迁移表中的边；暂停、取消、WAITING_EXTERNAL、BLOCKED 及其恢复属于用户命令与 Runtime 事实，Commander 提议一律 ILLEGAL_TRANSITION。到 COMPLETED，或 payload 带 accepted_requirements 时，要通过证据门禁。
5. record_assumption：只做公共校验；应用为 Run revision+1 与一条 `decision.applied` 事件。
6. create_tasks（REQ-038 计划校验，M2-T03）与 request_user_decision（NEED_DECISION 流程，M2-T13）在本任务中不应用：持久层返回 Unsupported 错误且不写任何行，直到对应任务实现。

**证据门禁（本任务的最小 fail-closed 版本，M2-T18 以验收投影替换）**：门禁只看提议信封中的 `candidate_id` 所指的候选 C（CONTRACT 第 7 条：新候选不得沿用旧候选的验收）。提议没有给出候选 → EVIDENCE_GATE_UNMET；C 不是该 Run 唯一的在用候选（状态为 FROZEN/VERIFYING/ACCEPTED 的候选恰为 {C}）→ CANDIDATE_MISMATCH（在 M2-T10 维护"冻结新候选时旧候选置 STALE"之前，多个在用候选一律视为无法确定当前候选）。需求 R 对 C 成立，当且仅当 C 的状态为 VERIFYING 或 ACCEPTED、spec_sha256 等于 Run 当前 spec，且 R 在当前 spec 下至少有一个 AC，每个 AC 对 C 至少有一行 acceptance_results 且全部为 PASS，每行所引用的 evidence 属于 C、outcome 为 PASS、check_id 等于该 AC 的 check_id。COMPLETED 需要 C 满足当前 spec 的全部 required_release 需求（至少一项）；accepted_requirements 需要 C 满足所列全部需求；Task→ACCEPTED 需要 C 满足该 Task 的全部 task_requirements（至少一项）。DEGRADED 暂不计为通过。

**能力与预算输入**：Task 角色的 required_capabilities（职位契约，M2-T07 起来自团队配置）与可预留预算（M2-T19 起来自 budgets 表的预留）由调用方随提议传入；探测到的能力取自绑定会话的 sessions.capabilities_json（值为 true 的键）。拒绝事件记录这些输入，便于复核。

## 未采用

- 让 Commander 可提议任意表内迁移：会绕过用户暂停/取消、QA barrier 与租约。
- 先单独提交 PROPOSED 再另起事务裁决：留下需要恢复流程的悬挂行，且不比消息重投更安全。
- 以时间戳选"最新候选"判定门禁：违反"排序只依据 events.seq"。
