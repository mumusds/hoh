# ADR-016 · Engine host 骨架：启动、本地 API 与命令幂等

状态：M2-T12 采纳（CTO 设计决定，细化 REQ-022、REQ-036、REQ-041、REQ-062，不改变 CONTRACT 或已锁定契约；故障注入点的形式见 CR-006）。日期：2026-11-06。

> 注记（ADR-030 决定 10，M2-T15）：决定 12 的项目锁随写线程持有，ADR-030 决定 10 以它推出“新 host epoch 即旧 host 的兼容套件已不在”：打开的套件只按当前 host epoch 计数，旧 host 没写成的结束由新 epoch 关闭。

## 背景

REQ-041 规定了 host 启动的顺序，REQ-062 规定了连接设置、writer 与位置检查，REQ-022/036 规定了命令的幂等与提交后才通知，openapi.json 给出了端点与 Error 体。以下各点它们没有规定：

- host 的文件放在哪里；
- token 与 Host/Origin 怎样校验；
- 未知 Run、被拒命令、PauseRun 的事件与 outbox 长什么样；
- SSE 怎样与提交顺序对齐；
- 各种存储错误的 HTTP 映射。

以下决定填补这些空白。实现在 `crates/hoh-app/src/host/`（hoh-app 的库目标 `hoh_app`）与 `crates/hoh-core/src/persistence/commands.rs`。

## 决定

1. **启动顺序**：
   1. 只读检查 `.hoh/` 最近存在的祖先所在文件系统。网络或共享文件系统直接拒绝，什么都不创建。
   2. 创建 `.hoh/`，以非阻塞 `flock` 锁住 `.hoh` 目录本身（锁一个文件的话，文件被删后第二个 host 就能锁上新文件，M2T12R-152）。先锁目录，再由持锁者把本进程 pid 写入 `.hoh/host.lock` 供诊断；被拒的启动只读这个文件，不创建也不改动它（M2T12R-182）。锁被占用时退出 69，并给出持有者的 pid（读不到时写 unknown）。

   目录锁挡住的是同一个 `.hoh` 目录上的第二个 host。把 `.hoh` 改名或删除后，新 host 建的是新目录和新数据库，两个 host 不会写同一个库。但若有人在旧 host 运行时把数据库文件挪进新建的 `.hoh`，两个 host 会写同一个库，这个锁挡不住。这种情况的防线是带 `host_epoch` 条件的写入 fencing（REQ-041 behaviour 4、AC-041-02，M2-T05 实现）；在那之前没有防线（M2T12R-183）。
   3. 打开 store：再次检查位置，做 WAL 自检，设置并校验连接参数，迁移。
   4. `PRAGMA quick_check` 通过后，在同一事务里取得或建立该仓库路径的项目，并把 `host_epoch` 加一。
   5. 打开 4 个只读连接，逐个校验设置，并确认它们拒绝写入。
   6. reconcile 尚未实现（M2-T05），目前没有可租出的工作。
   7. 先绑定 `127.0.0.1:<port>`，再绑定 `.hoh/host.sock`（模式 0600；只删除之前遗留的 socket，其他文件一概不动）。端口被占时不会留下 socket（M2T12R-08）。
   8. 原子写入 `.hoh/host.json`（模式 0600），内容为 pid、project_id、host_epoch、port、socket、token。

   第 8 步之前任何一步失败，host 都不提供服务；写 host.json 失败时先停止服务、移除 socket，再随错误释放锁（M2T12R-08）。位置被拒或 WAL 自检失败时退出 78（环境不能按配置使用），且不留下正式 DB 文件；其余失败退出 1。SIGTERM/SIGINT 时按决定 12 停止；锁文件与数据库保留。REQ-041 写“取项目锁→schema 与完整性检查”，done_when 写“先做 DB 位置检查与 WAL 自检”：上面的顺序（只读检查→取锁→完整打开）同时满足两者。
2. **端口**：默认 8787（openapi `servers`），可配置，0 表示取空闲端口。实际端口写入 host.json。每个项目一个 host，所以测试与多项目时不依赖固定端口。
3. **请求校验**：在路由之前、任何处理之前进行，失败一律返回 403 FORBIDDEN，Error 体完整。
   - token 为 32 字节随机数的十六进制，经 `X-HoH-Token` 传入，以恒定时间比较。
   - TCP 上必须恰有一个 `Host`，且等于 `127.0.0.1:<绑定端口>`；`Origin` 最多一个，只能不出现或等于 `http://127.0.0.1:<端口>`；绝对形式的请求目标所带的 authority 也必须是这个地址。这样可以挡住 DNS 重绑定和其他网页发来的请求（M2T12R-05）。
   - socket 上不检查 `Host`，但任何 `Origin` 都拒绝，带 authority 的请求目标也拒绝。
   - `/healthz` 不需要 token（openapi `security: []`），Host/Origin 照样检查。
4. **命令**：`POST /v1/commands` 先按协议 schema 校验 `Command`，再处理。
   - 目前实现 PauseRun（其他 kind 随各自任务实现，现在返回 422 CAPABILITY_UNSUPPORTED，不写任何东西）。
   - 幂等比较用的哈希取整个命令体的规范 JSON（键排序）的 sha256，而不只是 `payload`。否则 kind 不同、payload 相同的两条命令会被当成同一条。
   - 一条命令就是一个 `BEGIN IMMEDIATE` 事务，依次做：
     1. 按 idempotency_key 查找已有命令：哈希相同则原样返回已存的结果字节，并带 `Idempotent-Replayed: true`；哈希不同则返回 409 KEY_REUSE。
     2. Run 不存在时返回 409 RUN_NOT_FOUND，`current_revision` 为 null（openapi 的 submitCommand 没有 404）。
     3. 以 compare-and-set 迁移 Run（PauseRun → PAUSE_REQUESTED）。
     4. 追加事件 `run.pause_requested`，payload 为 command_id、state、reason。
     5. 插入一条发往 commander 的 outbox。
     6. 插入 commands 行，`result_json` 存的正是 202 体 `{command_id, run_id, revision, status:"ACCEPTED"}`。
     7. COMMIT。
   - 只有被接收的命令才有 commands 行（`accepted_at NOT NULL`）。被拒的命令重试时会重新判定，不记成拒绝结果。
5. **PauseRun 的 outbox**：outbox 行收件角色为 `commander`，role_epoch 为 1（角色绑定随 M2-T07 实现），payload 为运行时通知 `{notice:"runtime", kind:"run.control", control:"PAUSE_REQUESTED", run_id, command_id, event_id, reason}`（`notice` 标记见 ADR-018 决定 4）。它不是 HCP Message：HCP Message 必须带 task/attempt/spec，而暂停是 Run 级的。M2-T04 决定它保持为运行时通知：HCP 投递循环不领取它，由 host 循环（M2-T05/T06）消费（ADR-018 决定 4）。
6. **错误映射**：Error 体总是包含 code、message、retryable、current_revision。message 为固定文本，只有一处例外：表中“其他存储错误”的 503 UNPROCESSABLE 在固定前缀 “the store could not apply the request: ” 之后带上存储层给出的原因（PersistError 的文本；其中 SQLite 的部分是它的文字说明，如 “disk I/O error”），因为文件系统在 host 运行中转为只读时 host.log 也写不进去，客户端是唯一看得到原因的地方（2026-11-17 修订，见文末故障矩阵第 7 项注记第 3 条）。这一原因同时写到 host 的 stderr；任何响应中都不出现 SQLITE_* 符号（M2T12R-02；db_faults 的运行中转为只读一项断言客户端所见没有 SQLITE_）。未知路由与方法也返回 Error 体（404 NOT_FOUND）。

   | 情形 | 状态码 | code | retryable | current_revision |
   |---|---|---|---|---|
   | KEY_REUSE、ILLEGAL_TRANSITION | 409 | 原名 | false | Run 当前的 revision |
   | STALE_REVISION | 409 | STALE_REVISION | false | 存储中的 revision |
   | 约束违例（如 command_id 已被另一条命令使用） | 409 | CONFLICT | false | Run 当前的 revision |
   | 写锁超过 busy_timeout | 503 | DB_BUSY | true | Run 当前的 revision |
   | 写满（CR-006） | 503 | DB_FULL | true | Run 当前的 revision |
   | 其他存储错误 | 503 | UNPROCESSABLE | false | null |
   | 非 JSON、不合 schema、请求体过大或读不出 | 400 | BAD_REQUEST | false | null |
   | getRun 的 run_id 不是文本 | 404 | RUN_NOT_FOUND | false | null |
   | streamEvents 的 after、Last-Event-ID、run_id 或 kinds 读不出，或 after 为负 | 409 | CONFLICT | false | null |

   后两行使用 openapi 已为该端点列出的状态码：getRun 没有 400，读不出的 id 不指向任何 Run；streamEvents 没有 400，所以用 409（M2T12R-03）。
7. **提交后才可见**：writer 线程在每个请求结束后读一次最大事件 seq，只在它增大时发布 watermark。事务未提交时它不变，所以订阅者只会看到已提交的事件。处理器从不广播，客户端断开也不会丢失事件或让事件提前出现。
   - `GET /v1/events` 连接时先订阅 watermark，取当时的 H，从数据库回放 (after, H]（每页 500 条），之后每当 watermark 前进，就读新提交的事件。SSE 的 id 为 seq，data 为协议 Event，`attempt_id` 为 null（events 表没有这一列）。
   - `after` 与 `Last-Event-ID` 都给出且不一致时返回 409 CONFLICT。
   - M2 不清理事件，所以 410 不会出现。
8. **读**：`GET /v1/runs/{id}` 在一个读事务里同时读出 Run 与最大 seq（snapshot 与 watermark 一致）。它用连接池中的只读连接，在 `spawn_blocking` 中执行，不占 Tokio worker，也不等 writer（AC-062-01）。`projection` 为 mode、resume_state、blocked_reason。不存在时返回 404 RUN_NOT_FOUND。
9. **writer 队列**：host 使用 REQ-018 的 `writer_queue_capacity=256`（persistence 的默认值 64 留给其他调用方）。队列满时等待 busy_timeout，之后返回可重试的 DB_BUSY。
10. **诊断**：连接设置不在 openapi 中，由进程内接口 `Host::diagnostics` 给出 writer 与各 reader 的 PRAGMA，以及 reader 是否都拒绝写入（AC-062-01）。
11. **故障注入点**：按 CR-006 是空操作钩子，产品实现都只用 trait 的默认方法。
    - persistence 的 `FaultHooks`：提交前、WAL 自检每一步前。产品实现为 `NoFaults`。
    - WAL 自检第二进程的 `ProbeBehaviour`：打开、计数、各命令的应答。产品实现为按协议行事的 `NormalProbe`。
    - host 的 `HostHooks`：命令提交后、响应发出前。产品实现为 `NoHostFaults`。

    测试的实现负责制造故障：写满错误、自检某一步失败、第二进程不加锁、计数不更新、假锁、单向锁，以及在提交后丢弃连接（该处 unwind，连接任务结束，不写任何响应字节）。另有测试确认产品实现都不带方法体（有反例测试），并调用它们确认不产生故障。

12. **停止时的生命周期（设计修正，M2T12R-01、-60、-91 三轮属于同一类）**：锁的释放与“旧 host 已不可能再写”在结构上绑在一起，不靠某一步的超时或等待是否成功。
    - **锁由 writer 线程持有**。项目锁在 store 打开后交给 writer 线程（`Store::keep_until_closed`）。writer 线程只有在所有 store 句柄都被丢弃、队列中的请求全部处理完、写连接关闭之后才退出，退出时才释放锁。store 句柄只在所有连接任务、事件流和读任务都结束后才会全部丢弃。所以锁一旦释放，旧 host 就没有任何连接可以接收请求，也没有任何写入待提交。这一点不论 `Host::shutdown` 是否被调用、Host 是否被直接丢弃都成立：丢弃 Host 等同于发出停止。writer 线程若 panic，它持有的锁不随 unwind 释放，而是泄漏到进程结束，项目不会被别的 host 接管（M2T12R-120）。host 把这当作致命故障（M2T12R-150）：之后的写入返回 503 GONE（retryable=true，客户端应向下一个 host 重试），`/healthz` 返回 503；`host::run` 同时等待信号与 writer 结束，writer 先结束时停止 host 并以 1 退出，监督者看到失败，进程退出时锁随之释放，下一个 host 才能启动。此时 `Host::shutdown` 与失败的 start 返回时锁仍被持有，直到进程结束（M2T12R-151）。`Host::shutdown` 返回 writer 是否正常结束，`Host::writer_ended` 在 writer 结束时完成并给出同样的结果，进程内的使用者可以像 `host::run` 一样监听它；停止期间 writer panic 时，`host::run` 同样以 1 退出（M2T12R-185）。panic 展开时，引发 panic 的请求先收到 GONE，`writer_alive` 稍后才变为 false，要确知 writer 已结束应等 `writer_ended`（M2T12R-181）。
    - **接收**：接收循环由 host 实现（hyper http1），每条连接是 host 的 JoinSet 中的一个任务，请求头必须在 30 s 内读完。accept 出错时，除了连接被拒绝、中止或重置，其余错误（如文件描述符用尽）都先退避 1 s 再继续，退避期间仍响应停止（M2T12R-92）。
    - **停止**，依次进行：
      1. 置停止标志，监听不再接收新连接。事件流在被轮询的每一步（回放或等待）检查停止并结束（M2T12R-98）；客户端不读而堵住的流不再被轮询，在宽限期后随连接被中止。
      2. 每条连接优雅关闭：空闲的或还在读请求的立即关闭，正在处理的处理完即关闭。在停止与关闭之间恰好读到的请求返回 503 GONE（retryable=true，客户端应向下一个 host 重试）。
      3. 最多等 5 s，之后中止仍在的连接任务。被中止的请求若已把事务排进队列，该事务仍由 writer 完成。
      4. 移除本 host 的 host.json（按 token 认定）与它绑定的 socket（按 inode 认定）；别的 host 放在那里的文件不动（M2T12R-120）。启动中途失败与直接丢弃 Host 时同样移除（M2T12R-153）。
      5. 丢弃 store，等 writer 线程退出，锁随之释放；`shutdown` 在此之后才返回（writer panic 的例外见上）。
    - **启动失败**：store 打开之后的启动失败同样丢弃 store 并等 writer 退出，所以返回错误时锁已释放（writer panic 的例外见上）。
    - **已知缺口**：getRun 与 streamEvents 在读失败（读连接忙、存储错误）与停止期间返回 503，而 openapi 没有为这两个端点列出 503。等 openapi 的下一次 CR 补上（M2T12R-61，后续项）。

## 注记：故障矩阵第 7 项（2026-11-17，docs/09；在线备份属 REQ-063，M5，不在此列）

逐项实测了磁盘满、只读、SQLite busy 与迁移失败下 host 与客户端的行为：在临时项目里经产品二进制及其客户端测，需要文件系统的项用 `sudo -n` 挂载测试自己的 tmpfs 或 ext4 镜像。凡是事务，都整笔回滚，没有一处半提交。有四处丢失或说错了诊断，修正如下（各有先红后绿的测试）：

1. **决定 1 第 3 步的 WAL 自检**：`.hoh` 不能新建文件（无写权限、只读文件系统），或文件系统已满时，此前一律报 `DB_WAL_UNSUPPORTED`，说成文件系统不支持 WAL。现在自检先用 `create_new` 建出临时库文件，以 OS 的错误说明原因：不能写是 `PersistError::NotWritable`（“<.hoh> is not writable: Permission denied (os error 13)”），照旧退出 78（环境不能按配置使用）；没有空间是 `DB_FULL`，退出 1。自检任一步得到 SQLITE_FULL 也是 `DB_FULL`。其余失败仍是 `DB_WAL_UNSUPPORTED`。
2. **启动失败的原因只占一行**：客户端读 host stderr 的最后一行作为原因（client.rs `ended_before_ready`）。迁移失败的原因原本带着 rusqlite 附上的整段迁移脚本（约 16 KB），客户端于是只显示 “ at offset 165”。现在 host 把启动错误合成一行再写出；迁移中某条语句准备失败时，只取 SQLite 的消息（“migration 1 failed and was rolled back: table runs already exists”）。
3. **决定 6 表中“其他存储错误”的 503 UNPROCESSABLE**：消息带上存储层给出的原因（“the store could not apply the request: storage error: disk I/O error”）。码、状态与 retryable=false 不变。文件系统在 host 运行中转为只读时，写入报 SQLITE_IOERR_WRITE，而 host.log 也在同一文件系统上写不进去，此前客户端只看到一句泛泛的话。
4. 无需修正、由测试守住的行为：
   - 磁盘写满时命令返回 503 DB_FULL、retryable，不写任何东西，腾出空间后照常受理；
   - 运行中把 state.db 及其 -wal、-shm 改为只读（chmod），或在 `.hoh` 上加只读 bind mount，都不影响已打开的写连接（OS 的语义），命令照常受理；下次启动才被拒绝，并说明原因，什么也不写（state.db 只读时为 “attempt to write a readonly database”，退出 1；只读挂载时为 “cannot open host.lock: Read-only file system”）。两项各有测试，只读 bind mount 一项需要 `sudo -n`（第 1 轮审查 F7-52 补上；此前这一项没有测试）。运行中改 `.hoh` 目录本身的权限没有测试，不在此列；
   - 启动时另一进程持有写锁：等 busy_timeout，然后以 DB_BUSY 退出 1，客户端 69，什么也不写；
   - 运行中的写锁：命令侧由 TEST-062-01 守住；runner 侧实测在 host.log 中写 “the runner: DB_BUSY”，锁释放后自行恢复。空闲的 runner 何时写库不稳定，所以这一项没有断言测试；
   - 数据库来自更新的二进制：退出 78，消息给出两个版本，数据库不变。

测试：`crates/hoh-app/tests/db_faults.rs`（busy、迁移、只读的五项默认运行；运行中写满、启动时写满、启动时只剩几 KiB、运行中转为只读与运行中加只读 bind mount 五项需要 `sudo -n` 挂载，标为 ignore，只在 `--ignored` 时运行，没有 `sudo -n` 时失败而不是通过；CI 的 product 作业以 `--ignored` 运行它们，没有 `sudo -n` 时该步失败（F7-51）），以及 `crates/hoh-app/tests/host.rs` 的 `a_store_failure_reaches_the_client_with_its_reason_and_writes_nothing`（经 CR-006 的提交前钩子注入 SQLITE_IOERR 类错误）。

2026-11-17，第 1 轮审查（F7-01..-04、F7-50..-55）后补两条规则：

- **写满的判定（F7-01、F7-02）**：WAL 自检中失败的 SQLite 调用，按它的扩展结果码与该调用的 OS errno 判定。SQLITE_FULL（不论 errno）是 `DB_FULL`；增长或写入库文件的 I/O 错误（SQLITE_IOERR_SHMSIZE、_WRITE、_TRUNCATE、_FSYNC）只在 errno 为 ENOSPC 或 EDQUOT 时是 `DB_FULL`；其余 I/O 错误仍是 `DB_WAL_UNSUPPORTED`，单凭一个 I/O 错误从不判为写满。rusqlite 没有安全的 `sqlite3_system_errno`，errno 在失败的调用返回后立即读取。探针进程以同一形式回报自己失败的调用（`error code=<主码> extended=<扩展码> errno=<n|-> <消息>`），父进程解析后用同一规则（`out_of_room`）判定，探针的写满不再经“写锁”一步说成 `DB_WAL_UNSUPPORTED`。此前所剩空间够建文件、不够增长 -shm 时，host 报 `DB_WAL_UNSUPPORTED` 并退出 78。
- **临时文件的归属（F7-03）**：自检只使用、只删除本次调用建出的文件。它用 `create_new` 在至多 8 个名字中取第一个可新建、且 -wal、-shm、-journal 都不存在的名字；已存在的名字属于别的创建者，原样留下，换下一个；8 个都被占用时 open 一步失败，什么也不删。建文件的其他失败（目录不存在、文件描述符用尽等）直接是 open 一步的失败，不再让 SQLite 打开一个不是本次建出的文件。事后删除本次建出的库文件和 SQLite 为它建的伴随文件（取名时它们都不存在）。因伴随文件已存在而放弃的名字，本次刚建出的库文件随即删除，删不掉时 open 一步失败并给出它的路径（第 2 轮审查 F7-150）。此前 `create_new` 遇到同名文件后仍打开它，事后连同伴随文件一并删除。

2026-11-17，第 2 轮审查（F7-100、F7-101）后的设计修正：同一机制（把存储失败判为空间不足）第二轮出问题，判定改为直接观察，取代上面第一条规则里的 errno：

- **不在 SQLite 调用之后读 errno。** SQLite 在同一次调用里还会做回滚等 I/O（Codex：WAL 的 fsync 得 EDQUOT，随后回滚读取被 EINTR 打断并重试，调用返回时 errno 已是 4），调用返回后读到的 errno 不一定属于失败的那次系统调用。能拿到原 errno 的接口都不可用：rusqlite 不提供 `sqlite3_system_errno`，`trace::config_log` 是 unsafe，各 crate 保持 `forbid(unsafe_code)`。
- **SQLITE_FULL 由 SQLite 自己归因**（写入得 ENOSPC，或短写），直接是 `DB_FULL`，不探测。
- **增长或写入库文件的 I/O 错误**（SQLITE_IOERR_WRITE、_FSYNC、_TRUNCATE、_SHMSIZE）出现时，当场在库所在目录探测空间：新建一个本次认领的文件（库名加 `-room`，与 -wal 等一样取名时须不存在），写入 64 KiB 不重复的字节并 fsync，再删除。64 KiB 是自检单次分配上限（-shm 的 32 KiB）的两倍；字节不重复，压缩的文件系统也要真分配。探测（建文件、写或 fsync）得 ENOSPC 或 EDQUOT 即 `DB_FULL`，可重试，消息给出原来的失败与探测的结果。探测成功即不是空间不足；探测因别的原因失败则不能断定，按不是空间不足处理，消息带上探测的错误。
- **不是空间不足的失败仍是 `DB_WAL_UNSUPPORTED`，退出 78，不可重试**：REQ-062 行为 7 规定自检失败即以 `DB_WAL_UNSUPPORTED` 拒绝启动，`DB_FULL` 是 CR-006 对写满与超配额的定义带来的唯一例外，改码要先有 CR。但消息要说出它是什么：存储 I/O 错误、哪一类（write、fsync、truncate、-shm 增长）、SQLite 扩展码的数值，以及“目录有空间：64 KiB 写入并 fsync 成功”或探测的错误。-shm 映射失败（SQLITE_IOERR_SHMMAP）与 checkpoint 失败不探测，照 AC-062-06 是 `DB_WAL_UNSUPPORTED`。
- **父进程与探针用同一规则**：探针回报失败调用的主码与扩展码（`error code=<主码> extended=<扩展码> <消息>`，不再带 errno），父进程在同一目录做同一次探测。
- **有写入效果的语句执行到底（F7-101）**：`PRAGMA journal_mode=WAL` 在新库上要提交（写 journal、写库头）。`query_row` 拿到第一行就返回，提交的错误在 Rows 的 drop 里丢掉了，host 后来只说 “no -shm file”。自检与正式库的 writer 都改为逐行读到结束，把错误传回。
- **剩余风险**：失败与探测之间空间被腾出，会判为不是空间不足（退出 78），消息仍带原来的失败；只出现一次、随即消失的配额或空间错误同样如此。

2026-11-17，同一规则用于正式库的提交（docs/09 第 7 项的“写入时磁盘满”，第 2 轮修正后补）：writer 的提交（`writer::commit`、`commit_unhooked`）失败于写入、fsync、截断或 -shm 增长时，当场在 `.hoh` 里探测空间，用的是本进程此刻命名的文件（`state.db-room-<pid>-<纳秒>`，create_new，写 64 KiB 并 fsync 后删除）。探测得 ENOSPC 或 EDQUOT 即 `DB_FULL`：503、retryable=true，状态、事件与 outbox 不变（CR-006）。否则照旧是存储错误（503 UNPROCESSABLE，不可重试），原因写出失败的 I/O 类别、SQLite 扩展码与探测所见。SQLITE_FULL 照旧直接是 `DB_FULL`。提交之前的语句失败（页缓存溢出时的写入）不探测，照旧映射。host 若在探测中途崩溃，可能留下一个 64 KiB 的探测文件。

2026-11-17，第 3 轮审查（F7-200）后的规则：临时文件的归属第二次出问题（第一次是 F7-03），先定规则再改代码。

- **只经由建出它的那次认领删除。** 自检可能删除的每个文件，都只凭建出它的那次 `create_new` 留下的凭据删除：凭据是路径加上刚建出时的 (dev, inode)，删除前用 lstat 核对路径上仍是那个文件，是才删。不是本次建出的名字一律不删，事先检查过它不存在也不算数。
- **认领建出全部名字。** 取名时自检用 `create_new` 依次建出库文件与 -wal、-shm、-journal 的空文件，任何一个已存在，这个名字就是别人的：已建出的几个经凭据删掉，换下一个名字。SQLite 打开已存在的伴随文件照常使用；它自己在提交或最后关闭时删掉的，事后已不存在，无需再删。“共享 wal-index” 的判据因此由“-shm 存在”改为“-shm 非空”（SQLite 用它时长到 32 KiB）。
- **空间探测的文件归探测自己。** `-room` 由探测用 `create_new` 建出、经自己的凭据删除，外层清理不再碰它。探测遇到同名文件已存在，那是别人的：留着，空间按“不能断定”处理。
- **同名而 inode 不同的文件不是本次的**（别人建的，或 SQLite 删后重建的），不删。
- **剩余窗口**：lstat 核对与 unlink 之间路径被换掉的情形关不上：没有按 inode 删除的系统调用，rustix 也不提供，各 crate 保持 `forbid(unsafe_code)`。
