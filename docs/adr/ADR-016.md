# ADR-016 · Engine host 骨架：启动、本地 API 与命令幂等

状态：M2-T12 采纳（CTO 设计决定，细化 REQ-022、REQ-036、REQ-041、REQ-062，不改变 CONTRACT 或已锁定契约；故障注入点的形式见 CR-006）。日期：2026-11-06。

## 背景

REQ-041 规定了 host 启动的顺序，REQ-062 规定了连接设置、writer 与位置检查，REQ-022/036 规定了命令的幂等与提交后才通知，openapi.json 给出了端点与 Error 体。以下各点它们没有规定：

- host 的文件放在哪里；
- token 与 Host/Origin 怎样校验；
- 未知 Run、被拒命令、PauseRun 的事件与 outbox 长什么样；
- SSE 怎样与提交顺序对齐；
- 各种存储错误的 HTTP 映射。

以下决定填补这些空白。实现在 `crates/hoh-app/src/host/`（hoh-app 的库目标 `hoh_app`）与 `crates/hoh-core/src/persistence/commands.rs`。

## 决定

1. **启动顺序**：
   1. 只读检查 `.hoh/` 最近存在的祖先所在文件系统。网络或共享文件系统直接拒绝，什么都不创建。
   2. 创建 `.hoh/`，以非阻塞 `flock` 锁住 `.hoh` 目录本身（不删数据库就换不掉它；锁一个文件的话，文件被删后第二个 host 就能锁上新文件，M2T12R-152），并把本进程 pid 写入 `.hoh/host.lock` 供诊断。锁被占用时退出 69，并给出持有者的 pid。
   3. 打开 store：再次检查位置，做 WAL 自检，设置并校验连接参数，迁移。
   4. `PRAGMA quick_check` 通过后，在同一事务里取得或建立该仓库路径的项目，并把 `host_epoch` 加一。
   5. 打开 4 个只读连接，逐个校验设置，并确认它们拒绝写入。
   6. reconcile 尚未实现（M2-T05），目前没有可租出的工作。
   7. 先绑定 `127.0.0.1:<port>`，再绑定 `.hoh/host.sock`（模式 0600；只删除之前遗留的 socket，其他文件一概不动）。端口被占时不会留下 socket（M2T12R-08）。
   8. 原子写入 `.hoh/host.json`（模式 0600），内容为 pid、project_id、host_epoch、port、socket、token。

   第 8 步之前任何一步失败，host 都不提供服务；写 host.json 失败时先停止服务、移除 socket，再随错误释放锁（M2T12R-08）。位置被拒或 WAL 自检失败时退出 78（环境不能按配置使用），且不留下正式 DB 文件；其余失败退出 1。SIGTERM/SIGINT 时按决定 12 停止；锁文件与数据库保留。REQ-041 写“取项目锁→schema 与完整性检查”，done_when 写“先做 DB 位置检查与 WAL 自检”：上面的顺序（只读检查→取锁→完整打开）同时满足两者。
2. **端口**：默认 8787（openapi `servers`），可配置，0 表示取空闲端口。实际端口写入 host.json。每个项目一个 host，所以测试与多项目时不依赖固定端口。
3. **请求校验**：在路由之前、任何处理之前进行，失败一律返回 403 FORBIDDEN，Error 体完整。
   - token 为 32 字节随机数的十六进制，经 `X-HoH-Token` 传入，以恒定时间比较。
   - TCP 上必须恰有一个 `Host`，且等于 `127.0.0.1:<绑定端口>`；`Origin` 最多一个，只能不出现或等于 `http://127.0.0.1:<端口>`；绝对形式的请求目标所带的 authority 也必须是这个地址。这样可以挡住 DNS 重绑定和其他网页发来的请求（M2T12R-05）。
   - socket 上不检查 `Host`，但任何 `Origin` 都拒绝，带 authority 的请求目标也拒绝。
   - `/healthz` 不需要 token（openapi `security: []`），Host/Origin 照样检查。
4. **命令**：`POST /v1/commands` 先按协议 schema 校验 `Command`，再处理。
   - 目前实现 PauseRun（其他 kind 随各自任务实现，现在返回 422 CAPABILITY_UNSUPPORTED，不写任何东西）。
   - 幂等比较用的哈希取整个命令体的规范 JSON（键排序）的 sha256，而不只是 `payload`。否则 kind 不同、payload 相同的两条命令会被当成同一条。
   - 一条命令就是一个 `BEGIN IMMEDIATE` 事务，依次做：
     1. 按 idempotency_key 查找已有命令：哈希相同则原样返回已存的结果字节，并带 `Idempotent-Replayed: true`；哈希不同则返回 409 KEY_REUSE。
     2. Run 不存在时返回 409 RUN_NOT_FOUND，`current_revision` 为 null（openapi 的 submitCommand 没有 404）。
     3. 以 compare-and-set 迁移 Run（PauseRun → PAUSE_REQUESTED）。
     4. 追加事件 `run.pause_requested`，payload 为 command_id、state、reason。
     5. 插入一条发往 commander 的 outbox。
     6. 插入 commands 行，`result_json` 存的正是 202 体 `{command_id, run_id, revision, status:"ACCEPTED"}`。
     7. COMMIT。
   - 只有被接收的命令才有 commands 行（`accepted_at NOT NULL`）。被拒的命令重试时会重新判定，不记成拒绝结果。
5. **PauseRun 的 outbox**：outbox 行收件角色为 `commander`，role_epoch 为 1（角色绑定随 M2-T07 实现），payload 为运行时通知 `{kind:"run.control", control:"PAUSE_REQUESTED", run_id, command_id, event_id, reason}`。它不是 HCP Message：HCP Message 必须带 task/attempt/spec，而暂停是 Run 级的。投递形式由 M2-T04 决定，届时如需改为 HCP 消息，在该任务中修改。
6. **错误映射**：Error 体总是包含 code、message、retryable、current_revision，message 为固定文本。数据库自身的错误文本只写到 host 的 stderr，不会到达客户端，响应中不出现 SQLITE_*（M2T12R-02）。未知路由与方法也返回 Error 体（404 NOT_FOUND）。

   | 情形 | 状态码 | code | retryable | current_revision |
   |---|---|---|---|---|
   | KEY_REUSE、ILLEGAL_TRANSITION | 409 | 原名 | false | Run 当前的 revision |
   | STALE_REVISION | 409 | STALE_REVISION | false | 存储中的 revision |
   | 约束违例（如 command_id 已被另一条命令使用） | 409 | CONFLICT | false | Run 当前的 revision |
   | 写锁超过 busy_timeout | 503 | DB_BUSY | true | Run 当前的 revision |
   | 写满（CR-006） | 503 | DB_FULL | true | Run 当前的 revision |
   | 其他存储错误 | 503 | UNPROCESSABLE | false | null |
   | 非 JSON、不合 schema、请求体过大或读不出 | 400 | BAD_REQUEST | false | null |
   | getRun 的 run_id 不是文本 | 404 | RUN_NOT_FOUND | false | null |
   | streamEvents 的 after、Last-Event-ID、run_id 或 kinds 读不出，或 after 为负 | 409 | CONFLICT | false | null |

   后两行使用 openapi 已为该端点列出的状态码：getRun 没有 400，读不出的 id 不指向任何 Run；streamEvents 没有 400，所以用 409（M2T12R-03）。
7. **提交后才可见**：writer 线程在每个请求结束后读一次最大事件 seq，只在它增大时发布 watermark。事务未提交时它不变，所以订阅者只会看到已提交的事件。处理器从不广播，客户端断开也不会丢失事件或让事件提前出现。
   - `GET /v1/events` 连接时先订阅 watermark，取当时的 H，从数据库回放 (after, H]（每页 500 条），之后每当 watermark 前进，就读新提交的事件。SSE 的 id 为 seq，data 为协议 Event，`attempt_id` 为 null（events 表没有这一列）。
   - `after` 与 `Last-Event-ID` 都给出且不一致时返回 409 CONFLICT。
   - M2 不清理事件，所以 410 不会出现。
8. **读**：`GET /v1/runs/{id}` 在一个读事务里同时读出 Run 与最大 seq（snapshot 与 watermark 一致）。它用连接池中的只读连接，在 `spawn_blocking` 中执行，不占 Tokio worker，也不等 writer（AC-062-01）。`projection` 为 mode、resume_state、blocked_reason。不存在时返回 404 RUN_NOT_FOUND。
9. **writer 队列**：host 使用 REQ-018 的 `writer_queue_capacity=256`（persistence 的默认值 64 留给其他调用方）。队列满时等待 busy_timeout，之后返回可重试的 DB_BUSY。
10. **诊断**：连接设置不在 openapi 中，由进程内接口 `Host::diagnostics` 给出 writer 与各 reader 的 PRAGMA，以及 reader 是否都拒绝写入（AC-062-01）。
11. **故障注入点**：按 CR-006 是空操作钩子，产品实现都只用 trait 的默认方法。
    - persistence 的 `FaultHooks`：提交前、WAL 自检每一步前。产品实现为 `NoFaults`。
    - WAL 自检第二进程的 `ProbeBehaviour`：打开、计数、各命令的应答。产品实现为按协议行事的 `NormalProbe`。
    - host 的 `HostHooks`：命令提交后、响应发出前。产品实现为 `NoHostFaults`。

    测试的实现负责制造故障：写满错误、自检某一步失败、第二进程不加锁、计数不更新、假锁、单向锁，以及在提交后丢弃连接（该处 unwind，连接任务结束，不写任何响应字节）。另有测试确认产品实现都不带方法体（有反例测试），并调用它们确认不产生故障。

12. **停止时的生命周期（设计修正，M2T12R-01、-60、-91 三轮属于同一类）**：锁的释放与“旧 host 已不可能再写”在结构上绑在一起，不靠某一步的超时或等待是否成功。
    - **锁由 writer 线程持有**。项目锁在 store 打开后交给 writer 线程（`Store::keep_until_closed`）。writer 线程只有在所有 store 句柄都被丢弃、队列中的请求全部处理完、写连接关闭之后才退出，退出时才释放锁。store 句柄只在所有连接任务、事件流和读任务都结束后才会全部丢弃。所以锁一旦释放，旧 host 就没有任何连接可以接收请求，也没有任何写入待提交。这一点不论 `Host::shutdown` 是否被调用、Host 是否被直接丢弃都成立：丢弃 Host 等同于发出停止。writer 线程若 panic，它持有的锁不随 unwind 释放，而是泄漏到进程结束，项目不会被别的 host 接管（M2T12R-120）。host 把这当作致命故障（M2T12R-150）：之后的写入返回 503 GONE（retryable=true，客户端应向下一个 host 重试），`/healthz` 返回 503；`host::run` 同时等待信号与 writer 结束，writer 先结束时停止 host 并以 1 退出，监督者看到失败，进程退出时锁随之释放，下一个 host 才能启动。此时 `Host::shutdown` 与失败的 start 返回时锁仍被持有，直到进程结束（M2T12R-151）。
    - **接收**：接收循环由 host 实现（hyper http1），每条连接是 host 的 JoinSet 中的一个任务，请求头必须在 30 s 内读完。accept 出错时，除了连接被拒绝、中止或重置，其余错误（如文件描述符用尽）都先退避 1 s 再继续，退避期间仍响应停止（M2T12R-92）。
    - **停止**，依次进行：
      1. 置停止标志，监听不再接收新连接。事件流在被轮询的每一步（回放或等待）检查停止并结束（M2T12R-98）；客户端不读而堵住的流不再被轮询，在宽限期后随连接被中止。
      2. 每条连接优雅关闭：空闲的或还在读请求的立即关闭，正在处理的处理完即关闭。在停止与关闭之间恰好读到的请求返回 503 GONE（retryable=true，客户端应向下一个 host 重试）。
      3. 最多等 5 s，之后中止仍在的连接任务。被中止的请求若已把事务排进队列，该事务仍由 writer 完成。
      4. 移除本 host 的 host.json（按 token 认定）与它绑定的 socket（按 inode 认定）；别的 host 放在那里的文件不动（M2T12R-120）。启动中途失败与直接丢弃 Host 时同样移除（M2T12R-153）。
      5. 丢弃 store，等 writer 线程退出，锁随之释放；`shutdown` 在此之后才返回（writer panic 的例外见上）。
    - **启动失败**：store 打开之后的启动失败同样丢弃 store 并等 writer 退出，所以返回错误时锁已释放（writer panic 的例外见上）。
    - **已知缺口**：getRun 与 streamEvents 在读失败（读连接忙、存储错误）与停止期间返回 503，而 openapi 没有为这两个端点列出 503。等 openapi 的下一次 CR 补上（M2T12R-61，后续项）。
