## 决定

1. **TEST→check 的同一读取规则（S1；Q4、Q5）。** spec 对象（候选的 spec 文件解析结果）有 `scenarios` 键时，TEST→check 只取自它：每条 AC 的 `test_id` 在 `scenarios` 中按 `id` 找 `check_id`；找不到该 TEST 或它没有 `check_id` 时为空（报告为 broken，缺 check），**不**回退。只有 spec 对象没有 `scenarios` 键（HoH 自身仓库的 `contracts/requirements.json` 布局）时，`scripts/product/traceability.py` 的 `World.tests()` 才读 `contracts/acceptance-scenarios.json`。产品侧是 `hoh_core::trace::tests`，同一规则；产品从不读项目的 `contracts/`：没有 `scenarios` 键的 spec 在产品导出中每个 TEST 都是 broken（缺 check）。“追踪期间不打开项目根下 contracts/”的观察：Python 侧以 `sys.addaudithook` 记录 `open` 事件，产品侧代码里不构造这条路径，夹具项目没有 `contracts/` 目录且结束时仍没有（不在产品里加 open 拦截，ADR-033 Q7 的做法）。AC-032-04 的“没有成员证据时 3 个 TEST 都是 NOT_RUN 而不是错误”按 ADR-027 决定 10 读：场景检查完全没有成员时原则一的报告状态是 MISSING（NOT_RUN 要求该检查有成员），两者都是“没有结论、不满足、不是错误”；测试断言 World 不抛错、三个 TEST 都是 MISSING，不改原则一的状态定义。CR-035 把 AC-032-04 改写为 MISSING（与 ADR-027 的定义一致），这一读法由它确认（M3N-006）。

2. **产品追踪导出（S1–S3；Q1–Q3、Q13）。** `hoh_core::trace` 是纯函数：输入是现有表的行（规格修订的 REQ/AC、Task 与 `task_requirements`、候选、证据、`acceptance_results`）与 spec 对象，输出一份 JSON 文档，不写第二份事实（REQ-032 行为 4）。spec 对象取当前候选（Run 最新冻结、且 `spec_sha256` 等于 Run 当前修订摘要的候选）的 spec 对象文件（冻结时保存在 `.hoh/objects`）；没有当前候选或对象读不到时，取该修订由批准事务写下的行重建的索引（与 ADR-033 的 `indexed` 同形，含 `scenarios`），字段 `spec_source` 记 `candidate` 或 `revision`；修订的行重建不出索引（AC 正文不是索引 JSON）时 spec 为空、`spec_error` 写明原因，getRun 不因此失败。文档字段：`run_id`、`spec_revision`、`spec_source`、`candidate_id`（当前候选或 null）、`requirements[{requirement_id, ac_ids, task_ids}]`、`acceptance[{ac_id, requirement_id, test_id, spec_revision, statuses}]`（`statuses` 为该 AC 在当前修订、当前候选上各结果行的状态）、`tasks[{task_id, requirement_ids}]`、`candidates[{candidate_id, state, current, task_ids}]`、`tests[{test_id, ac_id, check_id}]`、`evidence[{evidence_id, candidate_id, check_id, outcome}]`、`results[{ac_id, spec_revision, candidate_id, evidence_id, status, stale}]`、`broken`、`orphan`、`stale`。链的边：REQ→AC（`requirement_id`），AC→Task（Task 引用该 AC 的 REQ），Task→候选（候选冻结的是该 Run 的工作区：Run 的全部 Task），候选→TEST（该候选上的证据经结果连到 TEST 的 AC），TEST→证据（TEST 的 AC 的结果所引证据），证据→结果（`evidence_id`）；反向即逆边。
   - **broken**（每项 `{node, id, missing}`）：AC 没有 TEST（`missing: test`）；TEST 没有 check（`check`）；TEST 在当前修订下没有任何一条所引证据存在的结果（`evidence`）；证据的候选不在候选表中（`candidate`）；Task 没有 REQ（`requirement`）。
   - **orphan**：状态 PASS 或 DEGRADED、而候选不是当前候选或修订不是当前修订的结果，不计入当前进度（REQ-032 失败模式 2）。
   - **stale**：修订不是当前修订、或候选为 STALE 的全部结果（不只受影响的链，REQ-032 行为 5，O6），历史行照旧列在 `results` 中，`stale: true`。
   - API：`GET /v1/runs/{id}` 的 `projection.trace` 是这份文档（openapi 的 `projection` 为自由对象）；`GET /v1/runs/{id}/acceptance` 的条目增加 `test_id`（AC 的 `test_id`）与 `evidence_ids`（该 AC 在该候选、该修订下各行所引证据，按行序），游标与顺序不变；实现 openapi 已声明的 `GET /v1/runs/{id}/tasks`（`listTasks`）：条目 `{task_id, state, role, writer, spec_id, requirement_ids, depends_on, lease}`，按 `created_seq`、`task_id` 排序，游标为最后一项的这两个值，带 watermark；`Page.items` 是自由对象，不改受锁 schema。TUI 的 `/status` 多一行，读 `projection.trace` 的 broken、orphan、stale 数与修订号。

3. **TEST-032-01 的产品导出与仿本（S2；Q1、Q2、Q15）。** traceability 检查与 `scripts/check.sh --bundle` 都不跑 cargo，CI 的 bundle 作业也没有产品二进制，所以 `tests/bundle` 的测试不能自己启动 host。做法：`crates/hoh-app/tests/trace.rs` 的集成测试用产品 host 建夹具（2 条 REQ、4 条 AC、3 个 Task、1 个候选与每条 AC 的 PASS），取产品的追踪导出，把易变的标识（Run、规格、候选、项目 id）换成固定占位，与提交的 `tests/bundle/fixtures/trace-export.json` 逐字节比较；不同即失败（`HOH_BLESS_TRACE=1` 时重写），所以该文件始终是产品当前的导出。`tests/bundle` 里名称含 `test_032_01` 的测试读这份导出，核对仿本（`scripts/product/traceability.py` 的 `chain`，与 `hoh_core::trace` 同一规则）在导出上算出的 broken、orphan、stale 与产品写在导出里的逐项相同，逐节点核对正反两个方向都能走到整条链，再在副本上删去一条 TEST 的证据、把一条 AC 的 PASS 改绑旧候选，核对仿本报告该 TEST 缺 evidence、该 PASS 为 orphan、其余链完整。不往原则一的 `traceability-report.json` 加 broken/orphan 字段，门禁不读它。
   - **Q15 收紧 ADR-027 决定 10。** v0.1 档运行时，自测除档内以本检查为场景检查的 TEST 外，也运行 spec 中场景检查为本检查、但不在本档的 TEST 在 `tests/bundle` 里的方法（今天是 TEST-032-01）；它们的行写进同一个 `test-results.jsonl`，任一行 FAIL 时检查退出非 0；方法不存在则不写行、不因此失败。报告的 `tests` 与 `unsatisfied` 仍只含所请求的档。检查计划的 argv 不改（改成 v1 仍归 M7-T02）。

4. **run.baseline（S4；Q6、Q7、Q16）。** host 的控制 tick 对处于 DISCOVERING、还没有 `run.baseline` 事件的 Run 做一次只读发现，写 `run.baseline{head, tree, dirty:[{path, sha256}], untracked:[{path, sha256}], build_commands, test_commands, docs}`，事件 id `child_id(run_id, "baseline")`，一个 Run 一条，不 Touch Run 的 revision。git：`rev-parse --is-inside-work-tree` 判断是否仓库；`rev-parse HEAD` 与 `rev-parse HEAD^{tree}`（没有提交或非 git 时为 null，不用会写对象的 `write-tree`，非 git 目录不调用会建仓库的命令）；`status --porcelain=v1 -z --untracked-files=all` 得到已跟踪的改动与未跟踪文件，摘要经 `objects::hash_file`（只哈希普通文件，非普通文件与删除的文件 sha256 为 null）。命令检测（纯函数 `hoh_core::baseline`，全部检测、不只取第一种）：`Cargo.toml`→`cargo build`、`cargo test`；`package.json` 有 `scripts.build`/`scripts.test` 时记 `npm run build`/`npm test`；`Makefile` 有 `test:` 目标记 `make test`，有 `build:` 或 `all:` 记 `make build` 或 `make`；`pyproject.toml` 配置了 pytest（`[tool.pytest` 段）时记 `pytest`；都没有时该侧为 `["unknown"]`（C10）。docs：根目录的 `README*`，以及存在的 `docs/`、`docs/adr/`、`adr/` 目录，排序，不哈希正文。发现不运行项目命令（O3），不创建 Task。T04 的 Runtime 推进以后调用同一个记录函数。

5. **离开 DISCOVERING 的条件（S4）。** `decision::transition_run` 从 DISCOVERING 到任何别的状态时，若该 Run 没有 `run.baseline`，返回 `ILLEGAL_TRANSITION`（CR26D-151，C34）；谓词 `baselined` 单独成函数（与 main 集成后：M3-T06 的 readiness 不并在这里，它在 `transition_run` 中单独挡住到 READY 的迁移，ADR-035 决定 4）。Commander 一轮里先 DISCOVERING 后 SPECIFYING 的决策按序处置：Run 处于 DISCOVERING 且还没有基线时，该 Run 其余的 Commander 输出**等待**（与 PAUSED 时的“Held”同一机制），host 写下基线后下一次处置照常应用，不被拒绝。**与 Q6 的偏差：** Q6 写“同一决策批里不能走出 DISCOVERING，脚本拆开”。拆开需要一个新的 Commander 唤醒（基线事件）和每个 Run 多一轮 Commander，改动几十个测试的时序并多花模型配额；等待处置只改 Runtime 的处置次序，守卫的拒绝语义不变（直接提交的决策照旧 ILLEGAL_TRANSITION），基线仍先于 Run 离开 DISCOVERING。若审查不接受，再按 Q6 拆脚本。

6. **计划必须引用 REQ（S5；Q10）。** `plan::check` 对 `requirement_ids` 为空的 Task 整计划拒绝（`PLAN_INVALID`，details 点名该 Task），零导入；未知 id 的整计划拒绝保持原样。

7. **脏文件挡写 Task（S5；Q11；与 main 集成后并入派发准入）。** 写 Task 的 `task_paths`（ADR-035 决定 3）与该 Run 基线的 `dirty` 和 `untracked` 路径按路径分量求前缀交（`src` 命中 `src/lib.rs`，不命中 `src2/x`；空范围不命中；读者 Task 与验证 Task 不挡）。Run 全程以基线为准，基线之后新弄脏的文件不在本任务判定之内。每个 Task 只问一次：已有它的 `dirty_workspace` 问题时不再挡，由用户的答复决定（Route::Continue：答复 continue 回到 READY，cancel 取消）。不改任何文件字节（不 stash、不 reset），不建 Attempt。
   - **判定只在派发准入里（2026-11-22 与 main 集成时的设计更正，依 ADR-035 决定 12）。** S5 最初把这道闸写成调度轮里的私有检查，Commander 的 dispatch 决策与直接创建都不经它（原剩余风险）。ADR-035 决定 12 规定每一道派发闸都经同一个 `persistence::admission::admit`，所以它改为 `admit` 的第 4 步（修订、职位归属、readiness 之后；M3-T04 的模式准入顺延为第 5 步）：`Refusal::DirtyWorkspace{paths}`，对三条路径一视同仁，调度轮里不再有私有检查（`admission/tests.rs` 的 `test_028_03_the_dirty_file_hold_is_judged_in_the_admission_only` 按源码搜索核对 `baseline::uncommitted(` 与 `baseline::touched(` 只出现在 `admission.rs`；ADR-035 的路径表测试照旧通过）。各路径对这条拒绝的写法沿用 ADR-035 的被拒写法：
     - 调度轮：被拒的 Task 不进入本轮候选；同一事务把它 CAS 到 `BLOCKED(NEED_DECISION)`，经 `need::task_event` 写 `WorkReason::DirtyWorkspace`（`dirty_workspace`）的问题，`paths` 列出相交的文件。本轮没有选中任何 Task 时也提交这次阻塞。提问只在这里写：它是唯一在被拒时写入的路径。
     - Commander：`decision.rejected`，ILLEGAL_TRANSITION（受锁的拒绝码里没有更合适的一项，与 `NotReady` 同一码），`details` 为 `{paths}`；Task 保持 READY、不提问，下一次调度轮照上一条提问。
     - 直接创建（`Store::create_attempt`、消费效果）：`PersistError::IllegalTransition{entity: Task, to: "LEASED"}`，`details` 为 `{paths}`，不写任何东西。
   - 测试：`crates/hoh-core/src/persistence/admission/tests.rs` 的 `test_028_03_the_admission_holds_a_write_task_on_dirty_files_on_every_dispatch_path`（`admit` 对三种 `By` 都拒绝 W 并给出文件、读者与范围外的写者放行；Commander 的 dispatch 被拒且 W 仍为 READY；直接创建被拒；调度轮阻塞并提问；问过之后准入不再挡）；端到端仍是 `crates/hoh-app/tests/discovery.rs` 的 `test_028_03_empty_req_rejected_and_dirty_blocks`。

8. **确认后的基线测试（S6；Q7、Q8、Q9；Q14 由 DC-T07 修订）。** 写基线的同一事务里，若 `test_commands` 不是 `["unknown"]`，以新的 `RunReason::BaselineTests`（`baseline_tests`，问题 id `runtime:baseline_tests`）提问，选项 `run`（运行一次）与 `skip`，**没有默认选项**（M3N-054：答复必须明确选 `run` 或 `skip`，正文对不上任何选项时 400，不会因缺省而启动项目命令）；Run 因此 BLOCKED(NEED_DECISION)，resume_state 为 DISCOVERING。答复释放声明、Run 回到 DISCOVERING；答复 `run` 时 host 的控制 tick 对每条测试命令运行一次（`sh -c`，项目根，stdin 为空，独立进程组，墙钟上限 30 分钟），进程的归属见下面的 DC-T07。输出写到 HoH 状态目录 `.hoh/baseline/<run>/` 下（不进项目的工作树），每次启动一个新文件 `<n>-<nonce>.log`（以 `create_new` 打开，从不截断已有日志）。全部命令正常结束后写第二条事件 `run.baseline_tests`（id `child_id(run_id, "baseline/commands")`）：`{commands:[{command, exit_code, timed_out, incomplete, status: pass|fail, failed_tests, log}]}`，`failed_tests` 从输出中 `test <name> ... FAILED` 行取（检测不到为 `[]`）；答复 `skip` 时写 `{commands:[], skipped:true}`。确认前不运行任何项目命令。问题挡住 DISCOVERING 中的 Run 时（BLOCKED、resume_state 为 DISCOVERING），Commander 的输出同样等待，不在 BLOCKED 中被处置；答复使 Run 回到 DISCOVERING 后再处置：问题与答复都推进了 Run 的 revision，所以等待中的迁移以 STALE_REVISION 结束并照 REQ-021 行为 6 重新唤醒 Commander，下一轮从 DISCOVERING 继续。基线是这两条事件的合并，第一条不改写。离开 DISCOVERING 的守卫只看第一条。回归判定是纯函数 `hoh_core::baseline::regressions(baseline_failed, candidate_failed)`：基线已失败的测试不算 HoH 引入的回归；候选失败的测试取自该候选证据所引 `test-results.jsonl` 产物中状态为 FAIL 的行的 `name`；结果放进 `projection.regression{candidate_id, baseline_complete, baseline_failed, candidate_failed, introduced, not_in_baseline}`（Q8）。

   **DC-T07（2026-11-22，第 1 轮审查的设计更正；M3N-003、M3N-050、M3N-051、M3N-053 同一类：基线测试命令不在其 Run 的进程归属之内）。** 原写法“不是 Attempt、不进取消阶梯、host 停止时杀组且不记录、下一个 host 重跑”只覆盖 host 正常停止：取消的 Run 可以在命令仍运行时到达 CANCELLED（CONTRACT 第 13 条），暂停可以在命令仍改写工作树时到达 PAUSED，host 被 SIGKILL 后进程组继续运行而下一个 host 再起一条并截断同一日志。更正后基线测试命令仍不是 Attempt、不建 cgroup，但它是其 Run 的、由 Runtime 拥有的进程：
   1. **先落盘身份，再产生效果。** 命令经一个只读一行的启动闸起动（`sh -c 'IFS= read -r go && [ "$go" = go ] || exit 125; exec </dev/null; exec sh -c "$1"'`，同一 pid、同一进程组），闸未打开时它不运行项目的任何东西。host 以 Attempt 所用的同一身份函数 `hoh_agents::identity::of` 读取 pid、boot id 与进程启动时间，在一个事务里写 `run.baseline_process{run_id, index, command, pid, boot_id, process_start_id, log}`（id `child_id(run_id, "baseline/process/<n>/<nonce>")`）后才写 `go` 打开闸。该事务只在 Run 处于拥有该命令的状态（第 4 条）且还没有 `run.baseline_tests` 时写入；否则不写，闸以关闭的 stdin 结束，进程被回收，命令不运行。
   2. **取消与暂停的屏障。** host 对自己正在运行的命令持有按 Run 的停止标志：CancelRun 的取消任务与暂停的安全点在推进 Run 之前先置标志、等待该命令被杀组并回收，再看该 Run 记录下且未确认结束的进程（第 3 条的同一判定）；任一仍在，取消不调用 `Canceller::step`、暂停不调用 `pause_step`，下一次再看。所以 CANCELLED 与 PAUSED 只在命令的进程组已空之后写下。被取消或暂停打断的命令不写 `run.baseline_tests`。
   3. **启动时与之后的协调。** 每个被 host 自己回收的命令写 `run.baseline_process_ended{run_id, process, settled_by: "host"}`。host 启动时，在 Attempt 的协调之后、控制循环开始之前，对项目里每条没有结束记录的 `run.baseline_process` 用 Attempt 协调所用的 `identity::presence` 判定：身份完全一致（`Ours`）时向其进程组发 SIGKILL 并等待组空（`Found::kill`、`Found::wait`），然后写 `run.baseline_process_ended{settled_by: "reconcile", seen, partial: true, log}`；已不存在（`Gone`）时同样写下结束；无法确认（`Leaderless`、`Unverifiable`、检查失败）时不发任何信号（ADR-019 决定 8），记录保持未结束。控制 tick 对不属于本 host 正在运行的命令重复同一判定。Run 有未结束的进程记录时不启动新的基线测试；旧日志保留为部分输出，重跑写新的日志文件。
   4. **只在拥有它的 Run 状态中启动。** 拥有基线测试命令的 Run 状态是非终态中除 PAUSE_REQUESTED、PAUSED 与 CANCEL_REQUESTED 之外的状态；`tests_waiting` 只返回这些 Run，第 1 条的事务再核对一次。暂停的 Run 恢复后，命令以新日志重跑。
   5. **超时的不完整失败集（M3N-053）。** 超过 30 分钟被杀组的命令，或日志读不到的命令，记 `incomplete: true`；回归投影中任一命令不完整时 `baseline_complete` 为 false，`introduced` 为 null（不把残缺名单当作完整的基线失败集），候选中不在残缺名单里的失败列在 `not_in_baseline`。

9. **AC-028-04（S7，Q12）。** git init、draft 答复、起草 Task、迁移 002 都归 M3-T04；本任务只保证基线的 seq 先于该 Run 的任何 Attempt 与 effect、空目录的 head 为 null。S7 在 M3-T04 合入前为 NOT_RUN。
