# ADR-024 · 角色交接：checkpoint 交接包、旧 epoch 隔离与交接后的崩溃恢复

状态：采纳（M2-T17，随任务分步补全）

## 背景

M2-T17 的验收是 REQ-019 的全部 AC（AC-019-01 至 -05；TEST-019-01 至 -04 属检查 `integration`，TEST-019-05 属 `recovery`）。done_when 另要求：交接包通过 ContextHandoff schema 校验。

需求依据（REQ-019）：

- 行为 1：绑定变更先持久化为待交接请求，到该职位当前 turn 结束或 writer 安全点才生效；生效前界面显示 pending。
- 行为 2：生效在同一事务内完成：更新绑定、role_epoch+1、追加交接事件、写入新会话启动的 outbox。
- 行为 3：role_epoch 低于当前值的 decision、steer 和消息只进入历史（REJECTED，STALE_ROLE_EPOCH），不改变任何状态，不产生派发。
- 行为 4：新持有者的首个输入是 checkpoint 交接包（goal、当前 spec_sha256/revision、已 APPLIED 的决策、OPEN/REOPENED issue、未 ACK 的 outbox 与 QUEUED 输入、当前 candidate 身份），不是旧会话全文。
- 行为 5：交接不重复原任务；新持有者对已租用或已 ACCEPTED 的 task 的派发由租约与状态检查拒绝。
- 行为 6：紧急中断写者时该 attempt 标为 UNKNOWN_EFFECT，先 reconcile，之后新写者才能取得写租约。
- 决定 1：role_epoch 按 (run_id, role) 维护，Commander 交接不隔离 Developer 的在途结果。决定 2：新 Agent 生效时探测失败，保留旧绑定与旧 epoch 并记录失败事件。决定 3：Commander 的安全点是当前 turn 结束或没有在途 turn。

起点（main 569ff2b）：

- ADR-022 决定 8（第三版）的 checkpoint 已在一个事务里换绑：没有在途 Attempt（PREPARED、STARTING、RUNNING）的职位 epoch+1、会话置空、写 team.binding_applied；新 Agent 不可用则拒绝（team.binding_refused），旧绑定继续工作。checkpoint 只写事件，不写 outbox。
- decide 已按 role_epoch 拒绝过期决策（REJECTED，STALE_ROLE_EPOCH，ADR-011）；派发 RUNNING 或 ACCEPTED 的 task 得到 ILLEGAL_TRANSITION；TaskResult 按 Attempt 的 epoch 拒绝（ADR-018 决定 5）。
- `hoh_core::handoff` 只有验证交接包（ADR-018 决定 6）；产品代码不写 handoffs 与 artifacts 表。
- StartRun 不写 spec，产品中没有任何代码设置 `runs.spec_id`；而 ContextHandoff 的 `spec_sha256`（64 位十六进制）与 `spec_revision`（≥1）必填。
- 产品还没有 Commander 的执行路径（turn 与唤醒属 M2-T08）。

预研：`.hoh-dev/evidence/m2t17-prep/`（analysis.md 的事实已按 main 569ff2b 逐条核对后才写入本 ADR）。

## 决定

1. **交接包只给 Commander。** `hoh_core::handoff::role_change` 是纯函数：`handoff_kind=role_change`、`task_id=null`、`role=commander`、`role_epoch` 为生效后的新值；goal 取 StartRun 命令的 goal（缺失或空白时用固定说明，与验证交接包同源：`results::started_goal`）；spec 取 Run 当前的 spec；candidate 取当前候选（最新的 FROZEN 或 VERIFYING，`outbox::current_candidate`，与 consume 栅栏同一定义），没有则为 null；`acceptance_ids` 与 `references` 为空（上下文装箱属 M2-T09）；`output_contract=DecisionPayload`；`budget_tokens` 用 `handoff::BUDGET_TOKENS`。`state` 只放行 id：`applied_decision_ids`（该 Run 的 APPLIED 决策）、`open_issue_ids`（OPEN 与 REOPENED）、`unacked_message_ids`（该 Run 所有不是 ACKED 的 outbox 行，含 DEAD_LETTER 与运行时通知；本次的启动通知在它之后写入，不在其中）、`queued_input_ids`（QUEUED 的输入）；每个列表排序、去重。不读任何原始日志或会话记录，所以旧会话的内容不可能进入交接包。其他职位换人时，新持有者的首个输入是它下一次被派发的任务自己的交接包，不另做交接包。

2. **生效事务。** Commander 换绑发生在 ADR-022 决定 8 的 checkpoint 事务里（`persistence::handover::prepare`，由 `team::checkpoint` 调用），在同一个 IMMEDIATE 事务中写：绑定（新 Agent、epoch+1、会话置空）、team.binding_applied、handoff.prepared 事件（run、role、新 epoch、新旧绑定、启动通知的 message_id、spec revision、candidate id、state 的各 id 列表），以及一行 outbox 运行时通知：`{"notice":"runtime","kind":"session.start","run_id","role":"commander","role_epoch","package"}`，`recipient_role=commander`、`role_epoch` 为新值、`event_seq` 指向 handoff.prepared。通知 id 由 run、role、epoch 派生（`child_id(run, "session-start/commander/<epoch>")`），同一次交接只有一行。不用 HCP Message：信封要求 task_id，consume 的修订号栅栏会把没有 Task 的消息判为 STALE_REVISION；运行时通知本来就被投递循环排除（ADR-018 决定 4），由 runner 处理（决定 4）。交接包在写入前按 protocol.schema.json 的 ContextHandoff 校验，不通过则整个事务失败。提交失败（含故障注入的 before_commit）时绑定、事件与通知都不写。

3. **不加迁移，不改 SQL。** handoffs 表要求 `package_artifact_id` 指向 artifacts，而工件存储属 M2-T09/M2-T10；交接包本身在启动通知的 payload 里，handoff.prepared 事件记录它的各 id 列表。

（决定 4 至 9 随切片补全：会话启动与首个输入的投递、Commander 安全点、旧 epoch 的拒绝点、缺认证、崩溃点、紧急中断写者。）

10. **没有 spec 的 Run。** AC-019-02 的前提是“run 含 goal G、spec revision 3”，TEST-019-02 的夹具预置了这些行，所以 REQ-019 的每条 AC 都以有 spec 的 Run 为前提。没有 spec 时做不出合法的交接包，也不编造摘要：checkpoint 拒绝 Commander 的这次修改，写一条 team.binding_refused（`reason=NO_SPEC`），旧绑定与 epoch 保留并继续工作，与 REQ-019 决定 2 的拒绝相同；拒绝在之后每个 checkpoint 重新判断，Run 有了 spec 就照常生效并带交接包。不写 CR：没有放宽任何校验，没有收窄 AC，没有删减范围。**已知限制**：StartRun 目前不写 spec，所以在产品中 Commander 的修改要等 Run 有 spec 才生效；本任务的报告写明这一点。

## 验证

- S1：`handoff::tests::a_role_change_package_is_schema_valid_and_carries_ids_only`（有候选与无候选两种，按 schema 编码与解码，id 排序去重）。
- S2：`persistence::team::tests::a_commander_change_writes_binding_package_and_session_start_in_one_transaction`（提交失败时什么都不写；提交后绑定 epoch 2，一条 handoff.prepared，一条指向它的 session.start 通知，交接包的 goal、spec、candidate 与各 id 列表与数据库一致）；`a_commander_change_of_a_run_without_a_spec_is_refused_until_the_run_has_one`（决定 10）。
