# ADR-024 · 角色交接：checkpoint 交接包、旧 epoch 隔离与交接后的崩溃恢复

状态：采纳（M2-T17，随任务分步补全）

> 更正（ADR-026 决定 3、6、10，M2-T09）：决定 4 的交接包位置改为模板第一个占位符的值里（六个内置模板都是 GOAL：目标之后、其余上下文之前），欠着期间每个 turn 仍先读到它；交接包整个放入，与强制项一起计入预算，装不下即 CONTEXT_BUDGET_TOO_SMALL（不截断、不以摘要代替）；决定 1 的 references 引用该职位前任持有者已登记的工件（只引用、不读内容，结构性保证不变），budget_tokens 取 Run 配置快照；决定 3 的 handoffs 表由 M2-T16 写。

## 背景

M2-T17 的验收是 REQ-019 的全部 AC（AC-019-01 至 -05；TEST-019-01 至 -04 属检查 `integration`，TEST-019-05 属 `recovery`）。done_when 另要求：交接包通过 ContextHandoff schema 校验。

需求依据（REQ-019）：

- 行为 1：绑定变更先持久化为待交接请求，到该职位当前 turn 结束或 writer 安全点才生效；生效前界面显示 pending。
- 行为 2：生效在同一事务内完成：更新绑定、role_epoch+1、追加交接事件、写入新会话启动的 outbox。
- 行为 3：role_epoch 低于当前值的 decision、steer 和消息只进入历史（REJECTED，STALE_ROLE_EPOCH），不改变任何状态，不产生派发。
- 行为 4：新持有者的首个输入是 checkpoint 交接包（goal、当前 spec_sha256/revision、已 APPLIED 的决策、OPEN/REOPENED issue、未 ACK 的 outbox 与 QUEUED 输入、当前 candidate 身份），不是旧会话全文。
- 行为 5：交接不重复原任务；新持有者对已租用或已 ACCEPTED 的 task 的派发由租约与状态检查拒绝。
- 行为 6：紧急中断写者时该 attempt 标为 UNKNOWN_EFFECT，先 reconcile，之后新写者才能取得写租约。
- 决定 1：role_epoch 按 (run_id, role) 维护，Commander 交接不隔离 Developer 的在途结果。决定 2：新 Agent 生效时探测失败，保留旧绑定与旧 epoch 并记录失败事件。决定 3：Commander 的安全点是当前 turn 结束或没有在途 turn。

起点（main 569ff2b）：

- ADR-022 决定 8（第三版）的 checkpoint 已在一个事务里换绑：没有在途 Attempt（PREPARED、STARTING、RUNNING）的职位 epoch+1、会话置空、写 team.binding_applied；新 Agent 不可用则拒绝（team.binding_refused），旧绑定继续工作。checkpoint 只写事件，不写 outbox。
- decide 已按 role_epoch 拒绝过期决策（REJECTED，STALE_ROLE_EPOCH，ADR-011）；派发 RUNNING 或 ACCEPTED 的 task 得到 ILLEGAL_TRANSITION；TaskResult 按 Attempt 的 epoch 拒绝（ADR-018 决定 5）。
- `hoh_core::handoff` 只有验证交接包（ADR-018 决定 6）；产品代码不写 handoffs 与 artifacts 表。
- StartRun 不写 spec，产品中没有任何代码设置 `runs.spec_id`；而 ContextHandoff 的 `spec_sha256`（64 位十六进制）与 `spec_revision`（≥1）必填。
- 产品还没有 Commander 的执行路径（turn 与唤醒属 M2-T08）。

预研：`.hoh-dev/evidence/m2t17-prep/`（analysis.md 的事实已按 main 569ff2b 逐条核对后才写入本 ADR）。

## 决定

1. **每个职位换给新持有者都交接（第 1 轮修正，M2T17R-03、-53）。** 行为 2 与行为 4 不限职位，schema 的 `role_change` 也不限职位，所以任何职位的绑定在 checkpoint 换给新的 Agent、模型或配置时都交接。交接包由纯函数 `hoh_core::handoff::role_change` 生成：`handoff_kind=role_change`、`task_id=null`、`role` 为该职位、`role_epoch` 为生效后的新值；goal 取 StartRun 命令的 goal（缺失或空白时用固定说明，与验证交接包同源：`results::started_goal`）；spec 取 Run 当前的 spec，Run 尚无 spec 时 `spec_sha256` 与 `spec_revision` 都为 null（CR-014，决定 10）；candidate 取当前候选（最新的 FROZEN 或 VERIFYING，`outbox::current_candidate`，与 consume 栅栏同一定义），没有则为 null；`acceptance_ids` 与 `references` 为空（上下文装箱属 M2-T09）；`output_contract` 为该职位交回的内容（`handoff::role_output_contract`：Commander 为 DecisionPayload，reviewer 为 IndependentReport，其余为 TaskResult）；`budget_tokens` 用 `handoff::BUDGET_TOKENS`。`state` 只放 id：`applied_decision_ids`（该 Run 的 APPLIED 决策）、`open_issue_ids`（OPEN 与 REOPENED）、`unacked_message_ids`（该 Run 所有不是 ACKED 的 outbox 行，含 DEAD_LETTER 与运行时通知；本次的启动通知在它之后写入，不在其中）、`queued_input_ids`（QUEUED 的输入）；每个列表排序、去重。不读任何原始日志、会话记录或行的内容，所以旧会话的内容不可能进入交接包。职位被移除（没有新持有者）时只换绑，不交接。原先的写法（交接包只给 Commander，其他职位以下一次任务自己的交接包为首个输入）不成立：产品不产生 `handoff_kind=task` 的交接包，Developer 的首个输入只有职位契约与任务头。

2. **生效事务。** 换绑发生在 ADR-022 决定 8 的 checkpoint 事务里（`persistence::handover::prepare`，由 `team::checkpoint` 调用），在同一个 IMMEDIATE 事务中写：绑定（新 Agent、epoch+1、会话置空）、team.binding_applied、handoff.prepared 事件（run、role、新 epoch、新旧绑定、启动通知的 message_id、spec revision、candidate id、state 的各 id 列表），以及一行 outbox 运行时通知：`{"notice":"runtime","kind":"session.start","run_id","role","role_epoch","package"}`，`recipient_role` 为该职位、`role_epoch` 为新值、`event_seq` 指向 handoff.prepared。通知 id 由 run、role、epoch 派生（`child_id(run, "session-start/<role>/<epoch>")`），同一次交接只有一行。不用 HCP Message：信封要求 task_id，consume 的修订号栅栏会把没有 Task 的消息判为 STALE_REVISION；运行时通知本来就被投递循环排除（ADR-018 决定 4），由 runner 处理（决定 4）。交接包在写入前按 protocol.schema.json 的 ContextHandoff 校验，不通过则整个事务失败。提交失败（含故障注入的 before_commit）时绑定、事件与通知都不写。

3. **不加迁移，不改 SQL。** handoffs 表要求 `package_artifact_id` 指向 artifacts，而工件存储属 M2-T09/M2-T10；交接包本身在启动通知的 payload 里，handoff.prepared 事件记录它的各 id 列表。

4. **会话启动与首个输入。** runner 每个 tick 在绑定器之后、调度轮之前看 PENDING 的 session.start 通知（`Waiting.session_starts`：通知、它的交接包，以及该职位绑定此刻的 epoch、会话与 Agent）。绑定的 epoch 已超过通知的：通知被取代，写一条拒绝的回执（`STALE_ROLE_EPOCH`）、通知置 ACKED、handoff.superseded 事件，永不投递。epoch 相同且绑定器已授予会话时，交给执行器 `Executor::open_session`：执行器收下后，在一个事务里写回执（consumer=runner）、通知 ACKED、handoff.delivered 事件；只有该通知自己 epoch 的那个会话能收（`deliver_session_start` 核对会话与 epoch），所以重复的结算什么都不做。默认执行器不收（通知留着，诊断只说一次），等待有界（10 s）后下一个 tick 再试。投递至少一次：收下之后、结算之前崩溃，重启后同一通知再交一次，执行器必须能无害地再收。产品执行器把交接包作为该会话的首个输入保存在 `.hoh/first-inputs/<会话>.json`：先完整写到自己的文件，再硬链接到位（位置上已有东西就失败），所以那里只会有一份完整的输入；同样的输入再来一次照收，不同的输入拒绝。首个输入未交付之前，该职位不被派发任何任务（`decide::load_binding` 的 active 要求该职位此刻 epoch 的启动通知已 ACKED，`handover::first_input_pending`），所以任务不会先于交接包到达新持有者。产品执行器在一个会话的第一个 turn 里，把保存的交接包完整放在职位契约之后、任务头之前。首个输入由 store 记账（第 3 轮设计修正，第 4 轮再修正：M2T17R-200、-201、-250、-300；同一类问题第 2、3、4 轮连续出现）：会话收到过交付给它的 session.start 之后，首个输入一直“欠着”，直到该会话有一个 Attempt 以 SETTLED 结束，即它的 turn 正常完成（runner 的结算，或 reconcile 观察到工作已完成）。不变量：欠着的期间，该会话的每个 turn 都从交接包开始，所以第一个完成的 turn 一定以交接包开头，它完成就证明 Agent 处理过这份输入。别的迹象都不算：起了进程（pid）、到了 RUNNING、记下了 Agent 的原生会话 id（Codex 在 `thread/start` 的回复、Pi 在 `get_state` 的回复里就给出它，早于任何任务输入，当时失败的结算也会记下它（第 6 轮起不再），第 4 轮 Codex 的 E1、E2）、结束为 FAILED 或 UNKNOWN_EFFECT，都不能证明 Agent 收到了以交接包开头的 turn。欠着的期间：Attempt 的分配带 `first_input`（为真），它的 turn 从交接包开始，保存的输入缺失或读不了就拒绝启动（FIRST_INPUT_UNAVAILABLE，瞬时类）；该会话同时只有一个 Attempt 在途（`decide::load_binding` 在该会话有 PREPARED、STARTING 或 RUNNING 的 Attempt 时不再派发，`handover::first_input_in_flight`），所以交接包不会同时给两个 turn。有一个 turn 完成之后不再欠，后续 turn 不带交接包，与会话能否续用、原生会话 id 何时出现都无关。代价（第 5 轮补全，M2T17R-453）：每个没有完成的 turn（失败、被取消、结果未知）之后，下一个 turn 都再带一次交接包，直到有一个完成；重复的是交接时的 checkpoint 快照，可能已落后于失败的 turn 留在工作区里的效果，标题仍写“本会话的首个输入”；这些都好过丢失（违反行为 4）。规则的活性依赖后续 turn 能在同一 HoH 会话里启动，下文的续用规则保证这一点；一个 turn 总不完成的会话每个 turn 都带交接包，且该职位一次只跑一个 Attempt；约束期间该职位的绑定不算 active，所以 Commander 此时派发该职位的另一个任务会被拒绝为 ROLE_CAPABILITY_MISSING（产品还没有 Commander 的执行路径，M2-T08 须给它“稍后再派”的原因或延后处理，M2T17R-352）。为什么用“完成”而不用“Agent 接受了提示”（Codex 的 turn/start 结果、Pi 的 prompt 成功、Claude 读完 stdin）：后者要每个适配器另报一个事实并逐一核对它们的先后，完成则是 store 已有、对每个 Agent 都成立的事实，而且必然晚于 Agent 处理了输入；它的代价只是失败的 turn 之后重复一次交接包。查询按通知 id（由 run、role、epoch 派生）定位，没有交接过的会话只花一次主键查找（`handover::first_input_owed`）。同一个证据也决定原生会话能不能续用（第 5 轮设计修正，M2T17R-450、-451；与 -200、-300、-350 同一类：过早出现的原生 id 被当成对话已存在的证据）：Agent 的原生会话 id 早于任何输入就会出现（Pi 在 get_state、Codex 在 thread/start 的回复里），而 Pi 1.5.0 只在会话有了消息之后才写会话文件，Codex 的线程看来也在第一条用户消息时才落盘；续用一个从未落盘的会话会在启动前就被拒（Pi 的 SESSION_NOT_FOUND，瞬时类，一直重试），该职位就永远跑不了任何 turn。所以 Attempt 的分配只在该会话有一个 Attempt 以 SETTLED 结束之后才带上 `native_session`（续用）；在那之前每个 turn 都新起原生会话（Pi 用由 HoH 会话派生的同一个 id 新起，与续用一个不存在的会话等价）。续用的目标也只由完成的 turn 写入（第 6 轮设计修正，M2T17R-500）：runner 结算一个 turn 时，只有结为 SETTLED 才把它观察到的原生会话 id 写进 `sessions.native_id`；失败、取消、结果未知的结算不写，所以过早给出的 id 不会成为目标，后来失败的 turn 也不会覆盖已完成 turn 的目标；reconcile 判为完成的 Attempt 没有观察到 id，就不写，下一个 turn 新起。续用的目标由构造保证来自完成的 turn（第 7 轮设计修正，M2T17R-600、-601；同一类问题第六次）：runner 结算一个 turn 为 SETTLED 时，在同一事务里写一条 `session.native` 事件（会话、原生 id、完成的 Attempt），Attempt 的分配只取该会话最近一条 `session.native` 事件里的 id 作为 `native_session`（按 run 与 kind 走索引）。`sessions.native_id` 不再决定续用：旧版本由失败 turn 写下的值、直接拿到 Store 的适配器在结算之前写下的值（doctor --live 的临时 store）、reconcile 判为完成却没有观察到 id 的 Attempt，都不会产生这条事件，也就都不会被续用；没有这条事件的会话，下一个 turn 新起原生会话。这条记录是保留的（第 8 轮，M2T17R-700）：写入器拒绝任何通用写入（`Store::commit`、Attempt 自己的事件、consume 的效果事件、结算带回的观察事件）写出 `session.native`，它只经 `writer::write_session_native` 在 SETTLED 结算的事务里写出；读取时也只采用引用了本会话一个 SETTLED Attempt 的记录，绕过 store 写进库里的、引用未完成 Attempt 的记录不会被续用。Pi 的 `handled`（后续分支，M2T17R-551）：Pi 以 `handled` 处置的 prompt（扩展命令、输入处理器）没有启动 HoH 这次的 run，本身不写消息，也就可能从未写出会话文件（扩展命令可以自己经 `sendUserMessage` 启动 run 并写入消息，那时文件已在，Pi 用同一个派生 id 接着用它，M2T17R-501；第 1 轮修正，M2T17FR-55）；这样的 turn 照 REQ-026 结为 SETTLED，对首个输入算作已被 Agent 收下（Pi 与它的扩展处置了这份输入，ADR-013 把输入记为 APPLIED），但 Pi 适配器不报告它的原生会话 id，所以它不产生 `session.native` 记录，下一个 turn 不会去续用一个从未落盘的会话（那会以 SESSION_NOT_FOUND 永远被拒）；之前已完成 turn 的记录不受影响。Pi 的例外（M2T17R-501）：Pi 每个 turn 都传同一个派生的 `--session-id` 与目录（ADR-013 决定 1），Pi 找到该 id 的会话文件就接着用它；一个在 prompt 之后失败的 turn 已经写了文件，下一个 turn 即使 HoH 不“续用”也会带上它的上下文（交接包在欠着时照样再给）。这修订了 ADR-022 决定 9 的续用规则，对从未交接过的会话同样适用（这个缺陷自 M2-T07 起就在，交接让它更容易出现）。代价：一个未完成的 turn 留在原生会话里的上下文不被续用，下一个 turn 从头开始（首个输入还欠着时，它照样从交接包开始；Pi 除外，见上文 M2T17R-501、-552）。执行器没有收下首个输入时，除了 stderr 的一行，还写一条 `handoff.undelivered` 事件（每个通知一次，带执行器的回答），团队页的成员显示 `first_input_pending`，所以职位在等首个输入是看得见的（M2T17R-150）。runner 在本 tick 的 checkpoint 与绑定器之后才看待投递的通知（它们与 StartRun 是 Run 绑定的唯一写者），所以同一 tick 里刚被 checkpoint 越过的通知只会被取代，不会交给执行器（第 1 轮修正，M2T17R-01）。首个输入的文件在硬链接之后同步目录，掉电也不会丢失已结算通知的输入；找到同样的输入时同样先同步目录才算收下（M2T17R-102）；崩溃留下的暂存文件在同一通知再次交付时删除（M2T17R-55）。不支持硬链接的文件系统上通知保持待投递，`handoff.undelivered` 与 stderr 说明原因（未改）。runner 在 checkpoint 与绑定器之后只重读待投递的启动通知（`Store::session_starts`），不重读整个等待状态（M2T17R-156）。**给 M2-T08 的义务**：Commander 的第一个 turn 必须以这份输入开头（Commander 的 turn 走产品执行器时自动满足）；M2-T08 落地后，TEST-019-02 改为断言假 pi 实际收到的输入（M2T17R-54）；产品的 HCP 投递循环出现时，同样不在首个输入交付之前向新持有者投递 steer 或交接（M2T17R-153）；consume 对重用 id 的 Commander 消息返回 KeyReuse，投递循环届时须把它结算为一次拒绝，而不是按投递失败重试直至死信（M2T17R-254）。

5. **Commander 的安全点。** 沿用 ADR-022 决定 8 的在途判定（REQ-019 决定 3：当前 turn 结束或没有在途 turn）：该职位有 PREPARED、STARTING 或 RUNNING 的 Attempt 时修改等待，生效前运行处于落后于团队修订的状态，界面据此显示 pending。产品目前没有 Commander 的执行路径，所以 Commander 的修改总在下一个 checkpoint 生效。**给 M2-T08 的义务**：Commander 的在途 turn 必须让这个在途查询看得到（例如作为该职位的一个 Attempt），否则交接会打断一个在途 turn。

6. **旧 epoch 的拒绝点。** Commander 的每个输出在进入时都过它自己的 epoch：决策经 `decide`（ADR-011 已有，REJECTED、STALE_ROLE_EPOCH）；steer、query 等其他消息经 `Store::commander_message`（Commander 发出的消息带的是它自己的 epoch）：epoch 不是 commander 绑定此刻的，就只进入历史，记为一条 decisions 行（REJECTED、STALE_ROLE_EPOCH，payload 为该消息）和一条 decision.rejected 事件，同一事务，其他什么都不写；当前 epoch 的通过且什么都不写，去往哪里由 M2-T08 的路由决定。同一条过期消息再交一次（应答丢失后的重试）得到第一次记录的拒绝，什么都不再写；同一 id 下内容不同的消息是 KeyReuse，在当前 epoch 时也是，两个栅栏都先查历史（`decide::recorded_commander_message`；第 1、2 轮修正，M2T17R-05、-60、-101）。入口处的栅栏不够：入口时 epoch 仍是当前的 steer 排队之后，交接才发生，它被消费时若只按接收方的 epoch 核对就会生效（M2T17R-02）。所以 consume 对 Commander 自己发出的消息（`sender_role=commander`）按 commander 绑定此刻的 epoch 核对，与它的效果在同一个事务里；被拒绝为 STALE_ROLE_EPOCH 时同样写一条 decisions 行（REJECTED，`INSERT OR IGNORE`：入口的栅栏可能已记下），之后再经入口栅栏时补写一次 decision.rejected 事件。这修订了 ADR-018 决定 2（consume 按接收方的 epoch 核对）对 Commander 消息的适用：Commander 的消息携带的是它自己的 epoch，其余消息不变。代价（M2T17R-154）：一个信封只有一个 role_epoch，所以 Commander 发给某职位、在该职位交接之前排队的 steer 由新持有者收到，不再按接收方的 epoch 拒绝；Commander 发出 `kind=handoff` 时，交接包的 epoch 须与信封相同。哪些 Commander 消息还要核对接收方的 epoch（例如按排队时接收方的 epoch 另行记录）由 M2-T08 的路由规定，写入 ADR-018/024。反方向同理：运行控制发给 Commander 的通知（PauseRun 的 run.control）在命令自己的事务里按该职位此刻的绑定填 epoch，交接之后就是新 epoch，不用调用方写的值。决策不走这个栅栏（它走 `decide`）。其余拒绝点不变：consume 按接收方的 epoch（ADR-018 决定 2）、TaskResult 按 Attempt 的 epoch（ADR-018 决定 5）、绑定器只给当前 epoch 授予会话、host_epoch 栅栏（REQ-041）。Developer 的在途 Attempt 不受 Commander 交接影响（REQ-019 决定 1）。

7. **缺认证。** host 的注册表对每个可用的 Agent 用它自己的状态命令看登录（与 `hoh doctor` 同一套：`hoh_agents::login`，从 doctor 移来，doctor 的行为不变），最多每 30 s 一次，与其他探测命令一样受 host 停止的控制（停止时被杀，被停止打断的一次不记录）。Agent 只有在登录也看过之后才算可用，所以修改不会抢在这次查看之前生效。状态命令明确说“未登录”时，该 Agent 进入 `Availability.auth_missing`：checkpoint 拒绝改到它的修改，写 team.binding_refused（`reason=BLOCKED_AUTH`，detail 是该怎么登录），旧绑定与 epoch 保留并继续工作（REQ-019 失败模式 3 与决定 2）；之后每个 checkpoint 重新判断，原因或 detail 变了就再写一条拒绝（例如先未安装、装好后未登录），相同的拒绝不重复写；团队页上待生效的修改显示最后一次拒绝的原因（第 1 轮修正，M2T17R-51）。输出说不清、或者没有不调用模型就能运行的命令（pi 没有默认 provider）时不拒绝：只有明确的“未登录”才拒绝。

8. **崩溃点。** 交接事务提交之前崩溃：整笔回滚，重启后按同样的输入重算，epoch 只加一次（事件与通知的 id 都由 run、role、epoch 派生）。提交之后、会话绑定之前（AC-019-05）：重启后绑定器为新 epoch 写唯一的会话行（会话 id 由 run、role、epoch 派生，`INSERT OR IGNORE`），然后投递。绑定之后、投递之前：重启后投递。执行器收下之后、结算之前：同一通知再交一次，产品执行器同样的输入照收（决定 4）。结算之后：什么都不做。旧 Commander 的在途 Attempt 由 ADR-019 的结算处理，交接等它结束（决定 5）。

9. **紧急中断写者（REQ-019 行为 6）：被中断的写者，其写租约只在记下工作区的同一事务里释放（后续分支，M2T17R-52）。** 不新增中断入口：交接本身不中断任何 Attempt（决定 5），ConfigureTeam 只接受 `apply_at=checkpoint`（REQ-018；主会话 2026-11-10 的取舍，未问过 owner）。产品里中断写者的已有路径有四条：runner 的结束（结为 UNKNOWN_EFFECT，或因取消结为 CANCELLED）、租约过期或执行器丢失后的 settle、启动 reconcile（ADR-019），以及取消的 pass（组空时结为 CANCELLED，ADR-021）。原先这四条都在 Attempt 迁移的同一事务里释放写租约（`attempts::move_attempt`），UNKNOWN_EFFECT 不记工作区，取消的工作区记录（`cancel.workspace`）在之后的 `finish_cancel` 才写，所以下一个写者可以在被中断写者留下的 HEAD、tree 与 diff 被记下之前取得写租约（M2T17R-52）。

   **规则（store 一处，`attempts::move_attempt`）。** “被中断的结束”是迁到 UNKNOWN_EFFECT，或从 RUNNING 迁到 SETTLED 以外的任何终态（FAILED、CANCELLED；第 1 轮修正，M2T17FR-50）。被迁移的 Attempt 若是项目 `writer` 租约行记着的持有者（不论是否过期：过期而未结束的持有者仍占着槽位，`leases` 的 effective），这次迁移必须带上工作区记录（`AttemptFacts.workspace`）：同一事务里先写 `attempt.workspace` 事件（与取消的 `cancel.workspace` 同一记录：HEAD、HEAD 的 tree，相对 HEAD 的 diff、未跟踪文件的名字与内容、status 各自的 sha256 与总的 sha256，`host::control::workspace`），然后才释放租约。不带记录的这种迁移被拒绝（`PersistError::WorkspaceRecordRequired`，事务回滚，什么都不写）：持有者没有结束，槽位仍被占着，任何新写者都拿不到写租约。读者与没有租约的 Attempt 不受影响；只有 SETTLED 的结束（Agent 完成了它的 turn）不是中断。FAILED 原先也被排除（理由是 Agent 自己结束、有观察到的结果），第 1 轮审查指出不成立（M2T17FR-50）：HoH 自己硬停写者时 Attempt 也结为 FAILED（适配器遇到超大帧时停止进程，PROTOCOL_FRAME_TOO_LARGE；截止时间同理），FAILED 本身分不出 Agent 自己的失败与 HoH 的中断，所以写租约持有者从 RUNNING 结为 FAILED 一律要求记录；代价只是每个失败的写者 turn 多一次 git 读（只在 store 拒绝之后才取）。

   **谁取记录。** store 不跑 git。host 在终止证明之后（ADR-021 决定 8d）、在阻塞线程上（决定 8g）取记录。每条路径先不带记录提交；store 拒绝为 `WorkspaceRecordRequired` 时，host 取记录，带着它把同一次结束再提交一次。host 不预判要不要记录：迁移是否“被中断”只在事务里才确定（取消标志可能在之间被设上，ADR-021 决定 8e；runner 的结束看 STARTED 的效果），预判漏掉的一次会被 store 拒绝而不是放过。四处：runner 的结束（`host::runner` 对 `runner_finished` 的调用）；settle 与启动 reconcile（同一个对 `reconcile_apply` 的包装 `host::reconcile::apply`）；取消的 pass（`cancel::Canceller::step` 经 `Processes::workspace`）。取消的 pass 在同一事务里先写本次 pass 的步骤事件（native_cancel、sigterm、sigkill、reaped），再写记录与结束，所以事件日志里工作区记录出现在中断之后（第 1 轮修正，M2T17FR-51）。取消时，取得记录的 pass 若是该步的最后一个 pass，随后 Run 的 `cancel.workspace` 复用这份记录，不再取第二次（AC-043-02 的 ≤17 s）；否则 `finish_cancel` 照旧另取。

   **崩溃。** 提交之前崩溃：什么都没写，持有者没有结束，槽位仍被占着；重启后的启动 reconcile 再走同一规则（它在 runner 启动之前完成，ADR-019），所以不会有授予抢在记录之前。事务中崩溃：回滚。提交之后：记录、结束与释放一起持久化。

   **读法（规格的歧义，主会话的取舍，未问 owner）。** A1：行为 6 说标为 UNKNOWN_EFFECT；取消仍结为 CANCELLED（REQ-043 的状态与测试不变，效果记 UNKNOWN，ADR-021 决定 8e），规则同样适用于 RUNNING → CANCELLED。STARTING 的 Attempt 在 gate 打开之前 Agent 没有运行（runner 先在一个事务里记 RUNNING 与工作效果 STARTED，再开 gate），所以 STARTING → CANCELLED 与 STARTING → FAILED（启动被拒）不需要记录；迁到 UNKNOWN_EFFECT 则一律需要（规则简单，代价只是一次 git 读；产品路径上 STARTING 的 Attempt 不会迁到 UNKNOWN_EFFECT，`reconcile::dispose` 与 runner 的结束都只让 RUNNING 的 Attempt 结果未知）。A2：记录按 Attempt 写（`attempt.workspace`，id 由 Attempt 派生）；取消仍另写 Run 的 `cancel.workspace`。A3：“reconcile 工作区 hash 与 commit”是只读地记下 HEAD、tree 与各 hash，不创建 git commit，不 reset、不 clean（ADR-021 决定 8g；docs/14）。A4：只适用于上述四条路径；没有启动过 Agent 的结束（取消 PREPARED 的 Attempt、暂停撤回、启动被拒的 STARTING）不在其内。A5：记录本身失败（不是 git 工作树、git 失败或超时）时，带 `error` 的记录照样算作记录，与取消一致（ADR-021 决定 8g）：否则不是 git 仓库的项目在一次中断之后永远拿不到下一个写者。git 工作树里 git 失败或超时（损坏的仓库、5 s 内读不完）同样如此：记录里有 HEAD（读得到时）与错误，没有 diff 与 status 的 hash；保留槽位并重试会让一个总是失败的仓库永远挡住所有写者（第 1 轮审查的疑问 M2T17FR-52，按 low 推迟：主会话的读法，没有降低任何门槛，未问 owner）。A6：行为 6 没有 AC/TEST 编号，测试用普通名字；补 AC-019-06 需要 CR，另提，不在本分支。A7：写者的主进程自己成功结束而进程组没清空时，租约到期后 settle 停掉残留进程，再按观察到的成功判为完成（SETTLED）：turn 已经完成并给出结果，残留进程的清理不算中断，不要求记录（第 2 轮审查的疑问 M2T17FR-150，按 low 推迟）。

   **代价。** 被中断的写者的结束多一次 git 读：小仓库毫秒级，最坏每条 git 命令 5 s、未跟踪内容 5 s 预算；启动 reconcile 每个被中断的写者多一次（AC-019-05 的 30 s 预算内）；runner 的结束只在 store 拒绝之后才取（正常结束不取）。取消在 pass 与 `finish_cancel` 之间若还有别的 Attempt 在跑，Run 的 `cancel.workspace` 照旧在之后另取，那时可能已有别的 Run 的写者在工作（REQ-043 的记录语义，未改）；被取消写者自己的状态由它的 `attempt.workspace` 记下。

10. **没有 spec 的 Run：修改照常生效，交接包以 null 表示尚无 spec（CR-014，项目所有者 2026-11-10 批准）。** REQ-018 行为 5 要求修改在下一个 checkpoint 生效，没有 spec 的前提；REQ-019 行为 2、4 要求交接包含当前 spec。产品中 StartRun 不写 spec（spec 由 ProposeSpecChange/ApproveSpec 带来，属 M3），原先的 ContextHandoff 又对所有种类要求 spec，两者在无 spec 的 Run 里不能同时成立。CR-014 让 `role_change` 交接包的 `spec_sha256` 与 `spec_revision` 在 Run 尚无 spec 时同为 null（验证与任务交接包不变），REQ-019 行为 4 写明这一点。于是 checkpoint 不再因没有 spec 拒绝修改：任何职位的修改照常生效并交接，交接包如实说明尚无 spec，不编造摘要；PLAN 阶段更换 Commander 也不会卡住。此前的做法（无 spec 就以 NO_SPEC 拒绝，第 1 轮修正扩展到所有职位）是主会话的取舍，没有问过 owner，第 2 轮审查判定它使产品里任何团队修改都无法生效（M2T17R-100，high），已撤销；第 1 轮为此给 M2-T07 测试加的 spec 也已撤回，测试回到原来无 spec 的前提。
