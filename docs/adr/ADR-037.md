# ADR-037 · 局部咨询、讨论升级与净进展诊断

状态：采纳（M3-T10，2026-11-22）。依据是 CR-026 的 REQ-023、REQ-040 与 CTO 在准备清单中已采纳的 Q1–Q11。实现基线为 `8a59e4f8370185f227554d6e0e8acd6050d34dc4`；M3-T02 和 M3-T09 已合入。本文不修改锁定契约，不声明验收通过。

## 边界与事务

客户端只构造命令与读取投影；咨询语义、账本、进展判定在 `hoh-core`，HTTP 与投递适配在 `hoh-app`。不新增 shell 命令、SQL 列、协议枚举、计划字段或唤醒种类。复用 M3-T09 的投递循环与工作请求入口，不增加活桥轮询。咨询任务使用已有调度器；取消仅为任务状态 CAS，不触碰进程组或文件删除。若实现改变这些边界，该切片必须由两名互补审查者审查。

任务、预算、事件与 outbox 在单写者的同一事务内提交。消息身份和请求来源沿用现有 attempt、role_epoch、规格及候选校验；重放返回持久结果，不重复创建任务或升级事件。终态咨询结果与任务收尾同事务写 outbox；投递与 ACK 仍由 M3-T09 负责。停止或过期身份不恢复工作。

实际基线核对：M3-T09 的输入投递已合入，但 `host/runner.rs` 的运行中请求入口仍以 verifier 与 helpers 的配对为前提。S6 必须把同一入口扩展到工作职位（仅咨询消息，验证检查仍限验证者），不另建轮询；这涉及请求与 Attempt 结束的顺序，S6 按双审处理。

## 已采纳的决定

1. **争议与轮数（Q1）。** `query.payload.intent="opinion"`，`controversy_id` 必填。每条接受的 `discussion.opinion` 为一轮；`conclude` 不计轮。相同的非空 `evidence_sha` 提前以 `DISCUSSION_LIMIT` 拒绝，详情为 `no_new_evidence`。超过上限同样拒绝；提前停止和达到上限都结束该争议的意见阶段，之后即使带新证据也返回首次停止的原因，不再接受新意见。每个争议只升级一次，摘要带已接受意见的事件引用。结论由 Commander 的 `record_assumption` 保存 Decision 或 ADR 引用。Runtime 不代写决策，不因升级阻塞 Run。
2. **咨询形状（Q2）。** `intent="consult"`，`question` 必填。子 Task 为只读任务，role 为目标职位，spec 为 Run 当前规格；parent 和 deadline 保存在 `task.consult`，预算保存在 task 范围的 `budgets`。显式预算和 deadline 从载荷取得，缺省取 Run 预算的一片和 `runs.deadline_at`。子任务、预算与等待中的 query 同事务入账；结果以原请求为 correlation 回到请求方。
3. **环检测（Q3）。** 从拟加入边的发送方出发，若经接收方可回到发送方（含自等）即拒绝 `CONSULT_CYCLE`；details 按环顺序列出成员。拒绝不建子 Task、不增加等待边。QA 请求修改当前候选保持 ADR-028 的拒绝与 Issue 路径。
4. **重大决定（Q4）。** 结构化 `intent="apply"` 的 `decision_class` 为 `spec`、`adr`、`public_api` 或 `gate` 时，拒绝 `ILLEGAL_TRANSITION`，details 带该类别，并升级 Commander。自由文本不作分类器。不在升级处理前导入或派发相应工作；规格变更仍走 REQ-033 的 CR。使用已有原因码，不新增 CR。
5. **STALLED 分工（Q5）。** `no_progress` 管验证仍推进却无净进展，STALLED 管没有任何推进。在关轮事务内，若存在 `runtime:stalled` 认领或 PENDING 的 `stalled/` 触发器，则抑制 `no_progress`。未消费的 `no_progress` 已属于停滞检测的未读唤醒集合。
6. **里程碑与发布（Q6）。** 当前 spec 的全部 AC 被接受时产生 `milestone_ready`；其中 `required_release=1` 的 AC 全部被接受且没有开放 critical/high 时产生 `release_request`。没有需求行不触发。每个 spec 各一次，身份为 `child_id(run,"milestone/<spec_id>")` 与 `child_id(run,"release/<spec_id>")`。两者仍是已有 Normal 类别，产生方在关轮事务，不从规格 adopted 事件触发。
7. **结果回程（Q7）。** 子任务结束事务生成 result outbox 行，调用既有 host 投递入口，不建立第二套传输账本或第二个循环。测试既断言账本与 outbox，也通过 M3-T09 的消费与 ACK 路径检查请求方可观察的结果。
8. **失败指纹（Q8）。** 使用现有 `closing::Item::fingerprint` 与 `round_issues` 的指纹，不从提交或文件变化构造新指纹。`no_progress` 同时含排序的 `fingerprints` 数组及供监督分类使用的单数 `fingerprint`。
9. **稳定阶段（Q9）。** 纯函数输入显式携带 `release_stable`；产品在当前 spec 已产生 milestone 或 release 事件后置真。不新增 Run 状态。
10. **任务列表（Q10）。** 复用既有 OpenAPI 的自由对象 `Page.items`，返回 parent、budget、deadline、role、state、dependencies 与 lease holder。只读分页遵循现有 limit、watermark 与 404 约定，不改锁定 schema。
11. **文档候选（Q11）。** 三轮只改文档的测试同时给出重复失败指纹与不下降的 critical/high。提交数只作为测试输入，绝不进入进展向量或改变判定。

## 进展窗口与持久恢复

纯模块按三个连续验证轮次判定：accepted 不增、开放 critical/high 不降、失败指纹存在非空交集。向量仅包含新增 accepted AC、关闭 issue、重开 issue、新增 critical/high 与未消除决策风险五个分量。关闭 issue、accepted 增加或规格新增 REQ 重设窗口；只有新增 REQ 的重设必须产生 `progress.reset{reason:"规格新增 REQ",spec_revision}`。关轮时比较当前 `requirements` 的 id 集合，不把 adopted 或任意规格变更误当新增 REQ。发布稳定阶段开放 issue 总数下降同样算进展。

关轮事务保存重建窗口所需的事实，并产生 `no_progress{window:3,fingerprints,vector,last_progress_seq,suggestions,fingerprint}`。建议固定为升级、研究、改计划。去重身份为 `child_id(run,"no_progress/<last_progress_seq>/<fingerprint>")`，第四轮与重启不会再唤醒同一状况；重设后的新窗口可独立诊断。验收事实复用现有验收判定，保持规格和候选绑定，不将模型声明当 accepted。

## S6 实现细节

未显式给出预算时，子任务取得 Run 中可消费种类的剩余额度（limit−used−reserved）的十分之一；第二轮设计修正将种类限定为 wall_seconds、attempts、tokens、usd，排除 iterations。未给 deadline 时取 Run 的绝对 deadline。没有可用的 Run 额度或绝对期限时，请求须明确提供，否则拒绝创建，避免无界咨询。预算、期限与问题进入子任务的强制上下文；任务列表从同一账本投影读取这些字段。

工作角色与验证者共用已有的 `ask <message.json>` 文件桥及 host 请求循环。工作角色的上下文给出 helper 路径和进入 RUNNING 后的 Task revision；`run-check` 仍只接受冻结验证任务。咨询等待行不由普通 transport 提前 ACK；子任务结果与该等待行的结束在一个事务内提交，结果通过既有输入 outbox/receipt 路径送回父角色。有效 TaskResult 保留为结果消息，既不自动接受 AC，也不把研究者的声明变成验收事实。缺失、截断或无效 TaskResult 使用已有的有界协议纠正；耗尽、取消或身份过期有独立 Runtime 诊断，不伪造 Agent 的 TaskResult。父角色或规格已过期时不把结果送给新身份。

S6 改动了现有请求与 Attempt 结束、恢复的衔接，并复用了原有输入扫描事务。因此该切片仍须两名互补 Reviewer 审查；没有新增进程管理循环、删除路径或 Agent 传输实现。

## 首轮审查修复：讨论关闭与新诊断窗口（M3K-01、M3K-51）

选择 docs/06 的“没有新证据即停止讨论”：持久化的唯一升级事件同时是意见阶段关闭的事实。重启后读取该事件，继续拒绝新意见；Commander 的唯一摘要因此仍覆盖全部已接受意见。`conclude` 记录仍只是参与者的说明，正式结论由 Commander 的 Decision 或 ADR 引用承担（M3K-05）。

严重度下降打断连续窗口时，同时清除窗口的 reported 标志；不把严重度下降冒充关闭 issue 或 accepted 增长，不改变 last_progress_seq。重新累计三轮新指纹 G 可以产生独立诊断；同一指纹仍由既有事件身份去重。持久测试先报告 F，再下降严重度并累计 G，在第六轮之前重启；另在原 TEST-040-01 重启后关闭第五轮验证同状况不重复（M3K-02）。自测记录见 `.hoh-dev/self-tests/m3t10-fix1/`，非验收。

## 首轮审查修复：咨询预算是派发边界（M3K-50）

AC-023-01 中子任务的预算与 deadline 作为实际派发约束。缺省切片在创建子任务的同一事务里增加 Run 的 `reserved_value`，并在 `task.consult.reserved_budget` 保存该任务拥有的预留；后续请求按扣除已有预留后的余额取十分之一。请求重放不再预留。显式预算是额外的任务上限，不扩大 Run 的预算；Run gate 仍生效，但第二轮设计修正允许持有者消费自身尚未使用的预留。

自动调度与 Commander 的 dispatch 共用咨询边界：读取 task 预算的 used+reserved，达到任一限额或 `task.consult` 的绝对 deadline 后不再分配 Attempt。attempts 还计已分配的尝试；wall_seconds 在已有结束/恢复事务内累计，运行中的时间按原有 OBSERVED 截止算法计算。tokens/usd 对照持久 Attempt 的用量，无法辨认的用量或未知定价阻止后续派发，不按零计算。iterations 保持既有验证轮次账本的含义，只读咨询不伪造候选轮次。此约束在派发边界生效，不中断已经运行的进程。

已消费的 wall_seconds 从该任务的 Run 预留转为 used；咨询正常结束、取消、父身份过期或尚未派发即耗尽时释放剩余预留，保留其他任务及既有 Run 预留。原 `task.consult_finished` 保证释放一次。因预算或期限停止的待派发任务置 BLOCKED，并向父角色返回 Runtime 诊断；不会伪造 TaskResult。若取消先释放、子 Attempt 随后才结束，后者仍计实际时长，但不再次扣除其他任务的预留。

测试包括：连续两片 80→72、请求重放、使用 30 秒后释放、五种 task 账本限额与 deadline 的两条派发入口、低于限额的正对照、Attempt 实际用量、到期诊断与释放。证据见 `red-50-behavior`、`red-50-expired`、`green-50-verified` 和 `slice2-*`。初版测试夹具的类型错误单独保留为 `red-50`，不算行为红灯。

派发门的夹具单独驱动真实 Store，避免宿主扫尾在断言之间把耗尽任务结束；到期结算在另一个显式扫尾测试验证。最初的并发夹具失败保留在证据中，不当作产品缺陷或绿灯。

## 首轮审查修复：不确定投递后的结果恢复（M3K-52、M3K-53）

M3-T09 的传输规则保持：旧输入一旦跨过原生 steer 的外部效果边界而没有回执，重投仍拒绝为 UNKNOWN_DELIVERY，不把它改回 QUEUED。APPLIED 是确认应用；DELIVERED 后父 Attempt 死亡仍不是确认应用。

仅对 Runtime 已保存的咨询 result，满足以下条件才在已有扫尾事务里再生成一次上下文输入：旧输入因 UNKNOWN_DELIVERY 或 attempt_ended 被拒；旧父 Attempt 已为 FAILED/CANCELLED/UNKNOWN_EFFECT；父 Task 未取消、规格与角色 epoch 仍相同、Run 可继续。重新解析子 Attempt 的 `attempt.outputs`，核对其中的 TaskResult 与原结果一致，保留原消息身份、correlation、状态和摘要。新输入与 `task.consult_recovered` 原子提交，以子任务派生 id 去重；不再派发 researcher，不重建子 Task，不执行原生 steer，也不声称旧外部效果没有发生。

新输入仅进入同一父 Task 的下一 Attempt 提示词；同职位其他 Task 不能取走。重复扫尾和重启不再生成第二份；若这一次恢复的父 Attempt 又失败，保留拒绝历史，不递归恢复。父身份过期、父任务取消、已应用结果、仍活跃的旧父 Attempt 均不生成恢复输入。

测试在登记 PID、启动标识与 boot_id 后对自身子进程执行 SIGKILL，覆盖“暂存后未收回执”“拒绝后未恢复”“已送达而父 Attempt 未完成”；正对照/负对照覆盖已应用、过期 epoch、换规格、父任务取消、同角色另一任务和恢复次数上限。TEST-023-01 的 OBSERVED 重启用例新增 correlation、result kind、完整 TaskResult（含 status 与 summary）断言；临时把恢复摘要改坏的变异测试确实失败，变异已恢复。证据为 `red-52-mutation`、`red-53`、`green-53`、`green-53-parent-boundary` 及最终回归，自测，非验收。

预算补充：Run 的运行中时长预留扣除已经包含在咨询切片中的部分，避免把同一段时间重复计入。`test_023_01_running_default_allocation_is_not_reserved_twice` 先红后绿验证这一交互。首次 static 扫描拒绝测试的 `#[path]` 布局后，测试改为常规模块目录；扫描规则、允许清单与门禁未改。

## 第二轮设计修正：咨询预留的所有者与消费（M3K-100、M3K-101）

M3K-50 的修复把预留加入了 Run 总账，却没有区分“其他任务不可使用的额度”和“持有者已经消费的额度”。本轮先明确三个不变量，再修改准入与结束判定：

1. 缺省切片只取只读咨询能够消费的 wall_seconds、attempts、tokens、usd；iterations 属于候选验证轮次，不进入缺省子任务预算或 Run 预留。显式 task 预算仍兼容已有种类；它不预留 Run 额度，也不产生验证轮次。
2. 自动调度与 Commander dispatch 按目标任务判定 Run 预算。只有该咨询仍有效、尚未释放且尚未消费的自身预留可从本次准入计算扣除；其他咨询、既有预留、实际用量、未知价格、Run deadline 与 task 边界仍生效。扣除只是事务内的判定视图，不释放账本预留。已消费额度（包括运行中的时长与已记录的用量）不能再次作为信用使用。
3. Run 的 INCOMPLETE 与恢复检查按实际消耗判定，不因尚未消费的咨询预留结束 Run。未消费的咨询预留从结束判定视图扣除；普通任务与 Commander 的准入仍受预留保护，预算风险仍使用原视图。达到实际上限或 Run deadline 后照旧停止，不重新定义 iterations 或降低限制。

创建、消费转账与释放仍在既有事务中完成，保留 task.consult / task.consult_finished 身份和一次性释放规则。无 schema、检查计划或基线变更。回归使用真实 Store 与数据库夹具，覆盖 9/10 轮、用量达到上限减自身预留、其他预留、两条派发入口、已消费额度与重启。记录位于 `.hoh-dev/self-tests/m3t10-fix2/`，自测，非验收。

## 第二轮修复：Runtime 停止由父角色处理（M3K-102）

咨询在派发前因预算或期限停止时，仍置 BLOCKED、结清等待边、释放剩余预留，并向父角色送出一次 Runtime 诊断。移除原先额外的 AgentBlocked / need_decision 唤醒，不写 NEED_DECISION 问询标记；由父角色根据诊断决定取消子任务、改计划或升级。真实 Agent TaskResult 的 FAILED / BLOCKED / INCOMPLETE 问询不变。

诊断与 task.consult_finished 保留 reason=budget_exhausted，增加 detail=consult_deadline、consult_wall_seconds 或对应的具体边界原因。诊断保留 origin=runtime，父角色收到的文本也包含 detail。两种停止路径都验证重复扫尾只结算一次、没有额外 need_decision、没有伪造 TaskResult、预留已经释放。M3K-103 的原有无 run_id 事件查询性能问题按委派要求留给 M3 low 清理包，见 `reports/reviews/m3t10-fix2.md`。
