# ADR-035 · Readiness Gate、独立规格审查与规格收敛（M3-T06）

状态：采纳（2026-11-22；M3-T06）。设计依据：实现清单 `.hoh-dev/evidence/m3-t06-prep/inventory.md`（只读，main 8d9ae599），CTO 决定 `.hoh-dev/evidence/m3-t06-prep/cto-decisions.md`（2026-11-22：清单 §8 的推荐默认全部采纳；Q3 与 Q10 合为一份 CR-033，由 CTO 撰写并批准，切片 S2、S4 等它在 main 上 relock）。本任务提前在 main b6681e9d 上开工，早于 M3-T02（规格来源，ADR-033）合入；需要 M3-T02 代码的部分等它合入后在其上重做（见“切片与依赖”）。

需求：REQ-031（AC-031-01..05）、REQ-030（AC-030-01..03）；`contracts/development-tasks.json` 的 M3-T06 done_when。依据：CR-026 第 6 节（REQ-031、REQ-030 的细化）、第 7 节（M3-T06）、第 8 节、应用时的更正 A（会话独立承接 CR-029）；CR-029（原生会话身份）；ADR-026 决定 12（按任务范围选代码）；ADR-028、ADR-029（候选报告的收取）；ADR-031 决定 1（阶段推进）。

## 背景

产品今天没有 readiness 判定：`BlockedReason::ReadinessNotMet` 只是枚举，没有任何代码写它，也没有 `readiness.passed`、`spec_review.*` 事件。可复用的是纯计划校验 `dag::validate`、pace 的置／解 BLOCKED 写法、纯决策校验 `decision::transition_run`、候选报告的 hoh-report 抽取与原生记录，以及 CR-029 的身份收集（`persistence/reports.rs`）。结构缺口有三：开放问题没有 id 也不落库；规格修订没有 git 提交；Task 的路径范围没有载体（清单 §0）。

## 决定（清单 §8 的推荐默认，CTO 2026-11-22 采纳）

1. **开放问题的 id 与落库（Q1）。** 语法改为 `- Q-<id> <文字>` 后接 `阻塞：是|否`，id 与 REQ、AC 共用唯一 id 集；解析器输出 `questions:[{id, text, blocking, path, line}]` 与 `decisions:[{text, source_kind, source_id, path, line}]`，都不进 index.json；批准事务为新修订写项目级事件 `spec.open_questions{spec_id, spec_revision, questions}`（id `child_id(spec_id, "open_questions")`），readiness 与 Run 投影读它。ADR-033 §1 的产生式由本任务在 M3-T02 合入后修改（切片 S5）。

2. **来源真实性归本任务（Q2）。** AC-030-03 在 M3-T06，所以 ADR-033 §1 中“来源真实性归 M3-T04”改为“来源真实性归 M3-T06；批准者身份归 M3-T04”（S6）。三种来源都校验：`question_id` 须是同项目 `question.answered` 的持久化问题 id 且答复来自用户命令；`input_id` 须是同项目 Run 的 `input_queue` 行；`event_id` 须是同项目 `decision.applied{kind: record_assumption}` 事件。任一失败即 422 SPEC_INVALID，`details.unsourced` 列出条目与缺失的来源，不写 change_requests 与新修订。

3. **Task 的路径范围（Q3，CR-033）。** `$defs.PlanProposal` 的任务项增加可选 `paths: string[]`（项目相对，拒绝绝对路径、`..` 与空串，唯一）；存进 `plan.imported` 的载荷，不加 SQL 列；缺省为空范围，即没有代码类来源，也不是 readiness 原因。读者 `Reader::task_paths(task)` 供上下文选码与 M3-T07 的脏文件判定。测试名不用 `test_039_*`（REQ-039 的 TEST 已在 M2 判定）。等 CR-033 relock（S4）。

4. **SPECIFYING→READY 由 Runtime 推进（Q4）。** readiness 步骤在 Run 级判定 READY 时写 `readiness.passed{run_id, spec_revision}` 并把 Run 从 SPECIFYING 推进到 READY；Commander 提出的 transition_run 到 READY 在 readiness 通过时照常应用（已 READY 时是同状态的 ILLEGAL_TRANSITION），未通过时 REJECTED(ILLEGAL_TRANSITION)，`decision.rejected` 的载荷在 `detail` 之外加 `details{reasons}`。READY→RUNNING 仍归 Commander。这修改了 ADR-031 决定 1 中“Run 的推进仍是 Commander 的”：SPECIFYING→READY 这一步由 Runtime 判定（C5），Commander 只能补规格或计划。

5. **审查的 git 提交（Q5）。** 开审时 host 沿 `git rev-list HEAD -- docs/spec` 从新到旧最多查 100 个提交，取第一个“其 docs/spec/*.md 重新生成的索引 sha256 等于 specs.sha256，且 index.json 字节相同”的提交；找不到就不开审，写一次 `spec_review.waiting{spec_id, spec_revision, reason: "spec_not_committed"}`（按 spec 与 HEAD 去重）唤醒 Commander。

6. **起草者身份（Q6）。** 读法：`spec.drafting{task_id, spec_sha256}`；起草某修订的一方 = `spec_sha256` 等于该修订 sha256 的这些 Task，按各自的 Run 与职位取该职位的当前绑定、该 Run 中该职位全部 Task 的 Attempt（绑定历史）与该 Run 的 `session.native` 记录中属于该职位的会话，再汇入它们的全部原生身份（CR-026 应用时的更正 A；审查 M3D-01 的修复）。起草职位与审查职位相同时，审查方自己的绑定也在其中，因而不独立。M3-T04 按此写入；本任务的测试用 SQL 夹具写这个事件。用户直接编辑而没有起草 Task 的修订，起草者集合为空。

7. **收取后审查 Task 的终态（Q7）。** CURRENT 与 REJECTED 都使审查 Task 为 ACCEPTED；readiness 看报告的 state。没有 hoh-report 块时也写 `spec_review.reported{state: REJECTED, reasons: ["report_missing: …"]}`，各引用为 null。审查 Task 终结而没有 CURRENT 报告时，`due` 为同一修订再开一次（新的 review_id）；不另设次数上限，由预算（pace）与 no_progress 兜底（清单风险 R2）。

8. **spec_review 不满足时置 BLOCKED（Q8）。** 与其他原因一致：计划任务为 BLOCKED(READINESS_NOT_MET, details.reasons 含 spec_review)，审查 PASS 后由 readiness 步骤解除。

9. **决策引用的 question_id（Q9）。** 持久化的 `question_id`（decision_id，即 `question.answered.question_id`）；Commander 自己的 `commander_question_id` 不接受。

10. **basis 未列出的拒绝码（Q10，CR-033）。** `$defs.RejectionReason` 末尾加 `ASSUMPTION_NOT_LISTED`，Rust 枚举与往返测试同步；只对无人值守的 Run 校验 basis。等 CR-033 relock（S2）。

11. **`unattended` 的来源（Q11）。** StartRun 的 `interactive:false` 写进 Run 配置快照 `unattended:true`，同时写 `assumptions:{key: value}`；快照缺这个键时按交互 Run 处理（保守、向后兼容，清单风险 R6）。

## 设计

### readiness 纯函数（`hoh-core::readiness`，S1）

输入为修订（REQ 及其 release_class、AC 的 then 与 check、开放问题的 id 与阻塞标记、修订号与 sha256）、计划视图（Task 的 id、REQ、依赖）与规格审查视图（该修订最新的报告与起草者、Commander 的身份）。输出 `Ready` 或 `NotReady(reasons)`，原因按代码聚合，每个代码至多一项、带对应 id，顺序固定：

| 代码 | ids | 条件 |
| --- | --- | --- |
| `missing_ac` | REQ id | 范围内 required REQ 没有 AC；计划引用而修订中没有的 REQ 也算（在该修订中它没有 AC） |
| `unobservable` | AC id | 范围内 AC 缺 then 或 check（产品路径上 ADR-033 的语法保证二者非空，只有夹具可达） |
| `DAG_MISSING_DEPENDENCY` | 缺失的依赖 id | 计划中的依赖不在计划里 |
| `DAG_CYCLE` | 环上的 Task id | 依赖成环；环检测与 `dag::validate` 共用同一个 Kahn 纯函数 |
| `undecided` | 问题 id | 标为阻塞的开放问题；语法没有把问题链接到 REQ，所以作用于该修订的全部 Task |
| `spec_review` | 发现 id（只在 blocking_findings 时） | 规格审查不满足，`detail` 为下表之一 |

Run 级判定的范围是修订的全部 REQ 与整个计划；Task 级判定只看该 Task 的 REQ 及其依赖闭包中各 Task 的 REQ、闭包内的依赖缺失与环。

规格审查的判定顺序：没有报告→`missing`；报告的修订号或 sha256 不是该修订的→`stale_revision`；报告 REJECTED→原因含 `not_independent` 时为 `not_independent`，否则 `rejected`；审查方身份与起草者及 Commander 的身份相交→`not_independent`；FAIL→`fail`；UNKNOWN→`unknown`；PASS 且有 critical 或 high 的发现→`blocking_findings`（ids 为这些发现的 id）；否则满足。模型自报的 PASS 不覆盖它自己的发现。

### 会话身份（`hoh-core::verification::identity`，S1）

CR-029 的规则写成纯集合函数：`Identities{hoh: {HoH 会话 id}, native: {(agent, 原生 id)}}`，`shared(a, b)` 为 HoH id 的交与 (agent, 原生 id) 的交之并。类型不明的字符串（原生记录的 `session_ids` 既可能是 HoH id 也可能是原生 id）以 `claim(agent, id)` 同时记入两个命名空间。候选报告的收取（`persistence/reports.rs` 的 `judge`）改为经它求交：两侧的字符串都按 `claim` 记入，结果与原来的字符串求交逐项相同（候选路径的行为不变）。规格审查与候选报告由此共用同一原则（done_when；CR-026 应用时的更正 A）。相同的原生 id 字符串属于不同 agent 时不相交。

### 两份 schema、构造与收取（S3）

- `schema::spec_review_report()`、`schema::spec_review_attempt()` 进入产品 schema 集（`include_str!`，与既有契约同一加载方式）。把报告 schema 放进审查者上下文的 `objects::RESOURCES` 属派发（S7），那时再加，以免提前改变资源摘要。
- `verification::spec_report`（纯）：`native(...)` 构造 `runtime_spec_review_export`（status 恒为 COMPLETED，只从 COMPLETED 的 TaskResult 调用），`build(...)` 从 `report::block(final_text, "reviewer")` 的块加上 Runtime 才知道的会话、修订三项与两个 FileRef 构造报告；二者都在 schema 下校验。`check(...)` 对字节做全部与 DB 无关的核对，**收集全部原因，不短路**。
- 收取的单一入口 `Store::intake_spec_review(SpecReviewIntake{review_id, attempt_id, report, native, raw, raw_sha256})`：report 与 native 是 host 已用 `objects::put` 保存的对象（artifact 与字节，缺失为 None），raw 是原始 stdout 日志的 artifact，raw_sha256 是 host 从日志字节重算的摘要。入口读 `spec_review.opened`（review_id 不存在、Attempt 不存在、对象字节与其 artifact 的摘要不符，是调用方的完整性错误），登记给出的对象（raw 的 sha256 不等于 raw_sha256 时不登记 raw，以免登记一个摘要与日志不符的 artifact），核对后写 `spec_review.reported{review_id, spec_id, spec_revision, status, state, reasons, session_id, attempt_id, report, raw_session, native_attempt, raw_sha256}`（spec_id 与 spec_revision 取自 `spec_review.opened`，供 readiness 按修订读取；后三者为 `{path, sha256}`，缺失为 null；报告无效或缺失时 status 与 session_id 为 null），事件 id `child_id(attempt_id, "spec-review/reported")`；重放的身份是 review_id、三个对象引用与 raw_sha256：同一 Attempt 全部相同时返回原结果、不写任何东西，任一不同（改投另一个 review、换对象或换日志实算摘要）为 `KeyReuse`（审查 M3D-03 的修复）。报告中的两个 FileRef 必须分别等于给出并登记的 raw 与原生记录 artifact 的 `{path, sha256}`，raw artifact 的 sha256 必须等于 raw_sha256，否则记原因（审查 M3D-02 的修复）。不写 `independent_reports`，不开轮次，不造候选。host 只构造字节，不核对，所以 AC-031-04 替换原生记录时走的是同一入口。
- 原因的格式为 `<代码>: <说明>`，代码：`report_invalid`（报告不是 JSON 或不符合 schema）、`native_attempt_missing`、`native_attempt_invalid`、`raw_session_sha256_mismatch`、`native_attempt_sha256_mismatch`、`raw_session_ref_mismatch`（报告的 raw_session 不是给出的 raw artifact）、`native_attempt_ref_mismatch`（报告的 native_attempt 不是给出的原生记录 artifact）、`raw_session_artifact_mismatch`（raw artifact 的 sha256 不是日志实算的 raw_sha256）、`session_not_in_native_attempt`、`role_mismatch`、`review_id_mismatch`、`attempt_id_mismatch`、`spec_revision_mismatch`、`spec_sha256_mismatch`、`git_commit_mismatch`、`stdout_sha256_mismatch`、`duplicate_finding_id`、`attempt_not_of_review`、`session_unknown`、`session_mismatch`（报告的会话不是收取它的 Attempt 的会话）、`session_role_mismatch`、`not_independent`。修订三项的不符按键各记一条（报告或原生记录任一与 `spec_review.opened` 不同）。
- 会话独立的身份收集：审查方 = 报告的 HoH 会话、原生记录 `session_ids`（排除自己的 HoH id，按 `claim`）与该会话已存储的原生身份（`sessions.native_id`、`session.native` 事件，同 `session_native_history`）；起草者与 Commander 一方 = 按（Run，职位）取当前绑定、该职位 Task 的全部 Attempt 与该 Run 的 `session.native` 记录中该职位的会话，职位为该 Run 的 Commander 与 `spec.drafting` 所指各 Task 的（Run，职位）（决定 6），各取 HoH id 与它们的全部原生身份（`sessions.native_id` 与 `session.native` 事件，带各自的 agent）。
- 审查 Task 的状态推进（决定 7）随收取接线一起在 S7 做；S3 的入口只写事件。

### `[assumptions]` 与无人值守的假设（S2）

- 加载器（`hoh-core::config`）：`[assumptions]` 的键是决定类名（ASCII 小写字母、数字与下划线，非空），值是字符串或字符串数组（`Config.assumptions`，缺省空表）。`product_direction`、`scope`、`non_goals` 与未知键同一路径拒绝（`ConfigError.key` 为 `assumptions.<名>`，消息含 “unknown key”）；键名或值不合规同样带键路径拒绝（数组元素为 `assumptions.<名>[i]`）。`config/hoh.example.toml` 的空表在同一提交加入（只有注释示例），该提交上重跑 TEST-018-01。客户端 `-p` 在本地加载配置时即以 78 退出，host 的 StartRun 也按同一加载器拒绝。
- Run 配置快照：`RunTarget::Start` 带 `assumptions` 与 `unattended`（StartRun 的 `interactive: false`），在 StartRun 事务里写进 `config_snapshot_json` 的 `assumptions`（键到值）与 `unattended`（决定 11）。
- basis 校验（`decision::validate` 的 record_assumption）：`Snapshot.assumptions` 只在 record_assumption 时由 `load_snapshot` 从快照读出；快照的 `unattended` 不是 `true` 时为 `None`（交互 Run，不校验）。无人值守时 basis 必须恰为 `assumptions.<键>` 且键在快照中列出，否则 REJECTED(ASSUMPTION_NOT_LISTED)，`detail` 为说明，`Rejection.details` 为 `{basis, key, listed}`（`key` 是 basis 去掉 `assumptions.` 前缀的部分，没有该前缀时为 null），写进 `decision.rejected` 的 `details`（只在有 details 时写这个键，其余拒绝的载荷不变）。不写假设，不推进 revision。
- Commander 的角色契约加一条：无人值守只假设 `[assumptions]` 列出的键，basis 写 `assumptions.<键>`，其余提问。监督摘要还不带快照里的键（Commander 在第一次被拒的 `detail` 中看到可用的键），留作余项。
- 测试世界：脚本化 Team 的决策可用 `world::rejected` 标为“预期被拒”，其后的决策不再加一 revision（AC-030-02 A 在同一 turn 内依次提交两条假设与一个提问）。

### 计划任务的路径范围与按任务范围选代码（S4，REQ-039，CR-033）

- `PlannedTask.paths: Vec<String>`（serde 缺省空、为空时不序列化）。`dag::validate` 在 schema 解码之后、重复 id 之前检查：以 `/` 开头、含 `..` 分量的路径（空串已由 schema 的 `minLength` 拒绝；检查里也保留空串一项）使整份计划被拒（`PlanError::Invalid`，每条违例写出 Task、下标与路径），不导入任何 Task。这关闭 CR-033 的审查发现 CR33-01（schema 接受的 `paths` 曾被 serde 丢弃）。
- 存放：`plan.imported` 载荷的每个 `tasks[]` 项带 `paths`（可为空数组），不加 SQL 列。读者 `Reader::task_paths(task)`（内部 `plan::task_paths`）取该 Task 所在 Run 中最新一条 `plan.imported` 里它的 `paths`；没有则为空，供上下文与 M3-T07 的脏文件判定。
- 上下文（`persistence/context.rs::work`）：有路径范围的工作 Task 在强制范围中多一行 `路径范围：…`；没有其他代码类来源（返工的被拒候选改动文件优先）时 `Facts.code_scope = Some(paths)`。执行器在装箱时（Attempt 起点）以 `scoped_files` 读工作区 HEAD：`git ls-tree -r --full-tree HEAD -- <paths>`，按路径排序，沿用代码类的 50 个文件、每个 64 KiB 上限，在该提交上读取（不读工作树），作为任务层的 Code 条目（`Facts::add_scoped_code`）；没有提交时给出不可读的原因条目，范围内还没有文件时给出说明条目。
- readiness 的 Task 详情显示路径范围随 S5 的 `settle` 一起做。

### readiness 的产品路径（S5）

- 语法：开放问题为 `- Q-<id> <文字>` 后接 `阻塞：是|否`，id 用 REQ 的 id 产生式，与 REQ、AC 共用唯一 id 集（ADR-033 §1 已改）。`Index` 另给出 `questions()` 与 `decisions()`（带路径与行号），不进 index.json。
- 批准事务（首次与 CR 两个分支）在新修订有开放问题时，紧随 `spec.changed` 写 `spec.open_questions{spec_id, spec_revision, questions:[{id, text, blocking, path, line}]}`（id `child_id(spec_id, "open_questions")`）；没有开放问题时不写，读者按“没有”处理。
- `persistence/readiness`：修订（AC 的 then 取已索引 JSON 的 `then`，不是 JSON 的旧行取 body 本身）、计划（Run 的 `plan.imported` 列出过的 Task，REQ 取 Run 修订下的 task_requirements，依赖取 task_dependencies；Runtime 的验证与审查 Task 不在其中）与审查视图（该修订最新的 CURRENT 报告，没有则最新的 REJECTED；审查方身份取报告会话的 HoH id 与它已存储的原生身份，原生记录的 session_ids 已在收取时判定；起草者与 Commander 一方按开审的 Run 取，决定 6）。`spec_review.reported` 的载荷为此增加 `findings:[{id, severity}]`。
- 步骤 `settle`：只在 SPECIFYING、READY、RUNNING、VERIFYING 中，先在写事务之外判定，没有要改的就不开写事务（不增加写者的 Begun 点，故障注入按第 n 次写计数的测试不受影响）；有要改的再在写事务内重新判定并写。PENDING/READY 的计划 Task 不就绪即 BLOCKED(READINESS_NOT_MET)，`task.blocked{task_id, reason, spec_revision, details:{reasons, paths}}`；因它被阻塞而已就绪的回到 READY（依赖全部 ACCEPTED）或 PENDING，`task.unblocked{task_id, reason, to, spec_revision}`；SPECIFYING 的 Run 在 Run 级就绪时 CAS 到 READY 并写 `readiness.passed{run_id, spec_id, spec_revision}`（id 含 Run 的 revision）。host 每个 tick 在 pace 之后、调度轮之前调用它。
- `transition_run` 到 READY：`Snapshot.readiness` 只在该提议时装载；Run 没有采用规格时不判定（None，照旧放行，保持既有行为）。
- 投影：`getRun.projection.open_questions:[{id, text, blocking, spec_revision}]`，与可答复的 `questions` 分开。
- 夹具（清单风险 R1、R7）：world 的 `seed_spec` 同时写该修订的 CURRENT PASS 审查报告（`seed_spec_unreviewed` 不写）；stall 的两条推进到 READY 的测试加同样的报告；TEST-002-03 的脚本 Commander 在 Run 已被 Runtime 推进到 READY 时同样给出 INCOMPLETE。都是按 REQ-031 改变行为后的夹具更新，断言不变。

### 来源校验（S6）

- `persistence/spec_sources::check` 在提议与批准（REJECT 除外）的事务里、冲突核对之后、任何写入之前调用，失败为新的 `PersistError::SpecUnsourced{unsourced}`，映射为 422 `SPEC_INVALID`（不写 `spec.index_failed`，那只属解析失败）。`unsourced[]` 为 `{path, line, text, source:{kind, id}, missing: question.answered|input|record_assumption}`。
- `question_id` 须有同项目的 `question.answered`，且其 `command_id` 是 AnswerQuestion 或 SendInput 命令（决定 9：只认持久化的问题 id）；`input_id` 须是同项目 Run 的 `input_queue` 行；`event_id` 须是同项目 `decision.applied{kind: record_assumption}`。

## 不采用

- 把规格审查写进 `independent_reports`：该表的候选外键与轮次只适用于候选（CR-026 CR26D-101、-200）。
- host 侧核对规格审查（候选路径那样先在 host 校验再交 store）：测试替换原生记录时会绕开 store 的入口，拒收会变成 host 的 Correct 而不是 REJECTED。
- 收取在第一处不符就停：AC-031-04 要求 reasons 指出每一处不符。
- 把类型不明的字符串只当原生 id：会放过原生记录里出现的他人 HoH 会话 id（CR-029 之前的 M2R-001 同类缺陷）。
