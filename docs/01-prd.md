# 产品需求 PRD

规范依据：CONTRACT.md。需求 ID 的完整清单和验收映射见 `contracts/requirements.json`，本 PRD 不另建重复需求源。

## 关键用户旅程

**新产品。** 用户执行 hoh，在 Auto 或 /plan 描述目标。系统用内置规格流程识别用户、范围、交互、模块和验收；需要真正用户选择的产品决定在 Plan 对话完成。批准实施后沿用当前项目和规格版本进入开发，不退出重新输入。

**已有仓库。** 从现有 Git/构建/测试/文档建立基线，报告已有失败与脏文件。新增 feature 只补必要规格，不强迫重构已有工程。背景任务不能覆盖用户当前未提交内容。

**无人值守。** hoh -p 接收明确目标，自动检查规格、拆解、开发、QA、审查与修复。不出现交互式对话框；能依据已授权默认值决策则记录假设，关键产品意图未知则持久化阻塞原因。

**监督团队。** Workspace 展示事实摘要；用户可展开某 Agent、检查 Timeline、发 @role 查询。Commander 被重要事件唤醒，不持续空转。发生架构问题时协调研究与最小方案，变更写 ADR/CR。

**恢复交付。** SSH 断开后 attach 原 run；系统恢复已提交状态并核对外部效果，完成后交付可执行产物、文档、证据和版本清单。

## 优先级与交付口径

P0 是底座先实现顺序，P1 是完整用户体验/可靠性与发布能力，二者全部纳入 v1 最终验收。M0–M7 只是实施顺序。未完成 Web、Pi 插件或真实联调不得把交付改名为“轻量生产版”以跳过范围。

所有需求初始 NOT_IMPLEMENTED；所有验收初始 NOT_RUN。开发任务完成、模型调用结束、代码提交和需求验收是四个不同状态。

## 非功能目标

参考机器：Ubuntu VM 4 vCPU/8GiB RAM，本地 SSD，80列以上 UTF-8 终端；模型服务外部提供。下列为验收目标而非基准结论。

|维度|v1 验收要求|
|---|---|
|长任务|72小时受控运行，至少20个真实工程增量轮次，含故障恢复；原始时钟/事件证据|
|数据|每次状态+事件+投递意图事务提交；ack后的已持久化数据不因单进程崩溃丢失|
|恢复|常见进程故障被检测并进入reconcile≤30秒；不含上游模型不可用等待时间|
|交互|本地TUI输入到可见变化p95≤100ms；已落盘事件到本地UI可见p95≤500ms|
|内存|idle Rust core RSS≤150MiB；不包含Agent子进程、浏览器与OS页缓存|
|规模|一百万历史事件可分页检索；一千条活跃任务依赖可稳定调度；禁止全量加载日志|
|可达性|80/120/180列布局、中文/emoji/多行粘贴、键盘无鼠标、NO_COLOR|
|互操作|stdout JSON无诊断污染；内部协议与公开API有版本；未知字段兼容策略明确|
|可维护|版本锁、迁移、回滚、记录实际模型/工具/Prompt/Skill版本；无活跃热更新|

费用上限可配置；未知价格显示 unknown，不把预算估算伪装为账单。CPU/内存默认调度限额与模型用量分别管理。

## 需求边界示例

“支持 QA”包含真实执行测试、记录失败、复现与候选绑定，不只是显示一个 QA 状态图标。
“支持 Web”包含读写控制、冲突和断线重放，不只是静态 Dashboard。
“内置 Skill”包含可离线读取的完整规则和输入输出，不是指向需用户手动安装的链接。
“支持长任务”包含中断恢复、预算、陈旧证据和闭环，不是套 while true 反复发送继续。
