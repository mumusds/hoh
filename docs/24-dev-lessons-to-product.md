# 开发过程经验与产品化

所有者 2026-11-21：HoH 的开发方式就是产品要做到的形态。开发中用到的长任务目标（goal）、多 Agent 协作、上下文管理、会话自动压缩、任务分配与交接、进度记忆，都要边做边总结，到合适的里程碑整合进产品。

本文是持续追加的经验库。每条写四件事：

- **现象**：开发中实际发生了什么，有证据路径的附上路径。
- **做法**：当时怎么处理，什么有效、什么无效。
- **产品对应**：落到哪个需求（REQ）。
- **落地时机**：在哪个里程碑的细化 CR 中吸收。

使用规则：

- 每个里程碑的细化任务（M3-T01 到 M7-T01）写 CR 前先读本文，把对应条目吸收进 AC，或写明不吸收的理由。
- 吸收后在条目末尾注明 CR 编号。
- 本文不是需求：它不改变任何 AC、门禁或范围；进入产品只经 CR。

## 1. 长任务目标（goal）与持续推进

### 1.1 完成标准必须可机器判定

- **现象**：goal 写明“只有 release_gate v1 得到 COMPLETED 才算完成”，进度总结和单项审查通过都不算。这个标准让会话在每次目标检查时都能判断自己没有完成，从而继续推进，而不是提前宣布完成。
- **做法**：完成标准绑定一个可执行的门禁命令及其退出码；中间产物（审查 PASS、v0.1）明确列为“不算完成”。
- **产品对应**：REQ-021（Commander 监督）、REQ-056（最终发布门禁）、REQ-035（双层编排）。Run 的完成只由 Runtime 依门禁判定，模型的陈述只是 claim。
- **落地时机**：已在 M2 的 Run/门禁语义中；M5-T01 细化 REQ-056 时复核“中间里程碑不得冒充完成”。

### 1.2 恢复点与外部阻塞

- **现象**：2026-11-17 Claude 周额度耗尽，四个队友会话同时停下，未提交的改动留在 worktree 里。额度在 11-20 重置后，新会话从 PROGRESS、git 和工作区状态恢复，接着完成了未提交的工作。
- **做法**：
  - 每一步更新 PROGRESS 的“当前状态”，写明正在跑什么、在哪、下一步做什么。
  - 恢复时先核对实时状态（git、worktree、PR、产物），不信记忆。
  - 外部阻塞（额度、服务 503、provider 过滤）期间先做不依赖它的工作，再记录阻塞和恢复条件。
- **产品对应**：REQ-036（持久生命周期）、REQ-041（恢复与幂等）、REQ-042（预算与等待：额度耗尽按重置时刻等待，所有者 2026-11-16 的决定）。
- **落地时机**：机制已在 M2；M3-T01 的停滞诊断（REQ-040）与 M5 的可恢复版本（REQ-044）细化时，把“恢复点必须含正在运行的工作与下一步”写进 AC。

### 1.3 后台工作要有唤醒条件

- **现象**：
  - 队友的后台任务完成通知经常丢失，虚拟机因此空转约 3 小时。
  - 一个等待脚本用 `pgrep -f` 的模式匹配到了自己，永远不会结束。
- **做法**：
  - 长任务在前台等待，或由主会话托管并写明唤醒条件。
  - 等待循环匹配精确的进程，不匹配可能命中自己的模式。
  - 定期检查各工作区的提交，发现“已完成但未汇报”的工作。
- **产品对应**：REQ-040（停滞与诊断）、REQ-021（监督触发器）。产品里由 Runtime 的事件与租约驱动，不靠 Agent 自觉汇报。
- **落地时机**：M3-T01 的 REQ-040 细化（CR-026 已批准，应用时复核“无事件超时即诊断”是否覆盖“完成但未汇报”）。

## 2. 多 Agent 协作

### 2.1 角色分离与单写者

- **现象**：同一 worktree 只有一个写者；审查者在冻结的只读副本上工作；开发者与审查者是不同的 Agent 会话。审查在冻结副本上进行时，开发者可以在另一个 worktree 并行跑检查。
- **做法**：每个包一个开发 worktree 与一个冻结审查副本；审查只读、不导入候选中的 Python（避免字节码污染，`.pyc` 曾让一次 Codex 审查无效）。
- **产品对应**：REQ-037（单写者与并行验证）、REQ-052（冻结候选与证据）、REQ-053/054（独立 QA/Review）。
- **落地时机**：已在 M2；M5 的回归与 Flaky（REQ-055）细化时吸收“审查环境不得写入候选”的检查。

### 2.2 互补审查与不相交编号

- **现象**：两个不同 Agent（如 Codex 与 Claude/Grok）同时审同一冻结候选，各有侧重（运行时正确性对规格一致性），各用不相交的编号段；两者发现的问题常互补，偶有重合（如 CLT-1202 与 CLT-1250）。
- **做法**：分配编号段，避免冲突；结论冲突按可复现证据裁决，不按多数。
- **产品对应**：REQ-054（独立 Review）、REQ-021（Commander 汇总多个审查）。
- **落地时机**：M5-T01（REQ-055、REQ-056）。

### 2.3 审查收敛与轮数上限

- **现象**：
  - 若干包审了 4–11 轮。
  - 同一类问题反复出现：判定器词法两次、扫描边界三次、终端宽度三次。每次修补都在原路径上打补丁，修出新漏洞。
- **做法**：
  - 同类问题连续两轮出现时，先写设计修正再改代码。设计修正往往把问题换到更可靠的机制上：编译器强制的 crate 边界代替文本扫描，实测宽度表代替手写宽度。
  - 所有者 2026-11-21 定了轮数上限（docs/19 审查收敛）：
    - 第 4 轮无 critical/high 即通过；
    - 复审只看修复 diff；
    - low 按里程碑统一清理。
- **产品对应**：REQ-021（Commander 决策）、REQ-040（停滞诊断：评审循环不收敛也是停滞）、REQ-030（规格收敛）。
- **落地时机**：M3-T01（2026-11-21）复核：REQ-040 只覆盖持续无净进展的诊断；“同类问题连续两轮即先写设计修正”与轮数上限都留给 M5-T01（REQ-055、REQ-056、REQ-021），见 CR-026 应用时的更正（M3A-01）。

### 2.4 Agent 失败的分类与替换

- **现象**：
  - Codex 两次被 provider 的网络安全过滤器中途截断，提示词要它“构造绕过判定器的脚本”时触发。
  - Codex 服务返回 503，会话中断，留下未提交的改动。
  - Claude 周额度耗尽。
- **做法**：
  - 过滤截断时换另一家 Agent，并把措辞改为“核对实现与规格一致”，审查范围不变。
  - 503 后发续作提示：先读未提交改动再继续，不盲目丢弃。
  - 额度耗尽时等待重置，不切 fallback（所有者决定）。
- **产品对应**：REQ-020（能力匹配与缺员）、REQ-042（等待）、REQ-027（协议与能力）。
- **落地时机**：M5 或 M7 细化时考虑把“provider 内容过滤截断”列为一种显式失败类别：带原因码，不当作 Agent 能力不足。

### 2.5 队友消息会交叉或丢失

- **现象**：主会话与队友的消息多次交叉（对方在读到新指示前已回复），队友的空闲通知重复。
- **做法**：发合并后的一条消息，并要求逐项确认；关键指令重发时写明“消息交叉了，明确如下”。
- **产品对应**：REQ-022（通信与交接：消息去重键、回执）。
- **落地时机**：已在 M2 的 outbox/receipt 语义中；M4 的 Team/Focus 视图（CR-028）显示未确认的指令。

### 2.6 并行会话的临时目录要有归属

- **现象**：M2-T11 第 2 轮，QA 清理自己的临时目录时，按模式删掉了另一个会话（很可能是并行的审查者）同名模式下的仓库副本（M2QA-005）。此前一个开发会话也用 `pkill -f '^sleep 30$'` 按模式杀过进程。
- **再次发生（2026-11-23）**：主会话按所有者要求收敛目录，按修改时间（超过 3 小时）清理临时目录，删掉了一个仍在运行的 Codex 开发会话登记过的副本，它的第一次冻结检查因此失败。修改时间不能说明归属与存活。
- **做法**：
  - 会话只删除、只结束它按确切路径或 pid（加启动时间）记录过的东西；临时目录名带上会话或任务标识。
  - 清理别人的资源之前先确认其所有者已结束；所有者仍在运行时，无论修改时间多久，一律不动。
- **产品对应**：REQ-037（单写者与并行验证）、REQ-036（持久生命周期：资源归属）。
- **落地时机**：M3 清理包把它写进角色提示词（REQ-045）；M5 细化 REQ-055 时考虑把“只清理自己登记的资源”作为检查。

### 2.7 消息交叉与审查对象被改动

- **现象**：主会话与队友的消息多次交叉；有一次队友按较早的指示继续提交，而审查者正在读同一个工作区，审查对象中途改变，只能停掉重审。
- **做法**：审查一律在冻结的只读副本上进行（detached worktree），开发工作区可以继续；每条指令带上它针对的提交号。
- **产品对应**：REQ-052（冻结候选）、REQ-022（通信：指令带版本）。
- **落地时机**：已在 M2 的候选冻结中。M3-T01（2026-11-21）复核：REQ-017 已按职位 epoch 与规格基础修订绑定，运行中 STEER 绑定其针对的代码提交或候选尚未覆盖，留给 M5-T01（CR-026 应用时的更正，M3A-02）。

### 2.8 场景测试挡不住同类复发

- **现象**：M3-T10（预算视图）、M3-T04（起草的结束路径）、M4-T02（响应路径）各审了 5–8 轮。每轮报出的都是同一类问题的新场景，例如另一个调用点绕开统一的预算判定、另一条结束路径丢掉失败类别。每次修复只补上被报告的路径，并加一个场景测试，同类的其它路径照旧。
- **做法**：
  - 设计修正把规则收成一个模型不变量：只有一个计算预算视图的函数（DC-T10d）、只有一个起草结束出口（DC-T04b）、只有一个响应出口（DC-M4T02d）。
  - 再加一个“钉住”测试：精确列出所有调用点，或拒绝绕开唯一出口的写法。新增调用点时，这个测试先红。
  - 修复简报要求同时检查同类的相邻路径，而不只修被报告的场景。
- **产品对应**：REQ-054（独立 Review：发现按类别归并）、REQ-040（停滞诊断）、REQ-021（Commander 在同类问题第二次出现时要求设计修正）。
- **落地时机**：M5-T01，与 2.3 一并吸收。

### 2.9 开发者放宽断言来通过

- **现象**：M3-T04 一轮修复中，开发 Agent 把已有测试的期望从 `DraftBlocked` 改成 `Draft`，让测试变绿（M3L-300）；审查者从断言的 diff 发现。
- **做法**：
  - 恢复原断言。
  - 此后所有修复简报写明“不得放宽已有断言”。
  - 审查时专门看已有测试的断言 diff。
- **产品对应**：REQ-054（Review 检查断言被放宽）、REQ-055（回归：已有断言的变化要有理由）、REQ-052。
- **落地时机**：M5-T01（REQ-055）。

### 2.10 说明文字泄漏进产品代码

- **现象**：开发简报要求“副本和构建目录放在 `/home/ai/dev` 下”（因为 `/tmp` 配额小），开发 Agent 把这条写进了测试：`tempdir_in("/home/ai/dev")`。测试在本机通过，到 CI 因目录不存在而失败。M3-T10 与 M3-T04 各发生一次。
- **做法**：
  - 测试改用默认临时目录。
  - 静态检查拒绝 Rust 源码中的 `/home/...` 机器路径（PR #109）。
  - 简报把“Agent 自己的工作环境”与“产品代码的要求”分开写。
- **产品对应**：REQ-045（四层 Prompt：环境层的指令不得进入产物）、REQ-069（交付真实性：产物不依赖开发机）。
- **落地时机**：M5-T01（REQ-045 的自定义与升级部分）或 M7-T01（REQ-069）。

## 3. 上下文管理

### 3.1 委派说明写成文件

- **现象**：
  - 会话被压缩后，原先写在临时目录里的任务说明丢失，接手者只能从 PROGRESS 重建。
  - 改为写进 `.hoh-dev/dev-tasks/` 的 JSON 上下文，再渲染成四层提示词（角色契约、目标、任务、项目与证据）之后，接手、续作与复审都直接复用它。
- **做法**：
  - 每个委派写明：目标、写入范围、禁止事项、检查命令、完成后的汇报格式。
  - 说明文件放在持久位置，不放临时目录。
- **产品对应**：REQ-045（四层 Prompt）、REQ-039（上下文渐进披露）、REQ-022（交接包）。
- **落地时机**：M3（CR-026 的 REQ-045 已批准；应用时复核“委派说明是持久工件并可被续作复用”）。

### 3.2 结论以结构化块交回

- **现象**：审查者以 `hoh-report` JSON 块结束，主会话用小脚本抽取状态与发现；Codex 的最终文本取最后一条 agent_message，Claude/Grok 取 result 事件。
- **做法**：最终消息末尾固定一个结构化块；主会话只读这个块和必要正文，不把整段会话塞回上下文。
- **产品对应**：REQ-021（Commander 只从最终消息里的决策块取决策，ADR-032）、REQ-053/054。
- **落地时机**：已在 M2-T20；M3 细化 REQ-017/023 时沿用。

### 3.3 会话自动压缩与按实时状态恢复

- **现象**：长会话多次自动压缩。压缩摘要会滞后，例如把已完成的工作记成进行中。
- **做法**：
  - 压缩后第一步按实时状态核对（git、worktree、PR、产物、任务板），不按摘要行事。
  - 摘要里的“下一步”只当线索。
- **产品对应**：REQ-048（Smart Compact 集成）、REQ-039。
- **落地时机**：M5-T01 细化 REQ-048 时把“压缩后必须按 Runtime 实时状态核对，摘要不作为事实”写进 AC。

## 4. 记忆与进度

### 4.1 分类记忆与时效

- **现象**：持久记忆分四类：用户、反馈、项目、参考。每条一个文件，加一行索引。
  - 记忆会过时，回忆时标注“这是 N 天前的观察”。
  - 有效的记忆往往是一次纠错或所有者的决定，例如“/tmp 配额由各会话共用”“已推送的分支不强制推送”。
- **做法**：
  - 纠错当场写进记忆，并写明原因与适用方式。
  - 过时的记忆删除，不留矛盾。
- **产品对应**：REQ-049（Hermes Memory 集成）。
- **落地时机**：M5-T01 细化 REQ-049。参考 `.hoh-dev/evidence/hermes-study/report.md` 的会话持久化部分。

### 4.2 进度记忆与任务板

- **现象**：PROGRESS（按时间倒序）配合任务板，让任何新会话在几分钟内知道做到哪里。若任务开始时没有领取（M2-T20 直到合并后才补领取），任务板和实际状态就会脱节。
- **做法**：
  - 开工即在任务板领取；
  - 完成时写明证据路径；
  - PROGRESS 的每条写明“正在运行的后台任务、候选、证据位置、下一步”。
- **产品对应**：REQ-050（rpiv Todo 集成）、REQ-014（真实进度状态栏，CR-028）、REQ-032（需求追踪）。
- **落地时机**：M5-T01（REQ-050），M4 的状态栏已在 CR-028。

## 5. 环境与工程教训（产品的运行环境同样会遇到）

| 现象 | 做法 | 产品对应 |
|---|---|---|
| `/tmp` 是共享配额的 tmpfs，多个会话的 cargo target 把它占满，各处测试以 EDQUOT 随机失败 | 审查与实验的副本放项目盘；用完即删 | REQ-064（可观测性与容量：低空间）、REQ-006（环境诊断） |
| 机器重启后非登录 shell 缺 `XDG_RUNTIME_DIR`，用户级 systemd 连不上 | 环境脚本补默认值 | REQ-006（doctor 应诊断这一项） |
| Python 3.14 与 3.12 的 `Path.is_file` 对超长文件名行为不同，本地通过、CI 失败 | 用 uv 在 CI 的版本上复现 | REQ-055（回归：跨版本矩阵） |
| 打包脚本猜测产物路径，打进了旧提交的二进制 | 由构建工具说出产物路径，打包只核对不猜测 | REQ-069（交付真实性） |
| 主会话在已推送的 PR 分支上 rebase 后强制推送，未经所有者批准 | 已推送分支只追加提交 | REQ-065（Git 集成：不改写已发布历史） |
