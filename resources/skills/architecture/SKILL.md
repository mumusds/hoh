# 架构设计

## 何时使用
- Standard/Full规格准备；新增模块或跨模块数据流；引入或替换依赖。
- 独立评审指出状态所有权不清、错误边界缺失或依赖成环。

## 输入
- REQ/AC、领域模型（domain-modeling产出）、已采纳ADR、研究记录。
- 固定约束（见CONTRACT）：Rust模块化单体、Tokio、SQLite、本地Git、Ratatui/Crossterm、Axum、TypeScript/React Web；原生Agent优先；不加微服务、消息队列、向量数据库或另一全局编排框架。

## 步骤
1. 约束表：区分不可偏离决定（写出处）与本次可选项。
2. 上下文边界：外部参与者（原生Agent CLI、Git、文件系统、TUI/Web客户端、插件）及交互协议。
3. 模块划分：每个模块写职责、输入/输出、拥有的状态、依赖；依赖方向由适配器与UI指向领域核心，禁止环。
4. 关键旅程数据流：每条旅程至少一条成功路径与一条失败路径（取消、超时、崩溃恢复、外部429/503）。
5. 状态所有者与事务：每类状态唯一写者；UI与日志只是投影；外部效果经effect ledger核对。
6. 错误与资源：错误分类（可重试/永久/未知效果）、取消传播（进程组信号+wait）、超时、背压，以及子进程、文件、锁的释放时机。
7. 备选比较：每个重要选择列2–3个最少必要方案（含“沿用现有组件”），按正确性、可恢复性、复杂度、可测性比较，写ADR。
8. 可测性：为外部适配器留fake/fixture接缝；列出验证设计的测试（单元/属性/集成/PTY/Web/live）与故障注入点。
9. 自检：
   - [ ] 每个REQ都能落到具体模块
   - [ ] 没有状态被两个模块写入
   - [ ] 每个外部调用都有超时、取消与错误映射
   - [ ] 模块依赖无环
   - [ ] 没有使用未经核验的CLI参数或配置键
   - [ ] 改变固定决定之处都有CR

## 产出物与格式
- `resources/templates/architecture.md`：上下文与约束、模块职责与依赖、运行时与数据流、状态所有者与事务、错误/恢复/资源生命周期、技术取舍ADR、可测性与演化。
- 每个重要选择一份 `resources/templates/adr.md`。
- TaskResult：evidence引用文档与ADR；issues列未决选择与风险；candidate_id通常为null。

## 完成判据
- 自检全部满足；验证计划可直接转为任务与测试。
- 评审者仅凭文档即可回答“这个状态谁写入、失败后如何恢复、如何测试”。

## 常见错误
- 为展示方便把状态放进UI或客户端。
- 因角色多而拆分服务或进程，或自造第四个Coding Agent。
- 只画成功路径，不写取消、超时与崩溃。
- 照抄未经核验的CLI参数或插件配置键。
- 架构文档没有验证计划，或悄悄推翻已有ADR。
