# 局部咨询与事实研究

## 何时使用
- Developer、CTO 或 Commander 发来 query（局部咨询，REQ-023）：接口行为、版本差异、库的用法、失败原因的外部线索。
- 规格细化或 readiness 前需要核实原生 CLI、插件或依赖的真实能力（docs/16 的事实核验）。
- 修复陷入僵局，需要独立视角查找根因线索。

## 输入（按顺序读取）
1. 问题本身：要回答什么、为谁回答、回答会影响哪个决定，以及时间与预算上限。
2. 相关 REQ/AC 与已有决定（decisions、ADR），避免重复研究已采纳的结论。
3. 环境事实：已安装版本（`--version`、lock 文件）、可用的认证与网络。
4. 最后才读请求方的猜测或已有结论，防止确认偏差。

## 步骤
1. 把问题改写成一到三个可判定的子问题，写明“回答到什么程度算够”。
2. 按来源优先级取证：已安装版本的源码与 `--help` > 官方文档与发布说明（对应版本）> 上游仓库的 issue/commit > 二手资料。每条都记版本、路径或 URL、commit 与查阅日期。
3. 需要实验时，在临时目录用最小复现验证，保存命令、输出与退出码；不在被测仓库里写文件，不调用会产生费用的 live 接口，除非任务明确授权。
4. 把结论分成四类：事实（有来源）、观察（本次实验）、判断（推理，写明依据）、未知（写明缺什么才能确认）。
5. 有冲突的来源全部列出，并说明采用哪个以及原因。
6. 回答原问题，给出对请求方决定的影响和建议；不替请求方实施修改。

## 产出物与格式
- TaskResult（`contracts/protocol.schema.json`）：status、summary（直接回答问题），evidence 引用研究记录与实验日志。
- 研究记录：每条结论含 `claim`、`kind`（fact/observation/assessment/unknown）、`sources`（版本、路径或 URL、commit、日期）、`confidence`（high/medium/low）与 `applies_to`（适用版本或条件）。
- 需要跨任务保留的结论交给 Commander 写入知识库，并保留引用与适用条件。

## 完成判据
- 每个子问题都有结论或明确的“未知 + 缺项”。
- 每条事实都有可复核的来源；每条观察都有原始输出。
- 没有修改产品源码、配置或台账。

## 常见错误
- 凭记忆回答版本相关的问题，或引用与已安装版本不符的文档。
- 把一次实验的结果说成普遍规律，或把判断写成事实。
- 研究范围失控：回答了没被问的问题，却没有回答原问题。
- 顺手修改代码或配置“验证一下”。
