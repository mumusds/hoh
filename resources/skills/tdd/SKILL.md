# 测试驱动开发

## 何时使用
- 任何生产行为的新增或修改；缺陷修复（先用测试复现缺陷）。
- 纯文档改动不适用，但文档中的命令仍需实际执行验证。

## 输入
- 范围内AC（Given/When/Then与TEST ID）；待修复issue的复现步骤。
- 现有测试布局与命令约定；哪些外部依赖在当前环境可用（认证、网络、插件）。

## 步骤
0. 基线：运行相关现有测试并保存记录；既有失败登记为issue，不在本循环中掩盖。
1. 行为清单：把每条AC拆成测试用例——成功、错误、边界、取消/重试/恢复；用例名或注释映射AC/TEST id。
2. 红（RED）：只写一个用例，然后运行它。
   - 确认它失败，并阅读失败输出，确认原因正是“期望行为缺失”（断言值不符、返回的错误类型不符等）。
   - 以下不算有效红灯，需先修正测试再重跑：编译或拼写错误、fixture/路径错误、环境缺失、测试未被发现（实际运行了0个测试）、超时。
   - 意外通过：要么行为已存在，要么断言写错；检查断言，必要时临时破坏实现确认测试能失败，随后恢复。
   - 保存红灯记录：命令、退出码、失败断言摘要。
3. 绿（GREEN）：写让该用例通过的最小生产代码；先运行该用例，再运行同模块相关测试。
4. 重构（REFACTOR）：在全绿下改善命名、重复与结构，不改变行为；每次重构后重跑。
5. 回到第2步处理下一个用例，直到行为清单完成。
6. 回归：运行影响闭包内的测试；影响不确定时跑完整套件；保存绿灯记录。

## 测试质量检查
- [ ] 断言可观察行为，而不是内部实现细节或“没有panic”
- [ ] 确定性：固定随机种子、注入时钟，不依赖sleep与执行顺序
- [ ] 隔离：使用临时目录与独立数据库，不读写用户真实配置
- [ ] 不mock被测单元本身；外部依赖用fake/fixture，并在名称或标签上标明mock
- [ ] 需要真实认证或网络的用例归入live组并可单独运行；不可用时以带原因的skip/ignore标出（Rust可用 `#[ignore = "原因"]`），结果记NOT_RUN，不计PASS
- [ ] 不变量类逻辑（排序、去重、状态机、重放）考虑属性测试
- [ ] 没有无断言测试、恒真断言或只打印输出的测试

## 产出物与格式
- 测试代码与生产代码（同一commit或相邻commit）。
- 检查计划：新测试需要独立检查时，在检查计划（`contracts/check-plan.schema.json`）中追加条目（argv、mode、cwd、产物）；不删改既有检查。
- 执行记录：冻结候选上的检查用 `contracts/execution.schema.json` 记录（自举期由 `tools/run_check.py` 按检查计划执行生成，参数以其 `--help` 为准）；冻结之前的红灯记录至少保存命令、退出码与输出文件路径。
- AC→测试映射表，写入TaskResult.summary或单独的证据工件。

## 完成判据
- 每个范围内AC至少有一个测试，被观察到因正确原因失败、随后通过。
- 相关回归全绿；或失败已作为issue记录，并说明是否为既有失败。
- 所有skip/ignore都有原因，且被归为NOT_RUN。

## 常见错误
- 先写实现再补测试，却声称TDD。
- 没运行红灯，或没看失败原因（实际上是编译失败）。
- 把测试期望改成当前的错误行为来“修复”。
- 为了绿灯删除、跳过或弱化既有测试。
- 用mock结果冒充live验证。
